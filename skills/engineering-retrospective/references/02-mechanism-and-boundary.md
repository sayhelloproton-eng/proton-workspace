# Mechanism and Boundary

## 从事件抽象到经验

高质量工程经验不是把项目名删掉以后换成几个抽象词，而是保留**真正决定结果的机制**，同时剥离偶然实现。

推荐用六步链条检查：

```text
Event → Assumption/Gap → Mechanism → Action → Boundary → Falsifier
```

### Event

具体目标、现象、影响、修复和验证。这里允许保留项目名、接口名和错误码。

### Assumption / Gap

原先相信了什么，或者漏掉了哪条责任/约束？这是经验为何存在的起点。

### Mechanism

寻找真正影响结果的结构，例如状态 ownership、持久化与后续 side effect 的分离、权限边界、信息缺失、调用顺序、恢复路径、可观察性或工具能力边界。

### Action

把机制转化成下一次可执行的动作：设计检查、测试、验收条件、恢复策略、工具路由或停止规则。

### Boundary

说明生命周期、风险、可逆性、信任程度、可观测性、外部依赖等条件。经验不是越“通用”越好。

### Falsifier

至少回答一次：出现什么新证据时，这条经验应该被缩小、修改或废弃？

## 抽象质量测试

- **Transfer**：换一个项目或技术栈，机制仍能帮助判断。
- **Mechanism**：解释了为什么，不只是说某实现“好/坏”。
- **Actionability**：下一次能据此做一个明确动作。
- **Boundary**：能说出至少一个不适用场景。
- **Counterexample**：知道什么证据会推翻或修订它。

## 例子

太具体：

> ProFlow 某次 `completeNode` 后没有唤醒 Test。

太泛：

> 分布式系统要注意状态一致性。

更有用：

> 当持久状态提交和后续调度属于两个独立 side effect 时，不能把“状态已写入”当作“调度已交接”；需要 durable continuation 或可恢复的调度 ownership，并用重启/重复触发场景验证恢复能力。

这条经验仍应保留原事件入口，未来才能判断新的场景是否真的同构。
