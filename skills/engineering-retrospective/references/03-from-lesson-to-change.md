# From Lesson to Change

## 经验不是自动规则

Retrospective 负责发现和提炼候选经验，不拥有正式工程规则的修改权。

一次经验完成后，先判断它应该停在哪里：

- **只保留经验记录**：机制有价值，但证据还不足以改变公共规则；
- **补测试/验收建议**：经验暴露的是可验证 correctness gap；
- **Skill 改进建议**：缺的是 Agent 的判断、触发、停止条件或工作方法；
- **Tool 改进建议**：缺的是可执行能力、参数、输出或真实事实获取；
- **Automation 改进建议**：缺的是重复、确定性的机械工作流；
- **项目规则建议**：结论只在某个项目边界内成立；
- **正式知识文章候选**：经验已经成熟，值得对外解释机制、证据和边界。

## Promotion evidence

下列信号会提高“应该正式改变某项能力”的置信度：

- 同一机制跨任务或跨项目重复出现；
- 用户多次指出同一种遗漏或错误动作；
- 新规则能够被明确测试或验收；
- 新做法已经在至少一次真实任务中验证有效；
- 旧规则与当前工具/API/运行时事实已经明确冲突。

但任何 promotion 都必须保留反例和适用边界。重复三次也不能把启发式自动升级成安全不变量。

## Separation of concerns

```text
Retrospective
  → 发现经验、解释机制、提出候选改变

独立 Engineering Decision
  → 修改 Skill / Tool / Automation / Test / Project rule
  → 执行真实验证
```

这样可以让 Chat 在工作结束后主动思考，又不会因为一次局部事件自动污染长期规则。

## Persistence and permissions

是否把经验写入文件，由当前宿主和任务授权决定。本 Skill 本身不授予写文件、Git、发布、外部 API 或配置修改权限。

如果当前任务没有落盘授权，可以只返回一份候选经验；如果已经授权沉淀，则写入当前任务指定的位置。不要为了“自动学习”绕过宿主权限。
