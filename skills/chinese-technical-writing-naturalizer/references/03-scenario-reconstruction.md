# Scenario Reconstruction

## 什么时候需要重建场景

当文章像术语卡片、定义集合或抽象总结时，先找真实工程问题，而不是先润色句子。

如果已有证据支持，可以沿着下面的因果链重建：

```text
某个角色需要在一个约束下完成目标
→ 简单方案一开始为什么可行
→ 具体失败、上限或新需求出现
→ 新机制改变了责任、状态或信息流
→ 得到什么收益，同时新增什么成本
→ 哪些条件下不应该使用
```

这不是固定模板。只保留当前文章真正需要的环节。

## 定义放在需要的位置

不要在文章开头一次性解释所有名词。读者第一次需要某个概念才能继续理解时，再给出最小充分定义；后续通过真实机制和例子加深理解。

## 例子优先承担区别

两个概念容易混淆时，优先给出一个能导致不同工程结果的例子，而不是连续写三次抽象定义。

例如要解释 Runtime 与 Harness，可以围绕“模型调用成功但任务为什么仍可能不可恢复”展开，让状态、恢复、工具、治理责任自然出现，而不是先写两段百科定义。

## 不得伪造真实感

没有来源的场景不能写成“我们线上曾经……”“某客户发现……”“生产数据表明……”。可以写“假设一个任务……”或“例如在下面的示意场景中……”，并保持其示意性质。
