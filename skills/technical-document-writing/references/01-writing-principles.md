# Writing Principles

## 1. 读者任务优先于文档类型

技术文档不是作者知识清单，也不是模板填空。写之前先回答：读者是谁、为什么点开、读完以后要理解什么、判断什么或做什么。结构应降低这个任务的理解成本，而不是证明作者“写得很完整”。

## 2. 一篇文档要有主问题，但不必只有一种内容形状

核心问题用于防止文章失焦，不代表全文只能用一种结构。可以根据真实关系组合：

- **因果**：为什么会出现这个问题，什么机制导致什么结果；
- **机制**：组件、责任、输入输出、状态和控制边界怎样配合；
- **比较**：多个方案、状态或能力在哪些维度不同；
- **演进**：旧方案为什么失效，关键转折是什么，现在为什么变成这样；
- **流程 / 时序**：谁先做什么，失败和恢复路径在哪里；
- **权衡**：得到什么，同时付出什么成本，什么时候不值得用。

这些是信息关系，不是文档分类。不要因为识别出一种关系就套固定目录。

## 3. 先整体，后局部

复杂文章通常先让读者知道范围、当前结论和系统处在哪一层，再进入细节。不要让读者读到一半才发现前面讨论的是目标设计，而不是当前实现。

对于长文，允许渐进披露：先给足以建立心智模型的信息，再展开机制、证据、例外和实现细节。渐进披露不是“先写空摘要再重复全文”。

## 4. 丰富是信息维度，不是字数

正式知识文章不以篇幅长短衡量丰富度。材料允许时，应围绕核心问题保留真正有判断价值的多个维度：

- 背景 / 问题与为什么值得解决；
- 真实场景和约束；
- 核心判断与关键决策；
- 机制、责任、输入输出和状态变化；
- 关键技术细节；
- 真实例子、输入输出或反例；
- 失败路径、例外和适用边界；
- 验证、结果和证据；
- 演进、复盘与进一步思考。

这不是固定章节清单。没有材料的维度不能硬编；已经存在的关键维度也不能为了“简洁”全部压掉。几个标题、几个 bullet 和一句总结通常不等于高密度内容。

## 5. 歧义就是缺陷

能被两种合理方式理解的状态、责任、边界和结论，应主动消歧。尤其注意：

- 当前 vs 目标；
- 已验证 vs 推测；
- 系统能力 vs 单次实验结果；
- 模型能力 vs Runtime / Harness 提供的能力；
- 调用成功 vs 业务目标完成；
- 局部 workaround vs 正式系统能力。

## 6. 写清主体、动作和状态变化

优先说明“谁在什么约束下做了什么，改变了什么状态，结果如何”。

“完成治理”“实现优化”“提升可靠性”“支持自动化”如果没有责任主体、机制和可观察结果，信息通常不够。

## 7. 定义在第一次真正需要时出现

不要在开头堆术语表。首次出现一个会阻碍理解的术语时，用最短解释建立共同语义；后文保持同一名称。熟悉读者不需要被基础定义打断，陌生读者也不应被迫跳到另一篇文档才能读懂当前关键段落。

## 8. 例子要证明东西

例子应该承担至少一种作用：证明概念差异、展示真实输入输出、暴露失败条件、说明边界或把抽象机制落到实际场景。

不要为了“好懂”虚构生产事故、客户、指标或个人经历。假设场景必须明确标记为假设。

## 9. 形式也要服从信息关系

形式丰富不是视觉装饰，而是为不同信息关系选择更合适的载体：

- **正常段落**：连续因果、解释、判断和论证；
- **表格**：精确横向比较、职责映射、参数与状态对照；
- **真实代码 / 命令 / 配置 / Schema / 输入输出**：说明实现边界或承担事实证据；
- **等宽文本图**：架构、流程、时序、状态、依赖、层级和拓扑；
- **正式图片**：首页总览、复杂全景或文本图明显不足以承载的视觉关系；
- **列表**：并列项、步骤和短检查项。

等宽文本图优先放在 fenced code block 中，使用空格、ASCII / Unicode 线条、箭头和短标签保持结构。它应该在纯 Markdown 中可读、可 Git diff、可持续修改，不依赖专有绘图格式才能理解。

如果一段文字正在描述多个组件之间的关系、多步骤流程、多角色交互、状态变化或拓扑结构，应主动判断表格或图是否能显著减少理解成本；能，就使用。不要求每篇文章强制出现每种形式。

## 10. 可扫描不等于碎片化

标题应该让读者扫描出论证路径。标题之间仍要有完整解释和自然过渡。一个章节如果只有标题、三个 bullet 和一句口号，通常不是“高密度”，而是解释被删掉了。

## 11. 图表不是正式感装饰

图、表、代码块和图片必须承担信息功能。不要为了显得“丰富”重复正文已经表达清楚的事实，也不要为了视觉效果把关键解释藏进一张无法检索和维护的图片里。

同一事实如果正文已经足够清楚，可以不画图；反之，如果一张简洁的文本图能替代两三段关系说明，就应该优先画图。

## 12. 尊重读者的追问路径

好的技术文档不需要提前回答所有问题，但它应该让下一层追问有入口。读者问“真的做了吗、为什么这样设计、替代方案是什么、失败过什么、怎么验证、边界在哪里”时，正文应能继续指向真实证据和更深机制，而不是只留下宣传式结论。
