# Review Checklist

这份检查表用于完成正文后的最后一轮审阅。不是所有条目都要变成文章章节。

## Reader

- 读者能在开头较快知道本文讨论什么、为什么值得继续读吗？
- 读完后应该形成的判断或理解是否真的被正文支持？
- 文章是否假设了读者不可能知道的隐藏上下文？

## Truth

- 当前实现、已接受决定、未来目标和推断是否分开？
- 每个关键结论是否有证据，或者明确写出证据缺口？
- 外部产品 / API / 版本事实是否足够新，并优先来自一手来源？
- 代码、命令、接口和数字有没有被为了“好看”而悄悄改写？

## Structure

- 章节顺序是否反映真实逻辑，而不是套模板？
- 是否有某个章节删掉后完全不影响读者理解？如果有，考虑删除。
- 是否有两个章节其实在重复同一个判断？
- 是否先建立了整体心智模型，再进入需要的细节？
- 标题能帮助扫描，但正文是否仍保持完整解释？

## Information depth

- 材料允许时，正文是否覆盖了理解核心问题所需的多个信息维度，而不是只留下结论和摘要？
- 背景 / 问题、真实场景、判断、机制、技术细节、例子、失败 / 边界、证据 / 结果、演进中，哪些是真正相关但被误删的？
- 是否为了“简洁”把能支撑追问的机制、反例、失败路径或证据一起压掉了？
- 是否存在为了“丰富”而硬凑的空章节、重复信息或无证据内容？

## Engineering depth

- 文章是否只说“做了什么”，却没有解释机制？
- 责任、输入输出、状态变化、失败路径和边界是否足够清楚？
- 权衡有没有写出来，还是只有方案优点？
- 单次实验结果有没有被扩大成系统能力？

## Representation

- 正常段落、表格、列表、代码 / 命令 / 配置、等宽文本图和正式图片是否按信息关系选择，而不是全文只有一种形状？
- 架构、流程、时序、状态、依赖、层级或拓扑如果用文本图明显更快理解，是否已经画出来？
- 文本图在等宽代码块中是否仍能靠空格、连线、箭头和短标签独立读懂？
- 图表是否真的降低理解成本，而不是重复正文或制造“正式感”？
- 关键事实是否仍存在可检索的文字表达，而不是只埋在图片里？

## Expression

- 术语是否在第一次真正需要时解释，并保持同名？
- 例子是否承担解释或证明作用？
- 是否存在大段空泛评价、宣传词、重复总结或无意义过渡？
- 是否自然、具体、像工程记录和知识沉淀，而不是模板化汇报？

## Public knowledge / external reader pass

当文档属于个人知识库、公开知识沉淀、作品展示或项目介绍时，再问一次：

- 一个不了解隐藏上下文的技术读者能否先建立整体心智模型？
- 能否看懂哪些是我的实践和判断，哪些是系统事实，哪些是外部背景知识？
- 如果继续追问“为什么、怎么实现、怎么验证、哪里失败过、边界是什么”，正文是否留下真实入口？
- 文章是否首先像一篇可以持续学习、总结和沉淀的知识文档，而不是为了某一种外部场景临时拼出的展示稿？

公开可读性是结果，不要求正文反复出现特定受众身份或求职语境。
