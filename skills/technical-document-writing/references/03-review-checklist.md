# Review Checklist

这份检查表用于完成正文后的最后一轮审阅。不是所有条目都要变成文章章节。

## Reader

- 读者能在开头较快知道本文讨论什么、为什么值得继续读吗？
- 读完后应该形成的判断或理解是否真的被正文支持？
- 文章是否假设了读者不可能知道的隐藏上下文？

## Truth

- 当前实现、已接受决定、未来目标和推断是否分开？
- 每个关键结论是否有证据，或者明确写出证据缺口？
- 外部产品 / API / 版本事实是否足够新，并优先来自一手来源？
- 代码、命令、接口和数字有没有被为了“好看”而悄悄改写？

## Structure

- 章节顺序是否反映真实逻辑，而不是套模板？
- 是否有某个章节删掉后完全不影响读者理解？如果有，考虑删除。
- 是否有两个章节其实在重复同一个判断？
- 是否先建立了整体心智模型，再进入需要的细节？
- 标题能帮助扫描，但正文是否仍保持完整解释？

## Engineering depth

- 文章是否只说“做了什么”，却没有解释机制？
- 责任、输入输出、状态变化、失败路径和边界是否足够清楚？
- 权衡有没有写出来，还是只有方案优点？
- 单次实验结果有没有被扩大成系统能力？

## Expression

- 术语是否在第一次真正需要时解释，并保持同名？
- 例子是否承担解释或证明作用？
- 表格、图、列表是否确实降低理解成本？
- 是否存在大段空泛评价、宣传词、重复总结或无意义过渡？

## External interviewer pass

当文档属于公开知识库、作品展示或项目介绍时，再问一次：

- 面试官能否看出“你具体做了什么”？
- 能否看出技术深度，而不是只看到技术名词？
- 能否区分你的判断、系统事实和外部背景知识？
- 如果继续追问“为什么、怎么验证、哪里失败过、边界是什么”，正文是否留下了真实证据入口？

这一步服务公开能力展示；普通内部文档不需要为了面试场景强行加入这些内容。
