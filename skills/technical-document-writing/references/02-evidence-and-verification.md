# Evidence and Verification

## 1. 文档不能比事实源更“确定”

写作不会创造事实。源材料如果只支持“观察到”“推测”“计划”“一次实验通过”，正文就不能升级成“系统已经稳定支持”。

遇到证据冲突时先保留冲突，不要通过润色把冲突抹平。

## 2. 根据事实类型选择最近的权威源

描述本地工程实现时，通常优先级是：

```text
当前运行 / 测试 / CLI 结果
→ 当前源码和配置
→ 当前仓库内仍有效的正式约束
→ 历史文档和聊天材料
```

描述外部产品、API、标准或版本行为时，优先当前一手文档和官方发布信息；二手文章适合补充解释，不应覆盖一手事实。

优先级不是机械规则。如果运行结果只证明一个实例，而源码合同定义的是更大的语义边界，要在正文中分别说明。

## 3. 重要 claim 要靠近证据

证据应尽可能出现在它支撑的判断附近，例如：

- 代码路径、接口或配置；
- 测试名称和结果；
- 真实请求 / 响应或运行状态；
- benchmark / Eval 结果和测试条件；
- 外部一手来源链接。

不要在文末堆一页“参考资料”，却不说明哪条来源支撑哪句话。

## 4. 区分 claim 强度

常见强度至少包括：

- **verified fact**：已有直接证据；
- **accepted decision**：已经决定，但不等于实现完成；
- **inference**：根据证据推导出的判断；
- **hypothesis**：需要进一步验证；
- **recommendation**：建议怎么做；
- **future plan**：未来动作或目标。

正文不一定要逐句贴标签，但不能让不同强度混在一起。

## 5. 代码、命令和配置要知道自己是哪一种

如果代码片段、命令或配置用于证明“现在就是这样工作”，在可用环境里应尽量从真实源读取或真实执行。无法验证时，应明确它是示意、伪代码或待验证命令。

不要为了文档整洁擅自改写真实命令的参数、路径、大小写或返回值。

## 6. 数字必须带上下文

延迟、吞吐、成功率、数量和时间等数字如果承担判断依据，应说明必要条件，例如版本、样本、并发、数据集、环境或时间范围。没有条件的精确数字很容易形成假的确定性。

## 7. 截图和图不是事实真源的替代品

截图可以证明某个时刻看到了什么，但通常不能单独证明系统合同、长期稳定性或根因。架构图也只是解释载体；如果图和当前实现冲突，以权威实现证据为准，并修正文档。

## 8. 找不到证据时写缺口

“当前没有足够证据确认 X”比补一个看似合理的结论更专业。缺口可以附带下一步验证方法，但不要把验证计划写成验证结果。
