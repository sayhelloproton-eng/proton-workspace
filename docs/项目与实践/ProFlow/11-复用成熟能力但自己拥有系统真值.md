# ProFlow｜复用成熟能力，但自己拥有系统真值

> 状态：ACTIVE_RESEARCH
> 主题：Buy / Build / Wrap / Delete 的真实边界
> 核心问题：ProFlow 为什么大量复用 ChatGPT、Custom GPT、Actions、Microsoft Dev Tunnel、OpenAI-compatible API、MCP 等成熟能力，却仍然自研 Task、Execution、Gateway、Browser Reality 和 Module Governance？

## 1. 这不是“能买就买，不能买就造”

ProFlow 的真实判断标准更接近：

```text
外部能力已经成熟
+ 不承载 ProFlow 的业务 Truth / Authority
→ REUSE
→ 只做最薄的 Adapter / Verification / Recovery

涉及 Task / Effect / Identity / Permission / Recovery Truth
→ OWN
→ 必须由 ProFlow 自己定义 Contract 与 State

自研层开始复制外部平台或其它 Owner 的事实
→ DELETE
→ 不因为已经写了很多代码就继续维护
```

因此真正稳定的原则不是“自研越少越好”，而是：**外部能力可以替换，内部 Ownership 不能漂移。**

## 2. 第一类复用：不重新造一个 Chat / Agent 前端

ProFlow 最早的路线选择之一，就是不先花大量时间自建通用聊天界面、模型选择器、文件上传、搜索、代码解释器和 GPT 配置系统。

已有 ChatGPT / Custom GPT 已经提供：

```text
高级模型交互
+ Instructions
+ Knowledge
+ Actions
+ File handling
+ Code Interpreter
+ Web Search
+ Conversation UX
```

所以 ProFlow 把 Custom GPT 当 Agent Carrier，而不是再实现一个“类 ChatGPT 产品壳”。

这个决策节省的不是几个页面，而是把研发重心直接放到缺失部分：

```text
ChatGPT
↕
本机 Task / Agent / Execution / Browser / Model Runtime
```

也就是：**成熟交互与认知表面复用，真实本机系统语义自研。**

## 3. 第二类复用：Carrier 已有 transport，就不要再造 File Transport

2026-08 的正式 Carrier 约束明确把 OpenAI 已提供能力直接纳入合同：

```text
小型结构化控制数据
→ GPT Action JSON

文档 / 文件 / 大型上下文
→ GPT Actions File Bridge

Conversation 内文件处理
→ 原生 file handling / Code Interpreter
```

这直接反向裁剪 Browser Host：大型 Task Markdown 不再靠浏览器注入；Worker 通过 Action 查询正式 Context，再由 File Bridge 放入当前 Conversation。

因此 Browser 只保留不可替代的 Reality 工作：

```text
CREATE / RESTORE / WAKE
Conversation identity
页面真实状态
Screenshot / DOM observation
真实 UI effect
```

这条规则的目的非常明确：**复用 Carrier transport，减少自研 transport；但 transport provenance 不能成为业务 Truth。**

## 4. 第三类复用：公网 Provider 可以换，内部 Contract 不跟着换

最早开发期公网链路使用过：

```text
Custom GPT
→ Cloudflare Worker / Edge
→ Tunnel / Bridge
→ Gateway
→ Runtime
```

这条路线真正暴露的问题不是“Cloudflare 不好”，而是阶段目标和基础设施复杂度不匹配：

- Worker 在线不等于本机 Origin 可达；
- Edge / Tunnel / Origin / Secret / Gateway / Runtime 同时引入，变量太多；
- 远端 Secret 漂移和阶段超时让 Evidence 难稳定复现；
- 还没证明 Actions → Local Runtime，就先背上完整 Edge 运维成本。

2026-07-30 后开发期入口切为：

```text
Custom GPT
→ Microsoft Dev Tunnels
→ Loopback Gateway
→ Loopback Runtime
```

真正重要的是：**被替换的是 public-ingress Adapter，不是 Gateway / Runtime / Auth / Policy / Capability Contract。**

## 5. Microsoft Dev Tunnel：复用官方实现，不放弃产品级治理

当前 `dev-tunnel` Module 不自己实现隧道协议。

它直接治理 Microsoft 官方 `devtunnel` CLI，并把它当 External Resource：

```text
Microsoft 官方 CLI
→ public HTTPS ingress

ProFlow dev-tunnel Module
→ pinned acquisition
→ login observation
→ stable tunnel identity
→ port reconciliation
→ host lifecycle
→ readiness verification
→ Fresh recovery
→ shared publicBaseUrl truth
```

这就是典型的 **Wrap, not Rebuild**。

ProFlow 自己拥有的不是 Tunnel 技术，而是“这个外部能力怎样成为可靠产品依赖”。

后续甚至进一步删除独立 `@tomflow/proflow-devtunnel-cli` wrapper，把 CLI acquisition 直接归 `dev-tunnel` Owner；固定官方版本、校验 artifact SHA-256，并禁止 PATH 中不受控的 system CLI 成为第二执行入口。

所以薄适配不等于无治理：**外部实现复用，版本、身份、恢复和 READY 语义必须本地可证明。**

## 6. 模型侧也是同一原则：复用协议，不绑定产品

手机模型实验最终没有把 MLXHub、iPhone、Qwen、Ollama、LM Studio 或 vLLM 写进平台 Contract。

Provider 边界被压成：

```text
OpenAI-compatible URL
+ auth
+ model inventory
```

Runtime 再自己验证：

```text
text
Vision
structured output
thinking / no-thinking
context capacity
output capacity
```

也就是说，外部生态负责“以兼容协议提供模型”，ProFlow 自己负责“这个模型是否有资格承担当前 FAST / REASON 角色”。

这让物理 Provider 可以替换，而 ReasoningSpec、Flow 和 Policy 不需要跟着重写。

同样的边界再次出现：**协议互操作性可以复用，业务角色资格必须由自己的 Evidence 决定。**

## 7. 研发 Harness 也没有重新造本机工具协议

研发侧 Chat 最终使用的是成熟能力组合，而不是 ProFlow 自己发明一个“超级本机 Agent Protocol”：

```text
OpenAI Secure MCP Tunnel
+ Desktop Commander / Local Dev
+ CodeGraph
+ Browser automation
+ Repomix
```

`gptweb-mcp` 后来只负责 runtime 生命周期、恢复、自检和统一入口。

它明确不是：

```text
新的 MCP Wrapper
新的业务 daemon
新的工具协议
```

讨论过再包一层 `Local Dev Guard MCP`，最终没有做，因为安全与执行纪律可以由现有工具 contract、instructions 和治理层表达，再包一层只会增加维护与调试路径。

这条研发经验和产品架构是一致的：**已有标准连接面时，不因为“统一感”就再发明一层协议。**

## 8. 哪些能力必须自己拥有：不是因为外面没有，而是因为这是系统真值

复用的边界一旦越过业务语义，就会变成 Authority 泄漏。

ProFlow 必须自己拥有的核心对象包括：

```text
Task
→ 长期业务状态、Requirement、Plan、Readiness

Agent / Role Binding
→ Role、Worker、Conversation 的稳定身份关系

Execution
→ Intent、Effect、Evidence、UNKNOWN、Recovery

Gateway
→ 外部请求认证、Role identity、schema normalization、owner routing

Browser Reality
→ 真实 Conversation / Tab / Page observation 与 physical effect

Module Governance
→ install/setup/status/start/stop 的 owner contract 与 recovery
```

这些不是“第三方没有同名功能”，而是它们决定 **ProFlow 自己认什么为真、谁有权改变真值、失败后怎样恢复**。

## 9. Protocol Success 不等于 Business Truth

这是“复用成熟能力”最容易犯错的地方。

```text
GPT Action 200
MCP call returned
Dev Tunnel HTTPS reachable
Provider HTTP 200
Browser click succeeded
```

这些都只能证明某个外部机制完成了一段交互。

它们不能自动证明：

```text
Task 已完成
Effect 已真正生效
当前 Worker 身份正确
模型建议有执行权限
远端结果值得信任
失败动作可以安全重试
```

因此 ProFlow 一直保留自己的 Validation / Evidence / Approval / Reconciliation。

可以复用协议和 transport，但**连接标准化不等于信任标准化，调用成功不等于 Truth Commit。**

## 10. ProFlow 会主动删除已经写完的自研层

“自研过”不构成继续保留的理由。

#

## `chatgpt-carrier`：整个 Module 被退休

早期 `chatgpt-carrier` 曾有完整的 DOCS、SETUP、adapter、descriptor、CLI、resource adapter 和测试。

2026-08-28 `eaae824` 直接删除整个 package。

原因不是 Carrier 消失，而是 Carrier truth 已经更合理地分散到真正 Owner：

```text
Agent Package
→ Role material / capability requirements

Execution Browser
→ Web materialization / physical reality

Role Registry
→ durable role identity / credential

Agent Gateway
→ Action auth / transport boundary
```

继续保留独立 Carrier Module，只会再维护一份“它是否 READY”的重复事实。

这是一条很强的架构信号：**当一个模块的存在价值只剩下复制别人的 Truth，它应该退休。**
#

## 中央 Deployment Planner：804 行也照删

2026-08-20 `e2f4ff7` 删除 Platform CLI 中 5 个 Planner 文件，约 804 行。

这不是功能缩水，而是发现中央 Planner 在重新汇总：

```text
Module config
Module effect
Module verification
Module dependency
Human action
```

这些本来应该由各 Module Owner 自己声明和执行。

因此后来 Deployment 变成：

```text
Module owns behavior / private config / operational truth
Platform owns discovery / ordering / forwarding / aggregation
```

同样的模式还出现在：

- Browser Host 从隐藏 Workflow Engine 削成 Reality Carrier；
- 独立 `proflow-devtunnel-cli` 被退休，CLI acquisition 回归 `dev-tunnel` Owner；
- File Bridge 成熟后删除 Browser 大文件 transport 职责。

**删除重复 Ownership，比继续抽象一层更难，也更有价值。**

## 11. Build / Reuse / Wrap / Delete 决策模型

到这里可以把 ProFlow 的技术选型归纳成四种动作：

| 动作 | 什么时候用 | ProFlow 例子 |
|---|---|---|
| `REUSE` | 成熟能力已解决目标问题，且不拥有业务 Truth | ChatGPT / Custom GPT、Actions、File Bridge、MCP、OpenAI-compatible API |
| `WRAP` | 外部能力成熟，但需要产品级 identity、lifecycle、verification、recovery | Microsoft Dev Tunnel、Model Provider、Browser external reality |
| `BUILD` | 对象本身就是 ProFlow 的业务语义、Authority 或长期状态 | Task、Execution、Role Binding、ReasoningSpec、Module Contract |
| `DELETE` | 自研层复制了别的 Owner、制造第二真源或隐藏编排 | `chatgpt-carrier`、中央 Deployment Planner、过厚 Browser transport、独立 devtunnel CLI wrapper |

最容易做错的是把 `WRAP` 写成 `BUILD`：

```text
外部系统有一点不方便
→ 自己重新实现整个协议 / runtime / service
```

ProFlow 后来的选择更克制：只补**产品真正缺少的治理层**。

反过来，也不能把 `BUILD` 错当 `REUSE`：外部平台即使提供 Task ID、tool call 或 confirmation，也不能因此接管 ProFlow 自己的 Task / Approval / Effect Truth。

## 12. “没有做”本身也是架构成果

这一条演进里有一批重要的非功能：

- 没有重新做一个通用 ChatGPT 前端；
- 没有为产品链强行引入 MCP，只因为 MCP 更“新”；
- 没有把 OpenAI Secure MCP Tunnel 硬塞成 Custom GPT Actions 的公网 REST ingress；
- 没有长期维持 Cloudflare Edge 基础设施，只为了证明开发期本机链路；
- 没有让 Provider Contract 识别 iPhone / MLXHub / 具体模型产品；
- 没有因为 File Bridge 出现就创建新的 File Domain / Artifact Domain；
- 没有把 Code Interpreter 当成本机真实 Execution；
- 没有保留一个中央 Deployment Brain；
- 没有为了工具统一再造一个超级 MCP Wrapper。

这些“不做”背后不是功能不足，而是同一个判断：

> 新层只有在它拥有一个无法被已有 Owner 表达的稳定责任时才值得存在。

这也是大型 Agent 工程控制复杂度最有效的方法之一。

## 13. Trade-off：复用不会自动消除工程成本

复用成熟能力减少了协议和底层实现成本，但会引入另一类成本：**外部平台漂移**。

例如：

- Custom GPT 产品字段和 Actions 限制会变化；
- File Bridge 的运行时对象可能与静态 OpenAPI 示例不完全一致；
- Dev Tunnel CLI 会有真实网络延迟、登录状态和 CLI 行为差异；
- OpenAI-compatible Provider 对 structured output / reasoning 的实现并不完全相同；
- MCP / Browser / ChatGPT 都有自己的 runtime lifecycle 与权限边界。

所以正确公式不是：

```text
REUSE = zero maintenance
```

而是：

```text
REUSE
+ Anti-Corruption Layer
+ Runtime Verification
+ Contract Conformance
+ Recovery
= 可控的外部依赖
```

ProFlow 节省的是重复实现成熟机制的成本，不是取消对外部现实负责。

## 14. 对大型 Agent 工程可复用的判断顺序

面对一个新能力，不要先问“我们要不要自己做”。先按下面顺序判断：

```text
1. 这个问题已有成熟实现 / 标准协议吗？
   ↓ yes
2. 它是否只负责 mechanism / transport / external resource？
   ↓ yes
3. 能否通过稳定 Contract 与内部系统隔离？
   ↓ yes
4. REUSE；必要时加薄 WRAP

如果它决定业务 Truth / Authority / Recovery：
→ BUILD owner-owned semantics

如果现有自研层已经没有独立 Ownership：
→ DELETE
```

还有一个更实用的问题：

> **如果明天把 ChatGPT、Dev Tunnel、手机模型或 Provider 换掉，哪些东西应该保持不变？**

那些应该保持不变的部分，才更接近平台真正应该拥有的核心 Contract。

## 15. Resume / Interview 边界

这条可以安全主张：

> 在 ProFlow 中围绕 ChatGPT/Custom GPT、公网隧道、模型 Provider 和研发 MCP 工具持续做 Build-vs-Reuse 决策：成熟的认知界面、协议和基础设施优先复用，通过 Anti-Corruption Layer、能力验证和恢复机制纳入系统；Task、Execution、Identity、Approval 等业务真值坚持 owner-owned，并在演进中主动删除中央 Deployment Planner、独立 Carrier 等重复 Authority 层。

更短的架构表达：

> **Reuse execution mechanisms; own semantic authority.**

或：

> **Wrap external reality, build internal semantics, delete duplicate authority.**

需要保持边界：

- 不声称节省了未经测量的百分比成本；
- 不声称所有第三方 Provider 都可以无缝互换；
- 不把 Microsoft Dev Tunnel 描述为最终生产公网方案；
- 不把研发侧 `gptweb-mcp` 包装成 ProFlow 产品功能；
- 不把 OpenAI / Microsoft / MCP 等第三方能力归为本人实现。

真正属于项目能力的是：**识别该复用什么、该拥有什么、该包多薄，以及什么时候应该把自己已经写过的层删掉。**
