## 已有较强证据、值得继续升级的主题

#

## Chat / Custom GPT / Model Runtime 三层认知角色

不是“都叫 GPT 就是一层”。研发 Chat、产品 Custom GPT Carrier、平台 FAST/REASON Runtime 的状态、权限、上下文与工具语义不同。

#

## 为什么基于 ChatGPT：Host-first / Control-plane-owned

已获得强证据。2026-07-28 第一份 `SOL-005` 的核心问题就是“ChatGPT 能否通过 Custom GPT Action 安全、稳定、可审计地调用 Mac 本机能力”，且先建立 Gateway/Auth/Policy/Local Runtime/allowlisted Capability，再接 Custom GPT；8 月初进一步把 Custom GPT 明确成无状态专业角色 Carrier，Task/Plan/Claim 不进聊天真源。后续 Wake Bridge、Browser Carrier、GPT provisioning 与 Application-first authority migration 都是在吸收 Host 限制，而不是把业务 Truth 交回 Host。核心判断：**Reuse the Host; own the Control Plane.** 边界：没有证据证明做过正式的 Custom GPT vs 自建 UI / Claude / local Agent benchmark。

#

## 三条本机桥

研发桥、Custom GPT Action Bridge、Browser Wake Bridge 分别解决不同方向的问题。研发桥本身还包含从人工 zip/Prompt 交接到 MCP/CodeGraph/Browser/Repomix 的独立演进史。

#

## 从窄 Capability 到 Agent Platform

最早只是 `runtime.status` / allowlist；随后才长出 Controller、Task、Local Control、Browser Host、Approval、Evidence。

#

## Cloudflare → Dev Tunnel 的基础设施取舍

值得深挖“为什么一个技术上可行的公网方案仍然不适合当前阶段”。

#

## Browser 从万能 Host 收敛成双平面 Reality Adapter

已获得强证据。Phase 2 真实 Chrome 证明 Browser Host 能 Observe/Dispatch/Approval/Delivery/Wake，也暴露 Observation、Execution、Approval wait、Response lifecycle、Human interaction、Continuation 被耦合进同一 command lifecycle；2026-08-15 `5278fc6` 真正删除 universal Task Driver，改成 deterministic Task Observer + read-only System Observer + Carrier Controller。研发验收侧又在 2026-09-01 的 Harness 事故与 09-03 的跨扩展 debugger 限制后，收敛成 Playwright 普通 Web + macOS AX privileged UI 双平面，并冻结 `locate → mutate → observe → verify`、stable business identity ≠ transient tab identity、UNKNOWN 不盲重放。核心判断：**Browser owns irreducible reality, not workflow authority.**

#

## 验证型实现 → 独立 ProFlow 正式工程

旧 `ai-agent-platform` 作为实验场；新 ProFlow 禁止 legacy dependency，按 Frozen DDD/SDD/Test Plan 重建，同时迁移已验证语义。

#

## 原生能力优先：不重复造 Custom GPT 已经有的东西

File Bridge、Code Interpreter、Web Search、Actions、Conversation 能力被当作 Carrier capability；平台只补 Task truth、Effect、Recovery、Deployment 等缺口。

#

## Carrier cognition 与 Model Runtime 分层

Custom GPT native Actions/Function Calling 不等于本地 FAST/REASON tool loop。这个边界对 Small-model-first 很关键。

#

## Agent Package 不只是 Prompt：外部 SaaS Agent 也被纳入 Deployment

已升级为独立专题 [15｜Custom GPT 从在线配置到外部 Deployment Resource](./15-Custom-GPT从在线配置到外部Deployment-Resource.md)。强证据链为：人工 Builder/setup assistant → Real-2 deterministic provisioning → reusable `createCustomGptRole` → 三角色公共部署路径 → pre-create Bearer / single-stage create → 真实 g-id Role → `LIVE_CREATED` 不可逆 recovery。重点不是“自动填表”，而是把第三方 SaaS Agent 纳入 version / identity / validation / recovery 的 Deployment Truth。

#

## GPT 身份从“页面”升级成 durable Role / Worker identity

`g-id` Role 与 `c-id` Conversation Worker 被显式建模，Tab 只作为 transient locator。

#

## 会主动删除失去 Ownership 的抽象

2026-08-28 `chatgpt-carrier` 整包退休。退休前它已明确 `Business Fact Owner: none`，只剩 ChatGPT Web reachability HEAD probe，而 concrete GPT readiness 已由 Agent Package + Browser provisioning + Role Registry + Gateway probe 拥有。这是“边界必须有 owner 依据”的反向实践。

#

## Deployment 是产品，不只是 DevOps

Fresh Workspace、Registry latest、普通用户视角、Cognitive Load / Automation / CLI / Default Output 四个门值得单独深挖。

#

## Release Supply-Chain Truth：源码绿灯不能越级代表用户现实

已获得强证据。ProFlow 把发布拆成 `Source Truth → Package Truth → Registry Truth → Installed Truth → Runtime/Product Truth`；真实 stale-dist `DESCRIPTOR_INVALID` 事故推动 build + isolated publishability 进入 canonical release，Registry UNKNOWN 通过 exact readback reconciliation 收敛，最终 Deployment 只认 real npm + Fresh Workspace。值得保留的原则是 **Upstream PASS cannot impersonate downstream reality**，而不是“会使用 npm/pnpm”。

#

## 自动化测试 Harness 会积累工程知识

真实失败不只产出 patch，还会写回 Runbook / CURRENT / Tool Rule / Recovery Rule；测试系统逐渐变成可复用执行资产。

#

## 研发 Chat 自己也被工程化，而且起点是人工 zip，不是 MCP

`PROJECT_OWNER_CONFIRMED` 的真实链路是：Codex 额度不足后转 Chat 高级模型 → 手工压缩仓库给 Chat → Chat 生成提示词给本地 DS → Chat 再生成压缩包/解压替换脚本 → zip 往返成为瓶颈后才调研并发现 Web Chat MCP → 先接 Shell → 查询效率低再接 CodeGraph → 手工 Browser 验证太慢再接 Browser MCP → 与 Work 对比仍有上下文吞吐差距再接 Repomix。

值得继续证明的不是“工具数量”，而是 Human Context Transfer / Code Navigation / Reality Feedback / Context Throughput 四类瓶颈如何逐层被消除。

#

## 实验代码怎样“毕业”，而不是直接进生产

已升级为独立专题 [16｜实验代码如何毕业为正式架构语义](./16-实验代码如何毕业为正式架构语义.md)。强证据是 `execution-flow-runtime` lab.1～13 → EF-6 Handoff 明确停止 lab.14、禁止直接迁入 packages，并逐项裁决 ADOPT / REWRITE / MIGRATE / DEPRECATE；后续 integration spike 完成验证后被删除。核心判断：**Prototype code is disposable; validated semantics are durable.**

#

## 从 UNCERTAIN 到 Reality Reconciliation

已升级为独立专题 [17｜从 UNCERTAIN 到 Reality Reconciliation](./17-从UNCERTAIN到Reality-Reconciliation.md)。Phase 2 Browser uncertain reporting → Phase 3 `UNKNOWN_SIDE_EFFECT` → Local/Browser/Agent/Release/SaaS resource authority readback 形成统一 no-blind-retry 纪律。核心判断：**A failed command is not proof that an effect did not happen.**

#

## 产品入口的演进

已升级并由 [09｜产品入口：从 Product GPT 到 Tasks Application](./09-产品入口从Product-GPT到Tasks-Application.md) 完整承接。Product-GPT-first → Extension/Application bootstrap → Side Panel Task Application → 当前 loopback `/tasks` 的 Authority/Surface 演进已经恢复；当前 Tasks 迁移仍未 commit，只保持 `CURRENT_DISK_VERIFIED / NOT_GIT_FROZEN`，不再作为“待考古”事项。

#

## 从 Controller-centric 到 Application-first fixed-role team

已获得强证据。Phase 2 的主循环以 Controller continuation 为中心；2026-08-15 v2.1 裁决明确把 New Task、Role discovery、Dev/Test selection 从 Product GPT 主链拿走，Extension/Application 先建立 PENDING Task 与固定岗位，再让 Product/Dev/Test-Ops Worker 进入。`32363da` 随即删除 Product 的 `createTask/listRegisteredRoles/getRegisteredRole`。亮点不是“三个 Agent”，而是**确定性工作从模型 authority 回迁到 Application/Task Owner**。

#

## 模型端设备无关化

已升级并由 [10｜手机模型实验如何塑造 Capability-Driven Model Runtime](./10-手机模型实验如何塑造Capability-Driven-Model-Runtime.md) 完整承接。FAST/REASON 早于手机实验；端侧 Reality 真正推动的是 capability probe、single-lane scheduler、Provider boundary 与自动 role mapping。历史 Qwen/MLXHub/设备只属于实验 Evidence，不进入当前 Contract。

## 仍缺证据、先不要升级的主题

- “高级模型 Token 完全不是瓶颈”的量化说法；目前只能作为 Project Owner 路线判断，不能包装成 benchmark。
- ProFlow 是否显著降低真实开发成本/时间；需要可比较数据。
- 多 Agent 是否比单 Agent 质量更高；当前更强证据是职责/恢复/产品流程，而不是模型效果 A/B。
- 手机模型的最终经济性与稳定性；设备/模型版本持续变化，需要真实实验。
- 当前 ProFlow Tasks 产品入口是否已完全替代所有旧 Product-GPT-first 流程；需继续按当前 code/spec 核验。

## 发现方法

每条候选继续问五个问题：

```text
1. 它最早解决的真实问题是什么？
2. 前一版方案是什么？为什么不够？
3. 哪个事故、实验或用户体验触发了变化？
4. 最终设计付出了什么代价？
5. 哪些证据能证明，而不是只靠我们事后解释？
```
