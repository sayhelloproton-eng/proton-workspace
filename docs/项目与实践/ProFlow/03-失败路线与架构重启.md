# ProFlow｜失败路线、真实事故与架构重启

> 状态：ACTIVE_RESEARCH
> 原则：失败路线不是负资产。能解释为什么主动放弃一个可工作的方案，往往比最终代码更能说明工程能力。

## 1. Cloudflare 路线：能工作，不等于应该继续

早期先建立 Cloudflare Worker 固定公网入口，再尝试 Tunnel / Gateway / Local Runtime。

问题逐渐集中在：

- Edge / Origin 配置；
- Remote Secret；
- Cloudflare 与本机状态漂移；
- VPN / Tunnel 运行条件；
- 为一个开发期入口引入过多运维对象。

最终开发期切换 Microsoft Dev Tunnels。

这里的经验不是“Dev Tunnel 比 Cloudflare 好”，而是：**基础设施选择必须服从产品当前阶段的复杂度预算。**

## 2. Phase 2 Browser Host：能力证明成功，架构仍然需要推翻

Phase 2 已真实证明 Browser Host 能：

- 绑定 GPT Conversation；
- Poll Dispatch；
- Approval；
- 页面输入和 submit；
- Delivery；
- Wake Controller 继续工作。

但真实串联也暴露：

```text
Observation
Execution
Approval waiting
Response lifecycle
Human interaction
Continuation
```

被塞进同一个 Browser command 生命周期。

表面 bug 包括 scroll、send readiness、Action Allow、claim/reclaim、Journal pressure；根问题却是**生命周期所有权错误**。

因此 Phase 3 的正确动作不是继续修 DOM selector，而是重新切责任边界。

## 3. “Browser Host 是隐藏 Workflow Engine”成为正式反模式

Phase 2 复盘明确写下：Browser Host 不应该成为隐藏 Workflow Engine。

Phase 3 后续实际提交：

```text
5278fc6 feat(browser): replace universal Task Driver with deterministic Observer/Carrier modules
```

这条历史特别重要，因为它证明当前“thin Browser Carrier”不是凭空设计出来，而是被真实系统复杂度逼出来的。

## 4. Phase 2 的收口方式本身是一种方法

第二阶段没有要求“再创造一个全新 Task，直到所有异步细节一次全绿”才算结束。

而是判断：

```text
核心能力存在
+ 领域边界基本成立
+ 真实串行链路已证明
+ 关键失败模式已暴露并理解
+ 下一阶段设计输入足够
= MVP COMPLETE
```

然后封存旧失败现场，不再拿 Browser 当旧状态机的持续 debugger。

这是一种很成熟的实验阶段退出标准：**阶段目标是获得足够的信息增益，不是维护沉没成本。**

## 5. 新 ProFlow 仓库：重写，但禁止失忆

2026-08-13 新仓库启动时同时做了两件看似矛盾、实际非常关键的事：

```text
禁止 legacy runtime dependency / wholesale copy
同时要求保留 Phase 2 已经证明的重要语义
```

也就是：

```text
REWRITE implementation
PRESERVE validated semantics
```

包括 Opaque refs、Approval、Idempotency、Delivery evidence、UNKNOWN/no-blind-retry、target identity 等真实教训。

这是“重构”和“重写”最容易做错的地方：要推翻错误实现，但不能把事故换来的知识一起删掉。

## 6. 后续还应重点找的失败路线

- 早期 Cloudflare Worker → Quick Tunnel → Edge proxy 中具体哪些维护成本触发裁决；
- six-command / seven-command deployment surface 的反复收敛；
- `chatgpt-carrier` 为什么最终被退休/吸收到新的 owner；
- Side Panel 为什么退出产品入口，独立 Tasks Page 如何形成；
- Real-1 / Real-2 中 Custom GPT provisioning 从人工 `ACTION_REQUIRED_WEB` 到自动 Browser provisioning 的完整演进；
- 自动化安装扩展时踩过的 privileged UI / Playwright controlled context 问题；
- `start` 不归还 shell、Dev Tunnel timeout、MCP 120s request 等怎样反向修改 Harness 规则。


## 7. 2026-08-28：删除没有独立 Truth Ownership 的 `chatgpt-carrier`

`eaae824 fix(platform): close setup status and retire carrier` 一次性删除整个 `packages/chatgpt-carrier`。

退休前 README 已经明确承认这个包：

```text
Business Fact Owner: none
```

它只做一件事：对 `https://chatgpt.com/` 发 HEAD，报告 ChatGPT Web 是否可达；它明确不拥有：

- Agent Role / roleRef / carrierUrl；
- GPT Instructions / Actions / Auth / Knowledge / Capabilities；
- Worker / Conversation identity；
- Custom GPT materialization state。

而 concrete GPT readiness 已经有完整 owner 链：

```text
Agent Package material
→ Browser Extension provisioning
→ Agent Runtime Role Registry / credential
→ Gateway authenticated probe
```

所以单独 `chatgpt-carrier` 只剩“网站能不能访问”的弱事实，却继续占据 Module Graph、setup/status 和依赖关系，价值已经小于治理成本。

## 可复用判断

DDD / Module Governance 不是只会“多拆几个边界”。当一个模块已经没有独立业务事实、不可替代 effect 或独立 lifecycle，只剩对别的 owner 的弱旁观时，**删除这个抽象本身就是架构收敛。**

这也是 ProFlow 很值得讲的一类能力：项目不是持续加层，而是多次主动删除已经失去所有权依据的层。
