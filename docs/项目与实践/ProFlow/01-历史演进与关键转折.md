## 跨阶段：研发 Harness 不是预先设计出来的，而是连续消除吞吐瓶颈

`PROJECT_OWNER_CONFIRMED`：研发侧最早只知道 Chat 网页端可以选择高级模型。Codex 额度成为限制后，先采用最原始的协作方式：

```text
手工仓库压缩包 → Chat 分析 / 生成提示词 → 本地 DS 执行 → 再打包给 Chat 审计
```

随后为了减少人工搬运，Chat 开始直接生成压缩包和解压/替换脚本，本地执行后再打包审计。但随着工程变大，`打包 → 上传 → 执行 → 再打包` 的 round-trip 本身成为瓶颈。

这才触发对 Chat 网页端能力的调研，并第一次发现 MCP：

```text
zip / script 往返太慢
→ 调研 Chat Web
→ MCP Shell：先解决直接访问/执行本机
→ CodeGraph：解决大型代码结构查询低效
→ Browser MCP：解决真实 UI 手工验证低效
→ 与 Work 对比仍有 Context throughput 差距
→ Repomix：解决批量上下文构建与读取
```

后期这些能力才进一步被治理为 `Repomix / CodeGraph / Local Dev / Playwright` 四 Plane，并由 `gptweb-mcp` 统一运行时管理；与此同时真实 Browser automation、Fresh replay、Custom GPT 创建、Dev Tunnel、Provider 等失败经验持续写回 `00-公共上下文` 的长期规则、CURRENT、自动化知识库和历史记录。

因此研发 Harness 的核心不是“工具很多”，而是：**每新增一层工具都对应上一代真实工作流已经出现的吞吐瓶颈；最终把人肉 Context Transfer 逐步改造成可持续的 AI Engineering Loop。**

## 4. 2026-09-03 当前 dirty source：Side Panel → Tasks Web Surface 正在迁移

当前 Git working tree 机械事实：

```text
D  extension/side-panel.html
D  extension/side-panel.ts
?? extension/tasks.html
?? extension/tasks.ts
M  manifest.json
```

因此这次变化**还没有 commit anchor**，不能写成已经完成的 Git 历史。

当前 manifest 已删除 `sidePanel` permission/default path，改为 Extension `action`；action 当前优先调用本机 Bridge mint `/v1/tasks/session`，打开：

```text
http://127.0.0.1:<bridge>/tasks/bootstrap/...
→ /tasks loopback Web surface
```

Bridge 不可用时才 fallback：

```text
chrome-extension://.../extension/tasks.html
```

公共自动化 Runbook 记录了直接触发这次迁移的真实约束：另一个扩展的 `chrome-extension://` 页面即使能进入 Playwright controlled group，Chrome 仍可能拒绝 `chrome.debugger.attach`；loopback `/tasks` 不受该跨扩展 debugger 限制。

这说明当前迁移同时服务两件事：

- 产品入口从狭窄 Side Panel 变成独立 Task application surface；
- 普通 Web surface 能进入 Playwright Reality Plane，支持真实用户视角自动化验收。

同时并未简单放宽安全：本次 `/tasks.js` 与 session cookie path 不匹配时，修复选择把脚本收敛到 `/tasks/app.js`，而不是把 cookie scope 从 `/tasks` 放宽到 `/`。

#

## 为什么这条变化重要

这是一次 **authority migration**：

```text
旧：智能体/Controller 既参与认知，也容易吸收系统 bootstrap / team discovery / workflow authority

新：Application / Task Owner 先建立确定性业务事实
    ↓
    Product / Dev / Test-Ops Worker 在已存在的 Task 内发挥智能
```

产品角色最终固定为：

```text
Product        = 运营 + 产品经理
Controller-Dev = 项目管理 + 研发
Test-Ops       = 测试 + 运维
```

但“固定三角色”并不是这里最深的亮点。更深的是：**能确定的组队、Task 创建、Role 类型和 readiness 由程序负责；模型不因为更聪明就获得不必要的系统启动权。**

这也解释了为什么当前 Product GPT 是 Task 内的业务角色，而不是 pre-Task system orchestrator。
