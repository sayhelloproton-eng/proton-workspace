# ProFlow｜实验代码如何毕业为正式架构语义

> 状态：ACTIVE_RESEARCH / STRONG_EVIDENCE
> 主题：Phase 2 收口后，ProFlow 如何用 `execution-flow-runtime` lab 与 integration spike 探索未知边界，又如何主动停止实验、拒绝直接复制实验实现，只让验证过的语义进入正式 Phase 3。
> 边界：这不是“做了很多 PoC”的数量叙事，而是实验退出、语义毕业与正式架构接管的工程方法。

## 1. 为什么需要一层实验 Runtime

Phase 2 已经证明多域链路可跑，也暴露 Browser lifecycle、异步恢复、模型分层等真实复杂度；但此时直接在正式架构里继续改，会把“探索未知”和“冻结系统承诺”混在一起。

于是 2026-08-09 出现独立：

```text
experiments/execution-flow-runtime/
```

它允许快速验证 Flow、Capability、Inference、Service/CLI、Scheduler 等假设，而不提前把实验结构升级成正式 package contract。

## 2. lab 不是一次性 demo，而是一串“问题逐步收窄”的实验

Git 显示这条线快速从 `lab.1` 演进到 `lab.13`。其中已经恢复出的关键节点包括：

```text
9a6321d  建立 TypeScript execution-flow-runtime lab
bed1716  lab.6：Provider / EF-2
72bd55d  lab.7：role service + FAST live PASS
93ee2ab  lab.8：FAST → REASON escalation
515fe96  EF-4：deterministic routing
410fd37  EF-5：transport / package semantics freeze
```

这里的价值不是版本号增长，而是每一轮实验都在减少一个仍未被现实证明的假设。实验目录允许快速重写实现，但协议、live test 与 security boundary 一起保留证据。

## 3. 真正的转折：EF-6 明确要求“停止继续实验”

2026-08-10 `310d66f` 的 Handoff 裁决不是“实验成功，直接合并”，而是：

```text
EF-0～EF-5 = GO / ACCEPT / FROZEN
EF-6 = HANDOFF READY / NO DIRECT INTEGRATION YET
不做 lab.14
不直接把 experiment 迁入 packages/
```

这是一条很强的退出纪律：实验阶段达到足够信息增益后就停止，不因为已经投入很多代码而继续把 lab 演化成事实上的生产架构。

## 4. 不是二选一：实验产物被逐项裁决

EF-6 没有用“保留 / 删除”两档处理 lab，而是逐项分类：

```text
ADOPT AS-IS
ADOPT SEMANTICS / REWRITE IMPLEMENTATION
MIGRATE AFTER COMMONS
DEPRECATE
```

例如 FAST/REASON role、serial scheduler、HTTP service/CLI lifecycle 可以直接保留语义；execution result 要与 Common Result 显式 mapping；built-in file/fixed-command capability 则退出 Runtime、只保留安全语义给 Local adapter。

这说明真正迁移的是**已经被现实证明的约束和语义**，不是因为某段实验代码已经能跑就默认升级。

## 5. Commons Freeze 是实验进入正式架构前的门

裁决还明确：

```text
Stage 1 Commons 冻结前：STOP
不迁 Runtime
```

原因是实验里的局部协议不能反过来定义平台 Common Result、Capability、Envelope。先冻结跨域共同语言，再决定 lab 语义如何映射，避免“PoC 先跑通”变成架构绑架。

## 6. integration spike 负责最后一道跨域可行性证明

EF Handoff 后并没有立刻进入正式 package。`62748a1 / 0388b97 / 86bea23` 又建立临时 Phase3 integration spike，分别证明 Task Runtime integration、FAST live、durable HTTP runtime integration。

当正式领域文档、Test Plan 和实现 wave 建立后，这批 spike 被删除。**Spike 的退出本身就是成功：它证明问题后，不需要永久占据正式系统。**

## 7. 这解释了 Phase 3 的 `REWRITE / PRESERVE`

Phase 3 不是从空白开始，也不是复制 legacy：

```text
实验 / Phase 2 implementation
→ 可以删除或重写

被真实验证的 semantic invariant
→ 必须进入正式 Spec / Test Plan / Contract
```

因此 `REWRITE implementation / PRESERVE validated semantics` 不是一句重构口号，而有一套前置实验毕业机制支撑。

## 8. 和 DDD / SDD / TDD 的关系

实验阶段负责回答“未知假设是否成立”；SDD 负责把毕业语义变成正式 system promise；TDD 再把 promise 变成 executable proof；DDD 则决定毕业后的语义属于哪个 Owner。

所以正式工程不会让 spike 直接越过 Contract：**Experiment discovers; Spec decides; Test proves; Owner implements.**

## 9. Trade-off：会主动丢掉可运行代码

这种方法的代价很直接：实验中已经工作的大量实现不会自动进入正式仓库，后续还要重新做 Commons reconciliation、正式 Spec、Test Plan 与 Production adapter。

它牺牲短期“复用率”，换来两件事：

- 沉没成本不再拥有架构投票权；
- 正式 Contract 只吸收已经被 Evidence 支持的语义。

## 10. 可复用的毕业 Gate

```text
1. 当前实验到底验证了什么？
2. 哪些只是实现偶然形状？
3. 哪些语义已经有真实/live evidence？
4. 与正式 Commons/Owner 是否冲突？
5. ADOPT / REWRITE / MIGRATE / DEPRECATE 分别是什么？
6. 正式 Spec/Test 冻结前是否必须 STOP？
7. Spike 完成使命后是否可以删除？
```

如果这些问题没有答案，实验“能跑”还不足以成为 production architecture。

## 11. 求职可讲的核心

可以讲：在 Phase 2 到 Phase 3 的架构未知期建立独立 execution-flow-runtime lab，通过 FAST/REASON、routing、transport、scheduler 与 live integration 逐步验证关键语义；实验完成后明确停止 lab.14，按 ADOPT/REWRITE/MIGRATE/DEPRECATE 做 handoff，正式 Commons/Test Plan 冻结后重新实现，并删除已完成使命的 spike。

不能讲：所有 Phase 3 架构都由这一个实验产生；也不能把 lab 代码量或版本数包装成生产规模。

最稳定的两句总结：

> **Prototype code is disposable; validated semantics are durable.**

> **Experiment discovers; Spec decides; Test proves; Owner implements.**
