# ChatWeb 阶段实战记录模板

每个阶段只记录真实发生过的内容；没有实现、失败或实验时明确写“本阶段无”，不为模板完整制造故事。

## 1. 阶段状态与项目真源

记录 ChatWeb 当前 stage/gate、Git branch/HEAD/working tree，以及对应 Owner Spec / ADR / Verification。没有 commit 时明确写 candidate，不能伪造 baseline。

## 2. 为什么现在做

这个阶段解决什么前置问题？为什么不能跳过？它和上一阶段、下一阶段怎样衔接？

## 3. 目标与非目标

写清这一步真正要证明什么，以及为了控制复杂度主动不做什么。

## 4. 开始前的判断

当时有哪些假设、备选方案、未验证风险；不要用事后结论重写当时认知。

## 5. 设计与取舍

说明 ownership、Contract、数据流、Runtime/Delivery 边界和关键替代方案；正式设计只引用项目 Spec，不复制第二套权威定义。

## 6. 实际实现过程

按关键批次记录代码职责、数据流与验证入口，重点解释为什么这样实现，不粘贴大量源码或终端日志。
## 7. 真实问题、排查与根因

保留现象、错误假设、缩小范围的方法、最终 root cause 和为什么之前的判断会错。

## 8. 修复与设计变化

说明最小修复是什么；是否需要 Spec Amendment；哪些旧结论被保留、废弃或 supersede。

## 9. Mechanical Evidence

记录 typecheck/build/test/E2E/architecture/security/performance 等实际 Gate。工具 PASS 不等于 User Review；失败也不能被最终 PASS 覆盖掉。

## 10. User Review / Final Acceptance

分别记录 Mechanical、User Review、Final Acceptance。用户未确认时就写 `WAITING/NO`，不能由学习档案替项目做验收。

## 11. 阶段结论与下一入口

哪些判断被证明、哪些被推翻、哪些仍待后续真实证据；下一阶段从哪个项目 Runbook / Spec 进入。

## 12. 面试提炼

只基于已经发生的工程事实沉淀：30 秒版本、3 分钟版本、高概率追问、真实问题案例、可展示证据和对应 commit。
