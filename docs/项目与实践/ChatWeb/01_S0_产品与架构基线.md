# 01｜S0 产品与架构基线

状态：S0 Final Acceptance 已完成；ChatWeb Git HEAD=`UNBORN`，baseline commit 等待用户明确授权

## 阶段目标

S0 不写 React 页面，也不接真实模型。它先回答一个更重要的问题：**ChatWeb 到底是什么，哪些东西必须由它负责，哪些东西应该通过外部能力接入，以及后面的工程阶段怎样证明自己没有跑偏。**

项目把需要冻结的问题收敛成十项：产品目标、RAG 边界、Chat Runtime 职责、Provider 分类、Conversation 模型、Streaming/Cancel/Retry/Error、Capability 插件模型、Public Web/Runtime 拓扑、V0 Scope、阶段路线与 Gate。

## 为什么不能直接从 UI 开始

Chat Demo 很容易做：输入框、消息列表、一个模型 API、SSE。真正难的是后面开始加 Retry、多个模型、RAG、Citation、Settings、Tool/MCP 后，谁拥有状态、谁决定失败、Browser 能看到什么、一次运行怎样恢复。

如果这些问题等 UI 写完才补，最终往往会出现：页面 state 成为事实源、RAG 变成主流程硬依赖、Provider 接口被各种 optional field 撑成万能抽象、Retry 覆盖历史事实、secret 穿进 Browser。

S0 因此先冻结承重墙，不冻结 framework、timeout、目录细节和漂亮参数。
## 十项设计最后收敛成什么

1. ChatWeb 是独立 Public AI Chat Web Product Shell / Chat Runtime；无 RAG 也能工作。
2. ProFlow RAG 是外部 Context Provider，只通过稳定 public contract 接入。
3. Chat Runtime 拥有 Conversation/Run 编排、Context composition、Model stream、terminal state 与失败映射。
4. ModelProvider 与 ContextProvider 分离；Tool/MCP 因副作用和多轮执行另设边界。
5. V0 用 Conversation + Message + ChatRun，不提前建立 Branch Thread Tree。
6. Streaming 使用类型化事件；Stop 传播 AbortSignal；首 delta 后禁止自动整次 replay。
7. 一次 Run 可选 0..N Context Provider，组合顺序、provenance 和 required/optional failure policy 由 Runtime 管。
8. V0 优先一个 public Web deployable，但 Browser 与 Trusted Runtime 的逻辑、依赖和 secret 边界严格隔离。
9. V0 只做能证明通用 Chat Runtime 成立的最小闭环，不提前做账号、长期 Memory、自主 Agent、微服务等。
10. 路线固定为 S0→S10→V0，每阶段必须经过 Mechanical Gate → User Review → Final Acceptance → 用户授权 commit。

## Conversation 为什么需要 ChatRun

只存 Conversation + Message 会把“回答内容”和“生成过程”混在一起。一次 assistant 回答可能生成中被 Stop、部分输出后失败、用户 Retry，甚至在首个 token 前发生 provider transport retry。`ChatRun` 把一次生成尝试单独建模，使失败和重试不必篡改历史 Message。
进一步审计后又补了一条关键 history 规则：同一个 user message 可能对应多个失败/重试 attempt，但后续模型上下文不能把这些 attempt 全塞进去。V0 因此只投影一个 effective assistant attempt；Retry 自身重放 trigger 时，history 截止到该 user message，排除被重试的旧 assistant attempt。

这也解释了为什么 V0 明确不做 completed answer 的 Regenerate：一旦允许同一个成功回答保留多个可切换版本，就已经进入 branch/answer-selection 模型，不能再假装只是“再发一次请求”。

## Provider 为什么没有做万能 CapabilityProvider

一开始最诱人的抽象是：Model、RAG、Search、Memory、Tool 都叫 Capability，然后统一 `execute()`。审计后明确拒绝，因为它们的生命周期不同：

```text
Model generation  = 长连接、Streaming、Cancel
Context resolution = 生成前 bounded read
Tool execution     = 可能有副作用、Approval、幂等、Model→Tool→Model loop
```

共享 descriptor/registry metadata 可以，但不能为了接口漂亮抹掉行为差异。Agent 也不能伪装成 ContextProvider；未来如果引入 Agent，它至少涉及模型、Tool、execution state、approval/recovery，应沿执行/编排边界演进。

## 多 Context Provider 谁负责组合

`0..N Context Provider` 如果只停在接口层，看似可插拔，实际上会把组合顺序、失败降级、去重和来源归属留给实现临时决定。S0 因此进一步冻结 ownership：**Provider 只返回自己的 ContextResult，Chat Runtime 决定组合和整个 Run 是否继续。**

每个 selection 必须表达 `required | optional`。required 失败时在 generation 前明确结束；optional 失败可以继续，但必须留下可观察 degradation。真正并行/串行、budget、dedupe 参数等到 S5 真实 RAG adapter 后再冻结。
## 第一次 Mechanical Gate 为什么不够

第一版 S0 Gate 看起来已经很整齐：44 份 Markdown、0 业务代码、11/11 PRD 有 Acceptance 映射、11/11 REQUIRED_CONTEXT 存在。但全量审计发现，这个 Gate 只统计了 Product Requirement，没有统计已经写进 Spec 的 System、Domain、Capability 和 Contract 不变量。

机械扫描后发现当时一共有 33 个 Requirement ID，其中 **22 个非 PRD Requirement 没进入 Acceptance Matrix**。这不是文档格式问题，而是治理规则自己违反了自己：既然要求 Requirement → Verification 可追溯，就不能只查 PRD。

纠偏后 Gate 改为从全仓抽取 Requirement ID，再验证三段闭环：

```text
Requirement ID
→ Acceptance Matrix mapping
→ Verification ID definition
```

后续又新增 `DOM-CHAT-007` history projection，因此最终 S0 是 34 个 Requirement。

## 全量审计还修了什么

- 清掉 Product Spec 中未定义的 `Capability Provider` 残词。
- `ModelProvider.listModels()` 从强制能力改成 optional discovery；不支持远端 discovery 时由 Trusted Runtime server allowlist 提供模型描述，禁止伪造 `/models` 能力。
- 补齐 Conversation `activeRunId`、Assistant Message ↔ run、ChatRun ↔ assistant message 的关联语义。
- Retry 明确只面向未成功 run；completed answer 的 Regenerate 延后到真正 branch 需求。
- 多 Context Provider 的 order、provenance 和 failure policy ownership 收回 Runtime。
- Agent 明确不能借 ContextProvider 接口进入系统。
- 十个 S0 问题新增 Review Matrix，只做索引，不复制第二套设计真源。
## 审计过程中还发生了一次真实工具失败

批量修正文档时，最后一步给 CURRENT 重新编号的 Python 脚本因为漏写 `import re` 中断。没有直接重跑整批，而是先机械恢复磁盘事实：确认前面的语义修正已经成功落盘，CURRENT 尚未写回，再只补剩余步骤。

这个小事故反而验证了项目治理里一条很重要的规则：**批量操作失败后先恢复权威状态，再决定补跑范围；不能因为“应该是原子操作”就假设全部没发生。**
