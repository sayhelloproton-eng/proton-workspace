# 02｜S1 工程骨架：从错误单体假设到 Sites + Local Backend

状态：S1-A～S1-G 已完成真实 Gate；S1 Final Acceptance 已通过；ChatWeb final baseline=`3ae2522`，closeout metadata=`0a9010f`

## 原始判断

最初根据“Public Web + Trusted Runtime”选择了 Next.js full-stack single deployable。这个判断在框架能力上没有错，但输入不完整。

## 真正遗漏

项目已有两个关键交付事实没有进入推理：前端主目标是 ChatGPT Sites，同时需要 localhost 开发；Trusted Backend 是本机服务，通过 tunnel 暴露公网 API。

这意味着物理部署边界天然就是 frontend/backend 两个 runtime，不能再用 Next Route Handler 把它们合并。

## 最终选型

```text
Next.js 16 frontend
  ├─ local development
  └─ ChatGPT Sites
        │
        ▼
NestJS 12 backend
  └─ local runtime → tunnel → public HTTPS API
```

Node 24 LTS，pnpm 11；仓库使用 pnpm workspace，但 S1-B 只创建真实存在的 `apps/web` 与 `apps/api`。

## 为什么这是一次有价值的纠偏

架构不能只从代码职责推导，还要把 deployment environment、network boundary、secret location 当成一等输入。机械 Gate 只能证明“当前文档自洽”，不能替代“输入是否完整”的审计。

幸运的是，问题在安装依赖和写业务代码之前被发现，因此只需修订 ADR/Topology，没有迁移成本。

## 后续验证

S1 要用真实证据确认 Next local source 对 Sites 的 build/preview compatibility，以及 Nest/tunnel 的 health、CORS、TLS 和生命周期；这些不能在 S1-A 靠假设冻结。


## S1-B｜Workspace Candidate

S1-A baseline `chatweb@766dc40` 后，建立了 pnpm workspace，只包含 `apps/web` 与 `apps/api` 两个真实运行单元。S1-B 没有写任何 page、Nest bootstrap 或 Chat 业务代码。

真实 lockfile 固定 Next `16.3.4`、React `19.2.8`、Nest `12.0.1`；Node 基线为 24 LTS，pnpm 为 `11.21.0`。

执行时第一次“批量写 + install”复合进程超时。恢复磁盘与进程事实后确认没有残留 install，才单独执行 lockfile resolution；registry 网络很慢但最终成功。这个案例再次验证：超时不等于失败，非幂等/有状态命令必须先恢复状态再决定是否重试。

S1-B Mechanical Gate 已 PASS，并在用户继续授权后提交为 `chatweb@b93a975`；随后进入 S1-C。
## S1-C｜最小可运行 Runtime Skeleton

S1-C 首次真正出现运行源码，但仍只有四个文件：Next 的 `layout/page` 与 Nest 的 `main/AppModule`。没有 controller、health、Conversation、Streaming、Model、RAG 或 shared package。

真实 `pnpm build` 同时通过 Next production build 与 Nest TypeScript build。Next 首次 build 会主动修订 tsconfig：补 `.next/dev/types/**/*.ts`，并把 `jsx` 改为 `react-jsx`；这类框架事实应接受后审计，而不是为了保持手写配置“漂亮”再覆盖回去。

运行验证中 Next 在 3100 返回 HTTP 200；Nest 在 3101 成功启动，根路由返回 404。这个 404 是预期状态，因为 health/controller 属于 S1-E，不能为了让 smoke 变绿提前跨阶段造 route。

第一次给 Next 生产 server 传测试端口时使用 `pnpm ... start -- -p 3100`，Next 把 `-p` 当成项目目录导致失败；改成 `pnpm --filter @chatweb/web exec next start -p 3100` 后通过。保留这个失败，是为了区分“CLI 参数透传错误”和“应用启动失败”。

结构审计时 CodeGraph 因 ChatWeb 尚未建立索引不可用，因此没有为了工具擅自初始化仓库元数据；Repomix + 当前磁盘精确搜索确认 web/api 双向 implementation import 都为 0。S1-C Mechanical Gate 已 PASS，并在用户继续授权后提交为 `chatweb@695cf81`。


## S1-D｜为什么没有创建 shared contract package

S1-D 的任务是验证“是否已经存在真实共享 contract”，不是为了 monorepo 外观去创建 `packages/shared`。基于 `chatweb@695cf81` 的 Git-tracked source，Web 只有 `layout/page`，API 只有 `main/AppModule`：fetch/API usage=0、Nest route=0、wire DTO/type=0、cross-app import=0。

因此当前 shared contract 的正确结果是 `NOT_REQUIRED_BY_CURRENT_EVIDENCE`。简单 health path、API base URL 或 primitive config 不足以制造一个 package；第一次真正需要两侧共同维护 request/response/error/event shape 时再重开，S3 streaming event protocol 是可能触发这一条件的阶段。

审计过程还出现两个值得保留的脚本错误：第一次递归搜索误扫 `.next` 生成物；第二次 Git `**` pathspec 漏掉 API 直接子文件。最终只采用 `git ls-files apps/web/app apps/api/src` 得到的 tracked source 集合，避免把生成物和 pathspec 假设混进架构裁决。

## S1-E｜Health、公开配置与 Secret Boundary

S1-D 在用户继续授权后提交为 `chatweb@8c732ab`。S1-E 第一次建立真正的 Frontend→Backend 网络配置，但仍不进入 Chat 业务：Nest 增加 `/health`、loopback-only bind、显式 CORS allowlist；Next 只读取 `NEXT_PUBLIC_CHATWEB_API_BASE_URL`。

Backend 把“本机 runtime”落实为可验证约束：默认 `127.0.0.1`，`0.0.0.0` 被拒绝，公网访问只能走 tunnel；CORS `*` 也被拒绝。Frontend 的生产 remote API base 必须 HTTPS，只有 localhost/loopback 可以 HTTP。这个边界让“公网地址是公开配置”和“Provider/RAG credential 是 secret”不再混在一起。

真实 `pnpm build` 通过；API malformed config 与 Frontend malformed public config 都做了 fail-closed 验证。运行时 `/health` 返回 200；允许 Origin 得到 ACAO，未列入 allowlist 的 Origin 不得到 ACAO。构建 Web 时注入 synthetic private probe，`.next` 中命中为 0，而 public API base 正常进入产物并由页面渲染。

过程里有两个小纠偏：root 没有 `./node_modules/.bin/tsc`，因为 TypeScript 是 app-scoped dependency，改用 `pnpm --filter @chatweb/web exec tsc`；第一次 source secret scan 只扫 tracked files，漏掉 working-tree 新文件，最终改成直接扫描当前源码并排除 build artifacts。

S1-E Mechanical Gate 与 User Review 均 PASS，正式提交为 `chatweb@b6bc85f`。
## S1-F｜边界审计为什么可以“零代码变更”

S1-F 不是继续堆功能，而是把 S1-A～S1-E 的架构声明反向投射到真实仓库：依赖方向、源码 import、Browser env、tracked env、loopback/CORS、tunnel ownership、future-module leakage 和 workspace 结构必须同时成立。基线是 `chatweb@b6bc85f`。

最终审计证明 Web 没有 Nest dependency、Route Handler、Server Action 或 backend implementation import；API 没有 Next/React dependency；Browser 只接触 `NEXT_PUBLIC_CHATWEB_API_BASE_URL/NODE_ENV`；真实 env 文件均被 ignore；Backend 只接触 `PORT/HOST/CORS_ORIGINS`；tunnel 没有变成 Chat Domain 可执行依赖；S2+ 目录仍不存在。因此正确结果是“边界成立，不改代码”，而不是为了显示工作量制造重构。

第一轮 Gate 的两个 FAIL 反而提供了审计方法论证据：CORS 检查把实现表达写死成单一字符串，source-scope 又把 README 当源码。两项都属于 Gate 假阴性。先读取真实实现确认语义，再修 Gate、完整重跑；没有为了迎合测试去改正确代码。第二轮 `S1F_ARCHITECTURE_SECRET_BOUNDARY_GATE=PASS`，User Review 通过并正式提交为 `chatweb@1b199e6`；随后进入 S1-G。


## S1-G｜从 quota blocker 到真实 Sites PASS

S1-G 本地链路先完整通过：Web/API typecheck、Next/Nest production build、Web/API runtime smoke、CORS、secret probe 都有真实证据。长 Gate 改为 `/tmp` 日志 + exit marker，避免工具 session 消失后只能猜结果。`tsc --noEmit` 还暴露了 `tsconfig.tsbuildinfo` 生成物，最终补 `*.tsbuildinfo` ignore；runtime cleanup 则证明“MCP session 消失”不等于 child Node 已退出，必须以真实 listener 为准。

第一次进入 Sites 时遇到 Work 5 小时额度耗尽。这里没有把 external quota 写成 incompatibility FAIL，也没有把“官方理论支持”写成 PASS，而是保持 `LOCAL_PASS / SITES_BLOCKED_BY_WORK_QUOTA` 等真实执行恢复。

额度恢复后，使用同一份 `apps/web` 源码做真实 Sites Gate。原始 Next.js 16 production build 本身 PASS，但默认 `.next` 不能直接满足 Sites 静态归档：需要 `out/index.html` 和 hosting manifest。Sites 只补了 `next.config.ts -> output: "export"` 与 `.openai/hosting.json -> static.directory="out"`，之后 compatibility/package check PASS，并成功保存未部署 Version 1；原有 `package.json`、`layout/page/runtime-config` 哈希保持不变。

把兼容层同步回本地后，又发现一个容易漏掉的副作用：`output: "export"` 会让 `next start` 真实 exit 1。因此不能只说“Sites 能部署”就结束，还要保证 localhost 工作流闭环。最终锁定 `serve@14.2.6`，形成 `next dev`（开发）→ `next build`（同一静态产物）→ `serve out`（本地生产预览）→ Sites（公网托管）的单源码链。两条本地运行路径都 HTTP 200，最终 typecheck/build/secret/cross-import/lockfile Gate 全 PASS。
