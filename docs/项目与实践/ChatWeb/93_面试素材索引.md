## 30 秒版本

我把原本依附在 RAG 场景里的 Chat 能力拆成独立 ChatWeb 产品：先用 Conversation/Message/ChatRun 固化消息事实和生成尝试，再通过 Provider-neutral Streaming、Context/RAG、Citation、Settings 和 Tool boundary逐层扩展。前端是 Next static export，正式目标是 ChatGPT Sites；后端是本机 Nest Trusted Runtime，经 HTTPS gateway 提供能力，secret/model/tool transport 永远不进 Browser。后来又把工程验证壳产品化成支持 Fast/Think、Vision/File、Search/Citation、READ_ONLY MCP、Voice、Stop/Retry 的日常 Chat，并通过真实 Browser Final Product Gate。

## 最值得展开的技术主线

- 为什么 Chat 产品不能围绕 RAG API 组织主流程。
- 为什么 Message 与 ChatRun 必须分开，才能正确表达失败、Stop、Retry。
- 为什么 ModelProvider / ContextProvider / ToolProvider 必须分开。
- 为什么 Browser 只表达公开 capability selection，endpoint/key/model mapping/schema/transport 留在 Trusted Runtime。
- 为什么 shared contract 在真实双端 consumer 出现后才建立。
- 为什么最终 Browser E2E 要验证真实交付 artifact，而不是 dev HMR。
- 为什么 discovery、readiness、enablement、execution、approval 不能混成一个“工具可用”。
- 为什么模型/工具/自动化失败必须先恢复 owner reality，再决定是不是产品缺陷。

## S12｜Chat Productization / Multimodal / MCP / Voice

这是目前最完整的一段产品工程故事，可以拆成六条线讲。

### 1. Thinking 产品抽象

用户需要“深度思考”而不是模型下拉框。Browser 只发 `thinkingMode`，Runtime 持有 Fast/Think mapping。当前 MLX reasoning 会混入 content，因此做 hidden reasoning pass → clean final pass，并用 regression + real Browser 证明 raw reasoning 不进入 SSE/Assistant。

可追问：为什么 Search structured decision 要强制 non-thinking；Retry 为什么冻结旧 thinkingMode。

### 2. Attachment / Vision / Document ownership

Attachment 属 immutable UserMessage，raw bytes 留在 bounded AttachmentStore；Browser ChatRun 只提交 attachment IDs。Vision 在 Runtime 内构造 provider-neutral image part；PDF/DOCX 走 bounded untrusted document extraction。

最好的故障故事是“PDF/DOCX 首次真机拒答”：extractor、production-dist messages、direct phone replay、transparent outbound proxy 都证明 payload 正确，最终归类小模型/运行态偶发，而不是盲改 parser。

### 3. Tool UX 与 MCP execution ownership

Wave E 只先做 public Tool metadata/UX，并真实发现 internal Citation `providerId` 泄漏，最终建立 explicit internal→public projection。

F1 又证明“本机已有 shared MCP owner 时不能为了 ChatWeb 再 direct-spawn”；F2 再把 readiness 与 execution authority 分开：Playwright 有 broker endpoint所以 READ_ONLY one-hop 可执行；Local Dev 没 endpoint 就必须 fail-closed。Chrome MUTATING 在 Approval Flow 前始终 unavailable。

可追问：为什么“一个 MCP 进程”并不自动等于“多个 consumer 有 session isolation”。

### 4. Voice 不另造 Runtime

主链是 Browser SpeechRecognition → Runtime Qwen Fast bounded Normalize → normal ChatRun → Browser speechSynthesis。Normalize 只能整理 transcript，不能替用户回答。server-side STT 只是 optional seam，不为过 Gate 在旧 Mac 另部署 ASR。

真实证据：API 83/83、Web 10/10、真人两轮 normalize 201 → chat 200、用户确认实际听到 TTS。

### 5. 产品 UI 边界由真实使用纠正

黑色 `N` 最终被证明是 Next Dev Tools indicator，不是个人中心；因此产品明确不做 Profile/Account/User Menu。

附件入口也按用户心智从“＋/file picker”收敛为 Paste + Drag&Drop。Drag&Drop 已真实 E2E；Paste 自动化因为当前 Playwright 无法桥接 macOS system clipboard而保留 harness gap，没有用 synthetic ClipboardEvent 冒充 PASS。

### 6. Final Product Gate 与自动化纠偏

最终 fresh Browser 重新串起整个产品：Fast=`FAST-OK`、Think=`THINK-OK`、真实 Drop Vision/File=`RED | FILE-CODE-731`、Search=完整回答+5 Citation、Chrome READ_ONLY MCP=`MCP-OK`、Stop cancel=201、同 scene Retry 完整生成。

收尾还发现 shared Playwright 的关键区别：**single raw owner ≠ per-consumer session isolation**。解决方式没有回到“多开一个 Playwright”，而是把通用 atomic target-bound scene 规则提升到公共 Acceptance Skill；ChatWeb 项目只保留产品事实。

机械终态：`S12_FINAL_PRODUCT_GATE=FINAL_PASS / S12_CHAT_PRODUCTIZATION=FINAL_ACCEPTED`。
