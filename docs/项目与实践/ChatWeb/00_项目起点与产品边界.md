# 00｜项目起点与产品边界

状态：持续更新；当前同步到 ChatWeb `S0_ARCHITECTURE_USER_REVIEW`

## 为什么要把 ChatWeb 单独拆出来

最初 Chat 能力出现在 ProFlow RAG 的验证与使用链路里，很容易形成一个错误心智：把“RAG 的前端”当成“Chat 产品”。一旦这样组织，Conversation、Streaming、模型选择、Retry、Citation、Settings 甚至未来 Tool/MCP 都会围绕 RAG 的接口长出来，普通 Chat 反而失去独立性。

因此拆仓不是代码搬家，而是重新定义产品 ownership：

```text
ChatWeb = Chat UI + Conversation/Run + Streaming + Provider Runtime + Public Delivery
ProFlow RAG = Knowledge Capability
```

ChatWeb 在完全移除 RAG adapter 后仍必须能通过 Model Provider 正常聊天。ProFlow RAG 通过稳定的 Context Provider Contract 接入，只向 ChatWeb 暴露通用 context/provenance/citation，不把知识构建内部模型带进来。

## 为什么 RAG 只能是外部能力

RAG 内部真正关心的是 Source、Corpus、Chunk、Embedding、Index、Retrieval、Rerank、Snapshot 与知识版本；Chat 产品关心的是用户消息、运行状态、流式反馈、模型选择、上下文装配、失败和重试。两边的核心对象和生命周期不同。
如果 ChatWeb 直接依赖 Chunk、Embedding、pgvector、Corpus 或 Snapshot，它就不是通用 Chat Runtime，而是另一个 RAG 前端。这个边界因此被列为用户已确认方向，只有产品方向改变时才重开。

## ChatWeb 真正拥有的东西

- Chat UI 与用户交互。
- Conversation / Message / ChatRun 的聊天执行语义。
- Streaming、Stop、Retry、Error、Partial Output。
- Model Provider 与 Context Provider 的稳定协作边界。
- Citation 与受控 Rich Output 的通用展示；Artifact 只在真实 producer 出现后增量设计。
- Provider/Model/Context Settings 与 trusted runtime config。
- Public Web Delivery、health、observability 与 E2E。

## 现在明确不拥有的东西

- RAG ingestion、Chunk、Embedding、Vector DB、Corpus、Snapshot build。
- 账号/RBAC/计费、多用户协作和跨设备云同步。
- Conversation branch tree 与完成回答的 Regenerate/多答案切换。
- 长期 Memory 产品。
- 自主 Agent planner/executor 与复杂 Tool approval workflow。

这些不是“永远不能做”，而是 V0 没有证据需要时不提前建设。
