# 00｜项目起点与架构基线

状态：实现主线已冻结；Post-V0 Maintenance baseline 待本轮 Final Review

## 为什么做这个项目

ProFlow RAG 不是为了做一个“能聊天的 Demo”，而是用公开 ProFlow 仓库完成一套真实、可验证、可展示的 RAG Capability Service；实现过程本身同时承担 RAG 学习和求职项目证据积累。

## 当前产品目标

`proflow-rag` 负责把公开 GitHub `main` 的源码、文档和测试构造成可追溯 KnowledgeSnapshot，并对外提供 Retrieval / Evidence / Context / Citation 能力。独立 `chatweb` 作为 consumer，负责 Conversation、Generation、Streaming 与 Chat UI。

## 为什么先做 SDD

项目一开始就存在知识构建、检索、模型、对外 Contract、端侧算力、审计、Eval 等多条链路。若直接写代码，最容易出现组件先长出来、边界后补的情况。因此先用 SDD 固定需求、系统边界、验收和变更流程，再进入实现。

## DDD 是怎样进入项目的

最初 Spec 曾按 Source Sync、Embedding、Retrieval、Rerank、Conversation 等技术组件平铺，后来收敛为 Knowledge Management、Grounded Answering、Quality & Evaluation 三个 Context。2026-09-06 ChatWeb 分仓后，Grounded Answering 再次重基线为 `RAG Query Orchestration`：Answer/Conversation/Generation 移交 ChatWeb，RAG 只保留 QueryExecution 到 Evidence/Context/Citation 的 ownership。

这两次调整共同说明：SDD 管项目设计生命周期，DDD 管领域语义与 ownership，Capability Spec 管 RAG 技术纵深，Verification 负责证明实现满足规格；真实实现发现边界错误时，应 amendment Spec，而不是让旧目录继续绑架架构。

## 最终实现路线

项目最后形成的不是“向量检索 Demo”，而是一条连续工程链：`Git source authority → immutable Snapshot → Corpus/Chunk → PostgreSQL/pgvector → Embedding → Hybrid Retrieval/RRF → Evidence → Context → Citation → public RAG API → Eval → ChatWeb consumer → Runtime/Readiness → rebuild/activate/rollback operator → Maintenance Mode`。

V0 Final Accepted 后又做了一次 Post-V0 consolidation：把拆仓前 Chat/Site/Phone/Tunnel 等 legacy 规格迁出 live authority，删除只有 README 的假 capability placeholder，清掉真实数据库里从未使用的空 `answering/quality` schema，并把 rollback 从 Domain 能力提升为正式运维入口。这个尾段没有增加 RAG 算法，它解决的是“项目做完以后，仓库是否真的适合作为长期服务继续维护”。
