# 93｜面试素材索引

这个文件只收敛已经有工程证据的内容，不提前编故事。

## 项目主叙事

目标：把公开 ProFlow GitHub `main` 建成一套可追溯、可评估、可独立运行的 RAG Capability Service。知识构建、检索、Evidence/Context/Citation 与 Eval 在 `proflow-rag` 内闭环；独立 ChatWeb 只通过稳定 Contract 消费 RAG，不知道 pgvector、Chunk、Embedding build 等内部实现。

## 当前可讲的架构点

- 为什么用 SDD 管设计生命周期，同时用 DDD 管 ownership。
- 为什么 ChatWeb 分仓后把 Grounded Answering 重基线为 RAG Query Orchestration。
- 为什么 Source 必须绑定 immutable commit/path/line。
- 为什么 Source Chunk 与 Vector Input 不是 1:1，37 个超长 Chunk 可派生多个 windows。
- 为什么 PostgreSQL + pgvector 足够支撑当前 7,670 vector V0，而 ANN 需要 latency+Recall A/B 后再决定。
- 为什么 QueryExecution 必须先 pin Snapshot，避免一次请求混用两个知识版本。
- 为什么 Published KnowledgeReadContract 不能暴露 build/activation repository 与 indexBuildId。

## 当前 30 秒版本

我把公开 ProFlow 仓库做成了一个 headless RAG 服务。先把远端 `main` 固定成 immutable commit，再用版本化 Corpus Policy、结构化 Chunk、PostgreSQL/pgvector 和 EmbeddingProfile 构建可激活 KnowledgeSnapshot；目前真实基线是 806 documents、7,624 Source Chunks、7,670 vectors。在线查询侧按 snapshot-bound Contract 读取 lexical/vector candidates，Query 看不到内部 index identity。整个项目用 Mechanical Gate + Eval 验证 source、hash、向量 profile、activation/rollback 和 read-only invariants，而不是只看最终回答“像不像对”。

## 已验证的问题案例

- TypeScript 7 / NestJS 12 的 NodeNext/ESM 边界。
- 手机 Runtime 没有 embedding endpoint，最终把 Embedding 回退到 Mac llama.cpp，同时保留手机 Generation 为另一产品能力。
- 第一份社区 Q4 缺 dense modules，与 Q8 不在同一 embedding space；通过 cosine/pairwise correlation 识别。
- Full embedding supervisor 曾失败，最终改进错误证据、token bucket 与恢复流程。
- P1-H 发现 IngestionRun 规格缺口，并通过 RED→补 persistence→全量 Eval 收口。
- P2-B Published Contract 初版在类型层泄漏 Knowledge Domain DTO，自审计后改成 contract-owned DTO。

## 后续逐阶段补充

每个完成阶段至少沉淀：30 秒项目表达、3 分钟深入版本、2~5 个高概率追问、一个真实问题案例、一组可展示 Verification/Eval 数据、对应 Git commit。


## P2-C Hybrid Retrieval 可讲案例

- 不把 FTS score 与 vector distance 直接相加；先以 `snapshotId+chunkId` 去重，完整保留 lexical/vector branch rank 与原始 score/distance。
- 补齐真实 `text query → Embedding → lexical/vector → HybridCandidatePool`，而不是用 self-query fixture 冒充在线 Hybrid。
- runtime identity guard 首版错误依赖 `/v1/embeddings` response model，实测发现是 request echo；改为 `/v1/models` 权威 loaded model 校验。
- 当前 Mechanical evidence：fixture `10+10→19 unique/overlap1`，真实 text query union=20，model guard/single-snapshot/read-only DB 全 PASS。

## P2-D RRF Fusion 可讲案例

- Hybrid Pool 不比较 FTS score 与 cosine distance，而用 `Σ 1/(k+rank)` 把各 branch 相对排名转换成统一 fusion order。
- RRF 结果新增 `fusionRank/fusionScore`，同时原样保留 lexical/vector branch evidence，便于 Trace/Eval 定位排序来源。
- 专门把 raw score/distance 改成相反极值，结果仍完全一致，机械证明实现只依赖 branch rank。
- `k` 不在实现阶段拍脑袋冻结；当前 smoke 用 60，最终参数交给 P2-F 固定 Dataset 的 Recall/MRR/ordering A/B。

## P2-E Reranker 可讲案例

- 先验证 Runtime contract，而不是看到手机里有模型就默认能 rerank：MLXHub 健康但 `/v1/rerank`、`/rerank`、`/v1/reranking` 全 404。
- 同一 sanity 淘汰两个“看起来合理”的候选：Qwen3-Reranker Q8 排序对但 3 docs≈57.53s；Q4≈11.65s但把无关文档排第一。
- 最终用 `llama.cpp b10516 + BGE-Reranker-v2-M3 Q4_K_M`，固定 revision/SHA，真实 ProFlow query 把直接描述 Start readiness 的 Chunk 从 RRF 第二提升到 rerank 第一。
- `RerankPort` 只处理 bounded prefix；Adapter 严格验证完整 permutation 与 score，timeout/profile mismatch/invalid response/model unavailable 全部显式回退原 RRF 顺序，不伪造 rerankScore。
- latency sweep 证明文本预算是老 Intel 的主要成本：2×200≈4.55s、3×200≈6.33s、3×300≈9.02s、3×600≈22.50s；正式 budget 留 P2-F Eval 决定。

## P2-F Retrieval Eval 可讲案例

- 建立 13-case 固定 Gold（8 Natural + 5 Exact Engineering），每题绑定 immutable source provenance，并证明 13/13 来自既有 P1 人工 case，防止 post-hoc 调题。
- Eval 先发现 online lexical Recall@10 只有 0.1538，与 P1 EXACT_INDEXED=1.0 冲突；沿调用链定位为 P2 漏接 exact signal，修复生产 read path 后 lexical R@10=0.6923，Exact 子集=1.0。
- RRF sweep 不只追 MRR：d5/k10 MRR=0.6692 但会漏 Gold；最终按 Recall-first 选 d20/k30，Recall@10=1.0、MRR=0.6581。
- 最终持续负载 rerank A/B 在 15s eval ceiling 下 0/13 成功、13/13 timeout fallback，因此 BGE/RerankPort 保留但默认关闭；fallback 后 RRF 指标完全不变。
- Query Embedding timeout/unavailable 降级 lexical-only；profile/model invariant mismatch 仍 fail closed。这个设计区分“服务暂时不可用”和“知识空间不一致”两类故障。

## P3-A Evidence / Context Rebaseline 可讲案例

- 没把 RRF Top-K 直接拼成 Prompt，而是先把 Candidate、Evidence、ContextBundle 拆成三层：Candidate 是检索排序结果，Evidence 是实际采用且可回溯 source 的事实，Context 是预算内的 consumer payload。
- EvidenceSet 强制 single-snapshot、Evidence/Chunk 唯一、selectionRank 连续；`AVAILABLE | NO_EVIDENCE` 形状先冻结，P3-D 再冻结状态语义，semantic acceptance threshold 若需要则留 P3-E Eval 校准。
- ContextBundle 用 `maxCharacters` 做 V0 model-agnostic budget，而不是绑定某个 GPT/Qwen tokenizer；FAST/THINK、Conversation、Prompt、Generation 都不能反向改变 RAG Context 语义。
- Context 的 source refs 必须与 selected Evidence 的 immutable source coordinate 精确一致，但这仍不是 Citation；P5 只能单向从已选 Evidence 派生 provenance。
- `pnpm verify:p3a` 完整 exit 0，机械覆盖 cross-snapshot、NO_EVIDENCE 空形状、source drift、unknown evidence、budget overrun，以及 P4/P5/Generation 字段不得进入 P3-A。

## P3-B Evidence Selection 可讲案例

- 没把 RRF Top-K 直接改名成 Evidence，也没有再用 fusionScore/rerankScore 做第二次相关性打分；P3-B 只消费统一的 final rank 语义并保持相对顺序。
- 默认 Retrieval baseline 的 reranker 是 OFF，因此用 `RankedEvidenceCandidate(snapshotId, chunkId, candidateRank)` 解耦具体排序实现：RRF 路径映射 fusionRank，未来显式 rerank 可以映射 finalRank。
- Evidence 集合用 `contentSha256` 去 exact duplicate，并用显式 `maxPerSource/maxEvidence` 治理单源垄断和集合大小；两个参数当前没有拍死，正式 baseline 留给 P3-E Eval。
- selection reason 不写进 Evidence，而是独立 decision trace，区分 `SELECTED / DUPLICATE_CONTENT / SOURCE_LIMIT / EVIDENCE_LIMIT`，保持 Evidence identity 稳定且选择过程可审计。
- `pnpm verify:p3b` 完整 exit 0；真实 snapshot1 frozen RRF 输入 39 candidates，probe 选出 5 条且严格保持 candidateRank 顺序；rerank default 仍 OFF、DB read-only、Context/Citation 尚未实现。

## P3-C Context Building 可讲案例

- 没把 Context Building 做成简单 `Evidence.content.join()`，而是明确“P3-B 决定 Evidence priority，P3-C 只能在预算下表示其连续前缀”，防止 Context budget 形成隐藏的二次 selection。
- 采用 whole-Evidence prefix：严格按 selectionRank 加完整 Evidence；不能跳过高 rank Evidence 填空间，也不能截半 Evidence，从而保持 content hash/source coordinate 与真实 payload 一致。
- 固定 `\n\n---\n\n` separator，运行时 7 characters，并把 separator 本身纳入 `maxCharacters`；`usedCharacters` 始终等于最终 payload 真实长度。
- 第一条 Evidence 都放不下时 fail closed，而不是伪装 `NO_EVIDENCE`；区分“预算不足”和“证据结果/执行降级”，后者由 P3-D 建模，semantic relevance threshold 若需要则留 P3-E Eval。
- truncation 的 omittedEvidenceIds 必须精确等于 EvidenceSet 未纳入的有序 suffix；evidenceIds/source refs 同序，保证后续 P5 provenance 可沿已用 Evidence 单向派生。
- `pnpm verify:p3c` 完整 exit 0；真实 snapshot1 链路 selected=5、included=2、omitted=3、usedCharacters=7718，DB read-only；probe budget 不冻结产品 baseline，正式值留 P3-E Eval。

## P3-D No Evidence / Degradation 可讲案例

- 把 `AVAILABLE | NO_EVIDENCE` 与 `degradation[]` 建模成正交维度：Embedding timeout 后 lexical-only 只要仍有 Evidence，最终就是 `DEGRADED`，不会误报“没有证据”。
- 结构性空 final candidates 明确得到 `NO_EVIDENCE / EMPTY_FINAL_CANDIDATES`；即使执行中发生 Embedding unavailable，No Evidence 仍保留 degradation trace，consumer 能同时知道“结果为空”和“执行降级”。
- 没拿 RRF `fusionScore` 直接当 relevance probability：默认 reranker OFF、没有校准 acceptance signal，因此有候选却要求 NO_EVIDENCE 时 fail closed，semantic threshold 留 P3-E 固定 Eval 决定。
- degradation reason 使用 stage-qualified code，区分 Retrieval Embedding 与 Rerank 的 timeout/unavailable/profile/invalid-response，避免裸 `TIMEOUT` 失去排障语义。
- `pnpm verify:p3d` 完整 exit 0；真实正常链最终 `COMPLETED`，真实 Embedding timeout → lexical-only 链最终 `DEGRADED`，DB read-only；第一次 Gate 结果不可恢复时先恢复进程/Git 状态，再用持久日志重跑并以唯一完整 exit 0 作为证据。

## P3-E Evidence / Context Eval 可讲案例

- 没把 P3-B smoke 的 `5/2` 或 P3-C probe 的 `7718 chars` 当产品参数，而是复用 13-case 人工 Gold 做 Recall-first sweep；最终最小 full-coverage Evidence baseline=`maxEvidence=9 / maxPerSource=2`。
- Context 先做 coarse sweep，再按每个 case 最后一个 Gold Evidence 的 selectionRank 反推 whole-prefix 精确字符需求，最终从粗档 32000 收敛到 `25748`；13/13 Gold coverage 仍为 100%。
- 加 8 个 exploratory out-of-scope query 审计 semantic signal，发现正负 top1 RRF score 重叠；保持所有正例时只能拒绝 37.5% 负例，因此明确冻结 `semanticAcceptance=NONE`，拒绝把 fusionScore 冒充 probability。
- 把 Eval 结果写成 `EVIDENCE_CONTEXT_BASELINE`，并让 Eval 反向断言代码里的 `9/2/25748/NONE` 与固定 Gold 推导一致，防止未来只改常量不改 evidence。
- P3 最终把 A～E 合成一次 `pnpm verify:p3` Stage Gate：一次 architecture/typecheck/build/DB/runtime 后连续回归全部能力，完整 exit 0；这是“提高吞吐但不降低验证强度”的工程治理案例。


## P4 RAG Capability API 可讲案例

- 把 ADR-012 留下的 P0 `site-api-contract` 正式迁移成 `@proflow-rag/rag-api-contract`，让 ChatWeb/CLI 只依赖跨进程 DTO，不 import RAG Domain/Repository。
- `POST /v1/rag/query` 不把 HTTP 当“万能配置入口”：固定消费 P2 `20/20/k30/rerankOff` 和 P3 `9/2/25748/NONE`，consumer 只允许把 Context budget 向下缩小；未知 `maxEvidence/rerank/snapshot` 等字段直接 400。
- `ExecuteRagQuery` 保持 framework-free，Nest Controller 只做 validation/mapping；因此 Delivery 不拥有 Retrieval/Evidence/Context 规则。
- 真实 HTTP smoke 启动 build 后 Nest/Fastify，经 PostgreSQL + Embedding 完整走 RAG 链；正常/narrow/invalid/expanded/tiny-budget 全验证，DB read-only，P5 Citation 与 Generation 都未抢跑。
- 第一次 smoke 因 10 秒 startup window 在并发负载下产生假阴性；通过独立启动真实 API 证明产品正常，再把 harness 改成 30 秒上限 + child-exit/log evidence。这个案例可以讲“如何区分产品故障与验证工具故障”。

## P5 Citation / Provenance 可讲案例

- 没让 LLM/ChatWeb 生成 URL，而是从 final selected Evidence 的 immutable SourceCoordinate 确定性派生 `citationId/evidenceId/snapshotId/contentSha256/source/url`；provenance truth 留在 RAG。
- GitHub permalink 固定使用 `/blob/<40-hex-commit>/<path>#Lx-Ly`，并 fail closed 校验 Evidence source commit 必须等于 QueryExecution pinned Snapshot commit，避免历史回答随 `main` 漂移。
- Citation 顺序严格等于 Evidence selectionRank；Context truncation 只决定哪些 evidenceIds 进入 payload，不触发新的 Citation selection。完整 EvidenceSet 仍保留全量 citation，方便审计 omitted Evidence。
- `NO_EVIDENCE → citations=[]`；P5 不重新读取 Knowledge、不改 P2/P3 baseline、不拥有 Generation。真实 HTTP smoke 返回 9 条 Citation，与 9 条 Evidence 逐项 identity/hash/source 对齐，DB read-only。
- P5 使用 Batch-first 原子 patch：第一次 README anchor 漂移时整批 0 mutation；修正后 15 个既有文件 + 3 个新文件、24 个 anchor 一次写入并通过唯一 `verify:p5`。


## P6 RAG Quality Eval 可讲案例

- 没用“最终回答看起来对”当 RAG 质量，而是同一 EvalRun 分层观察 Retrieval、Evidence、Context、Citation、Snapshot/Contract、No Evidence、degradation 与 latency。
- 复用 13-case immutable Gold，正式 public HTTP Eval 的 Evidence/Context full Gold、Citation correctness、Snapshot/Contract consistency 均 100%，DB read-only、rerank default OFF。
- 首次统一得到旧 Mac API total mechanical baseline：p50=1800.29ms、p95=11504.95ms；明确它不是产品 SLO，P7/P8 再测 integration/runtime overhead。
- targeted Eval 首次因 benchmark SQL join 写错失败；先分类为 Eval adapter defect，再读取正式 Snapshot repository 确认 join，只复验受影响 benchmark，最终唯一 `verify:p6` 完整 exit 0。
- P6 也是 Decision-level Batch-first 的第二轮验证：整阶段一次 batch implementation，失败按 blast radius 修复，最终一次 Stage Gate，没有为每个局部门重复结项。

## P7 ChatWeb Integration 可讲案例

- 独立 `chatweb` 仓只用最小 HTTP adapter，request 不允许控制 snapshot/rerank/Evidence/Embedding/DB。
- 真实两仓 API + deterministic Model fixture 证明 0-RAG、required RAG、optional unavailable 与 required fail-closed；Knowledge DB read-only。
- transparent proxy 做同请求 paired measurement，cleanup 后 consumer overhead≈201ms；拒绝用两个独立 run 相减。
- harness open handle、过短 timeout、旧 runner 残留进程均通过 direct runtime / process evidence 分类后修复，而不是降低产品断言。
- P7 也是吞吐方法的跨仓泛化验证：broad scan 误扫 `out` 促成 Minimum-Sufficient Batch。

## P8 Runtime / Operations 可讲案例

- 把 `/health` 从静态 liveness 升级成 `ready/degraded/unavailable` RAG readiness，同时不泄露 DB/model/PID。
- Embedding offline 不等于整体不可用：沿已冻结 degradation contract 保留 lexical-only；DB/Active Snapshot truth 不可建立才 fail unavailable。
- API start/status/stop 用 PID command ownership + bounded shutdown，不使用 `killall/pkill node`，Nest shutdown hook 释放 DB pool。
- Formal Gate 首次失败不是 Runtime regression，而是旧 P6 Eval 30s startup harness 假阴性；分类后只修 harness、targeted 复验，再跑一次最终 Gate。
- P8 首次量化吞吐：DCR≈95.8%、Mutation Density≈8 files/call、batch retry=0；同时承认 polling/harness 仍是剩余主要浪费。


## V0 Release 可讲案例

- Release 前发现仓库虽然有完整 P1 build 能力，却没有正式一键 operator；没有拿 `snapshot-activation-smoke` 冒充产品能力，而是补 `knowledge:rebuild`，把 immutable source→Corpus→Chunk→Index→Embedding→Validate→显式 Activate 串成 repository-owned 运维入口。
- 正式 operator 默认不 `--activate`，在当前 ACTIVE commit 上真实重跑得到 806 documents / 7624 chunks / 7670 embeddings，并证明 snapshot/commit/index build 前后不变；避免“启动服务顺手重建/切知识版本”的危险副作用。
- V0 Gate 不机械重跑 P0～P8 历史 Gate，而是组合每项当前最强证据；最终一次 Gate 覆盖 Knowledge、Retrieval、Citation、13-case public RAG Eval、degradation、Runtime、ChatWeb 22/22 consumer 与 real E2E，exit 0。
- 用户机器重启使第一次 V0 Gate 的 `/tmp` evidence 丢失，没有把 UNKNOWN 猜成 PASS/FAIL；恢复 P1 authority 指定的 Postgres.app PG17 旧 cluster，改用 `.runtime/release` durable evidence 后重新获得唯一可裁决 exit 0。这个案例可用于解释 durable execution、truth/evidence 与 failure classification。
- V0 最终 RAG Eval 仍保持 Evidence/Context/Citation/Snapshot Contract 100%，paired consumer overhead≈151ms；高吞吐执行没有用降低验证强度换速度。
