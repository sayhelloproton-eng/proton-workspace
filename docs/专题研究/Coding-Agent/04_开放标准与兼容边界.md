# 开放标准与兼容边界

> 唯一职责：区分产品私有实现、事实兼容、开放规范和真正可移植能力。

## 标准成熟度阶梯

```text
产品实现
→ 稳定产品约定
→ 事实惯例 / de facto compatibility
→ 开放规范 / public spec
→ 中立治理标准
```

不能因为多个产品“都支持某目录”就直接称为行业标准。

## 当前值得长期关注的开放边界

| 对象 | 主要解决什么 |
|---|---|
| AGENTS.md | 项目级 Agent 指令 |
| Agent Skills / SKILL.md | 可移植程序性知识 |
| MCP | Agent ↔ Tool / Data / Capability |
| A2A | Agent ↔ Agent / Agent System |
| Agent Plugins v1 | Plugin 的开放包装与分发核心 |

Claude Code Plugin 有非常强的生态影响，但它仍首先是一个平台生态约定，不能直接等同于统一开放标准。

## 为什么 Agent Plugins v1 没把所有东西统一

稳定、容易跨 Runtime 的部分主要是：

```text
Skill
MCP
```

而下面这些对象强依赖具体 Runtime：

```text
Commands
Agents lifecycle
Hooks
Permission
Sandbox
Recovery
Memory
```

因此一个健康的标准往往只标准化“稳定边缘”，而不是强行统一 Runtime 核心。

## 兼容至少分三层

### 语法兼容

文件能读、字段能解析。

### 结构兼容

目录、Manifest、Skill、MCP 等对象能被正确映射。

### 语义兼容

生命周期、Hook 时机、Permission、Agent 参数、阻断行为真的等价。

所以：

> 能安装 ≠ 能运行；能运行 ≠ 行为等价。

## Qwen Code 为什么是一个好观察样本

Qwen Code 对开放 Skill / MCP 的直接吸收能力较强，同时更深的 Commands、Agents、Hooks 等并不会天然获得同样语义。这恰好说明：跨平台兼容的“Portable Core”通常停在稳定边缘。

## 对 Plugin 工程最重要的结论

未来不要做“一个 Manifest 统治所有平台”的幻想式抽象。更稳妥的是：

```text
Portable Core
├─ Skill
├─ MCP
└─ 平台无关配置

Runtime Adapter
├─ Claude
├─ OpenCode
├─ Qwen
├─ Codex
└─ 其他平台
```

开放标准负责最大公约数；Adapter 保留各 Runtime 真正有价值的差异。
