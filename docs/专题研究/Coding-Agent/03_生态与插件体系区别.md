# 生态与插件体系区别

> 唯一职责：比较平台怎样包装、安装、分发和组合 Agent 能力。

## Plugin 不是一种能力

本专题冻结的定义：

> Plugin = 能力的包装、安装和分发边界。

一个 Plugin 里可以同时存在：

```text
Knowledge      Tool        Worker       Control
Skill          MCP         Agent        Hook
```

所以不能再把 Plugin、MCP、Skill、Agent 当成同一层概念。

## 四类核心对象

### Skill

回答：**当前 Agent 应该怎么做？**

适合 SOP、流程经验、领域知识、工作方法。它通常依赖模型理解和遵循。

### MCP

回答：**当前 Agent 能连接什么外部 Tool / Data / Capability？**

它是能力连接协议，不负责 Agent 生命周期和组织方式。

### Agent / Subagent

回答：**谁独立去做？**

只有 Context、Model、Permission、Parallelism 或独立判断确实需要变化时，拆 Agent 才有明显价值；否则 Skill 更轻。

### Hook

回答：**某个生命周期节点系统必须确定性做什么？**

Hook 与 Skill 最大区别是：Hook 由 Runtime 确定性触发，Skill 仍需要模型采纳和执行。

## 生态策略差异

### Claude Code

生态影响主要来自完整的工程 Agent 抽象：Plugin、Skill、Subagent、Hook、MCP、Project Instructions 等组合在一起，表达能力最丰富。

### Qwen Code

更像兼容实验场：主动吸收其他生态的指令、Skill、插件结构和开放协议，适合验证哪些资产真正可移植。

### OpenCode

强调 Runtime 可扩展和第三方创新，Plugin / Provider / Agent 都更适合作为开发者可控对象。

### OpenAI / Codex

更强调产品级分发和 Task Runtime；Plugin / App 能力与 ChatGPT 产品体系的分发面结合更深。

### CodeBuddy / WorkBuddy

一个重要特点是对 Claude Code 生态的兼容诉求，方便企业和开发者迁移已有资产，但兼容仍需区分格式与语义。

### GitHub Copilot

生态优势并不只来自 Agent 插件，而是 GitHub 本身拥有 Repo、Issue、PR、Actions、Review 等巨大开发者生命周期入口。

## 判断一个生态强不强，不看插件数量

至少要看：

1. 能力是否有稳定的包装格式；
2. 安装和分发是否顺畅；
3. Runtime 是否真的执行这些语义；
4. 第三方资产是否能升级和版本化；
5. 平台是否拥有足够大的真实工作入口；
6. 跨平台迁移成本是否可解释。

生态的真正价值，是让工程经验从“一次 Prompt”变成长期复用资产。
