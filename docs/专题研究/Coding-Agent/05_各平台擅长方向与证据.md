# 各平台擅长方向与证据

> 唯一职责：说明“支持某功能”为什么不等于“擅长”，并给出当前相对成熟的平台优势判断。

## “擅长”的证据门槛

只有同时接近下面四项，才适合写成平台优势：

> 官方持续主打 + 产品/Harness 结构支撑 + 真实使用模式反复出现 + 已知代价可解释。

因此不能因为某平台刚上线一个按钮，就宣布它“最强”。

## 相对成熟、辨识度较强的方向

### Claude Code：Agent Engineering / Harness 表达

优势来自 Skills、Subagents、Hooks、MCP、项目指令、Permission 等组合，不只是模型本身。

适合：团队希望把工程经验、规则和工作方法真正编进 Agent。

### Codex：Task Delegation / 多任务执行

优势在于完整任务委派、隔离执行工位、后台/云端任务和多任务监督。

适合：希望把“完整任务”而不是“下一行代码”交给 Agent。

### OpenCode：Open Harness / Runtime Ownership

优势是 Runtime 可控、Provider / Model / Agent 解耦。

适合：Agent Platform、模型路由、私有 Provider、第三方 Runtime 扩展。

### Cursor：Human-Agent IDE 协作

优势来自长期积累的 Editor interaction、代码 Context、Diff / Review 工作流。

适合：人仍深度参与整个开发过程。

## 路线明显，但长期独立证据仍需继续观察

- Qoder：Long-running Autonomous Delivery；
- Kiro：Spec-driven Agentic Development；
- Qwen Code：Compatibility-first Open Harness；
- CodeBuddy / WorkBuddy：Enterprise Agent Platform + Claude ecosystem compatibility；
- TRAE：从 Coding 向 Work 的 Agent 产品化。

GitHub Copilot 的 GitHub 生态成熟度非常高，但其“多 Agent 工作入口”仍在快速演进。

## 两两比较更容易看清

```text
Codex vs Qoder
→ 横向任务委派规模 vs 纵向长任务持续交付

Claude Code vs OpenCode
→ Harness 表达深度 vs Harness 所有权

Cursor vs Kiro
→ Human-Agent Interaction vs Intent / Spec 收敛
```

## 使用这些结论时的纪律

- 不写“永久冠军”；
- 不把“新功能支持”升级成“成熟优势”；
- 中国平台与海外平台使用同一证据门槛；
- 产品能力变化快，具体优势引用时重新查当前版本；
- 社区使用反馈是证据之一，但不能替代产品结构与官方合同。
