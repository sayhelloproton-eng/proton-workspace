# Coding Agent 平台介绍与区别｜专题总览与结项上下文

> 状态：专题已完成，2026-09-05 结项。
> 作用：保存本 Chat 的研究边界、关键裁决、正式产物、后续复用规则和停止条件；不替代学习正文。
> 时效边界：平台产品事实以 2026-09-05 前后的官方公开信息为基线。产品能力变化快，后续引用具体功能时需要重新核验。

## 1. 这个专题为什么开始

最初目标不是做“哪个 Coding Agent 最强”的排行榜，而是建立一套能长期使用的平台判断框架：

- 主流 Coding Agent / Agent Workspace 产品分别把什么放在产品中心；
- Model、Harness、Runtime、Task、Workspace 之间怎样分层；
- 生态、Plugin、Skill、MCP、Agent、Hook 分别是什么；
- 哪些能力正在标准化，哪些仍然绑定具体 Runtime；
- 各平台真正擅长什么，判断“擅长”需要什么证据；
- 不同角色应该如何选择平台；
- Usher 这类基于 Claude Code Plugin 协议的资产，跨平台兼容的真实边界在哪里。

研究始终围绕 Coding Agent / Agent Platform，不包含 ProFlow 真实系统教材、端云模型、岗位章节等其他学习线。

## 2. 固定研究视角

专题最终冻结为七个研究视角：

1. 产品：平台把 Chat、IDE、Task、Workspace、Runtime 中哪个对象放在中心；
2. 支撑：Model 之外，Harness / Runtime 如何让 Agent 真正完成任务；
3. 生态：平台怎样定义、吸收、分发和兼容能力；
4. 插件：Plugin、Skill、MCP、Agent、Hook 的真实责任边界；
5. 标准：产品实现、事实惯例、开放规范、中立标准怎样区分；
6. 擅长：平台能力必须通过证据门槛后才能写成优势；
7. 未来：Coding Agent 如何演进为 Agent Workspace / General Work Harness。

角色和平台选型是七个视角的综合结果，不单独增加第八类研究维度。

## 3. 产品族和命名上的关键纠正

研究过程中明确纠正了几类容易造成误判的产品关系：

- OpenAI 应按 `ChatGPT → Chat / Work / Codex` 理解，Work 偏长期多步骤工作，Codex 偏软件与技术任务；
- Anthropic 应按 `Claude → Chat / Cowork / Code` 理解，Claude Code 是 Coding Harness，不等于 Claude 全产品；
- 腾讯不是“CodeBuddy 改名为 WorkBuddy”，而是 CodeBuddy、WorkBuddy、Managed Agents 等形成共享企业能力的产品族；
- Qoder 不只是 IDE，正在形成 Coding IDE / CLI / Cloud Agents 与 Work / Task-centric 产品面；
- TRAE 需要区分 TraeCode 与 TraeWork；
- Qwen Code 已不是单纯 CLI，而是开放兼容型 Coding Harness；
- OpenCode Core 与 Oh My OpenCode（OMO）必须分开，前者是 Runtime / Harness，后者是其上的第三方体验与编排层；
- GitHub Copilot 不能再按“代码补全器”理解，当前已经延伸到 CLI、Agent、Custom Agent、Skills、MCP、Hooks 与 GitHub 生命周期。

后续研究任何产品，必须先把产品族、Runtime、第三方生态和兼容层分开，不能把品牌名变化直接解释成产品替代关系。

## 4. 平台的核心产品分化

专题形成的稳定判断不是“谁功能最多”，而是各平台当前主要优化对象不同：

- Claude Code：Agent + 工程规则，强调可编程 Harness；
- Codex：Task + 多 Agent，强调任务委派、隔离执行与监督；
- OpenCode：Runtime + 用户控制权，强调 Model / Provider / Agent / Plugin 解耦；
- Cursor：Editor + Agent，强调 Human-Agent Interaction；
- Kiro：Intent / Spec，强调先定义需求再执行；
- Qoder：Long-running Task，强调长任务自主交付；
- Qwen Code：Runtime + Compatibility，强调跨生态资产吸收；
- CodeBuddy / WorkBuddy：Organization + Agent，强调企业能力与生态迁移；
- TRAE：Work Mode / Code Mode，强调把复杂 Harness 产品化；
- GitHub Copilot：Repo / Issue / PR / CI / Organization 真值上的 Agent 层。

这些是当前优化方向，不是永久冠军标签。

## 5. Harness / Runtime 的稳定心智模型

专题最终把 Harness 理解为模型之外的“身体、工作记忆、工具箱、工作场地和安全规则”。五根主支柱是：

```text
Loop
Context
Runtime
State
Verification
```

模型决定推理能力的上限，Harness 决定系统是否能稳定接近这个上限。长期任务质量不能只归因于模型能力。

三个最有代表性的 Harness 方向：

- Claude Code：把工程经验、规则、Skill、Subagent、Hook、MCP、Permission 等编进 Agent；
- Codex：给 Task / Agent 提供 Worktree、Cloud / Background 等隔离执行工位，扩展任务委派规模；
- OpenCode：把 Model、Provider、Agent、Tool、Plugin、Runtime 的所有权更多交给开发者。

比较平台时必须区分：`model ability ≠ harness ability ≠ plugin ability ≠ ecosystem ability`。

## 6. Plugin / Skill / MCP / Agent / Hook 的裁决

本专题最重要的插件心智模型是：**Plugin 是能力的包装、安装和分发边界，不是一种单独能力。**

```text
Plugin
├─ Skill：当前 Agent 应该怎么做
├─ MCP：当前 Agent 能连接什么外部 Tool / Data / Capability
├─ Agent：谁作为独立 Worker 去做
└─ Hook：哪个生命周期节点系统必须做什么
```

补充边界：

- Permission 回答“有没有权做”；
- Sandbox 回答“即使获权，最多能影响什么”；
- Verification 回答“怎样证明结果真的发生”；
- Skill 依赖模型遵循，Hook 由 Runtime 生命周期确定性触发；
- 只有 Context、Model、Permission、Parallelism 或独立判断真的需要变化时，拆 Agent 才有明显增量；否则 Skill 往往更轻。

以后不能把 `.claude-plugin`、MCP、Skill、Subagent、Hook 混写成同一层，也不能把“支持某格式”直接写成 Runtime 语义完全兼容。

## 7. 标准成熟度与兼容边界

判断“是不是标准”时统一使用下面的成熟度阶梯：

```text
产品实现
→ 稳定产品约定
→ 其他平台主动兼容的事实惯例
→ 有公开 Spec 的开放规范
→ 中立治理的开放标准
```

本专题确认的稳定边界：

- AGENTS.md：开放项目指令约定；
- Agent Skills / `SKILL.md`：可移植程序性知识；
- MCP：Agent 与 Tool / Data / Capability 的开放连接协议；
- A2A：跨 Agent 系统发现和通信协议；
- Agent Plugins v1：以 Skill + MCP 为稳定核心的开放包装规范；
- Claude Code Plugin：具有很强生态影响和事实兼容性，但不能直接写成行业统一开放标准。

2026-07-28 的 MCP 规范继续走向 stateless core、Extensions、Tasks 和授权强化；Agent Plugins v1 刻意没有统一 Commands、Agents、Hooks 等 Runtime-specific 语义。Qwen Code 的支持矩阵提供了一个很直观的边界样本：标准 Skill / MCP 可直接处理，而更深 Runtime 语义需要平台自己的映射或忽略。

因此以后判断兼容必须至少区分：语法兼容、结构兼容、语义兼容。**能安装不等于行为等价。**

## 8. “擅长”必须经过证据门槛

不能因为平台“支持某功能”就写成“最擅长某方向”。本专题冻结的证据门槛是：

> 官方持续主打 + 产品/Harness 结构确实支撑 + 真实使用模式反复出现 + 已知代价能够解释。

按这一门槛，Claude Code、Codex、OpenCode、Cursor 的核心优势可以相对有把握地写成较成熟方向；Qoder、Kiro、Qwen Code、CodeBuddy / WorkBuddy、TRAE 的路线辨识度已经很强，但部分能力仍缺少同规模长期独立用户证据。GitHub Copilot 的 GitHub 生态已经成熟，但“多 Agent 工作入口”仍在快速变化。

后续文档必须继续使用“值得优先考察 / 当前更有辨识度 / 路线明显”等克制措辞，避免写成静态冠军榜。

## 9. 未来方向的稳定判断

专题对未来的判断不是“所有产品都会变成同一个 Agent IDE”，而是几个共同趋势正在收敛：

1. Coding Agent 是通用执行型 Agent 最成熟的专业试验场之一；
2. 产品中心从 Code / Chat 继续向 Task / Workspace 迁移，IDE 仍保留为专业操作和 Review 视图；
3. Agent 从单 Session 走向 Background、Persistent、Event-driven Worker；
4. Harness / Runtime 越来越像独立平台层；
5. Skill、MCP 等稳定边界继续标准化，而 Permission、Sandbox、Agent Lifecycle、Recovery 等 Runtime 核心仍会保持差异；
6. Multi-Agent 会进入基础设施，但 Agent 数量本身不是成熟度；
7. 多个 Agent 并行后，人类的 Review、Integration、Acceptance 和异常判断会成为稀缺资源；
8. 软件工程价值更多向 Intent、Domain Knowledge、Architecture、Constraint、Evaluation、Trade-off、Judgment 转移；
9. Autonomy 越强，Permission、Sandbox、Credential、Approval、Audit、Observability、Recovery、Evidence 组成的 Trust Runtime 越重要。

可以把总趋势压缩成：

```text
Coding Agent Harness
        ↓
Agent Workspace / Task Runtime
        ↓
General Work Harness
```

它是架构方向，不意味着所有 Coding 产品都会取消 IDE，也不意味着通用 Agent 会完全复制 Coding Agent 的内部实现。

## 10. 角色选型的最终决策图

如果目标只是高效率开发：

- 强 IDE 内 Human-Agent Loop：优先看 Cursor；
- 把较完整独立任务委派出去：优先看 Codex。

如果目标是把团队工程经验编进 Agent：优先研究 Claude Code。

如果目标是拥有和改造自己的 Agent Stack：优先研究 OpenCode。

如果目标是做跨平台 Skill / Plugin：

- Claude Code：学习 Rich Capability / 源范式；
- Qwen Code：做兼容性实验；
- Agent Skills + MCP + Agent Plugins v1：提炼 Portable Core。

如果目标是 Agent Platform / Plugin 工程能力，不应该只押一家平台，建议保持四角实验场：Claude Code、OpenCode、Codex、Qwen Code，分别观察 Harness 深度、Runtime 所有权、Task Delegation 和跨协议兼容。

## 11. Usher 的跨平台架构裁决

Usher 是本专题最重要的真实插件案例。它当前以 Claude Code Plugin 协议为主要表达方式，因此不能简单得出“继续绑定 Claude”或“立即改成统一标准”两个极端结论。

冻结的架构问题是：

```text
            Usher Capability Model
                    │
       ┌────────────┴────────────┐
       │                         │
Portable Core              Rich Runtime Adapters
Skill + MCP                Claude / OpenCode / Qwen / Codex ...
       │                         │
开放标准优先               保留平台真正有价值的差异
```

当前可移植性判断：

- Skill / `SKILL.md`：高；
- MCP：高；
- Agent Prompt / Role：中高，内容易迁，Worker Runtime 不同；
- Agent Runtime 参数：中；
- Hook：中低，生命周期与阻断语义高度依赖 Runtime；
- Plugin Manifest：低到中，可以转换但不是统一能力模型；
- Permission / Sandbox / Monitor / LSP：低，深度绑定具体 Harness。

后续如果重新打开 Usher 兼容专题，正确顺序是：先审计真实仓库的能力层，再做 Qwen Code / CodeBuddy 等真实导入验证，再判断是否需要独立 Capability Model。**本专题没有授权、也没有执行 Usher 重构。**

## 14. 这次执行暴露出的流程教训

### 学习完成不等于文件存在

曾经出现“08 文档已经完整，所以直接跳到 08/07”的判断错误。固定纠正：

```text
文档已写完 ≠ 用户已经学完
```

学习进度只能按实际互动确认：讲解 → 追问/质疑 → 补充 → 形成认知 → 用户认可 → 再沉淀。

### 不要把教材总路线替代当前 Chat 计划

本 Chat 的范围是 Coding Agent / Agent Platform。专题结项后应停止，而不是自动沿 README 继续进入下一章。后续任何“继续，按计划下一步”都必须先锚定当前专题计划，而不是全仓库目录顺序。

### 正文与研究上下文分层

学习正文只承载稳定认知和渐进阅读；研究过程、产品时效、纠错、结项状态、后续复用规则进入 Research 上下文。不要为了保存聊天历史继续膨胀学习正文目录。

### 提交纪律

本专题正文曾按 review gate 执行：先展示变更、用户继续后再提交。新的研究上下文当前仍应先保持未提交，让用户检查；未经确认不自动 commit。
