# 怎样选择合适的 AI 架构

> 唯一职责：比较 Code、Prompt、Chain、Workflow、Graph、Agent、Runtime、Multi-Agent、Platform，给出复杂度升级决策。本章只做选择与综合，不重复维护相邻章节的完整定义。

## 架构选择从最小可控方案开始

### 本节新词

- **Architecture Choice（架构选择）**：不是挑最流行的框架，而是决定“哪类责任由代码、模型、运行时或协作主体承担”。
- **Upgrade Signal（升级信号）**：当前方案出现稳定、可观察的失败，说明缺少某种新责任。没有 Upgrade Signal，就没有理由为了“先进”增加层级。

先只看已经学过的路径控制问题：

```text
确定规则            → Code
单次模糊生成        → Prompt
固定多步骤          → Chain
可枚举分支与状态    → Workflow / Graph
下一步必须看新观察  → Agent Loop
```

到这里仍然只是在决定“路径由谁控制”。后面真正遇到跨时间持续、独立责任拆分或多个产品重复建设时，才分别引出 Runtime / Harness、Subagent / Multi-Agent 和 Platform。

每次升级都同时增加能力和成本。正确问题不是“我们能不能上 Agent”，而是：

> 当前失败由哪类不确定性造成？增加哪一个最小责任，能以证据改善结果？

## 2. Code 什么时候就够

### 本节新词

- **Code（确定性代码）**：输入、规则和结果关系能够明确写进程序的逻辑。金额、权限、状态转换和格式校验等责任通常优先由它承担。
- **Schema Validation（结构校验）**：检查字段、类型、枚举和结构是否符合预定义 Schema。它能证明“结构合法”，不能单独证明业务语义正确。

如果输入、规则和输出都能明确表达，优先使用普通程序：

- Schema validation；
- 金额、时间、排序和权限判断；
- 已知状态机；
- 数据格式转换；
- 确定性路由；
- 不允许概率错误的硬门禁。

模型不是传统代码的升级版。把确定规则交给模型，只会增加成本和不确定性。

升级信号：需求中出现开放语言、模糊语义、长尾表达或难以手写规则的判断。

## 3. Prompt 什么时候足够

### 本节新词

- **Candidate（候选结果）**：模型给出的可供人或程序继续检查的建议，不自动等于最终事实或已执行结果。单次 Prompt 最适合产生这种低副作用候选。

单次输入可以产生有用候选，且结果会被人或确定程序检查时，Prompt 通常足够：

- 总结文档；
- 改写文本；
- 从非结构化内容抽取候选；
- 生成草稿；
- 对已有证据做解释。

升级信号：任务必须访问外部知识、分成多个依赖步骤，或单次输出无法验证完成。

Prompt 升级时应先考虑 RAG、Structured Outputs 或 Tool，而不是直接创建 Agent。

## 4. Chain 什么时候合适

Chain 适合路径固定的多步任务：

Extract → Normalize → Classify → Generate。

它的价值是每一步可以使用不同 Prompt、Model 和校验器。只要步骤顺序稳定，显式程序串联通常比开放循环更可预测。

升级信号：分支、循环、审批、暂停或错误恢复开始出现，线性 Pipeline 变成嵌套条件。

## 5. Workflow / Graph 什么时候合适

当允许路径可以预先描述，但不同输入会走不同分支时，使用 Workflow 或 Graph：

- 订单、工单、发布和审核；
- 有明确状态和转移规则；
- 关键节点需要 Human-in-the-loop（人在回路中，HITL）；
- 需要暂停、恢复或重放；
- 分支和循环需要可视化或审计。

Workflow / Graph 仍是 Programming the Path：开发者定义可走的路。Graph 可以表达 State Transition，但节点图本身不自动提供持久 Task、权限、幂等和恢复。

升级信号：有价值的下一步无法事先枚举，需要依据新的 Observation 动态选择 Tool 或策略。

## 6. Agent Loop 什么时候值得

Agent Loop 适合开放路径任务：

- 研究问题不断暴露新的知识缺口；
- 调试时下一步取决于刚出现的错误；
- 浏览器页面结构和状态不断变化；
- 工具很多，选择取决于中间证据；
- 目标明确，但路径不能完整预写。

引入 Agent 前至少要回答：

1. Goal 能否被验证；
2. 可用 Action 是否有清楚合同；
3. Observation 是否可信；
4. Stop condition 是否存在；
5. 高副作用动作怎样审批；
6. 失败时怎样恢复或安全停止；
7. 相比 Workflow 的增量收益怎样评估。

如果这些问题没有答案，“自治”通常只是把未知路径隐藏进模型。

## 7. Runtime 与 Harness 何时成为必要条件

下一层会正式学习 Runtime 与 Harness。这里不提前背定义，只看什么失败已经说明“Agent Loop 本身不够”。

当任务跨越多次调用、人工等待甚至进程重启，责任不能跟着一次回答消失；当超时后外部动作可能已经发生，系统也不能靠“再问一次模型”恢复。这些都是 Runtime 开始必要的信号。

另一类问题发生在模型每轮怎么工作：上下文总是缺关键材料、工具太多、工作目录和权限边界混乱、测试或页面回读没有进入循环。此时缺的通常不是更自由的 Agent，而是更好的 Harness。

```text
路径已经需要动态决定
→ Agent Loop

责任要跨时间继续存在
→ 进入 Runtime 层

模型每轮缺少受控工作环境
→ 进入 Harness 层
```

具体的 Task、State、Scheduler、Workspace、Sandbox、Permission 等机制，留到 04 层逐篇学习。本章只负责判断什么时候值得继续升级。

## 8. 什么时候先拆 Subagent，而不是新增独立 Agent

如果目的只是隔离 Context、并行处理局部问题或复用专业方法，先考虑把**一段边界清楚的局部责任**拆出去：主任务仍对最终 Goal 负责，子任务交回可验收结果，不需要独立长期身份和权限域。

只有当责任主体、权限边界、生命周期或跨 Runtime 协作确实独立时，才值得进入真正的 Multi-Agent 问题。Subagent、Delegation、Handoff 与 Shared State 会在下一层正式学习。

## 9. Multi-Agent 什么时候不是过度设计

Multi-Agent 的升级理由必须来自责任边界，而不是“多几个模型讨论也许更聪明”。比较可信的信号包括：不同责任必须由不同身份承担、权限和数据不能共享、多个主体需要长期独立运行，或者跨组织/跨 Runtime 互操作。

以下理由仍然不够：

- Context 很乱，但还没有做检索与压缩；
- 想靠多个模型互评自动提高正确率；
- 每个 Tool 都包装成一个 Agent；
- 没有 Eval，却默认 Agent 数量会带来质量。

本章只判断是否值得进入这一层；组织拓扑、交接和 A2A 留给 Multi-Agent 专章。

## 10. Platform 什么时候出现

一个 AI Application 跑通，并不自动说明需要平台。真正的平台信号来自**多个真实产品重复承担同一组已经稳定的工程责任**：模型入口、知识/能力目录、长期任务、权限治理、Eval、隔离执行或成本治理反复出现，而且共享以后能减少重复建设或风险。

只有一个产品时，先把责任在应用内实现清楚通常更安全。平台的责任图和平台化门禁都留给 07 层；这里不提前定义 Multi-tenancy、Quota 等平台概念。

## 11. 每次升级先回答五个问题

不要因为“下一层更先进”就升级。先把当前失败说清楚，再判断缺的究竟是哪一段责任。

| 要回答的问题 | 目的 |
|---|---|
| 当前形态真实失败在哪里？ | 避免为想象中的问题加组件 |
| 缺的是知识、路径、状态、权限还是组织边界？ | 定位真正缺失的责任 |
| 最小能补上的责任是什么？ | 控制复杂度 |
| 怎样证明结果改善？ | 防止只看架构图变复杂 |
| 如果没有收益，怎样退回？ | 保留退出路径 |

例如：

| 观察到的失败 | 不应直接做 | 优先补什么 |
|---|---|---|
| 模型不知道最新资料 | 创建 Multi-Agent | Retrieval / Knowledge Source |
| 输出格式漂移 | 增加 Agent reviewer | Schema / deterministic validator |
| 多步骤路径固定 | 开放 Agent Loop | Chain / Workflow |
| 进程重启后任务丢失 | 写更长 Prompt | Runtime State / Checkpoint |
| Tool 选择混乱 | 每个 Tool 配 Agent | Capability taxonomy / Tool retrieval |
| 结果无法证明 | 再跑一次模型 | Evidence / Eval |

## 12. 混合架构才是常态

真实系统通常同时使用多种形态：规则和校验交给 Code，已知主路径交给 Workflow，少量开放节点才进入 Agent Loop；跨时间责任交给 Runtime，高副作用动作保留确定性的批准与验证。

所以选择不是 Code 或 Agent 二选一，而是**把不确定性限制在真正需要智能判断的局部**。

## 13. 升级以后，用结果证明它值得

每增加一层复杂度，都应该有与这层责任相匹配的验证：Workflow 看分支和失败处理，Agent Loop 看 Goal success 与动作轨迹，Runtime 看恢复和重复副作用，Multi-Agent 看增量收益与协调成本，Platform 看复用和接入成本。

这里先保留这个通用原则，不再给它另起一套方法名。平台化时怎样把 Baseline、增量收益和退出条件系统化，由 [什么时候值得建设 AI 平台](../07_AI平台与产品/03_什么时候值得建设AI平台.md) 正式负责。

## 架构升级最常见的误判

### 用 Agent 替代普通程序

确定性规则变成概率判断，难测且更贵。

### 把 Graph 当 Runtime

画出了节点，却没有持久 State、幂等、权限和恢复。

### 用 Reviewer Agent 修复所有问题

Reviewer 与执行者共享同一盲区，增加调用却没有外部 Evidence。

### 先建平台再找复用场景

抽象围绕想象需求形成，应用反而被不稳定合同拖慢。

### 用行数和组件数证明成熟

架构价值来自 Outcome、可靠性和成本，而不是术语覆盖。
