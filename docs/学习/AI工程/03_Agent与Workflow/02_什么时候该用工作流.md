# 什么时候该用工作流

> 唯一职责：解释路径由代码决定时 Chain、Workflow、Graph 的价值与边界。  
> 前一章把模型带进应用；本章先回答怎样稳定组织多步骤调用，下一章才把“下一步是什么”交给模型。

## 当步骤已知，先把路径写清楚

### 本节新词

- **Deterministic Control（确定性控制）**：下一步由可以检查的代码、规则或状态条件决定。只要合法路径能提前写清，这种控制通常比让模型临场规划更容易测试和审计。
- **Chain（调用链）**：把几个已知步骤按固定顺序连接起来，例如“抽取 → 检索 → 生成”。它适合短而稳定的多步任务。
- **Workflow（工作流）**：由代码或配置拥有路径控制权，可以包含分支、等待、重试、人工节点和补偿。模型可以参与节点，但不必拥有整个流程。
- **Graph（图）**：用 Node（节点）和 Edge（边）表达步骤、依赖和转移关系。Graph 是 Workflow 的一种表达方式，不因为“画成图”就自动获得 Agent 自主性。

放在同一条控制权轴上看：Chain 先把步骤顺序串起来；Workflow 再加入状态、分支、等待和补偿；Graph 用节点与边表达更复杂的关系。三者都优先把已知路径写清楚，而不是把每一步都交给模型临场决定。

```text
Code        确定性逻辑直接完成任务
Chain       多个步骤按固定顺序连接
Workflow    显式状态、分支、等待、补偿和人工节点
Graph       用节点与边表达复杂 Workflow
```

它们共同的核心是：**开发者仍拥有路径骨架**。这不是落后的限制，而是很多生产任务最需要的可预测性。

当业务已经知道合法步骤、顺序和异常路径时，不需要让模型每次重新发明流程。例如一条发布链可以把“检索资料、模型生成、人工审批、真实写入、结果验证”明确分开。模型负责其中模糊的语言判断，Workflow 负责节点之间的确定性合同。

> 模型处理模糊性，软件处理确定性。

## 为什么 Chain 先出现

### 本节新词

- **Input / Output Contract（输入／输出合同）**：一个步骤明确接受什么、产出什么以及结果如何被下一步消费。Chain 能否可靠拆分，很大程度取决于步骤间合同是否清楚。
- **Intermediate Result（中间结果）**：链路尚未结束时某一步产生、可被观察或复用的结果。把它显式保存有助于定位哪一步开始出错。

一次 Prompt 很难同时完成资料检索、结构化提取、生成、校验和发布。Chain 把不同认知任务拆开：

```text
retrieve → summarize → draft → critique → revise
```

它的收益是可观察、可替换、可单测；弱点是现实一旦偏离预设顺序，Chain 只能失败或依靠大量条件分支。

Chain 适合：

- 输入输出合同清楚；
- 步骤少且顺序稳定；
- 中间结果有价值；
- 失败可以在固定位置处理。

不适合：

- 下一步取决于新观察；
- 需要探索未知空间；
- 任务目标明确但路径难以预先列完。

## Workflow：确定性不等于线性

### 本节新词

- **Branch（分支）**：根据明确条件选择不同后续路径。
- **Parallelism（并行）**：让互不依赖的节点同时执行，以减少总等待时间。
- **Compensation（补偿）**：当一组副作用只完成了一部分时，用另一个明确动作撤销、抵消或修正已发生的影响。它不等于简单 Retry。
- **Human-in-the-loop（人在回路中，HITL）**：把人工判断作为工作流中的正式节点或等待条件，而不是依赖线下口头确认。

Workflow 在 Chain 上增加了状态与控制流：

- 条件分支：依据业务字段选择路径；
- 循环：在明确上限内重复校验或补齐；
- 并行：互不依赖的节点同时执行；
- 等待：外部事件、审批、时间或资源；
- 补偿：副作用成功一半时如何恢复；
- 人工节点：把高风险判断持久化为事件。

Workflow 的路径可以很复杂，但**允许集合仍由开发者定义**。模型可以选择某个已允许分支，不能因此把整个系统称为 Agent。

## Graph：表达结构，不自动产生自治

### 本节新词

- **Node（节点）与 Edge（边）**：Node 表示工作或状态，Edge 表示节点之间允许的依赖或转移。
- **DAG（Directed Acyclic Graph，有向无环图）**：边有方向且不存在循环的图，适合只向前推进的依赖任务；需要回退和反复迭代时通常要使用更一般的 Graph / State Machine。
- **Checkpoint（检查点）与 Resume（恢复继续）**：Checkpoint 保存可继续执行所需的中间状态；Resume 从已保存位置继续。Graph 可以表达保存位置，但可靠持久化属于后续 Runtime。

Graph 是表达 Workflow 的一种方式：节点表示工作或状态，边表示转换与条件。它擅长：

- 共享子流程；
- 显式循环和汇合；
- 复杂分支的可视化；
- Checkpoint、Resume 和状态机映射；
- 静态验证不可达节点或非法转换。

但 `Graph framework used = Agent` 是错误推论。一个完全由代码决定下一节点的 Graph 仍是 Workflow；一个 Agent 也可以把局部执行包装进 Graph。框架名字不能替代责任判断。

## State Machine 与 Graph 的关系

### 本节新词

- **State Machine（状态机）**：定义一个业务对象可能处于哪些 State（状态），以及哪些 State Transition（状态转换）合法。它关注对象状态，不等于一张执行步骤图。
- **State Transition（状态转换）**：对象从一个合法状态进入另一个合法状态的变化，例如 `PENDING → RUNNING`。

状态机关注“对象处于什么状态、允许怎样转换”：

```text
PENDING → RUNNING → WAITING → RUNNING → SUCCEEDED
                      └──────────────→ FAILED
```

执行图关注“哪些工作节点及依赖关系要被执行”。二者可以组合，但不要把节点执行进度、业务状态和模型 Context 塞进同一个自然语言字段。

## 为什么 Graph-first 后来会降层

2023～2024 年很多系统试图把所有智能行为画成庞大图。实际问题是：

- 未知任务路径无法穷举；
- 图越大，维护成本越接近另一套业务代码；
- 模型能力升级后，一些微小分支可以交给模型判断；
- 可靠性问题并不会因为“画成图”自动消失。

留下来的不是“Graph 失败”，而是它回到合适位置：

```text
业务硬边界 / 审批 / 状态转换 / 恢复骨架 → Workflow / Graph
开放探索 / 下一步选择 / 工具组合           → Agent Loop
```

## Workflow + Model 的三种组合

### 本节新词

- **Runtime（运行时）**：真正承接任务执行、状态、调度和外部动作的软件层；本章只借它说明“模型建议分支后仍需软件校验”，完整定义在后续 Runtime 章节。
- **Fallback（回退路径）**：模型无法可靠给出分支建议时，系统预先准备的安全替代路径，例如走默认规则、升级强模型或交给人工。

### 模型作为节点

路径固定，模型只完成分类、提取、改写等局部工作。最容易测试和治理。

### 模型选择有限分支

模型给出结构化建议，Runtime 校验后选择允许边。适合模糊分类，但必须有 fallback 和置信度边界。

### Workflow 包住 Agent

外层确定 Task 生命周期、预算、审批与结果验证；某个节点内部允许 Agent Loop 动态行动。这常比“整个产品都是一个 Agent”可靠。

## 确定性编排会在哪些地方被误用

### 本节新词

- **Timeout（超时）**：调用在等待上限内没有得到确定结果。超时只说明“现在不知道结果”，不能直接证明外部动作失败。
- **Reconciliation（对账／状态核对）**：重新查询外部权威状态，确认此前动作到底有没有发生。
- **Idempotency（幂等性）**：同一个逻辑操作被重复执行时不会产生额外业务副作用的合同性质。
- **Evidence（证据）**：能够支持“动作已发生或目标已完成”的可检查事实。以上三者的可靠执行机制由 Runtime / Durable Execution 章节负责。

### 用 LLM 代替 if/else

税率、权限、版本比较、必填校验等确定规则不应交给概率判断。

### 为了可视化把简单函数拆成巨大 Graph

节点和边增加了状态、序列化、调试与升级成本。三步稳定逻辑通常一个函数或 Chain 就够。

### 把所有异常画成路径

外部系统会产生 Timeout、UNKNOWN、重复回调和部分副作用。单靠图无法解决 Reconciliation、Idempotency 与 Evidence；这些属于 Runtime。

### 把框架能力当成系统能力

框架支持 persistence、memory 或 multi-agent，不表示当前应用已经正确配置真值、权限、恢复和评估。

## 按分支、状态和恢复需求升级

### 本节新词

- **Agent Loop（Agent 决策循环）**：模型根据新 Observation（观察）动态决定下一步的循环。它与 Workflow 的关键区别不是有没有多个步骤，而是谁拥有下一步路径选择权。下一章完整展开。

| 任务形态 | 首选 |
|---|---|
| 完全确定、步骤少 | Code |
| 固定多步骤、无复杂分支 | Chain |
| 显式状态、分支、等待、审批 | Workflow |
| 复杂依赖、循环、共享子图 | Graph |
| 目标明确但路径必须依据观察改变 | 下一章的 Agent Loop |

升级前问：路径真的未知吗？模型选择路径是否产生可测增益？错误路径的代价是什么？能否限制动作集合？恢复和验证由谁负责？如果答案不清楚，停在更简单的层级。

## ProFlow Lens｜为什么先 Workflow，而不是先 Agent

ProFlow 的早期核心是 Node、Dependency、合法 State Transition 和人工门禁：业务路径本来就能被显式描述，因此 Workflow/Graph 比开放 Agent Loop 更合适。后来真正推动架构升级的，不是“模型还不够自治”，而是 Task 跨时间持续、真实 Effect 可能未知、浏览器环境需要回读——这些 Failure 最终把系统推向 Runtime/Harness，而不是简单增加 Agent。

## 这套编排怎样交给 Agent Loop

- Prompt/Copilot 让模型进入应用；Chain/Workflow 把多次调用组织成系统；
- 下一章 ReAct/Agent Loop 只接管动态决策，不接管权限、真值和持久化；
- Harness/Runtime 会把 Workflow 和 Agent 都托进长期 Task、State、Recovery 与 Evidence；
- 最后的架构选择章把这些方案放在同一复杂度梯度中比较。

## 检查路径是否应该保持确定

1. Graph 与 Agent 的区别由框架名决定，还是由谁拥有下一步决策决定？
2. 为什么确定性 Workflow 在 Agent 时代仍然重要？
3. 哪些问题不能靠画更多节点解决？
4. 什么情况下 `Workflow 包住 Agent` 比全自治更合理？
