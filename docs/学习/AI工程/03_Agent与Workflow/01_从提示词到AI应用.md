# 从提示词到 AI 应用

> 唯一职责：解释生成式 AI 如何从 Prompt 进入 Copilot 和真实应用，以及这次产品化改变了什么。

## 模型接口出现后，第一批产品先把人留在闭环里

2022～2023 年，生成式模型第一次让“直接描述目标”成为普遍可用的软件入口。团队很快发现：一次生成虽然惊艳，却还不能承担权限、最新数据、真实写入、长期状态和结果验收。第一批真正进入工作的产品因此没有一上来就追求全自治，而是先把人留在关键决策和副作用之前。

```text
自然语言描述目标
→ 模型给出候选
→ 人检查、修改或拒绝
→ 软件执行真实动作
→ 结果进入下一轮工作
```

这条路径后来会长成 Prompt、Chat UI、Copilot、RAG、Tool 和 AI Application，但本章不把它们当成一串名词年表。下面沿着产品真正遇到的问题逐步引入。

Foundation Model（基座模型）把许多任务统一成自然语言生成接口，但模型能力不会自动变成产品价值。2022～2023 的第一次开发范式变化，是开发者开始围绕模型构造交互、Context、知识、反馈和人类审核：

Prompt → Chat UI → Copilot → RAG / Tool → AI Application。

这一阶段最重要的遗产不是“会写 Prompt”，而是三个判断：

1. 自然语言成为软件的新入口，但不是完整系统；
2. Copilot 先于 Autonomous Agent 落地，因为人仍在真实副作用之前审核；
3. AI 产品的壁垒逐渐从一次生成转向专有 Context、业务流程、反馈数据和可验证 Outcome。

## 1. 为什么 Prompt-first 会爆发

### 本节新词

- **Prompt（提示）**：一次模型调用中交给模型的任务说明、当前材料和约束。它影响这一轮输出，但不负责长期状态或现实权限。
- **Prompt Engineering（提示词工程）**：围绕 Prompt 的任务表达、示例、约束和输出格式进行设计与迭代的方法。
- **System Instruction（系统指令）**：由产品或平台提供的高层要求，用来约束模型在当前交互中的行为。
- **Instruction Hierarchy（指令层级）**：不同来源的指令冲突时采用的优先关系。外部内容不能因为写着“忽略之前要求”就自动获得更高控制权。

传统软件要求用户适应菜单、表单、按钮和固定字段。生成式模型让用户可以直接描述目标、补充例子、指定格式和约束。

Prompt Engineering 最初解决的是一次调用的输入质量：

- Role：模型在本轮扮演什么工作角色；
- Instruction：要完成什么；
- Context：本轮可以参考什么；
- Example：期望输出长什么样；
- Constraint：格式、范围和禁止事项；
- Output contract：结果怎样被人或软件消费。

它的吸引力在于反馈周期极短：修改文字即可改变行为，不必重新训练模型。

但 Prompt 只能影响概率，不能独立承担：

- 权限；
- 持久 State；
- 外部数据的新鲜度；
- 真实副作用；
- 故障恢复；
- 最终结果验证。

所以 Prompt-first 是入口革命，不是 Runtime 的替代品。

随着产品开始接入历史消息、检索证据、Tool Result 和当前 State，问题也从“这句话怎么写”逐渐变成“这一轮到底应该让模型看到什么”。这就是后来 Context Engineering（上下文工程）被单独提出的原因：Prompt Engineering 主要优化任务表达，Context Engineering 管整个工作集。这里先保留这条历史桥梁，正式的信息分层留到 State/Context/Memory 章。

## 2. Chat UI：把模型变成大众产品

### 本节新词

- **Chat UI（对话界面）**：用连续消息组织人与模型交互的产品界面。它改善交互，不等于系统已经拥有可恢复任务。
- **Conversation History（对话历史）**：应用保存的过去消息记录。后续调用是否继续使用它，取决于应用怎样重新装配 Context。
- **Streaming（流式输出）**：模型生成过程中持续把增量结果发送给界面，而不是等待完整回答后一次返回。它改善等待体验，不改变结果是否正确。

Chat 产品把模型调用包装成连续对话。用户不再写 API 请求，而是通过追问、修正和补充上下文逐步表达需求。

产品层至少补了：

- Conversation history；
- System / product instructions；
- 文件和多模态输入；
- Streaming；
- 反馈入口；
- 身份、额度和安全策略；
- 可复用会话。

模型本身仍主要处理当前输入。对话连续性由应用保存历史并重新组织 Context 实现。Chat UI 让模型容易使用，但聊天窗口不等于 Task Runtime，更不等于 Agent。

## 3. Copilot：先增强人，再代理人

### 本节新词

- **Copilot（副驾驶）**：模型负责建议、生成或局部操作，人仍保留关键判断和真实副作用前的确认。
- **Human Review（人工复核）**：人在结果进入真实系统前检查、修改、接受或拒绝模型输出。它是一种明确的控制责任，不只是“有人看一眼”。
- **Autonomous Agent（自主 Agent）**：允许系统在约束范围内根据环境反馈自行决定后续动作的 Agent 形态。它需要的可靠性责任远多于一次 Copilot 建议。
- **Diff（差异）**：两个版本之间的具体变化集合。Coding 场景里，Diff 让人和测试系统能够审查模型到底改了什么。

Copilot 模式把模型嵌入已有工作流，在真实写入或提交之前保留人类判断。

典型循环是：

Work context → Model suggestion → Human review → Accept / edit / reject → Real effect。

它比完全自治更早落地，因为：

- 人掌握最终目标和隐含约束；
- 错误建议通常可以不接受；
- 产品能从接受、修改和拒绝中获得反馈；
- 不需要先解决长期自治的全部可靠性问题。

代码补全是典型例子。早期代码模型可以从自然语言或已有文件生成代码，IDE 中的人类负责决定是否采用；编译、测试和 Diff 又为结果提供机器反馈。这条路线后来演化成能读取仓库、执行命令和迭代测试的 Coding Agent，但 Copilot 与 Agent 的责任边界不能混淆。

## 4. 从 Demo 到 AI Application

### 本节新词

- **Demo（演示原型）**：证明某个输入下“模型可能给出有用结果”的最小展示，不等于可持续运行的业务系统。
- **AI Application（AI 应用）**：把模型能力放进用户交互、领域数据、业务流程、验证与反馈闭环的完整产品。
- **Outcome（业务结果）**：用户或业务真正得到的可观察结果，例如工单是否正确解决、代码是否通过验收，而不是模型是否生成了一段看似合理的文本。
- **Validation（校验）与 Eval（评估）**：前者更偏检查具体输出是否满足规则或合同，后者更偏用任务集和指标衡量系统整体表现。

一个 Prompt Demo 通常只证明：

模型在一组输入上偶尔给出有用结果。

真实 AI Application 还要回答：

| 产品问题 | 必须补上的工程责任 |
|---|---|
| 模型不知道私有或最新资料 | Retrieval / RAG / Knowledge Source |
| 输出需要进入软件流程 | Structured Outputs / Tool Contract |
| 结果可能错误 | Validation / Eval / Human review |
| 输入可能包含隐私 | Identity / Permission / Data boundary |
| 调用昂贵或缓慢 | Model selection / caching / budget |
| 用户需要持续任务 | Workflow / Runtime |
| 结果会改变现实世界 | Approval / Evidence / recovery |

第一次产品化让团队意识到：Model 是核心组件，但 Product、Knowledge、Capability 和 Evaluation 决定它能否进入业务。

## 5. 开放权重模型为什么迅速兴起

### 本节新词

- **Open-weight Model（开放权重模型）**：模型权重可被下载或在许可范围内部署的模型。它不自动等于开源软件，也不自动意味着商用无限制。
- **Serving（模型服务）**：把模型部署成可以接收请求、调度计算并返回结果的运行服务。自托管模型时，这部分责任由团队自己承担。
- **Quantization（量化）**：降低模型权重或计算的数值位宽，以减少存储、内存和部分推理开销；具体能力边界已在 Transformer 章解释。

闭源 API 让开发者快速获得强模型能力，但企业同时关心成本、延迟、隐私、离线运行、可定制性和供应商边界。

开放权重生态提供了另一条工程路线：

- 本地或私有环境部署；
- 量化后进入端侧设备；
- 领域微调和蒸馏；
- 用小模型承担分类、抽取、改写等高频任务；
- 与云端强模型形成分层路由。

LLaMA / Llama、Mistral、Qwen、DeepSeek、Gemma 等模型家族让团队看见了这种选择空间；这些名字是生态例子，不是固定排名，也不代表每个版本都适合自托管。真正落地还会遇到量化、部署格式和本地 Runtime 等工程问题，但它们属于后面的端侧/小模型章节；本章只保留“开放权重把部署选择权交给应用团队”这条产品演进。

开放权重不等于零成本，也不等于自动安全。团队仍要承担 Serving、评估、升级、容量和供应链治理。它留下的稳定价值是部署选择权，而不是“所有模型都应自托管”。

## 6. LangChain / LlamaIndex 等框架为什么爆发

### 本节新词

- **SDK（Software Development Kit，软件开发工具包）**：把 API、类型、辅助函数和常见集成方式封装成开发者可直接使用的工具集合。
- **Adapter（适配器）**：把不同模型、检索器或 Tool 的接口转换成框架内部统一形态的组件。
- **Callback（回调）**：某个运行事件发生时由框架调用的扩展入口，例如记录模型调用开始、结束或错误。
- **Tracing（链路追踪）**：记录一次任务经过哪些模型、Tool、节点和状态变化，帮助定位延迟与失败。
- **LangGraph / AutoGen / CrewAI**：分别代表图式 Agent 编排、多 Agent 对话和角色协作等框架路线。框架提供实现工具，不自动证明系统已经具备 Runtime、共享真值或可靠恢复。

开发者很快反复遇到同一批问题：

- Prompt template；
- Model adapter；
- Retrieval；
- Tool binding；
- Output parser；
- 多步骤调用；
- Conversation history；
- Callback / tracing。

应用框架把这些常见胶水代码抽象出来，让团队能快速试验 LLM 产品。LlamaIndex 长期更聚焦数据、检索和知识工作流；LangChain 更广泛地连接 Model、Prompt、Tool 和 Agent 组件。

随着任务开始出现显式状态和多 Agent 协作，LangGraph、AutoGen、CrewAI 等框架又分别探索了 Graph Runtime、Agent conversation 和 role-based collaboration。它们记录了开发范式的演进，但框架名不能替代架构判断：用了 LangGraph 不等于已经具备 Durable Execution，用了 AutoGen 或 CrewAI 也不等于责任、Shared State、Handoff 和 Eval 已经成立。

早期热潮也暴露了边界：

- 抽象更新快，调试时仍要理解底层请求；
- Chain 一多，Context 和错误传播会变得隐式；
- “框架有 memory”不代表系统已有可靠 State；
- 封装 Tool 不代表权限和副作用得到治理；
- Graph 表达路径，不自动提供完整 Runtime。

框架没有“消失”，而是许多能力降层成 SDK、组件或 Runtime 基础设施。

## 7. 这一阶段高估了什么

### 一个 Prompt 就是产品

Prompt 可以生成惊艳 Demo，但没有数据、流程、权限、反馈和分发时，价值容易被复制。

### 聊天套壳就是长期壁垒

相同模型和相似 System Prompt 很容易同质化。更稳固的差异来自专有 Knowledge、Workflow、Tool、用户反馈和领域 Outcome。

### Copilot 一定会立刻替代岗位

Copilot 改变的是任务分配：机器生成候选，人类负责目标、取舍、验证和后果。岗位变化必须由真实市场和工作结果验证，不能从模型能力直接推导。

### 框架越重越专业

简单任务用少量代码和明确合同往往更可靠。只有分支、状态、恢复或协作确实出现时，才需要升级架构。

除了上面四类历史高估，还要警惕几种工程化误判：为了展示“智能”把确定性数据转换交给模型；把全部聊天历史回放后宣称有了 Memory；让 Prompt 承担权限和业务状态机；因为框架存在 `Agent` 类就宣称系统拥有 Runtime；只看生成质量，不测接受率、修改量、任务成功率和人工负担。

## 8. 今天留下了什么

这次产品化留下了现代 AI Engineering 的基本分工：

- Prompt 是一次行为控制入口；
- Context 决定本轮模型实际看到什么；
- RAG 连接参数外知识；
- Structured Outputs / Tool 连接软件能力；
- Copilot 用人类审核控制副作用；
- Eval 证明结果是否有用；
- Workflow / Runtime 承接跨步骤和长期任务。

关键变化可以概括为：

Model capability → Interaction → Product workflow → Verifiable outcome。

## 9. 为什么下一步是 Workflow

当任务只有一次生成，Prompt + Code 通常足够。产品一旦出现“先检索、再判断、再调用、失败时换路径、关键动作需审批”，固定的单次调用就不够了。

下一章进入 Chain、Workflow 与 Graph：路径仍主要由开发者定义，但多步骤、分支和状态开始显式化。再下一章才把“下一步走什么”部分交给 Agent Loop。

## 让产品复杂度随真实结果增长

Evidence 的正式边界留给后面的 Durable Execution，Failure Slice 与系统评估留给 Eval。这里先用它们最朴素的意思：**没有可回读的失败和结果，就没有理由因为一个流行名词升级架构。**

优先选择最小可靠产品路径：

1. 先确认目标是否真的需要概率生成；
2. 用明确输入、输出和人工审核建立 Copilot；
3. 缺外部知识时增加 Retrieval；
4. 需要改变外部世界时增加受控 Tool；
5. 只有路径和状态复杂度出现后，才升级 Workflow / Graph；
6. 只有下一步无法预先穷举且收益可验证时，才引入 Agent Loop。

## 这些产品责任如何交给下一层

- 前一层由模型智能、Post-training、RAG 与 Tool 提供可用能力；
- 下一章解释 Chain、Workflow、Graph 为什么先于开放 Agent Loop 出现；
- Agent Loop 章解释模型怎样根据 Observation 动态改变下一步；
- Harness/Runtime 章节负责长期任务、权限、状态和恢复；
- 岗位判断只在真实系统与岗位章节基于有边界的 JD corpus 展开。
