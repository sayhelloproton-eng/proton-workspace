# 长任务怎样安全恢复

> 唯一职责：解释长任务怎样暂停和恢复、未知状态怎样对账、重复执行怎样避免产生第二次副作用，以及恢复点怎样与真实结果绑定。
> 读完要能回答：一个长期 Agent 怎样从 Proposal 走到真实 Effect，再把经过验证的结果提交为 Truth；如果要等待、超时、断线或需要审批，又怎样安全继续？
> 前置阅读：工具调用、长期任务运行和信息状态章节。本章沿“等待、超时、恢复、授权、验证”这条真实执行链展开；具体动作怎样做到可安全重复，仍由工具章节负责。

<a id="ch12-30s-core"></a>
## 退款请求超时后，最危险的动作就是立刻再试一次

用户发起退款，客户端等了十秒没有收到结果。此时最直觉的处理是“失败了，再调用一次”；但真实支付系统可能已经完成退款，只是响应在网络中丢失。如果立即再试，第二次调用可能制造重复副作用。

可靠系统必须先承认：**现在不知道第一次动作到底发生了什么。** 它要保存这个不确定状态，重新查询权威系统，确认现实 Effect，再决定继续、等待、重试、回滚或交给人工。长期任务的恢复能力，就是从这类“不知道现实发生了什么”的断点里长出来的。

<a id="ch12-deep-read"></a>
## 长期任务怎样避免重复副作用和虚假完成

<a id="ch12-event"></a>
### 3.1 Event ≠ State

#### 本节新词

- **Event（事件）**：描述“刚刚发生了什么”的事实信号，例如构建完成、审批通过、子任务失败。
- **State（状态）**：系统当前承认“现在是什么”的事实。Event 可以触发 State 更新，但不能因为一条事件文本就自动覆盖当前状态。
- **State Update（状态更新）**：根据 Event、版本和验证规则，把当前 State 修改到下一版本的确定性过程。

把同一次变化同时看成 Event 与 State，就能看见它们的差别：

```text
BUILD_COMPLETED
= Event

build.status = success
= State
```

两者的关键关系是：事件可以触发状态更新或对账，但不能直接覆盖当前真值。这样既能保留发生过程，也不需要模型从事件流猜现在到底是什么。

一条长任务可能依次产生 `TASK_STARTED`、`CHECKPOINT_CREATED`、`BLOCKED`、`HANDOFF_COMMITTED`、`TEST_FAILED`、`COMPLETED`。这些事件让 Scheduler、审计和上层任务知道“什么变了”；它们不是要求 Parent 持续轮询的进度文案，也不能单独覆盖当前 State。Runtime 应只在事件改变下一步决策时唤醒相应任务，并通过版本化 State 判断现在究竟处于哪一步。

<a id="ch12-waiting-scheduler"></a>
### 3.2 WAITING：长期任务不需要模型一直在线

#### 本节新词

- **WAITING（等待状态）**：Task 尚未完成，但目前没有值得立即执行或调用模型的工作。等待是合法生命周期，不是 Failure。
- **Scheduler（调度器）**：根据 Event、时间、依赖和资源判断等待中的 Task 何时重新变成 runnable。
- **Webhook（回调通知）**：外部系统在状态变化时主动向 Runtime 发送请求的机制，例如支付结果或审批系统通知。
- **Async Tool（异步工具）**：调用后不会立刻给出最终结果，而是稍后通过轮询、Event 或回调返回完成状态的工具。

常见等待对象包括：human approval、timer、webhook、external job、build/test、subagent、async tool。

```text
Task → WAITING
Model Invocation ends
...
Event arrives
↓
Scheduler marks task runnable
↓
Runtime resumes Task
↓
State/Context/Memory 章 rebuilds Context
↓
call Model only if needed
```

因此“Agent 在线”不是长期任务连续性的条件。

也不是所有 progress update 都值得唤醒 Parent / Model。普通心跳、百分比进度可以只更新状态；`CHECKPOINT / BLOCKED / NEEDS_DECISION / COMPLETED / FAILED` 这类会改变下一步决策的语义 Event 才通常值得触发 resume decision。

<a id="ch12-checkpoint"></a>
### 3.3 Checkpoint：在安全点保存可恢复事实

#### 本节新词

- **Checkpoint（检查点）**：在可恢复安全点持久化继续执行所需的 Task、State、Artifact、Evidence 和 Pending Work 等事实。
- **Recovery-safe Point（可恢复安全点）**：系统已经把关键副作用和当前真值处理到一致状态，即使进程此刻退出，也能从持久事实继续。
- **Pending Work（待处理工作）**：尚未完成、未来必须继续承担的明确动作或责任。

一个 Checkpoint 可以只保存恢复真正需要的引用和状态，而不是复制整个聊天：

```text
Task identity / status
Current State refs
Artifact version
Evidence refs
Pending Work
wait reason / resume condition
```

Checkpoint 的目标不是复制整个 Context，而是保证进程消失后，Runtime 仍能从可靠事实重新构造执行世界。

<a id="ch12-durable-execution"></a>
### 3.4 Durable Execution：长的是 Task，不是连接

#### 本节新词

- **Durable Execution（耐久执行／持久化执行）**：让长期 Task 跨模型调用、Session、Process 甚至机器中断后仍能从持久事实重新进入执行。
- **Machine Interruption（机器中断）**：进程所在主机重启、崩溃或失联等导致当前执行容器消失的情况。Durable Execution 不能依赖某一台机器一直在线。
- **Task World（任务世界）**：恢复任务所需的外部事实集合；恢复的是这些事实，不是模型隐藏思维。

它在工程上表现为一条“先提交可恢复事实，再允许当前进程消失”的链：

```text
Task running
↓
commit State / Checkpoint
↓
process or session ends
↓
restore persisted facts
↓
reconcile if needed
↓
rebuild Context
↓
resume Task
```

Runtime/Task 章解释任务生命周期；本章继续处理持久化、Checkpoint 与 Recovery。Resume 恢复的是 Task World，不是模型隐藏思维链。

<a id="ch12-safe-point"></a>
### 3.5 Checkpoint 要靠近已确认的 Effect boundary

#### 本节新词

- **Effect（现实副作用／效果）**：动作在外部世界真正产生的变化，例如退款、发信、创建资源、部署版本。
- **Effect Boundary（副作用边界）**：从“只是 Proposal”跨到“现实世界可能已改变”的执行边界。
- **Truth Commit（真值提交）**：在验证 Effect 后，把系统愿意让后续任务依赖的当前事实写入 State。

有真实副作用时，最危险的 checkpoint 是“动作发出后、结果未知时却把状态写成成功”。更安全的顺序是：

```text
Execute
↓
Observe
↓
Verify effect
↓
Commit current truth
↓
Checkpoint
```

如果中间断线，应保留 UNKNOWN 并进入 reconciliation，而不是伪造完成状态。

<a id="ch12-timeout-unknown"></a>
### 3.6 Timeout ≠ confirmed failure

#### 本节新词

- **Timeout（超时）**：在约定等待时间内没有得到确定结果。它描述“期限内未知”，不能直接证明动作失败。
- **UNKNOWN（未知 Effect 状态）**：系统不能确认副作用是否已经发生时使用的显式状态。承认 UNKNOWN 比伪造 `FAILED` 更安全。
- **Side Effect（副作用）**：调用除了返回数据之外，还改变外部状态的效果，例如扣款、删除、发布或发送消息。

例如支付、发信、提交表单、publish/deploy 都可能：服务端已成功，但客户端在响应回来前断线。

因此副作用动作的 timeout 首先应变成：

```text
effect = UNKNOWN
```

而不是：

```text
failed → retry immediately
```
<a id="ch12-reconciliation"></a>
### 3.7 State Reconciliation：先问现实世界，再决定下一步

#### 本节新词

- **State Reconciliation（状态对账／状态校准）**：在 Effect 不确定时重新查询权威系统，把本地认知与现实状态对齐。
- **Authoritative Source（权威来源）**：对当前现实状态拥有最终解释权的系统，例如支付平台的交易状态、部署平台的当前版本。
- **Ambiguous（仍然模糊）**：即使再次查询仍无法确认真实状态，此时应继续 WAIT、升级或人工处理，而不是假装确定。

实际恢复时可以按下面的分支回读现实：

```text
UNKNOWN
↓
query authoritative state / resource
├─ effect exists → validate + commit
├─ effect absent → retry if policy allows
└─ still ambiguous → WAIT / human / alternate path
```

它把“猜测刚才发生了什么”改成“重新观察现实世界”。

<a id="ch12-recovery"></a>
### 3.8 Recovery > Retry

#### 本节新词

- **Recovery（恢复）**：Task 从中断、失败或 UNKNOWN 中重新建立真实状态，并选择后续安全路径的整体过程。
- **Retry（重试）**：在已知安全条件下再次执行同一个或等价动作，只是 Recovery 的一种可能动作。
- **Replay（重放）**：重新执行过去的一段动作或事件序列；是否允许重放取决于幂等、版本和 Policy。
- **Rollback（回滚）**：用明确动作把系统恢复到之前的安全状态；它也是 Recovery 可能选择的路径。

两者最重要的关系可以直接写成：

```text
Retry ⊂ Recovery
```

Recovery 也可能得出：第一次已经成功，直接继续；需要换 Tool；等待依赖恢复；回滚；请求人工；取消 Task。把所有异常都统一成 Retry 会丢掉这些语义。正式边界仍是 `Retry ⊂ Recovery`。

<a id="ch12-idempotency-application"></a>
### 3.9 Idempotency 在 Recovery 中怎样使用

#### 本节新词

- **Idempotency（幂等性）**：同一个逻辑操作重复执行不会产生额外业务副作用，或系统能通过稳定操作身份返回第一次 Effect。Tool 章负责定义这个动作性质。
- **Operation Identity（操作身份）**：标识“这些重复请求其实属于同一次业务操作”的稳定 ID。
- **Idempotency Key（幂等键）**：客户端随请求携带的操作身份，服务端用它识别重复提交并避免重复生效。

这里直接使用 Tool 章已经定义的幂等动作合同：同一个 logical operation 在安全重放时不能制造第二次业务副作用。

在应用系统里，可以先采用下面这条规则：

```text
UNKNOWN
↓
Reconcile first
↓
if replay is required
    check idempotency / operation identity / policy
↓
Retry when safe
```

因此：`Idempotency ≠ Retry`，也不能因为操作“宣称幂等”就跳过 reconciliation。

<a id="ch12-permission-policy"></a>
### 3.10 Capability ≠ Permission ≠ Policy

#### 本节新词

- **Capability（能力）**：系统是否具备完成某个动作的机制。
- **Permission（权限）**：当前 Identity 在当前 Scope 下原则上被允许使用哪些能力。
- **Policy（策略规则）**：结合当前 Task、State、Risk 等条件，这一次具体动作应 `ALLOW / DENY / REQUIRE_APPROVAL`。
- **Authentication（身份认证，AuthN）**：确认“你是谁”。
- **Authorization（授权，AuthZ）**：确认这个 Identity 对某个资源或动作原则上“能不能做”。
- **IAM（Identity and Access Management，身份与访问管理）**：管理身份、凭证、权限和访问关系的系统能力。
- **RBAC（Role-based Access Control，基于角色的访问控制）**：根据 Role（角色）授予基础权限的常见授权模型。它提供静态基线，不足以独自裁决一次具体 Agent 动作。

| 概念 | 回答什么 | Owner |
|---|---|---|
| Capability | 系统会不会 / 能提供什么？ | Tool 章 |
| Permission | 当前 identity 在这个 scope 被允许做什么？ | Durable Execution 章 |
| Policy | 当前 Task/State/Risk 下，这次动作应 ALLOW / DENY / REQUIRE_APPROVAL？ | Durable Execution 章 |

模型知道一个 Tool、甚至成功选中了一个 Tool，都不等于它已经得到执行授权。身份认证只确认调用者是谁；静态授权给出原则上的资源边界；Runtime Policy 还要结合当前 Task、State、Risk 和目标版本判断这一次动作是否放行。

所以 `authenticated ≠ authorized ≠ policy-approved`。

传统 **IAM（Identity and Access Management，身份与访问管理）**和 **RBAC（Role-based Access Control，基于角色的访问控制）**仍是重要底座：它们可以确认操作者身份，并规定某个角色原则上能否访问资源。但 Agent 的一次真实动作还带着 `task / workspace / environment / risk / state / artifact version`。例如“发布者”角色通常有上线权限，不代表这个 Agent 可以在未经审批、测试失败或版本已变化时发布。因此 RBAC/IAM 提供身份与静态授权基线，Runtime Policy 再完成任务级、状态级裁决。

<a id="ch12-approval"></a>
### 3.11 Approval：把高权判断变成可持久事件

#### 本节新词

- **Approval（审批）**：针对一个具体高风险动作、目标和版本的显式授权。它应能被持久化和审计。
- **APPROVAL_REQUIRED（需要审批）**：Policy 判定当前动作不能自动执行、必须等待更高权主体确认的状态。
- **Human-in-the-loop（人在回路中，HITL）**：把人工判断作为正式执行节点或 Event 进入软件生命周期，而不是依赖线下口头许可。

一个高风险动作进入审批后，应成为正式状态机的一部分：

```text
high-risk Proposal
↓
Policy = APPROVAL_REQUIRED
↓
Task = WAITING_FOR_APPROVAL
↓
Checkpoint
↓
APPROVED / REJECTED Event
↓
re-evaluate current state
↓
resume / cancel / replan
```

这让 Human-in-the-loop 成为可暂停、可恢复的软件状态，而不是要求人持续盯着 Agent。

<a id="ch12-risk-autonomy"></a>
### 3.12 Risk-based Autonomy：人审异常和高风险，不审每一步

#### 本节新词

- **Risk-based Autonomy（基于风险的自治）**：根据错误代价、可逆性和不确定性决定自动化程度，而不是所有步骤都人工审批或全部放开。
- **Reversibility（可逆性）**：动作发生后能否可靠撤销或补偿。越不可逆的 Effect，通常需要越强的 Gate。
- **Human Load（人工负担）**：自动化系统仍要求人花费的审批、复核、异常处理和等待成本。
- **Audit（审计）**：事后能够追溯 Goal、关键动作、Evidence、异常和最终 Outcome 的能力，不应只剩低层 Tool 调用列表。

一个稳定工程判断是：

```text
Low risk / reversible
→ automate

Medium risk
→ automate + deterministic validator / evidence

High or unknown risk
→ stronger gate / approval / human
```

动作越容易可靠撤销，自动化空间通常越大；真实转账、生产删除、正式外发等不可逆副作用需要更强的 Permission / Policy / Approval。

这不是固定行业分级表，而是把 Human Load 放到真正需要权力和判断的位置。

相应地，成熟审计也不只罗列“Agent 调了哪些低层函数”，而要能追到 **Goal / Outcome / Evidence / Exception**：它想完成什么、实际产生什么结果、凭什么相信、哪里进入人工或异常路径。低层 Tool trace 仍是 Observability 输入，但不应成为唯一审计语义。

<a id="ch12-control-data-plane"></a>
### 3.13 Control Plane ≠ Data Plane

#### 本节新词

- **Control Plane（控制平面）**：决定系统允许怎样行动的高权规则与状态，例如 Identity、Permission、Policy、Task ownership 和 authoritative State。
- **Data Plane（数据平面）**：网页、文件、RAG 结果、Tool Result、邮件等供模型理解和处理的业务材料。
- **Prompt Injection（提示注入）**：Data Plane 中的文字试图冒充高优先级 Control 指令，诱导模型越过既有边界。

这条边界最重要的后果是：数据里出现一句命令，不会因此获得控制权限。

```text
Data contains text
≠
Data gains instruction authority
```

攻击路径可以理解为：低权数据里的文字试图冒充高权控制指令。成熟系统不能只靠模型“识别恶意文字”，还要靠 Permission / Policy / Sandbox / Validator 限制真实 Effect。

<a id="ch12-observation-assessment-truth"></a>
### 3.14 Observation ≠ Assessment ≠ Truth

#### 本节新词

- **Observation（观察）**：Tool、环境或 Source 实际返回的事实输入，例如 HTTP 状态、截图、退出码和测试输出。
- **Assessment（评估／判断）**：模型或规则对 Observation 意义、风险或根因的解释。
- **Truth / Current Truth（系统真值／当前真值）**：经过权威来源和验证规则确认后，Runtime 允许后续执行依赖的事实。
- **Hypothesis（假设）**：尚未验证的解释，例如“凭证可能过期”；它可以指导下一次检查，但不能直接 Commit 为 Truth。

用一个 `HTTP 401` 就能看见三者为什么必须分开：

```text
HTTP 401
= Observation

credential may be expired
= Assessment / Hypothesis

credential.status = EXPIRED
= Truth only after authoritative verification
```

因此模型可以提出根因，但不能为了“给答案”把未验证解释直接 commit 成 Truth。
<a id="ch12-fact-evidence-hypothesis"></a>
### 3.15 Fact / Evidence / Hypothesis / Decision 不要混成一段自然语言

#### 本节新词

- **Fact（事实）**：系统确认已经发生或当前成立的具体断言。
- **Evidence（证据）**：支持某个 Fact、Claim 或 Effect 的可重新检查材料。
- **Decision（决策）**：基于当前 Fact、Evidence、Policy 和风险选择的下一步。Decision 本身不是 Fact。

长期任务和未来 Multi-Agent 协作都需要把认识论对象拆开：

```text
Fact
= system currently accepts HTTP 401 occurred

Evidence
= trace / log / screenshot / test output supporting a claim

Hypothesis
= credential may be expired

Decision
= perform authoritative credential check before retry
```

后续 Multi-Agent 章节会把这种 truth discipline 应用到 Shared State，避免一个 Agent 的猜测污染共同真值。

<a id="ch12-artifact-evidence"></a>
### 3.16 Artifact ≠ Evidence

#### 本节新词

- **Artifact（产物／交付物）**：Task 正式生成或修改、可以版本化引用的对象，例如 commit、spec、report、build、ZIP。
- **Claim（主张）**：系统希望证明的一句话，例如“这个构建可以发布”。Evidence 用来支撑 Claim。
- **Provenance（来源／溯源）**：记录 Evidence 来自哪个 Source、版本、时间和执行上下文，使未来能够重新验证。
- **SHA（哈希标识）**：Git commit 或文件内容常用的哈希身份，可用于把 Evidence 精确绑定到某个版本。

针对一个 Artifact，Evidence 必须能够回到对应的 Claim、状态或真实 Effect，例如 test result、SHA、health probe、screenshot、来源引用。可靠 Evidence 还应尽量保留 Source / Provenance，否则未来只能看到结论，无法重新确认它来自哪里、针对哪个版本。

```text
release-v2.zip
= Artifact

sha256 + tests + deployment probe
= Evidence about that Artifact / Effect
```

产物可以成为被验证对象，但文件或提交本身不自动证明“正确”“已部署”“满足需求”。

<a id="ch12-evidence-bound-approval"></a>
### 3.17 Evidence-bound Approval：批准具体版本，不批准一个模糊未来

#### 本节新词

- **Evidence-bound Approval（证据绑定审批）**：审批同时绑定 Task、Action、Artifact Version、Evidence、审批人和 Scope，而不是对“未来任何变化”永久放行。
- **Stale（陈旧／失效）**：Artifact 已变化后，旧 Evidence 或 Approval 不再足以证明或授权新版本。

成熟 Approval 至少应绑定：

```text
Task
+ Action
+ Artifact Version / target
+ Evidence
+ approver / time / scope
```

如果 `Artifact A` 验证通过并获批，之后修改成 `Artifact B`，旧 Evidence / Approval 可能 stale。

```text
Artifact A → verified → approved
Artifact A changes to B
↓
old evidence may not prove B
↓
old approval may no longer authorize B
```

所以“一次说可以”不能无限延伸到未来不同版本的高风险 Effect。

<a id="ch12-validator-commit"></a>
### 3.18 Validator 在完整 Effect Lifecycle 里验证什么

沿用 Harness 章已经学过的 Validator，这里只看它在真实 Effect 链中的位置。

#### 本节新词

- **Tool Success（工具成功）**：某个局部动作报告执行成功；它不能自动证明更高层 Goal 已经完成。
- **Goal Success（目标成功）**：Task 的 Success Criteria 真正满足，例如产物正确、现实状态生效且证据齐全。
- **Effect Lifecycle（副作用生命周期）**：从 Proposal、授权、执行、Observation、Validation 到 Truth Commit 的完整链路。

这里必须保留一个更高层的完成边界：**Tool Success ≠ Goal Success**。一个 Tool 返回 `success` 只证明某个局部动作报告成功；Task 的 Success Criteria 可能还要求产物存在、业务状态正确、最终用户目标满足。因此 Tool Observation 仍需被更高层 Validator / Evidence 检查。

完整主链可以收束成：

```text
Observe current world
↓
Assess / Model Decision
↓
Propose Action
↓
Permission / Policy / Approval Gate
↓
Execute
↓
Observe actual result
↓
Validate + collect Evidence
↓
Commit Truth / State
↓
Checkpoint / Continue / WAIT / Complete
```

这就是 `Model proposes → Runtime commits` 的完整工程含义：模型可以提出，软件系统必须把现实 Effect、证据与当前真值重新闭环。
<a id="ch12-external-truth"></a>
### 3.19 External Truth：自我修改不能垄断自我验收

#### 本节新词

- **External Truth（外部真值）**：独立于当前 Proposal 的可验证来源，例如 test、compiler、Git Diff、权威 API、health check 或人工审批。
- **Closed-loop Self-confirmation（闭环自我确认）**：同一个概率主体既负责修改，又可以不经外部证据宣布“修改正确”的失效模式。
- **Health Check（健康检查）**：通过明确探测确认服务、资源或部署是否处于预期可用状态。

Agent 可以修改代码、配置甚至自身平台，但如果同一个概率主体既负责修改，又可以不经外部证据宣布“修改正确”，就会形成 closed-loop self-confirmation。

稳定原则是：重要 Effect 需要独立于 Proposal 的 External Truth，例如 test、compiler、Git diff、authoritative API、health check、human approval 或其他可重检 Evidence。

这为后续 Agent Eval 与 Multi-Agent independent verification 提供基础；Eval 的完整方法在 Evaluation 章。

<a id="ch12-governance-eval-boundary"></a>
### 3.20 Governance ≠ Eval / Observability / Economics

#### 本节新词

- **Governance（治理）**：确保动作在权限、Policy、Approval、审计和安全边界内执行。
- **Observability（可观测性）**：让系统能够回答“发生了什么、在哪里发生、耗时和状态如何”。
- **Eval / Evaluation（评估）**：衡量系统是否做得正确、稳定以及相对基线是否改善。
- **Economics（经济性）**：衡量质量收益与延迟、Token、算力、人工和平台成本是否值得。
- **Safety Gate（安全门禁）**：在高风险动作前由确定规则阻止不满足安全条件的执行。

平台层把 Governance / Eval 作为横向能力；本章只负责执行治理侧：AuthN/AuthZ boundary、Permission、Policy、Approval、Audit evidence、Safety gate。

```text
Governance
= 这次能否安全、合法、可追踪地执行

Observability / Agent Eval / Economics
= 发生了什么 / 做得好不好 / 值不值
= 完整评估方法留到 Evaluation 章
```

AI Platform 章 再负责它们作为 AI Platform cross-cutting responsibilities 的综合。

<a id="ch12-boundary-map"></a>
## ProFlow Lens｜Timeout 为什么不能直接 Retry

浏览器点击、Custom GPT 创建、外部部署等动作可能已经发生，只是响应丢失。ProFlow 因而需要把 Proposal、Authorized Action、Effect 与 Evidence 分开：Timeout 进入 UNKNOWN 后先回读现实状态，再决定 Commit、Retry、Compensate 或 Stop。这个案例把 Durable Execution 的抽象落到一个很具体的纪律：**先对账现实，再恢复流程。**
