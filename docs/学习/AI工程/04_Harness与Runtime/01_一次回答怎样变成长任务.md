# 一次回答怎样变成长任务

> 唯一职责：解释 Task、Turn、Thread、Session 生命周期与 Runtime 的连续性责任。  
> 读完要能回答：一次 Model Invocation、Thread 或 Session 都可以结束时，究竟什么责任必须继续存在，谁负责让它继续？
> 阅读前最好先懂 Workflow 与 Agent Loop。本章只回答“责任怎样跨调用、会话和进程继续存在”；Harness、State/Context/Memory 与恢复治理由后续章节分别展开。

<a id="ch10-30s-core"></a>
## 审批要等到明天，任务靠什么继续存在

设想 Browser Agent 已经把一份发布申请填写完，最后一步必须等负责人明天审批。今天的模型调用可以结束，浏览器窗口甚至可以关闭；但业务责任并没有结束。明天审批事件到达后，系统仍要知道：这是哪个目标、现在处于什么阶段、谁负责、已经产生了哪些结果、下一步从哪里继续。

这暴露了一个与“模型会不会思考”完全不同的问题：**短生命周期的调用可以消失，长期责任对象不能跟着消失。** 本章沿这条时间断点解释 Runtime 和 Task；具体 State、Context、Memory 以及故障恢复留给后续章节。

## Runtime 如何让任务跨进程和时间继续

<a id="ch10-runtime-definition"></a>
### 3.1 Agent Runtime：长期责任的确定性执行层

#### 本节新词

- **Agent Runtime（智能体运行时）**：让长期任务在真实软件世界里持续存在、被调度并执行的确定性软件层。模型负责概率判断，Runtime 负责让责任对象在模型不运行时仍然存在。
- **Lifecycle（生命周期）**：一个对象从创建、运行、等待到完成或失败所经历的状态过程。Runtime 需要管理的是 Task 的 lifecycle，而不是一条模型连接的寿命。
- **Owner（责任所有者）**：当前对任务推进和结果负责的主体。Owner 可以变化，但变化必须被系统显式记录。

因此 Runtime 必须同时承接生命周期、当前责任归属、可执行入口、调度接入和现实动作边界，使一次次短暂模型调用围绕同一个责任对象继续工作。

最小抽象是：

```text
Task exists
↓
Runtime decides whether work is runnable
↓
assemble needed invocation inputs (State/Context/Memory 章)
↓
Model proposes next decision
↓
Runtime / external system executes allowed effect
↓
Task remains / waits / completes
```

Runtime 不等于模型智能本身。模型负责概率性的 Decision；Runtime 提供确定性的任务容器与执行责任。

<a id="ch10-runtime-vs-workflow-harness"></a>
### 3.2 Runtime ≠ Workflow ≠ Harness

Workflow 已由前一层正式解释，Harness 会在本目录后面单独展开；这里不再给它们建立第二套定义，只用三者回答的问题做边界比较。

| 概念 | 主要问题 | Owner |
|---|---|---|
| Workflow | 允许怎样走？哪些路径预先存在？ | Workflow 章 |
| Harness | 这一轮怎样让模型更容易做对？ | Harness 章 |
| Runtime | 哪个 Task 正在承担什么责任，怎样持续执行？ | Runtime/Task 章 |

实现中三者可以位于同一个 framework，但心智模型必须分开。如果把 Runtime 写成“Agent Loop 的另一个名字”，会失去真正耐久的责任：Loop 关注下一步怎么决定；Runtime 关注**这个责任对象无论是否正在调用模型，都必须有地方存在**。

<a id="ch10-while-loop-boundary"></a>
### 3.3 为什么 `while(callLLM)` 不是 Durable Runtime

#### 本节新词

- **Process（进程）**：操作系统正在运行的程序实例。只存在于进程内存里的任务信息，会随着进程退出而丢失。
- **Persistence（持久化）**：把任务身份、状态或必要引用保存到进程之外，使系统重启后仍能重新定位。
- **Durable（耐久）**：这里指责任能够跨进程退出、等待和重启继续存在，不是“程序永远不报错”。
- **LLM（Large Language Model，大语言模型）**：这里是 Runtime 可能反复调用的智能计算组件；`while(callLLM)` 只能让一个进程持续调用模型，不能自己提供耐久任务语义。

一个内存里的循环可以连续调用模型，但只要进程退出、机器重启、等待审批或外部任务数小时，它的连续性就会断掉。

```text
while task_not_done:
    call_model()
```

缺少的是长期责任语义：Task identity、persistent status、resume entry、waiting ownership，以及与后续 State / Checkpoint / Recovery 的连接。

所以 Runtime 的出现不是为了“再包一层框架”，而是因为真实任务会跨时间、等待、断线、人工输入和不同执行容器。

<a id="ch10-task-definition"></a>
### 3.4 Runtime Task：长期责任对象

#### 本节新词

- **Runtime Task（运行时任务）**：跨模型调用、会话甚至进程持续存在的长期责任对象。它必须能被稳定标识，并拥有 Goal、Status、Owner、成功标准和待处理工作。
- **Task Identity（任务身份）**：让系统在未来重新找到“还是同一个任务”的稳定标识。它不能依赖聊天窗口当前是否还打开。
- **Status（状态标签）**：描述任务当前处于 `RUNNING / WAITING / SUCCEEDED / FAILED` 等哪一种生命周期位置。

一个真正可持续追踪的 Task，最少应该能回答：

```text
Goal 是什么？
当前 Status 是什么？
谁负责？
Success Criteria 是什么？
当前 Artifact / Pending Work 是什么？
接下来是否可运行？
```

State/Context/Memory 与 Durable Execution 两章会继续区分 State、Evidence、Checkpoint 等信息对象；这里先强调：**它们都挂在同一个可持续追踪的 Task responsibility 上。**

<a id="ch10-task-thread-session"></a>
### 3.5 Task ≠ Thread ≠ Session

#### 本节新词

- **Turn（轮次）**：一次用户/系统输入与模型输出形成的局部交互单位，通常比 Thread、Session 和 Task 都短。
- **Thread（消息线程）**：组织一串相关消息的沟通容器，主要保存 communication history。
- **Session（运行会话）**：一次临时工作台，可绑定浏览器、终端、模型连接或当前 Context，生命周期通常短于 Task。
- **Run（一次运行）**：某个 Task 或 Workflow 的一次具体执行尝试。产品可以把 API 命名为 run，但它不自动等于长期 Task。

| 对象 | 核心职责 | 常见生命周期 |
|---|---|---|
| Thread | 组织消息 / communication history | 一段消息链 |
| Session | 一次工作台，绑定临时执行资源与上下文 | 分钟～小时 |
| Runtime Task | 对 Goal 和结果负责的长期责任对象 | 小时～天甚至更久 |

一个 Task 可以经历多个 Session；一个 Session 也可能打开多个消息 Thread。正式边界仍然是 `Task ≠ Thread ≠ Session`。不要因为某个平台把长任务 API 叫 `thread` 或 `session`，就让产品命名反向覆盖知识架构里的责任模型。
<a id="ch10-model-task-lifetime"></a>
### 3.6 Model Invocation lifetime ≠ Task lifetime

#### 本节新词

- **Model Invocation（模型调用）**：一次把 Context 送入模型并取得输出的推理请求。调用完成后模型计算可以结束，但任务责任不必结束。
- **Inference（推理）**：模型使用已有参数处理当前输入并产生输出的过程；它与 Task lifecycle 是不同时间尺度。

```text
Model Invocation
Context in → inference → output → ends

Runtime Task
created → running → waiting → running → verifying → complete
```

真正长时间工作的不是一次 invocation，而是 Task。模型可以换、Context 可以重建、进程可以重启；只要责任还没完成，Runtime 就必须保留重新进入这个 Task 的能力。

这是 Runtime 最重要的一条责任边界：**Model can stop; Task responsibility persists.** “Context 可以重建而 State 必须持久”的信息对象一侧由下一章定义。

<a id="ch10-task-continuity"></a>
### 3.7 Task continuity ≠ Conversation replay

#### 本节新词

- **Task Continuity（任务连续性）**：系统能够持续认出同一个责任对象，知道它当前的位置、Owner 和下一执行入口。
- **Conversation Replay（对话重放）**：把历史消息重新装入模型 Context，帮助模型恢复语言上下文；它不能替代任务真值和生命周期。

聊天产品常通过重放 history 形成对话连续感，但长期 Task continuity 不能只靠复制整段聊天。

Task continuity 的最低要求是：系统能重新定位同一个责任对象，并知道它当前是否可继续、由谁负责、下一执行入口在哪里。

```text
Conversation replay
= 给模型看过去说过什么

Task continuity
= 系统知道当前责任对象仍是什么、现在应从哪里继续
```

前者属于应用/Context 手段；后者是 Runtime 责任。

<a id="ch10-resume-entry"></a>
### 3.8 Resume：重新进入 Task，不是恢复隐藏思维

#### 本节新词

- **Resume（恢复继续）**：在未来重新进入同一个 Task 的执行入口。它依赖持久化的任务世界，不要求恢复上一轮模型的隐藏思维。
- **Task World（任务世界）**：为了继续工作必须知道的外部事实集合，例如 Task identity、当前状态、Artifact 引用、待办和允许的执行入口。

真正恢复时，应从持久化的 Task World 重新建立执行条件，而不是声称恢复上一轮模型的 hidden Chain of Thought。

```text
Task identity
+ persisted current information
+ artifact / pending work refs
+ allowed execution entry
↓
rebuild Context (State/Context/Memory 章)
↓
new Model Invocation if needed
```

Checkpoint、State Reconciliation 与 Recovery 的完整机制留到 Durable Execution 章；这里先守住一个不变条件：**恢复的是责任世界，不是模型脑内状态。**
<a id="ch10-event-resume-application"></a>
### 3.9 Runtime 如何被未来变化重新唤醒

异步 Subagent、远端协作或外部任务完成后，平台会收到“审批通过”“Child Task 完成”“资源就绪”这类未来变化。这里先按 Runtime 语义理解：Event 是已经发生的变化，WAITING 表示任务仍存在、只是暂时不能继续。它们的完整状态与恢复机制留到 Durable Execution 章。

```text
external / child change
↓
Runtime locates durable Task
↓
resume entry becomes eligible
↓
State/Context/Memory 章 rebuilds needed Context
↓
new model call only if a decision is needed
```

所以 Agent 不需要常驻监听。**Runtime 持续拥有 Task；模型只在需要智能判断时被重新调用。**

<a id="ch10-parent-child-task"></a>
### 3.9A Parent / Child Task｜委派的是局部责任，不是把 Parent 复制一份

#### 本节新词

- **Parent Task（父任务）与 Child Task（子任务）**：Parent 把局部责任拆成可独立跟踪的 Child；两者拥有各自状态，但 Child 的结果要通过明确依赖关系影响 Parent。
- **Dependency（依赖关系）**：一个任务能否继续取决于另一个对象的明确关系，例如 Parent 必须等待 Child 成功。
- **Artifact Reference（交付物引用）**：指向子任务实际产物的位置或版本，而不是把全部内容复制进 Parent 聊天。

在 Agent Loop 中，异步 Subagent 是 Harness 提供的一种协作方式；进入 Runtime 后，更稳定的对象不是“两个聊天 Session”，而是 Parent Task 与 Child Task 的责任关系。

```text
Parent Task P
owner = Parent Agent
status = RUNNING / WAITING_CHILD
│
└─ delegate Child Task C
   owner = Child/Subagent
   success criteria = local goal
   artifact/evidence refs = local output
```

Child 可以使用独立 Session / Thread / Workspace，但这些只是执行容器；真正需要长期追踪的是 Child Task 的 Goal、Owner、Status、Result/Evidence，以及它和 Parent 的 dependency relation。

Parent 不应靠轮询 Child conversation 获得进度。Child 的确定变化进入 Event / State，Runtime 再判断是否影响 Parent runnable condition。

<a id="ch10-event-scheduler-resume-chain"></a>
### 3.9B Event → Scheduler → Context → Resume｜长任务真正怎样重新“活起来”

通用 Scheduler 的资源调度与 Policy 由后面的 Routing 章正式负责。这里新增的是 Runtime 场景里的两个状态语义：

#### 本节新词

- **Runnable（可运行）**：任务所需依赖已经满足，可以进入下一次执行。
- **Late Result（迟到结果）**：子任务或外部工作在 Parent 已取消、交接或版本前进后才返回的结果，不能无条件覆盖当前状态。

Scheduler 在这条链里只判断长期 Task 何时重新具备执行条件，不替模型在后台思考。完整应用链更接近：

```text
Child / external work changes
↓
semantic Event
COMPLETED / BLOCKED / NEEDS_DECISION / FAILED
↓
Runtime maps Event to durable Parent Task
↓
update dependency / runnable facts
↓
Scheduler evaluates: Parent now runnable?
├─ No → remain WAITING
└─ Yes
   ↓
   State/Context/Memory 章 Context Assembly
   Goal + current State + child Artifact/Evidence refs
   ↓
   new Model Invocation
   ↓
   Parent decides next Action
```

这解释了为什么 Scheduler 不是“后台帮模型继续思考”的组件。Scheduler 只负责确定：**什么时候这个长期责任对象重新具备执行条件。** 智能判断只在真正需要时重新调用模型。

如果 Parent 在等待期间已经 handoff、cancel 或 version 前进，晚到的 Child Result 也不能直接覆盖当前世界；Durable Execution 章介绍的 ownership、version 与 evidence gate 会决定它是接受、降为参考还是丢弃。

<a id="ch10-remote-resume-boundary"></a>
### 3.10 跨协议变化最终仍要落回本地 Runtime Task

#### 本节新词

- **Protocol Update（协议更新）**：MCP、A2A 或其他远端协议传来的状态变化。它是输入，不会自动成为本地 Runtime 的 Task 真值。
- **Mapping（映射）**：把远端对象的身份和状态关联到本地 Task responsibility 的规则。

远端 Agent / capability 的状态变化可以通过协议进入平台，但本地系统仍要把它映射回自己的 Task responsibility。

```text
remote status / protocol update
↓
local Runtime Task
↓
local information update (State/Context/Memory 章)
↓
scheduling / recovery gate (Durable Execution 章)
↓
resume
```

协议怎样传输，分别留到 MCP/Capability 章与 A2A/互操作章；Runtime 不把远端协议 Task 直接当成本地 Task 实现。

<a id="ch10-task-namespaces"></a>
### 3.11 Runtime Task ≠ MCP Task ≠ A2A Task

#### 本节新词

- **Namespace（命名空间）**：同一个词在不同系统中可以有不同正式含义。`Task` 必须先看属于 Runtime、MCP 还是 A2A，不能只按名字合并定义。
- **MCP Task / A2A Task**：分别属于能力调用协议和 Agent 协作协议的任务对象；它们可以映射到本地 Runtime Task，但不拥有同一语义。

| 名称 | 所属责任 | 继续阅读 |
|---|---|---|
| Runtime Task | 平台内部长期责任对象 | Runtime/Task 章 |
| MCP Task | capability invocation 的协议扩展生命周期对象 | MCP/Capability 章 |
| A2A Task | 独立 Agent 协作中的协议工作对象 | A2A/互操作章 |

它们可以建立 mapping，但不能因为都叫 `Task` 就共享一套定义。

<a id="ch10-boundary-map"></a>
## ProFlow Lens｜聊天为什么不能成为 Task Truth

ProFlow 的 Task 会跨会话、进程、人工等待和 Browser Conversation 继续运行，因此 `聊天历史还在` 不能证明任务状态还正确。Task/Node status、version、current node、Role/Worker binding 与 Event 必须进入 durable Runtime；新的模型调用只读取和重建 Context。这个演进正好说明：**长的是 Task/State，不是一次模型会话。**

## 当前 Runtime 与任务系统事实

这里没有把任何 2026 年厂商提供的 Session、Thread 或 Runtime API 当成通用定义。不同产品可以把容器命名为 thread、session、run 或 task，但任务生命周期和责任边界不会因此改变。

本章没有依赖未经核验的厂商动态事实。
