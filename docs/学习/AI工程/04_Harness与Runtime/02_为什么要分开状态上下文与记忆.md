# 状态、上下文与记忆为什么必须分开

> 唯一职责：区分 Current Truth、当前工作集、历史记录和可复用过去。  
> 读完要能回答：什么是当前真值，什么只是历史；什么值得未来复用；而一次模型调用真正应该看到什么？
> 前置阅读：上一章的长期任务运行，以及知识与检索章节。本章只回答四类信息怎样分开保存、选择、压缩和复用；模型容量、检索装配、恢复断点和真值提交留在各自专题。

<a id="ch11-30s-core"></a>
## 长任务为什么会被自己的历史信息带偏

一个任务执行了两天，聊天记录里可能同时存在旧计划、失败尝试、已经过期的状态、用户偏好、Tool 返回和临时推断。最危险的做法，是把整段历史重新塞给模型，然后让模型自己判断“哪个才是现在”。一条昨天正确、今天已经失效的信息，只要继续被当成当前事实，就足以让后续动作全部走错。

系统因此必须分开保存四种东西：现在继续执行依赖的事实、过去发生过什么、过去哪些内容以后值得复用，以及这一轮模型真正需要看到什么。它们可以互相流动，却不能因为都叫“信息”就塞进一个文本字段。

## 信息怎样被保存、选择、压缩和重新使用

<a id="ch11-information-model"></a>
### 3.1 四个信息对象先分开

#### 本节新词

- **State（状态）**：继续执行依赖的 Current Truth（当前真值）。如果它过期后仍被使用会直接导致错误动作，就不能只把它当普通历史。
- **History（历史记录）**：按时间保存“发生过什么”的记录，包括消息、事件、旧 Tool Result 和旧计划；它天然包含已经失效的内容。
- **Memory（记忆）**：从过去信息中筛选后，未来 Task / Session 仍值得复用的内容。Memory 是治理后的复用对象，不是 save-all。
- **Runtime Context（运行时上下文）**：某一次 Model Invocation 真正被装配给模型的工作集。它是调用时视图，不是持久存储层。
- **Current Truth（当前真值）**：系统当前愿意让后续执行依赖的事实状态。它需要来源和更新规则，而不是“最近一句模型描述”。

| 对象 | 核心问题 | 是否天然持久 | 是否当前模型一定可见 |
|---|---|---|---|
| State | 现在到底是什么？ | 应持久化关键真值 | 否，需装入 Context |
| History | 过去发生过什么？ | 可归档 | 否 |
| Memory | 过去什么值得未来复用？ | 按 scope/lifetime 治理 | 否，需 retrieval/assembly |
| Context | 这一次模型看到什么？ | 本身是调用工作集 | 是 |

这四者不是四种数据库。它们是四种**语义责任**，实现可以共享存储，但不能因为同库而合并概念。

正式边界可以压成：`State ≠ History ≠ Memory ≠ Context`。这个式子不是为了背名词，而是防止当前真值、时间记录、可复用过去和本轮工作集互相覆盖。

<a id="ch11-state"></a>
### 3.2 State：继续执行依赖的 Current Truth

#### 本节新词

- **Source of Truth（真值源）**：对某一类事实拥有权威解释权的系统或对象，例如当前数据库记录、受治理状态或当前源码。State 往往从这些来源提炼继续执行所需的当前事实。
- **Pending Work（待处理工作）**：任务还没有完成、后续必须继续处理的明确责任，而不是模糊的“以后再看看”。

例如一个跨天发布 Task，下一步真正依赖的是 `status`、current owner、latest artifact ref、verification status 和 pending work。它们一旦过期就会直接改变后续动作，因此必须作为 State 被当前系统维护。

实用判断：

> **如果一条信息过期后仍被使用，会直接导致错误动作，它优先属于 State / Source of Truth，而不是普通 Memory。**

State 不等于“最近发生的所有事情”，也不等于模型对情况的解释；Observation、Assessment 与 Truth 的提交边界留到 Durable Execution 章。

<a id="ch11-history"></a>
### 3.3 History：原始时间记录

#### 本节新词

- **Chronology（时间顺序记录）**：按发生顺序保留事件和消息。Chronology 有利于追溯，但“发生得更晚”不自动意味着“更权威”。
- **Archive（归档）**：把不需要常驻当前工作集、但未来可能需要追溯的历史保存到可检索位置。

messages、events、旧 Tool outputs、旧 plans 可以按时间继续保留。它们的价值在于追溯“当时发生了什么”，但其中天然会混入过期信息、失败探索、重复内容和已经被新事实覆盖的旧状态。

因此：

```text
History
≠ Current State
≠ Memory
```
<a id="ch11-context"></a>
### 3.4 Runtime Context：当前 invocation 的工作集

#### 本节新词

- **Working Set（工作集）**：为了完成当前一次判断而暂时放在一起的信息集合。Runtime Context 就是模型调用时的工作集。
- **Model Invocation（模型调用）**：把当前 Context 交给模型并取得一次输出的推理请求；上一章已经解释它与长期 Task 的时间尺度差异。

准备下一次 Model Invocation 时，Runtime 不会把所有持久信息原样搬进去，而是从当前 Goal、State、Memory、Knowledge、Tool Result 和必要 History 中挑出这一轮真正需要的工作集：

```text
System / task instruction
+ current Goal
+ selected State
+ relevant Memory
+ retrieved Knowledge
+ recent Tool Result
+ relevant History
↓
Runtime Context
```

因此“系统里保存了”不等于“模型这一轮看到了”；反过来，“模型这一轮看到了”也不代表它应该被长期保存。

<a id="ch11-memory"></a>
### 3.5 Memory：未来值得复用的过去

#### 本节新词

- **Scope（作用域）**：一条 Memory 可以被谁复用，例如 User、Project、Agent、Task 或 Session。
- **Lifetime（有效期／生命周期）**：这条 Memory 应在多长时间或什么条件下继续有效。长期保存不等于永久可信。
- **Reusable（可复用）**：信息对未来任务仍有稳定价值，而不是只对刚发生的这一轮有用。

只有那些**来自过去、以后还值得复用、并且知道适用范围和失效条件**的信息，才值得晋升为 Memory。一次失败尝试、刚刚读取的库存、已经被新版本覆盖的偏好，都不应该因为“系统见过”就长期记住。

它至少满足三个条件：

```text
past-derived
+ reusable later
+ governed by scope / source / lifetime
```

因此 Conversation History、Knowledge Source、KV Cache、Current State 都不能因为“也保存信息”就叫 Agent Memory。

<a id="ch11-context-assembly"></a>
### 3.6 General Context Assembly：把需要的信息组成本轮工作集

#### 本节新词

- **Context Assembly（上下文装配）**：在模型调用前，从 State、Memory、Knowledge、History、Tool Result 等来源中选择、排序、压缩并组合本轮工作集。
- **Context Engineering（上下文工程）**：设计“这一轮模型应该看到什么、什么不应该进入、怎样排序和压缩”的工程工作。
- **Prompt Engineering（提示词工程）**：更偏优化已经决定进入本轮调用的信息怎样表达。Prompt 是 Context 的一部分，不是 Context Engineering 的全部。
- **Capability Metadata（能力元数据）**：描述当前有哪些 Tool / Capability 可用、它们的用途和约束的信息；它也可能被选择性装入 Context。
- **Token Budget / Latency Budget（Token／延迟预算）**：这次调用允许占用多少上下文 Token 和等待时间，用于约束“信息越多越好”的冲动。

装配真正困难的地方不是“把资料拼起来”，而是决定哪些材料值得进入、如何排序以及哪些应该被排除。

这里也给出一个高价值边界：**Prompt Engineering（提示工程）**主要优化“已有输入怎样表达”；**Context Engineering（上下文工程）**首先决定“这次 invocation 到底应该看到什么”，再谈如何表达。

Context Assembly 的候选来源不仅有文本，还包括当前可用 Tool/Capability metadata、Policy constraints 与它们产生的 Result；是否真正装入仍按当前 Task 需要选择。

好的 Context 追求的是：

- decision-critical information 完整；
- 当前事实优先；
- 低冗余；
- 来源和边界清楚；
- 符合 token / latency budget。

所以 Context Engineering 的上位问题不是“Prompt 怎么写得更长”，而是：**这次 decision 应该看到哪些可信信息，又应该排除哪些旧噪声。**

<a id="ch11-context-compaction"></a>
### 3.7 Context Compaction：从工作集移除，不等于删除系统事实

#### 本节新词

- **Context Compaction（上下文收缩／压缩）**：在安全边界把低价值过程从当前工作集中移走、摘要或改成引用，再重新装配更干净的 Context。
- **Safe Point（安全点）**：系统已经把继续执行所需的关键 State / Artifact / Evidence 持久保存，可以放心压缩临时工作集的位置。
- **Summary（摘要）**：对历史文本的概率性压缩，适合恢复语义背景；它不能独自承担 Owner、硬约束或当前状态。

一个常见安全边界是两个 Agent Turn 之间：先保存继续执行依赖的事实，再归档低价值过程、压缩旧讨论并重新装配。

```text
old working set grows
↓
safe point
↓
persist correctness-critical information
↓
archive / summarize low-value history
↓
rebuild cleaner Context
```

**从 Context 移除 ≠ 从系统删除。** Raw History 可以归档后按需检索；State、Artifact、Evidence 等 correctness-critical 对象不能只靠概率摘要保存。
<a id="ch11-context-namespaces"></a>
### 3.8 Context Window ≠ Runtime Context ≠ RAG Context Assembly

#### 本节新词

- **Context Window（上下文窗口）**：模型一次调用可处理的 Token 容量边界，属于模型能力约束。
- **RAG Context Assembly（RAG 上下文装配）**：只负责把检索回来的外部证据筛选、排序并放进 Context，是 General Context Assembly 的一个特化。
- **Private Context（私有上下文）与 Handoff Context（交接上下文）**：Multi-Agent 场景中分别表示只给某个责任主体看的工作集，以及交接责任时必须传递的最小信息；后续协作章展开。

| 名称 | 含义 | Owner |
|---|---|---|
| Context Window | 模型一次调用可处理的 token 容量约束 | Transformer 章 |
| Runtime Context | 当前 invocation 被装配的工作集 | State/Context/Memory 章 |
| General Context Assembly | 多来源选择并组成本轮工作集 | State/Context/Memory 章 |
| RAG Context Assembly | 对检索候选证据做过滤、排序、版本与 budget 管理的 specialization | RAG 章 |
| Private / Handoff Context | Multi-Agent 信息边界 specialization | Multi-Agent 组织章 |

不要只写一个模糊的 `Context` 就让模型容量、工作集和检索装配混成一层。

<a id="ch11-context-quality"></a>
### 3.9 长任务“越做越笨”常是工作集质量问题

#### 本节新词

- **Signal-to-Noise Ratio（信噪比）**：当前 Context 中真正影响决策的信息与无关、过期、重复内容之间的比例。History 越长，不代表信噪比越高。
- **Stale Information（陈旧信息）**：曾经正确、但已经被新状态或新版本替代的信息。它进入 Context 后很容易与当前事实竞争注意力。

当旧 History、失败尝试、过期 Tool Result 和旧 Plan 不断累积，Signal-to-Noise Ratio（信噪比）下降，模型更容易重复、忘记约束或使用旧事实。

```text
more history
≠ more useful context
```

可靠方向不是无限扩展聊天，而是把重要信息提升到正确对象：Current State 留在 State；稳定经验经过治理后进入 Memory；低价值历史归档；下一轮重新装配干净 Context。

<a id="ch11-memory-taxonomy"></a>
### 3.10 Memory taxonomy：记多久，与记什么是两条轴

#### 本节新词

- **Short-term Memory（短期记忆）/ Long-term Memory（长期记忆）**：按复用时间和范围区分“记多久”。
- **Semantic Memory（语义记忆）**：保存相对稳定的事实或知识。
- **Episodic Memory（情景记忆）**：保存某次具体经历、过程和结果。
- **Procedural Memory（程序性记忆）**：保存反复验证后可复用的方法或操作知识。

这两组分类回答不同问题：Short/Long-term 关心“复用多久”，Semantic/Episodic/Procedural 关心“保存的是什么”。因此一段刚完成的任务经验可以是 short-term episodic；一个长期有效的操作方法则可能是 long-term procedural。

两条轴可以组合，不能把 `short-term = episodic` 或 `long-term = semantic` 机械画等号。

<a id="ch11-memory-promotion"></a>
### 3.11 Memory Write = Promotion

#### 本节新词

- **Promotion（晋升）**：把 History / Observation 中的候选信息经过来源、可信度、Scope、Lifetime 和冲突检查后，正式提升为可长期复用对象。
- **Memory Candidate（记忆候选）**：模型或系统认为“可能值得以后复用”的信息，在治理通过前仍不是正式 Memory。
- **Update Rule（更新规则）**：说明一条 Memory 在什么新事实出现时应该修改、失效或被替代。

`Memory Write = promotion`。Memory Write 不是“存起来”这么简单，而是把原始信息经过治理后**晋升**为未来可复用对象。

```text
History / Observation / Tool Result
↓
Memory Candidate
↓
source / trust / scope / type / lifetime / conflict gate
├─ continuation-critical truth → State
├─ reusable fact → Semantic Memory
├─ useful experience → Episodic Memory
├─ repeatedly validated method → Procedural Memory / Skill boundary
└─ temporary / weak / noisy → do not promote
```

模型可以提出 candidate；持久写入必须遵守 Runtime policy / validation。

每一条 Memory write 至少回答四组问题：**What**（记什么 / type）、**Scope**（谁能复用）、**Lifetime**（多久有效）、**Retrieval**（什么时候能被找回）；写入时还要记录 **Why / Source / Update rule**，否则以后无法判断它为什么存在、该不该信、何时失效。

<a id="ch11-memory-scope-trust"></a>
### 3.12 Scope 与 Trust：错误记忆传播范围越大，破坏越大

#### 本节新词

- **Trust（可信度）**：系统对某条信息来源和验证程度的信任判断。它不等于向量相似度，也不应只由模型“自信程度”决定。
- **Least Memory Scope（最小记忆作用域）**：不确定信息先限制在最小可用范围，只有证据充分时才扩大复用边界。
- **Hypothesis（假设）**：尚未被验证、但值得后续检查的推断。Hypothesis 可以被保存为候选，不能伪装成 Fact。

Memory 至少要知道属于哪个范围：User / Project / Agent / Task / Session。遵循 **Least Memory Scope（最小记忆作用域）**：不确定时先保存在更小范围，不轻易升级成全局事实。

来源可信度也要显式区分。通常：

```text
User explicit / authoritative source
+ verified observation
> unsupported model inference
```

这不是一个永恒数值排序，而是安全原则：**Inference 不能悄悄晋升为 Fact。** 若推断值得保留，应标记为 hypothesis / low-confidence candidate，而不是伪装成已验证事实。

<a id="ch11-memory-lifecycle"></a>
### 3.13 Memory lifecycle：记忆也会过期、冲突和被替代

#### 本节新词

- **Invalidate（失效）**：保留历史记录但明确标记它不再适合作为当前可复用事实。
- **Append-only（只追加）**：只允许新增、不允许修改或失效旧记录的存储方式。原始 History 可以接近 append-only，但 Memory 不能因此放弃冲突治理。

Memory 不应是 append-only 文本池。至少需要考虑：

```text
Create
Update
Merge
Invalidate
Delete
```

旧事实被新事实替代后，应显式失效、版本化或降权；否则 Retrieval 可能同时返回多个冲突版本，让模型猜“哪个才是真的”。

Episodic experience 也不能因为一次成功就自动升级成 Procedural Memory；稳定方法需要重复 Evidence 和验证。

<a id="ch11-memory-retrieval"></a>
### 3.14 Memory Retrieval：现在值得想起什么

#### 本节新词

- **Memory Retrieval（记忆检索）**：根据当前 Goal / Task / State 从已治理 Memory 中找出现在真正值得回忆的内容。
- **Top-K**：检索时取排序最前面的 K 个候选；它只是数量策略，不能替代 Scope、Freshness、Trust 和 Conflict 检查。
- **Freshness（新鲜度）**：信息距离当前有效状态有多近，是否已经被更新或替代。
- **Conflict Gate（冲突门禁）**：当候选 Memory 相互矛盾时，先按来源和版本处理冲突，再决定是否进入 Context。

真正的记忆检索还要经过需求识别、作用域、权限、新鲜度和冲突过滤，而不是对一个向量库做完 Top-K 就结束：

```text
Goal / Task / State
↓
Need detection
↓
Scope / type / permission filters
↓
Keyword / metadata / vector / hybrid retrieval
↓
Rerank
↓
Freshness / trust / conflict gate
↓
selected Memory
↓
Context Assembly
```

RAG 章的 Vector、Retriever 与 Reranker 负责检索；本章继续处理 Memory 的 scope、freshness、trust、lifetime 和 conflict。

<a id="ch11-knowledge-vs-memory"></a>
### 3.15 Knowledge Source ≠ Runtime Memory

#### 本节新词

- **Knowledge Source（知识源）**：Git、Spec、Database、正式文档等外部或权威资料世界。它们可以被检索进入 Context，但语义上不属于“从过去交互晋升出来的 Memory”。
- **Knowledge Base（知识库）**：组织和提供知识源或其索引的系统。是否使用向量数据库只是实现选择，不改变它与 Memory 的语义边界。

Git repository、Spec、Database、正式文档和外部 Knowledge Base 更准确地叫 **Knowledge Source（知识源）**。它们可以被检索进入 Context，但不应因为“Agent 以后还会用”就全部称为 Memory。

```text
RAG / Knowledge Source
= 外部或权威知识世界

Memory
= 从过去交互 / 经历 /决策中治理后保留的可复用信息
```

二者都可以用 Retrieval，也都最终通过 Context Assembly 被模型使用，但语义和 authority 不同。

<a id="ch11-memory-conflict"></a>
### 3.16 信息冲突：相似度不能决定真值优先级

#### 本节新词

- **Fresh Evidence（新鲜证据）**：靠近当前时间、版本和权威状态的可验证材料。它通常比历史 Memory 更适合裁决当前事实。
- **Authority（权威性）**：多个来源冲突时，哪个来源对这类事实拥有更高解释权。Authority 是治理规则，不是模型语言风格或相似度分数。

一个实用冲突顺序是：

```text
Current Source of Truth
→ Fresh Evidence
→ Current State
→ Relevant Memory
→ Historical Conversation
```

这是一条工程决策规则，不是跨所有业务的绝对法律；关键原则是：**更接近当前权威事实的来源，优先于过去经验和文本相似度。**

Evidence 与 Truth Commit 的完整机制留到 Durable Execution 章；这里关注的是怎样选择信息，避免旧 Memory 或 History 覆盖当前事实。
<a id="ch11-summary-state-checkpoint"></a>
### 3.17 Summary 不等于 State，也不等于 Checkpoint

#### 本节新词

- **Checkpoint（检查点）**：为了故障恢复而保存的可继续执行点，包含恢复所需的持久信息；完整定义属于 Durable Execution 章。
- **Artifact Version（交付物版本）**：某个文件、报告、代码或其他产物的明确版本标识，避免摘要只说“最新文件”却无法定位。
- **Evidence Reference（证据引用）**：指向可验证证据的位置或身份，而不是把全部证据复制进摘要。

Summary（摘要）适合压缩 History、恢复语义背景，但它是概率性表达。硬约束、当前 Owner、Artifact version、Evidence refs、Pending Action 等不能只放在 summary 中。

```text
Summary
→ semantic compression

State
→ continuation-critical current truth

Checkpoint (Durable Execution 章)
→ recovery-safe persisted execution point
```

所以本章只保留“Summary 不能替代持久 State”的信息模型侧；Checkpoint / Durable Execution 的完整定义留给后续章节。

<a id="ch11-reference-context"></a>
### 3.18 Reference-based Context：传引用，不复制整个世界

#### 本节新词

- **Reference-based Context（基于引用的上下文）**：Context 优先携带稳定对象引用和必要摘要，需要细节时再读取原对象，而不是复制完整历史。
- **Provenance（来源追踪）**：记录信息从哪个 Source、Version 或 Evidence 而来，便于后续验证和冲突处理。

当材料很大时，Context 可以优先携带 artifact/evidence/spec/checkpoint 的稳定引用，而不是复制几十页历史。需要时再按引用检索具体内容。

这同时提高：

- token efficiency；
- freshness；
- provenance；
- 多 Agent 隔离能力。

Multi-Agent 组织章会把这一原则进一步应用到 Private Context 与 Handoff Context。
