# 任务怎样选择模型和路径

> 唯一职责：解释一个任务怎样选择模型、推理档位、工具或责任主体，策略怎样限制候选路径，调度怎样安排有限资源。

## 选谁做、何时做、允不允许做是三类决定

### 本节新词

- **Router（路由器／路由决策）**：根据当前任务特征在候选执行路径中做选择。它只负责“从候选里选什么”，不能顺手吞掉权限、资源排队和最终真值。

一个平台同时有端侧小模型、云端通用模型、强推理档位和多种 Tool。请求进来以后，至少会出现几种不同问题：

```text
这次由哪个模型处理？
这个模型值得投入多少推理预算？
当前任务需要哪项 Tool？
如果存在多个独立 Agent，责任交给谁？
任务现在能不能运行、先占哪个资源？
这条候选路径是否被 Policy 允许？
```

这些问题后面会分别命名。这里先记住：**选择目标、安排资源、判断允许性不是同一个动作。** 把它们都塞进一个 `router`，一旦出现成本、权限、队列或恢复问题，就很难知道该修哪一层。

## Gateway、Router、Policy 与 Scheduler 怎样配合

### 本节新词

- **SLA / SLO（服务等级协议／服务目标）**：SLA 是对外承诺，SLO 是内部用来衡量延迟、可用性或成功率的目标。路由通常依据 SLO 做决策。

```text
Task metadata + risk + SLA + cost budget
  ↓
Policy filter：哪些模型/能力/主体允许
  ↓
Routing decision：选择执行目标与推理档位
  ↓
Scheduler：priority / concurrency / quota / admission
  ↓
Gateway / Adapter：规范请求、调用 Provider、记录 usage
  ↓
Result + telemetry + evidence
  ↓
Eval feedback：更新路由策略，不让模型自报胜率
```

路由是一个受约束决策问题，不只是负载均衡。

## Model Gateway 的稳定责任

### 本节新词

- **Provider（模型提供方）**：实际托管或提供模型推理服务的厂商、云平台或本地运行环境。
- **Quota（配额）**：限制用户、租户或任务可以消耗的调用量、Token 或计算资源。
- **Telemetry（遥测数据）**：调用时记录的 usage、latency、error、model/version 等运行数据，用于观测和 Eval。
- **Fallback（回退路径）**：首选 Provider/Model 不可用或不满足条件时切换到备用路径。Fallback 会改变模型行为和成本，不能当成无差别重试。

Model Gateway 通常负责：

- 统一 Provider/Model 调用合同；
- 身份、配额、速率和成本边界；
- 超时、取消、重试策略的基础原语；
- usage、latency、error、model/version 记录；
- Provider fallback 与健康状态；
- 数据保留、地区、隐私和合规策略；
- 为 Eval 提供可比较的调用证据。

它不应该自动拥有业务 Task、Tool Permission、Agent Plan 或最终 Truth。Gateway 知道一次调用发生了，不等于知道业务目标完成了。

## Model Routing：选择“让谁做”

### 本节新词

- **Model Routing（模型路由）**：根据任务类型、领域、风险、延迟、成本、Context、模态和历史评估结果，从候选模型或 Profile 中选择“让谁做”。
- **Modality（模态）**：文本、图像、音频、视频等不同输入/输出形式；路由必须先确保候选模型支持所需模态。

路由输入不应只有 Prompt 文本，还应包含：

这里的 SLO（Service-Level Objective，服务目标）是任务对延迟、可用性或成功率的明确要求，不是模型自己的属性。

```text
task type / domain
difficulty estimate
risk and reversibility
latency SLO
cost budget
context size / modality
tool requirements
privacy / region constraints
historical slice performance
```

候选先经过硬过滤，再按质量、延迟、成本排序。后面的 Eval 章会正式定义 Failure Slice；这里先用它作为路由输入：某模型总体更强，不表示它在代码迁移、中文长文或结构化提取这些具体任务切片上都更合适。

## Reasoning Routing：FAST / REASON 不是两个固定人格

### 本节新词

- **Reasoning Routing（推理路由）**：模型路径确定后，再决定这次调用值得投入多少推理计算、何时需要升级更深推理的策略。
- **FAST / REASON Profile（快速／推理档位）**：把低延迟低成本和更高推理预算抽象成两类服务档位；它们可以映射到不同模型，也可以是同一模型的不同 reasoning effort。
- **Escalation（升级）**：当前路径不满足质量、风险或置信要求时，提升到更强模型、更高推理档位、更多 Evidence 或人工审查。

Reasoning 章已经解释 inference-time compute 为什么会改变能力边界；这里把它放进系统路由。FAST/REASON 是一种策略抽象：

```text
FAST：低延迟、低成本，处理高频、低风险、可验证任务
REASON：更多推理预算，处理冲突、复杂规划、高风险或低置信任务
```

它可以映射为同一模型不同 reasoning effort、不同模型、端侧与云端不同 Provider，或分阶段流程。稳定的是升级条件，不是某个模型名。

合理升级信号包括：

- 输入冲突或缺失；
- FAST 置信不足；
- 高风险、不可逆动作；
- Validator 失败；
- 需要跨来源综合；
- 某 Failure Slice 显示 REASON 有稳定增益。

高风险不等于只把推理开到最大：还可能要求 Approval、只读模式、更多 Evidence 或直接拒绝自动执行。

## Tool Routing：发现、选择与授权

### 本节新词

- **Tool Routing（工具路由）**：从当前允许的能力集合中发现并选择最适合任务的 Tool。
- **Permission Filter（权限过滤）**：在模型参与语义选择前先排除当前身份、Scope 或 Risk 下不允许使用的能力。

沿用 Tool 章已经学过的 Discovery / Selection / Authorization，路由时通常先从 Registry 找到候选，再做任务相关性选择，并在执行前经过授权与策略检查。

模型只适合参与 Selection 的语义部分。Permission filter 必须先限制候选；副作用级别、数据域和用户授权不能由自然语言相似度决定。

## Agent Routing：路由的是责任

### 本节新词

- **Agent Routing（Agent 路由）**：在已经存在多个独立责任主体时，决定当前这段责任应该交给谁；它不是把同一个 Prompt 广播给多个角色。

Agent Routing 不是把同一 Prompt 发给多个角色。它要判断：

- 任务是否需要独立责任边界；
- 候选 Agent 的 Capability、Identity、Permission 和负载；
- 这次只是协作、局部委派，还是会真的改变责任 Owner；
- 原责任主体是否仍要对最终结果负责；
- 共享 State 由谁写，完成 Event 如何回传。

只有在 Multi-Agent 真的存在时才需要这一层；不要为了路由而先制造 Agent。Delegation / Handoff 的正式边界留给下一层协作章节。

## Scheduler：Task 可运行以后，资源怎样分配

### 本节新词

- **Priority Queue（优先队列）**：按优先级安排等待任务的队列；高优先级先执行，但必须避免低优先级永久饿死。
- **Concurrency Limit（并发上限）**：同一时间最多允许多少任务或模型调用并行执行。
- **Admission Control（准入控制）**：在任务进入执行队列前判断当前资源、配额或风险是否允许接受。
- **Backoff（退避）**：失败后逐步延长下一次 Retry 间隔，避免持续轰击故障资源。
- **Resource Lock（资源锁）**：确保同一独占资源不会被多个任务同时占用。

前面的 Runtime / Durable 章节已经用 Scheduler 表达“Event、依赖或时间条件变化后，哪个 WAITING Task 重新变成 runnable”。本章继续的是**资源调度**：Task 已经具备运行条件以后，谁先占用有限模型、设备或并发槽位。

这里主要处理：

- Priority Queue；
- concurrency limit；
- per-model / per-tenant quota；
- admission control；
- deadline 与 fairness；
- resource lock / lease。

Backoff 或定时唤醒仍会影响下一次 runnable 时间，但它们属于 Runtime 恢复链与资源调度的交界，不需要再发明第二种 Scheduler。

Priority 不能只由用户一句“紧急”决定。可组合业务价值、deadline、风险、等待时间、资源需求与公平性，并防止低优先级永久饥饿。

## 单资源互斥与优先队列

### 本节新词

- **Mutual Exclusion（互斥）**：某个资源同一时刻只允许一个任务使用，例如只能一次运行一个模型的端侧设备。
- **Lease（租约）**：任务在有限时间内获得资源使用权；超时未续约时系统可以回收，避免资源永久被“死任务”占住。
- **Aging（老化提升）**：等待时间越长，任务优先级逐渐提高，用来避免低优先级任务长期 Starvation（饥饿）。

当端侧设备一次只能运行一个模型，调度问题不是“开更多并发”，而是互斥资源分配：

```text
incoming jobs
  ↓ classify FAST / REASON
priority queue
  ↓ single worker lease
load / reuse model
  ↓ inference
release / next
```

需要显式处理：模型切换成本、队列等待、取消、租约过期、重复 job、设备离线和结果回传。FAST 优先可以降低整体延迟，但 REASON 任务需要 aging 或保留配额避免饥饿。

## Fallback 不是 Retry，也不是 Escalation

Fallback 已在 Model Gateway 小节定义；Retry / Reconciliation 已在 Durable Execution 章学过，Escalation 刚在 Reasoning Routing 中出现。三者放在一起时，差别在于：Retry 仍尝试同一路径；Fallback 换一条实现路径；Escalation 提高推理、验证、权限审查或人工介入级别。

Timeout 进入 UNKNOWN 后，不应该直接跨 Provider 重做高副作用动作。纯模型推理通常更容易安全重试；真实 Tool Effect 仍要先回读现实状态。

## Policy：把组织选择变成可审计规则

### 本节新词

- **Policy Version（策略版本）**：本次路由使用的具体规则版本。记录版本后，未来才能解释“为什么当时选了这条路”。
- **Decision Record（决策记录）**：保存路由输入、候选、最终选择、Policy Version 和理由的结构化记录。
- **Data Handling Restriction（数据处理限制）**：规定某类数据能否离开设备、进入哪个地区或由哪个 Provider 处理。

Policy 可表达：

```text
allowed models / regions
max cost / latency / retries
required evidence
side-effect risk level
approval threshold
data handling restrictions
fallback order
```

策略结果应记录 `decision inputs + selected route + policy version + reason`。否则成本或质量变化时无法解释系统为何选了某条路径。

## Eval 驱动路由

### 本节新词

- **p50 / p95 Latency（50/95 分位延迟）**：分别表示一半请求和 95% 请求在该时长内完成，用来观察“平均很快但长尾很慢”的问题。
- **Critical Error（关键错误）**：业务上不能接受的严重失败，例如高风险漏判或错误副作用。

路由策略不能只凭“更强模型应该更好”。至少按 slice 比较：

```text
task success
critical error
latency p50/p95
total cost
tool calls / retries
human intervention
recovery quality
```

如果 REASON 没有带来可测增益，就降级；如果 FAST 在某类高风险任务频繁漏错，就收窄适用范围。Routing 是持续评估后的工程 Policy，不是一次 prompt 分类。

## 路由系统容易犯的四类错误

### 只按 Token 数选模型

输入长短不能代表领域、风险、模态和验证难度。

### Router 自己没有 Eval

语义路由模型也会错；没有选择正确率与最终 Outcome 反馈，路由层只是在隐藏失败来源。

### Gateway 变成业务上帝服务

把 Task、Plan、Tool、Agent、Memory 全塞进 Model Gateway，会制造不可替换的控制平面单体。

### FAST 永远优先

没有 aging、公平或 deadline 规则，长推理任务会饿死。

## 先从能解释的最小路由开始

最小系统可以先固定一个模型和一组 Tool。只有出现可测的成本、延迟、质量、合规或资源冲突时才引入 Gateway/Router/Scheduler。每增加一个选择层，都必须同时增加决策记录和 Eval。

## 路由决策怎样接入 Runtime 与 Eval

- Reasoning 章定义单次调用的推理预算；本章把它变成 Runtime Policy；
- Tool 章定义能力合同，本章只负责选择与授权前过滤；
- Multi-Agent 章定义责任主体，本章的 Agent Routing 不重复其组织语义；
- Economics 章判断路由是否真正改善成本、延迟和可靠性；
- 端云协同真实系统章验证 FAST/REASON 与 Priority Queue 的具体落地。

## 检查每次分流是否有依据

1. Model、Reasoning、Tool、Agent Routing 分别选择什么？
2. Scheduler 与 Router 的责任为什么不同？
3. FAST/REASON 为什么不应绑定固定模型名？
4. Timeout 后何时能 Retry，何时必须先 Reconcile？
5. 一个 Router 本身需要哪些 Eval？
