# 检索系统怎样找到正确资料

> 唯一职责：解释面对不同类型的问题，系统怎样选择真正拥有这类事实的查询路径，并在必要时组合多种检索。
> 前一章回答“外部知识怎样进入模型”；本章只追问“这类问题到底应该去哪里查，查到的候选怎样合并成可靠证据”。

## 先判断你问的是哪一种事实

假设有人问：“当前 Runtime 的幂等冲突在哪里处理，什么时候引入，是否有测试？”如果只做一次语义搜索，可能找到一篇讲幂等的设计文档，却回答不了**当前代码在哪、哪个提交引入、哪些测试真的覆盖**。这些问题虽然都围绕同一主题，事实却分布在不同系统。

### 本节新词

- **Retrieval（检索）**：根据问题从资料或系统中找回候选信息的过程。本章把它理解成“向正确事实系统提问”，而不只是一种向量搜索算法。
- **Retriever（检索器）**：针对某一种资料形态执行查询并返回候选的组件，例如面向语义文本、精确词、代码关系、版本历史或结构化数据。Retriever 负责找候选，不负责最终裁决 Truth。
- **Truth Dimension（真值维度）**：本系列用来描述“一个问题究竟在问哪一类事实”的工程概念，例如语义内容、代码结构、版本历史、当前业务状态。它不是行业协议名。
- **Source of Truth（真值源／权威事实源）**：系统对某一 Truth Dimension 最终承认的事实来源。Index 可以帮助查询，但不会因为检索分数高就自动成为 Source of Truth。

先用普通语言识别问题类型：

```text
问“意思相近的资料在哪里”   → 语义检索
问“这个精确名字出现在哪里” → 词法 / 精确检索
问“谁调用了这个函数”       → 代码结构查询
问“什么时候改的”           → 版本历史
问“当前有多少条失败记录”   → 结构化数据库查询
```

真正需要 Hybrid 的时刻，是**一个问题跨越了多个 Truth Dimension**。不是因为“检索技术越多越先进”。

## 为什么 Vector 不够

### 本节新词

- **Vector Search / Dense Retrieval（向量检索／稠密检索）**：把 Query 和资料转换成连续 Vector，再按距离或 Similarity 找语义相近候选，适合“措辞不同但意思接近”的搜索。
- **FAISS — Facebook AI Similarity Search**：用于高效向量相似度搜索的开源库，可承担向量索引和候选召回；它不知道文档版本、权限或业务 Authority。
- **Top-K**：只保留检索分数最高的 K 个候选。它是一种候选截断参数，不保证前 K 个就是当前 Truth。

向量检索擅长同义改写、概念相近、自然语言描述与内容之间的模糊匹配。例如用户问“怎样避免长任务重复执行副作用”，向量检索可能找到标题并不包含这句话、但实际讨论安全重试和故障恢复的文档。

但它有明显盲区：

- 精确 ID、函数名、错误码、版本号可能被语义空间稀释；
- 相似段落可能来自已经过期或低权威文档；
- 它不天然理解 `A imports B`、`commit X introduced Y` 或 `sum(amount)`；
- top-k 相似不等于覆盖了问题所需的多种证据。

因此 Vector 更适合做**语义候选生成器**，而不是唯一查询引擎或最终裁判。

例如在本地知识库里，团队可以用 **FAISS（Facebook AI Similarity Search，向量相似度搜索库）**建立向量索引，快速找出与“恢复后避免二次扣款”语义相近的段落。FAISS 在这里负责相似度搜索和候选召回；它不知道哪份制度仍有效，也不拥有用户权限、文档版本和最终答案。把“用了 FAISS”写进架构，只说明一种索引实现，不能证明系统已经拥有完整 RAG、可靠 Retrieval 或 Source of Truth。

## Keyword / Lexical Retrieval 为什么一直留下来

### 本节新词

- **Keyword / Lexical Retrieval（关键词／词法检索）**：按文字本身、稀有词、标识符和词频统计寻找候选，适合函数名、错误码、配置键、版本号等精确线索。
- **Inverted Index（倒排索引）**：从“词 → 出现在哪些文档/位置”组织索引的经典结构，是很多全文检索系统的基础。它和 Vector Index 保存的表示方式不同。
- **BM25**：一种经典词法相关性排序方法，会结合词在当前文档和整个语料中的出现情况以及文档长度估计相关性；它不是 Embedding 方法。
- **Regular Expression / Regex（正则表达式）**：按字符模式匹配精确文本的规则语言，适合格式明确的 ID、版本和代码模式，不承担语义理解。

倒排索引、BM25、正则和精确搜索在以下问题上通常更可靠：

- `LOCAL_WORK_IDEMPOTENCY_CONFLICT` 出现在哪里；
- `ControllerClaim` 的定义和引用；
- 某个文件名、命令、配置键或稳定 ID；
- 包含两个必须共现术语的段落；
- 稀有专有名词、版本号和哈希。

它的弱点是词面不一致：用户说“恢复后避免二次写入”，原文可能只写“同一操作可安全重复提交”，纯 Keyword 就可能漏掉。因此常见做法是 Keyword 保精确性，Vector 补语义召回。

## CodeGraph：代码问题常常是关系问题

### 本节新词

- **CodeGraph（代码关系图）**：把 Symbol、调用、导入、实现、模块依赖等代码结构关系组织成可查询图的索引形态，适合回答“谁调用谁、改动会影响哪里”。它是派生结构，不替代源码本身。
- **AST — Abstract Syntax Tree（抽象语法树）**：Parser 把源代码转换成的语法结构树，可帮助识别函数、类、表达式和依赖，是构建 CodeGraph 的一种输入。
- **Language Server（语言服务器）**：为编辑器或工具提供符号、定义、引用、诊断等语言级能力的进程/协议实现，可作为代码关系信息来源之一。
- **Static Analysis（静态分析）**：不实际运行程序，通过源码和构建信息推断类型、调用、数据流或依赖的方法。动态调用和运行时配置可能超出它的可见范围。
- **Symbol（符号）**：代码里可被命名和引用的函数、类、变量、方法等实体。Symbol Search 与自然语言语义检索解决的是不同问题。

代码仓库不是普通文章集合。很多问题问的不是“哪段文字最相似”，而是：

```text
symbol definition
  → callers
  → imports
  → implementations
  → tests
  → configuration
  → runtime boundary
```

这类关系图可以由 AST、语言服务器、静态分析或构建信息生成，适合回答：

- 一个接口有哪些实现；
- 某个 schema 的生产者和消费者；
- 修改一个类型会影响哪些调用链；
- 哪些测试真正覆盖了某条执行路径。

但 CodeGraph 也不是代码真值本身。解析器可能不理解动态调用、生成代码、反射或运行时配置；最终仍要回读源码、测试和真实运行证据。

## Git：版本事实不能靠向量猜

### 本节新词

- **Git**：记录文件版本、提交关系和分支历史的分布式版本控制系统。本章把它当作“版本变化事实”的主要来源，而不是全文搜索工具。
- **Commit（提交）与 SHA**：Commit 是一次被 Git 固定保存的版本变化；SHA 是用于标识 Git 对象的哈希值，常用来精确指向某个 Commit。
- **HEAD**：当前 Git 工作位置所指向的提交/分支引用，回答“当前基线是哪一个版本”；它不包含尚未提交的本地修改。
- **Branch（分支）与 Tag（标签）**：Branch 是会随新 Commit 移动的开发引用，Tag 通常固定指向某个版本点。二者都用于定位版本，但生命周期不同。
- **Diff（差异）**：比较两个版本或工作状态之间实际文本变化的结果，适合回答“到底改了什么”。
- **Blame（逐行归属）**：把当前文件行追溯到最近修改它的 Commit 的 Git 视图，适合定位线索；它不能单独证明设计意图或完整责任。
- **Worktree（工作树）**：某个 Git 基线在本地展开后供编辑的文件状态；它可以包含尚未提交变化。Git 也支持多个独立 worktree 并行关联同一仓库。
- **WIP — Work in Progress（进行中的工作）**：尚未完成或尚未正式提交/验收的本地变化。检索当前仓库时必须区分 HEAD 事实和 WIP，否则容易把旧提交与当前磁盘状态混在一起。

当问题带有“当前”“何时”“谁改的”“从哪个版本开始”“这个判断是否已被替代”时，Git 是独立的 Truth Dimension：

- `log` 回答提交顺序与变更边界；
- `diff` 回答两个状态之间真实改变了什么；
- `blame` 提供一条定位线索，但不能独自证明设计意图；
- tag / branch / commit 固定可复现基线；
- worktree status 区分已提交事实与本地未验证 WIP。

把仓库全文做 Embedding 后，仍然回答不了“这段代码是否属于当前 HEAD”。没有版本约束的代码检索，很容易把旧实现和新实现混成一个看似合理的答案。

## SQL 与结构化 API：聚合问题应交给确定性系统

### 本节新词

- **SQL — Structured Query Language（结构化查询语言）**：用于对关系型数据库进行筛选、连接、聚合和更新的查询语言，适合边界明确的结构化事实。
- **Structured API（结构化 API）**：用固定字段和参数查询领域系统的程序接口，例如按状态、时间、用户读取业务记录。它提供确定性数据合同，不等于自然语言 RAG。
- **Join（连接）**：按字段关系把多张表的记录组合起来的数据库操作。
- **Aggregate（聚合）**：对记录执行计数、求和、平均、分组等确定性计算，不应让 LLM 从文档片段“估算”。
- **Parameterized Query（参数化查询）**：把用户输入作为独立参数传给 SQL，而不是直接拼接进查询字符串，降低注入风险并保持查询结构可控。
- **Row-level Access Control（行级访问控制）**：根据用户/角色限制数据库哪些记录可以被访问的权限机制，属于数据执行层，不应由模型自由判断。

以下问题不应该先让 LLM 在文档片段里估算：

- 最近 30 天失败任务数；
- 按模型、错误类型、版本分组的成功率；
- 一个 task 的当前 state 与 version；
- 满足权限、地区、价格和库存条件的记录；
- JD corpus 中某能力出现的频率。

SQL、搜索过滤器和领域 API 能表达明确约束、Join 与 Aggregate。模型可以负责生成查询计划或解释结果，但权限检查、参数化查询、行级访问控制和结果校验仍属于确定性执行层。

## Query Planning：先判断问题，再选 Retriever

### 本节新词

- **Query Planning（查询规划）**：先把一个复杂问题拆成需要哪些事实、约束和来源，再安排一个或多个 Retriever 的查询顺序。它是在检索前做路线设计，不是直接生成答案。
- **Query Intent（查询意图）**：当前问题要找解释、实体、关系、版本事实还是统计事实等检索目标。
- **Constraint（约束）**：查询必须满足的精确条件，例如 branch、时间范围、状态、客户、版本。
- **Retrieval Budget（检索预算）**：允许调用多少后端、耗费多少延迟、读取多少候选的资源边界，防止动态检索无限扩张。
- **Stop Rule（停止规则）**：明确“证据达到什么条件就不再继续检索”的规则；它比单纯设置最大轮数更接近完成标准。

一个可用的 Query Plan 至少包含：

```text
intent        要找解释、实体、关系、版本事实还是统计事实
entities      涉及哪些文件、符号、任务、岗位或时间范围
constraints   必须满足什么精确条件
sources       哪些系统对这类事实有权威性
budget        允许多少后端、延迟和结果量
stop rule     什么时候证据已经足够
```

示例：

> “当前 Runtime 的幂等冲突在哪里处理，什么时候引入，是否有测试？”

合理计划不是一个 Vector query，而是：

1. Keyword 找精确错误码和防重复操作键；
2. CodeGraph 找 handler、domain service 与 tests 的依赖；
3. Git 查引入提交与当前 HEAD 差异；
4. 回读源码和测试；
5. 把结论绑定到文件、行、commit 和测试证据。

## Candidate Fusion：不同分数不能直接相加

### 本节新词

- **Candidate Fusion（候选融合）**：把多个 Retriever 返回的候选去重、合并并形成统一排序的过程。不同后端的原始分数通常没有共同量纲。
- **Reciprocal Rank Fusion / RRF（倒数排名融合）**：基于候选在各检索结果中的名次而不是原始分数进行融合的方法，避免假设 Vector/BM25 等分数可直接相加。
- **Rule-based Boost（规则加权）**：对精确 ID、当前分支、正式状态等具有明确业务意义的候选按规则提高优先级。
- **Learned Reranker（学习型重排器）**：用训练得到的模型重新判断 Query 与候选的相关性；它优化 relevance，不自动拥有 Authority。
- **Diversity Constraint（多样性约束）**：避免 Top-K 被同一内容的近重复版本占满，让证据集合覆盖更多互补信息。

Vector similarity、BM25、graph distance、Git recency、SQL rows 没有天然统一量纲。常见合并策略包括：

- Reciprocal Rank Fusion：合并多个排序而不假设分数同尺度；
- rule-based boost：精确 ID、当前分支、正式状态获得额外权重；
- learned reranker：对候选与问题做更精细相关性判断；
- diversity constraint：避免 top-k 全是同一段话的近重复；
- authority/freshness filter：先过滤无权威或过期候选，再做语义排序。

Reranker 仍然只解决“对问题是否相关”。它不能替代权限、来源优先级和真值冲突处理。

## Authority、Freshness 与 Conflict

上一章已经定义 **Authority（权威性）** 与 **Freshness（时效性）**。这里不重复定义，只补它们在多来源冲突里的新责任。

### 本节新词

- **Conflict（冲突）**：两个或多个候选对同一事实给出不能同时成立的结论。系统应保留冲突并按 Authority、版本和 Evidence 裁决，而不是让 LLM 按语气“综合”。
- **Provenance（来源链／溯源信息）**：记录候选来自哪个 Source、版本、位置以及经过哪些转换，让结论可以回到原始证据。
- **`supersedes / superseded_by`（替代／被替代关系）**：显式记录新旧资料的版本继承关系，帮助系统排除已被新版本正式取代的内容。

真实知识系统必须能表达：

```text
source_id
source_type
version / commit / valid_at
authority
access_scope
supersedes / superseded_by
provenance
```

当两份资料冲突时，不要让 LLM 按语气或相似度投票。应先应用项目的事实优先级，例如：

```text
当前代码、测试、真实调用证据
  > 当前受治理状态
  > 已接受设计
  > 普通文档
  > 历史建议
```

如果仍无法裁决，输出 Conflict 和需要补充的 Evidence，而不是合成一个不存在的“平均事实”。

## 何时并行，何时串行

### 本节新词

- **Parallel Retrieval（并行检索）**：多个互不依赖 Retriever 同时查询，以缩短总等待或提高召回；它会增加资源消耗和候选融合成本。
- **Sequential Retrieval（串行检索）**：前一步结果缩小或决定下一步查询，例如先找到 Symbol，再扩展调用关系和版本历史。
- **Agentic Retrieval（智能体式动态检索）**：系统依据已有 Evidence 动态选择下一次 Retriever / Query 的方式；它仍必须受来源、预算、Permission 和 Stop Rule 约束。

并行适合：多个后端互不依赖、延迟预算允许、需要提高召回。串行适合：前一步结果决定下一步范围，例如先用 Keyword 找 symbol，再用 CodeGraph 扩展调用者，最后用 Git 限定版本。

```text
高召回探索：Vector || Keyword
精确代码调查：Keyword → CodeGraph → Source read → Test
版本问题：Git filter → Source retrieval
统计问题：SQL → anomaly slice → supporting documents
```

不要把“Agentic Retrieval”理解为无界搜索。动态选择 Retriever 仍应受来源白名单、查询预算、权限、停止条件和 Evidence 要求约束。

## 检索组合最常见的四种误判

### 失败 1：所有资料都切 Chunk 丢进一个向量库

结果是版本、权限、文档类型与结构关系消失。相似答案变多，但可追踪真值变少。

### 失败 2：Hybrid 等于 Vector + Keyword 固定并行

对于 SQL 聚合、Git 当前状态或代码依赖问题，这两个 Retriever 都不是正确主角，只会增加延迟和噪声。

### 失败 3：让 LLM 自己判断哪个来源“更可信”

没有显式 Authority 和 Freshness metadata 时，模型往往偏向措辞完整的文档，而不是当前代码事实。

### 失败 4：检索到了，就宣称问题已回答

#### 本节新词

- **Observation（观察结果）**：某次 Tool/Retriever 调用返回的原始或结构化结果，表示“系统看到了什么”。Observation 还需要版本、来源和验证，才能升级为支持结论的 Evidence。

Retrieval result 是候选 Observation。只有经过来源回读、版本确认、冲突检查和必要验证后，才可能成为 Evidence。

## 从最小可靠检索路径开始

### 本节新词

- **ADR — Architecture Decision Record（架构决策记录）**：记录重要架构选择、背景、方案和理由的版本化文档，适合解释“为什么这样设计”，但当前实现事实仍应回到代码和运行证据。
- **Evidence Gate（证据门禁）**：在复杂跨来源调查中规定“哪些来源/验证条件满足后才能接受结论”的工程规则，不是某个标准产品名。

| 问题特征 | 首选 | 常见补充 |
|---|---|---|
| 模糊描述、同义表达 | Vector | Keyword、Reranker |
| 精确 ID、错误码、配置键 | Keyword | Git、源码回读 |
| 符号、依赖、调用链 | CodeGraph | Keyword、测试 |
| 当前版本、历史变更 | Git | 源码、ADR |
| 聚合、过滤、Join | SQL / structured API | 文档解释 |
| 跨来源复杂调查 | Query planner | 多 Retriever + Evidence gate |

最小可靠原则是：**能用一个确定性来源回答，就不要先造一个通用 Agentic RAG；只有问题真的跨多种 Truth Dimension，才升级 Hybrid orchestration。**

## 这些检索责任交给谁继续展开

- 前一章给出 RAG 管线：本章把其中的 Retrieval 深挖成多真值查询系统；
- 下一章把“知道什么”推进到“能做什么”：检索结果不会自动获得 Tool 权限；
- 后面的 Runtime 负责保存 Task State 和 Evidence，不应把向量索引当作 State Store；
- Deep Research 会动态调用这些检索能力，但研究路线、证据冲突和停止条件属于研究 Agent 的责任。

## 用这些问题验收混合检索设计

1. 为什么 Vector similarity 不能决定哪份资料是当前真值？
2. 一个代码问题什么时候应该用 CodeGraph，什么时候必须回到 Git 和源码？
3. SQL 查询为什么不应被包装成“RAG 的一种高级形态”？
4. Hybrid Retrieval 的“Hybrid”到底发生在候选生成、排序、真值判定还是全部？
5. 如果两个来源冲突，系统应该合并、投票，还是保留冲突并补证据？
