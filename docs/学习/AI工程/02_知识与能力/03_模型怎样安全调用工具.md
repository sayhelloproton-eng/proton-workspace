# 模型怎样安全调用工具

> 唯一职责：解释模型怎样把自然语言判断变成可由软件检查和执行的外部动作，同时守住“提出动作、真正执行、业务生效”之间的边界。
> 读完要能回答：用户说“把订单退掉”以后，模型、运行层、外部系统分别做什么，系统怎样知道动作到底有没有成功？
> 阅读前最好先理解对话助手和结构化消息。本章只处理动作合同、执行结果和能力治理；高风险审批、长任务恢复和最终真值提交留到后续 Runtime 章节。

<a id="ch07-30s-core"></a>
<a id="ch07-3m-mental-model"></a>
## 用户说“退款”，模型并不会直接把钱退回去

用户说“把刚才那笔订单退掉”。模型可以理解这句话，也可以生成一份机器能读懂的退款请求；但钱是否真的退回，还取决于软件是否允许这次动作、调用了哪个外部系统、外部系统返回什么，以及系统最终能不能确认真实状态已经改变。

### 本节新词

- **Tool（工具）**：模型或 Agent 可以请求使用的外部能力，例如查询订单、创建工单、运行测试或发送消息。Tool 是面向任务的动作抽象，不等于底层 API 本身。
- **Runtime（运行时）**：模型之外真正接收 Tool 请求、检查规则、执行软件调用并处理结果的运行层。模型可以提出调用，Runtime 才是现实执行链中的软件责任主体。
- **Effect（副作用／外部效果）**：一次动作对外部世界造成的真实状态变化，例如付款、退款、写文件、发邮件。生成“我要退款”的结构不是 Effect。
- **Tool Call Intent（工具调用意图）**：模型表达“希望调用哪个 Tool、用什么参数”的结构化提议。它是 Decision 的输出，不是执行完成证明。

先把最重要的执行边界固定下来：

```text
用户意图
→ 模型提出 Tool Call
→ Runtime 检查并执行
→ 外部系统产生或没有产生 Effect
→ 返回可验证结果
```

后面的 Structured Outputs、Function Calling、Tool Contract，以及防止重复副作用的执行合同，都会继续让这条链更可解析、更安全、更容易判断失败发生在哪一层。

## 一次 Tool 调用穿过了哪些边界

<a id="ch07-structured-output"></a>
### 3.1 Structured Outputs：结构正确不是语义正确

#### 本节新词

- **Structured Outputs（结构化输出）**：要求模型的响应符合预先声明的数据结构，让程序能够按固定字段读取，而不是解析自由文本。它解决“结构能不能稳定解析”，不证明业务语义正确。
- **Schema（模式／数据结构合同）**：描述对象有哪些字段、类型、必填项、枚举等约束的机器可读规则。Schema 是结构合同，不是权限和业务规则的总和。
- **JSON — JavaScript Object Notation**：常见的结构化数据文本格式，用对象、数组、字符串、数字等表示数据；合法 JSON 仍可能不符合业务 Schema。
- **Enum（枚举）**：把字段值限制在有限允许集合中的 Schema 约束，例如 `status` 只能是 `pending / paid / refunded`。
- **Schema Validation（模式校验）**：检查输出字段、类型和结构是否符合 Schema。它不能证明收件人是否正确、金额是否允许或动作是否成功。

例如，软件可以要求模型只返回下面这类可解析结构：

```json
{
  "action": "send_email",
  "recipient": "...",
  "subject": "..."
}
```

模式校验只能证明：

- 字段存在；
- 类型正确；
- enum 合法；
- 结构可解析。

但它不能自动证明：

- recipient 真的是应该发送的人；
- subject 符合业务政策；
- 当前用户有权限发送；
- 这次动作不会重复执行。

因此：**Schema valid ≠ semantic correct ≠ authorized ≠ successful.**

<a id="ch07-function-calling"></a>
### 3.2 Function Calling：模型表达调用意图

#### 本节新词

- **Function Calling / Tool Calling（函数调用／工具调用）**：模型根据可用 Tool 定义，返回“调用哪个能力、参数是什么”的特殊结构输出。应用收到后仍必须自己执行对应代码并把结果返回给模型。
- **Call Intent（调用意图）**：Function Calling 产生的动作提议，通常包含 Tool 名称和 Arguments。它可以被 Runtime 拒绝、修改路线或要求审批。
- **Arguments（参数）**：调用 Tool 时传入的结构化输入，例如订单 ID、金额和原因；参数结构合法不等于值在业务上允许。

一次调用意图可以压成两个问题：

```text
我想调用哪个 Tool？
参数是什么？
```

它通常产生类似：

```text
tool_name = "create_ticket"
arguments = {...}
```

这只是 **Call Intent（调用意图）**。模型本身不是 operating system，也不是数据库驱动，它不会因为生成了函数名就自动产生现实副作用。

<a id="ch07-tool-definition"></a>
### 3.3 Tool：面向模型的外部动作能力

#### 本节新词

- **API — Application Programming Interface（应用程序接口）**：软件之间按约定请求和返回数据的程序接口。Tool 可以由 API 实现，但一个底层 API 不一定适合直接暴露给模型。
- **HTTP — Hypertext Transfer Protocol（超文本传输协议）**：Web API 常使用的请求/响应协议。它描述请求怎样在网络上传输，不定义业务 Tool 责任。
- **HTTPS — HTTP Secure（安全 HTTP）**：在 HTTP 传输上加入 TLS 加密保护的形式，用来保护链路中的数据；传输安全不等于调用者自动拥有业务权限。
- **RPC — Remote Procedure Call（远程过程调用）**：让程序像调用本地函数一样请求远端服务执行过程的一类通信抽象。Function Calling 可以类比“产生 RPC 风格请求”，但模型并没有因此亲自执行远端过程。
- **Shell Command（Shell 命令）**：由命令行解释器执行的系统命令，可以被 Tool 包装后供 Runtime 使用；高权限 Shell Tool 需要比普通查询 Tool 更严格的 Permission。

**Tool（工具）**是 Runtime 可以暴露给模型、并由软件真实执行的结构化外部能力。

Tool 可以由：

```text
Local function
HTTP API
Shell command
Browser automation
Database operation
MCP Tool
internal service
```

实现。

所以：

```text
API
= implementation interface

Tool
= model-facing action abstraction
```

如果熟悉分布式系统，可以把几层责任暂时类比为：Structured Outputs 像 Type / Interface / Schema，Function Calling 像一次 **RPC（Remote Procedure Call，远程过程调用）**的调用表达，Tool 像可被调用的 Capability / Service，Runtime 像 Executor + Policy Layer。这个类比只帮助定位责任：模型生成了 RPC 风格的请求，并不代表远端已经执行，更不代表权限、幂等和业务结果已经成立。

一个万能 API 直接暴露给模型并不会自动变成“好 Tool”。

<a id="ch07-logical-physical-executor"></a>
### 3.4 Logical Caller ≠ Physical Executor

#### 本节新词

- **Logical Caller（逻辑调用者）**：在决策语义上提出“应该调用这个能力”的主体，本章通常是 Model。
- **Physical Executor（物理执行者）**：真正运行代码、发送请求或改变外部状态的软件主体，通常是 Runtime / Application / External System。把这两个角色分开，才能在执行前插入权限和验证。

```text
Model
→ proposes call

Runtime / application
→ validates / gates / executes

Tool / system
→ produces real effect
```

因此可以说：

> **Model 是 Logical Caller（逻辑调用者），Runtime 是 Physical Executor（物理执行者）。**

Runtime/Task 章会解释 Runtime 与 Task，Durable Execution 章再处理 Permission 与 Truth Commit。

<a id="ch07-tool-schema"></a>
### 3.5 Tool Schema / Description 是 Tool Selection 的输入

#### 本节新词

- **Tool Schema（工具模式）**：描述 Tool 输入参数结构的 Schema，使模型和 Runtime 对“参数长什么样”形成共同合同。
- **Tool Description（工具描述）**：用自然语言解释 Tool 做什么、什么时候适用、关键限制是什么，是模型选择 Tool 的重要语义输入。
- **Tool Selection（工具选择）**：在多个候选能力中决定当前调用哪一个 Tool；它和“这个调用是否被授权”是两层判断。
- **Selection Error（选择错误）**：模型选择了错误但结构合法的 Tool，例如把“查询退款状态”误选成“创建退款”。增加更多相似 Tool 可能提高这类错误。

模型通常根据 Tool name、description、input schema、examples 等信息判断“哪个 Tool 更合适”。

如果几十个 Tool 描述高度重叠：

```text
search_data
find_data
query_data
lookup_data
```

模型 Selection Error（选择错误）会明显增加。

### 3.5A Toolformer：训练模型使用工具，不等于建立 Runtime 合同

#### 本节新词

- **Toolformer**：Meta 研究提出的一种训练方法，让语言模型通过少量 API 示例、自监督筛选调用位置，学习什么时候调用工具、如何生成参数并利用结果。它解释“Tool Use 可以被训练”，不提供生产 Runtime、权限或恢复机制。
- **Tool-use Policy（工具使用策略）**：模型层学到的“什么时候、用哪个工具、怎样调用”的行为倾向。它是概率行为，不等于 Runtime 的硬 Authorization Policy。

Toolformer 的历史价值，是把 Tool Use 从“Prompt 里手写几个调用例子”推进成一种可训练能力。它只需要每个 API 的少量示例，然后在普通文本中采样候选调用、真实执行 API，并比较工具结果是否改善后续 Token 预测；有帮助的调用被保留下来，形成带 API 调用的训练语料。

它希望模型学会四件事：

- 什么时候需要外部工具；
- 选择哪个 API；
- 怎样生成参数；
- 怎样把结果继续用于后续生成。

但 Toolformer 与现代 Function Calling 不在同一层：

| Toolformer 关注 | Function Calling / Runtime 关注 |
|---|---|
| 训练或适配模型的 Tool-use policy | 用 Schema 表达一次可解析调用意图 |
| API 调用是否改善语言建模结果 | 本次调用是否被允许、执行并验证 |
| 模型学习何时、怎样插入调用 | 软件承担授权、物理执行和副作用 |
| 把结果并回后续 Token 预测 | 返回 Result / Evidence / Error Contract |

因此，模型“学会用工具”不会自动提供权限、审批、防重复副作用、恢复或真值提交。Toolformer 解释了 Tool Use 为什么可以成为模型能力；Function Calling 和 Runtime 才把这种能力接进可治理的软件系统。

事实来源：[Meta AI Research｜Toolformer](https://ai.meta.com/research/publications/toolformer-language-models-can-teach-themselves-to-use-tools/)。

所以 Tool Schema 不是只给程序看的类型声明，它也是模型判断“该不该选这个 Tool、参数该怎样填”的语义界面。

<a id="ch07-tool-contract"></a>
### 3.6 Tool Contract：Tool 不应只是“函数签名”

#### 本节新词

- **Tool Contract（工具合同）**：除了输入输出 Schema，还描述能力语义、副作用、风险、失败类型、版本和重复调用语义的完整调用约定。
- **Side Effect（副作用）**：调用后会改变外部状态的效果，例如写数据库、发邮件、删除文件；只读查询通常副作用更低。
- **Reversibility（可逆性）**：动作发生后能否可靠撤销或补偿。不可逆动作通常需要更高审批和证据门槛。
- **Failure Class（失败类别）**：按后续处理方式对失败分类，而不是把所有错误都压成同一个 `ERROR`。后面 Failure Contract 会展开。

好的 **Tool Contract（工具合同）**至少描述：

- semantic purpose；
- input schema；
- output/result schema；
- side effect；
- reversibility；
- risk；
- failure classes；
- 重复提交与安全重试语义；
- identity / version key（如适用）。

这比把一个底层万能 API 改个名字更重要。

<a id="ch07-capability-contract"></a>
### 3.7 Capability Contract：把底层实现隐藏在业务能力后面

#### 本节新词

- **Capability（能力）**：平台从任务视角表达“系统能完成什么”的高层责任，例如 Search Repository，而不是暴露 Qdrant、SQL 之类底层实现细节。
- **Capability Contract（能力合同）**：描述一项 Capability 的输入、输出、边界和可用方式，使上层不依赖具体实现。一个 Capability 可以由一个或多个 Tool 组合完成。
- **Permission（权限）**：当前身份、状态和策略下是否允许执行某项能力。Capability 回答“会不会”，Permission 回答“这一次允不允许”。

因此平台对上层暴露的最好是任务能力，而不是底层实现名。例如：

```text
Search Repository
Create Deployment
Send Customer Message
Analyze Document
```

一个 Capability 可以由一个 Tool 实现，也可以内部组合 DB / Search / CodeGraph / API。

稳定边界：

```text
Capability
= 会不会 / 能提供什么

Permission
= 这一次允不允许
```

Permission 的完整机制留到 Durable Execution 章解释。

项目里最容易踩的坑，是把 backend implementation 直接当 Capability 暴露。以本知识库里的 Local Retrieval Runtime 为例，上层更应该看到 `search_project_knowledge(...)` 这种稳定能力合同，而不是知道内部到底用了 Vector DB、CodeGraph、Git 还是 SQL；完整项目推演见 [Custom GPT + Local Retrieval Runtime](../08_真实系统与岗位/02_云端Agent怎样访问本地知识.md)。

<a id="ch07-schema-semantic-validation"></a>
### 3.8 Schema Validation ≠ Semantic Validation

#### 本节新词

- **Semantic Validation（语义校验）**：在结构合法之后检查值是否符合业务含义，例如金额是否在限额内、recipient 是否有效、状态是否允许。它和 Schema Validation 的“类型/字段正确”不是同一层。
- **ISO 4217**：国际标准中的货币代码体系，例如 `CNY` 表示人民币。一个值符合 ISO 代码仍不代表当前业务账户允许该币种交易。

假设 Tool schema 规定：

```json
{"amount": 1000, "currency": "CNY"}
```

这里的 `CNY` 是人民币的 ISO 4217 货币代码。它格式正确，只说明字段能被解析，并不说明这笔交易在业务上允许执行。

结构完全合法，但业务上可能：

- amount 超过限额；
- currency 不被当前账户支持；
- recipient 状态失效；
- transaction 已经执行过。

所以结构化合同只是可靠边界的第一层。后续语义验证、权限检查、证据绑定和事后状态对账分别属于更高层治理。

<a id="ch07-failure-contract"></a>
### 3.9 Failure Contract：失败不是统一异常

#### 本节新词

- **Failure Contract（失败合同）**：明确 Tool 可能返回哪些失败类别，以及每一类允许怎样重试、修复、升级或停止的约定。
- **Argument Error（参数错误）**：Tool 选对了，但输入字段缺失、格式或语义不合法，需要修参数而不是换能力。
- **Environment Failure（环境失败）**：网络、依赖服务、文件系统等执行环境导致的失败。
- **Transient / Permanent Failure（暂时性／永久性失败）**：前者可能稍后恢复，后者在输入和环境不变时通常不会自行恢复，决定“是否值得再次尝试”。
- **Unknown Effect（效果未知）**：请求结果不明确，系统不知道外部 Effect 是否已经发生，例如付款接口超时。此时不能把“没收到成功”直接当“没有执行”。

Tool failure 至少可以按工程动作分为：

| Failure | 含义 | 常见下一步 |
|---|---|---|
| Selection Error | 选错 Tool | 重新选能力 |
| Argument Error | 参数错误 | 修参数 |
| Environment Failure | 网络/依赖/环境失败 | 判断 transient/permanent |
| Result Interpretation Error | 执行了，但结果理解错 | 验证/重新解释 |

进一步对执行错误分类：

```text
Transient
Permanent
Action Required
Alternative Available
Unknown Effect
```

分类的目的不是“让 Tool 更聪明”，而是给 Durable Execution 章 Recovery 提供确定输入。

<a id="ch07-idempotency"></a>
### 3.10 Idempotency primitive：重复执行不产生额外副作用

#### 本节新词

- **Idempotency（幂等性）**：对同一个 logical operation 重复提交时，不产生额外重复业务副作用，或由服务端识别为同一个操作。它是一种动作合同，不是重试策略。
- **Idempotency Key / Operation ID（幂等键／操作标识）**：用于让服务端识别“这次请求和上次是同一逻辑动作”的稳定标识。
- **Retry（重试）**：执行失败或结果不足时再次发起操作的恢复动作。只有合同允许、Effect 已知或具备幂等保护时才可能安全。
- **Reconciliation（对账／状态核对）**：当 Effect 未知时，主动查询外部系统真实状态，先确认刚才发生了什么，再决定是否重试或恢复。

这里先只看幂等性怎样落到工具合同；长任务恢复时怎样利用它安全重放，留到 Durable Execution 章。

实现上需要让服务端能够识别“这还是同一个 logical operation”，例如：

```text
create_payment(operation_id=abc)
```

如果第一次请求超时，客户端再用同一个 operation_id 调用，服务端能够识别它不是第二笔新付款。

必须保持边界：

```text
Idempotency
≠ Retry

Idempotency
= 让某些 Retry 更安全的动作合同
```

即便 Tool 声称幂等，`UNKNOWN Effect` 场景仍应先做 Reconciliation（对账），回读现实状态；完整 Recovery Policy 属于 Durable Execution 章。

<a id="ch07-result-evidence"></a>
### 3.11 Tool Result：尽量返回 Result + Evidence

#### 本节新词

- **Tool Result（工具结果）**：Tool 执行后返回给 Runtime / Model 的数据，描述本次调用观察到了什么。它不是自动成立的业务 Truth。
- **Tool Result Contract（工具结果合同）**：约定 Result 至少应包含哪些状态、资源标识、版本和 Evidence，使上层能够验证而不是只接收一句 `SUCCEEDED`。
- **Resource ID / Version（资源标识／版本）**：指向被创建或修改对象及其具体版本的稳定字段，帮助后续查询和验证同一个 Effect。
- **Observable State（可观察状态）**：能够从外部系统再次读取并核对的当前状态，是把 Tool Result 变成可靠 Evidence 的重要基础。

只返回：

```text
SUCCEEDED
```

通常不足以支撑可靠系统。

更好的结果合同可以包含：

```text
Result
+ operation_id
+ resource_id / version
+ observable state
+ evidence reference
```

这里先把 **Tool Result Contract** 说清楚；Evidence 怎样验证、怎样绑定 Artifact Version、怎样 Commit 为 Truth，留到 Durable Execution 章。

<a id="ch07-tool-explosion"></a>
### 3.12 Tool Explosion：把所有 Schema 塞给模型会变差

#### 本节新词

- **Tool Explosion（工具膨胀）**：可用 Tool 数量不断增加后，Schema 占用 Context、描述重叠、选择错误和权限面同时扩大的系统问题。
- **Dynamic Loading（动态加载）**：只把当前 Task 真正需要的一小组 Tool Schema 加入模型 Context，而不是永久暴露全部能力。

几百个 Tool 同时进入 Context 会带来：

- Context 膨胀；
- 描述重叠；
- selection error；
- token / latency cost；
- 权限面扩大。

解决办法不是“再写更长 Prompt”，而是维护可查询的能力目录，按当前任务发现候选，只把真正需要的能力动态加载进 Context。

<a id="ch07-registry-discovery-selection"></a>
### 3.13 Registry ≠ Discovery ≠ Selection

#### 本节新词

- **Registry（注册表）**：维护平台拥有哪些 Capability / Tool 及其元数据的目录，回答“系统有什么”。
- **Discovery（发现）**：根据当前任务、域和约束找出可能相关的一组能力，回答“这次有哪些候选”。
- **Selection（选择）**：在已经发现的候选中决定当前真正使用哪个，回答“现在用哪一个”。

```text
Capability Registry
= 平台拥有什么？

Discovery / Retrieval
= 当前 Task 可能需要什么？

Selection
= 现在具体调用哪个？
```

它们可以由同一个进程实现，但职责不能混。

<a id="ch07-capability-registry"></a>
### 3.14 Capability Registry 管什么

#### 本节新词

- **Provider（提供方）**：实现或提供某项 Capability 的服务、模块或外部系统。多个 Provider 可以实现同一高层能力。
- **Capability Registry（能力注册表）**：以 Capability 为中心维护 Provider、domain、version、schema、health、risk、side-effect、permission metadata 和 lifecycle 等治理信息。它描述能力，不替代当前 Task 的授权判断。
- **Health（健康状态）**：能力当前是否可连接、可执行、性能是否正常的运行状态，不等于业务调用结果一定正确。
- **Lifecycle / Availability（生命周期／可用性）**：能力是否处于 active、deprecated、disabled 等阶段及当前能否被使用。

一个成熟的 **Capability Registry（能力注册表）**不只存 Tool name，还可能维护：

- provider；
- domain；
- version；
- schema；
- health；
- risk；
- side-effect metadata；
- permission metadata；
- lifecycle / availability。

注意 permission metadata 只是“能力需要什么权限”的描述；当前 Task 是否被允许仍由 Durable Execution 章 控制。

<a id="ch07-tool-retrieval"></a>
### 3.15 Tool Retrieval / Dynamic Loading

#### 本节新词

- **Tool Retrieval（工具检索）**：根据当前 Task 从 Capability Registry 中检索少量相关 Tool 候选，再把这些 Schema 装入模型 Context。它检索的是“可做什么”，不是知识 Evidence。
- **Availability Filter（可用性过滤）**：在 Tool 暴露给模型前按健康、版本、环境等条件排除当前不可用能力。

当能力很多时，可以：

```text
Task / Context
↓
Capability search / rules
↓
small candidate set
↓
permission / availability filters
↓
load only relevant Tool schemas
↓
Model selects
```

这和 RAG 的“先检索候选，再装入 Context”在工程形态上很像，但检索对象从知识 Chunk 变成 Capability metadata。

<a id="ch07-selection-authorization"></a>
### 3.16 Tool 被选中，不等于已经获准执行

模型选中某个 Tool，只说明它提出了一个动作候选。执行前还要结合身份、资源、当前状态和策略做允许性判断。后面的 Durable Execution 章会正式展开 Authorization / Permission / Policy；这里先守住 Tool 的边界：**selection 不是 authorization。**

```text
Model proposes a Tool
↓
Runtime / Policy checks whether it may run
↓
Physical executor performs the effect
```

<a id="ch07-namespaces"></a>
### 3.17 Tool 章到哪里结束

Tool 章负责动作合同：模型怎样表达调用意图、动作能力怎样描述、失败和结果怎样返回、重复执行怎样避免额外副作用。

再往外会进入别的责任层：下一章讨论外部能力怎样通过协议和接入层被多个 AI Host 使用；Agent 章节讨论可复用工作方法以及谁控制下一步。这里不提前给 Connector、Plugin、Skill、MCP 再做一套定义，只保留一个判断：**它们都不是 Tool 的同义词。**

<a id="ch07-tool-workflow-agent"></a>
### 3.18 会用 Tool，不等于系统已经是 Agent

一个脚本连续调用十个 Tool，控制路径仍然可以由程序预先写死；一个 Agent 也可能只拥有两三个 Tool。Tool 回答“能做什么动作”，Workflow / Agent Loop 回答“下一步由谁决定”。详细控制结构留给后面的 Workflow 与 Agent 章节。

<a id="ch07-control-data-preview"></a>
### 3.19 Tool Result 先按外部数据处理

网页、文件、RAG 文档和 Tool Result 都可能包含不可信内容。即使结果文本写着“忽略系统指令”或“你现在有管理员权限”，它也不能因此获得更高控制权。

完整的 Prompt Injection、指令优先级、Permission / Policy 与 Control/Data 边界放到 Harness / Durable Execution 章节。本章只保留动作合同需要的一条底线：**Tool Result 是返回数据，不是新的系统指令。**

<a id="ch07-current-facts"></a>
## 当前接口事实｜2026-09-03

本章的架构边界不依赖 OpenAI，但当前 API 可以验证“结构化输出”和“模型提出调用、应用执行调用”确实是分开的产品接口：

- OpenAI 当前 [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 支持用 JSON Schema + `strict: true` 约束模型结构，并明确区分 Structured Outputs 与仅保证合法 JSON 的旧 JSON mode。
- OpenAI 当前 [Function calling](https://developers.openai.com/api/docs/guides/function-calling) 把 Tool Calling 描述为多步流程：应用先向模型提供 Tool，模型返回 Function Call，**应用侧执行代码**，再把 Tool Output 交回模型。

这两个当前实现只作为事实例子。稳定原则仍然是：**结构合法不等于业务正确；模型提出动作不等于物理执行；执行结果也需要被验证后才能进入系统 Truth。**
