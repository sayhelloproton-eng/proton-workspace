# 模型怎样使用外部知识

> 唯一职责：解释模型参数之外的资料，怎样经过一条可验证的证据链进入当前回答。
> 读完要能回答：面对会更新、私有或必须引用来源的知识，系统怎样找到正确内容、排除错误版本，再把足够的证据交给模型？
> 阅读前最好先理解 Transformer 与模型调用。本章只处理外部知识从资料源进入一次模型调用的过程；长期记忆、任务运行和外部动作由后续章节继续展开。

## “今天生效的报销制度”为什么不能靠模型记忆回答

用户问“公司今天生效的报销制度是什么”。模型参数里即使记得一份报销规则，也可能是旧版本；如果答案还要求引用正式条款，系统更不能只赌模型记忆。真正的问题变成：**当前权威资料在哪里，怎样把与问题有关的部分找出来，并让模型只依据这些证据回答。**

### 本节新词

- **Knowledge Source（知识源）**：系统承认可以提供原始事实或正式内容的来源，例如版本化文档、代码仓库、业务数据库或官方 API。它负责“事实从哪里来”，不等于为了检索速度建立的索引。
- **Evidence（证据）**：能够支持回答中具体事实、结论或引用的可追溯材料。本章里的目标不是“找到看起来相关的文本”，而是形成能回到来源的 Evidence。
- **RAG — Retrieval-Augmented Generation（检索增强生成）**：在模型生成回答前，从参数之外的 Knowledge Source 找回相关证据，并把筛选后的内容装入当前模型调用。它是一条知识供应链，不等于向量数据库。
- **Indexing（索引构建）**：在请求到来前，把知识源解析、切分并转换成便于查询的派生结构。Index 可以重建；原始事实、版本和权限仍由 Knowledge Source 负责。

先不要记 Retriever、Reranker、Embedding 等内部角色，只看业务上真正发生的两段工作：

```text
正式知识源
→ 预先整理成可搜索结构

用户问题
→ 找回候选证据
→ 排除过期 / 不可信内容
→ 把最终证据交给模型
→ Answer + Sources
```

后面的章节会沿这条链逐步给每个中间责任命名。这样先知道“为什么存在”，再记“叫什么”。

## 一条 RAG 链路究竟有哪些工程责任

<a id="ch06-why-rag"></a>
### 3.1 为什么需要 RAG：参数知识不是所有知识的唯一容器

#### 本节新词

- **Retrieval（检索）**：根据当前问题从外部资料中找回可能相关内容的过程，负责“去哪找、找回什么”。它不负责生成最终答案。
- **Context（上下文）**：这一次模型调用实际能看到的输入工作集。RAG 找到的 Evidence 必须进入当前 Context，模型才可能使用它；Context 的完整系统治理留到后续 Runtime 章节。
- **Vector Database / Vector DB（向量数据库）**：存储向量并支持相似度检索的一类基础设施，只是 RAG 可选的检索实现之一。把 RAG 等同 Vector DB 会丢掉查询、排序、版本和证据装配责任。

模型权重可以编码大量统计规律和知识，但真实应用经常遇到三类问题：

```text
知识后来才产生 / 会更新
企业私有资料不在训练集
回答需要可追踪证据，而不是只靠参数记忆
```

RAG — Retrieval-Augmented Generation（检索增强生成）让系统在回答前去外部知识源查找相关内容，并把证据装进当前调用的 Context；它不需要因此重新训练模型。

```text
Question
  ↓
Retrieve external knowledge
  ↓
Select evidence
  ↓
RAG Context Assembly
  ↓
LLM
  ↓
Answer grounded in evidence
```

所以正式边界是：

> **RAG = Retrieval + RAG Context Assembly；Vector DB 只是可选检索基础设施之一。**

RAG 可以使用 Vector Search、Keyword/BM25、SQL、Knowledge Graph、CodeGraph、Search API 或多种组合。

<a id="ch06-embedding-boundary"></a>
### 3.2 Retrieval Embedding ≠ Token Embedding

#### 本节新词

- **Retrieval Embedding（检索嵌入）**：把 Query、Document 或 Chunk 转成适合比较检索相似关系的连续向量表示，服务于外部知识检索。
- **Embedding Model（嵌入模型）**：专门产生 Retrieval Embedding 的模型。它负责表示和检索，不等于最终生成答案的 LLM。
- **Token Embedding（Token 嵌入）**：LLM 内部把 Token ID 转成初始连续表示的模型参数。它与 Retrieval Embedding 都叫 Embedding，但训练目标、系统位置和责任不同。
- **Hidden State（隐藏表示）**：模型中间层针对当前输入计算出的动态表示。理论上可以导出做其他用途，但“能拿到向量”不等于“天然适合生产检索”。

Transformer 章的 Token Embedding（Token 嵌入）属于语言模型内部参数：Token ID 通过 Embedding Matrix 变成模型计算所需的初始表示。

与模型内部的 Token 表示不同，检索时要把 Query / Document / Chunk 映射到适合比较相关性的向量空间。

```text
Token Embedding
Token ID → LLM 内部表示
用于 Transformer 内部计算

Retrieval Embedding
Query / Document → 检索向量空间
用于本章的外部知识检索
```

它们都叫 Embedding，但训练目标、使用位置和系统职责不同。生成式 LLM 的 Hidden State 理论上也能拿出来做 Vector，并不代表这种表示就天然适合生产检索。

BERT/GPT 章中的 BERT-style Encoder 说明了一类“形成理解/匹配表示”的模型路线；到了 RAG，问题进一步变成：**哪种 Embedding / Reranker 能把正确证据稳定找回来。**

<a id="ch06-vector-similarity"></a>
### 3.3 Vector 是表示，Similarity 才是比较结果

#### 本节新词

- **Vector（向量）**：一组有顺序的数值；在检索场景中，它表示文本在学习得到的语义空间中的位置。它本身不是“匹配度”。
- **Similarity（相似度）**：比较两个 Vector 后得到的接近程度分数，回答“表示有多像”。它不负责判断文档是否最新、正式或有权限使用。
- **Learned Vector Space（学习得到的向量空间）**：Embedding Model 训练出的表示空间，语义关系由模型训练目标决定，不是人为给每个维度固定一个可解释标签。
- **Deprecated（已废弃／已过期）**：资料仍可能存在、语义也可能与查询很相似，但已经不应作为当前事实使用的状态。Similarity 无法单独解决这个版本问题。

落到检索流程里，一份 Document 和一个 Query 会分别得到一组数值坐标：

```text
Document A → [0.12, 0.73, -0.41, ...]
Query Q    → [0.09, 0.70, -0.35, ...]
```

随后再计算两组坐标之间的相似程度，决定哪些候选更值得召回。

因此：

```text
Vector ≠ similarity score
```

“向量是坐标，比较以后才得到相似度”是一个很稳定的应用层心智模型。

但还要继续加一层：

```text
Similarity ≠ relevance guaranteed
Similarity ≠ authority
Similarity ≠ current truth
```

语义上很像的旧文档可能已经 deprecated；很不像的精确编号 `RFC-102` 却可能是唯一正确证据。

<a id="ch06-ingestion-chunking"></a>
### 3.4 入库链：Parser → Chunk → Index

#### 本节新词

- **Parser / Loader（解析器／加载器）**：把 PDF、Markdown、网页、代码或数据库内容读取并转换成系统可处理结构的组件；它负责“把源读进来”，不负责语义检索。
- **Cleaner / Normalizer（清洗器／归一化器）**：去掉无关噪声、统一格式或字段，使后续切片和索引更加稳定。归一化不应悄悄改变原始事实。
- **Chunk / Chunker（知识片段／切片器）**：Chunk 是可独立召回的候选内容单位，Chunker 决定怎样切分。切得太大难定位，太小会丢上下文。
- **Metadata（元数据）**：和 Chunk 一起保存的来源、版本、状态、更新时间、分支等结构化属性，后面用来做确定性过滤和权威判断。
- **Search Index（搜索索引）**：为了快速检索而构建的派生结构，可以是向量、关键词或图索引；它不是原始知识源。
- **Structure-aware Chunking（结构感知切片）**：优先沿标题、段落、函数、类、测试等自然结构切分，而不是只按固定 Token 数机械截断。
- **Chunk Overlap（片段重叠）**：让相邻 Chunk 保留部分重复内容以保护跨边界语义的做法；过度重叠会制造重复候选和 Context 噪声。

常见知识入库链路：

```text
PDF / Markdown / Web / Code / DB
  ↓
Parser / Loader
  ↓
Cleaner / Normalizer
  ↓
Chunker
  ↓
Chunks + Metadata
  ↓
Embedding / Keyword / Graph extraction
  ↓
Search Index
```

Chunk（知识片段）是检索系统的基本候选单位之一。切片太大，定位不准；切片太小，语义和上下文关系容易断裂。

因此优先考虑 Structure-aware Chunking（结构感知切片）：

```text
Markdown → Heading / Section
Code     → Function / Class / Method / Test Case
Docs     → Paragraph / Section / Table boundary
```

机械固定 Token 长度并不是永远错误，但不应该忽略天然结构；过度 overlap 也会制造重复候选、增加索引和 Context 噪声。

<a id="ch06-knowledge-source-index"></a>
### 3.5 Knowledge Source 与 Index：源和派生物必须分开

#### 本节新词

- **Source of Truth（真值源／权威事实源）**：系统在某一类问题上最终承认的事实来源。例如当前实现看 Source Code，正式合同看 Spec。不同问题可能有不同 Truth Owner。
- **Derived Index（派生索引）**：由 Knowledge Source 计算生成、可被重建的检索结构。它负责提高查找效率，不应因为“检索很快”就升级为业务真值源。
- **AST — Abstract Syntax Tree（抽象语法树）**：把程序代码解析成语法结构树的表示，可用于代码关系和符号索引；它描述代码结构，不是向量语义索引。
- **Git（分布式版本控制系统）**：记录源码版本、提交和变化历史的工程系统。本章把 Git 仓库视为一种可版本化知识源，后面的检索章再展开 Commit、Diff、HEAD 等细节。
- **API — Application Programming Interface（应用程序接口）**：软件之间按约定字段交换请求与响应的程序接口。API Response 可以成为知识来源，但接口返回成功不自动代表内容就是最终业务真值。

Knowledge Source（知识源）是被系统承认的原始或权威资料，例如：

```text
Git repository
正式 Spec
业务数据库
版本化文档
官方 API response
```

Vector DB、BM25 Index、CodeGraph/AST Index 常是为检索效率生成的 Derived Index（派生索引）。它们可以重建，因此不应天然被当成业务 Truth。

```text
Source of Truth
      ↓ derive
Vector / Keyword / Graph indexes
      ↓ retrieve
Evidence candidates
```

这条边界必须保持清楚：**Knowledge Source / retrieval storage 属于知识系统；State / Memory / Checkpoint 的完整定义属于后续 Runtime 章节。**

<a id="ch06-retriever-reranker"></a>
### 3.6 Retriever 与 Reranker：别漏 vs 别排错

#### 本节新词

- **Retriever（检索器／召回器）**：从大规模索引中快速找回一批可能相关候选，优先提高 Recall，避免真正答案一开始就被漏掉。
- **Recall（召回率）**：应该被找回的相关内容中，有多少进入了候选集合；高 Recall 不保证候选排序已经足够准确。
- **Reranker（重排序器）**：对 Retriever 已经召回的小批候选进行更精细相关性判断并重新排序，关注“正确内容能否靠前”。
- **Precision / Ranking Quality（精度／排序质量）**：候选中有多少真正相关，以及相关候选是否处在更前位置的质量维度。它和 Recall 优化目标不同。
- **Cross-Encoder（交叉编码器）**：把 Query 和候选文本一起输入模型做联合相关性判断的实现路线之一，可用于 Rerank；它不是 Reranker 这个系统责任本身。

实际检索通常先追求“别漏掉正确资料”，从大量候选中快速缩小范围：

```text
10 万 chunks
↓ Retriever
100 candidates
```

候选缩小后，再用更精细的判断把真正相关的内容排到前面：

```text
100 candidates
↓ Reranker
Top 10 evidence candidates
```

可以记成：

> **Retriever 解决“别漏”；Reranker 解决“别排错”。**

BERT / Encoder 描述的是模型路线；Reranker 描述的是检索系统责任。Cross-Encoder、专用 rerank model、甚至受控生成模型都可以实现重排序，因此：

```text
BERT ≠ Reranker
```

<a id="ch06-query-processing"></a>
### 3.7 Query Processing：不是每个用户问题都适合原样检索

#### 本节新词

- **Query Processing（查询处理）**：检索前对用户问题做规范化、改写、扩展或分类的一组步骤，目标是让后续 Retriever 收到更适合搜索的 Query。
- **Query Rewrite（查询改写）**：把依赖对话上下文、口语化或含糊的问题改成独立、可搜索的表达，不等于改变用户真实意图。
- **Query Expansion（查询扩展）**：为同一问题生成多个互补搜索表达，提高不同表述下找到证据的机会；它会增加检索和去重成本。
- **Query Classification（查询分类）**：判断问题更适合 Vector、Keyword、Graph、SQL，还是无需检索，从而选择搜索路径。

真正执行时，三种处理解决的是不同问题：对话里一句“那第二个呢”需要先改写成可独立搜索的问题；单一说法可能漏召回时再做扩展；只有当问题类型会改变检索后端时，才需要分类。

这些步骤属于检索前处理，不是 Vector DB 或 Embedding Model 自动替你完成的能力。

工程上也不应该默认每次都串行调用一个大模型：

```text
Query 已清楚       → 直接检索
简单别名 / 规范化   → 规则
模糊上下文依赖      → 小模型 rewrite
复杂多意图          → expansion / planner
```

这是一个 latency-aware（延迟敏感）的 Decision Rule：**能直接检索就不要先增加一次不必要的模型调用。**

<a id="ch06-hybrid-retrieval"></a>
<a id="ch06-codegraph-graphrag"></a>
### 3.8 RAG 不等于 Vector Search

Query Processing 之后，Retriever 不一定只有 Vector Search。精确标识符、代码关系、版本历史和结构化事实，本来就属于不同的信息形态；硬把它们都塞进同一个向量空间，往往会把“检索技术”误当成“真值类型”。

本章只需要建立这条边界：**RAG 可以组合多个 Retriever，选择什么检索路径取决于问题在追哪一种 Truth。** 语义相似可以用向量，精确词法可以用关键词/BM25，代码关系可以来自结构索引，版本变化应回到 Git，聚合事实应回到 SQL 或领域 API。

图结构也一样。GraphRAG 通常指把图结构或由文本构建的实体关系图用于检索与生成；CodeGraph 更聚焦函数、类、调用、导入等代码结构关系。两者都可能给 RAG 提供候选，但“用了图”不等于采用了同一种 GraphRAG 实现。这里保留这条边界，不继续展开各类 Retriever 的定义和融合算法。

真正的问题是：面对一次查询，**先搜哪种来源、要不要串行、怎样融合、冲突时信谁**。这些由下一篇 [检索系统怎样找到正确资料](02_检索系统怎样找到正确资料.md) 正式负责。

<a id="ch06-rag-context-assembly"></a>
### 3.10 RAG Context Assembly：这是 General Context Assembly 的检索特化

#### 本节新词

- **RAG Context Assembly（RAG 上下文装配）**：把检索候选经过去重、过滤、版本判断、排序、来源标注和 Token 预算控制后，组织成模型本次真正看到的 Evidence Context。
- **General Context Assembly（通用上下文装配）**：Runtime 层把 Goal、State、Memory、Instructions、Tool Results、RAG Evidence 等多种来源共同组装进一次调用的更大过程。RAG Context Assembly 只是其中知识检索的特化。
- **Token Budget（Token 预算）**：一次调用里为某类 Context 内容分配的 Token 空间。RAG 目标不是把候选全塞满，而是让有限预算承载高价值 Evidence。
- **Context Compression（上下文压缩）**：在保留关键事实、来源和边界的前提下减少 Evidence 占用的 Token；压缩产物是派生内容，不能替代原始 Evidence。

Retriever / Reranker 得到候选后，还不能直接“全部塞进 Prompt”。RAG Context Assembly（RAG 上下文装配）需要处理：

```text
Deduplication
Filtering
Version / Freshness
Ordering
Token Budget
Source labels
Evidence grouping
必要的 compression
```

于是：

> **Retriever 决定“找回来什么”；Reranker 决定“哪些更相关”；RAG Context Assembly 决定“哪些证据最终怎样给模型看”。**

General Context Assembly（通用上下文装配）还要整合 Goal、State、Memory、Instructions、Tool Results 等来源，因此留到 State/Context/Memory 章。本章只解释 retrieval evidence 怎样进入 Context。

Context Window（上下文窗口）是稀缺资源，正式容量概念属于 Transformer 章。RAG 的目标不是让 Context 越大越好，而是以更小 token cost 提供更高价值证据。

<a id="ch06-metadata-authority"></a>
### 3.11 Metadata、Freshness、Authority：语义相似之后还要判断“该不该信”

#### 本节新词

- **Freshness（新鲜度／时效性）**：候选内容相对于当前时间、版本或代码 Revision 是否仍然有效的属性。语义很相关的旧版本仍可能因为 Freshness 失败而被排除。
- **Authority（权威性）**：多份来源冲突时，系统依据来源责任和事实类型判断“哪一个更应该被相信”的规则。它不能从 Vector Similarity 自动推导出来。
- **Metadata Filter（元数据过滤）**：用 status、branch、version、environment 等结构化字段做确定性筛选的步骤，适合交给代码，而不是让 LLM 猜。

每条知识候选最好携带 Metadata（元数据），例如：

```text
source
source_type
status
version / commit
updated_at
branch / environment
owner
```

确定性条件应直接过滤，例如只保留 `status=active`、当前 branch，并排除 deprecated version。

Authority（权威性）回答“多份来源冲突时谁更应该被相信”。例如代码仓库里可能有：

```text
Spec         → 设计/合同 Truth
Current Code → 实现 Truth
Test/Evidence→ 验证 Truth
Git History  → 历史原因
```

于是长期可记：

> **Vector Search 找“像什么”；Metadata 决定“能不能用”；Authority 决定“更应该相信谁”。**

<a id="ch06-index-lifecycle"></a>
### 3.12 索引生命周期：可重建，不等于可以任意陈旧

#### 本节新词

- **Index Lifecycle（索引生命周期）**：索引从首次构建、增量更新、失效到全量重建的维护过程。索引是派生物，但陈旧索引仍会持续制造错误 Evidence。
- **Incremental Indexing（增量索引）**：只对新增、修改或删除的 Source 对象更新相关索引，避免每次全量重建。
- **`lastIndexedCommit`（最后索引提交）**：代码仓库索引可记录的版本游标，用来判断从哪个 Git Commit 开始计算变化。它是索引状态，不是业务 Truth。
- **Full Re-index（全量重建）**：当 Embedding Model、Chunk 策略、Parser 或 Index Schema 发生重大变化，或索引损坏时，从 Source 重新构建整个派生索引。

派生索引虽然不是 Source of Truth，但仍必须维护 freshness，否则检索会持续返回已经删除或过期的知识。

代码仓库可用增量策略：

```text
lastIndexedCommit
↓
git diff lastIndexedCommit..HEAD
↓
changed files
↓
re-parse / re-chunk / re-index affected data
```

适合 full re-index 的情况包括：

- Embedding Model 重大变化；
- Chunk strategy 版本变化；
- Parser 语义变化；
- Index schema / graph extraction 变化；
- 索引完整性损坏。

因此 Index State 本身也应版本化，例如 `embeddingModel`、`chunkStrategyVersion`、`lastIndexedCommit`。

<a id="ch06-naive-rag-failures"></a>
### 3.13 Naive RAG 的失败不是“向量数据库不够高级”

#### 本节新词

- **Baseline（基线）**：在引入更复杂检索、重排或 Agent 策略前，用来比较新增方案是否真的更好的最小可运行方案。
- **Naive RAG（朴素 RAG）**：最简单的“Query Embedding → Top-K Vector Search → 把 Chunk 塞进 Prompt → 生成”链路，适合做 Baseline，但容易暴露切片、版本、精确词和多跳关系问题。
- **Top-K**：按相关性分数只保留排名最高的 K 个候选。K 越大并不自动越好，过多低价值候选会污染 Context。
- **Multi-stage Retrieval（多阶段检索）**：用多个连续步骤逐渐缩小、验证或扩展候选，例如召回→重排→权威过滤，而不是一次搜索结束。

最简单的 Naive RAG 常是：

```text
Question
→ Embedding
→ Top-K Vector Search
→ chunks
→ Prompt
→ LLM Answer
```

它很快暴露出一组真实失败：

1. Chunk 断裂：答案跨多个边界；
2. 语义相似 ≠ 回答相关；
3. 编号、专有名词、精确字符串可能更适合 keyword search；
4. 多跳关系单次 Vector Search 难以完成；
5. Top-K 太大会污染 Context；
6. 多个版本语义都很像，但旧版本不应进入答案。

后续演进通常沿着下面这些能力组合展开：

```text
Hybrid Retrieval
+ Metadata Filter
+ Query Processing
+ Reranker
+ Multi-stage Retrieval
+ Better Context Assembly
+ Eval
```

<a id="ch06-agentic-rag"></a>
### 3.14 Agentic RAG：检索从固定一步变成可动态决定的行为

#### 本节新词

- **Agentic RAG（智能体式 RAG）**：检索策略不再固定为一次调用，而是根据当前 Evidence 决定是否继续检索、改写 Query、切换来源或停止。它借用了 Agent 式动态决策，但核心责任仍是找知识证据。
- **Deep Research（深度研究）**：围绕开放研究目标持续管理查询、证据缺口、冲突、来源和停止条件的长程研究任务。它可以使用 Agentic RAG，但目标和生命周期更大。
- **Evidence Gap（证据缺口）**：当前证据还不足以支持结论时明确缺少的事实、来源或对照项，用来驱动下一轮检索。
- **Stopping Condition（停止条件）**：决定研究或动态检索什么时候已经足够、应该结束的规则；没有停止条件会让 Agentic Retrieval 变成无边界循环。

传统 RAG 更像：

```text
Question → Retrieve once → Generate
```

当一次检索不足以回答问题时，系统可以根据已有证据改变下一轮检索策略：

```text
Goal
↓
需要检索吗？
↓
生成 / 改写 Query
↓
选择 Source / Retriever
↓
Retrieve / Read
↓
证据够吗？
├─ No → Rewrite / change source / retrieve again
└─ Yes → Synthesize
```

本章只解释检索策略怎样动态化；Agent Loop 怎样运行留到 Agent 章节，Deep Research 怎样组织研究留到执行环境与评估章节。

Deep Research 与 Agentic RAG 也不等价：Deep Research 围绕开放研究目标持续管理 Plan、Evidence Gap、Conflict 与 Stopping；RAG 的核心责任仍是为当前任务找到外部知识证据。

<a id="ch06-rag-vs-memory"></a>
### 3.15 RAG vs Memory：查外部知识 vs 复用过去

#### 本节新词

- **Memory（记忆）**：系统保存、筛选并在未来任务中复用的过去信息，例如用户偏好或历史决策。它和 RAG 都可能使用 Retrieval，但 Memory 的语义是“复用过去”，不是“查询外部知识源”。
- **Scope（作用域）**：信息允许在哪个用户、任务、项目或时间范围内被复用的边界。Memory 尤其需要 Scope，不能因为“检索到了”就自动进入所有 Context。

这是知识系统与运行时信息对象之间最重要的边界。

```text
RAG
= 查外部 Knowledge Source
= 本章解释的知识检索问题

Memory
= 保存值得未来复用的过去信息
= 由“状态、上下文与记忆”一章解释
```

二者可以共享 Retrieval / Ranking / Context Assembly 技术，但**系统语义不同**。项目的 Git/Spec/README 作为 Knowledge Source，不应全部粗暴称为 Agent Memory。

Vector Similarity 也只负责候选“像不像”。Memory 在进入模型前，还要受 scope、freshness、trust、permission、conflict 等约束；Memory 的作用域、可信度、冲突处理和 Context 装配留到 State/Context/Memory 章，Permission 这一硬边界留到 Durable Execution 章。

<a id="ch06-rag-sft-tool"></a>
### 3.16 Prompt / RAG / SFT / Tool：四个不同问题

#### 本节新词

- **Tool（工具）**：让模型或 Agent 通过 Runtime 请求执行外部动作的能力，例如查数据库、发请求或修改系统。RAG 负责提供知识证据，Tool 负责改变或读取外部世界，下一章会完整展开。
- **Capability（能力）**：对任务暴露“系统能做什么”的高层合同，例如 `search_project_knowledge`。Capability 可以由多个底层工具或后端实现，不应把 Vector DB 之类实现名直接当业务能力。

旧语料里这组心智模型值得保留，但这里不重复其他专题的完整解释：

```text
Prompt / ICL → 这次怎样表达任务       继续阅读 BERT/GPT、状态与上下文
RAG          → 这次参考什么外部资料   本章负责解释
SFT          → 长期训练什么行为       继续阅读后训练
Tool         → 真正执行什么外部动作   继续阅读工具调用
```

工程决策可以先问：

```text
模型没见过当前资料？      → RAG candidate
模型不会稳定做某种行为？  → Post-training candidate
必须绝对执行的硬规则？    → Code / Runtime candidate
需要改变现实世界？        → Tool / Capability candidate
```

这只是跨章 Decision Model，不让 RAG 章 变成 Post-training / Runtime / Tool 的第二定义站。

<a id="ch06-custom-gpt-knowledge"></a>
### 3.17 当前事实 · 2026-09-03｜GPT Knowledge 是上传参考资料，外部动态数据通过连接能力访问

#### 本节新词

- **GPT Knowledge（GPT 知识文件）**：Custom GPT 配置中由 Builder 上传、供 GPT 回答时作为 reference material 使用的文件。它适合参考资料，不应被当成自动同步外部数据库的实时状态层。
- **Apps（应用集成）**：ChatGPT / GPT 可连接的外部服务能力，用于搜索、引用或在权限允许时执行支持的动作；具体可用能力受计划、Workspace 和 App 配置影响。
- **Actions（自定义动作）**：Builder 用 OpenAPI Schema 和认证配置为 GPT 接入自定义 external API 的机制，可用于读取外部数据或触发外部流程。GPT 当前不能同时使用 Apps 和 Actions。
- **OpenAPI Schema**：用机器可读格式描述外部 API endpoint、参数和操作的接口规范；GPT Actions 通过它知道有哪些操作可以请求。

OpenAI 当前官方 GPT 文档把 Knowledge 描述为上传后供 GPT 回答时参考的文件；同一产品当前支持 Apps 和 Actions 两条外部连接路径，且一个 GPT 不能同时配置二者。Actions 通过 Builder 定义的 external API 与 OpenAPI Schema 接入外部系统；Apps 则连接用户或 Workspace 可用的外部服务。

因此稳定的工程判断仍然成立：**上传的 Knowledge 文件是静态参考资料，不会自动跟随 Git、数据库或业务状态变化。** 数据需要持续变化时，应从仍然拥有当前 Truth 的外部系统读取，再把结果作为本轮 Evidence 交给模型。

这属于会随产品变化的实现事实，阅读时应以当期官方文档重新核验；RAG 的稳定定义不依赖 GPT 产品具体叫 Apps、Actions 还是其他连接能力。

<a id="ch06-capability-runtime-boundary"></a>
### 3.18 Knowledge Backend ≠ Capability ≠ Runtime

#### 本节新词

- **Knowledge Backend（知识后端）**：Vector DB、CodeGraph、SQLite 等保存或查询知识数据的底层实现。它回答“数据怎样存／查”，不应该直接成为模型的业务合同。
- **Runtime（运行时）**：在任务执行期间选择能力实现、组装输入、控制生命周期和处理结果的系统层。它可以调用 Knowledge Backend，但不等于某个数据库。

这三个层级容易被写在同一句话里，需要明确拆开：

```text
Vector DB / CodeGraph / SQLite
→ 知识与数据后端的实现例子

search_project_knowledge(...)
→ 面向任务的高层能力合同

Runtime
→ 选择和编排实现，并控制执行生命周期
```

本章可以解释底层检索实现，但 Capability 怎样封装动作留到 Tool 章，Runtime 怎样承接长期责任留到 Runtime/Task 章。一个好的对外接口通常暴露“要完成什么”，而不是把内部数据库类型直接暴露给模型。

<a id="ch06-case-hybrid-retrieval"></a>
### 3.19 Case Lens｜代码仓库为什么会逼出 Hybrid Retrieval

代码仓库是一个很好的反例：需求文档要找语义相近内容，函数名需要精确命中，调用链需要结构关系，版本问题要看 Git，当前运行状态又可能来自数据库。它们共同进入一个知识系统，不代表应该进入同一种 Index。

这条案例在本章只承担一个判断：**Source 的 Truth 形态决定检索入口，Index 只是为了更快找到 Source/Evidence。** Keyword、BM25、CodeGraph、Git、SQL 怎样组合和校验，留给下一篇 Hybrid Retrieval 章节，不在这里再教一遍。

<a id="ch06-project-custom-gpt-local-runtime"></a>
#### 3.19.1 案例怎样进入真实系统章节

不同 Truth 需要不同检索方式；外部接口应暴露高层 Capability，而不是数据库类型；Index 要跟随 Source 变化。完整项目推演由真实系统章节承接：

- [Custom GPT + Local Retrieval Runtime](../08_真实系统与岗位/02_云端Agent怎样访问本地知识.md)负责云端交互、本地私有知识、受控入口、权限和 Evidence；
- [ProFlow 架构演进](../08_真实系统与岗位/01_ProFlow为什么从工作流走向Agent平台.md)负责 Spec/Source/Test/Git/Runtime 多种 Truth 和真实证据层级；
- [端侧与云端协同](../08_真实系统与岗位/03_端侧模型与云端模型怎样分工.md)负责模型档位、队列和 Context 隔离。

#### 3.19.2 增量索引是知识系统自己的责任

首次建立索引可以全量解析；持续运行时应根据 Git diff、文件 hash、数据库更新时间或 Source event 只重建受影响对象。删除 Source 时同步清除派生索引，Parser/Embedding/Schema 版本变化时显式触发重建。

索引可以重建，但不能任意陈旧。Freshness、source revision、index revision 和 last successful build 都应可观测。

### 3.20 RAG Eval：不要只看最终答案

#### 本节新词

- **RAG Evaluation / RAG Eval（RAG 评估）**：沿 Knowledge→Retrieval→Rerank→Context→Answer 分层测量整条知识链，而不是只检查最终回答“看起来对不对”。
- **Recall@K**：正确证据是否出现在 Retriever 前 K 个候选中的指标，主要检查召回层。
- **Rerank Top-K Hit**：经过重排后，目标证据是否进入前 K 名的指标，用来检查 Reranker。
- **Context Evidence Hit**：最终送给模型的 Context 是否真正包含期望 Evidence 的检查。
- **Faithfulness（忠实度）**：回答是否忠实于给定证据，没有编造或超出 Evidence 支持范围。
- **Completeness（完整性）**：回答是否覆盖了证据足以支持、任务要求必须回答的关键部分。

评估时要沿整条检索—装配—生成链定位失败层：

```text
Knowledge
↓
Retriever
↓
Reranker
↓
Context
↓
Answer
```

至少分别问：

| Layer | 典型问题 |
|---|---|
| Knowledge | 正确证据真的存在、版本正确吗？ |
| Retriever | 正确 Chunk 被找回来了吗？ |
| Reranker | 正确候选排到前面了吗？ |
| Context | 最终 evidence 干净、完整、版本正确吗？ |
| Answer | 模型正确使用证据了吗？ |

常见指标可以包括：

- Recall@K；
- Rerank Top-K Hit；
- Context Evidence Hit；
- Answer Accuracy；
- Faithfulness / Completeness 等语义质量。

<a id="ch06-eval-failure-slices"></a>
### 3.21 Failure Slice 与 Evaluator：可机械判断的不要浪费 LLM Judge

#### 本节新词

- **Failure Slice（失败切片）**：按问题类型、版本冲突、无答案、Query Rewrite 等维度把总体失败拆开，定位“哪一类输入在哪一层持续出错”。
- **Evaluator（评估器）**：执行某项质量判定的程序、规则、人工或模型；能用确定性逻辑判定的项目优先不用生成模型。
- **Deterministic Evaluator（确定性评估器）**：按可重复规则检查 document ID、anchor、version、JSON 字段等结果，输入相同就得到同样判定。
- **LLM Judge（大模型评审器）**：用较强模型辅助判断开放语义质量，例如 Correctness、Faithfulness、Completeness；它自身也会出错，不能替代可机械验证项。
- **Abstain（拒答／不作答）**：当资料中不存在可支持答案的 Evidence 时，系统明确不生成确定结论的行为，是 RAG 无答案场景的重要正确结果。

平均分很容易掩盖真实问题，因此 Eval 应按 Failure Slice（失败切片）拆开，例如：

```text
精确事实
语义改写
编号 / symbol
版本冲突
多文档综合
无答案
Query Rewrite
Rerank
Context Conflict
```

可机械判定的指标优先由 deterministic evaluator（确定性评估器）完成，例如：

```text
expected document id 是否进入 Top-K
expected evidence anchor 是否存在
无答案场景是否正确 abstain
版本 filter 是否选择 current
```

Correctness / Faithfulness / Completeness 等开放语义质量再考虑人工或强模型辅助评审。

> **RAG 成功要求 Retrieval → Context → Generation 整条链在真实问题集上稳定通过；偶尔答对一次不构成系统成功。**
