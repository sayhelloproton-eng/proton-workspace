# 怎样委派与交接任务

> 唯一职责：解释委派、交接、共享真值、私有上下文和 Parent/Child Runtime Event。

## 协作失败常常不是模型不够强，而是交接不完整

### 本节新词

- **Collaboration（协作）**：多个主体交换能力或信息，但当前责任 Owner 不一定改变。
- **Delegation（委派）**：当前 Owner 把局部责任交给另一个执行者，Parent 仍对总体结果负责。
- **Handoff（交接）**：同一责任对象的 Owner 正式转移给另一方；它必须有版本、状态和接受动作。
- **Owner（责任所有者）**：当前对某个 Task / State / Artifact 的推进和结果负责的主体。

```text
Collaboration  借用能力，责任 Owner 不变
Delegation     Parent 拆出局部责任，仍对总体结果负责
Handoff        同一责任对象正式转移 Owner
```

多 Agent 不能靠共享全部聊天协作。系统应区分 Shared State（共同真值）、Private Context（局部工作集）和 Handoff Context（接管所需最小包）。

## 三种信息平面

### Shared State

#### 本节新词

- **Shared State（共享状态）**：多个参与者必须共同承认的当前 Task 事实，例如 Owner、Plan Version、审批结果和已确认 Effect。
- **State Owner（状态所有者）**：对某个 State 字段或 Aggregate 的写入和冲突裁决负责的主体。Shared 不等于所有人都能写。
- **Transition Rule（状态转换规则）**：规定共享状态从一个合法版本进入下一个版本必须满足什么条件。

以一个跨 Agent 发布任务为例，Task status、当前 Owner、已确认 Effect、Evidence references、Plan version 和审批结果必须让所有参与者看到同一版本。真正危险的不是“别人看不到”，而是多人都能无条件覆盖这些字段，所以写入必须受 Owner、Version 和 Transition rule 约束。

### Private Context

#### 本节新词

- **Private Context（私有上下文）**：只服务某个 Agent 局部判断的工作集，可以包含候选方案、未验证假设和临时材料。
- **Local Hypothesis（局部假设）**：只在当前 Agent 内部成立、尚未经过共同验证的推断。它不能因为被广播就自动成为 Shared Fact。

研究 Agent 可以在自己的 Private Context 中保留候选方案、未验证假设和临时材料，而不必实时广播给所有参与者。这样既减少全局 Context 噪声，也避免半成品在“大家都看见了”之后被误当成共同事实。

### Handoff Context

#### 本节新词

- **Handoff Context（交接上下文）**：新 Owner 接管责任所需的最小、可核验信息包，包括目标、当前 State、已完成/未完成、关键 Evidence、风险和下一安全动作。
- **Minimal Transfer（最小交接）**：只传接手者真正需要的状态和引用，不复制发送方全部 Memory / History。

真正交接时，新 Owner 至少要拿到目标、当前 State、已完成/未完成、关键 Evidence、开放风险、允许动作、成功标准和下一安全动作。缺任何一项都可能让接手者重新猜历史；把完整聊天全倒过去又会把噪声一并转移。

## Information Funnel

### 本节新词

- **Information Funnel（信息漏斗）**：局部 Observation / Hypothesis 经过验证、Owner review 和 State Transition 后，才逐步晋升为 Shared Fact / Decision 的过程。
- **Finding（发现）**：局部调查得出的可复核结论，通常需要 Evidence 后才能进入共享层。

```text
private observation / hypothesis
  ↓ local validation
finding + evidence refs
  ↓ owner review / state transition
shared fact or decision
```

Hypothesis 不能因为被多个 Agent 重复就升级成 Fact。进入 Shared State 必须经过明确验证与提交动作。

## Delegation

### 本节新词

- **Child Task（子任务）**：Parent 为一段局部责任创建的可独立追踪工作单元。
- **Return Contract（返回合同）**：规定 Child 完成后必须返回哪些 Artifact、Evidence、状态和不确定性。

Parent 创建 Child Task，定义输入、Scope、预算和返回合同。Child 可以自主选择局部路径，但不能扩大 Parent 授权。完成后 Parent 根据 Evidence 接受、拒绝或要求补充。

适合：研究子问题、独立代码模块、并行审计、专门领域判断。  
不适合：高度耦合、共享写冲突、责任无法验收的模糊“帮忙”。

## Handoff

### 本节新词

- **Handoff Proposal（交接提议）**：旧 Owner 请求把责任转移给新主体的待确认动作。
- **Version（版本）**：State / Owner 每次受治理变化后的单调身份，用来拒绝迟到写入。
- **STALE_OWNER / STALE_VERSION（过期 Owner／过期版本）**：旧主体或旧版本返回的动作已经失去写入资格，应被拒绝而不是覆盖当前世界。

Handoff 改变 Owner，因此必须是 Control Plane 的正式状态转换：

```text
owner=A, version=7
  ↓ handoff proposed to B
  ↓ B accepts exact version
owner=B, version=8, HANDOFF_ACCEPTED event
```

聊天里说“你接着做”不够。系统要处理拒绝、超时、旧 Owner 的在途动作、版本冲突和权限迁移。

上面的 `owner=A, version=7` 完成交接后，系统承认的是 `owner=B, version=8`。如果 A 的旧请求稍后才返回，它不能因为“执行成功”就继续写入；Control Plane 应拒绝为 `STALE_OWNER` 或 `STALE_VERSION`，并要求根据 version 8 重新判断。否则一次正常的网络延迟就可能让旧 Owner 覆盖新 Owner 已确认的事实。

Handoff 要少。优先顺序通常是 Collaboration → Delegation → Handoff；只有责任确实需要转移时才交接。

## Parent / Child Runtime Event

上一章已经用 Child Event 解释异步 Subagent。这里不再重定义 Event，只补两项交接需要的信息。

### 本节新词

- **State Version（状态版本）**：Event 针对哪一版 State 产生，Parent 可用它判断事件是否仍然适用于当前世界。
- **requires_parent_action（需要父任务动作）**：结构化标记 Child 结果是否要求 Parent 重新决策，而不是所有进度都唤醒模型。

Child 进展通过结构化 Event 回到 Parent：

```text
child_task_id
parent_task_id
status
state_version
result_ref / evidence_refs
error_class
requires_parent_action
```

Event 表示已发生事实，不是命令。Parent 收到完成事件后重新装配 Context，不能假设自己一直在线等待。

## Shared State 写入规则

### 本节新词

- **Optimistic Versioning（乐观版本控制）**：写入时带上读取到的版本，只有当前版本仍一致才允许提交；冲突时返回失败而不是静默覆盖。
- **Compare-and-set（比较后写入，CAS）**：只有当前值/版本等于预期值时才更新，用来实现轻量并发控制。
- **Aggregate（聚合根／聚合对象）**：一组必须保持一致更新的业务状态边界，可以指定单一 Owner。
- **Actor / Reason（操作者／原因）**：记录是谁因为什么做了这次 State 写入，便于审计和冲突追踪。

- 单一字段或 Aggregate 有明确 Owner；
- 使用 optimistic version / compare-and-set；
- 写入记录 Actor、Reason、Evidence 和 previous version；
- 冲突返回结构化错误，不让 Agent 用自然语言争论；
- 派生摘要可重建，核心 State 不只存在于聊天；
- Artifact 与 Evidence 绑定具体版本。

## Private Context 的边界

### 本节新词

- **Reference-based Context（基于引用的上下文）**：跨 Agent 优先传 `task_id / artifact_ref / evidence_ref / commit` 等稳定引用，由接收方按权限读取原对象。
- **Sensitive Information（敏感信息）**：即使是 Private Context 也必须受访问、保留和审计规则治理，Private 不等于无限制。

Private 不代表不受治理。它仍受数据访问、保留、敏感信息和审计规则约束。只是不应把每个临时思路强制广播给所有参与者。

跨 Agent 传递时优先使用 Reference-based Context：传 `task_id / artifact_ref / evidence_ref / commit`，由接收方按权限读取，避免复制过期大段文本。

## 交接最容易丢失责任的地方

- 共享一份无限增长的聊天作为 State；
- 所有 Agent 都能改所有字段；
- Handoff 只转发摘要，没有版本和 Evidence；
- Parent 和 Child 同时对外执行同一副作用；
- 将 Child 的“我已完成”直接提交为全局 Truth；
- 为了透明强制公开全部 Private Context，最终制造噪声与从众。

## 先固定 Owner、Version 与 Evidence

如果只需要能力协助，用 Collaboration；需要局部独立产出，用 Delegation；需要长期 Owner 真正改变，才用 Handoff。无论哪种形式，都先定义 State Owner、返回合同、Evidence 与冲突规则。

## 责任转移怎样进入组织拓扑

- Subagent 章解释为什么拆局部责任；本章定义责任怎样合法流转；
- 拓扑章决定这些关系在组织上怎样连接；
- A2A 可承载跨 Runtime 消息与 Task，但本地 Shared State 仍由自己的 Runtime Commit；
- Durable Execution 提供 Version、Event、Recovery 与 Evidence 原语。

## 检查一次协作是否真正完成接管

1. Delegation 与 Handoff 的 Owner 变化有何不同？
2. Shared State 为什么不能等于共享聊天？
3. Private Context 如何安全晋升为共同事实？
4. Parent/Child 异步协作为什么依赖 Event 而不是常驻连接？
