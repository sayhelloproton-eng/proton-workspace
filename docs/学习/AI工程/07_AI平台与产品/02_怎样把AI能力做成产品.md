# 怎样把 AI 能力做成产品

> 唯一职责：解释 AI App、Vertical Agent 和领域工作流如何从业务目标走到可验证 Outcome。

## 从业务 Outcome 倒推最小 AI 系统

用户不会因为系统“用了 Agent”就获得价值。比如报销产品真正的目标可能是“用户得到正确、可追踪的报销处理结果”，而不是“模型成功生成了一段解释”。因此产品设计应从可验收 Outcome 往回推：用户怎样进入、当前业务事实从哪里来、哪些判断交给模型、哪些动作需要授权、最终怎样验证。

#### 本节新词

- **Business Outcome（业务结果）**：用户或组织最终能够观察、验收并认为有价值的结果。模型回答、Tool Success、Artifact 都只是可能通向 Outcome 的中间对象。
- **AI Application（AI 应用）**：把模型、领域 Context、交互、Workflow/Agent、Capability 与验证组合成面向用户 Outcome 的产品形态。是否需要 Agent 由路径动态性决定。
- **Minimum Viable AI System（最小可用 AI 系统，本章工作称呼）**：本章用它表示“满足当前业务 Outcome 所需的最小模型、知识、流程、能力和验证组合”。这是产品设计时的课程心智模型，不是行业统一架构标准。

```text
Business Goal
→ User Interaction
→ Domain Context
→ Workflow / Agent decision
→ Authorized Capability
→ Real Effect
→ Domain Validation
→ Outcome
```

AI App 可以只有一次模型调用；Vertical Agent 则在特定领域拥有持续工作、工具、权限和评估。二者都不必自动升级成 Platform。

## 从 Outcome 开始

#### 本节新词

- **Success Criteria（成功标准）**：把“什么才算业务完成”写成可以检查的条件。它需要先于模型或框架选择，否则团队只能评生成质量。
- **Failure Cost（失败代价）**：错误结果造成的返工、损失、风险和人工负担，用来决定自治、Approval 和验证强度。


先定义用户为什么付费或改变行为、什么叫成功、错误代价与人工接管点，再选技术。若成功只能写成“模型生成了回答”，产品边界通常还没定义完。

## Interaction / Product

#### 本节新词

- **User Interaction（用户交互）**：用户通过 Chat、Form、IDE、Extension、API、Event 或 Batch 等方式发起和理解任务。对话只是其中一种产品入口。
- **Streaming（流式反馈）**：结果生成过程中逐步返回内容或状态，降低等待感，但中间输出不应被误当成最终成功。
- **Undo（撤销）**：让用户回退某些可逆动作的产品能力；它能降低副作用风险，但不能替代 Permission。


对话只是入口之一。表单、IDE、浏览器扩展、后台、API、事件触发和批处理都可能更适合。产品层要处理流式反馈、进度、撤销、来源展示、审批和失败解释。

## Domain Context

#### 本节新词

- **Domain Context（领域上下文）**：当前业务对象、规则、历史、Evidence、权限和权威数据等完成本次领域任务所需的信息集合。它按 Task 装配，不等于一个永久大 Prompt。
- **Object Model（对象模型）**：业务系统中订单、工单、设备、客户等对象及其字段和关系定义，是 Domain Context 的结构基础。


Vertical Agent 的差异往往来自：领域术语、对象模型、当前业务 State、历史事件、规则、权限与权威数据源。Domain Context 不是一段大 Prompt，而是受版本和访问控制约束的工作集。

## Business Workflow

#### 本节新词

- **Business Workflow（业务工作流）**：组织已有状态、规则、审批和动作的确定性业务流程。AI 通常嵌入其中处理模糊判断，而不是重写全部规则。
- **Compliance（合规约束）**：法律、行业、组织政策要求必须满足的硬边界，通常应由 Code/Policy/Gate 承担，不交给概率模型自由决定。


很多业务已有确定流程：审核、结算、发布、故障处理、研发交付。AI 应嵌入流程中处理模糊判断，而不是把所有规则重写成 Agent Loop。

```text
hard rule / compliance → code & workflow
ambiguous classification → model
open exploration → agent
high-risk effect → approval + verification
```

## Domain Capability

#### 本节新词

- **Domain Capability（领域能力）**：面向业务语义的可执行动作，例如“创建退款提案”，而不是直接暴露底层表 CRUD。
- **CRUD（Create / Read / Update / Delete，增删改查）**：对底层数据对象的通用操作集合；直接把任意 CRUD 暴露给模型通常权限面过大，也缺少业务语义。


Tool 应表达业务动作，例如 `create_refund_proposal`，而不是把底层表任意读写暴露给模型。Capability Contract 包含输入、权限、副作用、错误、Evidence 与幂等语义。

## Vertical Agent

#### 本节新词

- **Vertical Agent（垂直 Agent）**：围绕一个明确行业/业务责任持续工作，并使用领域 Context、Workflow、Capability、State 和 Domain Eval 的 Agent。垂直化来自责任和数据边界，不只是行业 Prompt。
- **Exception Handling（异常处理）**：业务流程遇到缺资料、冲突、风险或外部失败时的明确处理路径，是垂直系统区别于 Demo 的重要部分。

Domain Eval 已在前面的模型/Eval 章节建立，这里只使用它：评价标准必须回到真实领域 Success Criteria、风险和 Failure Slice，而不是重新给它下定义。


一个有价值的 Vertical Agent 通常组合：

- 深领域 Context；
- 业务 Workflow 与 exception handling；
- 受控 Tool/Permission；
- 长期 Task/State；
- Domain Eval；
- 人工协作和组织流程；
- 与现有系统的集成。

护城河未必是模型，而可能是高质量 Workflow、Evidence、数据反馈和分发。

## AI App、Agent Runtime、Platform 的边界

#### 本节新词

- **AI Feature（AI 功能）**：产品中的一个局部 AI 能力，生命周期和责任可以很短；它不自动需要 Runtime 或 Agent。
- **Agent Application（Agent 应用）**：使用动态 Agent Loop 并能在环境中行动的 AI Application。是否叫 Agent Application 看责任和控制方式，不看 SDK 名称。


| 形态 | 稳定特征 |
|---|---|
| AI Feature/App | 一项具体用户价值，生命周期可短 |
| Agent Application | 路径动态、可行动、需环境反馈 |
| Agent Runtime | Task/State/Recovery/Evidence 连续性 |
| AI Platform | 多应用共享上述共性责任 |

使用框架不改变实际责任。一个调用 Agent SDK 的页面仍可能只是 AI App；一个没有聊天界面的后台系统也可能有真正 Runtime。

## Human on the Loop

#### 本节新词

- **Human in the Loop（人在回路中，HITL）**：流程在某个节点必须等待人工输入、审核或批准后才能继续。
- **Human on the Loop（人在环上监督）**：系统默认自动运行，人主要监控并在异常、高风险或低置信时介入。它要求更强 Observability 与可暂停能力。


成熟产品不是无人化竞赛。人可以在 Goal、Approval、Exception、Quality Review 和 Policy 位置介入。应减少持续看守，把人工集中在高风险与高判断价值节点。

## Feedback Loop

#### 本节新词

- **Feedback Loop（反馈闭环）**：把真实 Outcome、Failure Slice、用户修正、人工处理和成本数据送回 Eval、Routing、Workflow 或模型改进的持续循环。
- **Thumbs up/down（点赞/点踩反馈）**：低成本主观反馈信号，适合辅助发现问题，但如果不关联 Task 和 Outcome，很难直接指导工程决策。


产品反馈应连接：用户行为、任务 Outcome、失败 Slice、人工修复、成本与延迟。只收集 thumbs up/down 很难指导 Tool、Workflow 或 Runtime 改进。

## 应用架构最容易在哪些地方过度设计

- 从 RAG、Tool、Agent、MCP 等技术清单反推产品，而不是从 Business Outcome 倒推最小系统；
- 把聊天 UI 当成业务 Workflow；
- RAG 检索到资料就认为业务完成；
- Tool 成功却不回读 Effect；
- 为提高自治绕过审批；
- 通用模型 Demo 没有 Domain Eval 就宣称 Vertical Agent；
- 把每个客户差异都下沉到共享 Platform。

## 从一条可验收业务路径开始

先问：确定性代码是否够？一次模型调用是否够？固定 Workflow 是否够？只有路径确实依赖观察才用 Agent；只有长任务和副作用需要恢复才引入 Runtime；只有多个产品反复需要相同责任才平台化。

## 应用责任怎样交给平台与真实系统

- 平台责任图提供可复用组件，本章由业务目标选择组合；
- 后面的平台化门禁负责验证新增共享复杂度是否真的值得；
- 真实系统章验证云端交互、本地 Runtime、浏览器与端侧调度；
