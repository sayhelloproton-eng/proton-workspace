# 什么时候值得建设 AI 平台

> 唯一职责：用重复问题、共享责任、失败证据和增量价值判断何时平台化、何时停在应用层。

## 没有重复痛点，就没有抽象共享层的证据

如果只有一个产品、一个团队、一个稳定工作流，“先建平台以后总会用上”只是愿望。平台复杂度需要由已经出现的重复问题来证明：多个应用是否真的重复接模型、重复做权限、重复维护 Runtime、重复踩同一类故障；抽出来以后是否能让产品更快、更安全。

#### 本节新词

- **Platformization（平台化）**：把多个应用已经反复承担、边界相对稳定的责任抽成共享能力。它是对重复事实的响应，不是预设终点。
- **Architecture by Evidence（证据驱动架构，本教材工作称呼）**：每次增加抽象或复杂度前先要求可观察 Failure、Baseline 和可验证收益，用结果而不是趋势决定架构。它是本教材用于组织架构决策的方法标签，不是假装存在统一行业规范。

```text
重复出现的问题
→ explicit responsibility
→ smallest intervention
→ measurable outcome
→ only then abstraction
```

平台是复用经过验证的责任，不是提前画出的未来组织图。

## Evidence Ladder：本教材怎样区分证据层级

这里的 Evidence Ladder（证据阶梯）也是本教材的工作模型，用来避免“代码写完 = 系统完成”。

#### 本节新词

- **Implemented Candidate（已实现候选）**：代码已经存在、可以运行的候选实现。它证明“做出来了”，不证明真实环境和业务 Outcome 已通过。
- **Integrated Environment Evidence（集成环境证据）**：组件在真实或接近真实依赖组合中工作后的验证结果，比单包测试更接近系统事实。


```text
Idea / trend
< design
< implemented candidate
< tests / package evidence
< integrated environment evidence
< real external effect
< repeated production outcome
```

不同层级不能压平。单元测试通过不能证明真实浏览器或外部 Provider 完成；一次 Demo 不能证明多租户平台价值。

## 哪些现象说明应该重新评估平台化

#### 本节新词

- **Shared Contract（共享合同）**：多个应用都愿意依赖且语义稳定的接口/数据/行为约定；没有稳定合同，平台只会把变化放大。


- 第二、第三个真实场景开始重复实现同类 Gateway、Permission、Eval 或 Runtime；产品数量只是提醒你重新评估，不是 `count >= 3` 的硬门槛；
- 重复实现导致不一致安全边界或事故；
- Provider/Model 变化需要统一适配；
- 成本、配额、审计和数据边界需要组织级治理；
- 共享能力有独立生命周期和 Owner；
- 产品差异可以通过合同保留，而不是被平台抹平。

## 何时不要平台化

- 只有一个产品和一条稳定路径；
- 共性只存在于演示文稿，真实需求差异很大；
- 团队尚未定义 Outcome/Eval；
- Platform API 变化速度高于产品；
- 共享层会阻塞业务验证；
- 主要痛点只是代码重复，普通 library 已足够。

## 抽象不要一步跳到 Platform

#### 本节新词

- **Library（共享库）**：被多个应用以进程内依赖方式复用的代码/类型/工具，不需要承担网络服务的可用性和多租户责任。
- **Shared Service（共享服务）**：通过网络或进程边界为多个应用提供能力，需要承担版本、容量、可用性和运营责任。


```text
copy with learning
→ shared convention
→ library / schema
→ shared service
→ control plane / platform
```

选择最小能解决问题的层级。Library 不需要网络、租户和运营；Shared Service 则要承担可用性、版本与容量。

## Architecture Decision Record（ADR，架构决策记录）

#### 本节新词

- **ADR（Architecture Decision Record，架构决策记录）**：记录架构问题背景、约束、候选方案、决定、后果和退出条件的文档。它保存“当时为什么选”，不是永恒规范。
- **Exit Condition（退出条件）**：当共享方案不能产生预期价值或成本失控时触发降级/移除的条件，防止抽象建立后永久存在。


每次升级记录：触发问题、当前基线、候选方案、选中责任、未选理由、风险、验证指标、回滚/退出条件，以及未来什么变化会让这项决定重新打开。ADR 不是为了形式，而是防止未来只看到架构结果，看不到当时证据。

## Baseline 与 Counterfactual

Baseline 和 Incremental Value 前文已经用过，这里只补一个平台化特别需要的问题。

#### 本节新词

- **Counterfactual（反事实）**：追问“如果不做这次平台化/Agent 化，结果会怎样”，用于区分自然增长与架构变更真正贡献。

证明 Agent、Multi-Agent 或 Platform 的价值必须有对照：

- Agent vs Workflow；
- Multi-Agent vs focused Subagent；
- Platform service vs product-owned library；
- Strong model vs routing；
- Hybrid Retrieval vs simple search。

没有 baseline，复杂系统只能证明“它能运行”，不能证明“它值得”。

## 平台化到底量什么

#### 本节新词

- **Lead Time（交付周期）**：从需求/变更开始到可用结果进入目标环境的时间，常用于判断共享能力是否真的加快交付。
- **Escape Hatch（逃生口 / 旁路机制）**：当平台默认路径无法满足产品需求时允许受控绕开的机制。Escape Hatch 持续上升可能意味着共享抽象不合适。

安全执行章已经解释 Blast Radius；平台化后同一概念会放大到“一个共享故障会影响多少产品、租户和数据”。因此指标至少要覆盖：


```text
task success / critical error
lead time / change failure
cost per successful outcome
p95 latency
recovery success
human intervention
duplicate implementation removed
platform adoption and escape-hatch rate
incident blast radius
```

平台 adoption 高不一定成功：可能是强制使用。还要看产品交付是否更快、更安全，以及 escape hatch 是否持续增长。

## Current vs Target

#### 本节新词

- **Current（当前已验证状态）**：现在真正存在并有对应 Evidence 的系统事实。
- **Target（目标状态）**：未来希望达到的设计或 Roadmap。Target 不应写成已经完成，否则会制造假 READY。
- **Roadmap（路线图）**：按时间/阶段规划的未来演进方向，是计划信息，不属于当前实现 Truth。


文档必须区分：已验证实现、部分实现、已确认设计、未来候选、已被替代。把 Roadmap 画成当前架构会产生假 READY，也会让学习者误认为所有层必须一次建齐。

## Architecture Fitness Functions

#### 本节新词

- **Architecture Fitness Function（架构适应度函数）**：持续自动或半自动检查关键架构约束是否仍成立，例如依赖方向、Schema 兼容、Permission、Evidence 完整度和成本预算。
- **Schema Compatibility（模式兼容性）**：共享接口或事件 Schema 升级后，旧消费者是否仍能正确解析和使用。


把重要边界变成持续检查：schema compatibility、权限、Scope、依赖方向、版本、Evidence completeness、latency/cost budget。Fitness Function 能防止平台在迭代中逐渐破坏最初责任。

## Self-iteration 的边界

Agent 可以提出代码、配置和评测改进，但不能垄断自我验收。修改者、验证者、外部 Truth 和发布权限需要分离；否则系统会用自己的输出证明自己正确。

## 平台化判断最容易怎样走偏

- 以组件数量证明平台成熟；
- 先建 Registry/Router，再寻找需要路由的对象；
- 测试绿即宣称外部 E2E PASS；
- 所有产品被迫使用同一巨大 Workflow；
- 平台 Owner 只量调用量，不量产品 Outcome；
- 没有退出条件，抽象一旦建立永不降级。

## 把“以后再评估”的条件写清楚

今天不平台化不等于永远不做。ADR 里应该写清哪些可观察变化会重新打开决定，例如第二/第三个真实场景开始重复、合规要求升级、Provider 数量显著增加、事故重复、成本跨过既定阈值，或跨团队 Ownership 已经稳定。

这里的产品数量和成本阈值都只是**重新评估的触发条件**，不是自动升级 Platform 的规则。触发以后仍要重新比较 Baseline、收益和新增运营成本。

## ProFlow Lens｜平台责任是被重复问题逼出来的

以下两个名字是 ProFlow 的本地架构对象，不是通用 AI 行业术语。

#### 本节新词

- **Platform CLI（平台命令行入口）**：让用户执行平台安装、配置、状态查询和生命周期操作的命令行界面。它负责共享操作体验，不拥有各模块内部业务真值。
- **Platform Host（平台宿主）**：负责把多个运行模块装配起来、提供依赖和生命周期边界的宿主进程。它组织模块，不等于把所有模块业务逻辑集中到一个服务。

ProFlow 的 Platform CLI、Platform Host、模块依赖、共享 facts 和部署顺序，不是为了先拥有“平台”这个名字，而是多个运行模块反复遇到安装、发现、生命周期、状态与外部资源接入问题后才抽出的共享责任。与此同时，Task Truth、业务状态和模块内部诊断仍留在各自 Owner。**共享重复责任，而不是集中所有业务真值**，是这里的平台化证据。

## 检查平台化证据是否已经成立

1. 为什么 implemented candidate 不等于真实 Outcome？
2. Library 与 Platform Service 的成本边界是什么？
3. 怎样为 Multi-Agent 或 Platform 建立 Counterfactual？
4. 今天不平台化时，应该把哪些“未来重新评估条件”写进 ADR？
