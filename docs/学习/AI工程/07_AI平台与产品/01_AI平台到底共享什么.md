# AI 平台到底共享什么

> 唯一职责：解释 Model、Knowledge、Capability、Runtime、Governance、Eval 如何组合成平台责任图。

<a id="ch18-responsibility-map"></a>
## 多个应用反复承担同一责任时，平台才开始出现

一个团队只有一个 AI 功能时，把 Model Gateway、Runtime、Eval、Permission 全部抽成独立平台，往往只是提前制造依赖。真正的平台信号是：**多个产品反复遇到同一类工程责任，而且各自重复实现已经造成明显成本、风险或不一致。**

#### 本节新词

- **AI Platform（AI 平台）**：把多个 AI 应用反复需要的模型、知识、能力、Runtime、治理和评估责任做成共享服务与合同。统一模型 API 只是其中一部分。
- **Shared Responsibility（共享责任）**：跨应用重复出现、语义相对稳定、适合集中维护的工程责任。业务领域规则和最终 Outcome 通常不属于平台共享责任。
- **Responsibility Boundary（责任边界）**：明确平台与业务应用分别拥有哪类决策、State 和结果责任。边界比组件数量更能判断“是不是平台”。

```text
Interaction / Product
        ↓
Workflow / Agent
        ↓
Harness + Runtime
        ↓
Knowledge + Capability
        ↓
Model Gateway / Providers
        ↓
Infrastructure

Governance / Observability / Eval 横切所有层
```

平台的核心是 Responsibility Boundary，不是组件数量。

## Model Intelligence Layer

#### 本节新词

- **Model Intelligence Layer（模型智能层）**：平台中统一承接 Model Gateway、Provider、Routing、Reasoning Budget、Quota 与 Usage 的共享层。它分配模型计算，不拥有业务 Task。
- **Quota（配额）**：按用户、团队、租户或模型限制可使用资源的额度，用来控制容量和成本；配额不是任务优先级。
- **Usage（用量）**：模型调用消耗的 Token、请求、计算或费用记录，是计费、配额和 Economics 的输入。


提供模型调用、Reasoning budget、Provider adapter、Model Gateway、Routing、quota、usage 和健康。它回答“把哪种计算分配给谁”，不拥有业务 Task 或 Tool Permission。

## Knowledge Layer

#### 本节新词

- **Knowledge Layer（知识层）**：平台共享的知识接入、解析、索引、检索、版本和 Provenance 能力。它提供知识基础设施，但权威业务 Source 仍由对应系统拥有。


管理知识源、解析、索引、Hybrid Retrieval、Rerank、版本、权限与 Provenance。向量库是派生设施，不能替代 Git、数据库或正式文档真值。

## Capability Layer

#### 本节新词

- **Capability Layer（能力层）**：把 API、数据库、浏览器和本地执行封装成稳定 Tool/Capability Contract，并提供 Registry、Discovery、Connector/MCP 等共享机制。


将 API、数据库、浏览器和本地执行包装为稳定 Tool/Capability Contract，支持 Registry、Discovery、Connector/MCP、权限过滤和 Result/Evidence。它回答“系统能做什么”，不决定业务流程。

## Agent / Workflow Layer

#### 本节新词

- **Agent / Workflow Layer（Agent / 工作流层）**：业务应用组织 Chain、Workflow、Graph、Agent Loop 与局部 Subagent 的位置。平台可以提供基础设施，但不应强迫所有产品使用同一种 Agent 框架。


组织 Chain、Workflow、Graph、Agent Loop、Planner/Executor 和局部 Subagent。业务应用可以选择其中最简单的形态；平台不应强迫所有产品采用同一 Agent 框架。

## Harness Layer

提供 Instructions、Context Assembly、Skill、Tool surface、Workspace、Sandbox、Validator 和预算。Harness 让当前动作更容易做对，但不替代持久 Task。

## Runtime Layer

拥有 Task、State、Event、Checkpoint、Scheduler、Recovery、Idempotency、Approval 和 Truth commit。Runtime 让跨时间工作可持续、可恢复、可接管。

## Governance / Eval Layer

横切身份、权限、Policy、审计、Evidence、Tracing、Offline/Online Eval、成本与风险。治理不是“最后补日志”，而是在动作前过滤、动作中记录、动作后验证。

## Infrastructure Layer

#### 本节新词

- **Infrastructure Layer（基础设施层）**：服务、数据库、Queue、Cache、Network、Deployment、Secrets、Monitoring 和 Capacity 等传统软件基础设施。AI 系统并没有取消这些责任。
- **Secrets（密钥与敏感凭证）**：API Key、Token、证书等不应直接暴露给模型 Context 的敏感认证材料，应由受控执行层管理。
- **Capacity（容量）**：系统在给定资源下能承担的请求量、并发和吞吐能力；它与模型能力强弱是不同问题。


仍包括传统软件工程：服务、数据库、队列、缓存、网络、部署、Secrets、监控和容量。AI 没有取消这些责任，只增加概率行为、Context 和 Eval。

## Control Plane 与 Data Plane

Control Plane 管身份、配置、Policy、Registry、Task metadata、路由和治理；Data Plane 执行模型调用、Tool effect、浏览器/代码动作和数据流。二者可以共部署，但权限和故障边界应明确。

## Provider / Adapter

#### 本节新词

- **Provider（提供方）**：向平台提供模型、搜索、执行或数据能力的外部/内部服务。不同 Provider 的能力、错误和限制不应被假装完全相同。
- **Adapter（适配器）**：把 Provider 私有协议、认证、字段和错误映射到平台稳定合同的转换层。Adapter 隐藏接入差异，但不能抹掉真实语义差异。


接入层真正要做的是吸收字段差异、认证、错误和版本变化，把私有协议映射成平台合同，而不是把某个提供方的特殊概念泄漏到所有业务层。

## Platform 不应拥有的东西

#### 本节新词

- **Paved Road（铺好的推荐路径）**：平台提供的标准接入方式、默认合同和工具链，让常见场景更容易正确落地；它不是强制所有业务完全一致。
- **Guardrail（护栏）**：通过 Policy、Permission、Validator、Quota 等机制限制危险或不合规行为的硬/半硬边界。Guardrail 与业务规则不是同一层。


- 每个业务的全部领域规则；
- 所有应用的统一 Prompt；
- 一个全局万能 Memory；
- 每次 Agent 决策的业务 Owner；
- 外部系统的真实业务 State；
- 未经产品验证的抽象。

平台提供 paved road 和 guardrails，业务应用仍拥有目标、领域流程、数据意义与 Outcome。

## Multi-tenancy 与治理

#### 本节新词

- **Multi-tenancy（多租户）**：多个团队、组织或客户共享平台基础设施，同时保持数据、权限、配额、成本和 Observability 隔离的架构能力。
- **Tenant（租户）**：平台治理和资源隔离中的逻辑使用主体，可以是客户、团队或组织。
- **Cost Attribution（成本归属）**：把模型、Tool、基础设施等消耗准确归属到 Tenant / Product / Task，便于预算和优化。
- **Incident Containment（事故隔离）**：故障或越权发生时限制影响范围，避免一个租户或能力的问题扩散到整个平台。


共享平台必须处理 tenant、identity、quota、data boundary、model/tool allowlist、cost attribution、audit 和 incident containment。单机 Demo 没有这些责任，不应自称企业平台。

## 平台最容易在哪些地方失控

- 所有层塞进一个 `agent-service`；
- Model Gateway 直接修改业务 State；
- Platform 团队定义所有 Vertical Workflow；
- Tool Registry 只列函数，不记录权限与风险；
- Observability 只能看 API 成功，不能关联 Task Outcome；
- 把统一 SDK 或组件数量当成平台成熟度，却没有 Adoption 与 Outcome 证据；
- 为了“统一”抹掉不同产品的关键差异。

## Maturity Path

#### 本节新词

- **Maturity Path（演进路径）**：从单一功能、应用自有能力到共享平台的渐进演进顺序。它描述问题积累后的可能路径，不是所有团队必须走的成熟度等级。
- **Adoption（采用率）**：有多少真实产品/团队愿意并持续使用平台能力。平台内部组件很多但没有 Adoption，不能证明平台创造了共享价值。


```text
single AI feature
→ product-owned workflow / agent
→ reusable libraries and contracts
→ shared runtime/gateway/eval services
→ governed multi-product platform
```

每一步都应由重复问题和失败证据驱动。平台化不是最终必经阶段。
