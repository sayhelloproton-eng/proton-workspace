# 企业到底在招聘哪些 AI 人才

> 唯一职责：从真实 JD 归纳公司实际在构建哪些 AI 系统和责任域。  
> 样本边界：本地 job-search runtime 于 2026-08-22～23 收集职位；截至 2026-09-03 重新查询当前 `jobs` 表，`LIVE_DISCOVERY + LISTED` 口径仍为 261 条去重职位，其中 19 条有 JD 正文、18 条不少于 200 字、13 条不少于 500 字。`LIVE_DISCOVERY` 只表示由实时检索发现，`LISTED` 只表示采集时页面仍列出该职位；两者都不等于招聘方已确认职位持续开放。样本适合发现责任模式，不代表整个市场占比或长期趋势。

## 职位名称很吵，交付责任更稳定

同样叫 “AI Engineer”，一家公司可能要做 Coding Agent，另一家可能主要做推理基础设施；反过来，名字不同的岗位又可能都要求 RAG、Tool、Runtime、前后端和上线交付。只统计职位标题会把市场看成一团噪声，更有效的做法是读 JD 正文，找“这个人到底对哪段系统和 Outcome 负责”。

#### 本节新词

- **JD（Job Description，职位描述）**：公司公开描述岗位责任、能力要求和交付预期的文本。JD 是市场需求证据，不是候选人个人经历证明。
- **Responsibility Cluster（责任簇）**：把不同职位标题中反复出现、实际拥有相似系统责任的岗位归在一起。它比关键词热度更接近公司正在建设什么。
- **Job Family（岗位族）**：按长期责任和交付对象形成的一组岗位，例如 AI Application、Agent Runtime/Platform、FDE、Inference Infrastructure。
- **Outcome Ownership（结果责任）**：岗位是否对某段产品/系统最终交付和可验收结果负责，而不是只完成一个局部技术动作。

```text
AI Application / Vertical Product
Coding Agent / Developer Tools
Agent Runtime / Platform
AI Full-stack / Product Engineering
FDE / Solutions Delivery
Model / Inference Infrastructure
```

读 JD 的方法不是问“它是不是 Agent Engineer”，而是拆：它对哪段系统负责、交付什么 Outcome、需要哪些工程证据。


## 从 JD 句子还原公司正在建设的系统

#### 本节新词

- **Responsibility Mapping（责任映射）**：把 JD 中的职责句映射到 Model、Knowledge、Agent、Runtime、Product、Platform 等系统层，判断岗位真正拥有哪一段。
- **Title Noise（标题噪声）**：岗位名受招聘习惯、组织文化和营销影响产生的命名差异，不能直接用来判断技术责任。


```text
Job title noise
→ read JD responsibilities
→ identify owned system segment
→ cluster into job families
→ map to AI Engineering layers
```

真实岗位地图不是按“AI Engineer / LLM Engineer”标题分类，而是看**这个人最终对哪段系统和 Outcome 负责**。岗位标题变化快，Application、Agent、Runtime/Platform、Full-stack、FDE、Inference 等责任组合更稳定。

## 样本里能直接看到的责任

#### 本节新词

- **LIVE_DISCOVERY**：本次 job-search corpus 中表示职位由实时检索流程发现的采集状态；它只描述来源方式，不证明招聘方此刻仍开放。
- **LISTED**：采集时页面仍列出该职位的验证状态；它同样不等于招聘方官方确认“持续在招”。
- **Corpus（语料集）**：按一套采集和清洗规则形成、用于分析的一组 JD 样本。Corpus 的结论必须受采样范围和时间窗口约束。
- **Keyword Check（关键词机械检查）**：用规则统计某些词面在样本中出现次数的粗筛方法，适合发现模式，但会受到同义词和表达差异影响。


2026-08-23 的冻结 corpus 实验在这 18 条 JD 上做过一轮机械关键词检查，记录结果为：Owner / 主导 / 端到端 / 闭环 13，Full-stack / 前后端 12，AI Agent / 智能体 12，React 11，TypeScript 9，Node.js 7，测试 11，产品/体验/交互 11，RAG/知识检索 10，Tool/Function Calling 8，上下文/记忆 7，Workflow/Graph 7，Coding Agent/Codex 等代码智能体词面 7，CI/CD 6，Docker/Kubernetes/容器 6，可观测/监控/日志 6，MCP 5，显式 Evaluation/评测 3。

这些频率是当时实验产物，不伪装成 2026-09-03 重新运行同一脚本的结果：producer 保留了统计摘要，但没有保留一份可以逐字重放的同义词规则脚本。它们仍受中英文、同义词、关键词表达和小样本影响，只作责任模式路由信号。当前可现场复算的是 261 / 19 / 18 / 13 的数据库规模口径。

更重要的是完整职责。例如样本明确出现：

- AI 应用日常工程 Owner，从原型到可测试、可交付系统；
- Coding Agent 读取仓库、修改代码、运行测试和维护大型代码系统；
- Agent Harness/Runtime、状态、Graph/DAG（Directed Acyclic Graph，有向无环图）、异常恢复；
- Code/Doc/API/Runtime data 的知识体系与 IDE/CI/CD 集成；
- RAG、Tool、MCP、Context/Memory、评估和 Observability；
- ToB（面向企业客户）需求澄清、系统集成、认证权限、上线验收；
- React/TypeScript + Node/Python 的端到端产品交付。

## 这些责任在样本里怎样成团

下面只描述**样本里反复出现的工作组合**，不在这里给岗位下正式定义；下一篇 [AI 工程岗位怎样分工](05_AI工程岗位怎样分工.md) 才是岗位职责的 Canonical Owner。

### AI Application / Vertical Product

JD 里常把 Prompt / RAG / Tool / Workflow、后端接口、产品体验和上线结果放在同一责任链里。公司要的通常不是“会调用一个模型”，而是能把模型能力变成业务流程，并用真实用户路径和领域指标持续迭代。

### Coding Agent / Developer Tools

样本里出现仓库理解、代码修改、测试、IDE/Git/CI/CD、代码知识体系和研发效能。这类工作把普通软件工程与 Agent Harness 叠在一起：代码能生成只是起点，Repository / Shell / Test / Diff 才构成可验证闭环。

### Agent Runtime / Platform

另一组 JD 明确涉及 Harness、Task/State/Memory、Graph/DAG、Recovery、Gateway、Routing、Permission、Observability、高并发与高可用。这里的交付对象已经不是单个功能，而是多个 Agent / AI 应用能够长期运行的共享基础设施。

### AI Full-stack / Product Engineering

React/TypeScript 与 Node/Python 经常一起出现，职责还会覆盖流式交互、认证、文件/多模态、数据和部署。它说明很多 AI 产品岗位仍然需要从 UI 一直走到服务和上线，而不是“前端页面 + 一次模型 API”。

### FDE / Solutions / Delivery

ToB 场景里，需求澄清、系统集成、认证权限、数据边界、上线验收和客户协作会和 AI 能力一起出现。技术实现只是交付的一部分，最终还要证明能力进入了客户真实流程。

### Model / Inference Infrastructure

少数岗位更靠近训练/微调、Serving、GPU/分布式、吞吐和推理性能。它们与 Agent Platform 会共享 Gateway、Observability 等基础设施，但 Primary Ownership 落在模型生命周期和计算系统，而不是业务 AI Application。

## 标题噪声为什么不能代替正文

同样的责任可能写成 AI Engineer、LLM Engineer、AIGC 应用开发、Agent 全栈、AI 平台研发或研发效能工程师；相同标题也可能一个偏 Android 交互，一个偏 Runtime。职位名只能帮助初筛，真正的分类依据仍是 JD 正文里的交付对象、系统边界和 Outcome。

## 传统软件工程没有消失

样本反复要求前后端、API、数据库、Docker/Kubernetes、CI/CD、认证权限、监控和稳定性。AI 技能叠加在软件系统上，不替代系统设计、交付与运维。

## 样本限制

- 261 条列表只有 19 条有 JD 正文；
- 正式频率分析只使用 18 条不少于 200 字的 JD；1 条低信息文本保留为弱证据，不进入频率统计；
- 采集窗口短且以特定搜索方向为主；
- LISTED 不等于招聘方已确认在招；
- 关键词同义表达会漏计；
- 不从样本推导薪资、岗位总量或增长率。

因此本文结论是“责任模式在真实 JD 中出现”，不是市场统计报告。

## Evidence Provenance｜怎样回读和复算

#### 本节新词

- **Evidence Provenance（证据溯源）**：记录本章统计来自哪个 producer、数据库、表、过滤条件和时间窗口，使数字可以重新计算。
- **Producer-owned（生产者拥有）**：原始数据和权威统计继续由产生它的 job-search-system 仓库维护；教材只引用，不复制第二份账本。
- **Runtime Database（运行时数据库）**：job-search-system 当前运行和查询职位事实使用的数据库；复算前需要确认它的版本和时间戳。


本章使用 producer-owned job-search-system 事实，不在教材仓库复制第二份 JD 账本：

- 统计摘要：job-search-system/career-assets/resumes/experiments/2026-08-23-jd-corpus-g1/corpus-summary.md；
- 运行时数据库：job-search-system/app/db/runtime/job-search.db；
- 数据表：jobs；
- 基础过滤：origin_kind = LIVE_DISCOVERY 且 current_verification_status = LISTED；
- 有效 detail：trim(jd_text) 非空；
- 频率分析门槛：length(trim(jd_text)) 不少于 200。

复算时先确认 producer 仓库当前状态和数据库时间戳，再统计总职位、非空 JD、200/500 字门槛。若要重新计算关键词频率，必须先显式冻结新的同义词规则并保存为可重放脚本；不能拿一套临时 Regex 与 2026-08-23 的冻结统计混为同一口径。不同阈值、同义词表或采集窗口都会产生不同计数。

JD 是市场需求证据，不是候选人的个人事实；它只能决定学习和项目证据应该验证什么，不能反向创造个人经验。

## 对前七层的反向校验

真实 JD 已明确要求 RAG/Knowledge、Tool/MCP、Workflow/Agent、Harness/Runtime、Recovery、Eval/Observability 和传统全栈基础，因此这些能力都必须在教材有正式位置。Multi-Agent 在样本粗检索中不高频，说明它应作为有条件升级，而非入门主线。
