# 怎样从招聘要求反推学习路线

> 唯一职责：把 JD 能力映射回章节、学习缺口、项目证据与面试验证。

## JD 是市场证据，不是个人经历

看到一份 JD 写“熟悉 RAG、Agent Runtime、Kubernetes”，最容易犯的错是把这些词直接抄进简历，或者立刻收藏三门课程。正确做法是先问：这个岗位究竟要承担什么责任；自己目前有什么可回读 Evidence；缺口能不能通过一个真实项目补出来。

#### 本节新词

- **JD-driven Learning（JD 驱动学习，本章工作方法）**：本教材用这个名字表示“从真实职位责任反推能力缺口和项目证据”的学习方法；它不是招聘行业统一术语。
- **Capability Gap（能力缺口）**：目标岗位责任所要求的能力，与当前已有 Evidence 之间的具体差距。Gap 必须能转成可执行学习任务。
- **Career Fact（职业事实）**：由真实工作、项目、代码、绩效或其他可验证来源支持的个人经历事实。JD 只能说明市场需要什么，不能生成 Career Fact。

```text
JD sentence
→ responsibility
→ system layer
→ required capability
→ current evidence / gap
→ learning action
→ project proof
→ interview story
```

JD 是市场证据，不是个人事实。不能因为职位要求某项能力，就把它写成已有经历。

## 先拆 Hard Gate

#### 本节新词

- **Hard Gate（硬门槛）**：缺失时通常直接阻断申请或进入下一轮评估的条件，例如地点、工作授权、学历或关键经验。它与可通过学习补齐的 Skill Gap 不同。
- **PASS / RISK / BLOCK / UNKNOWN**：对 Gate 的四种状态标记：明确满足、存在风险、明确不满足、证据不足待确认。


地点、学历、年限、语言、领域、工作授权和强制技术栈先标 `PASS/RISK/BLOCK/UNKNOWN`。硬门槛与技术学习缺口不同；真正 BLOCK 可否决申请，UNKNOWN 需要定向确认。

## 再拆责任而非关键词

#### 本节新词

- **Responsibility Decomposition（责任拆解）**：把 JD 中的自然语言职责拆成 Outcome、System Layer、Capability 和 Evidence Requirement。
- **DAG（Directed Acyclic Graph，有向无环图）**：没有环路依赖的有向图，常用于表达任务依赖；JD 出现 DAG 不等于岗位一定在做 Agent。


例如 JD 写：

> 建设 Agent Harness / Runtime，完善工具调用、上下文与记忆、状态管理、Graph/DAG、异常恢复。

这里的 DAG（Directed Acyclic Graph，有向无环图）通常用来表达不存在循环依赖的任务图。

它映射到：

```text
02 Tool/Capability
03 Workflow/Agent Loop
04 Harness/Runtime/State/Recovery
06 Eval/Observability
07 Platform
```

不是“会 LangChain”一个关键词可以覆盖。

## Capability Map

#### 本节新词

- **Capability Map（能力地图，本章工作表）**：把 JD Responsibility 映射到教材层、当前证据、Gap 和应有项目 Evidence 的结构化视图，用来组织学习决策，不把它伪装成行业统一模型。
- **System Layer（系统层）**：Model、Knowledge、Capability、Agent/Workflow、Runtime/Harness、Platform 等责任所在的架构层，用来判断同一个技术词实际服务什么问题。


| JD 责任 | 教材层 | 应有项目证据 |
|---|---|---|
| RAG/知识库/代码检索 | 02 | 多检索器、版本/权限、RAG Eval |
| Tool/Function Calling/MCP | 02 | schema、授权、副作用、错误合同 |
| Workflow/Graph/Agent | 03 | 架构选择、动态路径、停止条件 |
| State/Memory/Recovery | 04 | durable Task、Checkpoint、UNKNOWN 对账 |
| Multi-Agent/Handoff | 05 | Owner、Shared State、增量 Eval |
| Browser/Coding/Sandbox | 06 | 真实环境、回读、Trajectory/Evidence |
| Eval/Observability/Cost | 06 | Failure Slice、Trace、cost per success |
| Gateway/Platform/Governance | 07 | 跨应用合同、SLO、权限和 adoption |
| Full-stack/部署 | 07/08 | UI→API→data→deploy→Outcome |

## 项目证据沿用前面的 Evidence Ladder

Platformization 章已经区分 Idea、实现候选、测试、集成环境、真实 Effect 等证据层级。求职时直接沿用这条纪律：学习笔记和 Toy Demo 可以证明理解，Tested Project 可以证明实现和局部验证，Integrated Environment 更接近真实系统，Real Outcome 才能证明外部结果。

```text
学习笔记 < toy demo < tested project
< integrated environment < real user/business outcome
```

简历和面试只描述自己真正到达的层级，同时说明未验证边界。这样既不会把课程学习包装成生产经验，也能清楚看见下一步还缺什么。

## 当前证据边界示例

#### 本节新词

- **Evidence Boundary（证据边界）**：明确当前事实最多能证明到什么程度，以及哪些能力仍缺少生产、真实用户或外部 E2E 证据。
- **Strength Profile（能力强弱画像）**：按已有 Evidence 而不是自我感觉描述不同能力的相对强弱，用来选择更真实的求职方向。

本章于 **2026-09-03** 重新回读 producer 仓库 `job-search-system/career-assets/FACTS.md`、`PROFILE.md`、`SKILLS.md`。其中 canonical 职业事实的 foundational baseline 标记为 **2026-08-22**；下面的画像只描述这些 producer-owned Evidence 当前支持到哪里，不会把 JD 需求反写成个人经历。

按这组事实，复杂前端/云平台、Developer Tools、Coding Agent/Skill/Plugin、Context/Eval 与工程治理证据强；Node/全栈中强；Agent Runtime/Recovery 在个人项目中中强；模型训练、RAG 生产和推理基础设施较弱；无正式人员管理强证据。

因此合理路线是强化 Agent Application / Developer Tools / Full-stack Platform 交叉，而不是把自己包装成模型训练专家。该判断来自事实库，不来自 JD 愿望。

## 从 Gap 到学习任务

#### 本节新词

- **Learning Action（学习行动）**：为了填补某个 Gap 而设计、最终能产出 Artifact/Evidence 的具体任务，例如实现 Hybrid Retrieval 并运行真实查询集。


Gap 要写成可验证任务：

```text
弱：学习 RAG
强：实现 Vector+Keyword+Git hybrid retrieval，
    建立 30 个真实查询集，按 recall/rerank/citation freshness 评估
```

```text
弱：学习后端
强：实现带 auth、queue、idempotency、observability 的 Node/Python service，
    部署并记录 SLO/故障恢复
```

## 从项目到 Evidence Card

#### 本节新词

- **Evidence Card（证据卡，本章工作模板）**：把一个项目的 Problem、Ownership、Constraint、Decision、Artifact、Validation、Result 和 Limitation 组织成可回读材料，方便简历与面试使用；它不是行业标准格式。
- **Limitation（限制 / 未完成边界）**：项目当前还不能证明、尚未验证或只在特定条件成立的部分。明确 Limitation 比夸大成熟度更可信。


每个项目故事至少包含：问题、责任边界、约束、设计选择、实现、验证、结果、失败/限制、可回读 Artifact。区分本人 Ownership 与协作范围，数字说明统计口径。

## 评分不是 Offer 概率

#### 本节新词

- **Confidence（置信度）**：对岗位信息、匹配判断或证据完整程度有多确定的标记。高分但低 Confidence 的岗位不应被当成确定机会。
- **Offer Probability（Offer 概率）**：获得录用的真实概率；简单岗位匹配评分无法可靠估计它。


可按核心职责、必备技术、项目/领域、Senior Ownership、方向价值和实际吸引力评分，并附 Confidence。低置信高分不应压过高置信稍低分；岗位匹配是时间优先级工具，不是成功概率预测。

## 学习优先级

#### 本节新词

- **Learning Priority（学习优先级，本章排序方法）**：把 JD Responsibility 的重复程度、当前 Evidence 缺口和目标方向价值放在一起，决定有限时间先补什么。
- **Core Trunk（主干能力）**：跨多个目标岗位反复需要、并支撑更高层 AI 能力的基础，例如 Backend、API、Database、Deployment、RAG/Eval、Runtime/Observability。


```text
真实 JD 高频 × 当前证据弱 × 与目标方向高相关
```

优先补主干，例如后端服务、RAG/Eval、Runtime/Observability；低频前沿词若没有责任上下文，不应抢占主线。Multi-Agent 应在单 Agent/Runtime 有可靠基线后再补。

## 面试验证

#### 本节新词

- **Interview Proof（面试证明材料）**：能在面试中回到具体代码、Artifact、Decision、Test、Deployment 或 Outcome 的证据，而不是只背概念答案。
- **Resume Version（简历版本）**：针对某一岗位使用的确切简历快照；面试准备必须与实际投递版本和 JD 对齐。


面试准备使用确切 JD、确切简历版本和 Evidence：

- 为什么选 Workflow 而非 Agent；
- 如何区分 State/Context/Memory；
- Timeout 后怎样避免重复副作用；
- 如何评估 RAG/Agent；
- 平台化的触发证据；
- 项目中哪些真实完成、哪些仍需外部 E2E。

## 反向校验教材

若多份真实 JD 反复要求教材中没有的责任，应回到 01～07 补正式位置；若某章内容在真实系统和岗位里找不到 Outcome/Evidence，应重新判断它是主干、选修还是热点。

## 从 JD 反推能力时最容易自我欺骗的地方

- 把 JD 要求复制成简历技能；
- 只按岗位名选学习路线；
- 用项目组件清单代替责任和结果；
- 把自动测试写成生产上线；
- 为提高匹配度虚构 RAG/训练/管理经验；
- 只追新词，不补 API、数据库、部署、稳定性主干。

## 检查能力图能否回到项目证据

1. 为什么 JD 是市场证据而不是个人事实？
2. 一个 Capability Gap 怎样改写成可验证学习任务？
3. 项目证据为什么必须注明验证层级？
