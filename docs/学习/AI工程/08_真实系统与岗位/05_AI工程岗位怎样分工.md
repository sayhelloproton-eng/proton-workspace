# AI 工程岗位怎样分工

> 唯一职责：比较岗位族的系统边界、主要产出、共同主干与差异能力。

## 四类岗位共享主干，主要 Ownership 不同

两个工程师都可能写 React、调用模型、接 Tool，但一个主要对业务 AI Outcome 负责，另一个可能对 Runtime 的恢复和可靠行动负责。岗位边界不是看“会不会某个技术”，而是看失败时谁必须把哪一段系统闭环。

#### 本节新词

- **Primary Ownership（主要责任）**：一个岗位对哪一段系统结果承担首要推进和闭环责任。岗位可以协作、能力也会重叠，但失败时应能定位谁必须把这一段收口。
- **SWE（Software Engineer，软件工程师）**：负责系统设计、接口、数据、测试、部署和运维等软件工程主干；AI 岗位是在这条主干上增加模型不确定性相关责任。

```text
AI Application Engineer  对一个业务 AI Outcome 负责
Agent Engineer           对动态决策与可靠行动闭环负责
AI Full-stack Engineer   对用户体验到服务/AI 集成的端到端交付负责
AI Platform Engineer     对多个应用共享的 AI 工程底座负责
```

四者高度重叠。岗位族不是身份标签，而是主要 Ownership 落在哪一段。

## 共同主干先别丢

四类岗位都建立在软件工程上：模型 API 与结构化合同、Tool、Data/Permission、测试/Eval、调试和证据，再加 React/TypeScript 等前端工程、Node/Python 服务、数据库、部署、监控与跨团队协作。差别主要是这些能力最终服务哪一个 Primary Ownership，而不是四套完全独立的技能树。

## AI Application Engineer

#### 本节新词

- **AI Application Engineer（AI 应用工程师）**：主要负责把模型、Knowledge、Tool、Workflow 和产品交互组合成可验收业务 AI Outcome 的工程角色。


### 主要问题

模型能力怎样解决具体业务问题，并以可用体验、稳定流程和可测 Outcome 上线？

### 责任范围

需求澄清、Prompt/Context、RAG、Tool、Workflow、产品接口、Domain Eval、上线迭代。通常调用现有模型/平台，不主攻底层训练。

### 产出证据

从用户目标到业务效果的完整链、失败 Slice、质量/成本指标、领域系统集成。

## Agent Engineer

#### 本节新词

- **Agent Engineer（Agent 工程师）**：主要负责动态决策、Tool 行动、Runtime/Harness、State/Memory、Recovery 和 Agent Eval 的可靠闭环。


### 主要问题

当路径必须动态改变时，怎样让 Agent 可行动、可恢复、可验证？

### 责任范围

Agent Loop、Tool/Skill、Planner/Executor、Context、Task/State/Memory、Harness、Sandbox、Recovery、Trajectory Eval；必要时 Subagent/Multi-Agent。

### 产出证据

真实环境任务、受控副作用、Checkpoint/Resume、Evidence、成功率与关键错误改进。

## AI Full-stack Engineer

#### 本节新词

- **AI Full-stack Engineer（AI 全栈工程师）**：从 UI/交互跨到后端 API、Data、模型/Tool 接入和 Deployment 的端到端产品工程角色。全栈不等于一个人必须拥有所有基础设施。
- **Integration（集成）**：把前端、服务、模型、Tool、Database、Auth 等独立组件通过稳定合同接成可运行产品的工作。


### 主要问题

怎样把 AI 交互、前端、后端、数据、模型与部署接成可交付产品？

### 责任范围

React/Vue/Next、流式 UI、Node/Python API、文件与多模态、认证权限、Tool/Model integration、数据库、部署与可观测。重点是端到端而非每层都深入。

### 产出证据

可运行产品、用户流程、前后端合同、部署、错误处理与迭代速度。

## AI Platform Engineer

#### 本节新词

- **AI Platform Engineer（AI 平台工程师）**：主要负责多个 AI 应用共享的 Model Gateway、Knowledge/Capability、Runtime、Governance、Eval 和 Multi-tenancy 底座。


### 主要问题

多个 AI 应用反复需要的 Gateway、Runtime、Knowledge、Capability、Eval 和 Governance 怎样共享？

### 责任范围

Provider Adapter、Model Gateway、Routing、Tool/MCP、Runtime、Identity/Permission、multi-tenancy、Observability、Eval Infrastructure、成本与可靠性。

### 产出证据

平台合同、跨应用 adoption、SLO（Service-Level Objective，服务目标）、成本归因、故障隔离、版本兼容和产品交付增益。

## 相邻岗位会和这四类责任交叉

- FDE / Solutions 更靠近客户现场、发现和集成交付；
- LLM / Inference Infra 更靠近训练、Serving、GPU、性能和分布式系统；
- Developer Tools / Coding Agent 横跨 Agent、Platform 与研发效能；
- AI Product Engineer 在一些公司里会把 Application 与 Full-stack 合并。

这些名字都不是硬分类。遇到具体岗位仍然回到 JD 正文确认 Primary Ownership。

## 边界不是墙

小团队可能一个人跨 Application/Full-stack/Agent；大组织会拆分。判断重点是：谁对最终 Outcome 负责、谁拥有 Runtime truth、谁运营共享服务、谁承担生产故障。

## 前端背景怎样把 Ownership 扩到 AI 系统

复杂前端已经积累了产品体验、状态、交互、工程化和平台意识。向 AI 工程扩展时，关键不是把这些经验清零，而是补上长期运行的后端责任：HTTP/API、Node/Python service、Database、Queue、Auth，再向 RAG、Tool、Runtime、Eval、Observability 和 Deployment 延伸。

```text
HTTP/API + Node/Python service
→ database / queue / auth
→ RAG / Tool / Agent
→ Runtime / Eval / Observability
→ deployment / reliability
```

目标是把原来主要落在 UI 的 Ownership 扩展成可验证的端到端 Outcome。

## 常见误判

- 会调用 LLM API 就自称 Agent Engineer；
- 做过聊天 UI 就自称 AI Full-stack；
- 写一个 Gateway 就自称 Platform Engineer；
- 用 Multi-Agent Demo 替代 Runtime/Eval；
- 把模型训练要求和应用工程混成一套能力表；
- 把技术 Owner 写成人员管理者。

## 选择岗位的责任问题

1. 日常主要交付用户功能、Agent 系统、端到端产品还是共享平台？
2. 谁拥有后端、部署和生产故障？
3. 是否要求训练/Serving，还是调用现有模型？
4. Eval 是业务效果、Agent trajectory 还是模型 Benchmark？
5. 成功按产品 Outcome、平台 adoption 还是基础设施 SLO 衡量？
