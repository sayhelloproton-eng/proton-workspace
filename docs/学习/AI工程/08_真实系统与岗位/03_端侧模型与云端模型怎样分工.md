# 端侧模型与云端模型怎样分工

> 唯一职责：验证端侧模型、云端控制、FAST/REASON 与资源调度的真实架构取舍。

## 一块推理资源被多个任务争用时，先解决调度

一台手机或边缘设备可能一次只能稳定跑一个模型，而业务又同时有高频简单判断和少量复杂任务。如果只讨论“端侧模型还是云模型谁更强”，会漏掉真正的工程问题：谁先执行、什么时候升级、模型切换要付多少成本、设备离线怎么办。

#### 本节新词

- **Edge / On-device Model（端侧模型）**：运行在用户设备或本地边缘环境中的模型，常用于低延迟、隐私敏感或离线任务。端侧不自动等于更便宜，仍有设备、能耗和维护成本。
- **Cloud Model（云端模型）**：通过远端服务提供推理能力的模型。它通常拥有更弹性的计算和更强模型选择，同时引入网络、数据边界和调用成本。
- **Provider Adapter（提供方适配器）**：把端侧和云端不同调用协议、错误和能力映射成统一接口，同时保留各 Provider 的真实限制。

Resource Scheduling、Model Routing 和 Scheduler 已在前面的 Routing 章定义。本章直接把它们落到“一块设备资源只能有限并发”的端云场景。

```text
Cloud / Local Controller
  ↓ task + mode=auto + priority + deadline
Provider Adapter
  ↓
Priority Queue → single Worker / lease
  ↓ FAST or REASON model
Result + metrics + evidence
  ↓
Runtime validates and continues
```

端侧模型提供推理能力，不拥有 Task、Permission 或业务 Truth。

## 为什么端侧

#### 本节新词

- **Data Locality（数据本地性）**：数据在产生或存储位置附近完成计算，减少跨网络传输和数据暴露。它是端侧价值之一，不等于绝对隐私。
- **Offline Inference（离线推理）**：没有网络连接时仍能在设备本地完成模型推理。
- **Thermal / Energy Constraint（散热 / 能耗约束）**：移动与边缘设备受温度、功耗和电池影响的资源边界，可能限制持续吞吐。


可能价值：数据本地性、离线、低边际成本、可控设备和低网络依赖。代价：内存/算力受限、模型切换慢、容量小、更新与健康复杂。是否使用必须由真实延迟、质量和隐私证据判断。

## FAST / REASON 与 Priority Queue 在端侧怎样落地

FAST / REASON、Priority Queue、Aging、Lease、Cancellation 的完整定义都属于 [任务怎样选择模型和路径](../04_Harness与Runtime/05_任务怎样选择模型和路径.md)。这里不再建立第二套术语，只看设备约束会怎样改变它们。

如果端侧一次只能稳定运行一个模型，队列至少要记录 `task/job id、mode、priority、deadline、enqueue time、required capability、cancellation state`。高优先级可以先行，但等待时间要进入 aging；同一 Task 的重复 Job 要去重；Deadline 过期就停止；设备离线必须返回明确状态。

若产品提供 `AUTO` 模式，它只应是 Policy 的一个入口：根据 Task metadata、Risk、Validator 和历史 Slice Evidence 选择 FAST、REASON、Edge 或 Cloud。`AUTO` 不是行业标准档位，也不能把模型自报 confidence 当成唯一升级依据。

## Model Switching

#### 本节新词

- **Model Switching（模型切换）**：在同一设备上卸载/加载不同模型或权重 Profile 的过程，可能带来加载延迟和内存峰值。
- **Model Checkpoint（模型权重检查点）**：可加载的一组模型权重版本，与 Durable Execution 的 Task Checkpoint 不是同一个对象。
- **Batching（批处理）**：把多个兼容请求组合执行以提升吞吐。批处理不能破坏 Deadline、Priority 和公平性。


如果 FAST 和 REASON checkpoint 不能同时驻留，切换会产生加载延迟与内存峰值。调度可在 deadline 允许时批处理相同 mode，但不能让吞吐优化破坏业务优先级。

## Cloud 与 Edge 的责任

#### 本节新词

- **Controller（控制器）**：拥有 Task、Policy、用户权限、全局路由和结果提交的上层控制主体。它决定“该做什么”，不直接等于模型 Provider。
- **Edge Provider（端侧提供方）**：负责模型加载、推理、设备健康、局部 Queue 和 Usage Telemetry 的设备执行边界。
- **Usage Telemetry（使用遥测）**：记录模型加载、推理时间、内存、能耗和调用量等运行数据，用于调度与 Economics。


Cloud/Controller 拥有 Task、Policy、用户权限、全局路由和结果提交；Edge Provider 拥有模型加载、推理、资源健康、局部队列和 usage telemetry。上层可以依赖 URL、Capability、Profile 等稳定合同，但 Provider 返回的仍只是建议或结果，必须由 Controller 验证后才能改变业务 State。

## 端侧不可用时，回退云端仍然是一次受治理的路线变化

Fallback 的通用语义已经由 Routing 章负责。端云场景额外要记录的是 **Provider Change（提供方切换）**：从 Edge 切到 Cloud 后，数据是否允许离开设备、成本是否变化、模型行为是否变化，以及旧端侧 Job 是否仍可能迟到返回。

因此端侧不可达、模型未就绪或质量不足时可以回退云端，但不能让两条路径同时推进同一高副作用任务。换 Provider 也不会自动扩大 Permission。

## 怎样证明端云调度真的更好

沿用 Eval / Economics 章的指标框架，端云方案至少要补充真实设备上的 queue wait、model load、inference latency、peak memory、energy/thermal、deadline miss、upgrade/fallback rate，以及各 Failure Slice 的成功率。

如果只证明“这个模型单次推理很快”，却没有把排队、加载、切换和云端回退算进去，就不能推出端到端方案更快或更便宜。

## 端云协同最容易失真的地方

- FAST 永远优先导致 REASON 饥饿；
- 多进程同时加载模型导致资源争用；
- Provider 根据结果直接推进 Task；
- Timeout 后重复同一高成本 job；
- 云端 fallback 未检查数据边界；
- 用模型自报 confidence 代替 Validator；
- 把本地 package test 写成真实设备负载 PASS。

## 先用硬约束决定留在端侧还是升级

先用单 Provider/单模型建立基线。只有任务 Slice 显示质量/延迟分层、设备资源确实受限时才引入 FAST/REASON 与队列。再用真实设备测量证明端侧相对云端的价值。

## 检查每次端云切换是否可解释

1. FAST/REASON 是模型身份还是路由策略？
2. Priority Queue 为什么需要 aging 与 idempotency？
3. Edge Provider 为什么不能拥有业务 Task？
4. 哪些指标才能证明端侧方案值得？
