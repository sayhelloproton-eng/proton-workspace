# 小模型怎样进入垂直业务

> 唯一职责：解释小模型为什么适合作为规则/检索与强推理模型之间的**高频语义执行层**，以及怎样通过结构化合同、验证、路由、端侧部署和必要的模型适配，把大量重复 AI 工作变得更便宜、更快、更私密、更高吞吐；Fine-tuning 只是后段手段，不是本章主角。
> 读完要能回答：哪些 AI 工作值得交给小模型长期高频执行，怎样证明它比“所有请求都进强模型”更便宜、更快、更可靠，并知道什么时候必须升级？

## 先看一个每天都会重复上万次的任务

#### 本节新词

- **SLM（Small Language Model，小语言模型）**：相对当前通用大模型更小、资源需求更低的语言模型。工程上是否算“小”，取决于目标任务、设备、延迟和质量门槛，不用固定参数量一刀切。
- **Semantic Worker / Model Worker（语义工作单元 / 模型工作单元）**：让模型承担分类、抽取、改写、路由等边界收紧的高频语义责任。它是 Runtime 管理的软件组件，不等于独立 Agent。
- **Throughput（吞吐量）**：单位时间内系统能够完成的合格任务数量。小模型的“高输出”首先指更高任务吞吐，不是生成更多文字。

Cost per Success 和 Baseline 已在 Economics / Platformization 章节定义。这里直接沿用：小模型是否值得，不看“参数更少”这个标签，而看它有没有让真实任务的质量、延迟、成本和人工形成更好的组合。


假设一个客服入口每天要处理上万条消息。大多数请求只是识别意图、抽取订单号、补齐 Tool 参数、归一化状态，再决定进入退款、查询还是人工路径。若每一步都调用最强推理模型，系统付出的不仅是单次 Token 价格，还包括更长延迟、更低吞吐，以及长尾生成给验证和治理带来的额外成本。

这里把小模型放在一段边界收紧的语义执行工作上：**把大量高频、受控、可验证的任务，从昂贵的通用推理路径里拆出来。**

它特别适合承担：分类、抽取、Query 改写、Tool 参数生成、结果归一化、Context 压缩、简单总结、路由、页面/日志状态识别、低风险局部判断等高频责任。大模型则保留给开放研究、复杂规划、跨领域推理和长尾异常。

```text
规则 / SQL / Embedding
      ↓ 纯确定或近确定任务
Small Model / Specialized Model
      ↓ 高频语义任务：快、便宜、可本地化
Validator / Policy / Runtime
      ├─ PASS → 提交结果
      └─ uncertain / hard / risky
                    ↓
          Strong / Reasoning Model
                    ↓
               Human if needed
```

小模型**不天然减少 Token 数量**。Token Count 先由具体 Tokenizer、Chat Template 和输入文本决定；如果两个模型使用不同 Tokenizer，同一段文字的 Token 数甚至可能不同。参数量变小只会改变每个 Token 背后的计算规模，不会直接把文字“压成更少 Token”。Small-first 真正能压缩的是强模型调用次数和送入强模型的上下文量：先分类、过滤、抽取和压缩，让强模型只处理真正需要高智能预算的请求。

因此这里的“高输出”指同样硬件预算下完成更多合格任务：吞吐更高、首响应更快、并发更多，最终降低 Cost per Success。

这也改变了垂直化工程的起点。直接走下面这条路通常既贵又难评估：

选择模型 → 收集数据 → 直接调优

更稳妥的路线从任务合同开始：

定义 Outcome 和边界
→ 把输入变成明确的软件输入合同
→ 把输出收敛为可机器检查的结构合同
→ 用确定性软件验证，不合格就拒绝或升级
→ 建立最便宜 Baseline
→ Prompt / Few-shot
→ RAG / Tool / Workflow 把知识、事实和确定路径移出模型
→ 收缩任务并设计路由与“小模型优先、难例升级”的级联路径
→ 仍有稳定 Failure Slice 才进入模型适配
→ 必要时蒸馏、持续预训练或全参数训练
→ 量化与目标硬件验证
→ 持续 Eval 和版本治理

其中最容易被低估的一步是：**结构化输入、结构化输出、确定性验证。** 它们几乎不增加模型训练成本，却能直接减少歧义、格式漂移、不可判定结果和线上失控，是垂直化最先应该拿到的工程收益。

## “小”由任务和部署约束共同定义

#### 本节新词

- **SLO（Service-Level Objective，服务级目标）**：对延迟、可用性、成功率或吞吐等服务质量设定的目标。模型大小必须和任务 SLO 一起讨论。
- **Multi-Model System（多模型系统）**：同一 Runtime 根据任务选择多个不同模型/模型档位的系统。模型数量增加不等于 Agent 数量增加。
- **Specialized Model（专用模型）**：围绕特定任务或领域优化的模型，可以是原生小模型、微调模型或蒸馏模型；专用不意味着拥有独立身份和 State。
- **Capability（能力）**：系统可调用的一项功能责任；一个专用模型可以只是 Capability，而不是 Agent。


“小模型”不是固定的 1B、3B、7B 或 14B 参数分界。工程上更有用的定义是：

> 在目标硬件、延迟、成本、隐私和质量约束下，能够通过该任务 Eval 的最小模型。

同一个 7B 模型：

- 对手机端离线抽取可能太大；
- 对服务器端客服分类可能已经很小；
- 对开放式科研推理又可能能力不足。

所以模型大小只能和任务、硬件与 SLO（Service-Level Objective，服务目标）一起讨论。

更重要的是，小模型的工程位置不是“缩小版 ChatGPT”，而更像一组受 Runtime 管理的 **Semantic Worker（语义工作单元）**。这里的 Semantic Worker 是本教材的心智模型称呼，不是行业协议名：

```text
                ┌→ Intent / Classification
                ├→ Extraction / Normalization
                ├→ Query Rewrite / Retrieval Triage
Request → Router├→ Tool Selection / Argument Fill
                ├→ Context Compression
                ├→ Environment State Classification
                └→ Simple Draft / Summary
                         ↓
                 Schema + Validator
                         ↓
             accepted / escalate / reject
```

这些工作往往具备四个共同特征：

1. 调用次数多，成本会被规模放大；
2. 输出空间小，可以用 Schema、枚举和 Validator 收紧；
3. 成功标准可以离线 Eval；
4. 错误可以安全拒绝或升级，而不是必须赌一次开放生成。

于是一个重要架构判断出现：**未来很可能是 Multi-Model（多模型）系统，但不一定是 Multi-Agent（多智能体）系统。** 一个 Runtime 下面可以挂多个专用小模型，它们只是 Model Worker / Capability；只有当身份、权限、State、生命周期和责任真正独立时，才需要升级成 Agent。

## 从软件收敛走到模型适配

不要把“垂直化”直接翻译成 Fine-tuning。先把责任一层层从开放问题里剥出来：确定逻辑交给 Code / Rule / SQL；实时知识交给 RAG / Database；真实动作交给 Tool；固定路径交给 Workflow；权限和高风险门禁交给 Runtime / Policy。剩下那段**仍然需要语义判断、调用频繁、输出可验证**的工作，才是小模型真正值得接手的责任。

如果现成小模型在这个责任上已经达到门槛，就停在 Prompt、Few-shot 和路由；如果仍有稳定、可复现、业务重要的失败，再考虑 PEFT、蒸馏或继续预训练。Failure Slice、Escalation 和 Baseline 都沿用前面 Eval / Routing 章节的定义，本章不再为它们建立第二套术语。

这也说明“小模型优先”不是模型崇拜：它是一种调用结构。简单请求在低成本层结束，复杂或高风险请求升级到更强模型或人工；模型层级可以很多，但 Agent 责任主体不必跟着变多。

## 第一原则｜先把问题变成结构化、可验证的软件合同

#### 本节新词

- **Input Contract（输入合同）**：规定模型可以依赖哪些字段、单位、枚举、来源和缺失值的结构化输入边界。它负责减少输入歧义。
- **Structured Outputs（结构化输出）**：要求模型按指定字段和类型返回结果，使后续软件可以稳定解析和检查。
- **Schema（模式）**：描述字段、类型、枚举和结构约束的机器可读合同；Schema 合法不等于业务语义一定正确。
- **Deterministic Validator（确定性验证器）**：用普通代码、规则或权威来源检查输出是否可接受的组件；它不让模型更聪明，而是让错误更早暴露。
- **OOD（Out-of-Distribution，分布外）**：输入明显偏离训练/验证数据常见分布的情况。OOD 样本通常应拒答、升级或人工处理，而不是强迫小模型猜。
- **Normalization（归一化 / 规范化）**：在模型前把单位、枚举、格式、时间顺序等确定性差异整理成统一表示。


贯穿本章用一个设备故障工单任务：输入最近 20 条告警、运行指标和维修记录，输出故障类别、证据和下一步工单路由；信息不足必须拒答，模型不能直接控制设备。

第一版通常先把模糊自然语言收敛成两个合同，再判断训练是否必要。

先把输入合同落到具体字段：设备型号、时间窗口、告警列表、指标摘要、维修记录引用、允许缺失字段和来源版本。日志清洗、单位统一、枚举映射、时间排序这些确定工作尽量在进入模型前完成。

```json
{
  "device_model": "PX-7",
  "alarms": ["E102", "TEMP_HIGH"],
  "temperature_c": 92.4,
  "pressure_kpa": 318,
  "maintenance_refs": ["WO-8821"]
}
```

**Structured Outputs（结构化输出）**再限制模型只交付系统真正需要的字段，而不是一段“看起来很专业”的自由文本：

```json
{
  "fault_type": "bearing_overheat",
  "evidence": ["TEMP_HIGH", "WO-8821"],
  "confidence": 0.86,
  "needs_human": false
}
```

最后必须有 **Deterministic Validator（确定性验证器）**：检查 `fault_type` 是否属于允许枚举、Evidence 是否真的来自输入、危险类别是否强制人工、必填字段是否齐全、置信或 OOD 门槛是否触发升级。Validator 不负责“让模型更聪明”，它负责让错误更早、更便宜、更明确地暴露。

因此最先应该建立的是：

```text
Raw input
→ Normalize / Structure
→ Model
→ Structured Output
→ Deterministic Validator
├─ PASS → downstream system
└─ REJECT / ESCALATE → stronger model / human
```

这套结构有三个高收益：输入噪声减少，输出可测试，失败可以被分类。只有这三件事成立，后面的 Prompt、RAG、Router 或 Fine-tuning 才有可靠 Baseline；否则训练很容易只是在拟合一个定义不清的问题。

## 小模型在系统里的位置｜高频语义执行层

#### 本节新词

- **Classifier / Router（分类器 / 路由器）**：识别意图、风险或任务类型，并把请求送到有限路径；Router 的决定仍要受 Policy/Validator 约束。
- **Extractor / Normalizer（抽取器 / 归一化器）**：从自然语言、日志或文档中提取字段并转成软件可消费的标准形式。
- **Tool Caller（工具调用工作单元）**：在有限 Tool 集中选择能力并生成参数；它不拥有 Tool Permission。
- **Context Worker（上下文工作单元）**：承担 Query Rewrite、证据筛选、压缩和局部总结，减少强模型看到的无关 Context。
- **Environment Interpreter（环境解释器）**：把 DOM、日志、测试或页面状态转成受控 Observation，不替代原始 Evidence。
- **Domain Worker（领域工作单元）**：只在窄领域任务上执行高频判断，例如故障分类或合同字段抽取。
- **Draft Worker（草稿工作单元）**：生成低风险、短、可验证的候选文本或摘要；正式发布仍由上层流程决定。


把小模型理解成“小一点的聊天机器人”会低估它。真实系统里更有价值的角色，是把自然语言、日志、页面、文档和用户意图转换成**后续软件可以消费的结构化中间结果**。

上面的七类 Worker 不要求一一部署成七个模型。一个模型可以承担多类窄任务，也可以按硬件、领域和风险拆成多个 Capability；是否拆分由 Eval、吞吐和治理成本决定。

关键边界是：

```text
完全确定的逻辑
→ Code / Rule / SQL

需要语义理解，但任务边界小、输出可验证
→ Small / Specialized Model

开放世界、复杂规划、跨领域推理、长尾异常
→ Strong / Reasoning Model

高风险最终决策
→ Policy / Domain Expert / Human Approval
```

小模型不是把确定性代码“AI 化”。相反，最好的位置通常是**确定性软件包住概率模型**：输入由软件收敛，模型只做难以手写规则的语义映射，输出再被软件验证。

## 真实业务场景一｜客服与运营：大部分请求其实不值得进强模型

#### 本节新词

- **Intent（意图）**：用户当前希望完成的业务目的，例如物流查询、退款或投诉；它与用户措辞本身不同。
- **Intent Accuracy（意图准确率）**：模型把请求分到正确业务意图的比例，是客服小模型比“回答像不像人”更重要的基础指标。
- **Routing Error Cost（错误路由成本）**：把任务送错 Workflow/Agent/Human 后产生的返工、延迟或风险，用来决定分类门槛和升级策略。
- **Escalation Rate（升级率）**：进入强模型或人工路径的请求比例；越低不一定越好，错误拒绝升级会伤害可靠性。


一个客服入口收到用户自然语言：

> “昨天买的那个空气炸锅还没发，帮我看看，要是不行就退了。”

如果所有请求都直接交给强模型，模型既要识别意图、抽订单号、判断物流状态、选择 Tool、解释政策、生成回复。这里真正需要开放推理的比例可能并不高，大量步骤是高频、受控的。

更合理的链路是：

```text
用户消息
↓
Rule / Parser：订单号、显式敏感字段
↓
Small Model
- intent = shipping_delay
- requested_action = inspect_then_refund
- sentiment = frustrated
- missing_fields = [order_id]
↓
Validator
↓
Tool：读取订单 / 物流 / 售后政策
↓
Workflow / Policy
├─ 常规路径 → 模板或小模型生成短回复
└─ 政策冲突 / 高金额 / 特殊投诉 → Strong Model / Human
```

小模型的价值在于把海量自然语言入口压成有限业务状态，同时把真正复杂的模型调用留给少数异常请求。

这里最关键的 Eval 不是聊天是否“像真人”，而是：Intent Accuracy、字段抽取正确率、错误路由成本、升级率、人工处理时间和 Cost per Success。

## 真实业务场景二｜RAG：先把 30 页证据变成强模型真正需要的 3 页

#### 本节新词

- **Structured Compressor（结构化压缩器）**：把长 Evidence 候选压缩成实体、数字、结论和来源引用等结构字段，降低强模型 Context 成本。
- **Derived Artifact（派生产物）**：由原始 Evidence 经过摘要、压缩或转换生成的二次对象；它可以辅助推理，但不应覆盖原始 Source。
- **Evidence Anchor（证据锚点）**：能从压缩结果回到原始文档位置、引用或 ID 的稳定指针，用于验证没有因压缩丢失事实。


RAG 系统最浪费的地方之一，是把大量候选 Chunk 原样塞给强模型，再希望它自己过滤噪声。

小模型可以承担一条前置证据流水线：

```text
User Query
↓
Small Model：Intent / Query Rewrite
↓
Retriever：召回候选
↓
Small Model / Reranker：相关性与问题覆盖分类
↓
Structured Compressor：只保留实体、数字、结论、来源引用
↓
Validator：引用是否仍可回到原文
↓
Strong Model：只对必要证据做综合推理
```

这时“小模型节省强模型 Token”才真正成立：它**减少了进入强模型的上下文长度和强模型调用次数**；参数量变小本身不会自动改变同一文本的 Token 数。

但压缩不能把 Evidence 变成二手传闻。高风险事实应保留原文引用和位置；小模型生成的摘要是派生 Artifact，不应覆盖原始 Evidence。

## 真实业务场景三｜Agent Runtime：一次任务里最贵的不是一通大模型，而是重复几十次

#### 本节新词

- **Reasoning Model（推理模型）**：为复杂规划、冲突解决和开放判断投入更高推理预算的模型档位；它不应承担每一个简单 Agent Turn。
- **Completion Candidate（完成候选）**：模型认为 Task 可能已经满足停止条件的候选判断；最终完成仍需 Runtime Validator/Evidence。
- **Model Capability（模型能力）**：由某个模型 Worker 提供的局部语义能力。多个 Model Capability 可以属于同一个 Agent Runtime。


Agent 系统与普通聊天最大的经济差异是：一个 Task 可能产生很多次模型调用。

例如 Coding Agent：

```text
理解任务
→ 找文件
→ 读代码
→ 选 Tool
→ 看结果
→ 归纳错误
→ 再选 Tool
→ 判断是否完成
```

如果每一步都调用最强 Reasoning Model，成本和延迟会随 Agent Loop 放大。

因此模型层可以拆成：

```text
Reasoning Model
负责：目标分解、架构判断、未知路径、冲突解决

Small Model Workers
负责：
- Tool 候选分类
- 参数抽取
- Result normalization
- 日志/错误分类
- Context compression
- 简单 completion candidate
- 下一步是否需要升级推理模型的 gate
```

Runtime 仍然拥有 Task、State、Permission、Evidence 和停止条件。**小模型不能因为“便宜”就成为 Truth Owner 或权限 Owner。**

这也解释一个重要边界：十个专用小模型不等于十个 Agent。它们完全可以只是一个 Agent Runtime 下面的十种 Model Capability。

## 真实业务场景四｜Coding / Browser Agent：先把环境噪声压成 Observation

#### 本节新词

- **Stack Frame（调用栈帧）**：程序异常时调用栈中的一个函数/位置记录，可帮助定位错误来源。小模型可抽取关键帧，但原始日志仍是 Evidence。
- **Exit Code（退出码）**：进程结束时返回的整数状态码，常用 `0` 表示程序层成功退出；它不能单独证明业务行为正确。
- **Accessibility Tree（无障碍树）**：浏览器为辅助技术暴露的语义控件结构，可作为 Browser Agent 的结构化 Observation。


真实环境的原始反馈非常大：一份测试日志可能几万行，一个网页 DOM 可能有大量无关节点，一个代码仓库可能有成千上万文件。

小模型适合做局部、高频的环境解释：

```text
Terminal output
→ 错误类别 / 关键 stack frame / failed test IDs

Git diff
→ 受影响模块候选 / 变更摘要 / 风险标签

DOM / accessibility tree
→ 可交互元素候选 / 当前页面状态

Browser action result
→ submitted / validation_error / auth_required / unknown
```

这些输出必须保留 Raw Evidence 引用。小模型说“测试通过”不能替代测试进程 exit code；小模型说“页面已经保存”不能替代浏览器回读。

它的作用是**压缩环境，不是制造事实**。强模型拿到的是更小、更干净的 Observation，因此能把推理预算放在真正难的地方。

## 真实业务场景五｜手机、PC 与边缘设备：本地小模型让 AI 从“调用云服务”变成“软件能力”

#### 本节新词

- **On-device Inference（端侧推理）**：模型直接在手机、PC 或边缘设备上运行，不必每次把原始输入发到云端。
- **Marginal Invocation Cost（边际调用成本）**：系统已部署后，每增加一次调用带来的额外成本。端侧没有云 API 按 Token 计费，不代表本地算力、电量和内存免费。
- **Function Calling Model（函数调用专用模型）**：专门优化从自然语言选择有限函数并生成参数的模型，例如本章当前事实中的 FunctionGemma。
- **Server Dependency（服务器依赖）**：功能是否必须依赖远端服务在线才能工作；端侧模型可以降低部分任务的 Server Dependency。


端侧模型最直接的价值体现在四个系统性质：

- **低延迟**：无需每次跨公网请求；
- **隐私**：原始个人数据可以不离开设备；
- **离线**：弱网或无网仍能执行部分能力；
- **边际调用成本低**：模型已经驻留设备后，高频调用不按云 API Token 次次计费，但仍消耗本地算力、电量和内存。

2026 年的真实产品路径已经说明这不是纯未来想象：Apple Foundation Models/Core AI 提供端侧模型和自带模型运行路径；Microsoft Edge 的实验性 Prompt/Writing Assistance APIs 使用内置 SLM；Google 的 FunctionGemma 270M 专门针对 function calling，并公开了 Mobile Actions 的端侧调优案例。它们共同指向一个趋势：**很多应用内 AI 功能会成为本地 Runtime 的常驻能力，而不是每次都远程调用一个万能模型。**

典型场景包括：

```text
本地邮件 / 消息
→ 分类、摘要、Action 候选

个人文件
→ 标签、实体抽取、本地检索 Query

语音命令
→ Intent → App Function Call

设备日志
→ 本地异常分类 → 只上传必要摘要
```

当任务需要更大 Context、开放知识或复杂 Reasoning 时，再把经过权限过滤和压缩的最小必要信息升级到云端。

## 真实业务场景六｜制造、IoT 与 Physical AI：小模型离现场更近，但不能替代安全控制

#### 本节新词

- **IoT（Internet of Things，物联网）**：传感器、设备和网络连接形成的物理设备系统，本章关注它产生的日志、状态和本地推理场景。
- **PLC（Programmable Logic Controller，可编程逻辑控制器）**：工业现场用于确定性控制机器/流程的专用控制器；安全硬控制不应交给生成模型替代。
- **Physical AI（物理 AI）**：AI 感知和决策进入机器人、设备、车辆等物理世界的系统方向，真实 Effect 风险通常高于纯软件内容生成。
- **Safety Rule（安全规则）**：必须由确定性控制层强制执行的安全边界，例如阈值、互锁或紧急停止。


在物联网设备现场，往往同时存在传感器阈值、PLC（Programmable Logic Controller，可编程逻辑控制器）、日志、工单、手册和自然语言维修记录。

合理分工是：

```text
传感器 / PLC / Safety Rule
→ 硬实时与安全门禁

Small Model on Edge
→ 日志语义分类
→ 故障描述归一化
→ 工单路由
→ 维修记录摘要
→ 异常模式候选

Cloud / Strong Model
→ 跨设备复杂诊断
→ 开放知识研究
→ 维修方案比较
```

不要让生成模型直接替代硬安全回路。小模型适合成为“现场语义层”，把机器数据和人的语言连接起来；真正控制设备的安全逻辑仍应保持确定、可验证和可审计。

## 真实业务场景七｜高并发 SaaS：真正要优化的是任务吞吐，不是单次 Demo 质量

#### 本节新词

- **SaaS（Software as a Service，软件即服务）**：通过在线服务向多个用户/企业持续提供软件能力的产品模式，高调用量会放大小模型的成本和吞吐优势。
- **Concurrency（并发）**：同一时间系统能够推进的请求/任务数量；模型内存和设备资源会限制真实并发。
- **Adapter（适配器）**：这里指为同一 Base Model 保存不同客户/领域行为差异的轻量参数模块，不要与 API Provider Adapter 混淆。

模型和 Adapter 一多，版本、Eval、目标硬件与发布状态仍应进入前面平台章节定义的 Model Registry；本章只使用这项平台能力，不重新定义。


当一个产品每天有大量分类、抽取、标签、摘要、Tool 参数和路由请求时，模型选择必须从“哪个回答最好”转成：

```text
Throughput
Latency P50 / P95
Cost per Success
GPU / CPU Memory
Concurrency
Escalation Rate
Human Load
```

一个强模型单次质量高，但如果大多数请求只需要有限语义判断，它可能浪费昂贵能力。小模型只要在该 Slice 达到业务门槛，就可以承接大部分流量；难例升级后，系统总体质量仍可保持高水平。

多租户场景还可以评估共享 Base Model + 不同 Adapter / Prompt / Policy，但这会引入 Adapter 版本、缓存、租户隔离、Model Registry 和路由治理，不能因为“模型小”就忽略平台成本。

## 小模型怎样真正节省 Token｜不要把三个概念混在一起

#### 本节新词

- **Token Count（Token 数量）**：文本经过某个具体 Tokenizer 和模板编码后得到的 Token 个数。比较两个模型时，Tokenizer 不同可能让同一文本得到不同数量的 Token。
- **Tokenizer（分词器 / Token 化器）**：把文本转换成模型 Token ID 的组件。参数量和 Tokenizer 是两条独立维度，不能因为模型更小就推断 Token Count 更少。
- **Token Compute Cost（Token 计算成本）**：模型处理每个输入/输出 Token 需要付出的计算与服务成本；模型规模、架构、硬件和服务定价都会影响它。
- **Frontier Token Volume（前沿强模型 Token 量，本教材工作指标）**：整个系统最终送进昂贵强模型的 Token 总量，用来观察 Small-first 是否真正减少了强模型负载。
- **Compressed Input（压缩输入）**：经过分类、抽取、Evidence 筛选或 Context Compression 后交给强模型的更小输入。

需要分清三个量：Token Count 由具体编码决定；每 Token 计算成本由模型与运行环境决定；系统最能主动改变的是**哪些请求需要进入强模型，以及进去多少上下文**。

小模型减少 Frontier Token Volume 的方法包括：

- 简单任务直接本地完成，**强模型调用 = 0**；
- 先做 Intent Routing，只把复杂 Slice 升级；
- 从长文档中抽取结构字段或保留必要 Evidence，减少 Context；
- 对 Tool Result、日志、DOM 做结构化压缩；
- 用固定 Schema 限制输出长度；
- 先识别无效、重复、低价值请求，避免进入昂贵链路。

可以把强模型预算理解成：

```text
旧方式：
Frontier Tokens = 所有任务的 Input + Output

分层方式：
Frontier Tokens = 只有 Escalated Tasks 的 Compressed Input + Necessary Output
```

目标是**让昂贵 Token 只出现在值得的地方**，而不是只追求每个 Token 再便宜一点。

## 到这里，第一遍主线已经闭环

如果你当前只想学“小模型在系统里该放哪里”，读到这里已经足够：先用确定性软件收缩任务，再让小模型承担高频、可验证的语义责任，失败时升级；经济收益来自调用结构和目标硬件，而不是“参数少”三个字。

后半篇回答两个更深入的问题：这种分层未来可能长成什么样，以及**什么时候值得真正修改模型权重**。做应用/Agent 架构时可以先跳到贯穿案例；准备训练、端侧部署或 ML 岗位时再完整读后半篇。

## 未来场景｜小模型可能成为 AI 系统的默认第一执行层

#### 本节新词

- **Architecture Hypothesis（架构假设）**：根据当前技术和产品信号提出、但尚未由长期生产数据证明的未来架构判断。
- **Model Mesh（模型网格，本章工作称呼）**：企业维护多个专用模型能力，由 Gateway / Registry / Runtime 统一发现和路由，而不是把每个模型都包装成 Agent。
- **Teacher–Student Data Flywheel（教师—学生数据飞轮）**：强模型或专家处理难例并产出经审核数据，小模型吸收这些数据后承接更多稳定流量，新失败再回到数据集。

下面都是架构假设，不是已经成立的行业结论。

### 个人设备：高频私人上下文留在本地

手机和 PC 上的小模型可以处理通知、邮件、文件、日历和应用状态，只把经过授权、压缩后的复杂问题升级到云端。它的价值来自隐私、延迟和离线能力，而不是“本地模型天然更聪明”。

### Agent Runtime：一个 Agent 背后可以是一组模型档位

同一个 Task 可以依次尝试 Rule / Embedding、Tiny Specialized Model、Local SLM、Cloud FAST、Cloud REASON，必要时再交给人工。外部看仍是一个 Agent，内部只是多模型路由。

### 企业模型网格：模型能力可以多，责任主体不必跟着膨胀

合同抽取、客服分类、日志解释、风险判断、Tool Calling 都可以作为受平台治理的 Model Capability；只有确实拥有独立 State、Permission 和生命周期的对象才升级成 Agent。

### Teacher–Student 飞轮：强模型探索，专用模型规模化

长尾失败先交给强模型/专家解决，经审核后进入 Dataset，再通过后文介绍的模型适配或蒸馏方式，让小模型接住更多重复流量。关键不是自动生成海量数据，而是把**真实失败变成可训练、可验证的窄任务**。

### Edge / Physical AI：语义理解下沉，硬安全控制保持确定性

摄像头、机器人、汽车和工厂终端会需要更多本地语言/视觉理解；复杂知识和重推理仍可上云。无论模型在哪运行，硬实时与安全回路都不能因为生成模型可用就取消。

## 不要神化小模型｜它仍然是概率模型

#### 本节新词

- **Model Explosion（模型膨胀）**：为大量微小任务各维护一个独立模型，导致版本、路由、缓存和 Eval 成本快速增长的反模式。
- **Drift（漂移）**：线上输入分布、业务规则或模型行为随时间变化，导致原有 Eval 结果不再代表当前性能。
- **Distribution Shift（分布变化）**：生产输入与训练/验证数据分布发生系统性差异，是 Drift/OOD 的重要来源。
- **Policy Enforcement（策略强制执行）**：由确定性 Runtime/Policy 层真正阻止不允许动作；小模型的风险分类不能替代它。


小模型作为落地抓手，不意味着“小模型比大模型更可靠”。它的可靠性来自：**任务更窄 + 输入输出更受控 + Eval 更具体 + Validator 更强 + 可以安全升级。**

几个必须保留的反例：

- 开放世界问题硬塞给小模型，只会得到更便宜的错误；
- 用小模型做权限判断，不能替代 Policy Enforcement；
- 用小模型摘要 Evidence 后丢弃原文，会失去 Truth；
- 为每个微小任务维护一个模型，可能形成 Model Explosion，与 Agent Explosion 一样增加版本和路由成本；
- 小模型 Fine-tuning 后也会 Drift，数据分布变化时必须重新 Eval；
- 本地运行不等于免费：仍有内存、电量、安装包、冷启动和硬件兼容成本。

因此更准确的原则是：

> **Deterministic-first；需要语义时 Small-first；复杂、未知或高风险时 Escalate；所有层都用 Evidence 验证。**

## 什么任务值得 Small-first，什么任务不值得

垂直业务给小模型机会，并不是因为行业知识天然更简单，而是因为业务系统能把开放世界问题收缩成有限责任：固定合同字段抽取、客服意图路由、设备故障分类、受控 Tool 参数生成、本地文件整理、短文本改写等。知识、事实、权限和确定路径被外部系统接走后，模型只需要做好剩下的语义映射。

适合 Small-first 的任务通常同时满足几项条件：调用频繁；输出空间有限；有真实验证集；错误能拒绝或升级；对延迟、隐私、离线或成本敏感。首 Token 很快、模型很小都只是系统信号，最终仍看真实任务门槛。

反过来，开放研究、跨领域复杂规划、极长上下文全局推理、无法定义成功标准的“万能助手”，以及没有权威 Tool / 规则 / 人工复核的高风险诊断，都不应为了省成本硬塞给小模型。更可靠的系统通常保留强模型和人工兜底。

所以本章的稳定判断不是“小模型取代大模型”，而是：

> **Deterministic-first；需要语义时 Small-first；复杂、未知或高风险时升级；每一层都用可回读证据验证。**

## 从软件到训练的决策顺序

下面的 `Level 0～4` 是**先后检查的软件决策顺序**：先排除不需要生成模型的问题，再把合同、知识和路由收紧。这里把“低成本层先处理，验证不通过再升级”的生产结构简称为 **Small-first Cascade（小模型优先级联，本章架构模式称呼）**；它不是行业协议名，也不要求所有任务都先调用一个小模型。

进入模型适配后则不再是严格的“等级阶梯”：后文会看到，显存受限的参数高效适配、蒸馏、继续预训练和全参数微调解决的不是同一种缺口，成本也不会保证单调上升。

因此每一步都沿用已有 Baseline 与 Failure Slice：先确认当前失败是什么，再选择能直接命中该失败的最小干预。

### Level 0｜不用生成模型

#### 本节新词

- **Traditional Classifier（传统分类器）**：Logistic Regression、Tree Model 等非生成式分类模型，在稳定有限标签任务上可能比 LLM 更便宜、可解释。
- **Threshold（阈值）**：根据分数决定接受、拒绝或升级的确定性边界；阈值需要由真实验证集选择。


先判断规则、SQL、全文检索、传统分类器或 Embedding 模型是否已经足够。

例如：

- 固定枚举映射使用规则；
- 精确金额聚合使用 SQL；
- 已知错误码路由使用查表；
- 二分类且数据稳定时先试轻量分类模型；
- 语义相似搜索先试 Embedding + 阈值。

这是最低成本、最高可解释性的起点。

升级条件：规则数量失控、自然语言变化导致维护成本持续上升，或传统模型无法达到真实召回和泛化门槛。

### Level 1｜Structured Input、Structured Outputs 与 Deterministic Validation

前面的设备工单已经完整建立 Input Contract、Schema 和 Deterministic Validator，这里只把它放回决策顺序：**生成式方案一旦进入业务，先把输入输出变成软件可检查对象，再谈训练。**

先做三件事：

1. **Structured Input / Input Contract**：把单位、枚举、时间、来源、缺失值和字段边界整理清楚；
2. **Structured Outputs / Schema**：只让模型返回业务真正消费的字段、枚举和证据引用；
3. **Deterministic Validator**：用普通代码检查 Schema、枚举、范围、来源引用、权限规则和必须升级人工的条件。

设备工单里，如果模型原本输出一大段自然语言，你很难判断它究竟错在哪；一旦输入输出结构化，错误可以立刻被切成“字段缺失、非法类别、证据不存在、规则冲突、应拒答未拒答”等 Failure Slice。

升级条件：输入输出合同已经稳定，Validator 能明确判错，但模型仍持续无法完成语义任务。

### Level 2｜Prompt、Few-shot 与 Chat Template

#### 本节新词

- **Few-shot（少样本提示）**：在 Prompt 中提供少量示例，让模型理解任务模式和边界，不修改模型参数。
- **Chat Template（对话模板）**：把 System/User/Assistant 等角色和特殊 Token 组织成模型训练/推理所需格式；模板不一致会导致明显行为偏差。
- **Zero-shot（零样本）**：不提供任务示例，只依赖任务说明和模型已有能力完成任务。


选择一个现成小模型，不改权重，在已经固定的输入输出合同上再优化：

- 清晰任务说明；
- 少量正例、反例和边界例；
- 固定 Chat Template；
- 领域术语说明；
- 明确拒答条件。

这一层验证两件事：

1. 基础模型是否已经具备任务能力；
2. 问题究竟是模型能力不足，还是任务表达和示例覆盖不清楚。

升级条件：Prompt/Few-shot 已稳定，结构化验证仍暴露出可重复的语义错误。

### Level 3｜RAG、Tool 与 Workflow

不要用 Fine-tuning 记忆会变化的事实。

- 最新政策放进 RAG；
- 商品价格通过 Tool 查询；
- 退款门槛交给 Policy；
- 多步骤确定流程交给 Workflow；
- 输出正确性用 Validator 检查。

Fine-tuning 更适合改变行为模式、格式、领域语言和决策边界，不适合替代实时数据库。

升级条件：外部知识和系统约束已补齐，模型仍无法稳定理解领域表达或执行固定任务。

### Level 4｜任务路由、输入收缩与级联

#### 本节新词

- **Task Slice（任务切片）**：把开放业务请求按意图、风险、难度或输入特征拆成更窄的可评估任务类别。
- **Confidence Gate（置信门禁）**：把模型分数、Validator、分布距离和业务规则组合成接受/升级条件，不只相信模型自报 confidence。


把开放请求先拆成有限 Task Slice：

- 小模型处理分类、抽取、改写和候选生成；
- 规则或置信门槛判断是否接受；
- 复杂、低置信和分布外样本升级给大模型；
- 高风险结果进入人工审批。

这种 Small-first Cascade 往往比把全部请求交给同一个模型更经济。

升级条件：小模型在目标切片上仍有稳定、可复现且业务重要的能力缺口。

### 适配路线 A｜参数高效微调

#### 本节新词

- **PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）**：只训练少量新增/选定参数以适配下游任务，降低显存和训练成本。
- **LoRA（Low-Rank Adaptation，低秩适配）**：冻结 Base Model，在部分层加入可训练低秩矩阵的 PEFT 方法。
- **LoRA Rank（LoRA 秩）**：低秩 Adapter 的容量超参数；Rank 更高代表可训练表达空间更大，但不保证任务效果更好。
- **Epoch（训练轮次）**：训练数据集被完整遍历一次的计量单位；Epoch 过多可能加剧 Overfitting。
- **Overfitting（过拟合）**：模型过度适应训练数据，在未见真实样本上表现下降。
- **Catastrophic Forgetting（灾难性遗忘）**：适配新任务时原有通用能力显著退化的现象。
- **Loss（损失函数值）**：训练优化的数值目标。Loss 下降只说明训练目标改善，不等于真实业务 Outcome 提升。


落到训练实现时，只更新少量新增/选定参数可以显著降低适配成本；LoRA 进一步冻结基础权重，在 Transformer 层加入可训练的低秩矩阵。

适合：

- Prompt、Schema、Validator 已经稳定，但领域语言到目标语义的映射仍持续出错；
- 适应领域术语、固定表达和稳定行为模式；
- 强化有限 Tool Calling 中“选哪个能力、怎样填语义参数”的模式，而不是只修 JSON 格式；
- 为不同客户维护独立行为 Adapter；
- 计算和显存不足以做 Full Fine-tuning。

如果问题只是字段缺失、JSON 格式漂移、枚举非法或硬规则不满足，优先修 Structured Output / Validator；**能由确定性合同解决的问题，不应为了“更稳”先训练 LoRA。**

LoRA Rank 控制 Adapter 的表达容量。Rank 更高不等于一定更好，应从小值建立 Baseline，再按验证集结果增加。

风险：

- 训练样本格式与真实推理模板不一致；
- 只训练正例，没有拒答和边界样本；
- 学习率或 Epoch 过高导致过拟合和灾难性遗忘；
- 训练 Loss 下降，但真实任务没有提升；
- Adapter、Base Model、Tokenizer 版本不匹配。

### 适配路线 B｜显存受限时的低秩适配训练

#### 本节新词

- **QLoRA（Quantized LoRA，量化低秩适配）**：在冻结的量化 Base Model 上训练 LoRA Adapter，以降低训练显存需求。
- **Gradient Accumulation（梯度累积）**：多次小 Batch 计算后再更新一次参数，用更小显存近似更大 Batch。
- **Kernel（计算内核）**：GPU/CPU 上执行矩阵、量化等底层计算的实现；硬件是否有高效 Kernel 会直接影响速度。
- **Post-training Quantization（训练后量化）**：模型训练完成后再降低权重/计算精度的部署优化。
- **Quantization-aware Training（量化感知训练）**：训练过程中显式模拟/适应量化误差，使低精度部署质量更稳定。


QLoRA 在量化后的冻结基础模型上训练 LoRA Adapter，显著降低训练显存需求。它适合资源受限的实验和中等规模模型适配。

QLoRA 不代表“任何电脑都能训练任何模型”。仍要考虑：

- 基础模型大小；
- Context Length；
- Batch Size 和 Gradient Accumulation；
- 优化器状态；
- 硬件与 Kernel 支持；
- 训练时长和数据吞吐。

还要区分：

- QLoRA：量化基础模型参与 Adapter 训练；
- Post-training Quantization：训练完成后再量化部署模型；
- Quantization-aware Training：训练过程显式适应量化误差。

不同框架支持路径不同，部署格式必须在训练前确认。

### 适配路线 C｜Knowledge Distillation｜知识蒸馏

#### 本节新词

- **Knowledge Distillation（知识蒸馏）**：让较小 Student Model 学习较强 Teacher Model 在选定任务上的输出/行为，以把能力迁移到更低成本模型。
- **Teacher Model（教师模型）**：产生示范、标注、排序或难例解释的较强模型。Teacher 错误会被规模化传给 Student，因此需要过滤。
- **Student Model（学生模型）**：用 Teacher/人工审核数据训练的较小模型，是独立模型，不是从 Teacher 直接删除参数。
- **Synthetic Data（合成数据）**：由模型/规则生成而非真实业务自然产生的数据，可以扩展覆盖，但必须标记来源并防止错误和分布偏差。
- **Data Contamination（数据污染）**：训练数据混入测试答案、错误标签或不当来源导致评估失真的问题。


当大模型在目标任务上已经表现良好，但成本无法接受，可以让 Teacher Model 产生：

- 高质量示范；
- 难例解释；
- 候选答案与排序；
- 推理轨迹或中间标签；
- 合成训练数据。

再用这些数据训练 Student Model。

蒸馏不是从大模型里删除参数，而是训练一个独立的小模型去学习被选择的能力。

风险：

- Teacher 错误被规模化复制；
- 合成数据缺少真实分布和长尾；
- 只学会语言风格，没有学会正确决策；
- 数据污染导致训练集与测试集泄漏；
- 生成推理轨迹看似合理但事实错误。

所有合成样本都需要来源、生成配置、过滤规则和抽样人工复核。

### 适配路线 D｜Continued Pre-training｜领域继续预训练

#### 本节新词

- **Continued Pre-training（继续预训练）**：在已有 Base Model 上继续使用大规模领域文本做预训练目标，使模型更熟悉领域语言和表示。
- **Domain Corpus（领域语料）**：用于继续预训练的专业文本集合，需要去重、来源、Copyright、PII 和质量治理。
- **General Regression（通用能力回归）**：模型垂直化后原有通用能力是否退化的评估。


当问题不是任务格式，而是模型缺少大量领域语言和概念表示时，才考虑在领域语料上继续预训练。

适合：

- 特殊语言、符号或专业术语密集；
- 领域文本规模足够大；
- 多个下游任务都需要同一领域表示；
- RAG 无法弥补底层语言理解缺口。

它比 SFT 更昂贵，也更容易造成通用能力退化。需要领域语料清洗、去重、版权与隐私治理，以及通用回归 Eval。

### 适配路线 E｜Full Fine-tuning 或从头训练

#### 本节新词

- **Full Fine-tuning（全参数微调）**：在下游数据上更新 Base Model 的全部/几乎全部参数，资源和遗忘风险高于 PEFT。
- **Training Stability（训练稳定性）**：训练过程中 Loss、梯度和参数更新是否稳定可控，是大规模全参训练的基础工程责任。
- **Training from Scratch（从头训练）**：从随机/初始参数开始训练一个新模型，需要大量数据、算力和研究投入，对多数应用团队不是默认路线。


只有以下条件同时出现时才认真考虑：

- PEFT 明确达不到质量门槛；
- 有足够高质量数据和训练算力；
- 需要深度改变模型行为或能力；
- 团队具备训练稳定性、评估、模型治理和部署能力；
- 增量收益能够覆盖训练与长期维护成本。

从头训练小模型则需要更大的数据和研究投入。对多数应用团队，它不是默认路线。

## 从零到上线的完整工作流

### Step 1｜定义可评估责任，并先冻结输入输出合同

弱目标：“做一个懂制造业的小模型。”

强目标：“输入单台设备最近 20 条告警和运行指标，输出限定故障类别、证据字段和置信等级；未知情况必须拒绝诊断并升级人工。”

在选模型之前先写清：

- Input Contract：哪些字段进入模型，单位、枚举、来源和缺失值怎样规范；
- Output Schema：业务真正需要哪些字段，哪些值必须来自有限集合；
- Deterministic Validator：哪些结果可以用普通代码直接判错；
- Reject / Escalate：信息不足、OOD、高风险时怎样拒答或升级；
- 允许和禁止的动作；
- 成功、失败与拒答标准；
- 延迟、内存、吞吐和隐私目标。

这一步经常比换模型、加参数或开始 Fine-tuning 更有效，因为它先把“模型能力问题”和“软件合同没定义清楚”分开。

### Step 2｜先建立最便宜 Baseline

至少比较：

- 规则或传统模型；
- 未调优小模型 + Zero/Few-shot；
- 小模型 + RAG/Tool；
- 当前大模型方案；
- 人工处理基线。

记录 Quality、Latency、Memory、Cost per Success 和 Human Intervention。没有 Baseline，就无法证明调优有价值。

### Step 3｜建立领域数据合同

#### 本节新词

- **PII（Personally Identifiable Information，个人可识别信息）**：可以直接或间接识别个人的数据，训练前需要按法律/组织规则处理。
- **Train Set（训练集）**：允许模型直接学习的样本集合。
- **Validation Set（验证集）**：用于选择超参数、阈值和早停策略的独立集合，不应作为最终成绩反复优化。
- **Test Set（测试集）**：在方案冻结后用于最终评估的集合，反复查看并调参会造成 Test Leakage。
- **Challenge Set（挑战集）**：专门覆盖长尾、OOD、对抗和高风险边界的测试集合。
- **Data Leakage（数据泄漏）**：训练/验证信息不当进入测试或跨集合重复，导致评估虚高。


训练数据不是“越多越好”。先保证：

- 数据有合法来源和使用权；
- PII（Personally Identifiable Information，个人可识别信息）、Secret 和客户数据得到处理；
- 输入与真实线上分布一致；
- 标签定义稳定且标注者一致；
- 正例、反例、边界例和拒答例齐全；
- 重复和近重复样本被识别；
- 时间、客户、设备或文档来源不会跨集合泄漏。

建议拆分：

- Train：模型允许学习的样本；
- Validation：选择超参数和停止训练；
- Test：最终冻结评估，不能反复看结果调参；
- Challenge Set：长尾、分布外、对抗与高风险样本；
- Online Shadow Set：真实流量影子评估。

### Step 4｜选择基础模型

#### 本节新词

- **License（许可证）**：规定模型权重、代码或数据是否允许商用、修改和再分发的法律合同。
- **Model Card（模型卡）**：发布方描述模型能力、训练背景、限制、评估和使用注意事项的文档，是选型 Evidence 之一。
- **Revision（版本修订）**：模型权重/仓库的精确版本标识，用于确保训练和部署可复现。

Base / Instruct 已在前面的模型章节解释，这里直接作为选型维度使用。不要只看排行榜。检查：

- 目标语言和领域基础能力；
- 参数量、Context Length 与目标硬件；
- Base / Instruct 版本；
- Tokenizer 和 Chat Template；
- Tool Calling 或 Structured Output 能力；
- License 是否允许商用、修改和分发；
- 训练框架、量化与部署格式支持；
- 社区维护、模型卡和已知限制。

选择原则：先找能在未调优 Baseline 上接近门槛的最小模型，而不是先选最小参数再希望训练创造全部能力。

### Step 5｜建立训练样本格式

#### 本节新词

- **Target Token（目标 Token）**：训练时希望模型学习预测的 Token，通常对应 Assistant/期望输出部分。
- **Context Token（上下文 Token）**：只作为条件输入、通常不希望计算生成 Loss 的 Token，例如 System/User/Tool Result。
- **Loss Mask（损失掩码）**：标记哪些 Token 参与 Loss 计算，防止模型错误学习复述输入。
- **Metadata（元数据）**：记录样本来源、领域、难度、版本等辅助属性，用于切片、治理和复现。


每条样本需要显式区分：

- System / User / Assistant 角色；
- 模型应该学习的 Target Token；
- 仅作为输入的 Context Token；
- Tool Call 与 Tool Result；
- 拒答和升级人工的输出；
- 数据来源、领域、难度和版本 Metadata。

训练时通常只对期望模型生成的部分计算 Loss。若把 System、User 或 Tool Result 也当 Target，模型可能学会复述输入而不是完成任务。

### Step 6｜做最小训练实验

#### 本节新词

- **Hyperparameter（超参数）**：学习率、Rank、Epoch、Batch Size 等训练前设定、不是模型直接学习得到的参数。
- **Training Checkpoint（训练检查点）**：训练过程中保存模型/Adapter/优化器等状态以便恢复和比较；它与 Runtime Task Checkpoint 不是同一个对象。
- **Seed（随机种子）**：控制数据打乱、初始化等随机过程的起点，有助于复现但不能消除所有硬件/并行非确定性。
- **Training Artifact（训练产物）**：本次训练产生的模型权重、Adapter、配置或 Eval 输出等可版本化交付对象。


先用小数据、小 Rank、少 Epoch 跑通：

- 数据加载与 Template；
- Token Length 分布；
- Loss Mask；
- Training Checkpoint 保存和恢复；
- Validation Eval；
- Adapter 与 Base Model 回载；
- 固定 Seed 下的可复现性。

一次只改变少量变量。记录 Base Model Revision、数据版本、代码 SHA、超参数、硬件、随机种子和 Training Artifact。

### Step 7｜按 Failure Slice 迭代

不要看到总分不够就盲目增加 Epoch。

先分类：

- 知识缺失：优先 RAG/Tool；
- 格式错误：先用 Structured Outputs / Schema / Deterministic Validator；只有格式背后的语义遵循仍稳定失败，才考虑训练；
- 领域表达不懂：领域数据、LoRA 或继续预训练；
- 推理能力不足：更强 Base Model、蒸馏或大模型兜底；
- 越权动作：Runtime Policy，不是继续训练；
- 分布外失败：拒答、路由和人工；
- 延迟过高：量化、批处理、缓存或更小模型。

### Step 8｜离线 Eval

Accuracy、F1、Exact Match、Calibration、Robustness 和 Safety Eval 的正式定义属于前面的 Evaluation 章。本章只关心选哪些指标来决定“小模型能否接流量”。至少要同时看：

- 任务质量：分类/抽取的 Accuracy、F1、Exact Match 或领域 Rubric；
- 拒答与升级：低置信、OOD、高风险样本能否进入正确兜底路径；
- 系统指标：首 Token、端到端延迟、吞吐、峰值内存和模型大小；
- 经济性：Cost per Success、人工升级率和强模型兜底比例；
- 关键 Failure Slice：不能让总体平均分掩盖高风险类别。

医疗、法律、金融和工业控制等高风险领域仍需要领域专家参与验收。

### Step 9｜量化与目标硬件验证

#### 本节新词

- **Quantization（量化）**：用更低位宽表示权重/部分计算以减少存储、内存和计算成本，可能造成质量下降。
- **Bit Width（位宽）**：数值表示使用的二进制位数，例如 16-bit、8-bit、4-bit；位宽越低通常越省资源，但精度风险越高。
- **FP16（16-bit Floating Point，16 位浮点）**：常见的半精度浮点格式，可降低模型训练/推理的内存和带宽占用；它与 4-bit/8-bit 权重量化不是同一概念。
- **CUDA（Compute Unified Device Architecture）**：NVIDIA 的 GPU 并行计算平台和软件生态。某个训练/量化方案依赖 CUDA，意味着它不能直接假设在 Apple、CPU 或其他加速器上拥有同样支持。
- **Cold Start（冷启动）**：模型尚未加载/缓存时第一次请求的启动延迟。
- **Warm Start（热启动）**：模型已驻留、相关缓存已准备后的请求延迟。
- **Peak Memory（峰值内存）**：运行过程中最大内存占用，决定模型能否稳定部署在目标设备。


量化用更低位宽表示权重或部分计算，可降低存储、内存带宽和部署成本，但可能损失质量。

必须在真实目标硬件上测：

- 模型加载时间；
- 冷启动与热启动；
- 首 Token 和生成速度；
- 峰值内存；
- 并发吞吐；
- 电量或能耗；
- 量化前后各 Failure Slice 的质量变化。

不要只在开发 GPU 上测完，就宣布手机、边缘设备或 CPU 部署可用。

### Step 10｜设计 Small-first Cascade

#### 本节新词

- **Margin（分类间隔）**：最高和次高类别分数之间的差距，可作为置信信号之一；Margin 高不自动保证正确。
- **Sampling Consistency（采样一致性）**：多次独立生成是否得到一致结论，可作为不确定性信号，但会增加调用成本。
- **Distribution Distance（分布距离）**：当前输入与训练/验证数据分布有多远的统计/表示度量，可辅助 OOD Gate。


推荐的生产结构：

输入
→ 规则和安全检查
→ Task Router
→ 小模型处理受控任务
→ Validator / Confidence / OOD 检查
→ 通过则提交
→ 不通过则大模型或人工兜底

路由不能只依赖模型自报置信度。可以结合：

- 分类 Margin；
- 多次采样一致性；
- Validator 结果；
- Retrieval 覆盖；
- 输入与训练分布距离；
- 高风险业务规则。

### Step 11｜Shadow、Canary 与回滚

#### 本节新词

- **Shadow（影子运行）**：让新模型接收真实输入并生成结果，但不影响正式业务，用于低风险比较。
- **Canary（金丝雀发布）**：只让少量低风险真实流量进入新模型，稳定后再逐步扩大。
- **Rollback（回滚）**：指标恶化或出现风险时恢复到已知稳定的模型、Adapter、量化格式或 Router 版本。


上线顺序：

1. Shadow：读取真实输入，但不影响真实结果；
2. Canary：只接少量低风险流量；
3. Compare：与旧系统、大模型和人工对比；
4. Expand：指标稳定后逐步扩流；
5. Rollback：模型、Adapter、量化格式和 Router 都必须可回滚。

### Step 12｜模型生命周期治理

#### 本节新词

- **Model Lifecycle（模型生命周期）**：从候选、训练、评估、发布、监控、替换到退役的完整治理过程。
- **Deployment Format（部署格式）**：目标 Runtime 实际加载的模型交付形态。格式能被加载只证明部署兼容，不证明任务质量通过。

Model Registry 已在前面的 SaaS 场景介绍；这里直接把它作为生命周期的版本化事实系统使用，不再重新定义。


每个可部署版本至少登记：

- Base Model 与 Revision；
- Tokenizer / Chat Template；
- Adapter 与合并状态；
- 数据集版本和授权；
- 训练配置和代码 SHA；
- 量化方法与部署格式；
- Eval Set、指标和未通过边界；
- 目标硬件与性能；
- Owner、状态、发布时间和回滚目标。

模型文件存在不等于模型可以上线。只有通过目标任务、系统、安全和部署评估，才能进入可用状态。

## 一个贯穿示例｜设备故障工单分类

### 业务目标

输入设备告警、指标摘要和维修记录，输出故障类别、引用证据和下一步工单路由。模型不能直接控制设备。

### 最低成本起点

1. 已知错误码先用规则映射，能不用生成模型就不用；
2. 把设备型号、告警、指标、维修引用统一成 Input Contract，先处理单位、枚举、缺失值和时间顺序；
3. 输出固定为 `fault_type / evidence / confidence / needs_human`，用 Schema + Deterministic Validator 拒绝非法结果；
4. 历史工单用 Embedding 检索相似案例，轻量分类器建立 Accuracy/F1 Baseline；
5. 小型 Instruct Model 在同一合同上做 Zero/Few-shot；
6. 未知类别、验证失败、低置信和高风险结果升级大模型或人工。

这里最先追求的是让系统能够**明确知道一次输出是否可接受**，而不是先追求“回答得像专家”。当 Validator 已经能把失败切清楚，Fine-tuning 才有可靠目标。

### 何时使用 LoRA

#### 本节新词

- **Hard Negative（困难负样本）**：与正类很相似、容易被模型误判但实际属于其他类别的训练/评估样本，用来逼出真实决策边界。


如果小模型反复混淆领域缩写、设备部件和有限故障类别，而 RAG 已提供正确事实、Prompt 已稳定，可用经过审核的工单对做 LoRA。

训练集必须包含：

- 常见类别；
- 容易混淆的 Hard Negative；
- 信息不足时的拒答；
- 新设备或未见错误码；
- 同一故障的不同语言表达；
- 禁止自动操作的高风险边界。

### 何时使用蒸馏

如果强模型能稳定解释证据和分类，但在线成本太高，可以让它在真实工单分布上生成候选与解释，经规则和专家过滤后训练 Student Model。

### 上线判断

不能只看总 Accuracy。还要看：

- 高风险故障的 Recall；
- 错误路由造成的业务成本；
- 拒答率与人工负载；
- 每个设备族的 Failure Slice；
- 量化后质量；
- 端侧延迟与内存；
- 大模型兜底比例和总 Cost per Success。

## 常见反模式

### 把输入输出合同问题当成模型能力问题

原始输入单位混乱、字段缺失、输出是自由文本、没有 Validator，却直接尝试更大模型或 Fine-tuning。结果即使“看起来更像专家”，系统仍然不知道何时可以提交、何时必须拒绝。优先把 Input Contract、Structured Output 和 Deterministic Validation 建起来。

### 一上来就 Fine-tuning

问题可能只是 Prompt 不清、知识过期、Tool 缺失或 Workflow 没写。训练会把系统问题藏进权重，反而更难维护。

### 用 SFT 记忆实时事实

价格、库存、政策和客户状态会变化，应由 RAG、数据库或 Tool 提供。

### 只看训练 Loss

Loss 下降不能证明任务质量、拒答、安全、延迟或成本改善。

### 数据越多越好

重复、错误、风格单一和标签冲突的数据会放大偏差。高质量、覆盖边界的数据通常比盲目堆量更重要。

### 小模型必须完全替代大模型

更可靠的系统往往是小模型处理高频受控任务，大模型处理复杂长尾，人类承担高风险最终判断。

### 先量化再假设性能

模型文件变小不等于目标硬件一定更快。Kernel、内存带宽、Batch、Context 和并发都会影响结果。

### 每个领域一个完整模型副本

若 Base Model 相同，可评估共享基础模型配合多个 Adapter；但多 Adapter 服务仍需要版本、缓存、隔离和路由治理。

## 这类项目在岗位面试里应该证明什么

前一篇岗位分工已经定义 AI Application、Agent、ML、Inference、Platform 等角色。本章不再给角色建第二套词典，只看“小模型垂直化”怎样形成跨角色证据。

一个有说服力的项目，不应只展示“训练了一个 LoRA”。更重要的是能够回答：原问题为什么值得模型化；最便宜 Baseline 是什么；为什么选择或没有选择 Fine-tuning；失败集中在哪些 Slice；目标硬件上的延迟、内存和吞吐如何；Small-first Cascade 怎样兜底；版本、回滚和真实 Cost per Success 怎样验证。

这组证据可以分别映射到应用任务定义、Agent 路由与 Runtime、ML 适配与 Eval、Inference 性能以及 Platform 模型治理。它比“会跑一个训练脚本”更接近真实工程责任。

## 当前事实核验与来源｜2026-09-03

### 端侧、小模型与专用模型正在进入真实产品路径

- Apple Foundation Models 文档明确把 on-device model 用于摘要、实体抽取、文本理解、分类/判断和标签等任务，并把更大 Context / 更强 Reasoning 作为升级到 Private Cloud Compute 或其他 server model 的理由；这与本章的“受控高频任务本地处理、复杂任务升级”分层一致：[Apple Foundation Models](https://developer.apple.com/documentation/foundationmodels)。
- Apple 2026 的 Core AI 路线进一步允许 App 带入自有模型并完全在设备侧运行；官方强调本地隐私、响应速度、无 server dependency 与无云 API token cost，但真实系统仍要承担设备内存、电量和模型分发成本：[Apple Core AI / Machine Learning](https://developer.apple.com/machine-learning/)。
- Microsoft Edge 的实验性 Prompt API 允许网页或扩展直接调用浏览器内置 SLM，并支持 JSON Schema / Regex 约束输出，说明“浏览器内小模型 + 结构化合同”已经是现实产品形态之一：[Microsoft Edge Prompt API](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/prompt-api)。
- Google 的 FunctionGemma 270M 是专门面向 function calling 的小模型。官方 Mobile Actions 评测中，针对任务 Fine-tuning 后从 58% 提升到 85%；同一官方模型卡还给出了 Samsung S25 Ultra CPU 上的端侧延迟、吞吐和内存数据。这个案例不能证明所有小模型都能达到同样收益，但它直接证明了“窄任务 + 专用数据 + 端侧执行”可以形成真实工程闭环：[FunctionGemma model card](https://ai.google.dev/gemma/docs/functiongemma/model_card)。
- NVIDIA Research 的 SLM/Agent position paper 提出的核心判断与本章相近：Agent 系统中大量模型调用其实是重复、窄任务，可由 SLM 承担，复杂通用对话和推理保留给更大模型。它是研究立场而非行业定论，但可作为 Multi-Model Agent 架构的一条现实信号：[Small Language Models are the Future of Agentic AI](https://research.nvidia.com/labs/lpr/slm-agents/)。

### 训练与适配

- LoRA 论文提出冻结预训练权重并注入可训练的低秩矩阵，以显著减少下游任务的可训练参数：[LoRA paper](https://arxiv.org/abs/2106.09685)。
- QLoRA 论文描述在冻结的 4-bit 量化基础模型上训练 LoRA Adapter，以降低 Fine-tuning 的显存需求：[QLoRA paper](https://arxiv.org/abs/2305.14314)。
- Google 的 Gemma 官方调优指南把工作流写成选择框架、收集数据、调优与测试、部署，并强调先建立测试计划；PEFT/LoRA 是降低资源消耗的选项，不是唯一方法：[Gemma fine-tuning guide](https://ai.google.dev/gemma/docs/tune)。
- Google 的 LoRA 教程说明 Rank 控制 Adapter 容量，并建议从较小 Rank 开始实验，再依据任务评估决定是否增加：[Gemma LoRA guide](https://ai.google.dev/gemma/docs/lora_tuning)。

这些来源支持“小模型正在成为端侧与专用任务的重要执行选择”，也支持 LoRA/QLoRA 能降低适配成本；它们**不能**证明 Small-first 对任何任务都优于强模型。最终判断仍必须来自目标任务、真实分布、目标硬件、Escalation Rate 与 Cost per Success。

## 用这些问题检查方案是否站得住

1. 为什么“小模型”不能用固定参数量定义？
2. 为什么说小模型更像 Semantic Worker，而不是缩小版 ChatGPT？
3. 小模型为什么不天然减少 Token Count，却可以显著减少 Frontier Token Volume？
4. 为什么 Structured Input / Structured Output / Deterministic Validator 往往比 Fine-tuning 更应该先做？
5. 客服、RAG、Coding/Browser Agent 各有哪些高频责任适合先交给小模型？
6. 为什么 Multi-Model 不自动等于 Multi-Agent？
7. 哪些问题应该用 RAG/Tool，而不是 Fine-tuning？
8. 什么 Failure Slice 才说明 LoRA 值得进入候选，而不是继续修 Schema/Validator？
9. LoRA、QLoRA、蒸馏、继续预训练分别解决什么缺口？
10. Small-first Cascade 如何处理分布外和高风险请求？
11. 端侧小模型的隐私、延迟和成本优势分别来自哪里，又有哪些本地资源代价？
12. 为什么训练 Loss 不能作为上线证据，量化后又为什么必须在目标硬件重新评估？
13. 哪些 Future Trigger 会让一个任务从 Strong-model-first 迁移到 Small-first？
14. 什么证据足以从 PEFT 升级到 Full Fine-tuning？
