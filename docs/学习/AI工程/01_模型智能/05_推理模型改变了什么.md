# 推理模型改变了什么

> 唯一职责：解释为什么同一个模型请求可以投入不同程度的推理计算，以及这会怎样改变质量、延迟和成本。
> 读完要能回答：一次模型调用什么时候值得“多想一会儿”，什么时候应该保持快速路径？
> 阅读前最好先理解 Transformer 与模型规模扩展。本章只讨论单次调用内部的推理预算；模型选择和跨多次调用的 Agent 执行各由后续章节继续展开。

## 同一次调用，为什么有时值得多想一会儿

把一封普通邮件分类成“账单 / 营销 / 其他”，和检查一次高风险数据库迁移，显然不应该消耗相同的智能预算。前者更看重低延迟和吞吐，后者可能值得让模型多做比较、检查和修正。Reasoning 章讨论的就是**一次调用内部**这笔计算预算怎么分配。

### 本节新词

- **Reasoning（推理）**：在本章指模型在最终回答或下一步动作前，用更多计算进行分析、比较、检查和修正的过程。它发生在一次调用内部，不等于 Agent 跨多轮持续执行。
- **Model Invocation（模型调用）**：应用向模型发起一次输入并接收一次模型结果的运行边界。一次 Agent Task 可以包含很多次 Invocation。
- **Inference-time Compute / Test-time Compute（推理时／测试时计算）**：模型训练完成后，在真实请求发生时为一次 Invocation 投入的计算量。它和 Scaling 章的训练期 Compute 属于不同阶段。

可以先抓住这一条：

```text
Task
↓
选择合适的模型能力档
↓
Model Invocation
↓
分配本次 inference-time compute
↓
Answer / Decision
```

后面的推理预算、预算选择条件，以及 Quality/Latency/Cost 都是在这条链上回答“多投入多少才值得”。Agent Loop 等真正跨 Invocation 的机制留到后续 Agent 章节。

## Test-time Compute 怎样改变一次调用

<a id="ch05-reasoning-definition"></a>
### 3.1 Reasoning：把更多计算放到一次调用里

#### 本节新词

- **FAST / REASON Profile（快速／推理档）**：本系列用来表示低推理预算与高推理预算两类能力档位的工程称呼。它可以映射不同模型，也可以映射同一模型的不同运行设置，不是固定厂商协议。

把开篇的定义落到资源上看，就是同一次 Invocation 可以走不同计算档位：

```text
FAST profile
Input → lower compute budget → Output

REASON profile
Input → more analysis/checking budget → Output
```

这是一种资源分配问题，因此可以被调度。

<a id="ch05-inference-time-compute"></a>
### 3.2 Inference-time Compute / Test-time Compute

Scaling 章的 Scaling 主要讨论训练阶段的 Parameters / Training Tokens / Compute。到了推理阶段，系统还可以决定每次请求投入多少额外计算。

```text
Training-time scale
→ 训练出能力底座

Inference-time compute
→ 这一次调用使用多少能力预算
```

这并不意味着推理计算可以无限替代更好的模型或更好的训练。它只是新增了一条“质量 ↔ 延迟 / 成本”的控制轴。

<a id="ch05-reasoning-budget"></a>
### 3.3 Reasoning Budget：推理也要有预算

#### 本节新词

- **Reasoning Budget（推理预算）**：系统愿意为一次 Decision 支付的推理计算额度。不同模型可能用不同参数或内部机制表达它，所以架构层不要把 Budget 绑定到某个固定 Token 数。
- **API — Application Programming Interface（应用程序接口）**：软件之间按约定字段发起请求、读取结果的程序接口。本节提到的推理参数是模型服务 API 暴露的控制方式，不代表所有模型内部都使用同一种实现。

这个预算不一定表现为一个公开 Token 数；具体模型 / API 可以用不同参数或内部策略实现。但架构层只需要知道：

```text
more budget
→ usually more latency / cost
→ may improve difficult decisions
→ does not guarantee correctness
```

<a id="ch05-reasoning-vs-cot"></a>
### 3.4 Reasoning ≠ Chain of Thought disclosure

#### 本节新词

- **Chain of Thought（思维链，CoT）**：模型在求解过程中形成的中间推理表达。系统可以获得推理能力，却不需要把模型私有 CoT 全量保存或公开。
- **Plan（计划）**：系统可外部记录的后续步骤安排，服务于任务执行和恢复；它和模型内部未公开的推理过程不是同一个对象。
- **Decision（决策）**：当前阶段已经作出的选择，例如“采用方案 B”或“下一步调用测试工具”，应能被任务状态引用。

模型可以进行内部推理，但系统不应依赖“完整打印私有 Chain of Thought”来维持 Task continuity。

真正值得外部保存的是 Plan、Decision、State，以及后续 Runtime / Durable Execution 会正式定义的 Evidence、Artifact 和 verifier result。它们都是可以被系统重新读取或验证的对象；任务怎样跨调用继续，留到 Runtime/Task 与 Durable Execution 两章展开。

<a id="ch05-reasoning-vs-agent-loop"></a>
### 3.5 Reasoning ≠ Agent Loop

```text
Reasoning
= one invocation 内部判断深度

Agent Loop
= multiple invocations 之间
  Observe → Decide → Act → Observe
```

一道复杂数学题可以高 Reasoning、零 Tool；一个网页填表 Agent 可以低 Reasoning、很多轮 Loop。

因此：**Reasoning 提高单次 Decision 的质量；Agent Loop 扩展 Decision 能够持续影响环境并根据反馈修正的能力。**

<a id="ch05-temperature-boundary"></a>
### 3.6 Temperature ≠ Reasoning Effort

#### 本节新词

- **Reasoning Effort（推理强度）**：模型 API 或运行配置用来表达一次调用要投入多少推理计算的控制轴。它影响计算预算；Temperature 主要影响采样分布，两者不能互相替代。

Temperature（温度）主要影响输出分布的采样随机性；Reasoning Effort 主要影响模型在一次调用中投入的推理计算。

```text
lower temperature
≠
more reasoning

more reasoning
≠
guaranteed correct
```

Temperature 已在 Transformer 章解释。

<a id="ch05-model-vs-reasoning-routing"></a>
### 3.7 选模型和分配推理预算是两个轴

Scaling 章已经说明不同模型会形成不同 Capability Profile。到了运行时，系统先决定“让谁做”，还可以再决定“这一次值得想多深”。后面的 Routing 章会把第二类系统决策正式称为 Reasoning Routing。

```text
Model choice
Task → model / profile
“让谁做？”

Reasoning budget
Invocation → reasoning effort
“这次投入多少推理？”
```

FAST / REASON 可以作为工程档位，不要求物理上必须是两套模型。这里先建立两个轴的区别，不再提前维护 Routing Policy。

<a id="ch05-routing-inputs"></a>
### 3.8 什么时候值得增加推理预算

#### 本节新词

- **Difficulty / Risk / Uncertainty（难度／风险／不确定性）**：决定一次调用该投入多少推理预算时常用的三个输入维度，分别描述任务分析复杂度、错误代价和当前信息不足程度；它们不能被压成一个“难度分”。
- **Verification Need（验证需求）**：结果在提交前需要多强的独立检查，例如多候选比较、规则验证或环境回读；高验证需求不等于只让模型多想。
- **Latency Budget / Cost Budget（延迟预算／成本预算）**：系统为一次任务允许消耗的时间和费用上限，与质量和风险一起限制 Reasoning Effort。

增加推理预算不能只看一句“这个任务看起来难”。一个问题可能分析复杂但错误代价很低，也可能题目很短却风险极高；信息不足时，不确定性又会和难度混在一起。系统还要同时看 Verification Need，以及允许付出的 Latency / Cost Budget。

高风险不等于“只让模型想更久”。有些高风险动作更应该进入 Durable Execution 章的 Permission / Approval / deterministic verifier。

<a id="ch05-routing-policy"></a>
### 3.9 把推理预算写成可评估规则

如果每次都靠模型自己说“这题很难，我要多想”，系统很难解释成本，也无法稳定回归。第一版规则完全可以很简单：

```text
if deterministic:
    use code/rule
elif easy_and_low_risk:
    low reasoning
elif ambiguous_or_complex:
    medium/high reasoning
elif high_risk:
    stronger reasoning + verifier / approval
```

重点是：Reasoning 是可调度资源，不是永远 MAX。

<a id="ch05-cost-tradeoff"></a>
### 3.10 Quality / Latency / Cost 的三角关系

#### 本节新词

- **Quality / Latency / Cost（质量／延迟／成本）**：评估 Reasoning Effort 是否值得时必须共同观察的三类结果。提高计算预算可能提升 Quality，同时通常增加 Latency 和 Cost，所以要看真实业务 Slice 的增量收益。
- **Critical Error（关键错误）**：会造成高业务损失、安全问题或不可接受结果的失败类型。平均成功率提高，如果关键错误没有下降，也不一定值得增加推理预算。

高 Reasoning × 长 Agent Loop 是最昂贵组合。

因此成熟系统应该通过 Eval 观察：

```text
增加一档 reasoning effort
→ 成功率提高多少？
→ latency 增加多少？
→ cost 增加多少？
→ critical error 是否下降？
```

如果高 effort 对某个 Slice 没有显著增益，就应该降级，而不是把“更深推理”当成身份象征。

<a id="ch05-current-fact-example"></a>
### 3.11 当前事实｜2026-09-03：Reasoning effort 已成为显式 API 控制轴

#### 本节新词

- **`reasoning.effort`**：OpenAI 当前 API 用于配置推理强度的字段。具体可选档位会随模型和产品变化，不能写成跨厂商、跨时间都固定的标准。

OpenAI 当前官方 Model Guidance 把 `reasoning.effort` 作为显式参数；GPT-5.6 当前支持 `none / low / medium / high / xhigh / max`。这支持“Reasoning Budget / Routing 是运行时可配置资源”的工程抽象；具体档位、模型名和默认值只是当前产品事实，不属于稳定定义。

核验来源：[OpenAI Model Guidance](https://developers.openai.com/api/docs/guides/latest-model) 与 [OpenAI Models](https://platform.openai.com/docs/models)。
