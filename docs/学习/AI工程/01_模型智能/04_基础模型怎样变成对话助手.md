# 基础模型怎样变成对话助手

> 唯一职责：解释一个会续写的基础模型怎样被训练和包装成稳定的对话助手。
> 读完要能回答：模型为什么需要额外学习“听指令、遵守角色、偏向更合适的回答”，而这些软行为为什么仍不能代替系统权限？
> 阅读前最好先理解 Transformer、BERT/GPT 与模型规模扩展。本章只讲从基础模型到对话助手的行为塑形和消息协议；工具调用、长期任务和权限控制留到后续章节。

<a id="ch04-30s-core"></a>
<a id="ch04-3m-mental-model"></a>
## 为什么“会续写”还不够成为助手

把“请总结这份报告”直接交给一个只完成通用预训练的模型，模型可能给出摘要，也可能继续模仿原文、续写问题本身。预训练让它学会语言和大量任务模式，却没有天然规定“用户说的话就是需要服从的指令”。从这里开始，问题从“模型会什么”转成“模型怎样表现”。

### 本节新词

- **Base Model（基础版模型）**：完成通用 Pre-training、具备语言和知识能力，但还没有被充分塑造成指令助手的模型版本。这里的 Base 描述训练／行为阶段，不等于 Foundation Model 的“公共基座”角色。
- **Post-training（后训练）**：Pre-training 之后，为指令遵循、偏好、安全或专项行为继续训练模型的一组阶段。它会改变模型参数，不等于本轮 Prompt 或 Context 临时变化。
- **Chat Assistant（对话助手）**：以多轮对话、解释和生成帮助用户完成交流任务的产品形态。它需要模型行为、角色协议和应用运行层共同配合，但还不自动拥有 Agent 的持续行动能力。

先只保留最短的转变链：

```text
Pre-training
→ Base Model
→ Post-training
→ 更稳定的指令 / 偏好行为
→ 对话协议与应用层
→ Chat Assistant
```

SFT、Preference、RLHF、DPO、Chat Template 等对象都属于这条链的不同位置，等正文真正走到它们时再解释。

## 助手行为是怎样被训练和编码出来的

<a id="ch04-base-assistant-gap"></a>
### 3.1 Base Model 为什么不能直接等同 Assistant

#### 本节新词

- **Behavior Gap（行为差距）**：模型已经具备某种底层能力，但面对真实用户指令时仍不能稳定按期望方式表现的差距。它指“能力怎样被使用”的问题，不等于模型完全没有这项能力。

Transformer 与 BERT/GPT 两章已经解释 next-token generation 与 ICL。即便 Base Model 能回答很多问题，它的底层训练目标仍然更接近：

```text
看到前缀
↓
预测后续 Token
```

用户却期待：

```text
把这段输入当成任务
↓
理解意图和约束
↓
按助手角色执行
```

这中间存在 **Behavior Gap（行为差距）**。Post-training（后训练）就是把已经存在的基础能力调整成更符合“助手使用方式”的行为。

<a id="ch04-instruction-sft-tuning"></a>
### 3.2 Instruction Dataset ≠ SFT ≠ Instruction Tuning

#### 本节新词

- **Instruction Dataset（指令数据集）**：由任务指令、可选 Context 和理想 Assistant 回复组成的训练数据，负责提供“拿什么教模型”的样本。
- **SFT — Supervised Fine-Tuning（监督微调）**：用监督目标继续更新模型参数的训练方法，回答“怎么训练”。它和把示例临时放进 Context 的 Few-shot ICL 不同。
- **Instruction Tuning（指令调优／指令微调）**：让模型更会理解并执行自然语言任务的训练目标，常用 SFT 实现；目标、数据和训练方法不能画成同一个词。

| 概念 | 是什么 | 类比 |
|---|---|---|
| Instruction Dataset | 指令 + 上下文 + 理想回答的数据 | 教材 |
| SFT | 用监督目标继续训练模型的方法 | 教学方法 |
| Instruction Tuning | 让模型更会遵循自然语言任务的目标 | 培养目标 |

三个概念经常一起出现，但不能画等号。

<a id="ch04-sft-next-token"></a>
### 3.3 SFT 仍然是 next-token training

#### 本节新词

- **Next-token Loss（下一 Token 损失）**：比较模型对下一个 Token 的预测与训练目标之间差距的损失信号。SFT 改变了样本内容和目标行为，但通常仍沿自回归 next-token 训练机制更新参数。

SFT 并没有把 Transformer 换成另一种推理机器。训练时仍然是在给定前文的情况下预测后续 Token，只是数据分布变成大量高质量“指令 → Assistant 回复”。

```text
System / User / Context
        ↓
Ideal Assistant Response
        ↓
next-token loss
        ↓
update parameters
```

因此 SFT 会改变参数；这与 BERT/GPT 章的 In-context Learning 完全不同：ICL 只改变当前 Context，不更新模型参数。

<a id="ch04-instruction-data-quality"></a>
### 3.4 Instruction Data 的价值不只在数量

#### 本节新词

- **Boundary Example（边界样本）**：专门覆盖临界条件、拒答条件、权限边界等容易出错位置的训练或评估样本；它帮助模型学会“什么时候不能照常回答”。
- **Deduplication（去重）**：识别并移除重复或近重复训练样本，避免数据量看似增加、实际只是重复强化少数模式，也减少 Train/Test 泄漏风险。

如果数据把“模糊指令 → 含糊回答”“危险请求 → 无边界执行”“结构任务 → 不稳定格式”大量教进模型，SFT 只会更稳定地复现这些模式。

所以高质量 Instruction Data 往往需要：

- 任务覆盖；
- 边界样本；
- 反例；
- 格式一致性；
- 去重；
- 难度分布；
- 人工 / 自动验证。

这和 Scaling 章的 Synthetic Data 原则相连：生成数据不是自动真值。

<a id="ch04-preference-data"></a>
### 3.5 Preference Data：多个可行答案中“哪个更好”

#### 本节新词

- **Preference Data（偏好数据）**：对同一输入下多个可行回答表达相对优劣的数据，例如 Chosen / Rejected。它可以代表产品、安全或一般质量标准，不等于某个用户的长期 Personalization。
- **Chosen / Rejected（偏好样本中的优选／劣选回答）**：同一 Prompt 下被比较的回答对，告诉训练过程“更偏向哪一个”。它们表达相对偏好，不表示 Chosen 就是唯一事实真相。

这些偏好并不只是“某个用户喜欢蓝色，所以模型永远说蓝色”。训练信号可以来自：

- 一般人类偏好；
- 安全原则；
- 产品规范；
- 业务标准；
- 对准确、简洁、帮助性的比较。

典型形式：

```text
Prompt
├─ Answer A  ← chosen
└─ Answer B  ← rejected
```

它表达的是相对偏好，而不是唯一绝对答案。

<a id="ch04-rlhf"></a>
### 3.6 RLHF：把人类比较转成可优化的奖励信号

#### 本节新词

- **RLHF — Reinforcement Learning from Human Feedback（基于人类反馈的强化学习）**：把人类对回答的比较转成奖励信号，再用强化学习方法调整模型行为的经典偏好优化路线。
- **Reward Model（奖励模型）**：学习给候选回答的偏好程度打分的模型，主要承担“裁判”责任；它与蒸馏中提供示范的 Teacher Model 不同。
- **Policy（策略／被优化模型）**：强化学习语境里根据输入产生行为的对象，这里通常就是正在被优化的语言模型；不要和 Runtime 的权限 Policy 混淆。

**Reinforcement Learning from Human Feedback（基于人类反馈的强化学习，RLHF）**经典链路可以简化为：

```text
Human preference comparisons
        ↓
Reward Model
        ↓
score candidate behaviors
        ↓
RL optimization
        ↓
policy/model behavior shifts
```

把它和蒸馏里的 Teacher Model 放在一起就更容易看清：Reward Model 主要给候选行为打偏好分，Teacher Model 主要提供示范或训练信号。二者都可能参与训练链，但承担的不是同一种责任。

<a id="ch04-dpo"></a>
### 3.7 DPO：直接学习 Chosen / Rejected

#### 本节新词

- **DPO — Direct Preference Optimization（直接偏好优化）**：直接利用 Chosen / Rejected 对训练模型偏好，不要求完整复制经典 RLHF 的独立 Reward Model + RL 优化链。它是一条偏好优化路线，不是“自动更好”的算法标签。
- **Preference Learning（偏好学习）**：让模型在多个可接受行为中更偏向目标风格、安全或质量标准的训练问题，RLHF 与 DPO 都属于这个更大的范畴。

相较经典 RLHF 的 `Reward Model → RL optimization` 链，DPO 直接使用 chosen / rejected pair 建立偏好优化目标：

```text
Prompt + Chosen + Rejected
        ↓
preference objective
        ↓
model update
```

应用层不需要把它理解成“DPO 永远优于 RLHF”。更重要的是：二者都属于 Post-training 中的 Preference Learning（偏好学习）路线。

<a id="ch04-alignment"></a>
### 3.8 Alignment 不是一个算法

#### 本节新词

- **Alignment（对齐）**：让模型行为更符合人类意图、产品目标、安全要求和社会约束的广义目标。它可以由多种训练、评估和 Runtime 控制共同实现，不是单一算法名。
- **Red Teaming（红队测试）**：主动设计攻击、绕过和危险场景去暴露模型或系统失败的评估方式；它用于发现边界，不等于训练本身。

因此，对齐通常不是某一步训练单独完成，而是多种训练、评估和运行约束共同作用：

```text
SFT
+ Preference Learning
+ Safety Training
+ Policy Data
+ Evaluation / Red Teaming
+ Runtime hard controls
```

最后一项必须分层：Runtime 的硬控制不是“模型 Alignment 算法”的一部分，而是生产系统的外部治理。

<a id="ch04-base-instruct-chat"></a>
### 3.9 Base / Instruct / Chat 与 Code / Math / Vision 是不同维度

#### 本节新词

- **Instruct Model（指令模型）**：经过指令相关 Post-training、更稳定按任务要求执行的模型形态。
- **Chat-oriented Model（对话导向模型）**：进一步围绕多轮角色消息和助手交互进行适配的模型形态；厂商命名不统一，不能只凭名字判断训练细节。
- **Code / Math / Vision Capability（代码／数学／视觉能力领域）**：模型擅长处理的任务域，与 Base/Instruct/Chat 这种训练和交互形态可以交叉组合。

```text
训练 / 行为形态维度：
Base → Instruct → Chat-oriented

能力领域维度：
General / Code / Math / Vision / Reasoning ...
```

它们可以交叉组合。例如一个 Code-oriented model 也可以有 Base / Instruct 版本。

不要把“Chat”理解成一种能力领域，也不要把“Code model”自动理解成未对齐的 Base Model。

<a id="ch04-role-protocol"></a>
### 3.10 Role：System / User / Assistant / Tool

#### 本节新词

- **Role（消息角色）**：对话协议用来标记“这段内容由谁提供、系统应怎样解释它”的消息类型。Role 是输入协议，不直接等于权限级别。
- **System / User / Assistant / Tool**：分别表示系统级指导、用户输入、助手输出和外部工具结果等常见消息角色；Tool Result 不会因为被标成 Tool 就获得 System 的控制权。

对话产品需要明确“谁说了什么”。一次真实消息序列可以是：System 给出产品规则，User 提问，Assistant 请求 Tool，Tool 返回结果，Assistant 再生成最终回答。Role 让模型和应用知道这些内容来自不同位置，但 Role 名称本身不会给 Tool Result 提升到 System 权限。后面的可靠执行章节会进一步区分高权控制规则、低权数据输入，以及数据中夹带恶意指令的问题。

<a id="ch04-prompt-chat-template"></a>
### 3.11 Prompt Template ≠ Chat Template

#### 本节新词

- **Prompt Template（提示模板）**：应用层把变量填入任务说明和格式要求的可复用文本结构，服务于业务输入组织。
- **Chat Template（对话模板）**：把带 Role 的消息序列序列化成模型训练时熟悉的 Token / special-token 格式，属于模型协议层。用错它可能造成角色和 Tool 消息解析异常，不是简单“文案没写好”。
- **Special Token（特殊 Token）**：模型词表中用于标记角色、分隔或控制结构的特殊符号，参与协议编码，不等同普通自然语言词元。

把两者放进同一次请求就很容易看出边界：应用先生成业务提示内容，例如：

```text
“请根据 {context} 总结 {question}”
```

随后模型协议层再把角色消息编码成模型熟悉的 Token / special-token 结构：

```text
messages[]
↓
role-aware serialization
↓
model tokens
```

错误的 Chat Template 可能造成角色混乱、System 指令遵循下降、Tool 消息结构不稳定。这不是“Prompt 写得不好”这一层的问题。

<a id="ch04-conversation-continuity"></a>
### 3.12 模型调用本身通常不是 Conversation Memory

#### 本节新词

- **Conversation Continuity（对话连续性）**：用户多轮交流时仍能延续先前信息的产品效果，通常由应用／Runtime 重新装配历史或摘要实现。
- **Conversation Memory（对话记忆）**：为了维持连续交互而保存并重新取用的历史信息；它不是普通模型 Invocation 自带的永久记忆，后续 State/Context/Memory 章会做正式分层。

普通推理调用可以近似理解成：

```text
Input Context
→ Model Invocation
→ Output
→ invocation ends
```

下一轮还能“记得上一轮”，通常是 Chat Application / Runtime 把历史消息、摘要或其他信息重新装配进新的 Context。

最简单的例子就是：第一轮用户说“我叫小明”。如果第二次 Invocation 只收到“我叫什么？”，普通模型调用并没有一块自动持久的记忆知道答案；应用把上一轮消息或等价摘要重新放进 Context 后，产品才表现出对话连续性。这个“记得”首先是应用行为，不等于模型参数被改了。

这里要守住章节边界：

- 本章只说明 **Chat product continuity 的应用边界**；
- Agent Runtime / Task continuity → Runtime/Task 章；
- State / History / Context / Memory → State/Context/Memory 章。

<a id="ch04-model-instruction-permission"></a>
### 3.13 Model Behavior ≠ Current Instruction ≠ Runtime Permission

#### 本节新词

- **Current Instruction（当前指令）**：这一次调用里交给模型的任务和约束，只影响本轮 Context，并不会自动改变长期参数。
- **Runtime Permission（运行时权限）**：系统在模型之外强制决定哪些现实动作允许发生的硬边界。模型“愿不愿意”执行和 Runtime “允不允许”执行必须分开。

```text
Model parameters
→ 长期行为倾向

Current instruction / context
→ 本轮要求

Runtime Permission / Policy
→ 现实动作能不能发生
```

这是生产系统极重要的三层边界。

“模型拒绝危险请求”是有价值的软边界；但文件删除、付款、部署、发信等真实副作用不能只依赖 Prompt。Permission、Policy 与 Approval 留到 Durable Execution 章。

<a id="ch04-chatgpt-composition"></a>
### 3.14 ChatGPT 为什么是产品突破

#### 本节新词

- **Chat UI（对话界面）**：让用户直接用自然语言连续输入并查看模型回复的交互层。它本身不是模型能力，却显著降低了普通用户使用通用模型的门槛。
- **Cloud Inference Runtime（云端推理运行层）**：在云端承载模型请求、计算和会话配套服务的运行基础设施；它负责把模型能力稳定提供给产品，不等于模型参数。

把 ChatGPT 只理解成“一个更大的 GPT”会丢掉产品层变化。更稳定的构成图是：

```text
Strong foundation model
+ Post-training / Alignment
+ Role / Chat Template
+ Conversation Context handling
+ Cloud inference runtime
+ Simple Chat UI
= Chat Assistant Product
```

这解释了为什么 ChatGPT 的爆发不是一个单一新算法事件，而是模型、后训练、会话形态和基础设施共同成熟。

<a id="ch04-chat-vs-agent"></a>
### 3.15 Chat Assistant ≠ Agent

#### 本节新词

- **Agent（智能体）**：能够围绕 Goal 持续观察、决策、调用能力并维护任务状态的执行主体。Chat Assistant 可以成为 Agent 的交互入口，但仅会多轮对话或 Function Calling 还不足以形成完整 Agent。
- **Agent Loop（智能体循环）**：Agent 在多步任务中反复 Observe → Decide → Act 的控制循环；它跨多次模型调用和环境反馈，不属于单次聊天生成机制。

Chat Assistant 主要目标：

```text
交流
生成
解释
多轮帮助
```

Agent 则进一步要求：

```text
Goal
+ Tool / Capability          → Tool 章
+ Agent Loop / Harness       → Agent Loop 章
+ Runtime / Task             → Runtime/Task 章
+ State / Memory / Context   → State/Context/Memory 章
+ Permission / Recovery      → Durable Execution 章
```

所以“能聊天、会 Function Calling”仍不自动等于完整 Agent。

<a id="ch04-prompt-rag-sft-tool"></a>
### 3.16 四种增强方式不要混

#### 本节新词

- **Enhancement Path（能力增强路径）**：这里用来区分 Prompt/ICL、RAG、SFT、Tool 分别改变哪一层：当前输入、外部知识、模型参数或现实动作。它不是新的正式协议名，而是本系列用于做架构判断的分类方法。

```text
Prompt / ICL → 这次怎么表达任务
RAG          → 这次参考什么外部资料
SFT          → 训练进什么长期行为
Tool         → 真正去外部世界做什么动作
```

这些概念分别在 BERT/GPT、RAG、Post-training 和 Tool 章节展开；这里集中解释 SFT 与其他 Post-training 方法怎样改变模型行为。
