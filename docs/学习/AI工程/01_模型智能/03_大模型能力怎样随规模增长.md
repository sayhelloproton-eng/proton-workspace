# 大模型能力怎样随规模增长

> 唯一职责：解释训练规模怎样改变模型能力，以及应用系统为什么不能只按模型大小做生产选型。
> 读完要能回答：为什么“预测下一个 Token”能逐渐表现出通用能力，参数、数据和计算投入又怎样共同影响结果？
> 阅读前最好先理解 Transformer、自回归生成，以及 BERT/GPT 两条路线。本章从训练规模一路走到真实业务评估和模型选择；推理预算留到下一章。

<a id="ch03-30s-core"></a>
<a id="ch03-3m-mental-model"></a>
## 模型为什么会随着训练规模变化

上一章看到 GPT 把很多任务统一成 next-token generation。接下来的问题不是“参数越多是不是越聪明”，而是：训练一个更大的模型时，究竟扩大了什么；这些投入怎样共同影响模型能力；为什么生产系统最后仍然不能只看模型大小。

### 本节新词

- **Pre-training（预训练）**：模型在进入具体产品适配之前，用大规模数据学习通用语言、知识与模式的训练阶段。它主要塑造能力底座，不等于后续为了指令遵循和偏好继续做的 Post-training。
- **Parameters（参数）**：训练过程中被优化、推理时用于计算的模型数值。参数量表示模型容量的一部分，不是一条参数对应一条事实。
- **Training Tokens（训练 Token）**：预训练阶段实际用于学习的 Token 数量，描述模型看过多少训练信号；它和一次用户请求里的 Context Token 不是同一个统计口径。
- **Compute（计算投入／算力）**：完成训练所消耗的计算资源。它和 GPU 数量有关，但不是简单的“有多少张卡”，还受训练时长、利用率和并行方式影响。
- **Scaling（规模扩展）**：同时扩大模型容量、训练数据和计算投入等训练规模变量，以继续提升模型能力的路线。它不能被缩写成“只堆参数”。

先用一条很短的链抓住本章前半段：

```text
next-token objective
        ↓
Pre-training
Parameters + Training Tokens + Compute
        ↓
模型能力底座发生变化
```

后半段再回答两个生产问题：大容量模型怎样降低每次计算成本，以及当不同模型各有强弱时，系统怎样用真实评估选择处理路径。具体模型架构、业务评测和模型选择策略等术语，等真正进入对应问题时再解释。

## 能力为什么会随规模变化，又在哪里失效

<a id="ch03-gpt-scaling-bridge"></a>
### 3.1 GPT-1 / GPT-2 / GPT-3：从预训练迁移到 ICL

这三代模型真正重要的不是“每一代参数变大”这一句话，而是开发范式逐步改变：

```text
GPT-1
通用预训练 → 下游 Fine-tuning 可行

GPT-2
统一 next-token objective
→ 同一个生成模型出现多任务迹象

GPT-3
更大规模 + 更广数据
→ Zero / One / Few-shot ICL 变得非常显著
```

BERT/GPT 章已经解释了 In-context Learning（上下文学习）。这里继续追踪它与 Scaling 的历史关系：**模型能力越来越通用，应用适配逐渐不再要求每个任务都重新训练专项模型。**

<a id="ch03-next-token-generalization"></a>
### 3.2 为什么 next-token prediction 会逼模型学习很多东西

要在开放文本中稳定预测“下一个 Token”，模型不能只背语法。它需要逐渐编码：

- 语言结构；
- 常见世界知识；
- 代码模式；
- 语义关系；
- 某些逻辑与任务格式；
- 长上下文中的依赖。

这不意味着 next-token objective 自动保证“理解”和“正确推理”，而是说明一个统一、覆盖面极广的训练目标可以把很多下游模式压进同一参数系统。

<a id="ch03-foundation-base-boundary"></a>
### 3.3 Foundation Model ≠ Base Model

#### 本节新词

- **Foundation Model（基座模型／基础模型）**：能够作为多个下游任务、应用或派生模型共同起点的通用模型，强调的是“一个基座服务很多下游”的系统角色。它不等于厂商模型名称里的 Base。
- **Base Model（基础版模型）**：相对于 Instruct / Chat 等后训练形态，通常指尚未充分面向助手交互进行指令与偏好塑形的模型版本。它描述训练／行为阶段，不是“是否能作为 Foundation”的判断。

这两个维度放在一起看最清楚：

```text
Foundation Model
= 一个基座服务多个下游

Base / Instruct / Chat
= 同一模型家族中的训练 / 行为形态维度
```

所以一个 Instruct Model 仍然可以是 Foundation Model；二者不是互斥分类。

<a id="ch03-scaling-variables"></a>
### 3.4 Scaling：Parameters + Training Tokens + Compute

#### 本节新词

- **FLOPs — Floating-point Operations（浮点运算次数）**：粗略衡量训练或计算过程执行了多少浮点运算的计量口径。它能描述计算量，不能直接当成模型能力、线上延迟或业务成功率。

应用层最危险的简化是：

```text
模型更强
= 参数更多
```

更准确的稳定心智模型是：

```text
Training Scale
≈ Parameters
+ Training Tokens
+ Compute
+ Data Quality
+ Architecture / Optimization
```

其中前三者是 Scaling 时代最核心的规模变量。数据质量、训练策略与架构决定同样资源是否被有效利用。

参数量更像**容量上限的一部分**，不是事实数量，也不是单独的能力分数。

训练团队还会用 **FLOPs（Floating-point Operations，浮点运算次数）**粗略核算一次训练消耗了多少计算。它回答“做了多少计算”，不直接回答“模型有多聪明”：相同 FLOPs 会因数据质量、架构、优化器、训练稳定性和硬件利用率不同而产生不同结果。生产选型也不能拿训练 FLOPs 代替实际延迟、吞吐、成本和任务成功率。

<a id="ch03-scaling-law"></a>
### 3.5 Scaling Law 与 Diminishing Returns

#### 本节新词

- **Scaling Law（缩放规律／规模定律）**：在特定数据分布、架构、训练方法和规模范围内，描述 Loss 或某些性能指标随模型、数据、算力投入变化的统计规律。它帮助估算投入趋势，不保证“更大一定更聪明”。
- **Diminishing Returns（边际收益递减）**：继续增加投入仍可能有收益，但每获得一单位额外提升要付出越来越高的资源成本。它解释为什么 Scaling 后期会同时追求更高效架构和更精细模型选择。

这两条规律合起来，把训练投资从“纯试错”推向了更可预测的资源决策，同时也迫使生产系统开始计算每一单位额外质量要付出的代价。

因此更合理的问题不是：

> 最大模型是谁？

而是：

> 在这个业务 Slice 上，为了再提高 1% 成功率，要增加多少延迟、成本与风险？

<a id="ch03-training-serving-systems"></a>
### 3.6 Scaling 把模型变成分布式系统问题

#### 本节新词

- **GPU Cluster（GPU 集群）**：把多张 GPU、甚至多台机器组织成共同训练或推理资源池的系统。它解决单设备容量和吞吐不足，不是新的模型架构。
- **Data Parallelism / Model Parallelism（数据并行／模型并行）**：前者让多个设备处理不同数据副本后同步训练结果，后者把同一个模型的计算或参数拆到多个设备。二者都属于分布式训练方法。
- **Checkpoint（检查点）**：训练或长任务过程中保存的可恢复状态快照；模型训练 Checkpoint 保存参数／优化器等状态，不要和 Agent Memory 混淆。
- **Serving（在线推理服务）**：把已经训练好的模型以服务形式接收真实请求、调度计算并返回结果的运行层，和 Training 是不同生命周期。
- **Batching（批处理）**：把多个请求或计算单元组合后一起执行，提高硬件利用率；它优化吞吐，不等于把多个用户 Context 合并成一个会话。
- **Scheduler（调度器）**：决定请求何时、在哪些计算资源上执行的运行组件；它管理执行顺序和资源，不负责判断模型语义能力。
- **Replica（服务副本）**：同一模型服务的多个可接收请求实例。Serving Load Balancer 在副本之间分配请求，和后面模型内部“给 Token 选择专家”的路由器不在一层。

大规模训练会进入 GPU cluster、数据并行 / 模型并行、通信、checkpoint 等系统工程；Serving（在线推理服务）则出现另一组问题：

```text
Request
↓
Context / KV Cache
↓
Batching / Scheduler
↓
Replica / Accelerator
↓
Decode
↓
Response
```

这里要保持 Transformer 章的边界：KV Cache 是推理缓存，不是 Agent Memory。

Serving Load Balancer（服务负载均衡器）负责把 request 分配给服务实例；它和下面的模型内部专家选择、后面的应用模型选择都不是同一层。

<a id="ch03-moe"></a>
### 3.7 Mixture of Experts：大容量不等于每次全算

#### 本节新词

- **MoE — Mixture of Experts（专家混合）**：在一个模型内部准备多个 Expert 子网络，再由专门的路由机制为当前 Token 选择少量路径参与计算的架构。它的目标是扩大总容量，同时避免每次都激活全部参数。
- **Expert（专家子网络）**：MoE 中可训练的子网络分支，常承担 FFN/MLP 一类计算。名字里的“专家”来自训练形成的专门化，不表示工程师事先给它固定业务岗位。
- **MoE Router（MoE 路由器）**：根据当前 Token 表示给 Expert 打分并选择激活路径的模型内部组件。它做 token→expert 选择，不处理应用请求该用哪个模型。
- **Sparse Activation（稀疏激活）**：每次只激活全部可用参数中的一部分计算路径，是 MoE 降低单次计算量的关键性质。

**Mixture of Experts（专家混合，MoE）**可以抽象为：

```text
Token representation
        ↓
      Router
    ↙   ↓   ↘
 Expert A B C ...
    \   |   /
 Sparse Activation
        ↓
 merged output
```

Router 为每个 Token 选择少量 Expert，使模型可以拥有很大的总容量，同时每次只激活部分计算路径。

<a id="ch03-moe-routing-boundary"></a>
### 3.8 MoE Router 与 Serving Load Balancer 为什么不能画成一个组件

#### 本节新词

- **Serving Load Balancer（服务负载均衡器）**：在在线推理层把 Request 分配给不同 Replica / Server，关注服务可用性和资源负载。它处理 request→replica，而 MoE Router 处理 token→expert。

先只比较本节已经需要的两种“路由”：

```text
MoE Router
Token representation → Expert
模型内部

Serving Load Balancer
Request → Replica / Server
在线服务基础设施
```

它们都在“选择路径”，但输入、选择对象和系统层完全不同。面向生产任务的模型选择与推理预算分配，等走到生产模型选择时再正式引入，不在这里提前占用读者记忆。

<a id="ch03-moe-balance"></a>
### 3.9 Expert specialization 与 load balance

#### 本节新词

- **Specialization（专门化）**：不同 Expert 在训练中逐渐形成不同参数偏好的现象，不代表它们拥有明确的人类角色标签。
- **Load-balancing Objective / Routing Regularization（负载均衡目标／路由正则）**：训练时约束 Router 不要长期把绝大多数 Token 压到少数 Expert 的机制；这里的“负载均衡”发生在模型训练内部，不是 Serving 负载均衡。

专家的 specialization（专门化）通常来自训练过程中 Router 和 Expert 的共同学习，而不是人工规定“这个专家只能写代码”。

训练还需要避免 Router 长期塌缩到少数专家，因此会引入 load-balancing objective / routing regularization 等机制，目标是让容量得到利用，而不是让某个 Expert 永远过载。

<a id="ch03-total-active-parameters"></a>
### 3.10 Total Parameters ≠ Active Parameters

#### 本节新词

- **Total Parameters（总参数量）**：模型所有参数的总规模，反映整体容量口径。
- **Active Parameters（激活参数量）**：处理当前 Token／当前前向路径时真正参与计算的参数规模。对 MoE 来说，它通常显著小于 Total Parameters。

因此 `Total Parameters ≠ Active Parameters`。对 MoE，二者差异尤其明显。看到厂商参数口径时要先确认它报告的是 total、active，还是其他自定义口径，不能机械横比。

<a id="ch03-distillation-synthetic"></a>
### 3.11 小模型为什么越来越强：Distillation 与 Synthetic Data

#### 本节新词

- **Knowledge Distillation（知识蒸馏）**：用更强 Teacher Model 产生示范、概率信号或训练数据，再训练独立 Student Model 的方法。它是“教另一个模型”，不是把大模型直接删参数变小。
- **Teacher Model / Student Model（教师模型／学生模型）**：蒸馏关系中的能力提供者和学习者。Teacher 的输出仍需过滤和验证，不能因为来自强模型就直接视为事实。
- **Synthetic Data（合成数据）**：由模型或程序生成、而非直接采集自原始现实样本的数据。用于训练前仍需要过滤、验证、去重和抽查，避免把生成错误规模化复制。

真正困难的地方随即从“能不能生成训练样本”变成“Teacher 输出怎样经过筛选后安全进入 Student 的训练集”。可靠链路至少需要：

```text
Generate
↓
Filter
↓
Verify
↓
Deduplicate / Sample
↓
Training set
```

所以今天的小模型可能受益于更好的数据、架构、后训练、蒸馏和合成数据，不能只用参数规模判断“代际强弱”。

<a id="ch03-capability-behavior"></a>
### 3.12 Model Capability ≠ Assistant Behavior

#### 本节新词

- **Model Capability（模型能力）**：模型在语言、代码、知识、表示或推理等任务上能够达到的能力表现，主要由模型层的训练和架构决定。它不等于平台层的 Tool Capability。
- **Assistant Behavior（助手行为倾向）**：模型面对指令时表现出的服从、风格、安全和偏好等行为特征；它可以由 Post-training 明显改变，即使底层知识能力没有同幅度变化。
- **Post-training（后训练）**：Pre-training 之后继续用指令、偏好、安全或任务数据塑造模型行为和专项表现的训练阶段。下一章会展开 SFT、RLHF、DPO。

Pre-training（预训练）更偏向建立基础 Model Capability（模型能力）：语言、代码、知识模式、通用表示和一定推理能力。

这里关注的是后训练带来的行为塑形：指令遵循、回答风格、安全边界和偏好会被进一步调整；SFT、RLHF、DPO 与 Chat Assistant 留到下一章完整展开。

因此：

```text
模型会不会
≠
助手愿不愿意 / 怎么表现
```

这里的 `Model Capability` 是模型层的能力表现；Tool 章的 Capability 是平台可识别、可路由、可治理的通用能力抽象，二者不要混名。一个模型“底层有能力”不代表它天然是一个好助手。

<a id="ch03-model-eval"></a>
### 3.13 Model Capability Eval：Benchmark 与真实 domain/slice evidence

#### 本节新词

- **Benchmark（基准测试）**：使用统一公开或固定题集比较模型表现的方法，适合提供外部参照，但不能代替企业自己的业务验收。
- **Domain Eval（领域评估）**：用目标业务领域的真实或代表性任务评估模型，回答“在我们的工作里能不能稳定完成”。
- **Slice Evaluation（切片评估）**：把总体评估按任务类型、风险、上下文长度等维度拆开，避免平均分掩盖关键长尾失败。
- **MMLU / GSM8K / GPQA / HumanEval / SWE-bench**：不同目标的公开评测集合，分别覆盖多学科知识、数学文字题、高难科学问答、短代码生成和真实仓库 Issue 修复等方向；它们彼此不能互相替代，更不等于你的业务 Eval。

生产模型选择不能停在综合分数。这里真正要做的是把公开参照和自己的业务切片放在一起，看模型在具体任务上的成功率、可靠性、延迟与成本。

一家团队准备给代码修复 Agent 换模型时，看到“综合 Benchmark 更高”还不能下结论。公开评测里的名字分别代表不同问题：**MMLU** 更偏多学科知识与理解，**GSM8K** 更偏小学数学文字题，**GPQA** 更偏高难科学问答，**HumanEval** 检查短代码题及测试通过情况，**SWE-bench** 才更接近在真实仓库、Issue 和测试约束下修改代码。它们能提供外部参照，却没有一个等于这家公司的仓库、工具权限、失败成本和验收流程。

完整的 Vertical Agent / 业务结果评估体系留到 AI Platform 章；这里使用其中与模型选择有关的 Domain Eval evidence。**Slice Evaluation（切片评估）**则把平均分拆开，例如：

```text
普通文本分类
长上下文
结构化 JSON
Tool 参数
风险边界
罕见长尾
```

平均 90% 可能掩盖一个关键 Slice 只有 55%。所以真正的 Model Capability Map（模型能力地图）应该记录各类任务成功率、延迟、成本、风险漏判等，而不是一个总分。

<a id="ch03-capability-map"></a>
### 3.14 Model Capability Map：把评估变成路由依据

#### 本节新词

- **Model Capability Map（模型能力地图）**：把多个模型在不同业务 Slice 上的质量、延迟、成本、风险等真实评估结果组织成可查询的能力画像，供路由策略使用。它不是一张静态排行榜。
- **p50 / p95 Latency（50／95 分位延迟）**：分别表示一半请求和 95% 请求能在该延迟以内完成，用来观察典型体验与尾部慢请求；不要只用平均延迟代表线上体验。

Capability Map 可以包含：

| 维度 | 示例 |
|---|---|
| Quality | task success / correctness |
| Structured reliability | JSON / schema / Tool arguments |
| Safety / risk | critical false negative |
| Latency | p50 / p95 |
| Cost | per task / per token |
| Context | long-context stability |

重要的是**基于真实业务切片持续更新**，而不是把 Benchmark 排名直接写死为路由规则。

<a id="ch03-routing-vs-reasoning"></a>
<a id="ch03-quality-gate"></a>
### 3.15 Capability Map 到这里，Routing 从下一层开始

做到 Model Capability Map 以后，本章已经完成自己的责任：解释为什么模型在不同任务切片上会形成不同的质量、延迟和成本画像。

接下来的系统问题不再是 Scaling 本身，而是**怎样使用这张画像做选择**。后文把“根据任务在多个模型或能力档位之间选择路径”正式称为 Model Routing（模型路由）；如果模型已经确定，还要决定这次请求投入多少推理预算，则属于 Reasoning Routing（推理路由）。

```text
Scaling / training
→ 形成不同模型能力

Domain / Slice Eval
→ 得到 Capability Map

Capability Map + task constraints
→ Routing 选择路径

Model output
→ downstream validation / quality gate
```

这里不再展开 Routing Policy、FAST/REASON、Quality Gate 和 Escalation 的完整规则，否则 Scaling 章会变成第二个 Routing 章。模型与路径怎样组合，由后面的 [Routing 章](../04_Harness与Runtime/05_任务怎样选择模型和路径.md) 正式负责；推理预算为什么是独立维度，由下一章 [Reasoning](05_推理模型改变了什么.md) 接住。

<a id="ch03-small-model-cluster-vs-moe"></a>
### 3.18 应用层小模型集群 ≠ MoE

#### 本节新词

- **Model Cluster / Multi-model System（模型集群／多模型系统）**：应用层部署多个彼此独立的模型，并通过外部 Routing Policy 分配任务的系统形态。它和单个 MoE 模型内部的 Expert 路由不是一回事。

多个独立模型组成的应用层模型集群，是外部 Routing 问题；MoE 是单模型内部的 token→expert 路由。

模型越多也不自动意味着系统更便宜、更稳定：路由错误、冷启动、部署、观测和回退都会增加系统成本。
