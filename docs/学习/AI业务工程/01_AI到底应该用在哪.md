# AI 到底应该用在哪

这一篇从研发视角看 AI 应该用在哪。研发链路里同时存在信息理解、专业判断、代码生成、工具调用、跨系统协作和真实执行，很多 AI 落地问题都会在这里直接暴露出来。

从接到需求开始，到代码上线，再到线上排障，工程师每天都在做这些事：

```text
理解需求
→ 找资料、读代码、找调用关系
→ 设计方案
→ 写代码、改代码
→ 测试、Review
→ 发布
→ 看日志、排障、继续维护
```

AI 几乎可以插进每一步。

但“哪里都能用”不等于“哪里都值得用”。如果只是看到 AI 会写代码，就把重点放在代码生成上，很容易错过真正耗时间、卡交付、甚至过去根本做不起的部分。

判断 AI 应该用在哪，最好沿着研发工作本身往下看：**它到底改变了哪一种限制。**

## 先从最直接的地方看：工程师每天花很多时间在“找”和“理解”上

写代码只是研发的一部分。

接手一个陌生模块时，工程师往往先要搞清楚：入口在哪、谁调用谁、数据从哪里来、这个字段为什么存在、改这里会影响什么。真正耗时间的，常常不是敲下那几十行代码，而是把这些关系弄明白。

这类工作很适合 AI 先介入，因为它本身就依赖大量阅读、搜索、归纳和解释。

例如，工程师要改一个接口。最有价值的第一步未必是让 AI 直接改，而是先让它回答：

- 这个接口在哪些地方被调用？
- 上下游数据怎么流？
- 哪些测试覆盖了它？
- 最近为什么改过这里？
- 哪些地方看起来相关，其实不能一起动？

如果这些问题原来需要人在几十个文件、文档和提交记录里来回找，AI 把信息先收拢，工程师再判断，收益通常比“帮我写一个函数”更稳定。

这里 AI 改变的是**获取和理解上下文的成本**。

但也要看到边界。如果仓库里本来就有明确的调用图、结构化索引或精确搜索，能直接给出确定答案，就应该优先使用这些工具。AI 更适合处理工具结果之外仍需要解释、归纳和关联的部分，而不是把所有确定性查询重新变成一次模型猜测。

## 代码生成当然有价值，但它未必是研发真正的瓶颈

AI 写代码最容易被感知，因为结果立刻可见。

一个 CRUD、一个类型定义、一段数据转换、一个单测骨架，模型可能几秒就能生成。原来需要二十分钟的机械工作，确实可能缩到几分钟。

问题在于，研发交付不是“代码生成完”就结束。如果需求还在反复、上下文没搞清、Review 排队、测试不完整、发布链路很慢，那么代码生成再快，也只是把更多改动更快推到后面的堵点。

比如一个需求从提出到上线要三天，其中真正写代码只占两小时。AI 把两小时压到二十分钟，当然有价值，但整条链并不会因此从三天变成半小时。

所以研发里看 AI 价值，不能只盯“写代码提速多少”。还要看：

- 需求理解是不是反复返工；
- 找代码、找影响范围是不是耗时；
- Review 是不是主要瓶颈；
- 测试是不是经常补不全；
- 发布是不是需要大量人工检查；
- 线上问题是不是因为信息分散而迟迟定位不了。

真正值得优先处理的，是限制交付结果的地方，不一定是模型最容易展示能力的地方。

## AI 还能把一些原本割裂的研发信息重新接起来

研发过程里有大量信息在不同载体之间来回丢失。

需求写在文档里，讨论在聊天里，代码在仓库里，问题留在 Issue 里，历史原因藏在 Git 记录里，线上事实又在日志和监控里。

人每接手一次任务，都要重新把这些东西拼起来。

一个 Bug 从用户反馈进入研发，常见的情况不是“没人会修”，而是先花大量时间确认：哪个版本出现、什么条件触发、对应哪段代码、最近谁改过、有没有类似历史问题。AI 在这里的价值，是把原本散落的信息往一个任务上下文里收拢：从现象找到相关日志，从日志回到代码，从代码找到调用关系，再把历史改动和已有测试一起带进来。

这样减少的不是某一个动作，而是反复切工具、反复搜索、反复重建上下文。

这类能力对老系统尤其重要。系统越大、历史越长、知识越分散，工程师越容易把大量时间花在“重新理解已经存在的东西”上。

## 有些研发流程，AI 进来以后应该被重做，而不是原样加速

研发里也有很多“历史流程”。

例如：

```text
需求文档
→ 工程师手工拆任务
→ 每个人再去找相关代码
→ 开发
→ 手工整理测试点
→ Review 时重新解释背景
→ 发布前再整理一次变更说明
```

如果 AI 能稳定拿到需求、代码和历史上下文，那么“每到一个环节都重新整理一遍”未必还有必要。

更合理的方向可能是让任务上下文一直带着走：需求里的目标和约束，在代码分析时继续使用；代码改动以后，测试点和影响范围跟着更新；到 Review 和发布时，不需要再从零写一份说明。

这时 AI 改变的是研发信息流，而不是单独替代某个岗位。

同样地，有些中间产物只是为了跨环节传递信息。如果后续系统真正需要的是结构化结果，就应该判断这个中间文档还有没有必要，而不是只追求“AI 把文档写得更快”。

## 更大的价值，是把过去人力覆盖不了的研发工作变成可做

AI 不只是把现有工作做快。

大型代码库里有很多事情过去根本做不起：不可能每次改动都人工通读全部相关模块，不可能持续检查所有跨包影响，也不可能让一个工程师随时掌握几十万行代码的全部历史背景。

所以现实里只能抽样、靠经验、靠熟悉模块的人兜底。

AI 和代码索引、调用图、测试、运行验证结合以后，第一次有机会把一些“以前只能靠经验覆盖一部分”的工作做得更广：

- 每次修改前都做更完整的影响分析；
- 按任务动态收集真正相关的代码和文档，而不是让人手工翻；
- 批量生成候选测试，再由工程师确认关键路径；
- 持续对大量改动做结构化检查，把异常集中给人；
- 给刚接手系统的人快速建立局部心智模型。

这些价值不能只用“节省了多少分钟”来算。它改变的是研发原本受限于注意力和上下文容量的上限。

## 什么时候反而不该用 AI

研发里有大量确定性问题，普通工具本来就做得更好。

格式化交给 formatter，类型问题交给 type checker，确定的依赖关系交给代码图，固定规则交给 lint，精确文本查找交给搜索，重复构建和发布步骤交给脚本或 CI。

如果一个问题已经能被确定性工具稳定解决，再套一层模型通常只会增加成本和不确定性。

AI 更适合放在这些工具之间仍需要理解、判断、归纳和生成的部分；确定性工具则负责给它事实、约束和反馈。

## 真准备做之前，先看它改变的是不是最终结果

拿研发场景来说，一个 AI 功能值不值得做，可以连续追几步：

1. 现在工程师真正花时间的地方在哪里，是写代码，还是找上下文、等 Review、补测试、查线上问题？
2. AI 介入以后，减少的是有效工作，还是只是把“写”换成了“检查 AI 写的东西”？
3. 这一环变快以后，整条交付链会不会真的变快，还是瓶颈马上跑到下一步？
4. 这件事有没有更确定、更便宜的工具已经能做好？
5. AI 能不能让原来只能抽样、靠经验或根本做不起的工作第一次被覆盖？
6. 如果答案错了，工程师能不能很快发现；如果不能，这个场景就不能只按提效来算。

例如，AI 十秒写完一段代码，但工程师为了确认上下文、行为和边界要花二十分钟 Review，这不一定比自己写更省。

反过来，如果工程师原来要半天才能摸清一个陌生模块的调用关系和历史背景，AI 配合代码图、搜索和文档把相关信息先整理出来，即使最后代码还是人写，价值也可能更大。

所以从研发视角看，AI 最值得进入的地方，通常不是“模型最会表演什么”，而是下面这些地方：

```text
人反复找和理解信息的地方
→ 专业工程师长期被低价值工作占住的地方
→ 需求、代码、测试、发布之间上下文反复丢失的地方
→ 因为人工限制而形成了多余步骤的地方
→ 过去因为代码量、信息量、检查成本太高而根本覆盖不了的地方
```

找到这些位置以后，再决定用模型、搜索、RAG、工具、Agent，还是普通程序。技术应该跟着问题走，而不是反过来。

## 找到值得用 AI 的位置之后，还要判断能把责任交到哪一步

前面解决的是“哪里值得用 AI”。但一个场景有价值、模型也会做，并不等于系统已经可以放心让它把整件事做完。

研发里这个分界很明显。让 AI 解释一段代码、补一个函数、改一个边界清楚的小问题，通常比较容易控制；一旦任务变成长时间、多步骤、跨模块执行，问题就从“模型会不会写代码”转向：它看到的信息够不够，前一步错了会不会污染后一步，怎么验证，怎么停，怎么回滚。

大型重构就是最典型的例子。它把上下文、状态、验证、恢复和权限同时拉进了任务里，也最容易暴露“模型能力”和“系统交付能力”之间的差距。

## 从“帮我看”到“自己做完”，中间隔着很多层

同样叫“AI 做研发”，实际可以是完全不同的责任深度：

```text
读代码、找资料
→ 分析问题
→ 给修改建议
→ 生成候选代码
→ 真正修改文件
→ 连续执行多批修改
→ 自己判断下一步并继续推进
→ 完成测试、发布和收尾
```

前几层里，人一直掌握任务状态。AI 分析错了，可以重新查；候选代码不对，可以不用。

从“真正修改文件”开始，AI 的输出进入了真实系统状态。再往后到“连续执行”，前一轮的结果会直接变成下一轮的输入。

这时候错误的性质变了。一个函数改错了，测试可能马上报错；但大型重构里，第 1 批如果漏掉一个隐藏调用方，第 2 批可能按错误边界继续迁移，第 3 批再删除旧实现。等到后面发现问题时，已经不是修一个文件，而是要回头拆一串建立在错误前提上的修改。

所以长任务危险的地方，不只是“做得久”，而是**错误会进入状态，并被后续步骤继承。**

## 大型重构最难的，往往不是写代码

真正进入一个成熟仓库以后，很多关键约束不写在当前文件里。

一个接口看起来多余，可能还有外部调用；一个字段看起来没人用，可能承担历史兼容；一段很绕的逻辑，可能是在规避某个真实运行问题。

这些信息可能分散在：

- 其他模块或其他仓库；
- 文档和历史设计；
- Git 提交和 Issue；
- 测试；
- 运行日志；
- 只有维护过这个系统的人才知道的经验。

AI 如果只看到当前代码，很容易得到一个局部合理的结论：结构确实更干净，类型确实更漂亮，测试甚至也可能通过，但真实系统的某个边界已经被破坏。

所以重构任务能不能继续往下放权，第一件事不是换更强模型，而是判断：**它现在掌握的事实，够不够支撑这个动作。**

## 第二个问题：这一轮做错了，下一轮开始前能不能知道

这是判断自主程度时很实用的一道线。

格式化、类型检查、Schema、单测，这些反馈都很快。AI 做错了，工具通常能马上给出证据。

但有些问题没有这么好验。

跨模块重构可能编译通过、单测通过，却破坏了真实调用；架构调整可能短期都能跑，后面才发现维护成本变高；一个长期 Agent 可能每一步都没有明显报错，最终状态却已经偏离原目标。

如果错误十步以后才暴露，就不能把十步当成一个黑盒交出去。

更稳妥的方式是把任务切成能验的小批次：这一批改完，先检查影响范围、跑对应测试、做真实运行验证；确认当前状态可靠，再允许下一批建立在它之上。

所以“验证”不是最后验收时才做的事情。对于长任务，它本身就是执行过程的一部分。

## 第三个问题：任务做到哪了，谁来维护这个状态

单轮问答里，状态很简单：用户问，模型答。

长任务不是这样。大型重构可能持续很多轮，期间会出现已经确认的结论、完成的批次、暂时不能动的区域、失败尝试、待验证项和下一步计划。

如果这些东西全靠一段越来越长的聊天记录维持，迟早会混乱。模型可能重复做已经完成的事，也可能忘掉早期约束，或者把一个还没验证的中间结论当成事实继续往下做。

所以长任务需要显式状态：当前目标是什么、哪些事实已经确认、哪些批次已经完成、哪些结果还没验、下一步为什么是这一步。

这也是为什么 Checkpoint、任务记录、阶段产物这些东西重要。它们不是为了“写更多文档”，而是为了让后续执行建立在可靠状态上，而不是建立在模型模糊的聊天记忆上。

## 第四个问题：做错以后能不能回来

研发里 Git 给了一个很好的直觉。

AI 改错一个文件，如果改动边界清楚、有提交点，回滚并不难；但如果它连续改了几十处、期间又顺手清理旧代码、更新测试、改配置，最后才发现最早的判断错了，恢复成本会急剧上升。

所以可恢复性直接影响能放多少权。

```text
只读分析
→ 几乎没有状态破坏

局部修改 + 明确 diff
→ 容易 Review，也容易撤销

多批连续修改 + 无检查点
→ 一旦早期判断错误，回退范围迅速扩大

自动发布、改生产数据
→ 已经涉及真实外部状态，恢复要求更高
```

越难恢复的动作，越不能只靠模型自信地继续执行。

## 第五个问题：AI 到底可以动什么

“会做”与“有权做”必须分开。

AI 可以生成一条数据库迁移 SQL，不代表它应该直接在生产库执行；可以给出发布命令，不代表它应该默认有生产发布权限；可以判断某段代码该删，也不代表它可以绕过 Review 直接删除。权限越接近真实外部状态，出错代价越高。

所以研发里的自主程度最好逐层增加：先让 AI 看、分析、给建议；再让它改局部文件；验证链路足够稳定以后，再扩大到多文件、多批次；涉及发布、生产数据和高风险操作时，继续保留明确的确认和权限边界。

这里没有一个统一的“自动化比例”。真正要看的是错误影响范围和恢复能力。

## Harness 为什么会在这里变得重要

当 AI 只负责回答问题时，一个好 Prompt、合适上下文、几次工具调用可能就够了。

当任务开始跨很多步骤，系统就必须承担更多责任：

- 给 AI 当前真正需要的上下文，而不是把整个仓库一股脑塞进去；
- 约束这轮任务能改什么、不能改什么；
- 记录已经确认的状态和阶段结果；
- 每一批修改后触发合适的测试和真实验证；
- 发现异常时停止，而不是带着错误继续；
- 保留可回滚的检查点；
- 控制工具和生产权限。

这些围绕模型的执行、状态、验证、权限和恢复机制，才是 Harness 真正有用的地方。

它不是让模型“变聪明”的魔法层。它做的是把一个原本容易失控的长任务，拆成一段段可看、可验、可停、可恢复的执行过程。

拿大型重构对比会很直观。

承接条件弱时，执行很容易变成：

```text
给整个仓库 + 一个大目标
→ AI 连续修改
→ 中间很少停下来确认状态
→ 最后统一看结果
```

看起来省了很多人工介入，实际把大量不确定性积到了最后。

条件补起来以后，流程会变成：

```text
先确认目标、边界和不能破坏的行为
→ 找影响范围
→ 拆一小批修改
→ 执行
→ 测试 + 真实运行验证
→ 记录当前状态
→ 失败就停或回滚
→ 通过后再做下一批
```

同样是 AI 重构，后者不是因为模型突然更强，而是系统终于能及时发现错误、限制影响范围，并把可靠状态交给下一步。

这也是为什么大型重构在 Harness 不成熟时可能完全做不下去，而承接条件逐步补齐后，同样的模型和任务又会变得可做。

## 判断一个研发任务能放给 AI 到哪一步

不用先给场景贴“适合”或“不适合”的标签。顺着下面几个问题判断更有用。

1. **它现在看到的事实够不够？** 关键代码、调用关系、业务约束、历史兼容是不是都能拿到。
2. **这一轮怎么证明自己做对了？** 有没有测试、运行验证、结构检查或明确的人审节点。
3. **如果做错了，下一轮开始前能发现吗？** 反馈越慢，任务越应该拆小。
4. **错了以后能不能回到可靠状态？** 有没有清晰 diff、检查点、回滚和旧状态。
5. **一个错误会影响多大范围？** 只影响一个候选文件，还是会继续污染后面的迁移、测试和发布。
6. **它需要什么权限？** 只读、改工作区、执行命令、改生产配置，风险完全不同。
7. **长任务状态由谁维护？** 已确认事实、阶段结果、待验证项和下一步是不是显式保存。

这些条件决定的不是“要不要用 AI”，而是**现在能把责任交到哪一层**。

同一个研发任务，今天可能只适合让 AI 做分析和局部修改；等上下文获取、测试、运行验证、状态管理和恢复能力补齐以后，才适合让它连续执行更多步骤。

这个判断也能迁移到研发之外。客服里“写回复草稿”和“自动退款”，数据里“生成 SQL”和“直接改生产库”，本质上也是同一个变化：AI 从提供候选结果，走向真正改变外部状态。

研发只是把这个问题暴露得特别清楚。

所以最容易翻车的场景，不是某个固定行业，也不是某种模型能力，而是**AI 承担的责任已经超过了当前系统能够看清、验证、约束和恢复的范围。**
