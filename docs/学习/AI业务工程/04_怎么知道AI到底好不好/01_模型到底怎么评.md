# 模型到底怎么评

真正评一个模型，不是打开几个排行榜看分数，也不是随便问十道题凭感觉比较。现实里的 Model Evaluation 是一套可复现的实验：**先确定评什么能力，选公开 Benchmark 和自己的真实任务，固定 Prompt / Sampling / Tool / Harness，让候选模型在同一条件下跑完整个 Dataset，再按任务选择指标、做多次 Trial、看置信区间和失败类型。**

这篇只回答模型层的问题：给你一个模型，或者给你两个候选模型，究竟怎么测、测什么、指标怎么看，以及 OpenAI、Anthropic、Stanford HELM、SWE-bench、LM Evaluation Harness、Arena 这些真实组织和 Benchmark 到底是怎么做的。

## 一、一次真实的模型评测到底怎么走

### 第一步：先说清楚你评的是“模型”还是“系统”

这是最容易搞错的一步。

如果你想比较两个基础模型本身：

```text
Model A
vs
Model B
```

那么除了模型，其他条件应该尽量固定：

- 同一套题；
- 同一个 Prompt；
- 同一 Chat Template；
- 同样的 System Instruction；
- 同样的 temperature / top_p / max tokens；
- 同样的 Tool；
- 同样的 RAG Context；
- 同样的 Agent Harness。

否则你测出来的可能不是模型差异，而是 Prompt、Harness 或 Tool 差异。

如果你想评一个真实产品，就不能只换裸模型，而应该把整套系统当成被测对象：

```text
Model
+ System Prompt
+ RAG
+ Tools
+ Memory
+ Agent Harness
+ Retry / Routing
= 被测系统
```

Anthropic 在 Agent Eval 中明确把 model + agent harness 看成一起被评的系统，因为工具编排和环境本身就会改变结果。

### 第二步：公开 Benchmark 先测“通用能力底盘”

公开 Benchmark 的作用不是告诉你“这个模型适不适合我的业务”，而是先建立一个能力坐标。

例如：

| 想看什么 | 常见 Benchmark / 任务形态 | 常见指标 |
|---|---|---|
| 通识 / 学科知识 | MMLU / MMLU-Pro | Accuracy / Exact Match |
| 高难推理 | GPQA、HLE 一类题集 | Accuracy / Exact Match |
| 指令遵循 | IFEval 一类 | instruction-level accuracy |
| 数学 | GSM8K、AIME 一类 | Exact Match / pass@k |
| 代码生成 | HumanEval 一类 | pass@k |
| 真实软件工程 | SWE-bench | Resolution Rate |
| Web / Research Agent | BrowseComp 等 | task success / grader score |
| 真实职业任务 | GDPval | 专家 blind comparison / win-tie-loss |

公开 Benchmark 解决的是：**这个模型大概在哪些能力上强，在哪些能力上弱。**

它不解决：**在你公司的订单、客服、代码仓库、合同、RAG 数据上能不能用。**

所以真实评测一定还有下一层。

### 第三步：拿自己的真实任务做 Internal Eval

如果你在选一个 Coding Model，就应该拿真正会发生的任务来评：

```text
修跨文件 Bug
新增一个 API
修改类型定义并修调用方
根据失败测试定位原因
重构但保持回归测试通过
读一个陌生仓库回答调用链问题
```

如果你在选客服模型，题也应该来自真实工作：

```text
正常退款
超时退款
用户信息不完整
政策冲突
不应该退款的情况
需要升级人工的情况
```

真实任务至少要覆盖三种东西：

```text
正常主路径
+ 边界 / 难例
+ 历史失败案例
```

公开 Benchmark 测“能力上限”，Internal Eval 测“我这里能不能用”。

### 第四步：固定 Evaluation Protocol

同一模型用不同配置，结果可能差很多。

所以正式评测必须把运行条件一起记录：

```text
model_id
model_version
prompt_version
chat_template
system_prompt
few-shot examples
temperature
top_p
max_tokens
reasoning_effort
tool_set
retriever_version
agent_harness_version
```

这也是为什么真实组织不会只发布“某模型 90 分”，而会同时描述评测配置。

一个典型错误是：

```text
Model A：官方推荐 Chat Template + 8k 输出
Model B：裸 completion + 1k 输出
```

然后拿结果说 A 更聪明。

这不是公平评测。

### 第五步：让模型真正跑完，而不是只保存总分

每个 task 至少应该留下：

```text
输入
模型原始输出
解析后的答案
得分
耗时
Token
失败原因
如果有 Agent：完整 trajectory / tool calls
```

原因很简单：最终总分只能告诉你“差了”，不能告诉你“为什么差”。

例如两个模型都 80 分：

```text
Model A：数学错得多，代码很好
Model B：数学很好，指令遵循经常错
```

对不同产品，结论完全不同。

### 第六步：不同任务用不同指标

评测不是永远看 Accuracy。

最常见的判断关系是：

```text
答案唯一、可精确比较
→ Accuracy / Exact Match

分类不均衡
→ Precision / Recall / F1

代码是否真的能跑
→ Unit Test / pass@k / Resolution Rate

开放式回答
→ Rubric / LLM Judge / Human Pairwise

模型是否稳定
→ 多 Trial Success Rate / pass^k

模型是否知道自己没把握
→ Calibration / ECE

上线是否划算
→ Latency / Throughput / Token / Cost
```

指标不能脱离任务。

### 第七步：随机模型不能只跑一次

生成模型不是普通确定性函数。

同一道题：

```text
Trial 1 PASS
Trial 2 PASS
Trial 3 FAIL
Trial 4 PASS
Trial 5 FAIL
```

这时“这题会不会”不能只看第一次。

Anthropic 在 Agent Eval 里把每一次尝试叫 Trial，并专门区分：

- `pass@k`：k 次里至少有一次成功；
- `pass^k`：k 次全部成功。

两者回答的是不同问题。

例如代码搜索工具可以接受“给 5 个候选，其中一个对”，那么 pass@5 有意义。

但客服 Agent 每次退款都必须稳定正确，这种场景更关心 pass^k 或多次运行成功率。

### 第八步：比较两个模型时要做 Paired Evaluation

不要这样比：

```text
Model A 跑 100 道题
Model B 另外随机跑 100 道题
```

应该这样：

```text
同一道 Task 001
A 跑
B 跑

同一道 Task 002
A 跑
B 跑
...
```

这样你才知道：

- 哪些题 A 赢；
- 哪些题 B 赢；
- 差距集中在哪类任务；
- 总分差异是不是被几个 Bucket 拉出来的。

开放式任务还可以做匿名 Pairwise：

```text
Prompt
├─ Response A
└─ Response B

Human / Judge：A 更好 / B 更好 / Tie
```

这就是很多 Arena 和真实职业任务评测使用的思路。

### 第九步：看置信区间，不要迷信小数点

100 道题：

```text
A = 82%
B = 84%
```

不等于 B 一定更强。

评测集越小，抽样误差越大；生成又有随机性，所以结果至少应该报告：

- 样本数 N；
- mean / success rate；
- standard error 或 confidence interval；
- 多 Trial 时的方差；
- pairwise win / loss / tie。

如果两个模型差距很小而置信区间大量重叠，正确结论可能就是：**当前证据不足以区分。**

### 真正的评测输出应该长什么样

不要只给：

```text
Model A：87.4
Model B：85.9
```

更有用的是：

```text
总体成功率
核心任务成功率
高风险任务成功率
各能力 Bucket
pass@1 / 多 Trial 稳定性
P50 / P95 latency
平均 Token / 成本
失败类型 Top N
与 Baseline 的 paired wins / losses / ties
置信区间
```

评测最终不是为了做排行榜，而是回答一个工程问题：

> **这个模型在什么任务上，比当前方案好多少；这个差距是否稳定；代价是什么；值不值得换。**

## 二、公开 Benchmark 和自己的真实任务怎么选

### Benchmark 本质是什么

Benchmark 可以理解成：

```text
固定 Dataset
+ 固定 Prompt / Protocol
+ 固定 Grader
+ 固定 Metric
```

大家在同一套条件下跑，才有可比性。

公开 Benchmark 最大价值是：

- 可复现；
- 有大量模型历史结果；
- 能形成共同坐标；
- 不需要每家公司自己发明一套通识考试。

但它只是能力切片。

### 第一类：知识和考试型 Benchmark

最典型的是 MMLU / MMLU-Pro 一类。

题型通常接近：

```text
问题
A / B / C / D
→ 选一个答案
```

它适合测：

- 学科知识；
- 基础推理；
- 多领域覆盖。

指标通常就是 Accuracy / Exact Match。

优点是简单、稳定、容易比较。

缺点也很明显：真实工作很少只是选四选一。

因此它适合做能力底盘，不适合单独决定产品模型。

### 第二类：高难推理 Benchmark

GPQA、Humanity's Last Exam 这类题更关注高难知识和推理。

它们常被用来判断 frontier model 的推理上限。

仍然要注意：

```text
高难考试答题强
≠
真实工具调用强
≠
真实软件工程强
≠
客服稳定性强
```

一个 Benchmark 测什么，就只对那个维度负责。

### 第三类：指令遵循 Benchmark

IFEval 这类任务不是只问“答案对不对”，而会加入明确约束：

```text
必须用 JSON
不能出现某个词
必须有 3 个 section
每个 section 满足某种格式
```

它测的是：

> 模型能不能按要求做，而不是只会给一个大概正确的答案。

对于 Agent、结构化输出、企业工作流，这类能力非常重要。

### 第四类：代码生成 Benchmark

HumanEval 一类任务通常给函数说明和测试，然后模型写代码。

评分不看文字像不像标准答案，而是直接跑 Unit Test。

常见指标：

- pass@1；
- pass@k。

这比文本相似度靠谱得多，因为两个完全不同的实现都可能正确。

### 第五类：真实软件工程 Benchmark

SWE-bench 比单函数代码生成更接近真实开发。

一条任务通常包含：

```text
真实 GitHub Issue
+ 真实 Repository
+ base commit
→ 模型生成 patch
→ 把 patch 应用到仓库
→ Docker 环境运行测试
→ 看 Issue 是否真正 resolved
```

SWE-bench 官方 Harness 会统计：

- submitted instances；
- completed instances；
- resolved instances；
- Resolution Rate。

所以它测的是“能不能把真实仓库问题修掉”，而不是“能不能写一段看起来像代码的文本”。

### 第六类：真实职业任务 Benchmark

OpenAI 的 GDPval 代表另一个方向：不再从考试题出发，而是直接从真实职业工作产品出发。

GDPval 第一版覆盖 44 个职业、9 个行业，full set 有 1,320 个专业任务；任务来自真实工作形态，例如法律文书、工程蓝图、客服对话、护理方案等。

它不是简单 Exact Match，因为这些任务没有唯一标准答案。

所以评法变成：

```text
行业专家制作任务和参考交付物
→ 模型完成同样任务
→ 同行业专家 Blind Review
→ 比较 Human vs AI deliverable
→ better / as good as / worse
```

这比考试题更接近“AI 能不能真正做工作”。

### 第七类：Agent Benchmark

Agent Benchmark 的重点不再只是最终文本。

例如一个 Flight Booking Agent：

```text
用户要求订票
→ Agent 查询
→ Agent 调工具
→ Agent 修改数据库
```

最终评分应该检查数据库里真的有没有 reservation，而不是只看 Agent 说“已经订好了”。

Anthropic 把这类评测拆成：

- Task；
- Trial；
- Grader；
- Transcript / Trajectory；
- Outcome；
- Evaluation Harness。

这已经非常接近系统集成测试。

### 为什么公开 Benchmark 不能全包

公开 Benchmark 有几个天然问题。

#### 1. 数据污染

题被模型训练过，分数可能虚高。

#### 2. Benchmark 饱和

大家都接近 95% 以后，它已经很难区分模型。

#### 3. 任务形态和真实业务不同

考试题、代码题和你的实际业务可能完全不同。

#### 4. Harness 会改变成绩

同一个模型，Chat Template、Prompt、Tool、Sampling、max tokens 不同，都可能改变结果。

因此不要只抄 leaderboard。

### 一个更实用的 Benchmark Stack

如果你真要给一个通用 LLM 做第一轮体检，可以按能力分组，而不是只跑一个总榜：

```text
知识 / 通识
→ MMLU-Pro

推理
→ GPQA / 高难 reasoning set

指令遵循
→ IFEval

代码
→ HumanEval / LiveCodeBench 类

软件工程
→ SWE-bench

真实工作
→ GDPval / 自建 occupational tasks

安全 / 稳健性
→ 专门 safety / robustness suite
```

具体选哪些 Benchmark 会随时间变化，但“按能力拼 Benchmark Battery”的方法更稳定。

### 最终一定要加自己的 Dataset

真实模型选型最好是：

```text
Public Benchmark
20%：了解行业坐标

Internal Capability Eval
评你的核心任务

Regression Eval
保护历史已经做对的任务

Online Evaluation
验证真实用户行为
```

这里的比例不是固定公式，重点是：**公开榜不能替代自己的真实数据。**

### 怎么判断一个 Benchmark 值不值得跑

问五件事：

1. 它到底测什么能力？
2. 输入和输出形态像不像我的真实任务？
3. Grader 是不是可靠？
4. Benchmark 有没有明显饱和或污染风险？
5. 这个分数能不能改变我的模型选择？

最后一个问题特别重要。

如果跑完一个 Benchmark，无论多少分你都不会改变任何产品决策，那它大概率只是“为了有个分数”。

## 三、这些评测指标到底怎么看

### 先把指标分成六类

```text
正确性
→ Accuracy / Exact Match / Precision / Recall / F1

生成与代码成功
→ pass@k / Resolution Rate

偏好质量
→ Win Rate / Tie Rate / Bradley-Terry / Elo-like rating

稳定性
→ Trial Success Rate / pass^k

可信度与稳健性
→ Calibration / ECE / Robustness / Safety

工程成本
→ Latency / Throughput / Token / Cost
```

一个模型没有“一个指标”能代表全部能力。

### Accuracy：最普通的正确率

公式：

```text
Accuracy = 正确样本数 / 总样本数
```

100 道选择题答对 82 道：

```text
Accuracy = 82%
```

适合：

- 选择题；
- 平衡分类；
- 有唯一答案的任务。

不适合：类别极不平衡时单独使用。

例如 1000 条交易里只有 10 条欺诈，模型全部预测“正常”：

```text
Accuracy = 99%
```

但模型一个欺诈都没抓到。

所以这时要看 Precision / Recall。

### Exact Match：必须精确答对

常用于：

- 数学最终答案；
- 短 QA；
- 某些结构化结果；
- Benchmark 的答案提取。

例如标准答案：

```text
42
```

模型最后抽取也是 42，则 Exact Match = 1。

需要注意 normalization：大小写、标点、空格、单位是否应该被忽略，必须提前定义。

否则 grader 本身会制造假失败。

### Precision / Recall / F1：分类和检索最常见

假设你要找“真正的高风险工单”。

#### Precision

```text
你判成高风险的里面
有多少真的高风险
```

高 Precision = 少误报。

#### Recall

```text
所有真正高风险里面
你抓到了多少
```

高 Recall = 少漏报。

#### F1

Precision 和 Recall 的调和平均：

```text
F1 = 2PR / (P + R)
```

适合需要同时控制漏报和误报的场景。

RAG Retrieval 也会用类似思想：

- Recall@K；
- Precision@K。

### Perplexity：模型对文本“有多意外”

Perplexity 是传统语言模型评测里的重要指标，反映模型预测下一个 Token 的不确定程度。

一般：

```text
Perplexity 越低
→ 对这类文本预测越好
```

但它不能直接回答：

- 指令遵循好不好；
- Agent 会不会用工具；
- 代码能不能跑；
- 回答是不是符合人类偏好。

所以现代 Chat / Agent Model 选型不能只看 Perplexity。

### pass@k：k 次里至少成功一次

代码模型里非常常见。

例如一道代码题生成 5 个方案：

```text
1 FAIL
2 FAIL
3 PASS
4 FAIL
5 FAIL
```

那么“5 次里至少一个解成功”就是 pass@5 的直觉。

pass@k 越大，说明多次尝试时找到可行解的能力越强。

但要小心：pass@10 很高不等于模型第一次就可靠。

产品只允许一次响应时，更关心 pass@1。

### pass^k：连续 k 次都成功

Anthropic 在 Agent Eval 中特别强调这个指标。

例如单次成功概率 75%，连续 3 次都成功的概率直觉上是：

```text
0.75³ ≈ 42%
```

这就是可靠性问题。

适合：

- 客服 Agent；
- 支付 / 退款；
- 企业自动化；
- 每次都必须稳定完成的任务。

所以：

```text
pass@k 看“多试几次能不能有一次做成”
pass^k 看“连续多次能不能都做成”
```

不能混。

### Resolution Rate：真实软件工程有没有修掉

SWE-bench 的核心结果之一就是 Resolution Rate。

它不是问 patch 像不像参考答案，而是：

```text
模型提交 patch
→ 应用到真实仓库
→ 跑测试
→ Issue 是否 resolved
```

```text
Resolution Rate
= resolved instances / submitted instances
```

对 Coding Agent 来说，这比 BLEU 或代码文本相似度有意义得多。

### Win Rate / Tie Rate：开放式回答谁更好

当任务没有唯一答案时，经常用 Pairwise Comparison。

```text
同一个 Prompt
Response A
Response B
→ 人 / Judge 选
A win / B win / Tie
```

跑很多题以后可以统计：

```text
A Win Rate
B Win Rate
Tie Rate
```

OpenAI GDPval 就让行业专家盲评 AI 和专业人士交付物，并记录 better / as good as / worse。

Arena 类评测也大量使用 pairwise preference。

### Bradley-Terry / Elo-like Rating：把大量两两比较变成排名

当有很多模型互相 Battle：

```text
A vs B
A vs C
B vs D
C vs D
...
```

直接看矩阵很难。

因此可以用 Bradley-Terry 之类的统计模型，把 pairwise win/loss 聚合成一个相对能力分数，再映射成类似 Elo 的 leaderboard。

这里要记住：

> Elo / Arena Rating 是“相对排名指标”，不是绝对正确率。

而且必须看置信区间；相邻两个模型分差很小，不一定真的存在显著差异。

### Calibration / ECE：模型的“自信”靠不靠谱

有些场景不仅要答案，还要模型知道什么时候自己不确定。

例如模型说：

```text
90% confidence
```

如果所有 90% confidence 的问题最终只答对 55%，它严重过度自信。

ECE（Expected Calibration Error）就是常见 Calibration 指标之一，衡量置信度和真实正确率之间的差距。

Stanford HELM 也实现了 ECE 等 calibration metrics。

这对高风险领域尤其重要，因为“错但很自信”通常比“知道自己不会”危险。

### Robustness：题稍微变一下还会不会

模型如果：

```text
原题答对
换个措辞就错
加一点无关信息就错
拼写有一点变化就错
```

那么它的鲁棒性很差。

Robustness Eval 常用 perturbation：

- paraphrase；
- typo；
- irrelevant context；
- format change；
- language / dialect change。

最后看：

```text
原始分数
vs
扰动后的分数
```

下降多少。

### Safety / Toxicity / Bias / Fairness

这些不是“正确率附属项”，而是独立的模型行为维度。

Stanford HELM 的整体评测思路就是不只看 Accuracy，还同时考虑：

- efficiency；
- bias；
- toxicity；
- calibration；
- robustness；
- fairness。

是否需要这些指标，要看产品风险。

### Latency / Cost：质量一样时才真正决定上线

模型评测如果不记工程指标，最后无法做产品选择。

至少建议记录：

```text
P50 latency
P95 latency
output tokens
input tokens
cost per task
success per dollar
throughput
```

例如：

| 模型 | 任务成功率 | P95 | 单任务成本 |
|---|---:|---:|---:|
| A | 91% | 18s | $0.30 |
| B | 89% | 4s | $0.04 |

如果业务能接受 2% 的质量差，B 可能才是正确选择。

### 置信区间：别把小差距吹成结论

所有 aggregate metric 都应该关心样本数。

```text
A Accuracy = 85.2%
B Accuracy = 84.6%
```

如果只有 100 条样本，这个差距很可能没有决策意义。

至少要一起看：

- N；
- standard error；
- 95% confidence interval；
- 多次 Trial 的 variance。

排行榜上的 0.6 分，可能只是噪声。

### 一张选择表

| 任务 | 优先指标 |
|---|---|
| 选择题 / 唯一答案 | Accuracy / Exact Match |
| 不均衡分类 | Precision / Recall / F1 |
| 信息抽取 | Field-level P/R/F1 |
| 基础 LM | Perplexity |
| 代码生成 | pass@1 / pass@k |
| 软件工程修复 | Resolution Rate |
| 开放式回答 | Pairwise Win/Tie + Rubric |
| 多次必须稳定成功 | Trial Success / pass^k |
| 模型置信度 | Calibration / ECE |
| 易受输入变化影响 | Robustness Delta |
| 实际上线 | Quality + Latency + Cost + Reliability |

这才是“几个指标”之间真正的关系：**不是都算一遍，而是按任务选择。**

## 四、其他组织到底是怎么真实评测模型的

### OpenAI：从考试 Benchmark 一路走到真实职业任务

OpenAI 对评测的演进本身就是一条很典型的现实路径：

```text
MMLU
学术 / 考试任务
↓
SWE-bench
真实软件工程
↓
MLE-Bench / Paper-Bench
专业工程 / 科研任务
↓
SWE-Lancer
带真实市场价值的软件任务
↓
GDPval
真实职业工作产品
```

GDPval 特别值得看，因为它已经不是“模型考试”。

第一版：

- 44 个职业；
- 9 个行业；
- full set 1,320 个任务；
- 任务作者和评审者都是有经验的行业专业人士；
- 任务来自真实工作交付物。

Dataset 不是随便写的。OpenAI 描述每条任务要经过多轮专家审查，确保：

- 代表真实工作；
- 另一个专业人士能完成；
- 可以被可靠评价。

评分时也不是 Exact Match。

流程是：

```text
专业人士制作 Task + Reference Deliverable + Rubric
↓
模型完成同样任务
↓
同行业专家不知道哪份是 AI、哪份是 Human
↓
Blind Comparison
↓
better / as good as / worse
↓
统计 wins / ties
```

同时 OpenAI 还训练 automated grader 去近似专家判断，但明确说它还不能替代专家，因此真实结论仍依赖 expert graders。

这里最值得学的是：

> 开放式真实工作，最终还是要回到“专业人士是否认可这个交付物”。

### Anthropic：Agent Eval 已经像系统测试

Anthropic 2026 年公开的 Agent Eval 方法把术语定义得非常清楚：

```text
Task
一条明确测试任务

Trial
同一 Task 的一次实际尝试

Grader
判定某个维度是否成功

Transcript / Trajectory
完整执行过程、Tool Calls、中间结果

Outcome
最终环境状态

Evaluation Harness
负责跑任务、记录、评分、汇总
```

这和传统软件测试越来越像。

例如 Flight Booking Agent：

```text
Agent 最终说：
“已经给你订好了”
```

不能算 PASS。

真正的 Outcome Grader 要查：

```text
reservation database
```

确认票真的存在。

Anthropic 还建议同时使用：

- code-based grader；
- model-based grader；
- human grader。

并区分两套 Eval：

```text
Capability Eval
→ 看“现在还能突破什么”

Regression Eval
→ 看“原来会的有没有退化”
```

对随机性，它还明确使用 `pass@k` 和 `pass^k` 区分“至少一次成功”和“每次都稳定成功”。

### Stanford HELM：不要只看 Accuracy

HELM 的出发点叫 Holistic Evaluation。

它做的事情可以简化成：

```text
统一 Dataset / Scenario
+ 统一 Model Interface
+ 统一 Prompt Protocol
+ 多维 Metrics
+ 保存 per-instance results
+ 可复现 Leaderboard
```

HELM 不只看 Accuracy，还长期强调：

- calibration；
- robustness；
- fairness；
- bias；
- toxicity；
- efficiency。

例如 classification 场景里，HELM 会计算 ECE 一类 calibration metric，判断模型置信度和真实正确率是否匹配。

它给我们的启发是：

> “答对多少”只是模型质量的一维，不是完整质量。

HELM 在 2026 年进入 maintenance mode，所以现在更适合把它当成**评测方法和可复现框架的经典参考**，而不是唯一的新 Benchmark 来源。

### SWE-bench：代码模型最后必须接受真实测试

SWE-bench 的评测方式非常直接：

```text
真实 Issue
+ 真实 Repository
+ base commit
↓
模型生成 patch
↓
应用 patch
↓
Container / Docker 环境
↓
运行测试
↓
Resolved / Not Resolved
```

官方 Harness 会保存：

- overall results；
- instance-level results；
- run logs。

核心指标包括：

- submitted；
- completed；
- resolved；
- Resolution Rate。

这个路径非常值得工程团队学习，因为它没有问“模型生成的 patch 和标准 patch 像不像”，而是直接问：

> **Bug 到底修好没有。**

这就是 Outcome-based Evaluation。

### EleutherAI LM Evaluation Harness：把公开 Benchmark 做成可复现流水线

LM Evaluation Harness 是开源模型评测最常见的基础设施之一。

它把 Benchmark 标准化成配置：

```text
dataset
prompt template
few-shot
model adapter
generation config
answer extraction
metric
aggregation
```

然后不同模型在同一个 task config 下跑。

常见 metric 包括：

- accuracy；
- exact_match；
- perplexity；
- task-specific metrics。

它的重要性不只是“能跑很多 Benchmark”，而是让不同模型**尽量在同一种 protocol 下比较**。

但 Harness 本身也提醒一个现实问题：评分配置、answer extraction、Chat Template 一旦不一致，分数就会变化。因此复现论文数字时，不能只看 task 名称。

### Arena：开放式回答用人类盲选，不强行造标准答案

开放聊天没有唯一答案时，Arena 路线很实际：

```text
同一 Prompt
↓
两个匿名模型同时回答
↓
用户不知道模型身份
↓
选择 A / B / Tie
↓
大量 Pairwise Votes
↓
Win Rate / Bradley-Terry / Elo-like Ranking
```

例如 LMArena 的 Search Arena 会先看 pairwise win rate，再用 Bradley-Terry 模型聚合出 leaderboard，并同时关注 confidence interval。

这种方法适合：

- 写作；
- 助手回答；
- 搜索总结；
- 很难定义唯一 reference 的任务。

缺点是：

- 人的偏好可能受长度、格式、风格影响；
- 投票需要大量样本；
- leaderboard 小分差不一定有统计意义。

所以 Pairwise 不是万能 Grader，但对开放任务非常现实。

### 这些组织其实在做同一件事

把它们放一起：

| 组织 / Benchmark | Task 来源 | Grader | 主要指标 |
|---|---|---|---|
| MMLU / lm-eval | 标准学术题 | Exact / Choice Match | Accuracy |
| OpenAI GDPval | 真实职业工作 | 行业专家 Blind Review | Win / Tie / Worse |
| Anthropic Agent Eval | 真实 Agent Task | Code + Model + Human + Outcome | pass@k / pass^k / success |
| SWE-bench | 真实 GitHub Issue | Repo Tests | Resolution Rate |
| Stanford HELM | 多类 Scenario | 多 Metric | Accuracy + Calibration + Robustness + Efficiency 等 |
| Arena | 真实用户 Prompt | 人类 Pairwise Vote | Win Rate + BT/Elo-like rating |

没有哪家只看一个“AI 总分”。

真实评测都是：

```text
任务定义
+ 可重复运行
+ 与任务匹配的 Grader
+ 多维指标
+ sample-level evidence
```

这才是应该学习的部分。

## 五、把模型评测压成一条可执行路径

```text
先定义要评的能力
↓
公开 Benchmark 建行业坐标
+
Internal Dataset 验证自己的真实任务
↓
冻结 Evaluation Protocol
Prompt / Chat Template / Sampling / Tool / Harness
↓
同一批题跑 Baseline 和 Candidate
↓
按任务选 Grader / Metric
Accuracy / F1 / EM / pass@k / Win Rate / Calibration ...
↓
随机任务做 Multiple Trials
↓
看 Overall + Bucket + Confidence Interval
↓
同时记录 Latency / Token / Cost
↓
得到“强在哪里、弱在哪里、是否值得换”的结论
```

公开 Benchmark 告诉你模型在行业坐标里大概站在哪；Internal Eval 才告诉你它在你的工作里到底能不能用。两者不能互相替代。
