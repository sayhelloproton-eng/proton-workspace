# AI 系统到底怎么评

模型评测解决的是“这个模型本身能力怎么样”，但真实 AI 产品通常还包着 RAG、Tool、Workflow、Agent、权限、外部系统和业务流程。到了这一层，只看模型 Benchmark 已经不够：**系统可能模型很强，却检索错了、工具用错了、外部状态没改成功，或者线上成本和失败率根本不能接受。**

所以系统评测的对象要从“回答”扩展到 **Retrieval、Generation、Outcome、Trajectory、Side Effect、Reliability 和真实业务结果**。这篇回答：RAG 怎么评、Agent 怎么评、团队怎么搭自己的 Eval Suite，以及离线通过以后怎么用 Shadow / Canary / A-B 和线上失败继续验证。

## 一、从模型分数走到系统结果

### 为什么最后必须进入真实业务

最终选模型不能只看 Benchmark。

真实决策通常是：

```text
公开 Benchmark
→ 判断能力底盘

Internal Eval
→ 判断业务任务是否能做

Latency / Cost / Stability
→ 判断能不能上线

Shadow / Canary / A-B
→ 判断真实用户是否受益
```

例如 Coding Model 的最终选择可能不是“公开榜第一”，而是：

```text
跨文件修复：A 稍强
简单修改：A/B 相同
稳定性：B 更高
P95 延迟：B 更低
成本：B 只有 A 的 35%
```

如果 80% 工作量都是简单修改，最后部署 B 完全合理。

## 二、RAG 怎么做真实评测

### RAG 先拆成两段

```text
Question
↓
Retriever
↓
Retrieved Context
↓
LLM
↓
Answer
```

如果最终回答错了，至少可能有两种原因：

```text
1. 根本没检索到正确资料
2. 资料拿到了，但模型回答错了
```

如果只看最终答案，就不知道该改 Retriever 还是 Prompt / Model。

### Retrieval 怎么评

如果你有“哪些文档应该被找到”的 Ground Truth，可以用经典 IR 指标。

#### Recall@K

```text
应该找回的相关文档
前 K 个里找回了多少
```

适合关心漏召回。

#### Precision@K

```text
前 K 个召回结果里
有多少是真的相关
```

适合控制噪声。

#### MRR

关注第一个正确结果出现得有多靠前。

#### nDCG

当“相关程度有等级”时，用来衡量整个排序质量。

所以 RAG 不是只有一个“RAG Score”。

### Generation 怎么评

Retriever 已经固定以后，再看生成层：

- Answer Correctness；
- Faithfulness / Groundedness；
- Citation Correctness；
- Citation Completeness；
- 是否该拒答时拒答；
- 格式 / 业务规则。

一个很关键的测试是：

```text
给模型已经包含正确答案的 Context
```

如果这时还答错，问题基本不在 Retrieval。

### RAG 要做端到端 Eval

最终还要跑：

```text
真实 Query
→ Retrieval
→ Rerank
→ Context Assembly
→ Generation
→ Answer
```

端到端看：

```text
Task Success
Answer Correctness
Citation
Latency
Token / Cost
```

局部指标解决“哪里坏”，端到端指标解决“用户能不能用”。

## 三、Agent 怎么做真实评测

### Agent 的评测对象更复杂

Agent 路径通常是：

```text
Task
↓
Reason / Plan
↓
Tool Call
↓
Observe
↓
再 Tool Call
↓
修改 Environment
↓
Final Answer
```

最后一句只是其中一小部分。

### Agent 第一指标：Outcome

例如退款 Agent：

```text
用户：给订单 123 退款
```

Agent 最后说：

```text
退款成功
```

不算 PASS。

真正应该检查：

```text
payment state
order state
refund record
是否重复退款
金额是否正确
```

这就是 Outcome Grader。

Anthropic 也特别强调 Agent Eval 要看最终环境状态。

### Agent 第二指标：Task Completion

根据任务类型，可以做 deterministic grader：

```text
数据库断言
API 状态断言
文件是否存在
单元测试
浏览器 DOM 状态
Git diff
```

Coding Agent 最典型：

```text
Patch
→ Build
→ Test
→ Regression Test
```

SWE-bench 就是这种思想。

### Agent 第三指标：Side Effect

“任务做成了”也可能做错很多额外事情。

例如：

```text
要求删除 1 条记录
Agent 删除了整个表
```

最终目标可能短期“达成”，但显然不能算成功。

所以 Agent Eval 还要检查：

- 有没有越权；
- 有没有多余修改；
- 有没有重复动作；
- 是否遵守安全边界；
- 是否留下脏状态。

### Agent 第四指标：Trajectory

如果结果失败，要看执行轨迹：

```text
选错 Tool？
参数错？
重复调用？
没读 Tool Result？
得到错误后有没有恢复？
陷入 loop？
```

Trajectory 更适合诊断，不一定全部参与最终 score。

不要为了轨迹“看起来优雅”惩罚一个最终正确而且安全的 Agent。

### Agent 第五指标：Reliability

Agent 的随机性通常比单轮 LLM 更大，因为每一步错误都会影响下一步。

所以同一 Task 应该跑多 Trial。

例如 20 个核心任务，每个跑 5 次：

```text
task_01: 5/5
 task_02: 4/5
 task_03: 2/5
```

这比只看一次 pass/fail 更接近真实可靠性。

可以同时看：

- pass@1；
- pass@k；
- pass^k；
- per-task success rate。

### 一个真实 Coding Agent Eval

任务：

> 修复 checkout 模块里“优惠券叠加导致负金额”的 Bug。

Evaluation Environment：

```text
固定 repo commit
固定依赖
Docker container
已有 failing test
hidden regression tests
```

Agent 可以：

```text
Read
Search
Edit
Test
```

最终 Grader：

```text
build PASS
原 failing test 变 PASS
existing tests 不回归
没有修改禁止区域
patch size 不异常
```

记录：

```text
success
trials
latency
tokens
tool calls
patch
trajectory
```

这就是一个完整的 Agent Eval。

### RAG / Agent 最终也要和 Baseline 比

例如把 Model A 换成 Model B：

```text
同一 RAG Index
同一 Top-K
同一 Tools
同一 Agent Harness
只换 Model
```

这样才能说模型导致了多少提升。

如果连 Retriever、Prompt、Tool Schema 一起改，应该把它称为“系统版本比较”，而不是“模型评测”。

### 最后记住

```text
RAG
→ Retrieval Quality + Generation Quality + End-to-End

Agent
→ Outcome + Side Effect + Reliability + Cost
```

越往 Agent 走，越接近真正的软件系统测试。

## 四、团队自己怎么搭一套真实 Eval Suite

### 不要从“买哪个 Eval 平台”开始

先从任务清单开始。

拿最近一个月真实工作，列出：

```text
用户最常做的任务
人工最花时间的任务
模型最容易翻车的任务
高风险不能错的任务
历史已经出过事故的任务
```

每一条都可以变成 Eval Task。

### 第一版只需要一套小而真的 Golden Set

不要一开始追求 5000 道题。

一个早期团队更需要：

```text
50～200 条真的代表业务的高质量 Task
```

这个范围不是标准，只是比“先造几千条低质量 synthetic data”更现实。

关键不是数量，而是：

- 每条任务真实；
- 有明确成功标准；
- 有代表性；
- 有失败样本；
- 能重复跑。

### 每条 Task 建议长这样

```json
{
  "id": "refund-017",
  "category": "refund_policy",
  "input": {...},
  "reference": {...},
  "grader": "refund_state_check",
  "must_pass": true,
  "risk": "high",
  "source": "production_failure",
  "tags": ["partial-refund", "vip"]
}
```

开放式任务可以把 reference 换成 rubric。

### Dataset 至少分四类

#### Core / Happy Path

最常发生的正常任务。

这决定模型是否基本可用。

#### Hard / Long-tail

复杂、长上下文、歧义、多约束。

这决定能力上限。

#### Regression

曾经失败、后来修好的任务。

这决定系统会不会退化。

#### Risk / Negative

不应该做、应该拒绝、应该升级人工的任务。

这决定安全边界。

### Grader 按确定性从低成本到高成本排

不要什么都用 LLM Judge。

```text
1. 程序 / Test / Schema / DB Assertion
2. Exact / Regex / Field Match
3. Task-specific metric
4. LLM Judge + Rubric
5. Human Expert
```

能用程序判的，不要让模型判。

例如：

```text
订单状态是否变成 refunded
```

查数据库就知道，不需要 GPT-5.6 读一遍再猜。

### 模型选型要保留 Baseline

每次评测至少有：

```text
Baseline
当前线上模型 / 系统

Candidate
准备替换的新模型 / 新版本
```

然后对同一套 Task 做 paired run。

最终报告至少包括：

```text
Overall
Core
Hard
Regression
Risk

Accuracy / Success
Win-Loss-Tie
Reliability
Latency
Cost
Failure Buckets
```

不要只输出一个 Overall。

### 一个模型评测表可以这样长

| Bucket | Baseline | Candidate | 变化 |
|---|---:|---:|---:|
| Core success | 93% | 96% | +3 |
| Hard success | 58% | 71% | +13 |
| Regression | 100% | 98% | -2 |
| Risk pass | 99% | 99% | 0 |
| P95 latency | 4.1s | 8.9s | +4.8s |
| Cost/task | $0.08 | $0.19 | +138% |

看到这个表，才可以做产品决策。

Candidate 总体更强，但 Regression 掉了 2%，就不能只喊“模型升级成功”。

### 公开 Benchmark 和内部 Eval 要同时留

推荐形成两层：

```text
Public Benchmark Suite
→ 看模型行业坐标和通用能力

Internal Eval Suite
→ 看真实业务是否适配
```

公开 Benchmark 让你知道模型有没有明显能力短板。

内部 Eval 决定你要不要上线。

### 小 Eval 放进 CI，大 Eval 定期跑

不是每次改一个 Prompt 都要跑 3000 个任务。

可以分层：

```text
PR / CI
→ 关键 Regression + Risk + Smoke

Nightly / Scheduled
→ 完整 Internal Suite

模型大版本升级
→ Public Benchmark + Full Internal + Human Review
```

这才不会把 Eval 做成一个昂贵到没人愿意跑的东西。

### 工具怎么选

如果主要跑公开 Benchmark：

- LM Evaluation Harness；
- HELM（方法参考 / 现有 Benchmark）。

如果主要跑自己的 Prompt / API：

- Promptfoo；
- DeepEval；
- 自己的 pytest / Node test harness。

如果要 RAG：

- Ragas；
- 自定义 retrieval metrics。

如果要 Trace + Dataset + Online：

- Langfuse；
- Phoenix；
- 自建 OpenTelemetry pipeline。

工具不是核心，**Task / Grader / Metric 才是评测资产。**

### 一套团队可以真正执行的流程

```text
1. 定义模型要承担的任务
2. 建立 Golden Set
3. 给每条 Task 写 Grader
4. 固定 Evaluation Protocol
5. Baseline 跑一遍
6. Candidate 跑同一批题
7. 自动算核心 Metrics
8. 看 Failure Buckets
9. 开放任务做 Pairwise / Human Review
10. 多 Trial 测可靠性
11. 看 Latency / Cost
12. 决定是否进入 Shadow / Canary
13. 线上失败回灌 Regression
```

这就是企业里的真实 Eval，不需要先把事情包装成复杂平台。

### 最后一句

模型评测最终不是回答：

> “哪个模型全世界最强？”

而是回答：

> **“在我们的任务上，哪个模型在可接受成本和风险下，稳定地做得最好？”**

## 五、离线 Eval 怎么走到线上验证

### 生产失败必须回流

最重要的闭环不是“每天算分”，而是：

```text
线上出现失败
↓
确认是真问题
↓
匿名化 / 清洗
↓
加入 Regression Set
↓
修复
↓
以后每个候选版本都必须重新通过
```

这样 Eval Suite 才会越跑越值钱。

### 上线前最后一关：Shadow / Canary / A-B

离线评测再好，也无法完整模拟真实用户。

#### Shadow

新模型吃真实流量副本，但不影响用户。

适合先观察：

- 输出质量；
- 延迟；
- 错误；
- 成本。

#### Canary

给少量真实用户。

适合确认没有严重线上问题。

#### A/B

当要比较用户真实行为时：

```text
A：旧模型
B：新模型
```

看真正的业务指标：

- task completion；
- user correction；
- human escalation；
- retention；
- conversion；
- time saved。

### 线上验证不是“再跑一次 Benchmark”

线上环境里真正会出现离线集没有覆盖的东西：真实用户表达、脏数据、权限差异、外部系统波动、并发、延迟、成本和长尾失败。系统上线后至少要把这些信号重新接回 Eval：

```text
Offline Eval
↓
Shadow / Canary / A-B
↓
真实 Trace + Outcome + 用户反馈 + 业务指标
↓
筛出新失败
↓
回灌 Regression Set
↓
下一版重新验证
```

系统评测的终点不是“离线 92 分”，而是**真实任务成功率、稳定性、风险、副作用、Latency、Cost 和最终业务结果都达到可接受水平。**

## 六、把系统评测压成一条可执行路径

```text
先确认模型层能力已过线
↓
RAG 分 Retrieval / Generation / End-to-End
↓
Agent 看 Outcome / Tool Use / Side Effect / Reliability
↓
建立 Internal Golden Set
Core + Hard + Regression + Risk
↓
Baseline vs Candidate
↓
小 Eval 进 CI，大 Eval 定期跑
↓
Shadow / Canary / A-B
↓
线上失败回灌 Regression
↓
最终看 Quality + Reliability + Latency + Cost + Business Result
```

模型评测回答“这个模型强不强”；系统评测回答“这套 AI 能不能在真实业务里稳定地把事情做成”。两篇合起来，才是完整的评测闭环。
