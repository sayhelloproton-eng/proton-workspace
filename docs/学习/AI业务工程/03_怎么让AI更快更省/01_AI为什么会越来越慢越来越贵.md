# AI 为什么会越来越慢、越来越贵

AI 已经能把事情做出来以后，下一步不是先找一个“省 Token 插件”，而是先确认一条任务到底慢在哪里、贵在哪里、为什么会反复做无效工作。模型输入、模型输出、调用次数、工具等待、长任务历史、失败返工、小模型和缓存解决的不是同一个问题。

这篇先把**整条效率和成本链路**讲清楚：钱和时间花在哪里，Token 为什么膨胀，Agent 为什么越跑越重，以及 Cache、Batch、并行、本地模型分别解决什么。至于“哪些信息根本不该进模型、哪些步骤应该交给程序、规则或小模型，以及上下文怎么少取、怎么压、怎么外置”，单独放到 [02_怎么节省Token.md](02_怎么节省Token.md) 深挖。

可以先记住一个判断：**优化的对象不是一次模型调用，而是一次可用结果。**

## AI 的时间和钱到底花在哪里

看到 AI 账单上涨，第一反应很容易是“把 Token 压下来”。但真做过 Agent 以后会发现，同样是“贵”，原因可能完全不同：上下文太长、模型调用太多、工具一直等、选了过贵的模型，或者前面判断错了导致整条链返工。

所以优化之前，先别把“Token、钱、速度”当成一个问题。

### 先看一次真实任务经过了什么

假设让一个 Coding Agent 修一个跨模块 Bug，它可能经历：

```text
读任务说明
→ 找相关代码
→ 查调用关系
→ 读日志
→ 模型判断
→ 修改代码
→ 跑测试
→ 测试失败
→ 再查代码和日志
→ 再修改
→ Review
→ 合入
```

这里真正消耗资源的，不止模型推理。代码和日志进入上下文要 Token，工具执行要时间，失败重试又会带着更长的历史重新调用模型，最后人工 Review 还要继续付时间。

### 三个指标必须分开看

第一是 **Token 数**。它回答“模型到底读了多少、写了多少”。真正减少 Token 的手段包括少取上下文、压缩、裁历史、减少工具 Schema、缩短输出和减少模型调用。

第二是 **Token 单价**。换便宜模型、Prompt Cache、Batch API 可能明显省钱，但 Token 数未必变少。100K Token 还是 100K Token，只是这 100K 更便宜。

第三是 **端到端时间**。并行工具、缓存、本地索引、减少网络往返会让任务更快，却未必减少 Token。

把这三件事混在一起，最容易出现“优化看起来成功，用户却没感觉”的情况。

### 真正该算的是单位有效结果

一条更接近工程现实的账是：

```text
一次可用结果的总成本
=
模型输入与输出
+ 模型调用次数
+ 工具和基础设施
+ 等待时间
+ 人工 Review
+ 失败后的返工
```

这里分母不是“调用一次模型”，而是“得到一个能进入下一步的结果”。如果一个便宜模型需要反复补上下文、重试和人工修正，单次调用便宜不等于任务便宜。

### 先找到占大头的那一段

如果任务主要慢在测试和构建，继续压一点 Prompt 没什么意义；如果每轮都带着大量 Tool Schema 和整段历史，单纯换更快的搜索工具也治不到根上。

可以先做一张很朴素的账：

| 环节 | 看什么 | 常见优化 |
|---|---|---|
| 模型输入 | input tokens、cached tokens | Context Selection、压缩、裁历史 |
| 模型输出 | output tokens | Structured Output、Output Budget |
| 调用次数 | request / loop 次数 | 缓存、批处理、停止无效循环 |
| 工具 | 每个工具耗时、返回大小 | 本地索引、过滤、并行、程序化调用 |
| 人工 | Review、返工、接管 | 更早验证、证据化输出、任务收窄 |

研发场景里，最好再把“文件读取、搜索、测试、日志、浏览器、网络请求”分别记下来。Agent 的成本问题通常藏在这些中间步骤里，而不是只藏在模型价格页。

### 后面的内容为什么这样排

接下来先回答 Token 到底从哪里冒出来，再看 Agent 长任务为什么会越来越重，最后区分 Cache、Batch、并行、本地模型各自真正解决什么。具体的 Context Selection、Compression、Pruning、Memory、Tool Search，以及程序/规则/小模型分工，放到独立的 Token 工程主文继续展开。

优化顺序可以先记一句：

> **先找到浪费发生在哪，再决定是少取、少传、少说、少循环，还是干脆不调用模型。**

## Token 为什么会越来越多，哪些消耗是真浪费

Agent 任务跑久以后，Token 往往不是一点点增加，而是每一轮都背着前面的东西继续走。问题不只是“聊天记录变长”，真正占窗口的东西比聊天多得多。

先把一轮请求拆开，很多浪费就看得见了。

### 一轮 Agent 请求里到底装了什么

一个 Coding Agent 发给模型的输入，通常可能同时包含：

```text
System / Developer Rules
+ 当前用户任务
+ 已加载 Skill / Instructions
+ Tool / MCP Definitions
+ 当前代码和文档
+ Search / RAG 召回结果
+ Tool Result：文件、日志、测试、网页、API
+ Conversation History
+ 上一轮模型生成的内容
```

模型看到的不是“用户这一句话”，而是这整包上下文。

所以用户只问一句“继续”，后端依然可能重新发送非常大的请求。真正需要治理的是这个完整请求，而不是只盯用户 Prompt。

### 最容易被忽略的，是 Tool Schema 和 Tool Result

工具少的时候感觉不明显；一旦接了很多 MCP，每个工具的名字、说明、参数和 JSON Schema 都可能在模型调用前进入上下文。工具越多，什么都还没做，基础请求就已经很重。

Anthropic 现在把这件事单独当成 Context Management 问题处理：Tool Search 让模型先看到一个很小的搜索入口，需要某个工具时再加载完整定义，而不是把整个工具箱一次性摊在桌面上。

另一头是 Tool Result。一次 `grep`、测试、日志查询、数据库查询可能返回大段结果。如果这些内容原样进入 History，后面每一轮都可能继续携带。

这类结果最好先在模型之外做确定性过滤：通过项折叠、失败项和关键字段保留、搜索结果去重聚合，再把真正需要判断的部分交给模型。模型没必要先读几千行 stdout，再花一轮自己总结。

所以 Tool Token 有两块：**调用前的工具说明，调用后的工具结果。两头都能膨胀，也都应该尽量在模型之外先治理。** 具体工具和实现放到第二篇展开。

### 代码和 RAG 也不是“取到了就全塞”

在大仓库里直接读几十个文件，和 RAG 一次召回几十个 Chunk，本质上是同一种问题：检索已经完成，但还没有做最后的信息选择。

代码场景可以进一步缩到 symbol、调用方、依赖关系、相关行；知识场景可以做 Top-K、Rerank、去重、相邻 Chunk 合并和 Query-aware Compression。

代码场景更适合先用结构索引、symbol / reference 查询、Repo Map、调用图等方法缩小范围，再让模型读取命中的实现。关键不是“把代码压得更短”，而是**先决定什么代码值得进入当前 Context**。这些具体工具和取舍放到第二篇展开。

### History 最终会把一次性信息变成长期税

某段日志可能只在第 3 轮有用；第 20 轮还带着它，就是历史税。某个文件第 5 轮已经重新读取过，第 1 轮的旧版本还留着，就是重复税。长任务里最好把历史分成三类：

| 信息 | 怎么处理 |
|---|---|
| 当前决策必须依赖 | 留在 Working Context |
| 已经确认、后面还要继承 | 收敛成 State / Summary |
| 原始材料以后可能追溯 | 移到文件、数据库、Memory，只留 Reference |
| 已经过期或被新结果覆盖 | 从当前 Context 退出 |

这比“每隔十轮总结一次聊天”可靠，因为它明确了什么是当前状态，什么只是历史证据。

### 输出也会反过来制造下一轮输入

模型这一轮写的长解释，下一轮往往也会成为 History 的一部分。所以一句本来只需要返回 `PASS` 的内部判断，如果写成几百字，不只是多花了输出 Token，还可能让后面每轮都继续背着它。

面向程序的节点应该尽量返回结构化结果、Patch、ID、状态和证据引用；真正需要给人看的时候，再展开解释。

### 最后还有一种浪费：根本不该发生的模型调用

同一个答案已经算过，却再次调用；一个 JSON Schema 用普通代码就能验证，却让模型读一遍；Agent 没有获得任何新事实，却在同一个错误上循环。这些不是“单次 Prompt 太长”，而是调用次数本身没有必要。

因此总 Token 更接近：

```text
总 Token
≈
每轮输入 Token
+ 每轮输出 Token
再乘上真正发生的模型轮次
```

把一次请求压短只是一个方向；让不该发生的请求直接消失，收益往往更大。

### 判断是不是浪费，别只看“这段长不长”

遇到一段 Context，可以依次问：

1. 当前这一步真的需要它吗？
2. 它能不能只留索引、symbol、ID 或证据引用，需要时再展开？
3. 它是不是已经被更新结果覆盖？
4. 能不能由程序先过滤，再让模型理解？
5. 下游真的需要模型写这么多吗？
6. 这一次模型调用本身能不能被规则、缓存或已有结果替代？

真正应该追求的不是“上下文越短越好”，而是**当前判断所需的最小充分信息**。少了关键事实会返工；多了死信息会持续交税。

这些判断对应的具体工程手段、开源项目和 Agent 平台实现，集中放在 [02_怎么节省Token.md](02_怎么节省Token.md) 里继续展开。

## Agent 为什么越跑越慢、越跑越贵

单轮问答的 Token 很容易理解：输入一包，输出一包。Agent 麻烦在于它会不断循环，而且上一轮产生的东西很容易变成下一轮的输入。

所以长 Agent 的问题不是“某一次请求特别大”，而是**Context 会随着执行过程不断积累**。

### 一次工具调用为什么会变成长期成本

例如 Agent 为了排查失败测试，先读文件，再跑测试：

```text
Round 1：读 a.ts
Round 2：读 b.ts
Round 3：跑测试，返回长日志
Round 4：再读 a.ts 新版本
Round 5：重新跑测试
```

如果 History 原样 append，Round 5 可能仍然带着 Round 1 的旧 `a.ts`、Round 3 的完整日志和所有中间说明。

当这些东西已经完成使命却不退出时，每多跑一轮，模型都要重新付一次阅读成本。

### Agent 需要的不是“无限记忆”，而是 Context 生命周期

一个长任务至少要区分：

```text
当前正在决策的材料 → Working Context
必须持续继承的任务事实 → State
以后可能复用的稳定知识 → Memory
原始代码、日志、网页、文件 → External Evidence
已经失效的中间结果 → Prune
```

把所有东西都留在 Conversation History，只是最省开发时间的实现，不是长期 Agent 的正确状态模型。像 Mem0 这类 Memory Layer 解决的是“长期事实放到哪里、下一次怎么按需召回”；`.codegraph` 则是代码领域更确定性的外部状态：调用关系和 symbol 索引长期保存在本地。两者都不是让 History 无限增长。

### Tool Result 应该有“保质期”

Tool Result 是长 Agent 最容易膨胀的地方。文件内容、搜索结果、测试日志通常只对接下来几步有价值。

长任务运行时应该具备类似的清理能力：达到阈值后，让已经完成使命的旧 Tool Result 退出，同时保留最近仍可能影响判断的证据。

实际工程里可以按结果类型定策略：

- 文件读取：新版本已经读取后，旧版本退出；
- 搜索结果：结论已确认后，只留命中位置或引用；
- 测试日志：只保留当前失败项和关键栈；
- 网页 / API：抽出后续决策需要的字段，原始响应外存；
- 大 Tool Result：需要追溯时保留 handle，而不是正文常驻。

这不是简单“删旧消息”，而是让一次性证据在被消费以后退出热 Context。

### Compaction 解决的是“历史还要继承，但原文太重”

有些历史不能直接删。比如已经做过哪些修改、哪些边界不能碰、当前失败在哪，这些要继续继承。

这时可以把长 History 收敛成结构化状态：

```text
Goal
Constraints
Decisions
Completed
Current Failure
Evidence Refs
Next Step
```

Compaction 做的就是这件事：达到阈值后把历史收敛成可继续执行的状态，后续从状态继续，而不是一直重放早期所有消息。具体平台实现放到第二篇比较。

### 工具本身也会制造固定成本

工具越多，Schema 越重；工具调用越碎，中间结果进入 History 的次数也越多。诊断时要把“工具定义占了多少”和“工具往返制造了多少中间 Context”单独记账。具体的 Tool Search、Lazy Schema 和 Programmatic Tool Calling 放到第二篇。

### Prompt Cache 和 Context Pruning 会互相拉扯

固定 System Prompt、Tool Definition 和稳定前缀适合 Prompt Cache；但如果你不断修改历史、删除旧 Tool Result，缓存前缀会发生变化。

因此不能同时喊“尽量保持前缀不变”和“每轮都精细裁历史”。更合理的是达到一定阈值后一次清掉足够多，再形成新的稳定前缀。

这也是为什么“cached tokens 很高”不等于 Token 已经优化好了。缓存主要降低重复输入的费用和计算，Context 本身仍可能很肥。

### 最贵的循环，是没有产生新状态的循环

Agent 真正失控时，经常出现：重复搜索同一关键词、反复读同一文件、测试失败后没有新诊断就再跑一次、在两个方案之间来回切。

每一轮都应该至少产生一种东西：新事实、有效修改、排除一个假设、通过一个验证。连续几轮都没有，就应该停止、重规划或升级人工，而不是继续调用。

### 一个可落地的长任务运行方式

可以把一次长任务按批次管理：

```text
冻结 Goal / Constraints
↓
当前 Batch 建 Working Context
↓
执行 + 验证
↓
把稳定结果写成 State
↓
原始证据外存并保留引用
↓
清掉已完成批次临时 Context
↓
进入下一 Batch
```

这比让一个对话从第 1 轮一直 append 到第 100 轮更稳。真正需要跨批继承的是任务状态和关键证据，不是全过程录像。

### 判断 Agent 是否该做 Context 治理

出现这些信号时，就不该再靠“模型窗口够大”硬扛：

- 每轮输入 Token 持续上升，但当前任务规模没变；
- Tool Result 占 Context 大头；
- 相同文件和日志被反复读取；
- Context 接近窗口以后模型开始遗漏早期约束；
- 大量工具定义长期不用却每轮携带；
- Prompt Cache 命中不错，但实际请求仍然巨大；
- Agent 频繁发生无进展重试。

长 Agent 的性能问题，本质是状态管理问题。**只会扩大 Context Window，只是把爆炸推迟一点；真正可持续的是让信息有进入、保留、压缩、外存、恢复和退出的规则。**


## 缓存、批量、并行、本地模型分别解决什么问题

AI 优化里最容易发生的一件事，是把所有“看起来更省”的机制都叫成省 Token。其实它们解决的是完全不同的问题。

先把结论摆出来：**Prompt Cache 通常不减少 Context Token；并行通常不减少总 Token；本地模型也不减少 Token。真正能让整次模型调用消失的 Cache，和这几个不是一回事。**

### Exact Cache：完全相同的结果别再算

如果输入可以稳定归一化，而且结果在有效期内不变，可以直接用普通 Cache：

```text
normalized input
+ prompt version
+ model / config
→ cache key
```

命中以后，模型调用直接消失。这是真正减少总 Token。

例如固定文档解析、Embedding、稳定分类结果、代码索引中间产物，都可以考虑缓存。

难点仍然是失效：源文件、模型版本、Prompt、权限或业务数据变化以后，旧结果是不是还能用。

### Semantic Cache：问题不完全一样，也可能复用

Semantic Cache 会用 Embedding + Vector Search 找语义相近的历史请求，再根据相似度决定是否直接复用已有结果。

它把“只有字符串完全相同才能命中”扩展成“意思足够接近也可能命中”。收益更大，风险也更大，因此特别依赖相似度阈值、业务边界和 Cache 失效策略；具体项目放到第二篇。

### Prompt Cache：主要是省钱和 Prefill，不是删 Context

System Prompt、Tool Definition、长规则如果在很多请求里保持完全稳定，Provider 可以复用前缀计算。这样重复输入的计费和延迟可能下降，但模型逻辑上仍然需要这段 Context。

所以看到 `cached input tokens` 很高时，不应该说“这些 Token 已经没有了”。更准确的是：**Token 还在，只是这部分输入被缓存复用了。**

Prompt Cache 最怕前缀频繁变化。长 Agent 如果每轮都重写早期 History，会降低缓存命中；因此 Context Pruning 和 Prompt Cache 需要一起设计，而不是各自开到最大。

### 批量：减少固定开销，重点是吞吐

大量独立小任务逐条请求时，会反复支付连接、调度、固定 Prompt 和调用开销。能合并的分类、Embedding、离线抽取可以批量做。

但 Batch 不保证总 Token 下降。如果 100 条数据最后还是都要被模型读取，信息量仍然在那里。它主要改善的是吞吐和固定调用成本。

### 并行：缩短关键路径，不等于减少工作量

几个互不依赖的文件读取、搜索、检查可以同时发起：

```text
串行：A 结束 → B → C
并行：A / B / C 同时开始
```

结束时间可能明显提前，但三件事仍然都做了，所以总 Token 和总计算量不一定下降，甚至可能因为并发探索过多而上升。

因此并行前要先问：这些分支真的都必要吗？先消掉无效工作，再把必要工作并行。

### 本地模型：改变成本归属，不自动改变 Token 数

把任务从云 API 搬到本地，可能减少外部调用费用、网络延迟和数据外发，但同一段 Prompt 仍然要被模型处理。

本地真正适合的是高频、边界清楚、模型能力够用，并且 API 成本、网络或数据边界确实形成瓶颈的步骤。机器、内存、部署、模型更新、监控、热启动和失败维护都要计入成本。

如果本地小模型能力不够，导致更多重试和更长上下文，最终甚至可能比直接用强模型更慢。

### 这些手段到底算不算“省 Token”

| 手段 | Token 数 | 主要收益 |
|---|---|---|
| 结构索引 / Context Selection | 真减少 | 少做探索，少把无关代码送进模型 |
| Context Pruning / Compaction | 真减少 | 后续输入更小 |
| Structured / Short Output | 真减少 | 输出更小 |
| Exact / Semantic Cache | 命中时整次消失 | Token、延迟、费用 |
| Prompt / Context Compression | 真减少 | 输入更小 |
| Prompt Cache | 通常不减少 | 重复输入更便宜、更快 |
| 小模型 | 不一定减少 | Token 单价下降 |
| Batch | 不一定减少 | 吞吐、固定开销 |
| 并行 | 通常不减少 | 端到端延迟 |
| 本地模型 | 不一定减少 | 成本归属、隐私、网络 |
| gzip / zstd 请求压缩 | 不减少模型 Token | 网络字节和传输 |

最后一项尤其容易误解。HTTP Request Body 用 gzip / zstd 压成更少字节，只是网络上传得更小；服务器解压以后，模型看到的文本和 Token 基本没变。

### 优化时先选对问题

可以这样快速判断：

```text
同样答案反复算 → Exact / Semantic Cache
固定前缀反复发送 → Prompt Cache
任务独立而数量大 → Batch
互不依赖却在排队 → Parallel
高频稳定任务受 API / 网络限制 → Local Model
代码探索反复花 Token → 结构索引 / Symbol / Repo Map 先做结构选择
Context 本身太肥 → 去独立 Token 工程主文做 Selection / Compression / Pruning / Compaction
```

“更快更省”不是把所有优化开关都打开，而是先确认瓶颈到底是 **Token 数、Token 单价、调用次数还是关键路径时间**，再动对应那一层。

## 把整条效率链放在一起

真正做优化时，可以把前面的判断收成一条顺序：

```text
先确认业务结果有没有做对
↓
再看时间花在哪：模型、工具、等待还是返工
↓
再看 Token 为什么增长：输入太大、输出太长还是轮次太多
↓
能由程序、索引和规则确定的工作先拿走
↓
确实需要模型的任务再决定强模型、小模型和路由
↓
重复结果用 Cache，独立任务再谈 Batch / Parallel
↓
最后再看 Prompt Cache、本地模型和单价优化
```

顺序反过来很容易出现假优化：模型换便宜了，但返工更多；并行开满了，但做了更多无效探索；Prompt Cache 命中很好，但每轮 Context 仍然巨大。

所以“更快更省”的最终验收不是某个技术指标变漂亮，而是：**同样质量的可用结果，端到端等待更短、总成本更低、返工更少，而且系统没有因此变得更脆弱。**
