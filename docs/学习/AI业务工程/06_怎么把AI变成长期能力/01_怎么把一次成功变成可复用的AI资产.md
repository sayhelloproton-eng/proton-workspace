# 怎么把一次成功变成可复用的 AI 资产

一次 AI 使用真正有价值，不是这次回答很好，而是下一次遇到类似任务时，不需要从零重新解释业务、重新找资料、重新试 Prompt、重新踩一遍坑。

所以“长期能力”的起点不是平台，而是一个更小的问题：**这次成功里，到底有什么东西值得留下来？应该留下成文档、模板、CLI、Skill、Workflow，还是 Agent？**

很多团队的问题恰好相反。大家每天都在和 AI 做大量高质量工作，但成功经验只活在聊天记录里。换一个人、换一个会话、过两周再做，几乎又回到起点。

真正的资产化，是把一次性的“人脑 + 对话 + 临场判断”逐步变成可以被别人发现、理解、执行、验证和维护的东西。

## 先看一个最常见的浪费

假设一个工程师第一次让 AI 排查线上接口延迟：

```text
先查 Trace
→ 找最长 Span
→ 看 Tool / DB / Model latency
→ 对照 Release version
→ 检查 Token 是否异常
→ 找到 Retrieval 结果暴涨
→ 调整 TopK
→ 跑 Regression
→ 上线观察
```

第一次做这件事，人可能和 AI 来回十几轮。

如果最后只留下聊天记录，下次另一个人遇到同类问题，又会重新问：

```text
“接口为什么慢？”
“该看哪些指标？”
“Token 为什么突然多了？”
“怎么判断是不是 Retrieval？”
```

真正应该留下来的不是那 200 轮对话，而是里面已经被验证过的结构：

```text
排障顺序
+ 必查数据
+ 查询脚本
+ 判断规则
+ 常见 Failure Bucket
+ Regression Case
+ 最终验证方法
```

这才是可复用资产。

## 不是所有成功都值得沉淀

资产化本身有维护成本。

如果一个任务：

- 只会发生一次；
- 每次输入、目标和流程完全不同；
- 没有稳定的成功判断；
- 沉淀以后几乎没人复用；

那就没有必要为了“体系化”强行做成 Agent。

真正值得沉淀的任务通常有几个信号：

```text
重复出现
+ 每次都要重新补同样的 Context
+ 有相对稳定的步骤
+ 有可以验证的结果
+ 错误模式开始重复
+ 不止一个人需要做
```

出现的信号越多，越值得资产化。

## 资产化不是“把 Prompt 存下来”

Prompt Library 很容易成为第一反应，但 Prompt 只是资产的一种，而且往往不是最重要的一种。

一个真实任务通常由很多东西共同决定：

```text
任务说明
+ 输入数据
+ 业务规则
+ Context
+ Tool
+ Prompt
+ 输出 Schema
+ Validator
+ Eval
+ 人工判断
```

只保存 Prompt，会把真正决定成功的条件丢掉。

例如：

```text
“帮我分析本周退款异常。”
```

这句话本身几乎没有复用价值。

真正可复用的东西可能是：

```text
数据口径
退款状态定义
异常阈值
SQL
业务维度
固定分析顺序
输出表格 Schema
证据引用要求
历史异常案例
```

所以更准确的名字不是 Prompt Asset，而是 **Task Asset**。

## 一次成功可以沉淀成很多层级

不应该一成功就上 Agent。

更合理的是从最轻的资产开始，根据复用次数和复杂度逐步升级。

```text
经验 / Case
↓
Checklist / 模板
↓
Prompt / Context Pack
↓
CLI / Script / Validator
↓
Skill
↓
Workflow
↓
Agent
↓
共享 Service / Platform Primitive
```

每升一级，都意味着更高的开发和维护成本。

因此原则应该是：

> **用能解决复用问题的最轻资产，不为了“高级”而升级。**

## 第一层：先留下 Case 和 Decision

最早应该留下的是“发生了什么”和“为什么这么判断”。

例如一次 RAG 事故，不要只留下：

```text
把 TopK 从 20 改成 5。
```

应该留下：

```text
现象：P95 Token 从 8k 升到 24k
证据：Retrieval documents 从 6 增到 20
根因：新索引配置覆盖了旧 TopK
修复：TopK=5 + rerank top3
验证：Regression 42/42 + 线上 P95 恢复
```

这种 Case 的价值在于：以后 AI 或人看到相同信号，可以迅速找到历史模式。

Case 是未来 Regression Set、Knowledge Base、Runbook 和 Skill 的原料。

## 第二层：Checklist 解决“总是漏步骤”

如果问题不是不会做，而是每次都漏一两项，就不需要 Agent。

例如 AI Change Review：

```text
[ ] Model version 是否变化
[ ] Prompt version 是否变化
[ ] Knowledge snapshot 是否变化
[ ] Tool Schema 是否变化
[ ] Eval 是否通过
[ ] Canary 是否配置
[ ] Rollback target 是否存在
```

Checklist 的优点是便宜、透明、容易 Review。

很多团队太快跳到自动化，反而把尚未稳定的流程写死。

流程还在快速变化时，Checklist 往往比 Workflow 更好。

## 第三层：模板解决“结构总是一样”

当任务的输出结构稳定，可以先沉淀模板。

例如 Incident Report：

```text
现象
影响范围
开始时间
版本变化
关键 Trace
根因
缓解措施
最终修复
Regression
后续资产化动作
```

模板不是为了文档好看，而是让每次执行都产生可比较的数据。

如果每次事故都按同样结构记录，后面才能让 AI 自动聚类、找重复根因、统计恢复时间。

## 第四层：Prompt / Context Pack 解决“总在重复解释”

如果每次使用 AI 都要重复说明同一套业务规则，可以把稳定 Context 封装起来。

例如：

```text
退款业务定义
状态机
字段含义
关键约束
常见异常
```

但这里必须区分：

```text
稳定规则
→ Context Pack / Skill

实时事实
→ Tool / RAG

用户本次输入
→ Runtime Context
```

不要把所有东西塞进一个巨型 System Prompt。

否则资产越“完整”，每次调用反而越贵、越难更新。

## 第五层：确定的事情优先 CLI / Script

这是非常重要的一条资产化原则。

如果某个步骤已经可以确定执行，就不要继续让模型“每次重新理解”。

例如：

```text
JSON Schema 校验
→ validator

Git diff / hash
→ git

日志过滤
→ rg / jq / script

代码 caller / callee
→ CodeGraph

仓库批量上下文构建
→ Repomix

数据库统计
→ SQL
```

这类能力一旦变成 CLI，就获得了几个 Prompt 做不到的性质：

```text
明确输入
明确输出
Exit Code
可测试
可组合
可版本化
可被任何 Agent 调用
```

所以 CLI 不是“老工具”，而是非常重要的 **Agent Capability Asset**。

## 第六层：Skill 适合封装“模型需要学会的一种做法”

Skill 更适合下面这种任务：

```text
有一套稳定的方法
+ 需要模型理解语义
+ 需要按需加载说明
+ 可能配套脚本 / 示例 / 资源
```

例如：

```text
代码 Review Skill
Incident Triage Skill
SQL Analysis Skill
Technical Writing Skill
Release Audit Skill
```

一个 Skill 不应该只是几十页 Prompt。

它最好同时包含：

```text
什么时候使用
什么时候不要使用
输入要求
执行步骤
CLI / Script
输出约束
正例 / 反例
验收方法
```

2026 年 Agent Skills 快速流行，本质原因也在这里：它把 Instructions、脚本和资源打成模块，需要时才加载，而不是所有 Agent 永远背着一套巨大 Context。

## 第七层：Workflow 适合稳定、可预测的业务路径

如果流程已经比较固定：

```text
取数据
→ 校验
→ 分析
→ 生成草稿
→ 人工确认
→ 发布
```

那就适合做 Workflow。

Workflow 的核心价值不是“自动化”，而是把已经验证过的路径固定下来。

它比自由 Agent 更容易：

- 测试；
- 观察；
- 审批；
- 恢复；
- 控成本；
- 定位故障。

Anthropic 长期强调：可预测任务优先使用简单、可组合的 Workflow，只有真正需要模型自主决定路径时才上 Agent。

## 第八层：Agent 适合“步骤本身无法提前完全写死”

什么时候才应该把资产升级成 Agent？

通常需要满足：

```text
任务重复存在
但每次路径不同
需要根据中间结果决定下一步
需要多次 Tool Call
成功结果可验证
有明确权限边界
有预算和停止条件
```

例如代码排障 Agent：

```text
问题不同
涉及模块不同
调用工具不同
排查路径不同
```

这时候固定 Workflow 很难覆盖所有情况。

Agent 的价值来自动态决策。

但 Agent 也意味着你必须同时继承前面几章的全部工程能力：

```text
Context
Tool
State
Eval
Observability
Recovery
Security
```

所以 Agent 应该是资产成熟后的结果，而不是资产化的起点。

## 第九层：什么时候才值得做公共 Service

如果多个 Workflow / Agent 都在重复实现同一种能力，就可以再往下抽。

例如：

```text
模型路由
Embedding
Rerank
Document Parsing
PII Redaction
Prompt Registry
Eval Runner
Trace Storage
Credential Broker
```

这时它们已经不应该属于某一个 Agent，而应该成为共享 Primitive。

判断标准不是“技术看起来通用”，而是：

```text
至少多个真实消费者
+ 接口已经相对稳定
+ 重复实现成本明显
+ 统一治理有实际收益
```

没有真实消费者时，不要提前平台化。

## 一项资产至少要有一个 Contract

没有 Contract 的“资产”最终还是只能靠原作者解释。

一个真正可复用的 AI Asset，至少应该回答：

```text
Name
Purpose
Owner
Use When
Do Not Use When
Input
Output
Dependencies
Permissions
Examples
Failure Modes
Eval
Version
Changelog
```

如果是高风险能力，还需要：

```text
Risk Tier
Approval Policy
Rollback
Audit Requirement
```

## Asset Contract 示例

```yaml
name: incident-triage
version: 1.4.0
owner: ai-platform/ops

purpose: |
  对生产 AI Incident 做第一轮分类和证据收集。

input:
  - trace_id
  - release_id

output:
  schema: incident-triage.v2

allowed_tools:
  - trace.read
  - metrics.query
  - release.read

forbidden_actions:
  - production.write
  - release.rollback

success:
  - failure_bucket != unknown
  - evidence_refs >= 2

eval:
  dataset: incident-regression-v7
  gate: accuracy >= 0.9
```

一旦做到这个程度，它才真正能被团队复用。

## 资产必须有 Owner

公共资产最大的死亡方式不是“技术不先进”，而是没人维护。

没有 Owner 以后会发生：

```text
Prompt 过期
Tool Schema 已变
Knowledge 路径失效
Eval 半年没跑
模型升级没人验证
```

所以 Owner 负责的不只是代码，而是资产的长期有效性。

至少包括：

```text
兼容性
Eval
版本
安全
文档
弃用
```

## 资产必须能被发现

资产化以后，如果别人不知道它存在，团队仍然会重复造轮子。

所以需要最小 Registry。

最简单甚至可以只是：

```text
assets/
├── skills/
├── workflows/
├── cli/
├── agents/
└── services/
```

配一个统一索引：

| Asset | 解决什么 | Owner | Consumers | Version |
|---|---|---|---|---|
| incident-triage | AI 故障初筛 | Ops | 4 | 1.4 |
| repo-map | 代码结构查询 | DevX | 11 | 2.1 |
| release-eval | 发布评测 | AI Platform | 6 | 3.0 |

重点不是 UI，而是让“先找已有能力”成为默认动作。

## 资产升级应该有 Promotion Rule

不要靠感觉决定“要不要做成平台”。

可以使用一条很实用的 Promotion Ladder：

```text
第一次成功
→ 留 Case

重复 2～3 次
→ Checklist / Template

重复解释 Context
→ Context Pack / Skill

重复确定步骤
→ CLI / Script

路径稳定
→ Workflow

路径动态且需要自主决策
→ Agent

多个消费者重复实现
→ Shared Service

跨团队需要统一治理
→ Platform Primitive
```

这条规则最重要的意义，是防止过度工程化。

## 不只是升级，也要允许降级

有些 Agent 跑了一段时间以后，会发现：

```text
80% 的路径其实固定
```

那就应该把稳定部分重新下沉成 Workflow / Script，只把少数不确定步骤留给模型。

长期能力不是不断把东西“做大”，而是不断找到更稳定、更便宜的表达方式。

## 资产需要 Eval，不然只是在收藏 Prompt

一个 Skill、Workflow、Agent 升级以后，怎么知道没退化？

必须绑定 Eval。

```text
Asset v1.3
↓
Regression Dataset
↓
Baseline
↓
Candidate v1.4
↓
Quality / Reliability / Cost
↓
PASS
↓
Release
```

前面 04 讲的 Eval，到这里开始变成组织记忆的一部分。

没有 Eval，经验无法安全演进。

## 失败案例比“最佳实践”更值得资产化

最佳实践告诉你：

```text
通常应该怎么做
```

失败案例告诉你：

```text
哪些做法已经真实失败过
```

后者往往更有价值。

例如：

```text
Prompt Injection Case
Token Spike Case
Agent Loop Case
Wrong Tool Case
Bad Rollback Case
Permission Escalation Case
```

这些案例应该逐步进入：

```text
Knowledge
→ Failure Bucket
→ Eval
→ Security Regression
→ Runbook
```

这样“踩过一次坑”才真的变成长期能力。

## 不要把 Chat History 当作知识库

聊天记录可以是原料，但不是最终知识形态。

原因很简单：

- 信息密度低；
- 上下文强依赖当时对话；
- 大量中间错误；
- 难版本化；
- 难引用；
- 难判断是否仍有效。

正确做法是从对话里提炼：

```text
Fact
Decision
Procedure
Case
Rule
Eval
```

再进入相应资产。

## 一个真实的沉淀闭环

假设一个工程师和 AI 完成一次复杂发布事故排查：

```text
Chat / Work
↓
找到真实根因
↓
提取 Incident Case
↓
新增 Failure Bucket
↓
把确定查询写成 CLI
↓
把排查方法写成 Skill
↓
新增 Regression
↓
连续多次复用
↓
稳定路径升级 Workflow
```

这才叫“经验沉淀”。

不是：

```text
把聊天导出成 Markdown
```

## 资产质量最终看复用结果

不要用“资产数量”当 KPI。

```text
Prompt 数量
Skill 数量
Agent 数量
```

越多不一定越好。

真正应该看：

```text
复用次数
成功率
节省重复工作量
失败率
维护成本
多少重复实现被消除
新成员多久能独立使用
```

## 这一篇最后要形成的判断

一次 AI 成功之后，不要先问：

> 要不要做成 Agent？

而应该按顺序问：

```text
这件事会不会再发生？
↓
真正可复用的部分是什么？
↓
哪些是知识？
哪些是规则？
哪些是确定性程序？
哪些需要模型判断？
↓
用最轻的资产承载
↓
绑定 Owner + Version + Eval
↓
真实复用后再升级
```

长期能力的第一个飞轮其实很小：

```text
做一次
→ 留下来
→ 再用一次
→ 修正
→ 变得更稳定
```

当这个动作成为默认习惯，AI 才开始从“个人效率工具”变成真正可积累的工程能力。
