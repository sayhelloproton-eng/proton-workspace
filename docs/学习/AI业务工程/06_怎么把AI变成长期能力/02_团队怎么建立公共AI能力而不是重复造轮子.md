# 团队怎么建立公共 AI 能力，而不是重复造轮子

当一个团队只有两三个 AI 用例时，每个人自己选模型、写 Prompt、连 Tool，看起来最快。

问题通常在第十个、第二十个用例以后出现：

```text
每个项目自己接模型
每个项目自己做 RAG
每个项目自己保存 Prompt
每个项目自己写 Trace
每个项目自己做权限
每个项目自己做 Eval
每个项目自己处理重试
```

这时候“AI 项目很多”不等于“AI 能力很强”。

相反，组织可能只是拥有很多彼此不能复用、不能统一治理、不能一起升级的小孤岛。

长期能力的第二步，是把反复出现的工程问题抽成公共能力，让业务团队把精力放在自己的业务差异上。

## 先看什么叫重复造轮子

两个团队都做 Agent。

A 团队：

```text
OpenAI SDK
自写 Prompt Loader
自写 Tool Registry
自写 Trace
自写 Token 统计
```

B 团队：

```text
Anthropic SDK
另一套 Prompt Loader
另一套 Tool Registry
另一套 Trace
另一套 Token 统计
```

表面上两个团队都交付了功能。

半年以后你会发现：

- 模型切换要改两套；
- 安全规则要接两套；
- Eval 数据不兼容；
- 成本没法统一看；
- Tool 定义重复；
- 事故经验无法共享。

真正的长期能力，是让共同问题只解决一次。

## 先区分“业务差异”和“公共能力”

不要把所有东西都抽平台。

一个简单判断：

```text
业务规则不同
→ 留在业务域

多个业务都需要
且变化逻辑相似
→ 候选公共能力
```

例如：

```text
退款条件
→ 退款业务域

统一模型调用 / 成本 / Retry
→ 公共能力

订单字段定义
→ 订单业务域

Prompt Version / Eval Runner
→ 公共能力
```

平台的目标不是接管业务，而是消除重复的非差异化工作。

## 公共 AI 能力通常分几层

可以把团队公共能力看成一组横向 Primitive：

```text
Model Access
Knowledge
Tools
Workflow / Runtime
Eval
Observability
Security
Asset Registry
Developer Experience
```

它们不一定一开始就属于一个“大平台”。

可以逐个出现。

## 第一层：统一 Model Access

如果每个项目直接写 Provider SDK，很快会遇到：

```text
模型切换困难
凭证散落
成本无法统一
Rate Limit 各自处理
Fallback 不一致
```

公共层可以提供：

```text
model.generate()
model.embed()
model.reason()
```

背后再处理：

```text
Provider
Model Routing
Retry
Quota
Cost
Policy
Fallback
```

但不要过早发明一套“万能 Model Gateway”。

当只有一个消费者时，直接 SDK 往往更简单。

## 第二层：统一 Knowledge Access，而不是统一所有知识

公共平台不应该把全公司的知识硬塞进一个 Vector DB。

更合理的是统一接入方式：

```text
search(query, scope, identity)
```

同时把知识 Ownership 留在领域团队。

例如：

```text
HR Knowledge
→ HR Owner

Finance Knowledge
→ Finance Owner

Platform 提供
→ indexing / retrieval / ACL / freshness / observability
```

公共的是能力，不是内容所有权。

## 第三层：Tool Registry

Tool 是 Agent 真正进入业务系统的入口。

如果每个团队自己包装：

```text
create_ticket
createTicket
jira_create
open_issue
```

最终会出现大量语义重复、权限不一致的 Tool。

公共 Registry 至少应该知道：

```text
Tool Name
Description
Owner
Input Schema
Output Schema
Risk Tier
Permissions
Rate Limit
Version
Consumers
```

这样 Agent 才不是“能连多少 MCP Server”，而是使用一组治理过的能力。

## 第四层：Workflow / Skill / Agent Registry

第一篇已经讲了资产化。

到了团队级，需要让这些资产可发现。

例如：

```text
Skill Registry
Workflow Registry
Agent Registry
```

但 Registry 不应该只是商店页面。

真正重要的是：

```text
哪个仍在维护
哪个已过期
哪个被多少团队使用
最新 Eval 如何
风险等级是什么
```

没有生命周期信息的 Marketplace 很容易变成垃圾场。

## 第五层：Eval 是公共基础设施

如果每个团队自己写 Eval Runner，就很难跨项目积累。

公共 Eval 能力应该提供：

```text
Dataset Version
Runner
Grader
Baseline
Candidate
Report
Regression Gate
```

但业务团队仍然负责：

```text
什么叫业务成功
真实 Golden Set
高风险 Case
```

Platform 负责“怎么稳定地跑”，业务负责“什么值得测”。

这是很关键的边界。

## 第六层：Observability 应该统一数据语言

前面 05 已经讲过 AI Observability。

长期能力要求所有 Agent 至少能说同一种基本语言：

```text
trace_id
session_id
model
prompt_version
knowledge_version
tool
latency
tokens
cost
outcome
quality_score
release_id
```

否则事故发生以后，平台团队连跨 Agent 比较都做不了。

统一 Trace Schema 的价值通常比统一 Dashboard UI 更高。

## 第七层：Security / Identity 不能每个项目自己发明

前面 06 讲的：

```text
Least Privilege
Task-scoped Permission
Credential Broker
Approval
Audit
Kill Switch
```

这些一旦进入多个 Agent，就应该尽量进入公共基础设施。

尤其是：

```text
身份
凭证
审批
审计
```

不适合让每个业务项目各写一遍。

## 第八层：Developer Experience 决定公共能力会不会被用

平台能力正确，不代表有人愿意用。

如果接入需要：

```text
填 12 个 YAML
申请 6 个权限
手写 400 行初始化代码
```

团队还是会绕过平台。

所以公共能力应该提供 Golden Path。

例如：

```text
ai init
↓
选择 use case
↓
生成基础工程
↓
默认接 Trace / Eval / Security
↓
本地跑通
↓
部署
```

Golden Path 不是强制所有项目长一样，而是让“正确的默认做法”最省力。

## Platform 不是“大一统框架”

AI 生态变化太快。

如果内部平台把某个框架绑定得太死：

```text
所有 Agent 必须 LangGraph
所有 Tool 必须 MCP
所有 Prompt 必须某种 DSL
```

一两年以后很可能变成新的迁移负担。

更稳的做法是抽稳定 Contract：

```text
Model Contract
Tool Contract
Trace Contract
Eval Contract
Identity Contract
```

具体实现可以变化。

## 尽量对稳定边界标准化，而不是对实现细节标准化

例如：

不稳定：

```text
Agent Framework
Prompt Technique
Model Provider
```

相对稳定：

```text
输入输出 Schema
权限
Trace
Eval
Artifact Metadata
```

公共平台应该优先控制后者。

## 什么时候真的需要 AI Platform

不是有了三个 Prompt 就建平台。

几个很实用的触发信号：

```text
多个团队重复接模型
多个团队重复封 Tool
成本无法统一看
权限和 Secret 开始散落
Eval 无法复用
事故经验无法跨团队传播
模型升级需要同时改很多项目
```

当这些问题同时出现时，平台的 ROI 才开始清晰。

## 平台应该从真实重复里长出来

健康路径通常是：

```text
项目 A 解决问题
↓
项目 B 再次遇到
↓
识别重复部分
↓
抽 Shared Library
↓
项目 C 验证
↓
接口稳定
↓
Platform Primitive
```

而不是：

```text
先设计一个“企业 AI 中台”
↓
一年后找业务使用
```

## 公共能力的 Owner 怎么分

通常需要区分：

```text
Platform Owner
Domain Owner
Asset Owner
```

例如 RAG：

```text
Platform
→ Index / Retrieval / ACL / Eval infra

Domain
→ 文档质量 / Freshness / 权限来源

Agent Owner
→ 查询策略 / Prompt / End-to-End Outcome
```

如果 Ownership 模糊，出了问题所有人都会说“这是别人的层”。

## 平台要服务“自治”，不是制造中央审批瓶颈

最差的平台模式是：

```text
所有 Prompt 改动
都找 AI Platform Team

所有 Tool
都等中央团队开发
```

这样平台会成为瓶颈。

更合理的是：

```text
中央提供 Guardrail + Primitive + Golden Path
领域团队自治组合
关键风险由 Policy Gate 统一控制
```

这和现代 Platform Engineering 的思想一致：给团队自助能力，而不是中央替大家做全部工作。

## Build vs Buy 不要按情怀决定

公共能力不等于全部自研。

可以按差异性判断：

```text
行业成熟、非差异化
→ 优先 Buy / Open Source

决定核心业务竞争力
→ Build

需要统一治理但实现成熟
→ Wrap
```

例如：

```text
Tracing backend
→ 很可能 Buy / OSS

业务 Tool / Workflow
→ Build

Model Provider
→ Buy

统一 Model Contract
→ Wrap
```

## 不要把 Vendor Feature 当成组织能力本身

今天某个平台有：

```text
Prompt Registry
Agent Builder
Eval UI
```

明天产品可能调整、迁移或下线。

真正的长期能力应该保留在你自己的：

```text
Asset Contract
Dataset
Eval Definition
Tool Contract
Knowledge Ownership
Trace Schema
Security Policy
```

Vendor 可以换，组织资产不应该一起消失。

## 公共能力也必须有版本和兼容策略

例如 Tool Schema 从：

```json
{"userId":"123"}
```

变成：

```json
{"user_ref":"123"}
```

如果没有 Version，几十个 Agent 可能同时坏。

所以 Shared Primitive 也需要：

```text
Semantic Version
Deprecation Window
Migration Guide
Consumer List
Compatibility Test
```

## Consumer List 很重要

一个公共能力准备改时，最先要知道：

```text
谁正在用？
```

如果连消费者都不知道，就无法做 Impact Analysis。

这和普通软件平台完全一样。

AI 只会让依赖更隐蔽，因为很多依赖藏在 Prompt / Tool / Workflow 配置里。

## Usage Analytics 是平台治理的一部分

不要只看“接入项目数”。

应该看：

```text
Active Consumers
调用量
成功率
成本
Eval Pass Rate
重复能力减少多少
平台绕过率
升级迁移速度
```

一个没人用的“完整 AI Platform”没有长期价值。

## 平台最重要的指标之一：从想法到安全上线要多久

最终平台应该降低这条路径的摩擦：

```text
Idea
→ Prototype
→ Eval
→ Security
→ Deploy
→ Observe
→ Improve
```

如果每个阶段都需要重新造工具，平台就没有发挥作用。

## 真实长期能力应该形成一条 Golden Path

一个新 AI Use Case 进入团队以后，理想路径可以是：

```text
先查 Registry 是否已有 Asset
↓
能复用就组合
↓
缺能力再 Build
↓
接统一 Model / Tool / Identity
↓
创建 Dataset / Eval
↓
默认 Trace / Cost / Security
↓
Canary
↓
上线
↓
失败回 Regression
↓
成熟能力再回 Registry
```

注意它是闭环，不是平台“提供一堆 API”。

## 一个最小 AI Platform 不需要很多组件

第一版甚至只需要：

```text
Model Gateway
Tool / Asset Registry
Eval Runner
Trace
Identity / Secret
```

再加一套约定。

等真实问题出现再扩：

```text
Knowledge Platform
Prompt Management
Routing
Cost Policy
Agent Runtime
```

## 怎么避免平台团队脱离业务

平台团队必须持续吃真实 Use Case。

一个有效规则是：

> **每一个新的 Platform Primitive，都必须有真实业务消费者。**

最好至少来自两个不同场景。

否则很容易做出只有平台团队自己觉得优雅的抽象。

## 组织真正应该复用的是“解决问题的方法”

工具可以换。

例如今天：

```text
LangGraph
OpenAI Agents SDK
Claude Agent SDK
```

未来都会变化。

真正应该长期保留的是：

```text
什么时候用 Workflow
什么时候用 Agent
怎么定义 Tool Contract
怎么做 Eval
怎么追 Trace
怎么做 Permission
怎么恢复失败
```

这些才是组织的 AI Engineering Knowledge。

## 这一篇最后要形成的判断

平台不是最终目标。

最终目标是：

```text
一个团队解决过的问题
↓
其他团队不需要再从零解决
```

所以公共能力应该沿着真实重复生长：

```text
Asset
→ Shared Primitive
→ Golden Path
→ Platform
```

而不是：

```text
Platform
→ 再寻找需要它的业务
```

当团队可以快速发现已有能力、组合已有资产、默认获得 Eval/Trace/Security，并只开发真正有业务差异的部分时，AI 才开始成为组织基础设施，而不是几十个互不相干的 Demo。
