# AI 线上问题怎么排查、恢复和管住变更

AI 系统真正难管的地方，不是“会不会出故障”，而是**一次行为变化通常同时跨 Model、Prompt、Knowledge、Tool、Workflow 和 Runtime**。如果这些东西各自随便改，出了问题就很难回答“到底哪次变更导致的”；如果没有预算、超时、幂等和恢复设计，Agent 一旦卡住还可能把故障放大成重复写入、Token 暴涨或业务副作用。

这一篇把三件事放在同一条生产链里：**先管住变更，再定位故障，最后安全恢复。**

## 一、模型、Prompt、知识和流程变更怎么管理

AI 系统最容易踩的一类生产坑，是把某个“看起来只是配置”的改动当成无风险改动。

例如：

```text
换一个模型 alias
改两句 System Prompt
更新一批知识库文档
Top-K 从 5 改成 8
Tool Schema 增加一个字段
Agent 多加一个分支
```

这些都可能不改一行业务代码，却让线上行为大幅变化。

所以 AI 上线以后，治理的基本单位不能只有 Git Commit。你需要管理的是整个 **Behavior Release**。

### 先建立一个判断：AI 的“版本”不是 Model Version

一次生产行为由这组东西共同决定：

```text
Behavior Release
├─ Application Code
├─ Model / Provider
├─ Prompt
├─ Sampling Config
├─ Guardrail
├─ Knowledge Snapshot
├─ Embedding Model
├─ Chunking
├─ Retriever
├─ Reranker
├─ Tool Schema
├─ Tool Implementation
├─ Workflow / Agent Graph
├─ Memory Policy
└─ Feature Flags
```

只要其中任何一项变化，AI 行为就可能变化。

因此应该给整套组合一个：

```text
release_id
```

例如：

```text
ai-release-2026.09.07.3
```

然后每个 Trace 都带上它。

### 为什么“Prompt 改一句”也要版本化

假设客服 Prompt 原来是：

```text
如果无法确定退款资格，请转人工。
```

后来改成：

```text
优先根据已有信息判断退款资格；仅在信息明显不足时转人工。
```

这可能导致：

```text
human_handoff_rate ↓
自动处理率 ↑
错误退款率 ↑
```

代码没有变，但业务风险变了。

因此 Prompt 至少需要：

```text
prompt_id
prompt_version
content_hash
created_at
owner
change_reason
```

最好还能关联：

```text
Eval Result
Release
Rollback Target
```

Langfuse 当前 Prompt Management 就把版本控制、部署标签以及 Prompt Version 和 Trace/Metric 关联作为主要能力之一。真正值得借鉴的是这种思想，而不是必须使用某一个平台。

### Model Change 也必须过 Eval，不要相信“新模型一定更强”

升级模型常见想法：

> “新版本 Benchmark 更高，直接换。”

但真实业务可能发生：

```text
知识题 ↑
格式遵循 ↓
Tool Call 参数稳定性 ↓
Latency ↑
Cost ↑
拒答率 ↑
```

所以模型升级应该和 04 的 Eval 闭环：

```text
Current Model
vs
Candidate Model
↓
同一 Internal Eval Suite
↓
Quality / Reliability / Latency / Cost
↓
Failure Bucket
↓
Shadow / Canary
↓
Promote or Reject
```

不要直接从 Benchmark Leaderboard 跳到生产。

### Knowledge Change 本质上也是 Release

知识库更新经常被认为是“只是数据更新”。

但如果新增 10 万份文档，可能改变：

```text
Embedding Distribution
Search Ranking
Top-K Composition
Index Size
Retrieval Latency
Context Length
Answer Grounding
```

所以 Knowledge 也应该有：

```text
knowledge_snapshot_id
source_version
index_version
embedding_version
chunking_version
built_at
```

一次大规模 Rebuild 前后最好都能回放同一套 Retrieval Eval。

#### 为什么要保留旧 Index

如果新 Index 上线后线上质量骤降，你需要能：

```text
switch index-v12 → index-v11
```

而不是只能：

```text
重新跑 3 小时 rebuild
```

因此生产 RAG 至少应该支持一段时间的：

```text
N / N-1 index coexistence
```

### Tool Schema 变化同样会改变模型行为

例如：

```json
{
  "name": "createRefund",
  "parameters": {
    "orderId": "string"
  }
}
```

变成：

```json
{
  "name": "createRefund",
  "parameters": {
    "orderId": "string",
    "reasonCode": "string"
  }
}
```

后端服务可能认为这是普通 API Schema 变化。

但对 Agent 来说，Tool Schema 本身就是 Prompt 的一部分。

它会影响：

```text
上下文 Token
工具选择
参数生成
Validation Failure
Retry
```

所以 Tool Schema 也应该有独立版本。

### Workflow Change 是最像传统代码、但仍有 AI 特殊性

例如：

```text
原来：
Intent → Retrieve → Answer

后来：
Intent → Plan → Retrieve → Rerank → Verify → Answer
```

流程增加后可能：

```text
质量 ↑
Latency ↑
Token ↑
Failure Surface ↑
```

所以不能只问：

> “新流程是否更聪明？”

还要问：

```text
每个成功任务增加了多少 Step？
多了多少 Tool Call？
P95 延迟变化？
成本变化？
失败点增加在哪？
```

### 所有变更最好生成一份 Release Manifest

例如：

```yaml
release: ai-release-2026.09.07.3
application: 1.42.0
model:
  provider: openai
  name: model-x
prompt:
  refund: refund-v17
knowledge:
  snapshot: kb-20260907
  embedding: embed-v3
  index: refund-index-v12
retrieval:
  config: hybrid-v8
tools:
  schema: refund-tools-v12
workflow:
  version: refund-agent-v21
flags:
  new-refund-verify: true
```

这份 Manifest 不是为了形式主义。

它解决三个实际问题：

1. **能复现。** 当时到底跑的是什么组合；
2. **能比较。** A/B 两个 Release 差在哪；
3. **能回滚。** 哪些组件需要一起退回。

### Change Management 最重要的是“一次少改几个变量”

最难排查的发布方式：

```text
同时换模型
+ 改 Prompt
+ Rebuild Index
+ 改 Tool Schema
+ 改 Workflow
```

线上变好了，你不知道为什么。

变差了，也不知道为什么。

更好的方式：

```text
Baseline
↓
一次主要改变一个变量
↓
Eval
↓
Canary
↓
Promote
```

如果必须多个变量一起发布，就把它们作为一个明确 Release，并提前接受“无法单独归因”的代价。

### 发布前至少做三层验证

```text
Layer 1：确定性 Gate
Schema / Type / Test / Permission

Layer 2：Offline Eval
Golden Set / Regression / Risk

Layer 3：Production Validation
Shadow / Canary / A-B
```

三层解决不同问题。

#### Layer 1

防止：

```text
JSON Schema 错
Tool 不存在
权限不够
配置缺失
```

#### Layer 2

防止：

```text
质量退化
历史 Bug 复发
格式行为变化
```

#### Layer 3

发现：

```text
真实流量分布
真实外部依赖
真实延迟
真实成本
```

### Canary 不只是“10% 用户”

AI Canary 更应该关心：

```text
10% 哪些用户？
哪些任务？
风险级别？
有没有状态写入？
```

高风险写操作不能简单随机给 10% 用户试。

可以：

```text
低风险只读任务先 Canary
↓
内部用户
↓
低价值业务流量
↓
真实写操作
```

把**影响面**当成发布变量。

### Rollback 必须提前设计，而不是出事以后想

AI Release 经常跨多个组件。

例如：

```text
Prompt v17
+
Index v12
+
Workflow v21
```

如果只把代码 rollback，却继续用 Prompt v17 和 Index v12，行为并没有真正回去。

所以 Release Manifest 还应该明确：

```text
rollback_target
```

例如：

```text
ai-release-2026.09.06.4
```

可以一次恢复完整组合。

### Feature Flag 对 AI 特别有价值

适合控制：

```text
new_prompt
new_model
new_retriever
new_tool
new_workflow_branch
new_memory_policy
```

它允许：

```text
不重新部署代码
↓
快速关闭危险能力
```

但 Feature Flag 自己也必须记录进 Trace，否则后续又无法解释为什么两条相同请求行为不同。

### 发布以后要做 Version-Sliced Monitoring

不要只看：

```text
success_rate = 91%
```

要看：

```text
release A = 95%
release B = 84%
```

再看：

```text
prompt v16 = 95%
prompt v17 = 84%
```

同样：

```text
cost
latency
loop_rate
handoff_rate
quality
```

都应该能按 Version 切。

### 什么时候不要把 Prompt 独立于代码发布

Prompt Platform 很方便，但不是所有场景都应该让 Prompt 随时在线修改。

如果 Prompt 和：

```text
Tool Schema
Workflow State Machine
Output Parser
Safety Rule
```

强耦合，独立发布 Prompt 反而会产生版本错配。

这时更合理的是：

```text
Prompt Version
和
Application Release
绑定发布
```

不是“Prompt 一定配置化”，而是根据耦合度决定。

### 一个真正可执行的 AI Change Flow

```text
提出 Change
↓
明确变更变量
↓
生成 Candidate Release Manifest
↓
确定性 Gate
↓
Offline Eval
↓
对比 Baseline
↓
Shadow
↓
Canary
↓
按 Release 监控
↓
Promote
或
Rollback
```

每一步都留下：

```text
版本
证据
结果
```

### 最后记住

AI 的生产变更管理不是：

> “把 Prompt 存到 Git 里就算版本化。”

真正要管理的是：

```text
Behavior Release
=
Model
+ Prompt
+ Knowledge
+ Retrieval
+ Tool
+ Workflow
+ Runtime
```

只要用户能感知到行为变化，它就是一次需要 Eval、发布、监控和回滚能力的生产 Change。

## 二、Token 暴涨、Agent 卡死和死循环怎么排查

Agent 线上最典型的一类事故，不一定报错，而是**一直在做事，却没有进展**。

表现可能是：

```text
任务平时 8 秒
今天跑 90 秒

平时 6k Token
今天 80k Token

平时 3 次 Tool Call
今天 27 次
```

最后甚至还返回一个“正常回答”。

这种问题如果只看 HTTP 状态码，几乎完全看不见。

### 先把三个问题分开

```text
Token 暴涨
Agent 卡死
Agent 死循环
```

它们经常同时出现，但原因不完全一样。

#### Token 暴涨

指的是：

```text
input_tokens
output_tokens
或 total_tokens
```

远高于任务正常基线。

#### 卡死

指的是任务：

```text
长时间不结束
```

但不一定真的“没有执行”。

可能正在：

- 等 Tool；
- 等网络；
- 等 Browser；
- 等子任务；
- 等一个永远不会返回的 Future；
- 在重复推理。

#### 死循环

指的是 Agent 在控制流上重复：

```text
相同状态
→ 相同动作
→ 相同结果
→ 再次进入相同状态
```

关键不是“步骤很多”，而是**没有新增信息和没有状态推进**。

### 第一类 Token 暴涨：Context 自己越滚越大

最典型：

```text
每一轮都带完整 History
+
每轮又追加 Tool Result
+
输出再成为下一轮输入
```

于是：

```text
Round 1:  4k
Round 2:  8k
Round 3: 14k
Round 4: 23k
Round 5: 37k
```

真正需要监控的不是只有最终 `input_tokens`，而是：

```text
tokens_by_step
context_growth_rate
history_tokens
tool_result_tokens
retrieval_tokens
prompt_tokens
```

如果每个 Step 的 Context 都增长，就能很快定位。

### 第二类 Token 暴涨：Tool Result 太肥

例如让 Agent：

```text
执行 git diff
```

一次把 5 万行 diff 原样塞回模型。

或者：

```text
查询数据库
→ 返回 20,000 rows
→ 全部进入 Context
```

Agent 可能只需要：

```text
5 个异常项
```

却消费了所有数据。

这类问题的排查指标：

```text
tool_result_size_bytes
tool_result_tokens
tool_name
result_row_count
```

一旦发现某 Tool 占整个 Context 的 70% 以上，先处理 Tool 边界，不要先换模型。

### 第三类 Token 暴涨：Retrieval 过量

例如：

```text
Top-K = 20
每 Chunk = 2000 tokens
```

理论上单次就可能塞入数万 Token。

如果 Agent 每一步都重新 Retrieve，又会重复累积。

应该监控：

```text
retrieved_chunk_count
retrieved_tokens
unique_document_count
duplicate_chunk_rate
```

尤其要看：

> **取回的内容有多少是重复的。**

### 第四类 Token 暴涨：重复重试

例如 Tool Timeout：

```text
Tool Call
→ timeout
→ LLM 思考
→ Retry
→ timeout
→ LLM 再思考
→ Retry
```

这时 Token 暴涨只是结果，真正根因是 Tool Retry Policy。

Trace 里要能看到：

```text
retry_count
retry_reason
tool_status
```

### 第五类 Token 暴涨：Agent 在“自言自语”

有些 Workflow 会让模型反复：

```text
Plan
Critique
Replan
Reflect
Verify
```

每层看起来都有意义，但如果没有新的外部信息进入：

```text
只是重复重写已有判断
```

这类 Agent 的 Step Count 会很高，但 Tool Call 很少。

可以看：

```text
step_count ↑
tool_call_count ≈ 0
external_state_change ≈ 0
```

这是典型 no-progress 信号。

### Agent 卡死第一步：先看最后一个未完成 Span

最有效的排查方式通常不是看 Prompt，而是看 Trace Tree：

```text
Agent Trace
├─ LLM 1  1.2s
├─ Tool A  0.4s
├─ LLM 2  1.0s
└─ Tool B  76s  ←
```

如果一个 Span 占了 90% 时间，优先查它。

常见等待源：

```text
HTTP
Database
Browser
MCP
Queue
Subagent
File IO
External Job
```

所以 Agent 的每类 Tool 都应该有独立 Timeout，而不是只靠外层请求 Timeout。

### Timeout 要分层，不要只有一个“大超时”

例如：

```text
整体 Task Deadline = 60s

单次 Model = 20s
单次 Tool = 10s
Browser Action = 8s
Retrieval = 3s
```

这样 Tool 卡住时能尽早失败。

如果只有：

```text
HTTP Request Timeout = 120s
```

系统会白等两分钟。

### 死循环到底怎么识别

最简单的方式是找重复 fingerprint。

例如每一步生成：

```text
fingerprint = hash(
  state
  + selected_tool
  + normalized_args
  + key_result
)
```

如果连续出现：

```text
A
B
A
B
A
B
```

或者：

```text
A
A
A
A
```

就非常可疑。

不一定需要模型理解，程序就能先做 Loop Detection。

### No-progress 比 Loop 更重要

真实 Agent 不一定完全重复。

它可能：

```text
搜索 "refund error"
搜索 "refund timeout"
搜索 "refund api timeout"
搜索 "payment refund api"
```

动作字符串不同，但实际没有得到新信息。

所以更强的判断是：

```text
有没有新的 Evidence？
有没有新的 State？
有没有减少 Unknown？
有没有产生 External Effect？
```

如果连续 N 步都没有：

```text
no_progress_count += 1
```

超过阈值就停止或换策略。

### Agent 必须有几个硬 Budget

一个生产 Agent 不应该拥有无限自由度。

至少可以有：

```text
max_steps
max_model_calls
max_tool_calls
max_retries
max_input_tokens
max_output_tokens
max_total_cost
deadline
```

这不是为了“限制智能”，而是为了把故障影响面变成可控。

例如：

```text
max_steps = 12
max_tool_calls = 8
max_cost = $0.50
deadline = 60s
```

超出后进入：

```text
fallback / human handoff / partial result
```

而不是继续烧钱。

### Budget 告警要看“接近耗尽”而不只看“耗尽”

如果所有任务都在第 11/12 Step 才成功，说明系统已经接近结构性问题。

因此监控：

```text
budget_utilization
```

例如：

```text
step_budget_utilization = used_steps / max_steps
```

如果 P95 长期 > 0.8，应该提前优化。

### 重试不是越多越稳

重试只适合：

```text
短暂网络错误
429
临时 5xx
```

而不适合：

```text
权限错误
参数错误
Schema 错
业务拒绝
```

否则会出现：

```text
必然失败
×
自动重试
=
更慢、更贵地失败
```

所以 Retry Policy 要按 Error Type 分类。

### Tool Retry 应该带 Backoff 和 Jitter

例如：

```text
1s
2s
4s
8s
```

加随机抖动，避免大量 Agent 同时重试打爆依赖。

但更重要的是：

> **Retry 之前必须确认这个操作是否安全重试。**

例如：

```text
GET order
```

通常可以。

但：

```text
createRefund
```

如果第一次其实成功、只是 Response 丢了，第二次可能产生重复退款。

这就进入下一篇的 Idempotency 问题。

### 一个 Token Spike 的标准排查路径

假设告警：

```text
p95_tokens
从 12k → 49k
```

按下面顺序：

```text
1. 按 release / prompt / model / workflow 切分
↓
2. 找增长最大的 Trace
↓
3. 看 tokens_by_span
↓
4. 判断来源：History / Retrieval / Tool / Output
↓
5. 看 step_count / retry_count
↓
6. 看是否存在 duplicate context
↓
7. 回到最近 Version Change
```

不要一上来就“压 Prompt”。

### 一个 Agent 卡死的标准排查路径

```text
1. 看 Trace 是否还有活动 Span
↓
2. 找最长 Running Span
↓
3. 判断是外部等待还是模型循环
↓
4. 外部等待 → 查 Timeout / Dependency
↓
5. 模型循环 → 查 step / fingerprint / no-progress
↓
6. 看 Budget 是否生效
↓
7. 看最终为什么没有触发 fallback
```

### 一个死循环的标准排查路径

```text
1. 找重复 Tool / State / Result
↓
2. 看每一步是否获得新 Evidence
↓
3. 看失败结果是否被模型正确理解
↓
4. 检查 Error 是否被错误归为 Retryable
↓
5. 检查终止条件
↓
6. 增加 deterministic loop detector
```

### 生产上最有价值的几个告警

```text
p95_input_tokens ↑
p95_step_count ↑
p95_tool_calls ↑
retry_rate ↑
no_progress_rate ↑
loop_detected_rate ↑
timeout_rate ↑
cost_per_successful_task ↑
```

这些指标一起变化时，比单纯 `error_rate` 更能提前发现 Agent 正在失控。

### Debug 时不要把“模型思考”当第一证据

排查顺序应该优先确定性证据：

```text
Trace
Tool Result
External State
Version
Metrics
```

最后才是模型自然语言解释。

因为模型对“为什么自己刚才这么做”的解释，也可能只是事后生成的合理化。

### 最后记住

Agent 生产故障最关键的概念不是“有没有报错”，而是：

> **有没有持续推进任务状态。**

所以真正应该治理的是：

```text
Progress
Budget
Deadline
Retry
Loop
Outcome
```

只要这六个东西被程序约束住，Agent 即使判断错，也更容易以**有限成本、有限时间、有限副作用**失败，而不是无限运行。

## 三、AI 故障以后怎么降级、恢复和回滚

AI 系统上线以后，故障处理不能只有两种状态：

```text
正常
或
整个服务挂掉
```

一个成熟系统更应该问：

> **某一层坏了以后，还能安全地提供多少能力？**

这就是降级。

而 Agent 还多一个传统聊天系统不明显的问题：它可能已经对外部世界做了一半操作。所以恢复也不能简单等于“重新跑一次”。

### 先看一个最危险的恢复错误

退款 Agent：

```text
Step 1 查询订单       SUCCESS
Step 2 创建退款       SUCCESS
Step 3 写审计日志     TIMEOUT
```

外层 Task 最终显示：

```text
FAILED
```

系统自动 Retry 整个任务：

```text
Step 1 查询订单       SUCCESS
Step 2 创建退款       再执行一次
```

如果 `createRefund` 没有幂等保护，就可能重复退款。

所以 Agent Recovery 第一原则：

> **先确认已经发生了什么，再决定从哪里恢复。**

### 降级、重试、恢复、回滚是四件不同的事

#### Retry

```text
同一个操作再尝试一次
```

适合短暂失败。

#### Recovery

```text
任务中断以后，从已知安全状态继续
```

#### Fallback / Degradation

```text
主能力不可用时，切换到更弱但安全的能力
```

#### Rollback

```text
把系统版本恢复到上一套已知稳定组合
```

不要把它们混成一句“失败重试”。

### 先设计降级梯子

一个 AI 功能可以有：

```text
Level 0：完整 Agent
↓
Level 1：弱化 Agent
↓
Level 2：只读 AI Assistant
↓
Level 3：规则 / 搜索 / FAQ
↓
Level 4：人工
```

例如售后：

#### Level 0

```text
Agent 自动判断
+ 自动退款
```

#### Level 1

```text
Agent 自动判断
+ 人工确认退款
```

#### Level 2

```text
AI 只提供建议
不执行写操作
```

#### Level 3

```text
返回标准售后流程
```

#### Level 4

```text
转人工客服
```

这样模型或 Tool 出问题时，不必“一刀切”关闭整个服务。

### 哪一层坏了，就降哪一层

#### 模型 Provider 故障

可以：

```text
Primary Model
→ Backup Model
→ Rule / Search
```

#### RAG 故障

不要让模型继续“凭记忆答”。

可以：

```text
RAG unavailable
→ 明确进入 no-knowledge mode
→ 只回答不依赖企业知识的问题
或
→ 转人工
```

#### Tool 写操作故障

可以切：

```text
Read-Write Agent
→ Read-Only Agent
```

#### Judge / Eval 服务故障

通常不要阻塞主链：

```text
异步评测暂停
主任务继续
```

除非 Judge 本身就是高风险放行 Gate。

### Fallback Model 不是随便找一个便宜模型

Fallback 必须提前验证：

```text
Prompt 是否兼容
Tool Call 是否兼容
Structured Output 是否兼容
Context Length 是否兼容
Safety 行为是否兼容
```

否则主模型挂了以后：

```text
自动切备用
↓
备用根本不会正确调用 Tool
↓
事故扩大
```

所以 Fallback 也必须进入 04 的 Eval Suite。

### Agent Recovery 必须有 Durable State

长任务不能只存在内存里。

至少要能持久化：

```text
task_id
current_state
completed_steps
external_effects
pending_action
attempt
checkpoint
```

这样进程重启以后才能回答：

```text
已经做到哪？
哪些操作成功？
哪些没做？
```

### Checkpoint 应该放在哪里

不是每一步都必须持久化完整 Context。

更适合在：

```text
状态发生关键变化
外部写操作成功
进入新阶段
人工审批完成
```

以后建立 Checkpoint。

例如：

```text
ORDER_VALIDATED
REFUND_CREATED
NOTIFICATION_SENT
```

恢复时从业务状态继续，而不是从一大段对话继续。

### 写操作必须设计幂等（Idempotency）

Agent 会重试、进程会崩、网络会丢包，这是正常现实。

所以高风险写操作最好带：

```text
idempotency_key
```

例如：

```text
refund:{order_id}:{refund_reason}:{task_id}
```

第一次成功后，再次请求直接返回已有结果。

这样：

```text
Retry
≠
Repeat Side Effect
```

### 无法幂等的操作要有补偿动作

有些业务天然不能简单幂等。

可以设计 Compensation：

```text
Step A 创建资源
Step B 更新关系
Step C 发送通知
```

如果 B 失败：

```text
Compensate A
```

这更接近 Saga 思想。

Agent 不需要知道“Saga”这个词才能工作，但 Runtime 必须把这些确定性恢复规则写清楚。

### Retry 前先判断“发生了没有”

最危险的是：

```text
Request timeout
```

它不等于：

```text
Operation failed
```

可能是：

```text
服务端成功
但 Response 丢了
```

所以恢复步骤应该是：

```text
timeout
↓
query external state
↓
已经成功？
├─ yes → continue
└─ no  → retry
```

而不是直接重试。

### Circuit Breaker 适合保护外部依赖

如果支付 Tool 已经：

```text
连续 50% timeout
```

继续让所有 Agent 调用，只会：

```text
大量等待
大量 Retry
大量 Token
把依赖打得更死
```

Circuit Breaker 可以：

```text
Closed
→ failures exceed threshold
→ Open
→ fast fail / fallback
→ after cooldown Half-Open
→ probe
```

这样故障更快收敛。

### Bulkhead：不要让一个坏 Tool 拖死全部 Agent

例如浏览器 Tool 大量卡住。

如果所有任务共享同一个无限并发池：

```text
Browser stuck
→ worker exhausted
→ unrelated text Agent 也不能运行
```

可以按能力分隔资源：

```text
Model Pool
Browser Pool
Code Execution Pool
External Tool Pool
```

限制每类并发。

这就是 Bulkhead 思路。

### Dead Letter Queue 适合“现在做不了，但不能丢”的任务

例如：

```text
第三方 API 持续故障
```

任务重试 3 次仍失败。

不要无限 Retry。

可以进入：

```text
DLQ
```

留下：

```text
task_id
failure_reason
last_state
attempts
next_action
```

待依赖恢复后重新驱动，或人工处理。

### Rollback 要回滚完整 Behavior Release

上一篇已经讲过：

```text
AI Behavior
=
Model
+ Prompt
+ Knowledge
+ Retrieval
+ Tool
+ Workflow
```

所以事故时如果只执行：

```text
git revert
```

不一定恢复行为。

真正的回滚目标应该是：

```text
release-2026.09.06.4
```

完整恢复：

```text
Prompt v16
Model A
Index v11
Retriever v8
Tool Schema v11
Workflow v20
```

### Prompt Rollback 应该快于代码重新发布

如果确认事故来自 Prompt v17，理想状态：

```text
prompt label
production: v17 → v16
```

几秒内恢复。

但前提是 v16 和当前代码/Tool Schema 仍兼容。

这就是为什么 Release Manifest 必须知道组件兼容关系。

### Knowledge Rollback 也要快速切换

如果 Index v12 Rebuild 有问题：

```text
active_index = v12
```

切：

```text
active_index = v11
```

比重新构建更可靠。

因此不要发布新 Index 后立即删除旧 Index。

### 故障期间最重要的是限制副作用

检测到异常后，可以快速进入：

```text
READ_ONLY_MODE=true
```

例如：

```text
仍允许：
查询订单
查询库存
生成建议

禁止：
退款
删除
发布
转账
修改权限
```

这是 Agent 系统非常有价值的全局 Emergency Brake。

### Human Handoff 是正式降级能力，不是失败兜底文案

很多系统所谓“转人工”只是输出：

> “请联系人工客服。”

真正的 Handoff 应该把上下文结构化交过去：

```text
任务目标
已确认事实
已完成步骤
失败原因
相关证据
推荐下一步
```

否则人工还要从头问一遍，AI 并没有真正降低处理成本。

### 故障恢复以后不要立刻全量放开

依赖恢复后：

```text
Circuit Breaker Half-Open
↓
少量 Probe
↓
Canary
↓
逐步恢复
```

不要：

```text
服务一恢复
→ 全部积压任务同时重放
```

否则会产生恢复风暴。

### Incident Timeline 必须把 AI 版本变化放进去

事故复盘至少记录：

```text
12:01 prompt v17 promoted
12:07 tool_retry_rate ↑
12:09 p95_tokens ↑ 3.2x
12:12 success_rate ↓ 14pp
12:15 alert fired
12:18 switched READ_ONLY_MODE
12:21 rollback release
12:27 success_rate recovered
```

这样才能建立因果链。

### 复盘不是只写“根因：Prompt 问题”

更有价值的是：

```text
为什么没有在 Offline Eval 发现？
为什么 Canary 没拦住？
为什么告警晚了？
为什么 Fallback 没生效？
为什么影响面这么大？
为什么恢复需要人工改 5 个配置？
```

每个问题都应该转成一个系统资产：

```text
Regression Case
Alert
Guardrail
Circuit Breaker
Runbook
Rollback Automation
```

### 一个实用的故障处理顺序

```text
1. Stop the bleeding
   限流 / Read-only / Circuit Break
↓
2. Preserve evidence
   Trace / Version / External State
↓
3. Identify scope
   哪些 Release / User / Task 受影响
↓
4. Decide action
   Retry / Recover / Fallback / Rollback
↓
5. Validate recovery
   Canary / Outcome
↓
6. Gradually restore
↓
7. Convert incident into regression assets
```

先止血，再定位，不要反过来。

### 最后记住

一个能真正上线的 Agent，不只是会成功完成任务，还必须会：

```text
失败得有限
重试得安全
恢复得确定
降级得可用
回滚得完整
```

如果“失败以后怎么办”没有设计，Agent 的自主性越高，生产风险反而越大。

## 四、把变更、排障和恢复连成一个闭环

```text
Behavior Release
→ Eval / Canary / Version-Sliced Monitoring
→ 发现异常
→ Trace 找最后一个异常 Span
→ 判断 Token / Tool / Retrieval / Retry / Loop / Dependency
→ 限制副作用
→ Retry / Fallback / Recovery / Rollback
→ 小流量重新放开
→ Incident 结论进入 Regression / Release Guard
```

最重要的不是“故障处理得快”，而是**每一次变更都可识别、每一次故障都可定位、每一次恢复都不会重复制造副作用。**
