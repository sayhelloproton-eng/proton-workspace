# AI 上线以后怎么看得见问题

AI 上线以后，最先解决的不是“再优化一次 Prompt”，而是先回答两个生产问题：**一次任务到底发生了什么，以及整个系统是不是正在慢慢变坏。**

普通 Web 服务看到 200、P95 和错误率，很多时候还不够。AI 请求可能 HTTP 成功，但检索错了、工具走错了、Token 暴涨了、最后业务状态没有改变；也可能单次看不出问题，但用户分布、知识、Provider、Retrieval 或 Workflow 已经持续漂移。

这一篇把两件事串起来：先建立 AI Observability，让一次任务可追踪；再建立线上健康度和漂移监控，让“什么时候开始变坏”可判断。

## 一、一次 AI 任务为什么成功或失败，怎么追踪

AI 上线以后，最危险的状态不是“接口报错”，而是**接口没报错，但你不知道它到底做了什么**。

一个普通 HTTP 请求返回 200，至少说明服务端完成了一次请求；一个 Agent 返回 200，只能说明外层接口结束了。它内部可能调用了 8 次模型、查了 3 次知识库、重复调用同一个 Tool 4 次、花掉几万 Token，最后还只是“自称任务完成”。

所以生产里的第一件事，不是先做一块漂亮 Dashboard，而是让一次 AI 任务能够被完整还原：**谁发起、用了什么版本、经过哪些步骤、每一步输入输出是什么、花了多少时间和 Token、哪里失败、最后真实结果是什么。**

### 先看一个真实故障为什么普通日志不够

假设线上有一个售后 Agent，负责查询订单、判断退款资格并提交退款。

用户投诉：

> “AI 跟我说退款成功了，但钱一直没退。”

普通应用日志可能只有：

```text
POST /refund-agent 200
latency=8.2s
```

从服务角度看，没有异常。

但真实执行可能是：

```text
User Request
↓
LLM #1：识别退款意图
↓
Tool：getOrder
↓
LLM #2：判断退款资格
↓
Tool：createRefund
    ↳ timeout
↓
LLM #3：看到了一段不完整 Tool Result
↓
最终回答：退款已成功提交
```

真正的问题不是 HTTP 500，而是：

```text
Tool 没有成功
+
Agent 错把不完整结果当成功
+
最终文本和外部系统状态不一致
```

如果没有 Trace，只看应用日志很难还原这条链。

### 一次 AI 任务至少要有三层可观测结构

最实用的心智模型是：

```text
Session / Conversation
└─ Trace：一次完整任务
   ├─ Span：模型调用
   ├─ Span：Retrieval
   ├─ Span：Tool Call
   ├─ Span：Guardrail
   ├─ Span：Handoff
   └─ Span：自定义业务步骤
```

#### Session：一段连续业务过程

例如：

```text
用户：我要退昨天的订单
AI：找到两个订单，请问是哪一个？
用户：第二个
AI：……
```

这里可能产生多个请求甚至多个 Trace，但业务上属于同一次 Conversation / Session。

Session 适合回答：

- 这一段用户旅程发生了什么；
- 前后状态为什么不一致；
- 哪一轮开始跑偏；
- 一次会话总成本是多少；
- 是否发生人工接管。

#### Trace：一次端到端任务

Trace 适合回答：

> “这一次任务从开始到结束到底经过了什么？”

例如：

```text
trace_id=refund-20260907-001
workflow=refund-agent
user_id=u123
release=2026.09.07.3
outcome=FAILED
```

#### Span：一次有开始和结束的操作

典型 Span：

```text
LLM generation
Retrieval
Rerank
Tool call
HTTP request
Database query
Agent handoff
Guardrail
Code execution
```

每个 Span 至少应该有：

```text
start_time
end_time
status
parent_id
operation_name
关键输入摘要
关键输出摘要
错误类型
```

### 这已经不是自定义习惯，而是在逐渐标准化

OpenTelemetry 已经建立 Generative AI 相关语义约定。当前 GenAI 属性里可以表达模型、输入/输出 Token、Tool 定义等信息；官方示例也展示了 Agent 顶层 span、LLM chat span 和 Tool execution span 的关系。

例如当前约定中可以看到类似：

```text
gen_ai.request.model
gen_ai.usage.input_tokens
gen_ai.usage.output_tokens
gen_ai.response.finish_reasons
gen_ai.tool.definitions
```

这件事的意义不是“字段名字统一比较漂亮”，而是 AI Trace 开始能像 HTTP / DB Trace 一样，被标准 Observability 系统理解和关联。

OpenAI Agents SDK 也默认提供 tracing，记录 LLM generations、Tool calls、handoffs、guardrails 和 custom events，并把一次 workflow 表示为 Trace、内部步骤表示为 Span。

所以一个成熟 Agent 的生产诊断，不应该靠：

```text
console.log("进入步骤2")
```

而应该有真正的执行树。

### 但 Trace 不是把所有 Prompt 全量存下来

“为了排障，什么都记录”会立刻引入三个问题：

1. 敏感数据泄露；
2. Observability 存储成本爆炸；
3. Trace 自己变成无法检索的大垃圾堆。

所以要区分：

```text
必须结构化记录
vs
必要时采样记录
vs
禁止记录
```

#### 建议始终记录的结构化字段

```text
trace_id
session_id
workflow_name
release/version
model
prompt_version
knowledge_version
retriever_version
workflow_version
tool_name
tool_version
latency
input_tokens
output_tokens
cached_tokens
cost
retry_count
step_count
finish_reason
status
error_type
outcome
```

这些字段低敏感，而且最适合搜索、聚合和告警。

#### 需要按策略采样的内容

```text
Prompt 原文
Model Output 原文
Retrieved Chunks
Tool 参数
Tool Result
Conversation History
```

它们排障价值很高，但往往包含：

- 用户隐私；
- 企业内部知识；
- Access Token；
- 身份信息；
- 大段业务数据。

生产中更合理的是：

```text
Redaction
+ Sampling
+ Retention Policy
+ Access Control
```

而不是无脑全量落盘。

### AI Trace 里最容易漏掉的是“版本”

假设昨天成功率 95%，今天突然掉到 82%。

如果 Trace 只有：

```text
model=gpt-x
```

几乎没有排查价值。

你至少需要知道这次任务实际用了哪套完整组合：

```text
release=2026.09.07.3
model=gpt-x
prompt_version=refund-v17
knowledge_snapshot=kb-20260907-0900
embedding_model=embed-v3
retriever_config=hybrid-v8
reranker=v4
tool_schema=refund-tools-v12
workflow=refund-agent-v21
feature_flags=...
```

因为线上 AI 的行为不是“Model 单独决定”的，而是：

```text
Behavior
=
Model
+ Prompt
+ Context
+ Knowledge
+ Retrieval
+ Tool Schema
+ Workflow
+ Runtime
+ External System
```

少记录一个版本，都可能把真实原因藏掉。

### 一次 Trace 还要记录“Outcome”，不能只记录 Output

这是 Agent 生产监控和普通聊天日志最大的区别之一。

```text
Output
= Agent 最后说了什么

Outcome
= 真实世界到底发生了什么
```

退款 Agent：

```text
Output = "退款成功"
Outcome = payment.refund.status == SUCCESS
```

Coding Agent：

```text
Output = "问题已修复"
Outcome = tests_pass && expected_diff && no_forbidden_change
```

工单 Agent：

```text
Output = "工单已创建"
Outcome = ticket_exists && fields_correct && no_duplicate
```

只有 Outcome 才能回答：

> **这次 AI 任务到底成功没有。**

### Trace 里还应该有 Quality Score

HTTP Observability 常见的是：

```text
error rate
latency
throughput
```

AI 还必须补：

```text
quality_score
correctness
groundedness
task_success
policy_violation
user_feedback
human_handoff
```

原因很简单：

```text
HTTP 200
≠
AI Answer Good
```

线上质量可以来自：

- 确定性规则；
- LLM-as-a-Judge；
- 用户反馈；
- 人工抽检；
- 真实业务 Outcome。

但不要对所有流量都用昂贵 Judge。更常见的是：

```text
全量：便宜结构指标
↓
规则筛异常
↓
抽样：LLM Judge
↓
高风险/争议：人工
```

### 生产 Dashboard 最少要回答五个问题

不是“有多少 Trace”，而是：

#### 1. 有没有做成

```text
task_success_rate
resolution_rate
human_handoff_rate
fallback_rate
```

#### 2. 做得好不好

```text
quality_score
user_feedback
hallucination_rate
policy_violation_rate
```

#### 3. 花了多少

```text
input_tokens
output_tokens
cached_tokens
cost_per_task
cost_per_successful_task
```

其中真正应该盯的是：

> **cost per successful task**

而不是单次模型调用价格。

#### 4. 花了多久

```text
end_to_end_latency
model_latency
retrieval_latency
tool_latency
p50 / p95 / p99
```

#### 5. 为什么失败

```text
error_type
tool_failure
retrieval_miss
model_refusal
invalid_output
loop_detected
timeout
budget_exhausted
```

### 一个实用的 Trace 排障顺序

收到“AI 今天不对劲”时，不要先读 Prompt。

按这个顺序更快：

```text
1. 找到失败 Trace
↓
2. 看 Outcome 是否真的失败
↓
3. 对比最近成功 Trace
↓
4. 先看版本差异
↓
5. 看耗时最长 / Token 最大 / Retry 最多的 Span
↓
6. 看 Retrieval / Tool 是否异常
↓
7. 最后再读具体 Prompt / Output
```

这是因为很多“模型问题”最后其实是：

```text
Knowledge Index 没更新
Tool API 超时
Schema 改了
Prompt Version 发错
Context 截断
External API 返回空数据
```

### Trace 和 Log、Metric 的职责不要混

```text
Trace
→ 这一单为什么失败

Metric
→ 最近一小时是不是系统性变差

Log / Event
→ 某个离散事件具体发生了什么
```

比如：

```text
Metric：退款 Agent 成功率从 94% 降到 78%
↓
Trace：失败集中在 createRefund Tool
↓
Log/Event：支付服务 12:03 开始 timeout
```

这三层连起来，才叫可观测。

OpenTelemetry 在 2026 年还明确推动新事件往 Logs API + Trace Context 的方向统一，而不是继续扩大旧 Span Event API。对我们更重要的不是 API 迁移本身，而是一个原则：**Trace、Metric、Log/Event 应该可以用同一上下文关联起来。**

### 一个最小可用的 AI Observability 数据模型

```text
Session
  session_id
  user_id
  started_at
  ended_at

Trace
  trace_id
  workflow
  release
  versions{}
  started_at
  ended_at
  outcome
  quality_score
  total_tokens
  total_cost

Span
  span_id
  parent_id
  type
  name
  status
  latency
  tokens
  error_type

Event / Log
  timestamp
  trace_id
  event_name
  severity
  attributes{}
```

不需要一开始就做成复杂平台。

只要这几层能稳定关联，很多线上问题就已经能真正排查。

### 最后记住

AI 上线以后，可观测性的目标不是“留下更多日志”，而是：

```text
一次真实业务任务
↓
能还原完整执行路径
↓
能知道每一步用了什么版本
↓
能看见 Token / Cost / Latency
↓
能识别 Retrieval / Tool / Model / Workflow 的失败
↓
能验证真实 Outcome
↓
能从单次失败聚合成系统性问题
```

如果只能看到模型的最终回答，你监控的还不是 AI 系统，只是在保存聊天记录。

## 二、线上质量、成本和行为为什么会变化

AI 上线以后，经常会出现一种非常让人困惑的情况：

> 代码没改，但效果变了。

昨天回答正常，今天开始拒答；昨天一单 6 千 Token，今天变成 2 万；测试环境成功率 95%，生产一周以后只剩 82%；同一个 Agent 偶尔两步完成，偶尔跑十几步。

传统软件里，我们习惯把“行为变化”和“代码发布”绑定。但 AI 系统的行为由更多动态变量共同决定，所以生产治理必须先理解：**什么东西会漂。**

### 先把“漂移”分成几种，不要都叫模型漂移

线上变化可以粗分成：

```text
1. Traffic Drift
2. Data / Knowledge Drift
3. Model / Provider Drift
4. Prompt / Context Drift
5. Retrieval Drift
6. Tool / Dependency Drift
7. Workflow Drift
8. Cost / Latency Drift
```

它们发生在完全不同的层。

### 第一类：用户和任务变了

最常见，但最容易被误诊成“模型质量下降”。

例如刚上线时只有内部员工试用：

```text
输入完整
术语规范
任务简单
```

一个月以后开放给真实用户：

```text
错别字
省略信息
长对话
情绪表达
非标准需求
恶意输入
多语言
```

结果：

```text
质量分下降
拒答率上升
平均 Token 上升
人工接管上升
```

模型没变，是流量分布变了。

所以质量指标一定要能按维度切：

```text
user_segment
region
language
use_case
intent
input_length
risk_level
```

只看 Overall Average 很容易被骗。

### 第二类：知识和现实世界变了

RAG 系统尤其明显。

例如：

```text
政策更新
商品价格变化
组织结构变化
接口文档更新
代码仓库变更
```

模型没变，Prompt 没变，但知识库已经过期。

典型症状：

```text
Retrieval 看起来成功
↓
但取回的是旧文档
↓
回答有引用
↓
引用本身已经过期
```

所以除了 `retrieval_hit_rate`，还要监控：

```text
knowledge_freshness
index_age
document_version
stale_document_rate
```

如果业务高度依赖新鲜信息，**知识年龄本身就是生产指标。**

### 第三类：模型或 Provider 发生了变化

即使你的代码没发版，也可能变化：

```text
model alias 指向新版本
provider inference stack 更新
sampling 默认值变化
safety policy 调整
context / tokenizer 行为变化
rate limit / latency 变化
```

所以生产中不要只记录：

```text
model="smart-model"
```

而应该尽量记录能够确定实际运行版本的信息，并把“模型升级”当成一次正式 Change。

如果 Provider 只能提供 alias，也至少要把：

```text
provider
model_alias
request_time
API version
release
```

和 Trace 绑定，否则出现行为变化时无从比对。

### 第四类：Prompt / Context 其实一直在变

即使 System Prompt 没动，实际送给模型的 Context 每次都不同：

```text
System Prompt
+ User Input
+ Conversation History
+ Retrieved Context
+ Tool Schema
+ Tool Result
+ Memory
```

长会话里 History 越来越长，可能导致：

```text
重要规则被淹没
上下文被截断
Token 上升
Prompt Cache 命中下降
模型注意力被无关历史稀释
```

所以不要只监控 Prompt Version，还要看：

```text
context_length
history_turns
retrieved_chunk_count
tool_schema_tokens
memory_items
truncation_flag
```

### 第五类：Retrieval 会自己“坏”

RAG 的线上质量变化可能来自：

```text
Embedding Model 换了
Index Rebuild
Chunking 改了
Top-K 改了
Reranker 改了
Metadata Filter 改了
文档大量新增
索引失败
```

这些都可能让：

```text
同一个 Query
→
取回完全不同的 Context
```

所以 Retrieval 不是一个黑盒 Tool Call。

至少应该记录：

```text
query
retriever_version
embedding_version
index_version
top_k
filter
retrieved_doc_ids
retrieval_score
rerank_score
```

然后在线监控：

```text
no_result_rate
low_score_rate
retrieval_latency
retrieved_context_size
stale_result_rate
```

### 第六类：Tool 和外部依赖变了

Agent 很容易把外部系统变化伪装成“模型变笨”。

例如：

```text
API schema 新增 required field
权限过期
第三方接口限流
数据库变慢
浏览器页面结构变化
MCP Server 版本升级
```

Agent 的表现可能变成：

```text
重复调用 Tool
→
拿不到结果
→
再次推理
→
再调用
→
Token 暴涨
```

所以 Tool 层应该有独立指标：

```text
tool_success_rate
tool_latency
timeout_rate
retry_rate
schema_error_rate
permission_error_rate
```

### 第七类：Workflow 的路径分布变了

假设一个 Agent 有：

```text
A → B → C
    ↘ D
```

平时 90% 走 `A-B-C`，突然大量走 `A-B-D`，最终成功率下降。

单看模型质量很难发现。

因此 Agent 还应该监控：

```text
step_count
path_distribution
handoff_rate
retry_count
loop_count
fallback_rate
human_handoff_rate
```

这类指标本质上是“控制流健康度”。

### 第八类：成本和延迟也会漂

即使质量没变，生产系统仍可能变坏：

```text
平均 Context 变长
输出越来越长
Tool 调用次数增加
缓存命中下降
重试增加
模型路由更多落到昂贵模型
```

因此成本至少分：

```text
cost_per_request
cost_per_task
cost_per_successful_task
```

最后一个最重要。

例如：

```text
方案 A
$0.02 / request
成功率 50%

方案 B
$0.03 / request
成功率 95%
```

只看单次请求，A 更便宜。

看“成功任务成本”，结论可能完全相反。

### 生产监控不要只看平均值

AI 的很多事故藏在长尾。

例如平均延迟：

```text
mean = 4.5s
```

看起来不错。

但：

```text
p50 = 2.1s
p95 = 18s
p99 = 58s
```

真实用户会觉得系统非常不稳定。

Token 也一样：

```text
median input_tokens = 6k
p99 input_tokens = 88k
```

这里很可能已经存在长会话、死循环或异常 Tool Result。

所以常见生产指标应该有：

```text
p50 / p95 / p99 latency
p50 / p95 / p99 tokens
p50 / p95 / p99 step_count
```

### AI 生产健康度至少看四个维度

可以把 Dashboard 压成四块：

#### Quality

```text
task_success_rate
quality_score
user_positive_rate
hallucination_rate
human_handoff_rate
```

#### Reliability

```text
error_rate
timeout_rate
retry_rate
loop_rate
fallback_rate
tool_failure_rate
```

#### Performance

```text
end_to_end_latency
model_latency
tool_latency
retrieval_latency
p95 / p99
```

#### Cost

```text
input_tokens
output_tokens
cached_tokens
cost_per_task
cost_per_successful_task
```

一个维度好看，不代表系统健康。

### 线上质量怎么监控，不可能每条都人工看

更现实的做法是分层：

```text
全量流量
↓
确定性规则 / Outcome / Error
↓
异常流量 + 随机采样
↓
LLM-as-a-Judge
↓
高风险 / 低置信 / 用户投诉
↓
人工 Review
```

Langfuse 当前的生产 Evaluation 路线就是类似思路：可以给 live traces 附加自动分数、用户反馈或人工标注，并按分数趋势做监控；Token、Cost、Latency 则可以按 model、user、feature、prompt version 等维度聚合。

这说明“Observability”和“Eval”上线以后会合流：

```text
Trace 告诉你发生了什么
Eval 告诉你发生得好不好
Metric 告诉你是不是系统性变化
```

### 监控变化时，一定要绑定 Release / Version

看到成功率下降：

```text
95%
↓
82%
```

本身没有诊断价值。

真正有用的是：

```text
release A：95%
release B：82%
```

继续拆：

```text
prompt v16：95%
prompt v17：82%
```

或者：

```text
retriever v8：94%
retriever v9：79%
```

所以生产指标要能按这些维度切：

```text
release
model
prompt_version
knowledge_version
retriever_version
workflow_version
tool_version
```

否则 Dashboard 只能告诉你“出事了”，不能告诉你“从哪里开始出事”。

### 告警不要只用固定阈值

例如：

```text
cost_per_task > $0.5
```

有时有意义，但很多变化是相对异常：

```text
过去 7 天 p95 = $0.11
今天突然 = $0.27
```

虽然没到 `$0.5`，已经值得检查。

因此可以同时有：

```text
绝对阈值
+
相对基线变化
+
异常检测
```

例如：

```text
success_rate 低于 90%
OR
相比 7-day baseline 下降 > 8pp
```

对流量有明显周期性的业务，还应该做时间段基线，而不是拿凌晨和白天硬比。

### 最容易被忽略的是“分母”

看到：

```text
hallucination_rate = 1%
```

先问：

```text
在哪些请求里统计？
样本多少？
谁打分？
哪些模型？
哪个版本？
哪些用户？
```

如果昨天 10000 条，今天只有 30 条 Judge 样本，那么两个 1% 不是同一种可信度。

所以线上 AI 指标必须同时知道：

```text
sample_count
sampling_rule
evaluator_version
confidence / uncertainty
```

### 一个实用的漂移排查顺序

```text
1. 先确认是不是流量组成变化
↓
2. 再看最近 Release / Config / Version 变化
↓
3. 看 Retrieval / Tool / External Dependency
↓
4. 看 Context / Token / Step Count 分布
↓
5. 看模型和 Provider 行为
↓
6. 最后看单条 Trace
```

不要反过来一上来就挑几条回答开始“感觉模型变笨”。

### 最后记住

AI 线上变化不是一个“Model Drift”可以概括的。

更准确的心智模型是：

```text
线上 AI 行为
=
Traffic
×
Model
×
Prompt / Context
×
Knowledge / Retrieval
×
Tool / Dependency
×
Workflow
×
Runtime
```

任何一层变化，都可能表现成：质量下降、成本上升、延迟变高、行为异常。

真正的生产治理，是让这些变化**能被看见、能定位到版本、能回到具体 Trace。**

## 三、把可观测性和漂移监控连成一条线

真正能工作的线上治理不是两个 Dashboard：

```text
单次 Trace
→ 找到某次失败发生在哪一步

版本切片 + Metrics
→ 判断失败是不是开始成片出现

Drift / Distribution
→ 判断问题来自流量、知识、模型、检索、工具还是流程

Outcome / Quality
→ 判断技术异常有没有真的伤到业务结果
```

所以观察 AI 的顺序应该是：**先能还原单次任务，再能看群体分布，最后把变化和版本、业务结果连起来。**
