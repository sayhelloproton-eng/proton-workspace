# 怎么用 AI 反过来治理质量和业务

把 AI 系统本身管住以后，下一步才是让 AI 反过来帮助人治理大规模生产数据。这里不是让模型“自动当老板”，而是把它放到传统规则和统计不擅长的语义层：从大量 Trace、用户反馈、输出和业务记录里找失败模式、知识缺口、流程瓶颈和异常信号。

关键边界是：**规则和统计负责筛，AI 负责解释和归类，高风险结论仍然要有证据和人工/确定性 Gate。**

05 前面的内容都在讲：

> 怎么把 AI 管好。

但 AI 上线以后还有另一类价值：

> **让 AI 帮你看系统、看业务、看异常。**

这不是让 Agent 接管生产运维，而是把原来需要大量人工阅读、归类、抽查、分析的工作交给 AI 做第一层处理。

真正适合 AI 的地方，是传统规则很难覆盖、但又存在大量文本和半结构化证据的场景。

## 第一类：线上输出质量抽检

假设每天有 10 万条客服回答。

人工不可能逐条看。

可以做：

```text
100% 流量
↓
确定性规则
↓
抽样 5% / 高风险 100%
↓
LLM Judge
↓
低分 / 争议样本
↓
人工复核
```

Judge 可以检查：

```text
是否答非所问
是否违反政策
是否包含事实冲突
是否引用了错误政策
是否过度承诺
是否缺少必须字段
```

但 Judge 不是绝对真理。

它应该有：

```text
rubric_version
judge_model
judge_prompt_version
score
reason
```

并且定期和人工结果校准。

## 第二类：从大量 Trace 里自动发现失败模式

人工看单条 Trace 很有用，但线上每天可能几十万条。

可以让程序先聚合：

```text
error_type
step_count
tool_name
latency
tokens
release
```

然后 AI 再对异常 Cluster 做语义总结。

例如：

```text
过去 24h 失败 Trace
↓
按结构指标聚类
↓
得到 6 个 Cluster
↓
AI 阅读每组代表 Trace
↓
总结共同模式
```

输出：

```text
Cluster 3：
多数发生在退款任务；
createRefund 返回 409；
Agent 没有识别“重复退款”是终态；
继续 Retry 3 次；
导致 Token 和延迟增加。
```

这里 AI 的价值不是“替代 Metrics”，而是：

> **把大量机器证据压缩成人能理解的问题模式。**

## 第三类：自动 Incident Triage

告警触发后，AI 可以自动收集：

```text
异常指标
最近 Release
相关 Trace
Dependency Health
Error Logs
Feature Flag Change
```

然后生成第一版 Incident Brief：

```text
影响范围
开始时间
最可能变化点
代表 Trace
可能根因
建议先检查什么
```

这比让值班工程师手工在五个系统之间切换更快。

但不能让 AI 看到几个日志就自动：

```text
rollback production
```

高风险动作仍然应该有确定性 Policy 和 Approval。

## 第四类：自动审计 Agent 有没有越界

Agent 的 Tool Call 本身就是非常好的审计数据。

可以检查：

```text
不该调用的 Tool
不该访问的数据
异常高频写操作
越过审批步骤
不符合业务流程的路径
```

例如：

```text
refund > $500
```

规定必须人工审批。

Trace 中发现：

```text
Agent → createRefund
```

却没有：

```text
approval_granted
```

确定性规则就能直接判违规。

AI 适合的是更模糊的审计：

```text
是否存在规避审批意图
是否使用了不合理参数组合
是否存在异常操作模式
```

## 第五类：从用户反馈里自动找产品问题

用户反馈通常是：

```text
“不好用”
“答非所问”
“又让我重复说一遍”
“明明有库存却说没有”
```

如果只看星级平均分，很难知道改什么。

可以：

```text
Feedback
+ Trace
+ Outcome
↓
AI 分类
↓
Failure Taxonomy
```

例如：

```text
Knowledge stale       31%
Wrong intent          22%
Tool timeout          18%
Too verbose           11%
Policy refusal         9%
Other                  9%
```

然后按业务损失排序，而不是按出现次数排序。

## 第六类：自动生成 Failure Bucket

04 里已经讲过 Failure Bucket。

生产阶段可以自动把失败 Trace 归类到：

```text
Retrieval Miss
Hallucination
Tool Failure
Invalid Argument
Timeout
Loop
Policy Violation
User Ambiguity
External Dependency
```

程序先做能确定的：

```text
HTTP timeout
schema error
budget exhausted
```

AI 只处理：

```text
语义跑偏
事实冲突
意图误判
复杂根因总结
```

这和前面 Token 工程的原则一致：

> **能确定计算的先程序做，AI 只接模糊判断。**

## 第七类：运营分析

AI 还能把大量对话和任务记录变成业务洞察。

例如售后：

```text
最近一周客户为什么要求退款？
哪些 SKU 的投诉突然增加？
用户最常问但知识库没有覆盖的问题是什么？
哪些流程最容易转人工？
```

传统 BI 适合：

```text
退款率多少
订单量多少
```

AI 更适合：

```text
退款原因是什么
用户真正抱怨什么
话术里有哪些共同模式
```

两者结合：

```text
SQL / BI
→ 定量

LLM
→ 定性
```

不要让 LLM 替代 SQL 算数字。

## 第八类：发现知识库缺口

可以从真实 Query 中找：

```text
高频问题
+
Retrieval 无结果
或
低 Groundedness
```

聚类后生成：

```text
Knowledge Gap List
```

例如：

```text
1. 新版退款时效 412 次
2. 港澳地区物流 267 次
3. 企业发票修改 193 次
```

这会形成：

```text
生产问题
→ 知识补全
→ RAG Eval
→ 发布
```

## 第九类：发现流程瓶颈

从 Agent Trace 聚合：

```text
哪些 Step 最慢
哪些 Tool 最容易 Retry
哪些路径最常转人工
哪些步骤最常被用户打断
```

AI 可以进一步阅读代表样本，解释：

```text
“为什么大量任务在 step 4 失败？”
```

例如发现：

```text
不是模型问题
而是 step 4 总要求用户提供一个实际上系统已经拥有的订单号
```

这就从“AI 监控”进入“业务流程优化”。

## 第十类：自动生成日报和周报，但不要只做摘要

最没价值的 AI Ops 是：

> “把 Dashboard 数字重新说一遍。”

更有价值的日报应该回答：

```text
1. 今天发生了什么变化？
2. 哪些变化超过正常波动？
3. 主要集中在哪些 Release / Use Case？
4. 代表 Trace 是什么？
5. 可能原因是什么？
6. 最值得先处理的三件事是什么？
```

例如：

```text
退款 Agent 成功率 -9pp
主要集中在 Prompt v17
createRefund retry_rate +34pp
p95 token +2.6x
高概率与错误重试有关
建议先暂停 v17 Canary
```

这才是有行动价值的报告。

## AI 做异常发现不能只靠“问模型有没有异常”

正确顺序通常是：

```text
Metrics / Rules / Statistics
↓
筛出异常窗口
↓
提取相关 Trace / Log / Change
↓
AI 做归类、总结、推断
```

不要：

```text
把全部生产数据扔给模型
→ 问“有没有异常”
```

前者便宜、稳定、可解释。

## AI 分析必须保存证据引用

运营分析如果只输出：

> “用户对物流问题不满意。”

几乎不可验证。

更好的输出：

```text
结论
+ 样本量
+ 代表 Trace IDs
+ 对应 Feedback
+ 时间范围
+ 版本范围
```

这样人才能回查。

## 不要让 AI 自己审自己后直接放行

例如：

```text
Model A 生成回答
↓
Model A 评价自己
↓
PASS
```

这很容易共享同样偏差。

至少可以：

```text
Generator ≠ Judge
```

高风险场景更应该：

```text
确定性 Rule
+
Independent Judge
+
Human Sample
```

## 线上 Judge 要控制成本

不需要 100% 流量都走强模型 Judge。

可以：

```text
高风险任务：100%
普通任务：1%～10% sample
异常 Trace：100%
用户差评：100%
新 Release Canary：提高 sampling
```

再根据风险动态调整。

Langfuse 当前的生产 Evaluation 就支持对 live trace 做自动评分、用户反馈和人工标注，并把 Score 按版本和时间趋势分析。这个思路值得借鉴：**线上 Eval 是 Observability 的质量层。**

## AI 运营分析最好有固定问题，不要每日报告都自由发挥

例如固定：

```text
QUALITY
- 哪个 use case 下降最多？

COST
- 哪个 release 成本涨幅最大？

RELIABILITY
- 哪类 Tool Failure 增长？

USER
- 新出现的前三类投诉是什么？

KNOWLEDGE
- 哪些高频 Query 缺文档？

ACTION
- 哪三项最值得先处理？
```

Prompt 固定以后，跨天结果更可比较。

## 最后形成一个治理闭环

```text
Production Traffic
↓
Trace + Metrics + Outcome + Feedback
↓
规则 / 统计发现异常
↓
AI 聚类、审计、总结
↓
Human Review
↓
形成 Change / Regression Case / Knowledge Update
↓
Offline Eval
↓
Canary
↓
Production
```

这里 AI 不是“系统管理员”，而是：

```text
高吞吐分析器
+
语义分类器
+
证据整理器
+
异常解释助手
```

## 最后记住

“用 AI 管业务”最有价值的地方，不是让它自动替你做所有决策，而是：

> **把过去人根本看不过来的大量 Trace、反馈、文本和异常，压缩成有证据、能行动的问题。**

但最终的高风险生产决策，仍然应该落到：

```text
规则
权限
审批
可回滚动作
```

而不是一句模型判断。

## 把 AI 治理放回完整生产链

```text
Logs / Metrics / Traces / Feedback / Business Data
→ 规则与统计先筛异常
→ AI 做语义分类、聚类、解释、摘要
→ 输出 Failure Bucket / Knowledge Gap / Incident Hypothesis / Ops Insight
→ 人或确定性程序验证
→ 修 Prompt / Knowledge / Tool / Workflow / Product
→ 回到 Eval 和线上监控
```

AI 真正适合的不是替代监控系统，而是把海量、非结构化、难人工阅读的生产证据变成**可调查、可验证、可行动的问题清单**。
