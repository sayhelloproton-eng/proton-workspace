# 怎么让 AI 真正把事情做好

AI 已经决定要用了，下一步就不是继续讨论“值不值得”，而是解决一个更具体的问题：为什么它明明能写、能分析、能调用工具，最后交出来的结果还是经常不能直接用？

从研发视角看，问题通常不只在模型。任务可能一开始就没说清，业务目标和边界没有进入任务；该看的代码、历史约束和运行事实没有拿到；输出虽然像答案，却不能稳定被程序或人接住；证据不足时模型仍然被要求继续回答；系统也可能在简单方案还没跑通时，就急着堆 RAG、Memory、Workflow 和更强模型。

所以“把事情做好”不是把 Prompt 越写越长，而是逐步把一件研发任务变成一个模型能够正确理解、拿到必要事实、产出可检查结果、并根据真实反馈继续修正的工程闭环。


## 先让 AI 真正理解要做什么

AI 做错一件研发任务，很多时候不是“不会写代码”，而是一开始就没拿到一个足够完整的问题。

工程师之间协作也一样。只说“把这个模块重构一下”“把性能优化一下”“这个 Bug 修掉”，对方通常会继续追问：为什么改、现在出了什么问题、哪些行为不能变、做到什么算结束。

AI 不会自动知道这些隐含条件。

例如只给一句：

```text
把上传模块改成支持大文件。
```

它可以有很多合理理解：分片上传、调大请求限制、改成流式处理、做断点续传，甚至换存储方案。每一种都说得通，但未必是当前项目要解决的问题。

所以第一步不是研究“高级 Prompt 写法”，而是把任务本身说完整。至少需要回答：

- 现在遇到的真实问题是什么；
- 当前行为是什么；
- 期望改变什么；
- 哪些行为必须保持不变；
- 这次明确不做什么；
- 最后拿什么证明完成。

如果同一个上传需求补成：“当前单文件在 200MB 左右开始失败；现有鉴权协议和存储接口不能改；这次只处理浏览器到服务端这一段；小文件行为必须保持；需要补对应测试”，模型面对的已经不是一个开放题，而是一个有边界的工程任务。

### “听懂需求”还不等于“理解业务”

工程需求里经常有两层东西：一层是要改什么，另一层是为什么这样改。

还是“大文件上传”。如果只知道“要支持 1GB 文件”，AI 可以设计出技术上成立的方案；但如果真实业务是“用户上传长视频，失败后不能从头重传，而且移动网络会频繁切换”，设计重点就会完全不同。这里决定方案的不是文件大小本身，而是用户流程、失败代价和业务上必须保住的行为。

所以理解业务至少要知道几类信息：

- 这个改动最终影响谁、解决什么真实问题；
- 用户或上游系统现在怎么走这条流程；
- 哪些规则是业务语义，不是实现细节；
- 哪些异常可以接受，哪些一旦发生就算需求失败；
- 技术验收通过以后，业务上怎样才算真的可用。

这也是为什么把一份 PRD 原样丢给 AI 往往还不够。文档可能告诉它“做什么”，真正影响实现的边界却散在现有行为、历史兼容、上下游合同和业务规则里。

### Prompt 解决的是“任务接口”，不是项目知识

Prompt 真正有价值的地方，是把目标、背景、约束、输出和验收方式说清楚。

它能减少歧义，但只能表达你已经知道、并且愿意写进去的东西。项目复杂以后，很多关键事实根本不在 Prompt 里：真实调用关系、历史兼容、当前配置、某次事故留下的限制、跨仓库依赖。

这时继续把 Prompt 写长，并不会让模型自动获得这些事实。

所以要区分两类问题：

```text
任务没说清
→ 补 Prompt / Task Contract

任务说清了，但做判断所需的信息没进来
→ 补 Context
```

这两个问题经常混在一起。结果不对时，如果不先判断是哪一种，就容易陷入“再改一版提示词”的循环。

### Context 不是越多越好，而是当前任务真正需要的工作集

接手陌生仓库时，把整个仓库一股脑塞给模型通常不是好办法。

大量无关代码、重复文档、历史版本和生成文件混在一起，会挤占真正重要的信息。上下文窗口大，不代表注意力可以无限分散。

更实用的做法是围绕任务逐层找相关材料：先入口、相关 symbol、调用方和测试；发现还依赖配置、历史兼容或其他包，再继续扩。

例如排查一个线上 Bug，真正需要的上下文往往不是整个仓库，而是：

```text
报错现象
→ 对应日志
→ 触发入口
→ 相关调用链
→ 最近改动
→ 现有测试
```

每一层都在回答一个具体问题。日志说明发生了什么，调用链说明问题经过哪里，Git 历史解释为什么会这样，测试说明哪些行为已经被系统明确保护。

如果这些信息都拿到了，AI 才有机会理解业务约束，而不是只看代码表面。

### 怎么判断“信息够了”

不是材料越多越安全。更实用的是问：当前这一步做决定时，还缺不缺会改变结论的事实。

如果要改一个接口，至少要知道调用方、上下游合同、关键测试和不能破坏的兼容；如果要排障，要拿到真实错误、运行路径和最近变化；如果要设计方案，要知道目标、非目标和现有架构约束。

一旦发现答案依赖当前上下文里没有的事实，就不要让模型继续猜。先把事实找回来，再继续。

让 AI 真正听懂需求，最终靠的不是一句“请深入思考”，而是两件事：**任务本身有明确边界，做判断所需的信息真的在场。**

## 结果能生成，还要能稳定进入后续流程

AI 回答“看起来不错”，和结果真的能进入研发流程，是两回事。

工程里最麻烦的输出，不一定是完全错误，而是每次都不太一样：这次给结论，下次给解释；这次漏一个字段，下次多一个字段；代码能跑，但改动范围超出任务；分析说得很完整，却没有证据位置。

人手工聊天时，这种变化还能靠阅读吸收。一旦结果要继续被程序、测试、Review 或另一个 Agent 使用，问题马上暴露。

所以控制输出，不是为了“格式漂亮”，而是让结果**可消费、可检查、可比较**。

### 先区分内容边界和格式边界

例如让 AI 分析一个接口，真正需要的可能只有四类结果：

```text
调用方
风险
证据位置
未确认项
```

如果模型顺手又开始设计新架构、修改无关模块、评价整个项目，哪怕这些内容本身有道理，也已经超出任务边界。

内容边界解决“该说什么、不该说什么”；格式边界解决“这些内容以什么稳定结构交出来”。两者缺一不可。

研发任务里最有用的约束通常来自下游：谁要消费这个结果，下游真正需要哪些字段、哪些证据、哪些状态。

### Structured Output 的价值，是把自然语言结果变成可检查合同

如果结果要进入程序，最好不要让下游继续猜自然语言。

可以把输出约束成 JSON Schema、明确枚举、Patch、测试用例列表、错误码，或者一份字段固定的 Markdown 结构。Schema 至少能先挡住缺字段、类型错误和非法枚举。

但结构正确不等于业务正确。

一个合法 JSON 里的 `status` 可以写错；一条 SQL 语法完全正确，也可能操作错表；一个 Patch 格式没问题，依然可能破坏行为。

所以 Structured Output 解决的是“结果能不能被稳定解析和初步校验”，不是“结果已经正确”。

### 输出最好带着证据和不确定性一起交付

研发里仅有结论往往不够。

例如 AI 说“这个接口没有外部调用”，真正有用的输出应该同时说明它查了哪里、依据是什么、哪些范围没有覆盖。这样 Review 的人才能快速判断结论值不值得信。

可以把结果拆成：

- 已确认事实；
- 证据位置；
- 推断或建议；
- 未确认项；
- 下一步需要验证什么。

这样做不是让输出更啰嗦，而是让“确定”和“不确定”不再混成一段很顺的文字。

### 稳定性来自约束和校验，不来自要求“每次都一样”

模型本身有随机性。真正需要稳定的，不一定是每个字都一样，而是关键字段、边界和可验证行为稳定。

例如代码生成可以允许实现细节不同，但不能允许：

- 随意扩大改动范围；
- 漏掉必须保持的兼容；
- 跳过明确要求的测试；
- 输出无法应用的 Patch；
- 把未确认推断写成已验证事实。

所以稳定性要落在软件合同上：输入约束、输出结构、业务规则、测试和 Review，而不是期待模型永远生成同一句话。

如果一个结果只能靠“读起来还不错”验收，它很难进入稳定流程。能被程序检查的先交给程序，必须由人判断的地方明确留下 Review 点。

控制 AI 输出的目标不是把自然语言变僵硬，而是让下游知道：**该拿什么、怎么检查、哪里不能越界、哪些地方仍然需要人判断。**

## 为什么会胡说、瞎猜、跑偏，以及返工为什么降不下来

研发里最危险的 AI 结果，不是明确报错，而是“看起来很合理”。

它可能没看到真实调用方，却说“这个接口只在当前模块使用”；没拿到生产配置，却根据开发环境推断线上行为；没查历史提交，就补出一个听起来很像真的设计原因。

这些问题常被统称成“幻觉”，但真正处理时要拆开看。

### 胡说，常常发生在证据不足但系统仍要求它给答案的时候

语言模型很擅长补全一个连贯答案。没有事实时，它也能生成一个符合常识和上下文风格的解释。

所以减少胡说，不能只在 Prompt 里写“不要编造”。更有效的是让任务允许不确定：

- 找不到证据时明确说未确认；
- 事实、推断、建议分开写；
- 关键结论必须附来源或验证方式；
- 缺关键事实时先查，不够就停。

在工程场景里，“我还不能确认”往往比一个漂亮但错误的结论更有价值。

### 瞎猜，往往是本来可以查，却没有去查

“这个函数有多少调用方”“测试到底过没过”“当前配置是什么”，这些问题如果系统能直接给事实，就不该让模型靠语言概率推断。

能搜索就搜索，能查调用图就查调用图，能跑测试就跑测试，能看真实日志就看真实日志。工具的意义，是把“模型觉得可能这样”变成“系统现在确实这样”。

当然，工具结果也不是最终真理。搜索命中只是候选，编译通过不等于业务正确，单测通过也不代表真实流程一定没问题。证据要和它能证明的范围对应。

### 跑偏，往往不是某一句答错，而是任务目标和状态慢慢漂了

这里要和前面的“胡说”分开。胡说主要是事实可靠性问题；跑偏更像目标管理问题——模型说的每一句甚至都可能成立，但整件事已经离原任务越来越远。

长一点的研发任务很容易出现这种情况：前几轮还在解决原问题，后面开始顺手重构、顺手清理、顺手补“更优雅”的设计，最后改动越来越大。

原因通常不是模型突然失控，而是：

- 目标没有被持续保留；
- 已确认和未确认状态混在一起；
- 每一轮都重新解释任务，边界逐渐变化；
- 中间结果没有验，就继续往后推进。

所以长任务需要阶段目标和停止点。每一批都要知道自己解决什么、什么不动、做完以后拿什么验证。

### 返工多，先看 Review 到底在修什么

如果 AI 每次生成后，人都要花很久 Review，不能只得出“AI 质量不行”这个结论。

把返工原因拆开更有用：是需求理解错了、上下文缺了、事实没查、输出结构不稳定、代码行为错了，还是改动范围太大。

不同返工原因需要不同修法。缺事实就补事实，边界不清就补任务合同，结构不稳就加 Schema，行为错误就加测试和真实运行验证。

### 真正有效的修正，依赖新证据进入下一轮

工程师写代码本来就不是“一次生成完事”。会编译、跑测试、看日志、Review，再根据结果继续改。

AI 也一样。

```text
AI 先给出修改
→ type check 报错
→ 把报错作为新证据送回去
→ 修正
→ 跑 targeted test
→ 根据失败继续修
→ 最后做真实运行验证
```

这和“多生成几次碰碰运气”完全不同。前者每一轮都增加了外部证据；后者只是在同一片信息里继续采样。

所以减少返工的关键，不是让模型第一次就绝对完美，而是让错误更早暴露、原因更容易分类，并把真实反馈送回下一轮。

测试覆盖好的项目往往更容易把 AI 用好，也正因为如此：不是测试让模型变聪明，而是系统能更快告诉它哪里错了。

看到 AI 胡说、瞎猜、跑偏时，先别急着换模型。先问：**它缺的是事实、边界、状态，还是反馈？** 找到这一层，返工才有机会真正降下来。

## 信息缺口不同，Context、RAG、Tool、Memory 不能混用

一个线上问题交给 AI 排查时，可能同时缺四种完全不同的信息：这次报错和相关代码、过去为什么这样设计、系统现在真实跑成什么样、以及项目长期约定。

表面看都叫“补信息”，实际拿法完全不同。把四种东西都塞进 Prompt，会越来越乱；反过来，一看到信息多就上 RAG、Memory，也可能把系统做重却没解决真正缺口。

这里先不从技术名词出发，而从一个判断开始：**这条信息是当前任务临时需要、从知识库里按需找、必须去真实系统现查，还是值得跨任务长期复用？**

前面已经讲过“当前任务要把真正需要的材料带进来”；这里再往前一步，把不同类型的信息拆开，避免 Context、Search / RAG、Tool、Memory 互相替代。

### Context：这次任务现在就需要的工作集

Context 是当前任务里必须直接看见的材料。

例如改一个接口时，相关实现、调用方、测试、任务约束都应该进入当前工作集。排障时，报错、日志、触发路径和最近改动也应该在当前上下文里。

Context 的特点是“和这次任务强相关”。任务变了，工作集也应该跟着变。

它不追求把项目所有知识都装进去，而是保证当前这一步不会因为缺关键材料而瞎猜。

### Search / RAG：需要时从大量知识里把证据找回来

项目文档、历史方案、接口说明、规范、FAQ 可能很多，不适合每次全部放进 Context。

这时需要搜索或 RAG：问题出现以后，先找到相关材料，再把真正有用的片段送给模型。

RAG 解决的是“知识很多，当前只需要其中一小部分”。它不是让模型永久记住知识库，也不等于检索出来的内容自动就是真实事实。

检索出来的文档可能过期，也可能和当前代码冲突。因此 RAG 给的是证据候选，最终还要判断来源、版本和权威性。

### Tool：答案依赖当前真实状态时，直接去系统里查

有些问题不是“知识缺失”，而是事实会变化。

当前分支有没有新提交、测试到底过没过、某个接口实际返回什么、生产配置是什么、数据库里某条记录现在是什么状态——这些都应该从真实系统读取。

这时 Tool 比继续扩 Prompt 或 RAG 更重要。

研发里常见的 Tool 包括精确搜索、调用图、Git、测试、构建、日志、数据库查询、浏览器和外部 API。它们的共同作用，是把模型的推断拉回到当前可验证事实。

### Memory：跨任务复用那些长期仍然成立的信息

有些内容每次任务都重新解释很浪费，例如项目长期规则、稳定的代码风格、用户偏好、固定工作流程。

这类信息适合进入 Memory，让下一次任务不必从零开始。

但 Memory 不能当实时状态。

某个任务现在做到哪、线上配置有没有变化、当前仓库 HEAD 是什么，这些都应该重新读取。旧记忆如果被当成当前事实，会形成一种很隐蔽的错误：答案看起来有历史依据，实际已经过期。

### 四者怎么选

可以先用一个最简单的判断：

```text
这次任务现在就需要的材料 → Context
大量项目知识里按问题找证据 → Search / RAG
答案依赖当前真实状态 → Tool
跨任务长期复用的稳定信息 → Memory
```

它们可以组合，但组合顺序仍然应该跟着问题走。

例如排查一个线上问题：任务目标和当前报错进入 Context；历史事故和设计说明通过 Search / RAG 找回来；当前日志、代码、测试结果通过 Tool 读取；项目长期的排障约束和代码规范可以由 Memory 提供。

这样每种信息都有来源，也知道什么时候需要重新读取。

真正要避免的，是用一种机制硬扛所有信息问题：把整个知识库塞进 Context、拿 Memory 当实时数据库、让 RAG 代替真实运行验证，或者明明可以查却让模型猜。

让 AI 拿到信息，重点不是“越多越好”，而是**信息的类型、时效和来源要和当前判断匹配。**

知道每种机制解决什么以后，还要多问一步：这些能力是不是现在就需要系统化。一个机制“有用”，不等于每个任务都值得为它增加一层架构。

## 什么时候普通提示就够，什么时候才值得把系统做重

一个 AI 任务做不好，很容易马上想到“是不是该上 RAG、Agent、Memory，或者换更强模型”。

但一次结果不好，通常不足以证明系统需要升级。可能只是任务没说清、少给了一个文件、验收条件没写，或者本来可以直接查的事实没有查。

更实用的判断不是“哪个技术更高级”，而是：**当前这套简单做法，究竟在哪个地方已经反复撞到上限。**

### 先把最小闭环做完整

例如让 AI 修改一个解析函数。如果相关实现、输入输出和测试都已经给到，任务边界也很清楚，那么普通 Prompt + 当前材料 + 一次测试反馈通常就够。

这个阶段如果结果不好，先查最基础的几件事：

- 任务目标有没有歧义；
- 关键文件是不是漏了；
- 输出范围是不是没约束；
- 有没有明确测试告诉它哪里错。

这些问题都没处理，就直接上更重架构，通常只是把原来的模糊问题包进更多组件里。

真正该升级，是简单方案已经完整，但同一种限制仍然反复出现。

### 反复缺同一类项目知识，才说明检索应该进入系统

如果每次改接口都要人工去文档里找协议、历史设计和业务规则，问题已经不是“这次少给一份材料”，而是知识选择本身成了重复工作。

这时 Search / RAG 才开始有明确价值：让系统按当前问题去找相关证据，而不是每次靠人手工拼 Context。

反过来，如果项目很小、需要的材料固定，而且工程师两分钟就能选出来，接一套检索链路未必更好。

升级信号不是“文档很多”，而是**人工挑知识已经反复成为任务的一部分，而且容易漏、容易拿错版本。**

### 结论总依赖“现在到底是什么状态”，才值得接 Tool

一个任务如果只需要解释现有代码，静态材料可能足够。

但当问题反复卡在“当前调用方是谁”“测试现在过没过”“线上实际返回什么”，继续补文档已经解决不了，因为这些事实会变。

这时系统需要能够直接读取当前状态。

真正的升级信号是：**模型经常因为缺少可查询的实时事实而猜，而这些事实本来可以从系统直接拿到。**

### 输出开始被程序消费，才值得把结构化约束提到系统层

如果结果只是给工程师读，一段结构清楚的 Markdown 可能已经够用。

但当输出要继续被程序解析、进入下一步自动化，或者多个 Agent 之间传递，结构不稳定就会直接变成系统故障。

这时才值得把 Schema、固定字段、枚举和 Validator 提到更正式的位置。

升级信号是：**下游已经不能靠人读一遍兜底，结果必须被机器稳定消费和检查。**

### 同样的稳定信息每次都重复解释，Memory 才有价值

如果每次任务都要重新说明同一组长期规则、代码风格、项目约束，重复已经开始影响一致性和使用成本。

这时可以把真正稳定的信息沉淀下来。

但只要内容会快速变化，就不应该因为“经常用”就放进长期记忆。当前分支状态、线上配置、任务进度仍然应该现查。

升级信号是：**信息跨任务仍然成立，而且重复解释本身已经成为负担。**

### 任务必须连续经过多步判断和反馈，才需要 Workflow / Agent Loop

如果任务只是“分析并给建议”，单轮交互已经能完成，不需要为了自动化而自动化。

真正的变化发生在任务必须这样推进时：

```text
分析影响范围
→ 修改一批
→ 跑测试
→ 根据失败修正
→ 再验证
→ 决定下一批
```

这里后一步依赖前一步的真实结果，系统需要维护阶段状态、工具反馈和停止条件。此时 Workflow 或 Agent Loop 才不是装饰，而是任务本身的承载结构。

升级信号是：**任务已经天然是多步闭环，靠一轮 Prompt 或人工不断复制结果才能勉强串起来。**

### 模型选择和训练，应该在系统问题排干净以后再判断

如果任务边界、上下文、知识、工具和反馈都不稳定，很难证明失败真的是模型能力不足。

只有这些条件已经相对固定，而且大量同类样本持续暴露同一个能力缺口，才值得比较更强模型、小模型专项化、Few-shot、微调或其他训练手段。

否则很容易花力气“训练模型”，最后发现真正的问题只是输入不完整或事实根本没接进来。

### 最后别问“要不要上某个技术”，问“现在反复卡在哪”

可以把升级判断压成一条很短的链：

```text
任务本身有歧义 → 先把任务说清
每次都人工挑同类知识 → 再考虑检索
结论依赖实时事实 → 接真实工具
下游必须机器消费 → 收紧结构和校验
稳定信息反复解释 → 再考虑 Memory
任务天然多步并依赖反馈 → 再上 Workflow / Agent Loop
系统条件都稳定后仍有能力缺口 → 再看模型与训练
```

真正重要的不是这条顺序本身，而是每次升级都能回答：**如果不加这一层，哪个已经反复出现的问题解决不了？**

回答不出来，就先别加。

这样系统不会因为“AI 技术很多”越堆越重，也更容易知道结果变好到底是因为哪一层起了作用。
