# ProFlow 历史证据与决策档案

这份档案保存 ProFlow 从 2026 年 7 月末到 9 月初形成当前架构时，仍然值得追溯的**时间线、失败现场、Decision Episode（决策事件：旧方案、真实触发、裁决、代价和证据构成的一条变化链）、commit 锚点和证据边界**。

它不是第八篇主题文章，也不是当前工程真源。README 与 01～07 负责让读者理解“系统现在为什么这样设计”；这份档案只在读者继续追问“当时到底发生了什么、凭什么做出这个判断”时提供 Provenance（来源链：一个结论从哪些历史事实和证据演变而来）。

2026-09-17 完成全量覆盖审计后，原 `docs/项目与实践/ProFlow/` 下的 20 份研究材料退出正式维护。它们的独有信息已经进入当前知识文章、本文或其它仍存的专题研究归档。原文件名继续作为历史来源身份保留，避免删除文件以后丢失出处。

## 如何使用这份档案

当前事实发生冲突时，权威顺序始终是：

```text
当前 Runtime / 外部 Reality / Owner fact
> 当前 Source / Spec / Test / Registry
> Git 历史与原始 Evidence
> 本档案的历史总结
```

因此，下面出现的“当时 READY”“dirty migration”“手机模型性能”“Real-2 通过”等，只证明对应历史时间点，不自动代表 2026-09-17 之后的当前状态。

历史材料曾使用多种证据标签。这里统一理解为：

- `GIT_VERIFIED / SOURCE_VERIFIED`：能由对应 Git 或源码材料机械复核；
- `HISTORICAL_VERIFIED`：在对应历史实验中有真实设备、API、文件或运行结果；
- `PROJECT_OWNER_CONFIRMED`：项目 Owner 明确确认的路线与工作现场；
- `DERIVED`：由多条已验证事实推导出的架构判断，不冒充原始证据。

## 一、从“ChatGPT 能不能安全碰到 Mac”开始

### 2026-07-28：最小可信本机闭环

第一批连续提交包括：

```text
5b1c293  docs(gateway): add incremental Custom GPT Actions MVP plan
979ae05  feat(contracts): add task and result contract v1
e69d018  feat(gateway): add local health and readiness service
f640bb5  feat(auth): protect gateway capability endpoint
0340074  feat(policy): enforce capability allowlist
b061e14  feat(runtime): add local task execution service
a4a441c  feat(gateway): connect local runtime task pipeline
```

当时问题非常窄：Custom GPT 能否通过 Action 安全、稳定、可审计地调用 Mac 本机能力。顺序先建立 Contract、Gateway、Auth、Policy、Local Runtime 和 allowlisted Capability，再把 Custom GPT 接进来。

这个顺序留下了后来一直没有变的原则：**Host 可以表达意图，但不能因为会说自然语言就直接获得 raw shell、任意文件系统或最终业务 Authority（决定权：谁有资格改变某类正式事实）。**

### Gateway / Runtime 的可信链路当时具体验证了什么

随后 EXP-005 / EXP-006 把这条“能碰到 Mac”的结论推进到更严格的信任链验证。历史实验真实验证过：

```text
Public Action
→ 只进入 Gateway
→ 外部身份 / Key 校验
→ Gateway default-deny Policy
→ Loopback Runtime
→ 独立内部 Key
→ Runtime 再做一次 default-deny Policy
→ allowlisted Capability
→ structured TaskResult
```

Gateway 与 Runtime 当时都只监听 Loopback，公网入口只暴露 Gateway；外部 Key 和内部 Key 分离，请求体、响应体、并发与 timeout 都有边界，未知 Capability 默认拒绝，错误响应不回传原始 Stack 或 Secret。这个实验没有证明“生产级 Gateway”或“完整持久 Task Runtime”已经成立，它证明的是：**自然语言 Host 到本机能力之间必须存在两层独立的程序性信任边界，公网可达也不能等价成 Runtime 裸露。**

同一阶段的 `Task / Result / Error Contract v1` 还留下一个后来一直适用的协议纪律：先冻结跨服务合同，再实现服务；`contractVersion: "1.0"` 与 npm package version 独立演进，Task、Result、Error 和 Evidence 都使用结构化边界，破坏性语义变化必须显式升级 Contract，而不是借包版本悄悄改变协议。

### 2026-07-29～07-31：Cloudflare 路线主动收缩

开发期公网入口先尝试 Cloudflare Worker / Tunnel / Edge proxy。它技术上可工作，但 Edge、Origin、Remote Secret、VPN / Tunnel 条件和本机状态同时存在，使一个“先证明 Action → Local Runtime”的阶段背上过多运维对象。

2026-07-30 Project Owner 做出切换，7 月 31 日 Git 落下：

```text
cf86998 feat(mvp): complete Microsoft Dev Tunnels Custom GPT workflow
```

这里不能推导“Dev Tunnel 永远优于 Cloudflare”。历史能证明的是：**基础设施复杂度必须服从当时阶段目标；可工作的方案也可能因为治理成本过高而被主动放弃。**

## 三、Phase 2 证明能力，也证明万能 Browser Host 不该继续长大

2026-08-04～08-10，平台从“本机 Capability”扩展到 Controller、Task Control、Local Control、Browser Host 和手机模型实验。主链开始接近：

```text
User Goal
→ Controller Decision
→ Task Coordination
→ Local / Browser Effect
→ Approval / Evidence
→ Result
→ Controller Continuation
```

真实 Chrome 串联证明了 Observation、Dispatch、Approval、Delivery、Wake 都能发生，也暴露 Browser Host 同时承担 observation、execution、approval waiting、response lifecycle、human interaction 和 continuation 的结构性问题。

Phase 2 因此以明确边界收口：

```text
MVP COMPLETE
Production Ready = NO
允许 Phase 3 颠覆性重塑
REWRITE implementation
PRESERVE validated semantics
```

这次退出非常重要：**验证型实现的目标是产生足够信息增益，不是因为已经投入很多代码就无限打补丁。**

### Phase 2 收口不是一次“Happy Path 全绿”

旧 `ai-agent-platform` 第二阶段材料保留了比最终结论更细的真实验收链。`Level 2（只读串联验收：不产生真实页面写副作用的跨域闭环）` 已经完成：Task `phase2-l2-real-20260808-0040-02` 最终 `COMPLETED`，并留下 `TASK_CREATED → ROLE_WORK_REQUESTED → ROLE_WORK_SUCCEEDED → HOST_DISPATCH_CREATED → HOST_DISPATCH_DELIVERED → HOST_RESULT_REPORTED → TASK_COMPLETED` 的完整事件链。

`Level 3（写链验收：包含真实 Browser 副作用、人工授权和 Controller continuation）` 没有一次跑完，而是靠多次真实失败逐段暴露边界：

```text
attempt-01
→ ordinary SUBMIT_MESSAGE 被错误要求 PLATFORM_WAKE 授权
→ 后续由 e9fb952 修正 Platform Wake 与 Human Approval 路由

attempt-02
→ Approval Draft 已存在，但 precondition / action fingerprint 不一致
→ 后续由 d8cd8b2 稳定 approval precondition

attempt-03
→ Draft 之后页面或 planned action 发生变化
→ 无 Delivery / Result / 可见消息副作用

attempt-04
→ RECEIVED
→ CLAIMED
→ APPROVAL_PENDING
→ 多次 reclaim
→ PREPARED
→ EXECUTING
→ UNCERTAIN
→ REPORTED
→ USER_CONTROL_ACTIVE
```

attempt-04 尤其重要。Draft 到最终 Observation 期间，`binding_id`、`conversation_ref`、`gpt_ref`、`page_fingerprint`、`action_fingerprint` 和 `page_precondition_hash` 保持稳定，因此这次 `UNCERTAIN` 不能再简单归因于 durable identity 漂移。它直接推动了 `ca6bda0` 的 user-control execution gate，也强化了后来“副作用结果不确定时先读现实、禁止 blind retry”的纪律。

Phase 2 最后还真实形成过 `HOST_DISPATCH_DELIVERED`，但 Browser Delivery 之后继续等待 Controller response，使下游 response / Action confirmation failure 可能反向污染已经发生的页面副作用。这个现场是后来 **Delivery terminal boundary（交付终止边界：真实副作用已经有交付证据后，该 Effect 的生命周期应结束）** 的直接来源。

这一轮关键 hardening commit 包括：

```text
3847c7d  separate browser executor and page target roles
595c209  harden browser execution protocol
42e90c7  harden production browser approval flow
e9fb952  separate platform wake from human approval
d8cd8b2  stabilize browser approval preconditions
b99f49e  defer approval resume while controller is busy
ca6bda0  defer browser execution during user control
c2bded0  filter inadmissible controller commands
```

因此 Phase 2 的真实结论不是“写链已经 Production Ready”，而是：**能力已经被证明，生命周期边界也已经被真实失败证明有问题，继续在旧模型上补丁的边际价值开始低于进入 Phase 3 重塑的价值。** 当时用户在验收里仍承担 Reload、Binding 检查、Poll 检查、Approval / Journal 回读和页面状态判断，这也说明平台内部事实还没有完全从人手里收回来。

## 七、Browser 的几条关键事故不能只剩“Driver”这个结论

当前 04 已经完整说明 Browser Extension 的多条 Lane；这里保留促成那些边界的历史证据。

Phase 2 Observation 为了“看最新内容”曾主动 scroll，造成：

```text
observe
→ viewport 被改变
→ user_reviewing / precondition 判断变化
→ 下一次 observe 再改变页面
```

于是冻结 `OBSERVE != MUTATE`：观察必须纯读，scroll / focus / click / input / submit 都属于显式 Effect（副作用：会改变页面或外部现实的动作）。

另一类事故是 Browser submit 已经完成 Delivery，却继续等待 Controller response；下游模型或 Action Permission 后来失败时，整个 Browser command 又被反向判失败。这逼出了 terminal boundary：

```text
Browser submit
→ Delivery evidence 成立
→ Browser Effect SUCCEEDED
→ END

Controller continuation
→ 独立生命周期
```

2026-08-15 的 `5278fc6` 真正删除 Universal Task Driver；Browser 之后负责 irreducible reality（不可替代的页面现实），不再拥有 workflow authority。

研发验收又补出双 Reality Plane：普通 Web 优先 Playwright，`chrome://extensions`、Toolbar、系统文件选择器等 privileged UI 使用 macOS AX / system screenshot。历史事故还证明：**visible 不等于 controllable；controllable 也不等于 durable business identity。**

## 八、自动化验收从“大 E2E”变成分层证据

Phase 2 的真实 Browser 既是验收场又是调试场，昂贵 E2E 同时承担发现、定位和最终证明。Phase 3 逐渐把便宜、确定的问题前置到 package / contract / presmoke，再把真实 Reality 拆成 Real-1 / Real-2 / Real-3。

2026-08-31 的 `c6c8a98` 与 `52bf3e3` 把 Deployment Acceptance 进一步切到“第一次使用 ProFlow 的普通用户”视角。正常路径只能走真实 Registry、Fresh Workspace、公开 CLI 和真实 Browser / Tunnel / Model / Custom GPT；工程内部入口可以诊断，不能代替用户成功。

2026-09-01 的 Harness 事故说明测试机器人自己也会制造假失败：AX helper、file picker、TTY prompt、事件已经发出但页面 mutation 尚未完成等问题，污染了最终耗时。于是形成：

```text
locate
→ mutate
→ observe visible state
→ verify
```

并明确把 `HARNESS_OVERHEAD` 与产品 happy-path time 分开。

验证成本最终分层为：

```text
source / contract / package proof
→ changed / affected targeted gate
→ FAST REPLAY / SAME SCENE
→ Real Browser / External Reality
→ FULL FRESH / Product Acceptance
```

对应历史锚点包括 `cb9dd64`、`6a1fd0f`、`a80547e`。这些 commit 名值得保留，因为它们证明 Harness 方法不是事后包装出来的口号。

## 九、Project Memory 曾经治理失败过一次

2026-08-24 的 `1d458f1` 第一次正式建立 `00-公共上下文`，目标是让新 Chat 不依赖旧模型内部状态也能接管。

随着 Deployment / Real-3 增长，handoff 自己变成负担：为了防失忆不断新增接力文档，同一规则开始被多份镜像。2026-09-03 的 `c85e986` 把公共上下文重组为长期规则、CURRENT、自动化知识和历史记录，并给知识本身建立 Owner。

但第一轮治理随后暴露“原则保留、执行记忆压缩过度”。新 Chat 能理解原则，却不知道怎样真实恢复工具、Runtime 和失败现场。于是知识迁移被要求至少包含五类信息：

```text
EXECUTION_ENTRY
= 从哪个公开命令 / helper / tool 进入

CANONICAL_ASSET
= 已验证且应复用的唯一脚本 / helper / API

AUTHORITY_SOURCE
= 当前真值去哪里机械读取

RECOVERY_PATH
= timeout / UNKNOWN / 断连后按什么顺序恢复

DO_NOT_REPEAT
= 哪些旧 transport / 临时脚本 / 昂贵步骤禁止重新探索
```

项目最后还做 Lost-context Simulation（失忆上下文模拟：不给新 Chat 旧 handoff 全文，只给正式入口和 Runbook，验证它能否恢复执行）。这个反例值得长期保留，因为它说明：**理解原则不等于拥有可执行记忆。**

### 一次人工恢复实验把“续跑”具体化为 Checkpoint

EXP-009 记录过两个真实人工恢复场景：一次是 Ruby 编码门禁连续停止后的最小修正，另一次是 35 路径冻结包在已有正确工作区上的 Continuation。它们共同验证的不是“自动 Recovery Service 已完成”，而是恢复前必须把当前执行点变成可核对的 Checkpoint（检查点：允许下一班在不重做正确工作的前提下，从已确认状态继续）。

当时稳定下来的快照信息包括：

```text
task_id / version
source_commit / remote_commit
workspace / branch
scope / delete paths
index / unstaged / untracked
completed_gates
failed_gate / raw_error
root_cause_status
approval / lease / side_effect refs
execution_point
allowed_next_change
integrity_hash
```

恢复不是“重新跑一遍”。正确顺序是先重新验证 Git SHA、输入版本、Scope、已经成立的工作和可能发生的副作用，只对已经确认的根因开放最小修改范围，再从原执行点继续。这个实验后来与 Project Memory、UNKNOWN / Reality Reconciliation 汇合成同一条长期原则：**理解历史不够，恢复必须知道当前真实状态、允许改什么，以及哪些正确结果绝不能因为一次失败被重做。**

## 十、Deployment 从中央 Planner 收缩到 Module 自治

## 十一、DDD / SDD / TDD 的证据不只是方法论名词

2026-08-15 的顺序能机械证明一次架构语义先于实现迁移：

```text
02:26  8e66b90  v2.1 architecture ruling
02:41  a33a477  全仓 Test expectation / proof inventory
04:10  32363da  Task / Agent identity + binding implementation
09:53  5278fc6  Browser universal Task Driver → Observer / Carrier
```

8 月 20 日 Deployment 重构同样先有 `0968242` 设计冻结，再有 `36c59a6` Test Plan alignment，随后 `def5628 / 6eab785 / 10a527e / 450f724` 等实现迁移。

历史材料还记录了 Change Amplification（变更放大：一个跨域语义变化同时传播到规范、测试、实现、包和证据）的量级示例：08-15 v2.1 中，`a33a477` 涉及大量 generated test inventory / matrix / proof surface；不能把它宣传成“2.8 万行手写测试”，但可以证明一次 Owner / Contract 改动会机械影响很多 proof surface。

Git 能证明 Test Plan / expectation 多次先于实现，也能证明 RED-first 被写成工程 Gate；它**不能证明每个功能都有单独的 RED commit**。这个证据边界必须保留。

## 十二、Build / Reuse / Wrap / Delete 的反例同样重要

ProFlow 不是“能买就买、不能买就造”。历史裁决更接近：

```text
成熟外部 mechanism / transport
→ REUSE

外部能力成熟，但需要 identity / lifecycle / verification / recovery
→ WRAP

对象本身就是 ProFlow 的长期 Truth / Authority
→ BUILD

自研层已经复制别的 Owner、没有独立事实
→ DELETE
```

真实 DELETE 例子包括：2026-08-28 `eaae824` 退休 `chatgpt-carrier`；中央 Deployment Planner 也被删除，而不是因为已经投入 804 行左右代码就继续保留。后续独立 devtunnel CLI wrapper 同样退出，让 CLI acquisition 回到真正 owning Module。

同样重要的是一批“刻意没有做”：没有重写通用 ChatGPT 前端，没有为了产品链更“新”就强行引入 MCP，没有把 Provider Contract 绑定 iPhone / MLXHub / Qwen，没有让 Code Interpreter 冒充本机 Execution，也没有为了统一感再包一个超级 MCP Wrapper。

这些“不做”是复杂度治理的一部分。

## 十三、发布系统最终形成五层 Truth Chain

历史发布事故证明：

```text
Source green
!= Package artifact correct
!= Registry version present
!= Fresh Workspace installed correctly
!= Runtime / Product actually adopted
```

2026-08-30 出现过典型 stale-dist：`package.json.version`、Module descriptor source 已更新，但 `dist` descriptor 仍旧，直到 Fresh install 才以 `DESCRIPTOR_INVALID` 暴露。`bafb4bb` 之后 canonical release 把 build + isolated publishability 固定到 publish 前。

Publishability（可发布性验证：真实 pack 后在隔离 consumer 中安装并调用公开入口）证明 Package Truth，不证明 Registry Truth。

Registry 对 exact `package@version` 至少分 `PRESENT / MISSING / UNKNOWN`。`pnpm publish` timeout / non-zero 时，恢复先做 exact readback；Registry 已经存在就接受 APPLIED reality，仍然未知就 STOP，不 blind republish。

真实 Deployment Acceptance 最终只认 real npm + Fresh Workspace，不用 local tarball / npm link / workspace symlink 冒充用户分发路径。

发布凭据也与 Git 授权分开：npm publish authorization 不自动推出 git push authorization。历史治理使用 granular token、短生命周期环境变量和临时 npmrc；这些属于发布安全边界，不代表构建了企业级供应链平台。

## 十四、手机模型实验真正留下的是 Capability-driven Runtime

FAST / REASON 抽象早于手机实验。手机实验的价值，是把逻辑角色丢进真实受限算力以后暴露物理约束。

历史样本中：FAST 短请求约 3～4 秒；REASON 常见数十秒，曾记录约 46 / 80 / 104 秒；长 reasoning 还出现过 `<think>` 未闭合、最终 JSON 缺失。并发实验出现过同设备延迟显著放大、跨模型 409 / `model_busy` 等问题。

这些只是 2026-08 对特定设备 / 服务 / 模型的样本，不是当前 SLA。留下的可迁移判断是：

```text
业务表达 FAST / REASON 需求
→ Runtime 吸收设备串行、优先级、切换和资源竞争
```

当时还真实尝试过 `enable_thinking`、`reasoning_effort` 等动态参数，却没有证明任意同 model ID 都能可靠切换 think / no-think。因此后续设计转向 live capability probe（在线能力探测：用受限真实请求证明当前模型实际行为），而不是根据 model ID 名称猜能力。

2026-08-26 的 `ea9bed3 / 47bc8dc` 把 Provider 边界收敛到 OpenAI-compatible URL、auth、`/v1/models` inventory 和 reachability；设备 / App / FAST-REASON mapping 不进入 Provider Contract。

2026-08-30 的 `20f0483` 又修复真实 Provider 差异：thinking 可能出现在 `<think>` 或 `reasoning_content`，structured output 可能原生支持，也可能只能 prompted。Capability Profile 最终记录“实际成功过什么”，而不是“配置声称支持什么”。

## 十五、Custom GPT 从人工配置变成外部 Deployment Resource

2026-08-20 第一代 setup 仍带有明显人工 Builder 步骤。Real-2 从 08-24 开始把远端 GPT 物化成正式部署行为。

`1d458f1` 冻结真实 Custom GPT provisioning；`3b74c3e` 暴露 reusable `createCustomGptRole`；`4c0423e` 首先把 Product role 切到公共 API，随后 Controller / Test-Ops 也进入同一路径。

最终 Role material 包含 Name、Description、Instructions、Starters、Knowledge ZIP、Model、Capabilities、Action Schema 和 role-scoped Bearer。Auth ordering 也经历真实纠偏：先尝试 post-create repair，最后收敛为 candidate credential 在 Create 前准备并写入同一个 Editor。

最重要的恢复语义是 `LIVE_CREATED`：

```text
远端 GPT 已创建
→ stable g-id / carrierUrl 已经成为现实
→ 后续 validation failure 不能 rollback 本地 identity 再重复 create
→ 保留同一 Role
→ 重做只读 validation / 原位恢复
```

Real-2 最终真实创建三个角色，历史证据记录 `ROLE_COUNT=3` 且 current Role 使用不同 g-id；同 package 显式 recreate 获得新 g-id，但 current binding 始终保持唯一。

这条历史证明的是“外部 SaaS Agent 如何进入 Deployment Contract”，不是“实现了 OpenAI 的 GPT 管理 API”。

## 十六、UNKNOWN / Reality Reconciliation 从事故变成跨领域纪律

这条语义在 Phase 2 就有前身：

```text
2026-08-06  c3ea9bf  safe recovery + uncertain reporting
2026-08-06  1a7244a  durable receipts + recovery
2026-08-07  f45e7ce  Browser lifecycle / exactly-once recovery
```

当真实 Effect 可能已经发生而调用结果丢失时，系统不再强迫异常落进 SUCCESS / FAILED 二选一。Phase 3 将副作用收敛为：

```text
APPLIED
NOT_APPLIED
UNKNOWN
```

恢复顺序是：durable intent / precondition → external or owner readback → reconciliation → 业务状态转换。不同 effect 读取不同 postcondition：文件看 hash，commit 看 HEAD，进程看 PID / listener，Browser 看 message fingerprint，publish 看 Registry exact version，Custom GPT 看 stable g-id。

这条纪律后来跨到 Agent delivery、Browser、npm publish 和 SaaS resource recovery：**A failed command is not proof that an effect did not happen.** 不能证明没发生，就没有资格安全重试。

## 十八、哪些说法仍然没有足够证据

历史完整不等于所有漂亮结论都可以讲。以下边界继续保留：

- 2026-07-27 之前更早的 Planner / Chat / DDD 起源缺少足够第一手仓库证据，不从最终架构倒推；
- 没有证据证明项目做过正式的 Custom GPT vs 自建 Chat UI vs Claude / 本地 Agent 全量 benchmark；
- 没有正式 A/B 能证明 Multi-Agent 相对 Single-Agent 的模型质量提升；
- 没有稳定对照实验可以量化 ProFlow 把研发效率提高了多少倍、降低了多少成本；
- 手机模型历史性能、热稳定和经济性受设备、模型、Serving 版本影响，只能作为对应时间点实验事实；
- 历史 `/tasks` dirty migration 不能冒充当前 Product Surface 真值；
- Real-1 / Real-2 / Real-3 或 Deployment PASS 不能自动推出后续 Phase 4 / Monitor 新能力已经通过；
- 当前个人项目的发布、验收与恢复实践不能夸大成生产级 SLA、企业级供应链或通用分布式 exactly-once 平台。
