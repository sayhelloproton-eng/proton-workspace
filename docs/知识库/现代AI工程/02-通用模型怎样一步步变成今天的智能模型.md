# 通用模型怎样一步步变成今天的智能模型

Transformer 提供了可规模化的语言建模底座，但“会预测下一个 Token”距离今天可以对话、写代码、遵循指令、调用工具、进行复杂推理的模型还很远。中间发生的不是一次神奇升级，而是几层不同问题被依次解决：**表示方式、规模化预训练、任务适应、指令对齐、偏好优化，以及把更多计算放到推理时。**

把这些阶段分清非常重要。否则遇到模型问题时，很容易把所有提升都归到“再训练一下”或“换更大的模型”。

## BERT 和 GPT 先证明了两条不同的 Transformer 路线

BERT 主要使用 Transformer Encoder，通过 Masked Language Modeling 学习双向上下文表示。它的优势在于：整段输入都已知时，可以同时利用左右两边信息，特别适合分类、检索表示、实体识别等理解型任务。

GPT 采用 Decoder-only + Causal Mask，只根据左侧已有 Token 预测下一个 Token。这看起来更受限，却和开放式生成天然一致：训练时做什么，推理时也做什么。

于是两条路线逐渐形成不同位置：

~~~text
Encoder-oriented
→ 强表示 / 理解 / Embedding / 分类

Decoder-only autoregressive
→ 生成 / 对话 / 代码 / 通用任务接口
~~~

后来的大语言模型主线没有证明 Encoder “没用”，而是证明 Decoder-only 的生成接口更容易统一大量不同任务。Encoder 路线仍然广泛存在于 Embedding、Reranker、分类和其他表示型模型中。

## 预训练把“一个任务一个模型”变成“一个底座，多种能力”

Pre-training（预训练：在大规模通用数据上先学习语言和世界模式）让模型不必从零针对每个任务训练。大量文本和代码本身就构成监督信号：给定前文，预测后续。

随着参数、数据和计算规模增大，模型逐渐获得语言、代码、常识、模式识别和一定推理能力。Foundation Model（基础模型）由此出现：先训练一个通用底座，再通过上下文或后训练适配很多下游任务。

Foundation Model 和 Base Model 也不是完全同义。Foundation Model 强调“可以支撑很多下游任务的通用底座”这一系统角色；Base Model 更常指某个模型家族中尚未经过特定指令/偏好后训练的基础权重状态。

这改变了应用工程：以前常常是“为任务训练模型”；后来越来越多问题变成“怎样把通用模型放进正确 Context 和系统边界里”。

## Scaling Law 说明能力增长可以被系统性投资，但不是无限魔法

Scaling Law（缩放规律：模型损失或能力随参数、数据和计算规模变化呈现可预测趋势）让行业看到，大规模训练投入不是完全靠运气。扩大模型、数据和计算，通常能稳定改善平均建模能力。

但 Scaling 并不意味着：

~~~text
参数更多
= 所有任务都更好
= 当前事实更准确
= 更安全
= 更便宜
= 更适合所有延迟要求
~~~

更大的模型会增加训练、Serving、延迟和成本，数据质量和训练配比也会成为瓶颈。Scaling 还存在 Diminishing Returns（边际收益递减）：继续增加参数、Token 和计算仍可能改善能力，但每增加一份资源不保证得到等比例业务收益。

系统最终还需要 Routing，让不同任务使用刚好够用的模型和推理预算。

## 真正的 Scaling 不是只加参数，还要同时安排数据和计算

参数量只是训练规模的一根轴。一个模型如果参数继续增大，但训练数据不足、重复过多、质量很差，或者总计算预算跟不上，新增参数并不会自动变成同等比例的有效能力。

工程上更应该把训练理解成三个变量的联合分配：

~~~text
model capacity
+ training data
+ compute budget
→ achievable training quality
~~~

Compute-optimal Training（计算最优训练：在固定训练计算预算下合理分配模型规模和训练 Token）提醒我们，训练计划不能只追求“参数越大越好”。数据清洗、去重、混合比例、代码/语言覆盖和难样本质量，都会改变最终能力。

这也解释了为什么同样参数量的模型表现可能差很多：参数只是容量，训练语料和优化过程决定这些容量最终学到了什么。

## MoE 把总参数容量和每次推理计算进一步分开

MoE（Mixture of Experts，专家混合架构：每个 Token 只激活部分专家子网络）提供了另一种扩大模型容量的方式。

它希望获得这样的工程效果：

~~~text
更大的总参数容量
↓
每个 Token 只激活部分参数
↓
单次计算不必与总参数量线性增长
~~~

但 MoE 不是“免费大模型”。Router（路由器：决定当前 Token 进入哪些专家）会增加训练稳定性、负载均衡、通信和部署复杂度。分布式 Serving 里还会遇到专家分片、跨设备通信和热点专家问题。

因此看到“总参数很大、激活参数较小”的模型时，要先区分**总容量**和**每 Token 实际参与计算的参数**，不能直接拿总参数量推断单次推理成本。

## MoE Router、Serving Load Balancer 和应用 Model Router 不是同一个 Router

“Router”这个词在 AI 系统里至少会出现在三层。

~~~text
MoE Router
→ 在一个模型内部，为当前 Token 选择 Expert

Serving Load Balancer
→ 在多个服务实例 / GPU Worker 之间分配请求

Application Model Router
→ 根据 Task、风险、成本等选择哪个模型 / Profile
~~~

MoE Router 是模型架构的一部分，通常发生在一次前向计算内部；Serving Load Balancer 解决基础设施负载；应用 Model Router 则属于 Runtime / Gateway 的策略选择。

同样，应用层维护一组小模型并按任务路由，也不等于 MoE。前者是多个独立模型能力的系统编排，后者是单个模型内部的专家稀疏激活。

## In-context Learning 把 Prompt 变成临时任务接口

当模型规模达到一定程度以后，人们发现模型可以通过 Prompt 中的自然语言说明和少量示例临时适应任务，而不需要更新权重。这通常称为 In-context Learning（上下文学习，ICL）。

Zero-shot、One-shot、Few-shot 描述的是当前 Prompt 中示例数量，不是三种训练算法：

~~~text
Zero-shot
→ 只给任务说明，不给示例

One-shot
→ 给一个示例

Few-shot
→ 给少量示例
~~~

例如：

~~~text
给出三个“用户句子 → 意图标签”样例
→ 模型在同一次 Context 中理解模式
→ 对第四个句子继续分类
~~~

这些示例只改变当前 Context，不修改模型参数。这也是 ICL 和 Fine-tuning 最根本的边界之一。

但 ICL 有两个天然限制：规则只活在当前 Context；模型仍然可能忽略、误解或在长 Context 里遗忘约束。因此 Prompt 很重要，却不应该承担长期状态和硬安全边界。

## SFT 让模型从“会续写”转向“会按指令回答”

SFT（Supervised Fine-Tuning，监督微调）使用高质量的指令—回答样本继续训练模型，让它更熟悉“用户提出任务，助手完成任务”的交互形式。

它适合教模型：

- 怎样回答不同类型指令；
- 怎样保持特定结构；
- 怎样使用角色和对话格式；
- 怎样在常见任务上表现得更像助手。

SFT 改变的是行为分布，而不是自动注入实时知识。价格、库存、当前 Git 状态等变化事实仍然更适合 RAG、数据库和 Tool。

## Instruction Dataset、SFT、Instruction Tuning 不是三个同义词

Instruction Dataset（指令数据集）是训练材料：通常包含指令、输入、回答或多轮消息。

SFT 是训练过程：使用监督目标继续更新模型参数。对生成式模型来说，它在技术上仍然是在做 next-token prediction，只是训练数据已经从大规模通用语料变成了更明确的“任务—高质量回答”分布。

Instruction Tuning（指令调优）则是更偏目标和方法族的说法：希望模型经过一组多任务指令数据后，整体更会理解和执行自然语言任务。它常通过 SFT 实现，但不能把“有一份指令数据”“运行了 SFT”“最终获得了稳定指令遵循”当成同一件事。

因此：

~~~text
Instruction Dataset
= data

SFT
= optimization procedure

Instruction Tuning
= desired general behavior / training approach
~~~

高质量、覆盖足够且边界清楚的指令数据，往往比单纯扩大样本数量更重要。

## Preference Optimization 处理“多个可行回答里哪个更符合目标”

只靠 SFT，模型会模仿训练答案，但很难直接表达“这两个回答都能说通，我更希望哪个”。因此出现了基于偏好的后训练路线。

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）先从人类偏好学习 Reward Model，再用强化学习优化模型行为。DPO（Direct Preference Optimization，直接偏好优化）等方法则用成对偏好数据更直接地调整策略。

不同训练阶段解决的不是同一个问题：

~~~text
Pre-training
→ 学语言和世界模式

SFT
→ 学怎样完成指令

Preference Optimization
→ 学哪些行为和回答更符合偏好 / 安全 / 产品目标
~~~

## Alignment 不是一个算法，模型“是什么版本”也不是一条轴

Alignment（对齐）更适合理解为一组目标：让模型行为更符合人类意图、产品规范和安全约束。SFT、RLHF、DPO、规则数据、可验证奖励等都可能参与其中，所以不能把 Alignment 直接等同于某一个具体训练算法。

模型名字也经常混合两类不同维度。

一类是行为阶段：

~~~text
Base
→ 通用预训练底座

Instruct
→ 更强调指令遵循

Chat
→ 进一步适配对话协议和产品交互
~~~

另一类是能力域：

~~~text
Code
Math
Vision
Multimodal
Embedding
...
~~~

一个模型可以同时是 Instruct + Code，也可以是 Chat + Vision。这些标签不能被画成一条单向升级链。

## 多模态扩大的是 Observation Surface，不是 Truth Ownership

Multimodal Model（多模态模型：能够联合处理文本、图像、音频等不同模态输入或输出的模型）把模型能读取的世界从纯文本扩展到了截图、图表、照片、语音和界面状态。

对 Agent 工程来说，这个变化很重要。过去很多环境事实必须先被转换成文本；有了视觉和多模态能力以后，模型可以直接把页面截图、设计稿、图表或相机画面当成 Observation（观察：模型当前拿到的环境信息）的一部分。

但“看见”仍然不等于“系统已经知道”。

~~~text
screenshot / image / audio
→ model observation candidate
→ 与 DOM / API / Source / Runtime readback 交叉核对
→ Evidence
→ 才可能进入 Current Truth
~~~

例如模型从截图判断“按钮已经禁用”，这是有价值的视觉判断；如果页面同时存在可读取 DOM 属性，就应该优先或同时用结构化事实验证。模型从图表读出一个数字，也不自动替代产生这张图的原始数据源。

因此多模态真正新增的是**感知表面**，不是新的业务 Authority：

~~~text
more modalities
→ richer observation

richer observation
≠ stronger permission
≠ authoritative state
≠ effect already happened
~~~

这条边界后来直接影响 Browser Agent、Computer Use、视觉验收和多模态 Artifact 处理：模型可以帮助理解复杂界面，但 Permission、Readback、Evidence 和最终 Truth 仍然属于模型外的软件系统。

## Chat 产品不只是模型，它还增加应用层协议和控制

当 Foundation Model 进入 Chat 产品以后，用户看到的是一个更大的系统：System / Developer / User / Assistant / Tool 等 Role（角色：消息在对话协议中的来源和控制位置）、Conversation History、文件、工具、产品策略、流式输出、Memory 等都在模型外组织。

Prompt Template（提示模板）和 Chat Template（对话模板）也不是一个东西。前者是应用怎样组织任务文本；后者通常还负责把结构化 Role / Message 转换成模型训练时熟悉的 Token 序列格式。

因此至少要分开：

~~~text
Model Behavior
→ 权重经过训练形成的行为倾向

Current Instruction
→ 这一次 Context 里希望模型遵循的任务和约束

Runtime Permission
→ 软件真正允许发生的动作
~~~

模型经过 Alignment 更愿意拒绝危险请求，不代表它就拥有真实 Permission；反过来，Runtime 允许某项 Tool，也不意味着模型一定会正确选择它。

所以“Chat Assistant 很会对话”不能完全归因于基础模型权重。产品 Harness 怎样构造 Context、组织 Role、提供工具、过滤能力，也会显著改变最终体验。

## Reasoning Model 把更多预算放到推理时

传统模型一次生成会按照固定服务策略完成推理。Reasoning Model（推理模型：在复杂任务上允许投入更多推理时计算的模型或服务形态）则让系统可以根据任务难度增加 Inference-time Compute（推理时计算，也常称 Test-time Compute）。

工程上可以把它理解成：

~~~text
简单任务
→ 少量推理预算，快速回答

复杂任务
→ 更多内部推理 / 搜索 / 自检预算
→ 更高延迟和成本
~~~

这带来一个关键变化：**模型能力不再只由“是哪一个模型”决定，还取决于这一次调用愿意投入多少计算。**

因此系统开始需要 Reasoning Routing：FAST 路径处理高频、低风险、可验证任务；REASON 路径只给冲突、复杂规划和高风险判断。后面的 Runtime/Routing 章节会继续展开。

## Reasoning、可见 Chain of Thought、Agent Loop 和 Temperature 不是同一件事

Reasoning 表示模型在复杂问题上投入更强的求解过程或更多推理时计算；产品是否把内部推理文本展示给用户，则是另一层交互和安全选择。

因此：

~~~text
Reasoning capability
≠ disclosed Chain of Thought

Reasoning Model
≠ Agent Loop
~~~

一个模型可以在单次 Invocation 中进行更复杂推理，却没有任何 Tool、Observation 或长期 Task；Agent Loop 则强调根据外部 Observation 多轮选择和行动。

Temperature 更不是 Reasoning Effort。Temperature 调的是 next-token sampling 分布；Reasoning Effort / Budget 决定这次求解愿意投入多少推理计算。

模型选择和推理预算也应看成两个轴：

~~~text
which model?
×
how much reasoning budget?
→ one invocation profile
~~~

同一个模型可以有快/慢不同推理 Profile；两个不同模型也可能被分配相近预算。把它们拆开以后，Runtime 才能真正按 Task 难度、风险、延迟和成本路由。

## 推理时计算并不等于“把答案想得越久越好”

Inference-time Compute 可以通过不同方式消耗：更长的内部推理、生成多个候选、搜索不同路径、让 Verifier（验证器：对候选结果进行额外检查或打分的组件）筛选，或者对关键步骤重新计算。

这意味着“推理预算”不是一个单纯的 Token 开关，而是一种系统资源：

~~~text
task difficulty
+ risk
+ latency budget
+ cost budget
+ validation availability
→ reasoning strategy
~~~

开放任务里更多计算可能提高质量，但也会增加延迟、费用和错误路径数量。能够用确定性 Test、Schema 或外部事实快速裁决的问题，不一定值得让模型多轮自我反思。

## 更会推理仍然不能替代外部事实和工具

一个常见误区是：模型推理能力增强以后，RAG、Tool 或 Workflow 就不重要了。实际上推理越强，越应该把它用在真正需要判断的地方。

以下工作仍然应该交给外部系统：

| 问题 | 正确 Owner 倾向 |
|---|---|
| 当前库存是多少 | Database / Tool |
| 最新规范是什么 | Retrieval / authoritative source |
| 这个用户有没有权限 | Auth / Policy |
| 文件是否真的写成功 | Filesystem readback |
| 测试是否通过 | Test runner |
| 任务当前状态 | Runtime State |
| 高风险动作是否批准 | Approval store |

Reasoning Model 可以解释这些事实和综合冲突，但不能因为“想得更久”就成为事实 Owner。

## Fine-tuning、RAG 和 Prompt 的选择，本质是先识别缺口

“领域知识应该微调还是 RAG”不能只从技术偏好出发，应该先拆清楚系统缺的究竟是什么。

Prompt / Few-shot 适合低成本地改变当前任务表达；RAG 适合动态、可引用、会变化的外部知识；Fine-tuning 更适合稳定行为模式、领域语言、输出风格或有限决策边界。

| 缺口 | 优先手段 |
|---|---|
| 指令没说清 | Prompt / Few-shot |
| 最新事实缺失 | RAG / Tool |
| 输出结构不稳 | Structured Output / Validator，再评估 SFT |
| 领域表达长期理解差 | SFT / LoRA / continued pre-training 候选 |
| 复杂推理不足 | 更强模型 / 更高 reasoning budget |
| 权限或安全越界 | Runtime Policy，不是训练 |

不要用权重去记本来应该由数据库拥有的实时事实，也不要用 Prompt 去替代程序可以强制的规则。

## 模型能力越来越像一种可路由计算资源

经历这些演进以后，“模型”在工程系统里的位置发生了变化。

早期常把一个模型直接等同于整个 AI 应用；现代系统更常把它当成可替换计算节点：

~~~text
Task
→ choose model / profile / reasoning budget
→ Model Invocation
→ structured result
→ Validator / Runtime
→ continue
~~~

同一个产品可以同时使用 Embedding Model、Small Model、Cloud FAST、Cloud REASON、Vision Model；它们不需要各自变成 Agent。Model 是计算能力，Agent 是围绕目标持续承担判断责任的主体，这两层不能混。

## 模型选型最终应该回到任务切片，而不是榜单总分

一个模型在公开 Benchmark 上更强，不代表它在当前产品里一定更好。真实系统更关心自己的 Task Slice（任务切片：具有相似输入、风险和成功标准的一组任务）。

例如：

~~~text
短文本分类
→ 看准确率、延迟、吞吐、成本

长文档问答
→ 看长上下文质量、检索协作、引用

复杂代码修改
→ 看 Tool 使用、长任务恢复、测试通过率

高风险决策
→ 看关键错误、校准、拒绝/升级能力
~~~

所以“模型 A 比模型 B 强”通常是一个缺少任务边界的句子。系统真正需要的是：**在指定任务、硬件、预算和验证条件下，哪个模型路径的 Cost per Successful Outcome 更好。**

## 把模型演进的边界收束起来

BERT 与 GPT 的差异不只在 Encoder / Decoder，而在训练目标和产品接口：Decoder-only 的 next-token 目标和开放生成一致，因此更容易成为通用生成入口；Encoder 路线则继续在表示、匹配和检索中发挥价值。

Scaling 也不能简化成“参数越多越好”。参数、数据和训练计算需要匹配，MoE 还会进一步把总容量和每次实际激活计算分开；MoE 内部 Router、Serving Load Balancer 和应用 Model Router 分属不同责任层。

SFT、RLHF / DPO 等后训练主要塑造指令遵循和偏好行为，不应该被当成实时知识数据库；Base / Instruct / Chat 描述的是行为阶段，Code / Math / Vision 描述的是能力域，也不能混成一条升级链。

Reasoning Model 的关键变化则是推理时计算成为新的系统预算；Reasoning、可见 Chain of Thought、Agent Loop 和 Temperature 各自属于不同层次，需要在质量、成本和延迟之间动态分配。

到这里，模型已经从专项算法演进成可路由的通用智能计算资源，但仍有一个明显缺口：**它知道的世界主要来自参数和当前 Context。下一篇开始进入模型外部知识。**
