# AI 能力怎样最终变成产品和平台

技术团队最容易倒着做 AI 产品：先列 RAG、MCP、Agent、Memory、Multi-Agent、Router，再想这些组件可以拼成什么产品。真正能长期工作的系统通常走相反方向：**先定义用户/业务最终需要的 Outcome，再倒推最小的模型、知识、流程、能力、Runtime 和验证组合。**

平台化也一样。不是组件够多就叫 Platform，而是多个真实产品反复承担同一工程责任，复制实现已经更贵、更危险，共享边界才开始成立。

## 从 Business Outcome 倒推，而不是从 Agent 名词正推

Business Outcome（业务结果）是用户或组织真正能观察和验收的价值。

例如报销产品的 Outcome 不是“模型生成了一段解释”，而可能是：

~~~text
提交材料被正确理解
→ 规则和证据被正确检查
→ 必要审批完成
→ 报销状态真实更新
→ 用户能看到可追踪结果
~~~

模型输出、Tool Success、Artifact 都只是中间对象。

因此设计顺序应是：

~~~text
Business Goal
→ Success Criteria / Failure Cost
→ User Interaction
→ Domain Context / Truth
→ deterministic workflow vs model decision
→ authorized capability
→ real effect
→ domain validation
→ Outcome
~~~

## AI Feature、AI App、Agent App、Runtime、Platform 是不同责任层

| 形态 | 核心特征 |
|---|---|
| AI Feature | 产品里的一个局部模型能力，生命周期可以很短 |
| AI Application | 模型、Context、交互、流程和能力组合成用户价值 |
| Agent Application | 路径需要模型根据 Observation 动态选择，并能行动 |
| Agent Runtime | Task/State/Event/Recovery/Evidence 的长期执行层 |
| AI Platform | 多个真实应用共享稳定 AI 工程责任 |

调用 Agent SDK 不会自动把页面升级成 Agent Application；没有聊天 UI 的后台系统也可能拥有真正 Runtime。

看责任，不看框架标签。

## Domain Context 决定垂直产品真正懂什么

Vertical Agent（垂直智能体）不是“行业 Prompt + 通用模型”。它需要把领域对象、规则、当前 State、历史事件、权限和权威数据真正装进系统。

Domain Context（领域上下文）可能来自：

- Object Model；
- Database；
- Policy；
- Knowledge Source；
- current case / task state；
- user / organization permission；
- historical events；
- Evidence。

这些事实按 Task 装配，而不是全部塞进一个永久 System Prompt。

## Business Workflow 仍然应该拥有确定性业务规则

很多行业流程原本就有审批、状态机、合规规则和数据库事务。

AI 不应该因为进入系统就重写这些硬规则。

一个很好用的分工是：

~~~text
hard rule / compliance
→ code / workflow / policy

ambiguous classification
→ model

open exploration
→ agent

high-risk effect
→ approval + validation
~~~

概率模型只承担真正需要语义判断的部分。

## Domain Capability 应表达业务动作，不是裸 CRUD

对模型暴露 update_row(table, where, values) 权限过大、语义过弱。

更好的 Capability 可以是：

~~~text
create_refund_proposal
approve_refund
lookup_customer_case
publish_reviewed_article
~~~

业务语义让 Permission、Effect、Idempotency 和 Evidence 更容易被准确治理。

底层 CRUD 仍然可以存在，只是不应直接成为模型自由使用的业务接口。

## Human on the Loop 比“每一步都人工审批”更成熟

Human-in-the-loop 表示流程必须在某些节点等待人工。

Human on the Loop（人在环上监督）则让系统默认自动运行，人主要处理高风险、低置信、异常和最终责任判断。

要实现后者，系统必须有更强 Observability、Pause、Rollback、Evidence 和 Exception Routing。

成熟产品不是无人化竞赛，而是把人的注意力放到最有价值的位置。

## Feedback Loop 必须回到真实 Outcome

只收集 thumbs up/down 很难指导架构。

更有价值的 Feedback Loop 连接：

~~~text
real outcome
+ failure slice
+ user correction
+ human repair
+ latency / cost
→ Eval
→ routing / workflow / prompt / model / product change
~~~

这样系统才能知道问题属于 Model、Retrieval、Tool、Runtime 还是产品流程。

## AI Platform 真正共享的不是“所有 AI 东西”

多个产品反复需要的共享责任大致可以画成：

~~~text
Interaction / Product
        ↓
Agent / Workflow
        ↓
Harness + Runtime
        ↓
Knowledge + Capability
        ↓
Model Gateway / Providers
        ↓
Infrastructure

Governance / Observability / Eval
横切所有层
~~~

平台核心是 Responsibility Boundary，而不是组件数量。

## Model Layer：统一计算入口，不拥有业务 Task

共享 Model Intelligence Layer 可以负责：

- Provider Adapter；
- model catalog；
- routing；
- reasoning budget；
- quota；
- usage；
- health；
- fallback；
- cost telemetry。

它回答“把什么模型计算分给谁”，不应该直接修改业务 Task State。

## Knowledge Layer：共享知识基础设施，但不抢 Source of Truth

平台可以共享：

- source ingestion；
- parsing；
- indexing；
- retrieval；
- rerank；
- provenance；
- permission filter。

但 Git、业务数据库、正式文档等原始 Truth 仍然属于对应系统。

向量库是派生基础设施，不应该成为全局权威事实。

## Capability Layer：共享稳定动作合同

Capability Layer 可以统一 Tool Contract、Registry、Discovery、Connector/MCP、Permission metadata 和 Result/Evidence 结构。

它回答“系统能做什么”，不负责决定某个业务什么时候必须做。

业务 Workflow 仍然由产品拥有。

## Harness / Runtime：平台共享的是基础原语，不是所有 Agent Prompt

平台可以提供 Context Assembly、Tool Surface、Workspace/Sandbox、Validator、Task、Event、Scheduler、Checkpoint、Recovery 等基础设施。

但每个产品仍应拥有自己的 Goal、领域规则、Success Criteria 和最终 Outcome。

如果 Platform 团队开始定义所有 Vertical Workflow，边界通常已经过度集中。

## Governance / Eval 必须横切，而不是最后补日志

Identity、Permission、Policy、Audit、Evidence、Tracing、Eval、Cost 都应该和真实 Action 同步进入系统。

治理如果只在事故后查日志，就无法在危险 Effect 前阻止越权。

Eval 如果只在模型升级时跑一次，也无法持续判断 Routing、Workflow 和 Platform 是否退化。

## Infrastructure 仍然是传统软件工程

AI 系统没有取消：

- Service；
- Database；
- Queue；
- Cache；
- Network；
- Deployment；
- Secret；
- Monitoring；
- Capacity；
- SLO。

概率模型只是增加了新的不确定性、Context 和 Eval 责任。

“会 Agent”不能替代后端、分布式和生产工程。

## Control Plane 和 Data Plane 在平台里要继续分开

Control Plane 管 Identity、Config、Policy、Registry、Task metadata、Routing 和 Governance。

Data Plane 执行 Model Invocation、Tool Effect、Browser/Coding Action 和真实数据流。

二者可以共部署，但不要让 Data Plane 中的自然语言结果反向获得 Control 权限。

## Provider Adapter 的目标是吸收差异，不是假装差异不存在

不同 Model、Search、Browser、Runtime Provider 会有不同字段、错误、能力和限制。

Adapter（适配器）应该把私有表面映射到平台稳定合同，但不能为了“统一”抹掉真正语义差异。

例如一个 Provider 不支持 Tool Calling，就不能只通过字段转换伪装成完全支持；应该由 Capability/Eval 明确暴露限制。

## Multi-tenancy 让共享平台真正进入企业级责任

多个团队/客户共享基础设施以后，Platform 需要额外承担：

- Tenant identity；
- data isolation；
- model/tool allowlist；
- quota；
- cost attribution；
- audit；
- incident containment。

一个单机 Demo 即使组件很多，也还没有这些共享治理责任。

## 什么时候真的出现 Platformization 信号

Platformization（平台化）应该由已经出现的重复问题触发，例如：

- 第二、第三个真实产品重复实现同类 Gateway/Runtime/Eval/Permission；
- 重复实现已经导致安全边界不一致；
- Provider 变化需要统一适配；
- 成本/配额/审计需要组织级治理；
- 共享责任已经有稳定 Contract；
- 共享能力有明确 Owner 和 Lifecycle。

产品数量不是硬门槛，只是提醒重新评估。

## 什么时候不要平台化

- 只有一个产品；
- 所谓共性只存在于 PPT；
- 不同业务差异远大于共性；
- Platform API 变化比产品需求更快；
- 业务还没有 Outcome/Eval；
- 普通 Library 已经能消除重复；
- 共享层会拖慢产品验证。

“以后可能需要”不是当前复用证据。

## 抽象应该逐级购买

更健康的路径是：

~~~text
copy with learning
→ shared convention
→ library / schema
→ shared service
→ control plane / platform
~~~

Library 只承担代码复用，不需要网络可用性和多租户；Shared Service 开始承担版本、容量和 SLO；Platform 才进一步拥有组织级治理和公共控制面。

不要一步跳到最重形态。

## Evidence Ladder 防止“代码写完”冒充平台价值

平台能力也应该按证据层级判断：

~~~text
idea
< design
< implemented candidate
< tests
< integrated environment
< real external effect
< repeated production outcome
~~~

一个 Registry 能启动，不证明产品愿意使用；一组单测全绿，不证明跨产品整合已经降低 Lead Time。

## Baseline 和 Counterfactual 是平台化最容易缺的一步

平台化前要问：

> 如果不抽这层，继续让产品自己拥有，会怎样？

这就是 Counterfactual（反事实）。

需要比较：

~~~text
shared service vs product-owned library
multi-agent vs bounded subagent
agent vs workflow
router vs fixed model
hybrid retrieval vs simple search
~~~

没有基线，复杂方案只能证明“可行”，不能证明“更值得”。

## ADR 应该记录退出条件，不只是“为什么选”

Architecture Decision Record（架构决策记录）至少保留：

- trigger problem；
- current baseline；
- options；
- chosen responsibility；
- evidence；
- risks；
- validation metrics；
- rollback / exit condition；
- future trigger to reopen decision。

平台能力必须允许未来降级或被外部成熟方案替代。

## Current 和 Target 必须分开写

Roadmap 里的 Agent Registry、Multi-Agent、Cloud Runtime 不能因为设计已接受就写成当前 READY。

正式文档必须区分：

~~~text
Current verified
Partially implemented
Accepted design
Future candidate
Superseded / retired
~~~

否则学习者和维护者会从文档获得错误现实。

## Architecture Fitness Function 让关键边界持续被检查

共享层建立以后，可以把关键架构约束变成持续 Gate，例如：

- Schema compatibility；
- dependency direction；
- Permission invariants；
- Evidence completeness；
- latency / cost budget；
- tenant isolation。

Architecture Fitness Function（架构适应度函数）不等于单元测试，而是持续检查“这套架构为什么仍然成立”的关键约束。

## Coding Agent 为什么是 Agent Workspace 演进的现实样本

Coding 产品过去几年形成一条很清楚的趋势：

~~~text
Completion
→ Chat / Copilot
→ Coding Agent
→ Task + isolated workspace
→ background / long-running work
→ Agent Workspace
~~~

当工作中心从“当前光标”变成 Task，人开始一次委派多个长期工作，Runtime、Workspace、Review、Evidence 和 Recovery 的价值自然上升。

稳定趋势值得保留，具体 2026 产品差异和 Claude Code / Codex / OpenCode / Cursor 等路线由 [Coding Agent 真正竞争的是什么](../Coding-Agent.md) 专门维护，避免在主教材里重复一份易过期排行榜。

## 生态里越接近 Runtime，越难完全标准化

Skill / MCP 这类内容和协议边界更容易成为 Portable Core；Hook、Permission、Sandbox、Lifecycle、Recovery 与具体 Runtime 紧密相关。

所以跨平台兼容通常分三层：

~~~text
syntax compatibility
→ 文件能读

structural compatibility
→ 对象能映射

semantic compatibility
→ lifecycle / permission / recovery 行为真的等价
~~~

能安装不等于行为完全一致。

开放标准更适合先收敛稳定边缘，而不是为了“统一”抹平 Runtime 的真实差异。

## 一个真正有价值的平台应该让上层更简单

最终判断不看组件数量，而看：

~~~text
产品 Lead Time 是否下降？
安全边界是否更一致？
重复实现是否减少？
Cost per Success 是否改善？
Recovery 是否更可靠？
真实 Adoption 是否成立？
Escape Hatch 是否持续增加？
共享故障 Blast Radius 是否可控？
~~~

如果平台建立以后，上层每个产品反而要理解更多内部细节、升级更慢、绕过路径越来越多，那么这层抽象可能没有偿还自己的运营税。

## 平台化真正成立的判断

AI Platform 不应该由组件数量定义，也不应该成为产品自然演进的默认终点。

真正成立的条件是：多个真实应用反复遇到相同的 Model Gateway、Knowledge / Capability、Runtime、Identity / Policy、Eval 等责任；这些责任的合同已经稳定；继续让每个产品重复实现，成本、风险和不一致开始显著高于共享层本身的运营税。

因此平台化更适合沿下面的路径逐级发生：

~~~text
product-owned implementation
→ shared convention
→ library / schema
→ shared service
→ platform / control plane
~~~

是否继续上升，要用 Baseline、Adoption、Lead Time、Cost per Success、Recovery 和 Incident Blast Radius 证明；如果共享层不能让上层更简单，就应该允许它降级、拆回 Library，或被更成熟的外部能力替代。

完整的复杂度升降判断可继续读 [Agent 工程复杂度与边界](../Agent工程复杂度与边界.md)。
