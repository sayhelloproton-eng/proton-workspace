# 模型为什么必须使用外部知识

一个模型可以在训练数据里学到大量知识，却无法保证知道“此时此刻”的项目状态、企业数据、最新政策或私人文档。把模型换得更大，最多改善通用知识和推理能力，不能消除这个时间、权限和来源边界。

因此现代 AI 系统必须把两种世界分开：**模型参数里压缩过的通用模式**，以及**由外部系统持续拥有、可以重新读取和验证的知识与事实**。RAG 解决的正是第二个世界怎样进入本轮推理。

## 参数知识为什么永远不够

模型参数中的知识至少有四个限制。

第一是 Freshness（新鲜度）。训练完成以后，世界还会继续变化。

第二是 Private Knowledge（私有知识）。公司文档、用户文件、本地源码本来就不应该全部进入公共模型训练。

第三是 Provenance（来源链）。即使模型给出正确答案，也很难仅凭权重回答“这条结论来自哪份规范、哪个版本、哪一行”。

第四是 Authority（权威性）。模型学过十篇网页，不代表它知道当前系统真正应该相信哪一个 Source of Truth。

所以模型系统必须有外部知识层。

## RAG 不是“接一个向量数据库”

RAG（Retrieval-Augmented Generation，检索增强生成）的最小链路是：

~~~text
Knowledge Source
→ parse / chunk / index
→ Query
→ retrieve candidates
→ rerank / filter
→ Context Assembly
→ Model
→ Answer + Citation
~~~

每一段都解决不同问题。向量数据库只处在“索引与候选召回”的一部分。

真正成熟的 RAG 要回答：原始知识从哪里来、当前版本是什么、怎样切分、哪种检索器适合这类问题、候选如何排序、冲突来源怎样处理、最终送进模型的证据是否足够，以及回答能不能回到原始 Source。

## Knowledge Source 和 Index 必须分开

Git、数据库、正式文档、对象存储里的文件可以是 Knowledge Source（知识源：对内容本体或当前事实拥有权威性的原始系统）。Embedding Index、全文索引、向量库通常只是为了检索效率生成的派生结构。

因此：

~~~text
Source changes
→ Index should refresh

Index says X
≠ Source currently must be X
~~~

如果索引过期，不能让“检索到了旧 Chunk”覆盖 Git HEAD 或数据库当前记录。

这和后面的 State/Memory 纪律一致：派生表示不能反向成为原始真值。

## Index Freshness 必须是可观测状态

索引系统如果没有记录 Source Version、Indexed Version 和更新时间，就很难回答“这次检索到底基于哪个版本”。

一个更可靠的索引元数据至少能回答：

~~~text
source_id
source_version
indexed_version
indexed_at
parser_version
embedding_model_version
permission_scope
~~~

增量索引也不能只处理新增内容，还要处理删除、重命名、权限变化和旧 Chunk 失效。否则知识源已经删除一段敏感内容，向量库里却仍然可以召回。

所以索引不仅是性能设施，也有自己的 Freshness 和 Lifecycle。

## Chunking 决定检索系统以什么粒度理解资料

Chunking（分块：把长资料切成可检索单元）会直接影响召回质量。

切得太小，上下文容易断裂；切得太大，每个候选噪声很多，Embedding 也可能把多个主题压进一个向量。

合适的 Chunk 不一定按固定字符数切。代码可以按函数、类、模块；规范可以按章节；结构化文档可以保留标题路径；对话可以按语义轮次。

更重要的是保留 Metadata：Source、Version、Section、Timestamp、Permission 等，让候选被找回来以后仍然知道自己来自哪里。

## Retrieval Embedding 和 Token Embedding 不在同一层

前面的 Transformer 章节已经出现过 Token Embedding：它是模型把某个 Token ID 映射成内部向量表示的一部分，用于一次前向计算。

Retrieval Embedding（检索嵌入）解决的是另一个问题：把 Query 和文档 Chunk 映射到适合语义检索的向量空间，使系统可以比较它们在“检索意义上是否接近”。

~~~text
Token Embedding
→ 模型内部计算表示

Retrieval Embedding
→ 检索系统的文档 / Query 表示
~~~

两者都叫 Embedding，不代表它们由同一个模型产生，也不代表可以互换。

## Vector 是表示，Similarity 才是比较结果

Embedding Model（嵌入模型：把 Query 和文档片段映射到同一向量空间）产生的是 Vector（向量表示）。检索系统还要使用 Cosine Similarity、Dot Product 或其他距离/相似度函数，才能得到两个向量“有多接近”的比较结果。

因此：

~~~text
Vector
≠ Similarity score
≠ Truth score
~~~

Vector 是表示；Similarity 是在某个度量下的比较；二者都不能自动告诉系统某条资料是否新鲜、权威或有权限。

Vector Retrieval（向量检索）特别适合：

- 用户用另一种说法描述同一概念；
- 长文档中存在语义相近内容；
- 查询不包含精确符号。

但一个语义很像的旧版本文档可能比当前规范更相似，因此必须和 Metadata、Freshness、Authority 一起判断。

## Keyword / BM25 仍然非常重要

Keyword Retrieval（关键词检索）和 BM25 一类稀疏检索对精确 Token 非常敏感。错误码、函数名、类名、协议字段、版本号、订单号这类信息，向量检索反而可能不如精确词匹配。

因此 Hybrid Retrieval（混合检索）通常会组合：

~~~text
semantic vector recall
+
lexical / keyword recall
+
metadata / scope filters
→ candidate union
→ rerank
~~~

“Vector + Keyword”也只是开始。真正的工程问题是不同 Truth 需要不同 Retriever。

## 多路召回之后还要解决分数不可直接比较

向量相似度、BM25 分数、代码结构命中和数据库查询结果来自不同评分体系，不能简单把数值相加。

Fusion（融合：把多个检索通道的候选合成统一候选集）可以使用排名、归一化或规则权重。RRF（Reciprocal Rank Fusion，倒数排名融合：主要依据候选在各路结果中的排名合并）是一种常见、相对稳健的方法。

但任何 Fusion 都不应该覆盖硬规则：

~~~text
permission
current version
source authority
scope
> relevance score
~~~

一个无权限但非常相关的文档，不能因为融合得分高就进入 Context。

## Query Rewrite 和 Query Decomposition 解决“用户问题并不总适合直接检索”

用户可能问：“为什么重启后 Worker 没恢复，而且浏览器里还是旧页面？”

这其实混了多个信息需求：

~~~text
restart lifecycle
+ worker binding
+ browser reality
+ current version
~~~

Query Rewrite（查询改写：把用户自然语言整理成更适合检索的表达）适合补同义词、代码符号或领域术语。

Query Decomposition（查询拆解：把复合问题拆成多个可独立取证的子问题）适合不同 Truth Owner 必须分别查询的情况。

但是拆解不能让模型提前发明答案。正确顺序是：

~~~text
question
→ identify information needs
→ retrieve each need from appropriate owner
→ combine evidence
→ synthesize conclusion
~~~

先写结论再“搜索支持材料”，会把 RAG 变成确认偏误机器。

## Agentic RAG：检索本身也可以成为动态 Action

最简单的 RAG 往往是一条固定链：

~~~text
user query
→ retrieve once
→ assemble context
→ answer
~~~

当任务更开放时，Agent 可能先读一轮证据，再根据 Knowledge Gap 决定是否继续检索、改写 Query、换 Retriever、查询另一个 Source，或者停止。

这种形态通常被称为 Agentic RAG（智能体化检索增强：让检索动作和检索路线可以根据中间 Observation 动态变化）。

~~~text
Goal
→ retrieve
→ inspect evidence / gap
→ decide
├─ enough → answer
├─ rewrite query → retrieve again
├─ choose another retriever
└─ stop / escalate
~~~

它增加的是“检索路线由运行时新证据驱动”这一能力，不意味着每个 RAG 都应该升级成 Agent。问题明确、一次检索已经稳定满足任务时，固定 Retrieval Pipeline 更简单、更便宜，也更容易 Eval。

## 权限过滤应该尽量发生在候选进入模型之前

如果用户无权读取某个文档，最好的设计不是“先检索出来，再在 Prompt 里告诉模型不要泄露”，而是让 Permission Filter（权限过滤：依据当前身份和资源 Scope 排除不可见候选）尽早生效。

理想顺序：

~~~text
identity / tenant / task scope
↓
hard permission filters
↓
retrieval
↓
rerank
↓
context assembly
~~~

某些向量库支持 Metadata Filter，但业务权限通常仍然要由真正的 Auth/Policy Owner 计算，不能把权限逻辑偷偷复制进索引层后长期漂移。

## 不同事实有不同的 Retrieval Owner

一个问题如果问“这个函数谁调用”，最佳来源往往不是把整个仓库切 Chunk 做向量检索，而是 CodeGraph（代码结构图：基于语法和依赖关系建立符号、调用和影响关系的结构化索引）。

如果问“当前分支哪个 commit”，应该回 Git。

如果问“过去一周成功订单数”，应该用 SQL 或数据库查询，而不是让模型从几个文本 Chunk 推断。

因此现代 Retrieval 更接近 Query Plan（查询计划）：

~~~text
用户真正问什么
↓
需要哪种 Truth
├─ semantic docs → Vector
├─ exact text / symbol → Keyword
├─ code relations → CodeGraph
├─ version → Git
├─ structured fact → SQL / API
└─ external current info → Web / authoritative service
↓
merge / rerank / verify
~~~

这也是为什么“RAG = 向量数据库”是一个过窄模型。

## Reranker 解决“召回到”以后谁更值得进入 Context

Retriever 的目标通常是高 Recall（召回率），宁可多带一些候选。Reranker（重排器：使用更精细特征或模型重新比较 Query 与候选）负责把真正相关的证据往前排。

候选排序可以同时考虑：

- semantic relevance；
- keyword match；
- source authority；
- freshness；
- permission；
- document type；
- version；
- coverage diversity。

不能只用一个 cosine similarity 决定最终 Truth 顺序。

Reranker 也有成本梯度：轻量规则和分数融合很便宜，Cross-Encoder（交叉编码重排：把 Query 与候选一起送入模型直接打相关性分数）更精细但更慢，大模型重排可以理解复杂语义但成本更高。

所以常见形态是“便宜方法广召回，昂贵方法只比较较小候选集”。

## Context Assembly 不是把 Top-K 原样拼进去

RAG 最终要把候选转成当前模型调用的工作集，这一步叫 RAG Context Assembly（RAG 上下文装配）。

它需要处理：

~~~text
哪些候选真正回答当前问题？
是否存在冲突版本？
同一来源是否重复？
证据是否超出 token budget？
应该保留全文、片段还是稳定引用？
Citation 怎样回到原文？
~~~

所以 Top-K=10 只是一个中间参数，不是最终 Context 设计。

后面的 State / Context / Memory 章节会把它放进更大的 Runtime Context：当前模型看到的不只有 RAG，还可能包含 Goal、State、Memory、Tool Result 和 Instructions。

## Citation 和 Evidence 不只是“显示链接”

Citation（引用）让最终 Claim 可以回到 Source。成熟链路需要尽可能保留：

~~~text
claim
→ evidence snippet / structured fact
→ source
→ version / timestamp
→ locator
~~~

如果系统只是让模型“根据这些资料回答”，最后却丢掉来源位置，RAG 很容易退化成另一种不可验证生成。

Citation 也不自动证明 Claim 正确。它只能证明“这段回答可以回到这个来源”，还需要检查来源是否权威、是否真的支持该 Claim，以及是否已经过期。

## Freshness 和 Authority 比相似度更接近 Truth

假设向量库同时存在：

- 2025 年设计稿；
- 2026 年已上线实现；
- 一篇社区讨论。

用户问“当前系统怎样工作”，语义相似度最高的可能是设计稿，但 Source of Truth 应该是当前实现或正式运行事实。

因此候选排序不能把“像不像”当“真不真”。一个实用顺序是：

~~~text
current authoritative source
→ fresh verified evidence
→ current accepted documentation
→ historical material
→ weak secondary discussion
~~~

不同业务会有不同 Authority 规则，但必须显式存在。

## RAG 的常见失败不只有“没搜到”

至少有这些 Failure Slice（失败切片）：

- Retrieval miss：正确资料没召回；
- Wrong source：召回了相似但错误的来源；
- Stale evidence：旧版本覆盖当前事实；
- Permission leak：检索到了当前用户无权看到的内容；
- Chunk fragmentation：关键上下文被错误切断；
- Rerank failure：正确证据被排在噪声后面；
- Context overflow：召回太多导致真正关键信息被稀释；
- Citation mismatch：回答引用了来源，但来源并不支持该 Claim；
- Synthesis error：证据正确，模型综合仍然出错。

只有把失败拆开，才知道该修 Retriever、Index、Rerank、Context 还是 Model。

## RAG Eval 需要分层

只让 LLM Judge 看最终答案，会把多个责任混在一起。更有用的是：

~~~text
Query set
↓
retrieval recall / precision / coverage
↓
rerank quality
↓
context quality / freshness / authority
↓
answer correctness
↓
citation faithfulness
~~~

真实系统还要量 latency、index freshness、cost 和 permission failures。

这就是为什么 ProFlow-RAG 后来把 Knowledge、Retrieval、Evidence、Context、Citation 和 Eval 分开，而不是把“搜到几个 Chunk”直接当 RAG 完成。更深入的项目证据可以读 [ProFlow-RAG](../ProFlow-RAG/README.md)。

## Knowledge 和 Memory 只在存储形态上可能相似

Git、规范、数据库属于外部 Knowledge Source；Memory 则是系统从过去交互或经历中筛选后，未来值得复用的信息。

两者都可能使用向量检索，但 Authority 完全不同：

~~~text
Knowledge Source
= 外部 / 权威知识世界

Memory
= 从过去经历晋升出来的可复用信息
~~~

因此这一篇只保留“Knowledge 不等于 Memory”的边界；Memory 怎样写入、失效和进入 Context，由 [State、Context、Memory 为什么必须分开](./07-State-Context-Memory为什么必须分开.md) 继续展开。

## 一个完整 RAG 系统至少守住五层边界

第一层是**为什么需要外部知识**：模型参数不够新、不够私有，也很难提供稳定来源链。

第二层是**检索链本身**：Source、Parsing、Chunking、Index、Retriever、Fusion、Reranker、Context Assembly、Citation、Eval 各自负责不同阶段。

第三层是**表示、相似度和 Truth 不同**：Retrieval Embedding 不是 Token Embedding，Vector 不是 Similarity，Similarity 更不是 Authority。

第四层是**不同 Truth 使用不同 Retriever**：代码关系、Git 版本、SQL 事实、Web 当前信息不能都被压成向量相似度。

第五层是**动态检索也要有购买条件**：Agentic RAG 适合路线需要被新证据改变的任务；固定一次检索能稳定完成时，不需要为了“Agentic”增加 Loop。

当模型已经能稳定获得外部证据，下一个自然问题就是：**它怎样不只读世界，还能真正改变世界。**
