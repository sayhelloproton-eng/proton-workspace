# 模型怎样从“会回答”变成“能做事”

RAG 让模型能看到外部知识，但它仍然只是读取世界。真正进入 Agent 工程以后，模型需要查询数据库、运行测试、调用 API、操作浏览器、创建工单甚至触发发布。这里发生的是一次非常重要的责任变化：**模型从生成文本，变成提出结构化 Action；但现实动作仍然必须由确定性系统执行和治理。**

Tool Calling、Capability、Permission 和 MCP 经常被混成一团。这篇只负责把“模型怎样表达动作，以及外部能力怎样被接入系统”说清；长期副作用恢复由后面的 Durable Execution 章节完整负责。

## Structured Output 是第一步：让模型结果可以被软件消费

如果模型只返回一段自然语言：

> “我觉得应该查询订单 123。”

软件很难稳定判断它到底要调用什么、参数是什么。Structured Output（结构化输出：让模型按 Schema 返回机器可解析字段）先把开放语言收敛成合同，例如：

~~~json
{
  "action": "lookup_order",
  "arguments": {
    "order_id": "123"
  }
}
~~~

Schema（模式：规定字段、类型、枚举和必填关系）能检查结构是否合法，但它不能证明这个动作被授权，也不能证明订单 123 真的存在。

~~~text
schema-valid
≠ semantically correct
≠ authorized
≠ executed
≠ business success
~~~

## 结构校验之后还需要语义校验

JSON 合法并不意味着参数合理。

例如退款工具要求：

~~~json
{
  "order_id": "A-100",
  "amount": 99999
}
~~~

字段类型都合法，但这个订单可能只支付了 99 元。

Semantic Validation（语义校验：结合当前业务事实检查参数是否在真实可接受范围内）需要读取订单、币种、退款上限和当前状态，而不是只看 Schema。

因此动作进入 Executor 前至少可能经过：

~~~text
syntax / schema
→ semantic invariant
→ permission / policy
→ approval when required
→ execution
~~~

模型最擅长把意图变成候选参数，业务不变量仍应该由确定性 Owner 检查。

## Tool Calling：模型负责提出调用意图

Tool（工具：向模型暴露一个明确外部能力的结构化接口）通常包含名称、描述、输入 Schema，以及执行后返回的 Result。

模型看到有限 Tool Surface 后，可以根据用户目标选择工具并生成参数。Runtime 再决定是否执行。

典型链路：

~~~text
Goal + Context + available tools
→ Model
→ Tool Proposal / Tool Call
→ Runtime validation
→ Executor
→ Tool Result / Observation
→ Model
~~~

模型负责语义选择，执行器负责真实动作。这使模型可以进入循环，但不需要拥有底层凭证或数据库连接。

## Tool Contract 不只是函数名和参数

一个成熟 Tool Contract（工具合同）至少要让上层知道：

- 输入字段和类型；
- 返回结构；
- 错误类型；
- 是否只读；
- 是否会产生 Side Effect（副作用：改变外部世界的效果）；
- 是否支持 Idempotency（幂等：同一个逻辑操作重复提交不会产生第二份业务结果）；
- 需要什么 Identity / Permission；
- 结果怎样形成 Evidence；
- Timeout 后应该进入哪类恢复语义。

例如 get_order 和 refund_order 都是 Tool，但后者的风险完全不同。不能因为都能用 JSON 调用，就给它们相同的权限和 Retry 策略。

这里需要知道“Tool 必须声明副作用与恢复合同”，但不在本篇重复完整的 UNKNOWN / Reconciliation 算法；那部分由 [长期 Agent 怎样安全执行和恢复](./09-长期Agent怎样安全执行和恢复.md) 负责。

## 错误合同比“返回 error 字符串”重要得多

Tool Error 至少要区分几类责任：

| 类别 | 示例 | 常见处理 |
|---|---|---|
| Validation | 参数缺失、非法枚举 | 修参数，不执行 |
| Authorization | 无权限、需要审批 | 拒绝或进入 Approval |
| Not Found | 对象不存在 | 回到 Goal / 事实核对 |
| Conflict | Version 已变化、状态不允许 | 重新读取当前 State |
| Transient | 临时网络 / 限流 | 证明安全后 Retry |
| Timeout / Unknown | 结果不确定 | 进入 Reconciliation |
| Permanent | 能力不支持、合同不成立 | Replan / Fallback |

如果所有错误都压成 tool_failed，Agent 只能猜应该重试、换参数还是停止，Runtime 也无法执行有区别的恢复策略。

## Tool Result 不是现实 Effect

HTTP 200 说明服务端返回了一次成功响应，不一定证明业务 Goal 已满足；timeout 说明客户端没有及时拿到结果，也不证明服务端没有执行。

所以：

~~~text
Tool Result
= 本次调用观察到的返回

Effect
= 外部世界真正发生的变化
~~~

发布 API 返回成功以后，还可能需要读取部署版本；Browser 点击提交以后，需要回读目标对象；付款超时以后，要去支付系统查交易状态。

Tool Success ≠ Goal Success。

本篇只建立这条边界。Effect 怎样在 Timeout、断线、重启后被恢复为 Current Truth，由 09 继续展开。

## 同步 Tool 和异步 Tool 有不同生命周期

有些 Tool 可以很快返回最终结果，例如读取文件；有些动作只是提交一个长期 Job，例如 Build、Deploy、Video Generation。

Async Tool（异步工具：调用后先返回任务句柄，真实工作在外部继续执行）不应该强迫模型一直轮询。

更合理的模型是：

~~~text
submit action
→ operation_id / job_id
→ Task = WAITING
...
external event / status change
→ Runtime wakes task
→ read final result
~~~

这里的 job_id 是外部能力自己的身份，Runtime Task 是本地长期责任身份。两者可以关联，但不能混成同一个对象。

## Operation Identity 让 Runtime 能识别“同一次逻辑动作”

副作用 Tool 需要能表达：后续重试是在重复同一逻辑动作，还是在创建新的业务动作。

Operation Identity（操作身份：用稳定 Key 标识一次业务动作）和 Idempotency Key 是常见基础。

~~~text
same logical action
+ same operation identity
→ duplicate request should not create a second effect
~~~

但幂等只是恢复条件之一，不是恢复算法本身。Key 可能有有效期、Scope 或版本限制，外部系统也可能不支持。真正 UNKNOWN 之后仍要回到现实对账，细节留在 09。

## Capability 和 Tool 不是完全同一个概念

Capability（能力合同：用稳定业务语义描述系统能够完成什么）更偏上层抽象；Tool 是当前 Runtime 实际提供的一种执行表面。

例如“读取当前 Git 状态”是一项 Capability，今天可能由 Local Dev 的某个 Tool 实现，明天也可能换另一个 Executor。

只有当出现多个 Provider / Executor、多个消费者，或者需要围绕能力表达统一 Policy 时，才值得额外抽 Capability 层。一个系统只有一个实现时，不必为了架构漂亮先造 Registry。

## Model 选择 Tool，不代表它有 Permission

Permission（权限：当前 Identity 在当前 Scope 下原则上允许做什么）必须由模型外部系统判断。

模型可以正确生成一个 delete_repository Tool Call，结构和语义都可能“正确”，但当前主体仍然可能没有权执行。

更完整的执行链是：

~~~text
Model proposes
↓
Schema validation
↓
Capability / Scope check
↓
Permission / Policy
↓
Approval if required
↓
Execute
↓
Readback / Evidence
~~~

Prompt 里的“不要删除生产数据”只能帮助模型少提危险动作，不能代替真正的权限拒绝。

## Discovery、Selection、Authorization 是三件事

当 Tool 很多时，系统通常要先做 Tool Discovery（发现：从平台能力里找出与当前任务有关的候选），再让模型做 Selection（语义选择），最后执行 Authorization（授权判断）。

顺序很重要：

~~~text
all capabilities
→ hard permission / scope filters
→ task-relevant candidates
→ model semantic selection
→ execution policy gate
~~~

不要先把几百个 Tool Schema 全塞给模型，再希望它自己既选对又不越权。巨大的 Tool Surface 会增加 Context 成本和选择冲突。

## Skill 和 Tool 为什么不能混

Tool 提供“能做什么”；Skill（技能：可复用的程序性知识，说明一类工作应该怎样完成）提供“应该怎么做”。

例如：

~~~text
Tool
- read_file
- search_symbol
- run_test

Skill
- 怎样做一次可审计的仓库重构
- 先看哪些事实
- 什么时候停止
- 验证顺序是什么
~~~

Skill 可以指导 Agent 调用多个 Tool，却不应该绕过 Tool Permission，也不拥有长期 Task State。

## MCP 为什么出现：能力连接也需要共同协议

每个 Agent 产品如果都为 Git、数据库、浏览器、SaaS 自己定义一套私有插件接口，能力生态很难复用。MCP（Model Context Protocol，模型上下文协议）提供了 Host / Client 与 Server 之间相对标准化的能力连接边界。

可以先建立这个简化模型：

~~~text
Agent / Host
   │
   ├─ MCP Client
   │      ↓
   └── MCP Server
          ├─ Tools
          ├─ Resources
          └─ other protocol capabilities
~~~

MCP Server 把某一组能力和数据通过协议暴露出来；Host 决定是否连接、哪些能力对当前 Agent 可见，以及怎样把结果进入 Context。

MCP 的核心价值是 Interoperability（互操作：不同 Host 和 Server 可以在共同协议边界上协作），不是让模型自动获得所有权限。

## MCP 不拥有业务 Permission 和本地 Truth

连接到 MCP Server 只证明协议可达。真正系统仍需要判断：

- 当前是谁；
- 允许访问哪个项目、目录或账号；
- 哪些 Tool 可以调用；
- 高风险动作是否审批；
- 返回内容是否可信；
- 外部副作用怎样验证。

MCP 可以携带或支持认证相关机制，但“协议连接成功”不能替代应用自己的 Identity、Policy 和 Source of Truth。

这和 Tunnel 一样：能连通只解决 Reachability，不解决业务授权。

## MCP Task、Runtime Task 和 A2A Task 需要保留命名空间

现代协议里经常出现 Task，但要先看语义 Owner。

- Runtime Task：本地系统对长期 Goal、State、Recovery 负责的对象；
- MCP Task：能力调用协议中的生命周期对象；
- A2A Task：独立 Agent 协作协议中的工作对象。

它们可以 Mapping，但不能因为字段都叫 task_id 就共享一套语义。外部协议状态进入本地以后，仍然要由本地 Runtime 按 Policy、Version 和 Evidence 处理。

## Connector、Plugin、MCP 不要只按产品名理解

Connector（连接器）通常代表把某个外部服务或数据源接入当前产品的适配能力；Plugin（插件）更偏能力的包装、安装和分发边界；MCP 是协议。

一个 Plugin 可以包含 Skill、MCP Server、Agent 定义和 Hook；一个 Connector 也可能内部使用 OAuth + REST 而不是 MCP。判断时看责任，不要用一个产品术语覆盖所有层。

更完整的生态边界可以在 [Coding Agent 真正竞争的是什么](../Coding-Agent.md) 继续读。

## 原生 Tool Calling 失败不等于模型没有工具语义能力

端侧模型实验曾出现过一个典型证据：OpenAI-compatible 接口接受 tools 请求并返回 HTTP 200，但实际响应没有标准 message.tool_calls。如果直接下结论“模型不会用 Tool”，就把 Provider Protocol 和 Model Capability 混了。

后来让同一模型直接输出 JSON Tool Proposal，再由平台做 Schema、Permission、Approval 和外部执行，模型能够稳定完成工具选择和参数抽取。

因此需要分层归因：

~~~text
Model semantic capability
≠ Provider native tool protocol
≠ Runtime permission
≠ Executor effect
~~~

详细实验见 [端侧模型](../端侧模型.md)。

## 一次工具动作的可信链

把前面的责任收束成一条链：

~~~text
Goal
↓
Model proposes Action
↓
Schema / normalization
↓
Semantic validation
↓
Permission + Policy + Approval
↓
Executor performs effect
↓
Observation / readback
↓
Validator + Evidence
↓
Runtime commits current truth
~~~

中间任何一步都不能被“模型说成功了”跳过。

## 工具系统最容易混淆的五个边界

Function Calling 和 MCP 不在同一层：前者表达模型或应用怎样提出工具调用，后者解决 Host 和外部能力 Server 的互操作连接。

Tool 和 Skill 也不在同一层：Tool 是动作原语，Skill 是程序性方法。

Schema 校验通过只说明结构合法，不代表语义正确、获得授权或适合执行。

Tool 返回成功只说明得到一个调用结果，不代表真实 Effect 已经被验证，更不代表上层 Goal 完成。

Tool Timeout 如果涉及副作用，不能直接按普通网络错误处理；它会把系统带入 UNKNOWN / Reconciliation 语义，而完整恢复由 09 负责。

有了 Tool，系统终于能行动。下一篇继续解决一个更大的问题：**下一步到底应该由代码预先决定，还是让模型根据环境动态决定。**
