# 模型为什么能够理解和生成文本

大语言模型最容易被神秘化的地方，是把“它为什么能生成这么像人类的语言”直接归结为“参数很多”。参数规模很重要，但如果不了解 Token、Embedding、Attention 和自回归生成之间怎样连接，后面的 RAG、Context、Reasoning、Agent 都会缺少底层心智模型。

这篇只回答模型内部最基础的一条链：**文本怎样变成向量，向量怎样彼此建立关系，模型怎样基于这些关系一步步生成下一个 Token。**

## 文本进入模型以后，第一步不是“理解”，而是 Tokenization

模型不能直接处理字符串。Tokenizer（分词器：把文本切成模型词表中的离散单位并映射为整数 ID）先把输入转换成 Token 序列。

一个 Token 可能是一个完整英文单词、单词片段、汉字、标点或其他字节模式。不同模型使用不同词表和切分算法，因此：

~~~text
同一段文字
→ 不同 Tokenizer
→ Token 数可以不同
~~~

这件事后来会直接影响 Context Window、成本和端侧模型性能。模型更小不等于同一文本天然拥有更少 Token，因为参数规模和 Tokenizer 是两条不同维度。

Token ID 仍然只是整数，没有语义。下一步才是 Embedding。

## Embedding：把离散 Token 放进连续向量空间

Embedding（嵌入向量：把离散 Token 映射成连续高维数值表示）让神经网络能够计算 Token 之间的关系。

可以先把它想成：每个 Token 不再是字典里的编号，而是高维空间中的一个点。训练以后，这些向量不会只保存“词义”，还会参与编码语法、上下文角色和大量统计关系。

但单个 Token 的初始 Embedding 还不知道它在当前句子里的位置，也不知道周围出现了什么。因此模型还需要 Position Information（位置信息）和 Attention（注意力）把“这个 Token 在这里出现”与其他位置联系起来。

## 位置信息为什么不能省：Attention 本身并不知道先后顺序

Self-Attention 在数学上主要比较向量之间的相关性。如果只给它一组 Token Embedding，而完全不告诉位置，“A 在 B 前面”和“B 在 A 前面”的顺序关系不会自然出现。

因此 Transformer 需要显式或隐式注入 Position Encoding（位置编码：告诉模型 Token 在序列中的相对或绝对位置）。早期 Transformer 使用固定的正弦/余弦位置编码，后来常见模型更多使用 RoPE（Rotary Position Embedding，旋转位置编码）等相对位置方案。

对工程理解来说，不需要背每一种公式，但要知道它解决的是：

~~~text
Token 本身是什么
+
它出现在第几个位置
+
它和其他 Token 相隔多远
→ 才能形成有顺序的上下文关系
~~~

这件事还会影响长上下文外推。一个模型训练时只稳定见过较短序列，后来把 Context Window 扩大，不等于所有位置关系都能无损延伸。长上下文能力既和模型架构有关，也和位置表示、训练分布、推理实现有关。

## Attention 真正解决的是“当前这个位置应该看谁”

RNN 一类早期序列模型通常沿时间步传播信息，距离越远，依赖路径越长。Transformer 的核心改变之一，是让序列中的位置通过 Self-Attention（自注意力：同一序列内部不同位置直接计算相关性）建立更短的依赖路径，并且适合在训练时大规模并行。

一个位置会从自己的当前表示生成三组向量：

- Query（查询向量，Q）：我现在在寻找什么；
- Key（键向量，K）：我可以被怎样匹配；
- Value（值向量，V）：如果你关注我，我实际提供什么信息。

简化以后可以理解成：

~~~text
当前位置的 Q
×
所有位置的 K
→ relevance scores
→ softmax 得到注意力权重
→ 对对应 V 做加权求和
→ 得到结合上下文后的新表示
~~~

公式常写成：

~~~text
Attention(Q, K, V) = softmax(QKᵀ / √d) V
~~~

这里的缩放项 √d 用来避免维度增大后点积数值过大，让训练更稳定。

关键不是背公式，而是理解责任：**Q/K 决定“该关注谁”，V 决定“从被关注位置取回什么”。**

## Wq / Wk / Wv 是模型参数，Q / K / V 是这一轮计算出来的结果

Q、K、V 很容易被误解成模型里固定保存的三份知识。实际上，模型训练得到的是投影矩阵 Wq、Wk、Wv 等参数；当前 Token 表示经过这些参数变换以后，才在这一轮前向计算中产生具体的 Q、K、V。

可以粗略写成：

~~~text
current hidden representation X
↓
X × Wq → Q
X × Wk → K
X × Wv → V
~~~

所以：

~~~text
Wq / Wk / Wv
= learned parameters

Q / K / V
= current input under those parameters 的动态结果
~~~

这条边界很重要。Parameter 是训练后长期保存的模型状态；Activation、Q/K/V 是一次具体输入经过模型时产生的中间计算结果。KV Cache 缓存的是后者，不是在训练过程中修改模型参数。

## 为什么 Attention 很强，却也让长上下文很贵

标准 Self-Attention 需要计算每个位置与大量其他位置之间的关系。序列长度为 n 时，注意力矩阵规模大致按 n² 增长。

这意味着 Context 从 8K 增长到 128K，不只是“多装 16 倍 Token”这么简单；计算、显存/内存、KV Cache、Prefill 延迟都会迅速增加。现代模型会通过 FlashAttention、GQA/MQA、Paged Attention、稀疏注意力等技术降低实际代价，但“长上下文有真实系统成本”这个事实不会消失。

因此在工程系统里，Context Window 的正确使用方式不是“越大越好”，而是：

~~~text
模型有较大上限
+
系统做 Context Selection / Compression / Retrieval
→ 实际只送当前判断需要的信息
~~~

这也是后面 Context Engineering、RAG 和 Memory 治理出现的底层原因之一。

## Multi-Head Attention：同一段文本需要同时看不同关系

如果所有关系都挤进一次 Attention，模型表达空间会受限。Multi-Head Attention（多头注意力：并行计算多组独立 Q/K/V 投影）允许不同 Head 学到不同类型的关系。

某些 Head 可能更敏感于局部语法，某些可能追踪实体指代，某些更关注远距离约束。不能把每个 Head 人格化成固定功能，但多头结构确实让模型可以同时在不同表示子空间里建立关系。

各 Head 的结果随后拼接，再通过线性层继续混合。

## 一个 Transformer Block 不只有 Attention

典型 Transformer Block 还包括 Feed-Forward Network（前馈网络，也常写作 FFN / MLP：对每个位置独立做非线性变换）、Residual Connection（残差连接：让输入可以直接跨层相加，帮助深层网络训练）和 Layer Normalization（层归一化：稳定激活分布和优化过程）。

可以把一层的作用粗略理解成：

~~~text
当前各位置表示
→ Attention：跨位置交换信息
→ Residual / Norm
→ FFN / MLP：每个位置内部继续加工
→ Residual / Norm
→ 下一层
~~~

Attention 更像“位置之间怎样交流”，FFN / MLP 更像“一个位置拿到上下文以后怎样继续变换”。多层堆叠以后，一个位置的表示已经不再只是原始 Token，而是不断吸收整段 Context 后形成的上下文表示。

## Decoder-only 为什么自然走向开放生成

Transformer 原始架构同时有 Encoder 和 Decoder。BERT/GPT 为什么后来走向不同产品路线，由下一篇完整展开；这里先只保留和生成机制直接相关的边界。

GPT 类模型沿 Decoder-only 路线发展，用 Causal Mask（因果遮罩：当前位置只能看见自己之前的 Token）训练“预测下一个 Token”。这使训练目标和生成天然一致：

~~~text
给定前文
→ 预测 next token
→ 把预测结果接到末尾
→ 再预测下一个
~~~

因此 Decoder-only 很自然地成为开放式生成、对话、代码和后续 Agent 模型的主干。Encoder 路线则更多保留在表示、匹配、Embedding 和理解型任务里。

## 从最终表示到下一个 Token：Logits → Softmax → Sampling

最后一层 Transformer Block 得到的是连续向量表示，还不是文字。模型需要把当前位置的表示投影回 Vocabulary（词表）大小的空间，为每个候选 Token 产生一个 Logit（未归一化分数）。

随后：

~~~text
final hidden representation
→ vocabulary projection
→ Logits
→ Softmax
→ next-token probability distribution
→ Sampling / argmax
→ chosen Token
~~~

Logit 不是概率，Softmax 才把一组候选分数转换成总和为 1 的概率分布。Sampling 再根据 Temperature、Top-p、Top-k 等规则，从这个分布中选择真正输出的 Token。

这条链把“神经网络内部连续数值”接回“用户看到的离散文本”。

## 自回归生成为什么既强大又天然带概率性

Autoregressive Generation（自回归生成：每次基于已有序列预测下一个 Token，再把结果继续作为输入）意味着最终文本是一步一步长出来的。

模型每一步都会输出一个对词表的概率分布。系统可以直接选择概率最高的 Token，也可以通过 Temperature（温度：调整概率分布平滑程度）、Top-k、Top-p 等 Sampling（采样）策略在多个候选里选择。

于是两个事实同时成立：

1. 模型可以在开放空间生成非常灵活的结果；
2. 同一输入不一定永远得到同一输出。

这也是为什么后面的 Agent 工程不能只靠“模型通常会做对”。结构、权限、状态和关键验证需要由确定性软件承担。

## 解码参数改变的是采样策略，不是模型“知识量”

Temperature、Top-p、Top-k 经常被误解成“让模型更聪明/更保守”的开关。它们真正影响的是：已经得到 next-token 概率分布后，系统怎样从候选中选择。

低 Temperature 会让分布更尖锐，输出通常更稳定；较高 Temperature 会增加低概率候选被采样的机会，提高多样性，也增加结构漂移风险。

结构化任务常把随机性压低，而创意写作可以接受更大采样空间。

但即使 Temperature=0，也不能把模型当成普通函数：底层服务实现、并行数值、模型版本、上下文变化、工具返回都可能让最终行为变化。**低随机不等于系统级确定性。**

## Context Window 是一次调用的可见容量，不是长期记忆

Context Window（上下文窗口：一次模型调用能够处理的 Token 容量上限）决定当前 Invocation 最多能送进去多少输入和已有输出。

它经常被误解成 Memory。实际上：

~~~text
Context Window
= 当前一次推理的容量约束

Memory
= 系统从过去信息中治理后，未来仍值得复用的对象
~~~

一次调用结束，模型并不会因为刚才“看过”某段内容就自动永久记住。对话连续性来自应用把历史或摘要重新装进下一轮 Context，而长期 Task State 和 Memory 必须由外部系统维护。

## KV Cache 为什么会影响长上下文和生成速度

在自回归生成中，第 1000 个 Token 生成以后，再生成第 1001 个时，前面 1000 个位置的 Key/Value 不需要每次从头重算。KV Cache（键值缓存：保存先前 Token 在 Attention 中产生的 Key/Value 表示）用内存换计算，显著提高逐 Token 生成效率。

因此长 Context 不只是“模型理论上能装多少”，还会影响显存/内存、Attention 计算、首 Token 延迟和后续生成速度。不同架构还会使用 GQA、MQA 等方法减少 KV Cache 成本，但工程上真正需要记住的是：**Context 容量、推理延迟和内存不是互相独立的。**

## Prefill 和 Decode 为什么要分开看性能

一次 LLM 请求至少可以粗分成两个阶段。

Prefill（预填充）处理用户给进来的整个 Prompt/Context，计算这些 Token 的内部表示；Decode（逐 Token 解码）则是在已有 KV Cache 上一个 Token 一个 Token 继续生成。

所以两个常见指标要分开：

~~~text
TTFT（Time To First Token）
≈ 输入处理 + 调度 + 首次解码

TPS / tokens per second
≈ 后续生成吞吐
~~~

很长的 Context 可能让 TTFT 明显上升，即使后续 Decode 速度还不错。反过来，一个短输入但输出 4000 Token 的任务，主要成本又会落在 Decode。

这对 Agent 很重要：大量工具调用链里，频繁重复塞长 Context 会把 Prefill 成本不断放大。因此 Runtime 会尝试做 Context Projection、缓存和更短的中间结构，而不是每一步都把整个历史重新投喂。

## Training 和 Inference：一个更新参数，一个使用参数

Training（训练）和 Inference（推理）都运行 Transformer 计算，但目标不同。

训练阶段会让模型看到大量样本，计算预测误差，再通过反向传播和优化器更新 Wq/Wk/Wv、Embedding、FFN 等参数。推理阶段则固定这些参数，只对当前输入执行前向计算并生成结果。

~~~text
Training
→ forward
→ loss
→ backward
→ update parameters

Inference
→ fixed parameters
→ forward / decode
→ output
~~~

这也是为什么“当前对话里模型学会了一个事实”通常不等于模型权重真的被训练更新了。当前 Context、外部 Memory、RAG 和真正的参数训练是不同层次。

## Transformer 为什么适合 Scaling

Transformer 能成为 Foundation Model 的主干，原因不只在效果，还在训练形态。

Self-Attention 允许训练阶段对序列位置进行更高效的并行计算；统一的“Token → Transformer Blocks → next-token probability”目标又可以直接吸收海量无标注文本、代码和多模态离散表示。随着 GPU/TPU、大规模分布式训练和数据工程成熟，这种结构特别适合扩大参数、数据和计算规模。

于是能力提升不再依赖“为每一个任务单独设计一个模型”，而是先训练一个大基础模型，再通过 Prompt、SFT、RAG、Tool 和 Runtime 适配各种任务。

本地推理时还会遇到模型格式、量化、内存、设备带宽、冷启动和具体硬件实现等问题。这些属于模型“怎样在真实设备上跑起来”的另一层工程责任，本系列不在 Transformer 章节重复展开，真实 Apple Silicon / iPhone 证据统一放在 [端侧模型](../工程工具与运行时/端侧模型.md)。

## Transformer 没有解决模型外部世界

理解底层以后，更重要的是知道它没有提供什么：

- 它不会自动知道最新世界状态；
- 它不会自动连接数据库、Git、浏览器和 API；
- 它不会保存正式 Task State；
- 它不会因为注意到了某条安全规则就获得或失去真实权限；
- 它不会证明自己生成的结果在现实世界已经生效；
- 它不会自动把一次对话经验治理成长期 Memory。

这些都属于模型外面的系统责任。

## 把模型内部机制串成一条完整链

这一篇的机制可以压成：

~~~text
Text
→ Tokenizer
→ Token IDs
→ Embedding + Position
→ Transformer Blocks
   ├─ Wq/Wk/Wv → dynamic Q/K/V → Attention
   └─ FFN / Residual / Norm：继续变换表示
→ Causal next-token representation
→ Logits
→ Softmax
→ Sampling
→ Autoregressive generation
~~~

再把性能约束接上：

~~~text
长输入
→ 更高 Prefill / Attention 成本
→ 更大的 KV Cache
→ 更高 TTFT / memory pressure

长输出
→ 更长 Decode
→ 更高逐 Token 生成成本
~~~

因此 Context Window 只是一次调用的可见容量，KV Cache 是推理优化，不是长期记忆；模型生成很灵活，却仍然是概率计算组件。外部事实、权限、状态、真实执行和结果证明，都必须由模型外的软件系统继续补齐。
