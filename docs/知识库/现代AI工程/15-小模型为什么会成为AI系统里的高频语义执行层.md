# 小模型为什么会成为 AI 系统里的高频语义执行层

一个客服系统每天有十万条消息，其中绝大多数工作只是识别意图、抽取订单号、把自然语言归一成有限字段、判断该进入哪个 Workflow。如果每一步都调用最强 Reasoning Model，系统付出的不仅是 Token 价格，还有排队、延迟、功耗和长链失败成本。

小模型真正有价值的地方，不是“也能做一个缩小版 ChatGPT”，而是作为**高频、边界收紧、可验证的语义执行层**，把大量重复判断留在低成本路径，把复杂和高风险长尾升级给更强模型或人工。

## “小”不是固定参数量，而是任务和部署约束的相对概念

SLM（Small Language Model，小语言模型）没有一个跨所有设备和任务都成立的 1B/3B/7B 分界。

工程上更有用的定义是：

> **在目标硬件、延迟、成本、隐私和质量门槛下，能够通过该 Task Slice Eval 的最小模型。**

同一个 7B 模型，对手机可能很重，对服务器分类服务可能已经很小，对开放科研推理又可能能力不足。

因此模型大小必须和 SLO、硬件和任务一起讨论。

## Small Model 更像 Semantic Worker，不是独立 Agent

Semantic Worker（语义工作单元：承担分类、抽取、改写、路由等有限语义责任的模型组件）常见职责包括：

~~~text
Intent / Classification
Extraction / Normalization
Query Rewrite
Tool candidate / argument fill
Context Compression
Environment state classification
Simple Draft / Summary
~~~

这些 Worker 可以全部由同一个小模型承担，也可以按领域拆不同模型。

关键是：它们没有必要拥有独立 Task Identity、Permission 和 Lifecycle。

所以：

~~~text
Multi-Model
≠ Multi-Agent
~~~

一个 Agent Runtime 背后完全可以路由多个专用 Model Capability，却仍然只有一个长期责任主体。

## 最稳定的系统原则是 Deterministic-first，Semantic Small-first

把任务按不确定性分层：

~~~text
完全确定
→ Code / Rule / SQL / traditional model

需要语义理解，但范围小、输出可验证
→ Small / Specialized Model

开放世界、复杂规划、跨领域推理
→ Strong / Reasoning Model

高风险最终动作
→ Policy / Domain Expert / Human Approval
~~~

小模型不是用来把普通代码“AI 化”。相反，它最适合站在确定性软件中间，专门解决规则难以手写的语义映射。

## Fine-tuning 不是垂直化的第一步

很多团队一说“做垂直小模型”，路线就变成：

~~~text
选模型
→ 收集数据
→ Fine-tune
~~~

更可靠的顺序应该先把业务问题收紧：

~~~text
定义 Outcome / Task Slice
→ Structured Input
→ Structured Output
→ Deterministic Validator
→ Cheapest Baseline
→ Prompt / Few-shot
→ RAG / Tool / Workflow
→ Small-first Routing / Escalation
→ stable failure slices remain?
   ├─ no → stop
   └─ yes → model adaptation candidate
~~~

只有软件合同已经清楚，训练才知道自己真正要修什么。

## Input Contract 先减少输入歧义

假设做设备故障工单分类，原始输入可能混着自然语言日志、不同单位、时间顺序和缺失字段。

先收敛成 Input Contract（输入合同）：

~~~json
{
  "device_model": "PX-7",
  "alarms": ["E102", "TEMP_HIGH"],
  "temperature_c": 92.4,
  "pressure_kpa": 318,
  "maintenance_refs": ["WO-8821"]
}
~~~

单位转换、枚举映射、时间排序等确定性工作在模型前完成。

这比让模型同时处理脏数据和领域判断更稳定，也更容易 Eval。

## Structured Output 让错误可以被机器分类

模型输出固定 Schema：

~~~json
{
  "fault_type": "bearing_overheat",
  "evidence": ["TEMP_HIGH", "WO-8821"],
  "confidence": 0.86,
  "needs_human": false
}
~~~

有了结构合同，失败才可以分成：

- missing field；
- invalid enum；
- evidence not present；
- unsafe auto-decision；
- should reject but guessed；
- semantic misclassification。

如果结果只是一段自由文本，很难知道 Fine-tuning 到底改善了什么。

## Deterministic Validator 是小模型生产化的核心

Validator 不让模型更聪明，它负责在便宜路径上快速拒绝不可信结果。

例如：

- fault_type 是否在允许枚举；
- Evidence 是否真的来自输入；
- 高风险类别是否必须人工；
- 必填字段是否完整；
- 当前输入是否明显 OOD；
- Confidence / Margin 是否低于 Gate。

~~~text
Small Model
→ Structured Output
→ Validator
├─ PASS → downstream
└─ REJECT / ESCALATE → stronger model / human
~~~

没有这层，小模型只是在更便宜地产生概率文本。

## 客服：大量入口请求本质上是有限状态映射

用户说：

> “昨天买的空气炸锅还没发，要是不行就退了。”

低成本链路可以是：

~~~text
Rule / parser
→ Small Model
   intent = shipping_delay
   requested_action = inspect_then_refund
   missing_fields = [order_id]
→ Validator
→ lookup order / logistics / policy
→ Workflow
├─ normal path → short reply
└─ conflict / high amount / special complaint → strong model / human
~~~

这里最有价值的指标不是“回答像不像真人”，而是 Intent Accuracy、字段正确率、Routing Error Cost、Escalation Rate、人工时间和 Cost per Success。

## RAG：小模型可以先把 30 页候选压成强模型真正需要的 3 页

RAG 系统经常把大量 Chunk 原样塞给强模型。

Small Model 可以参与：

~~~text
Query Rewrite
→ retrieval
→ relevance classification / rerank
→ structured compression
→ preserve evidence anchors
→ Strong Model synthesis
~~~

Structured Compressor（结构化压缩器）只保留实体、数字、结论和 Source Reference。

但压缩结果是 Derived Artifact（派生产物），不能覆盖原始 Evidence。高风险事实仍然要能回到原文。

## Agent Runtime：最贵的往往不是一次强模型，而是几十次重复调用

一个 Coding Agent Task 可能经历：

~~~text
理解目标
→ 找文件
→ 分类错误
→ 选工具
→ 看结果
→ 压缩日志
→ 再选工具
→ 判断是否完成
~~~

如果每一步都调用最强 Reasoning Model，Loop 会放大延迟和成本。

可以把高难决策保留给强模型，小模型负责：

- Tool 候选分类；
- 参数抽取；
- Result normalization；
- 日志类别；
- Context compression；
- completion candidate；
- escalation gate 的语义信号。

Runtime 仍然拥有 Task、Permission、Evidence 和 Stop Rule。

小模型不能因为便宜就成为 Truth Owner。

## Browser / Coding Environment：小模型适合压缩环境噪声

Terminal 输出几万行、DOM 几千节点、Diff 几百行时，小模型可以生成结构化 Observation：

~~~text
logs
→ error class / key stack frame / failed test ids

diff
→ affected module candidates / risk labels

DOM / accessibility tree
→ interactive candidates / page state
~~~

但 Raw Evidence 必须保留。

小模型说“测试通过”不能替代真实 Test Result；说“页面已保存”不能替代 Browser Readback。

它的价值是压缩环境，不是制造事实。

## 端侧模型把小模型变成本地软件能力

手机、PC、边缘设备上的 On-device Inference（端侧推理）可以带来：

- 更低网络依赖；
- 数据本地性；
- 离线能力；
- 高调用量下更低云 API 边际成本。

但本地并不等于免费：模型占内存、耗电、发热、需要冷启动和版本管理。

复杂 Context 和高难推理仍可以经过权限过滤和压缩后升级到云端。

真实 iPhone 研究已经验证：模型可以成为受 Runtime 调度的推理 Provider，但 Task Truth、Permission、Execution Flow 和真实 Effect 必须留在上层。完整过程见 [端侧模型](../工程工具与运行时/端侧模型.md)。

## 制造 / IoT：语义理解可以下沉，硬安全控制不能下沉给生成模型

工业现场可以让小模型做：

- 日志语义分类；
- 故障描述归一化；
- 工单路由；
- 维修记录摘要；
- 异常模式候选。

但 PLC、安全阈值、互锁、紧急停止等 Hard Safety Rule 仍应该由确定性控制系统执行。

~~~text
sensor / PLC / safety rule
→ deterministic control

edge small model
→ semantic interpretation

cloud / strong model
→ complex diagnosis / research
~~~

模型能理解设备语言，不意味着可以替代硬实时安全回路。

## 高并发 SaaS 真正优化的是吞吐和 Cost per Success

当每天有海量分类、抽取、摘要、Tool 参数和路由请求时，应该比较：

~~~text
Throughput
p50 / p95 latency
Cost per Success
memory
concurrency
Escalation Rate
Human Load
~~~

一个小模型只要在目标 Slice 达到业务门槛，就可以承接大量流量；长尾升级后，系统总体质量仍可能保持高水平。

## 小模型不天然减少 Token Count

必须区分三个量。

Token Count 由具体 Tokenizer 和文本决定。

Token Compute Cost 由模型规模、架构、硬件和服务定价影响。

系统最能主动减少的是 Frontier Token Volume：送进昂贵强模型的请求数量和 Context 总量。

~~~text
all requests → strong model

vs

simple requests → small model complete
hard requests → compressed context → strong model
~~~

Small-first 真正省的是昂贵模型调用和高价 Context，不是参数少就自动把同一段文字变短。

## 模型适配路线解决的是不同缺口

如果 Prompt、RAG、Tool、Contract 都稳定以后，仍然有可重复的重要 Failure Slice，再选择适配方式。

### LoRA / PEFT

LoRA（低秩适配）冻结大部分 Base Model，只训练少量低秩参数。

适合：

- 稳定领域术语；
- 有限行为模式；
- 固定任务决策边界；
- Tool Calling 语义选择；
- 不希望付全参训练成本。

如果问题只是 JSON 字段缺失，优先修 Schema/Validator，不要用 LoRA 训练格式纪律。

### QLoRA

QLoRA 在量化冻结 Base Model 上训练 LoRA Adapter，主要解决训练显存压力。

它仍然受 Base Model、Context、Batch、Kernel、训练时长影响，不等于“普通设备能训练任意模型”。

### Distillation

Knowledge Distillation（知识蒸馏）让 Student Model 学习较强 Teacher 在目标任务上的经过筛选行为。

适合大模型已经能稳定做对、但成本太高的场景。

风险是 Teacher 错误被规模复制，因此 Synthetic Data 必须保留来源、过滤和人工抽样。

### Continued Pre-training

Continued Pre-training（继续预训练）适合模型对整个领域语言、符号和表示都缺乏基础，而不是只缺一个任务格式。

它需要更大 Domain Corpus、版权/PII 治理和通用能力回归测试。

### Full Fine-tuning / Training from Scratch

只有 PEFT 明确达不到质量门槛、数据和算力充分、团队真正拥有训练与部署能力时，才进入全参数更新甚至从头训练。

对多数应用团队，这不是默认路线。

## Dataset 必须先有真实数据合同

训练数据至少分：

- Train；
- Validation；
- Test；
- Challenge Set；
- Online Shadow Set。

要防止 Data Leakage（数据泄漏）、重复样本和标签冲突。

还需要记录：Source、License、PII、版本、标注规则和实际线上分布。

Test Set 被反复拿来看结果再调参以后，就已经不再是干净 Final Test。

## Base Model 选型不能只看排行榜

至少检查：

- language / domain baseline；
- context length；
- tokenizer / chat template；
- structured output / tool calling；
- license；
- hardware support；
- quantization/deployment format；
- model card / revision；
- known limitations。

更好的起点是：选择一个在未调优 Baseline 上已经接近门槛的最小模型，而不是先挑最小参数，再希望 Fine-tuning 创造全部能力。

## 量化必须回到目标硬件重新 Eval

Quantization（量化）降低权重位宽，可以减少模型大小和内存，但也可能损害质量。

目标设备上必须真实测：

~~~text
load time
cold / warm start
TTFT
throughput
peak memory
energy / thermal
concurrency
quality by failure slice
~~~

开发 GPU 上跑得快，不能证明手机或 CPU 也一样。

## Confidence Gate 不能只相信模型自报 confidence

Small-first Cascade（小模型优先级联）可以结合：

- classifier margin；
- sampling consistency；
- deterministic validator；
- retrieval coverage；
- distribution distance；
- high-risk business rule。

模型自己说 confidence=0.98 只是一个信号，不是系统授权。

OOD（分布外）和高风险输入应该拒绝、升级或进入人工，而不是强迫小模型给确定答案。

## Shadow、Canary、Rollback 让模型版本进入软件发布纪律

上线新模型/Adapter 可以遵循：

~~~text
Offline Eval
→ Shadow
→ Canary
→ compare
→ gradual expansion
→ rollback if degraded
~~~

Model Registry 应记录 Base Model Revision、Tokenizer、Adapter、Dataset、Training Config、Quantization、Eval、Target Hardware、Owner 和 Rollback Target。

模型文件存在不等于模型可以上线。

## Small-first 最大的反模式是 Model Explosion

为每个小任务各维护一个模型，可能制造 Model Explosion：版本、缓存、路由和 Eval 成本超过节省下来的推理成本。

多个类似任务可以共享 Base Model + Adapter/Profile，也可以由一个小模型承担多种 Schema 受控的工作。

模型数量同样需要用增量价值证明。

## 一条最值得记住的决策顺序

~~~text
能用规则 / SQL / traditional model？
→ 用确定性方案

需要语义，但边界窄、可验证？
→ Small Model

知识变化快？
→ RAG / Tool

路径固定？
→ Workflow

复杂 / OOD / high-risk？
→ Strong / Reasoning Model or Human

稳定重要 Failure Slice 仍存在？
→ LoRA / Distillation / Continued Pre-training candidate
~~~

模型训练永远不是权限、安全和当前 Truth 的替代品。

## 小模型真正值得的条件

小模型不是因为参数少就值得进入系统，而是因为某一类高频 Task Slice 已经被收紧到可以结构化输入、结构化输出和机械验证，并且使用更强模型的边际质量收益不足以覆盖延迟和成本。

一个成立的 Small-first 路径通常具备：

~~~text
high frequency
+ narrow semantic boundary
+ deterministic validator
+ clear escalation condition
+ measurable cost / latency gain
+ no ownership of permission or truth
~~~

它适合承担分类、抽取、路由、Context 压缩等语义工作；失败、OOD 或高风险请求升级强模型或人工。它主要减少昂贵模型的调用次数和 Frontier Token Volume，而不是天然减少同一文本的 Token Count。

Multi-Model 只是 Runtime 内的计算路由，不等于 Multi-Agent；只有稳定 Failure Slice 在 Prompt、RAG、Tool 和 Workflow 已经收紧之后仍然存在，才值得进一步考虑 LoRA、Distillation 或 Continued Pre-training。

这也是小模型从“模型研究对象”真正变成 AI 工程系统组件的分界点。
