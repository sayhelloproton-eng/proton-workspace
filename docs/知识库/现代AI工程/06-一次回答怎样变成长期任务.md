# 一次回答怎样变成长期任务

一个模型调用可以在几十秒后结束，一个浏览器页面可以关闭，一个 Session 也可以被重建；但真实任务可能要等审批、等构建、等另一位执行者、等明天继续。只要责任还没有结束，系统就必须能回答：**这是哪个任务、现在到哪一步、谁负责、下一次从哪里继续。**

这就是 Runtime（运行时）真正出现的地方。它不是“把模型包在一个 while 循环里”，而是把长期责任做成可持续存在的软件对象。

## Invocation、Turn、Thread、Session、Task 是不同时间尺度

| 对象 | 主要回答什么 | 常见生命周期 |
|---|---|---|
| Model Invocation（模型调用） | 这一次推理输入什么、输出什么 | 秒～分钟 |
| Turn（轮次） | 一次交互往返 | 秒～分钟 |
| Thread（消息线程） | 一串相关消息如何组织 | 分钟～长期 |
| Session（运行会话） | 当前工作台、连接、浏览器或终端环境 | 分钟～小时 |
| Runtime Task（运行时任务） | 哪个长期责任仍在推进，当前状态是什么 | 小时～天甚至更久 |

最重要的边界是：

~~~text
Model Invocation lifetime
≠ Session lifetime
≠ Task lifetime
~~~

一个 Task 可以跨多个 Session，一个新的 Invocation 也可以继续处理同一个 Task。

## Runtime Task 是长期责任对象

Task 不是一条 Prompt，也不是“聊天标题”。一个能够跨时间继续的 Task 至少要拥有稳定 Identity，并能描述：

~~~text
Goal
Status
Owner
Success Criteria
Current State refs
Artifact refs
Pending Work
wait / resume condition
~~~

系统重新进入任务时，不需要恢复模型过去的隐藏思维，只需要恢复这个任务世界。

Resume（恢复继续）因此更接近：

~~~text
Task identity
+ persisted state
+ artifact / evidence refs
+ pending work
+ allowed execution entry
→ rebuild Context
→ new Model Invocation when needed
~~~

恢复的是责任世界，不是模型的连续意识。

## Agent Loop 不是 Durable Runtime

最小 Agent Loop 可以写成：

~~~text
while not_done:
    observation = observe()
    action = call_model(observation)
    execute(action)
~~~

它能在同一进程内持续工作，但没有回答：

- 进程退出后任务在哪里；
- 等审批时谁保存状态；
- 外部构建两小时后怎样重新唤醒；
- 谁现在拥有任务；
- 旧请求晚到以后还能不能写当前状态。

因此 Loop 解决“下一步怎样决定”，Runtime 解决“这个责任怎样持续存在”。

## Workflow、Harness、Runtime 是三类责任

~~~text
Workflow
→ 允许怎样走，哪些路径和状态转换预先存在

Harness
→ 当前这一轮怎样给模型更好的工作环境

Runtime
→ 哪个 Task 现在承担什么责任，怎样跨时间持续
~~~

它们可以实现于同一框架，但不能在心智模型里合并。

Conversation Memory 不等于持久 Task State；一个 Agent Loop 能继续调用模型，也不等于任务可以安全断线恢复。

## WAITING 是长期任务的正常状态

真实 Task 经常在等待：

- Human Approval；
- Timer；
- Webhook；
- Build / Test；
- 外部资源；
- Child Task；
- 异步 Tool。

正确状态不是让模型继续轮询，而是：

~~~text
Task = WAITING
Model Invocation ends
...
meaningful Event arrives
→ Runtime marks task runnable
→ Scheduler schedules work
→ rebuild Context
→ invoke model only if a new decision is required
~~~

长期任务的连续性因此不依赖模型常驻在线。

## Event 告诉 Runtime“发生了什么”，State 描述“现在是什么”

例如：

~~~text
BUILD_COMPLETED
= Event

build.status = SUCCEEDED
= Current State
~~~

Event 可以触发状态更新，但不能把一句事件文本无条件覆盖成真值。Runtime 应结合当前 Version、Owner 和 Transition Rule 决定它还是否适用。

Event 还可能重复、乱序或迟到。

~~~text
duplicate event
late event
out-of-order event
same event after owner changed
same event after task already terminal
~~~

因此 Event 需要稳定 Identity，State 提交需要 Version 保护。

真正目标不是假装网络“只投递一次”，而是让重复不会制造第二份业务事实。

## Parent / Child Task 只定义长期关系，不定义完整协作策略

Runtime 可以把委派表达成正式 Parent / Child Task：

~~~text
Parent Task
├─ goal / owner / state
└─ Child Task
   ├─ local goal
   ├─ owner
   ├─ status
   ├─ artifact refs
   └─ evidence refs
~~~

Child 可以使用独立 Session、模型或 Workspace。Parent 不需要常驻读取 Child 的聊天，只需要消费语义 Event，例如 CHILD_COMPLETED、BLOCKED、FAILED、NEEDS_DECISION。

这里 Runtime 只负责“这两个长期 Task 怎样存在和被唤醒”。真正什么时候值得拆 Subagent、怎样验收 Child、怎样 Handoff，由第 10 篇负责。

## Owner、Lease、Version 防止旧执行者晚到覆盖新事实

长期任务最危险的并发错误之一，是旧 Worker 已经失去责任，却仍然提交结果。

Lease（租约：在有限时间内授予某个执行者处理当前 Task Version 的权利）可以和 Version 一起约束：

~~~text
task_id
task_version
owner / worker
lease_expires_at
~~~

提交 State 时检查：

~~~text
current owner == caller
AND current version == expected version
AND lease still valid
~~~

任一条件不成立，都应该返回冲突，而不是让“最后到达的写入”覆盖当前事实。

Handoff、Reopen、Restart 都必须保留这种身份和版本连续性。

## Scheduler 先回答“能否运行”，再回答“谁先获得资源”

Scheduler 至少涉及两个层面。

Runnable Scheduling：某个 WAITING Task 的依赖满足以后，什么时候重新具备执行条件。

Resource Scheduling：已经 runnable 的任务，谁先获得模型、设备、浏览器或并发槽位。

后者会涉及：

- Priority Queue；
- concurrency limit；
- quota；
- deadline；
- fairness；
- resource lease。

“现在能不能运行”与“能运行以后谁先获得资源”不是同一判断。

## Deadline 和 Cancellation 也是正式生命周期

Cancellation（取消）不是简单杀进程，因为系统还要判断：

- 已经发出的副作用能不能撤销；
- Child Task 是否要一起取消；
- External Job 是否只能标记“不再关心”；
- 是否需要等到安全点；
- 是否必须保留 Evidence。

更可靠的状态可能是：

~~~text
RUNNING
→ CANCEL_REQUESTED
→ reach safe boundary
→ cancel child / external job when possible
→ reconcile existing effects
→ CANCELLED
~~~

对于已经发生的现实 Effect，取消只能停止后续责任，不能把过去事实抹掉。完整补偿和 Reconciliation 由第 09 篇负责。

## Router 和 Scheduler 不在同一层

Router（路由器：在允许的候选执行路径里选择模型、Tool 或责任主体）解决“选谁做”。

Scheduler 解决“什么时候得到资源”。

更清楚的链路是：

~~~text
Task metadata + risk + budget
↓
Policy filter
↓
Routing
- model / reasoning profile
- tool candidate
- agent candidate
↓
Scheduler
- queue / priority / concurrency / quota
↓
Gateway / Adapter
↓
execution result + telemetry
~~~

Policy 是允许性问题，Router 是选择问题，Scheduler 是资源问题。

## Gateway 只是调用入口，不应该长成业务上帝服务

Gateway / Adapter（网关／适配器：把统一请求合同转换成具体 Provider 或执行环境调用）通常会位于很多链路中央，所以它很容易在工程演进中不断吸收“顺手加进去”的职责。

最初只是：

~~~text
统一请求
→ Provider Adapter
→ 调用
→ 标准化结果
~~~

后来如果继续把 Task State、Plan、Tool Permission、Agent Routing、Memory、业务重试和最终 Truth 都塞进去，Gateway 很快就会变成新的中央控制单体。

位置居中不等于拥有事实。

更稳定的分工应该保持：

~~~text
Policy
→ 哪些候选允许

Router
→ 选择哪条路径

Scheduler
→ 什么时候获得资源

Gateway / Adapter
→ 怎样调用具体 Provider / Executor

Task / Domain Owner
→ 当前业务事实是否成立
~~~

Gateway 可以记录 usage、latency、error、Provider version 等 Telemetry（遥测：调用层产生的运行数据），也可以执行协议级 timeout、cancel、健康检查和基础 fallback；但它知道“一次调用成功”并不等于知道 Task 已经完成。

这条边界很重要，因为真正可替换的 Provider 层必须尽量保持薄。否则每换一个模型、设备或执行环境，都要连带迁移业务状态和权限语义。

## Routing Decision 本身也应该成为可审计对象

当 Task 从 FAST 升级到 REASON、换 Provider 或选了某个 Agent，如果只能靠日志里的自然语言猜，后续很难评估路由质量。

Routing Decision（路由决策记录：保存一次实际选择及其输入条件）至少可以记录：

~~~text
task slice
candidate set
hard filters
chosen route
reason code
budget
model / provider version
fallback / escalation trigger
~~~

它不需要保存模型隐藏思维，只需要让系统能回答：这次选择基于什么规则，后来结果怎样。

## Model Routing：模型是可分配资源，不是系统身份

一个 Task 不一定永远绑定一个模型。

Model Routing 可以根据任务类型、风险、延迟目标、成本、Context 长度和历史 Eval 选择不同模型或 Profile。

~~~text
FAST
→ 高频、低风险、可验证、低延迟任务

REASON
→ 冲突、复杂规划、高风险、低置信任务
~~~

FAST / REASON 可以对应两个模型，也可以是同一模型的不同 Reasoning Budget。稳定的是升级条件，不是物理模型名。

端侧模型实践已经证明这一点：物理模型形态可以变化，但 Runtime 仍然消费稳定逻辑 Profile。详情见 [端侧模型](../端侧模型.md)。

## Routing 不是一次写死的 heuristic，而是持续被 Outcome 校准的 Policy

Routing 很容易停留在一组看起来合理的静态规则：

~~~text
短任务 → FAST
长任务 → REASON
失败 → 换更强模型
~~~

这只能作为初始 Baseline（基线：当前最简单、可比较的默认策略），不能自动证明策略长期正确。

真正的路由质量要回到真实 Task Slice（任务切片：输入、风险和成功标准相近的一组任务）观察至少几类结果：

~~~text
task success / critical error
latency p50 / p95
total cost
tool calls / retries
human intervention
recovery quality
~~~

例如 REASON 在某类任务上更贵、更慢，却没有显著降低关键错误，就应该缩小使用范围；FAST 如果在某个高风险 Slice 反复漏错，也不能因为平均延迟漂亮就继续默认优先。

因此 Routing Policy 的正确演进是：

~~~text
initial rule
→ record Routing Decision
→ observe real Outcome
→ compare slices
→ update policy boundary
→ keep rollback path
~~~

Router 本身也需要 Eval。否则它只是把模型选择错误隐藏在系统更上游，让后面的 Agent、Tool 或 Runtime 为错误分流背锅。

这条原则也意味着：**模型更强，不自动等于应该更常用；路由复杂度只有在真实质量、成本、延迟或资源冲突出现时才值得购买。**

## Retry、Fallback、Escalation 是三种不同恢复动作

Retry：同一逻辑路径再次执行。

Fallback：换实现路径或 Provider。

Escalation：提高模型能力、验证级别、权限审查或人工介入。

~~~text
FAST confidence low
→ Escalate to REASON

cloud provider unavailable
→ Fallback to another provider

transient error + proven safe replay
→ Retry
~~~

它们都属于 Runtime 的控制动作，但涉及副作用时不能只凭传输错误直接决定。Effect 是否已发生由第 09 篇完整处理。

## Attempt、Task、Effect 不能混

一个 Task 可以经历多次 Attempt（执行尝试：同一个长期任务的一次具体运行实例）。

~~~text
Task
├─ Attempt 1 → process crash
├─ Attempt 2 → provider timeout
└─ Attempt 3 → complete
~~~

Attempt 失败不等于 Task 失败；Task Reopen 也不等于创建一个新 Task。

同样，现实 Effect 不能只挂在某次 Attempt 上。已经确认发生的副作用必须被后续 Attempt 继承为事实。

## Task Continuity 不等于 Conversation Replay

Conversation Replay 让模型知道过去说过什么。

Task Continuity 要求系统知道当前责任对象仍是谁、现在是什么状态、哪个版本、谁拥有、下一执行入口在哪里。

~~~text
Conversation Replay
= 语言上下文连续

Task Continuity
= 责任和真值连续
~~~

前者可以靠 History 和摘要；后者必须依赖持久 Task / State。

## Runtime Task 和协议里的 Task 要保留命名空间

MCP、A2A 等协议也可能定义 Task。

~~~text
Runtime Task
→ 本地长期责任、Policy、Truth、Recovery

MCP Task
→ capability invocation protocol lifecycle

A2A Task
→ remote agent collaboration lifecycle
~~~

协议对象可以映射到本地 Task，但本地 Runtime 仍然拥有自己的 Truth 和恢复规则。

## 一个长期 Task 的最小生命周期

~~~text
CREATED
  ↓
RUNNABLE
  ↓
RUNNING
  ├─→ WAITING ──event──→ RUNNABLE
  ├─→ FAILED ──reopen / recovery──→ RUNNABLE
  ├─→ CANCEL_REQUESTED → CANCELLED
  └─→ VERIFYING → SUCCEEDED
~~~

不同系统的枚举会变化，但等待、失败、取消、恢复和验证都应该成为正式生命周期，而不是几条聊天说明。

## Runtime 最终拥有的几条边界

Agent Loop 负责根据 Observation 选择下一步；Runtime 负责长期 Task 的 Identity、Status、Owner、Event、Routing、Scheduling 和 Continuity。

Router 选路径，Scheduler 分配资源。

Attempt 是一次运行，Task 是长期责任。

Event 可以重复和乱序，所以 State 提交需要 Version。

Owner / Lease 防止旧 Worker 晚到写入。

Cancellation 结束后续责任，却不能假装已经发生的副作用不存在。

这几条边界一旦建立，模型调用可以结束、Session 可以更换，Task 仍然能继续。下一篇进入 Runtime 的信息世界：**哪些信息是当前真值，哪些只是历史，哪些值得记忆，哪些应该进入这一轮 Context。**
