# 把整套 AI 工程知识放回真实系统和真实岗位

前面的文章从 Transformer 一直讲到 Platform，如果只停在概念层，很容易形成一种错觉：好像现代 AI 工程就是把 RAG、Agent、Memory、MCP、Multi-Agent、Eval 这些模块按图拼齐。

真正的工程判断必须被现实反向校验：**真实系统到底是被什么失败逼着升级的，真实岗位到底要求工程师为哪段 Outcome 负责。**

这篇用几条已经实践过的链路把整套知识重新收回来。公开岗位样本在这里仅作为外部 Reality Check：它帮助观察市场实际在为哪些工程责任付费，但不拥有技术结论。

## ProFlow 最有价值的不是“用了 Agent”，而是每一层都有真实升级理由

ProFlow 可以被看作 Architecture Laboratory（架构实验场：用持续演进的真实系统检验每一项抽象是否有必要）。

它的演进大致是：

~~~text
Workflow / Task Graph
→ durable Task / Node / Event
→ execution truth / recovery
→ Browser Carrier / reality evidence
→ Role / Worker binding
→ FAST / REASON model policy
→ Platform Host / module lifecycle
~~~

这条路线没有从一开始就以“Agent Platform”为目标，而是每一次真实失败才增加新的正式责任。

## 第一阶段：Workflow 先把业务路径说清楚

任务可以拆成 Node、Dependency、Input/Output 时，固定 Task Graph 比开放 Agent 更自然。

模型只处理局部模糊工作，路径和合法状态由软件拥有。

这对应前文的基本原则：确定路径不需要为了 Agentic 而交给模型。

## 第二阶段：Chat 不能继续承载 Task Truth

当任务跨 Conversation、Process、人工等待继续时，必须把 Task/Node Status、Version、Current Node、Role Binding、Document Metadata、Event 和 Execution History 移到持久状态。

这验证了：

~~~text
conversation continuity
≠ task continuity
~~~

模型可以重建 Context，关键 State 不能只从聊天摘要猜。

## 第三阶段：Execution Truth 出现以后，Timeout 不能再当普通错误

Browser 提交、创建资源、部署等动作可能已经发生，只是响应丢失。

ProFlow 因而需要：

- Idempotency；
- Effect Boundary；
- Artifact identity；
- lost-response reconciliation；
- UNKNOWN reality verification；
- restart without blind replay。

这正是 Durable Execution 章节的现实来源。

## 第四阶段：Browser Carrier 证明环境能力不属于模型本体

真实 ChatGPT / Browser 页面里的 Conversation create/restore/wake、DOM submit、permission interaction 和 physical delivery 需要一个真正执行环境。

Browser Carrier / Adapter 可以承担页面动作和 Readback，但不应该成为 Task Truth Owner 或全局 Scheduler。

模型提出动作、Runtime 调度、Carrier 执行、现实回读——这四层必须分开。

## 第五阶段：Role / Worker Binding 让身份从“名字”变成正式事实

同一个 Role 可以对应具体 Worker / Conversation。不能每次根据角色名猜目标页面。

持久 Binding 解决：

~~~text
Task / Role
→ which Worker
→ which Conversation / runtime identity
~~~

同值重复绑定可以幂等，异值冲突必须显式处理。

这说明多角色系统最先需要的往往不是动态 Discovery，而是稳定 Identity。

## 第六阶段：FAST / REASON 证明模型只是 Policy 可分配的计算资源

低成本高频判断和复杂异常诊断不应该默认使用同样预算。

ProFlow / 端侧模型路线都形成了：

~~~text
Policy hard rule
> model suggestion

FAST
→ common bounded decisions

REASON
→ conflict / ambiguity / complex diagnosis
~~~

模型可以建议，不能覆盖 Mandatory Approval 和硬 Policy。

## 第七阶段：Platform Host 只抽真正重复的生命周期责任

多个 Runtime 模块反复出现安装、发现、依赖顺序、生命周期和共享基础设施问题以后，Host/CLI 才开始有共享价值。

它们负责装配和 Lifecycle，不应该吞掉 Task Runtime 或领域包内部 Truth。

这正是 Platformization 的正确姿势：共享重复责任，而不是集中所有业务状态。

更完整的 ProFlow 演进见 [ProFlow 知识库](../ProFlow/README.md)。

## 云端 Agent 访问本地知识：最重要的是窄 Capability，而不是“把本机接上云”

如果云端模型需要回答“我本机仓库当前实现是什么”，最危险的设计是直接给它任意 Filesystem / Shell 权限。

更合理的边界是：

~~~text
Cloud interaction
↓
public ingress / tunnel
↓
Agent Gateway
- auth
- capability allowlist
- scope
- rate / result limits
↓
Local Retrieval Runtime
- Vector
- Keyword
- CodeGraph
- Git
- SQL
↓
authoritative local sources
↑
minimum sufficient evidence + provenance
~~~

Tunnel 只解决 Reachability，不拥有 Auth、Permission 或 Retrieval Truth。

云端表达高层意图，例如 search_project_knowledge(query, scope, version)，本地 Runtime 决定真正走哪种 Retriever。

这条边界把 RAG、Tool、Security 和 Local Runtime 连接成一条现实链。

## 上传 Knowledge 为什么不能替代动态本地 Truth

静态上传文件适合稳定参考资料，但本地 Git、Database、Task State 会持续变化。

动态事实必须请求时回到权威系统，并保留 Source、Version、Timestamp 和 Evidence。

Vector Index 也不能因为方便查询就升级成 Source of Truth。

## 端云协同：真正难的是资源和责任，而不是争论“本地还是云更强”

端侧模型可以降低网络依赖、保护本地数据、支持离线和高频低成本请求；云模型拥有更强算力和开放知识。

合理分工常见为：

~~~text
Controller / Cloud Runtime
→ owns Task / Policy / global routing / truth commit

Edge Provider
→ owns model loading / inference / device health / local queue / telemetry
~~~

端侧一次只能稳定运行一个模型时，系统需要 Priority Queue、Lease、Aging、Cancellation，而不是创建更多 Agent 假装并发。

Provider 返回的模型结果也不直接改变业务 State。

## 真实 iPhone 实验把“端侧智能节点”收敛成了推理节点

端侧模型路线最初设想过一个手机 App + 多角色 Agent。真实实验逐步发现：

- Context 理论容量不等于生产预算；
- 图片简单探针不等于真实任务延迟；
- 原生 Tool Protocol 失败不等于模型没有工具语义能力；
- 模型判断正确不等于获得权限；
- 异模型并发会争用设备；
- 锁屏/后台生命周期影响可用性；
- Harness 自身也可能制造假红灯。

最终手机被放回正确位置：受 Runtime 管理的 Model Provider，只负责推理，不拥有 Task、Permission 和真实 Effect。

这个过程完整记录在 [端侧模型](../工程工具与运行时/端侧模型.md)。

## ProFlow-RAG 证明 RAG 的核心不是向量库

ProFlow-RAG 把 Knowledge Version、Hybrid Retrieval、Rerank、Evidence、Context、Citation、Eval 做成独立 Capability Service。

这说明真正可复用的是检索和证据合同，而不是“某个 UI 里加一个 RAG 开关”。

当前更完整的过程见 [ProFlow-RAG](../ProFlow-RAG/README.md)。

## ChatWeb 则提醒：产品边界不应该被平台野心吞掉

ChatWeb 的核心是通用 Chat Product Shell / Runtime：Conversation、Streaming、Provider、RAG Context、Citation、Web Search、Thinking、File/Vision/Voice。

它没有因为工作区里存在 ProFlow，就必须拥有同一套长期 Task Control Plane。

产品只有在真实用户语义出现 Background Task、WAITING、Resume、长期 Agent 时，才应该购买对应复杂度。

这验证了“共享工具和知识，不代表所有产品共享同一种业务 Runtime”。

可继续读 [ChatWeb](../ChatWeb/README.md)。

## 本机 Agent 工具链把 Fact Owner 变成了日常工程方法

真实工程里不同事实有不同 Owner：

~~~text
Local Dev
→ current files / git / shell / process reality

CodeGraph
→ symbol / caller / dependency / blast radius

Repomix
→ broad repository snapshot / wide audit

Browser automation
→ visible DOM / user-facing reality
~~~

工具增加不是为了“能力数量”，而是不同事实反复需要不同权威入口。

再把稳定方法放进 Skill，把稳定机械动作下沉 Automation，模型就可以把 Token 留给真正的判断。

完整过程见 [本机 Agent 工具链](../工程工具与运行时/本机Agent工具链.md)。

## 真实岗位也在要求这些责任，而不是只招聘“会 Prompt 的人”

历史 Job Search corpus 在 2026-08-22～23 收集职位；2026-09-03 的重新查询口径中，LIVE_DISCOVERY + LISTED 有 261 条去重职位，其中 19 条有 JD 正文、18 条正文不少于 200 字、13 条不少于 500 字。

这个样本很小、时间窗口也有限，不能推导整个市场占比，但足以观察真实责任组合。

JD 中反复出现的不是单一“Agent”词，而是一整段工程责任：

- AI Application / Vertical Product；
- Coding Agent / Developer Tools；
- Agent Runtime / Platform；
- AI Full-stack / Product Engineering；
- FDE / Solutions Delivery；
- Model / Inference Infrastructure。

同时反复要求传统工程主干：前后端、API、Database、CI/CD、Container、Auth、Observability、Deployment。

AI 没有让软件工程消失。

## 岗位标题噪声很大，Primary Ownership 更稳定

同样叫 AI Engineer，可能一个负责业务应用，另一个负责 Runtime；相反，不同标题的岗位又可能承担非常接近的责任。

更可靠的 Job Family 判断是看 Primary Ownership（主要责任）：失败时，这个人必须把哪一段系统收口。

### AI Application Engineer

主要对一个业务 AI Outcome 负责：Prompt/Context、RAG、Tool、Workflow、产品交互、Domain Eval、上线迭代。

### Agent Engineer

主要对动态决策和可靠行动闭环负责：Agent Loop、Tool/Skill、Harness、State/Memory、Recovery、Trajectory Eval、必要时 Multi-Agent。

### AI Full-stack Engineer

主要对 UI → Backend → Data → Model/Tool → Deployment 的端到端产品交付负责。

### AI Platform Engineer

主要对多个应用共享的 Gateway、Knowledge/Capability、Runtime、Identity/Policy、Eval、Multi-tenancy 和 Reliability 负责。

### FDE / Solutions

更靠近客户现场：需求澄清、系统集成、认证权限、数据边界、上线验收和组织协作。

### Model / Inference Infrastructure

主要拥有训练/Serving、GPU、分布式、吞吐、推理性能和模型生命周期。

这些岗位能力会交叉，真正边界看 Ownership，不看名字。

## 传统软件工程背景怎样扩展到 AI 工程责任

进入 AI 工程不意味着把已有的软件工程能力清零。

前端、后端、全栈、基础设施等背景已经积累的产品理解、状态管理、API、数据、工程化、浏览器、部署和可靠性能力，都会继续存在。需要补的是概率模型带来的新责任，以及从局部模块扩大到完整 Outcome 的 Ownership。

一个常见扩展路径是：

~~~text
UI / product interaction
→ HTTP / API
→ service / database / queue / auth
→ RAG / Tool / Agent
→ Runtime / Eval / Observability
→ Deployment / Reliability
~~~

重点不是把每个人都训练成模型研究员，而是让已有工程能力能够接住模型进入产品以后新增的 Context、Tool、State、Recovery 和 Eval。

## JD 更适合做责任需求证据，而不是事实来源

JD（职位描述）能告诉我们市场当前希望某类岗位承担什么责任，但它不能反向创造个人经历，也不能证明某项技术在所有公司都同样重要。

更合理的映射链是：

~~~text
JD sentence
→ responsibility
→ system layer
→ required capability
→ current evidence / gap
→ learning or implementation action
→ verifiable project proof
~~~

例如 JD 写 RAG、Kubernetes，只能说明该岗位把这些能力列为要求之一。是否真的具备，仍然必须回到真实项目、运行结果和可验证产物。

## Capability Gap 要改写成能产出 Evidence 的工程任务

弱目标：

> 学习 RAG。

更强的目标：

> 实现 Vector + Keyword + Git/CodeGraph 的多路检索；建立真实 Query Set；按 Recall、Rerank、Citation Freshness 和 Failure Slice 评估。

弱目标：

> 学后端。

更强的目标：

> 实现带 Auth、Queue、Idempotency、Observability 的 Node/Python Service，部署并记录 SLO 与 Recovery Evidence。

真正的 Capability（能力）不是“看过这个术语”，而是能够在受约束场景里完成实现，并产出可重新检查的 Artifact、Evidence 和 Outcome。

## 项目 Evidence 也有强弱层级

可以继续沿用：

~~~text
learning note
< toy demo
< tested project
< integrated environment
< real user / business outcome
~~~

每一层只能证明自己的责任边界。

Package Test 不应该包装成生产能力，设计方案也不能包装成已经落地；一个真实用户 Outcome 也不能自动证明所有底层机制都已经通用化。

这和前文的 Evidence Ladder 是同一条纪律：**结论强度不能超过证据强度。**

## 术语最终必须落回责任—机制—证据

真正掌握一个 AI 工程概念，不能停在“知道定义”。

至少要能建立三层：

第一层：它解决什么真实问题。

第二层：机制怎样工作，它和相邻概念的边界是什么，例如 Runtime ≠ Harness、Memory ≠ State、Tool Success ≠ Outcome。

第三层：什么 Evidence 能证明这套机制真的成立，失败时又会在哪个 Owner 暴露。

以“为什么 Task State 不能放聊天里”为例，答案不是背一句定义，而是能够解释：

> Session 是沟通容器，Task 是跨时间责任。ProFlow 的任务需要跨浏览器会话、失败、等待和 Reopen；如果当前 Status、Version、Worker Binding 只留在聊天，重启以后无法判断 Current Truth。因此关键 State 进入正式 Runtime，Conversation 只提供上下文。

这种“问题—机制—证据”结构，才是知识从术语变成工程判断的标志。

## 把 17 篇最后压成一套责任地图

~~~text
Model
→ 提供概率智能计算

Knowledge / Retrieval
→ 提供外部事实和证据

Tool / Capability
→ 提供真实行动接口

Workflow / Agent
→ 决定固定路径还是动态决策

Runtime
→ 让长期 Task 持续存在

State / Context / Memory
→ 管理当前真值、本轮工作集和可复用过去

Harness
→ 让 Agent 更容易做对

Durable Execution
→ 让真实副作用可授权、可恢复、可证明

Subagent / Multi-Agent
→ 在真实独立责任出现时组织协作

Environment
→ 提供现实观察、动作和反馈

Eval / Economics
→ 判断做得对不对、稳不稳、值不值

Product / Platform
→ 把能力组成 Outcome，并只共享已经重复的责任

Small / Multi-Model
→ 把高频窄语义任务放到更合适的计算层
~~~

这张图里最重要的不是组件齐全，而是**每一种事实和控制都有清楚 Owner。**

## 现代 AI 工程最终训练的不是“知道更多名词”

如果整套学习最后只让人多记住 RAG、MCP、A2A、LoRA、Runtime，一旦生态换一轮产品，知识很快过期。

真正长期的能力是能持续问：

~~~text
当前真正的问题是什么？
哪个事实源最权威？
这一步需要概率判断还是确定性代码？
当前 Task 的长期状态由谁拥有？
模型能做和模型有权做是否分开？
真实 Effect 怎么回读？
失败以后怎样安全恢复？
复杂度比简单基线多创造了什么？
当前证据最多支持到哪个结论？
~~~

能稳定回答这些问题，一个工程师面对新的模型、协议、Agent 框架和产品，仍然能够快速找到它们在系统中的真实位置。

这也是这一整套“现代 AI 工程”最后希望建立的判断：**模型负责不确定性的智能，软件系统负责真值、边界、执行和证明；复杂度由现实购买，架构由证据校准。**
