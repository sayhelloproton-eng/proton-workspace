# 上下文工程：怎样把知识、状态和运行现实编译成 Agent 当前真正需要的输入

长任务做久以后，Agent 变差，很多时候不是模型能力突然下降，而是它开始同时看到旧计划、失败尝试、过期状态、聊天摘要、检索片段和最新现实，却没有一套机制告诉它：**哪些只是历史，哪些才是现在，哪些只对某个角色有效，哪些一旦过期就必须停止继续。**

这也是我们后来把 Context Engineering（上下文工程：决定当前这一次模型调用应该看到什么、为什么看到、相信到什么程度，以及什么时候必须重新读取现实）单独看待的原因。它比 Prompt Engineering 更上游：Prompt 解决“已经选进来的内容怎样表达”，Context Engineering 先解决“什么东西有资格进来”。

**我们的方案先说清楚。** 当前并没有把所有上下文责任做成一个万能的中央 Context Builder 服务。相反，我们让不同 Fact Owner（事实归属方：某类正式事实唯一可信来源）各自保存自己的真值，再在每次执行前按 Consumer（上下文消费方：真正需要这份输入的角色或系统）、Task、Role 和 Phase 重新编译本轮工作集。

~~~text
长期规则 / 正式知识 / Skill
        +
当前 Task / Node / Requirement / Acceptance
        +
Git / Workspace / Runtime / Browser 当前现实
        +
Permission / Approval / Evidence
        +
按需 RAG / Memory / History
        ↓
识别当前 Consumer / Role / Task / Phase
        ↓
回到各自 Owner 读取最新事实
        ↓
处理声明强度、版本、冲突、权限、敏感度、新鲜度和预算
        ↓
Context Package
面向当前角色的最小充分工作集
        ↓
Harness 叠加本轮 Tool Surface / Workspace / 最新 Observation
        ↓
Context Instance
真正进入这一次 Model Invocation 的输入
        ↓
Agent / Worker 判断与执行
        ↓
Artifact / State / Evidence 回写各自 Owner
~~~

在 ProFlow 里，这个区别非常具体。Product 需要的是 Goal、约束、当前 Product Docs、已有 Evidence 和仍未解决的问题；Dev 需要正式 Requirement、Acceptance、Scope、当前源码基线、Workspace、可用 Tool 和工程规则；Test 需要原始 Acceptance、实际 Artifact / Diff、真实 Runtime 和验证 Evidence，而不是 Dev 的“我已经做完了”摘要。出现失败或换班时，Recovery / Monitor 读取的是当前 Task、最近安全点、Effect 回执、Owner readback 和正式 Handoff，也不是把旧 Conversation 原样续上。

所以这套方案的核心不是“让模型知道更多”，而是：**稳定知识长期保存，动态事实由软件和现实拥有，本轮 Context 每次重新编译。**

## 上下文的第一个问题不是“装多少”，而是“谁拥有真值”

早期很容易把上下文问题理解成资料搜集：文档越全、聊天历史越长、RAG 命中越多，模型应该越聪明。真实运行以后我们发现，最危险的并不是缺资料，而是**多个来源同时声称自己代表当前事实**。

例如同一句“这个任务已经完成”，可能同时出现在旧 Conversation、上一班 Handoff、Runtime State、Git Commit 和浏览器页面里。它们不是同一种证据，也没有同样的决定权。

我们后来更强调按事实类型找 Owner，而不是建立一条简单的“所有来源统一排名”：

| 要判断的事实 | 应回到哪里 |
|---|---|
| Task 当前是 READY、WAITING、FAILED 还是 SUCCEEDED | Task / Runtime Owner |
| 当前代码、Branch、HEAD、文件内容 | Git / Workspace |
| Browser、外部服务或发布副作用是否真的发生 | 对应真实系统 Readback |
| Role、Requirement、Acceptance、长期规则 | 对应正式 Spec / Docs / Role Owner |
| RAG 返回的知识片段来自哪个版本 | 固定 Knowledge Snapshot / Source Citation |
| 过去讨论、偏好和经验 | History / Memory，只提供辅助信息 |

这里的关键不是“Git 永远比文档高”或“Runtime 永远比用户高”，而是**不同事实有不同 Owner**。Task 状态应该问 Task，文件现实应该问 Git，Browser submit 是否真正发生应该看 Browser Reality。遇到冲突时不能把几份文字平均一下，也不能让模型选自己最喜欢的一份；先找到拥有这类事实的来源，再决定其他材料只是解释、历史还是候选。

但找到 Owner 还不够。**同一个 Owner 里的声明也有不同事实强度。** 一篇正式文档里可能同时存在当前事实、已经接受的决策、未来目标、历史路线和工程推断；如果 Context Builder 把它们都压成“项目事实”，模型仍然会把未来设计当成当前能力。

实际编译时至少要保留下面这层语义：

| 声明性质 | Context 应怎样使用 |
|---|---|
| Current / Verified Fact | 可以作为当前判断依据，但仍受版本和 Freshness 约束 |
| Accepted Decision | 作为当前规则或方向，不能冒充已经实现 |
| Target Design | 只能表达目标，不得推导当前系统已经支持 |
| Historical / Superseded | 用来解释演进和禁止重复旧路，不作为当前执行前提 |
| Inference / Hypothesis | 提供判断线索，但需要 Evidence 或 Owner readback 才能提升事实强度 |
| Non-claim / Boundary | 明确告诉模型哪些能力不能宣称、不能假设存在 |

这使 Context 从“资料袋”变成一种同时带有 Authority（事实权威）、Provenance（来源追踪）和 Claim Strength（声明强度）的工作视图。Conversation 里即使还保留昨天的正确答案，只要 Owner 已经变化，它就只是 History；目标设计写得再完整，只要尚未验证，也不能在运行时被当成 READY。

这也是为什么 Memory（记忆）不能替代 State（当前状态）。过去经验可以提醒模型“这里曾经失败过”，但不能宣布当前 Task 仍然 FAILED；模型可以推断 Approval 可能过期，但是否仍然有效要回到真正的授权事实。

## 同一个 Task 不应该给所有角色同一份上下文

找到事实来源以后，下一步不是把所有正确事实一起塞进模型，而是问：**当前是谁在工作，他为了这一阶段真正需要什么？**

同一个 Task 中，Product、Dev、Test 的目标不同，看到的 Context 也应该不同。

Product 需要理解用户 Goal、业务约束、已有产品结果和仍未解决的 Gap，但没有必要默认加载底层构建日志和所有源码；Dev 需要已经冻结的 Requirement / Acceptance、当前 Source Baseline、允许修改的 Scope、环境和工程规则，但不应该重新从几十页 Product Conversation 推测需求；Test 要拿原始 Acceptance、当前 Artifact、运行方式和真实 Evidence 独立判断，而不是继承 Dev 的结论。

所以 Context 的完整主语更接近：

~~~text
某个 Consumer
在某个 Task / Version
以某个 Role
处于某个 Phase
位于某个 Workspace / Execution Lane
为了一个明确 Goal
在当前 Permission / Environment 下
需要哪些最小充分事实
~~~

这里还要多做两层过滤。

第一层是 Sensitivity（敏感度：某条信息是否允许进入当前消费者的工作集）。一条事实即使真实，也不代表所有角色都应该看到。Secret 不应进入 Context 正文；个人信息只在任务确实需要时以最小范围或脱敏视图进入；Reviewer 可以看到验证所需 Evidence，但不应该因为“看到了”就继承 Executor 的写权限。

第二层是执行边界。Goal、Scope、Acceptance、Permission 之外，Context 还必须保住 Output Contract（输出合同：当前角色必须交付什么）和 Stop Condition（停止条件：什么情况下必须停、等待或请求新的决定）。长 Context 压缩如果把这两类约束丢掉，模型很容易“理解了任务”却继续做超出授权的事。

我们把这件事理解成“编译”而不是“复制”。Context Source 是长期或实时事实来源；Context Package（上下文包：面向某个角色和任务阶段生成的可重建工作集）从这些来源里选择、过滤、压缩并保留引用；真正调用模型时，Harness 再叠加最新 State、Tool Result、Workspace 和 Capability，形成更短命的 Context Instance（上下文实例：这一轮模型实际看到的输入）。

~~~text
Source
正式知识 / Task / Git / Runtime / Evidence / RAG / Memory
        ↓
选择、声明强度、权限、敏感度、Freshness、Budget、Output / Stop
        ↓
Package
面向某个 Role / Task / Phase / Workspace
        ↓
叠加当前 State / Tool Result / Environment
        ↓
Instance
本次调用实际看到的内容
~~~

Package 和 Instance 都是派生产物，不应该反过来成为第二真源。它们的价值恰恰在于可以重新生成。

同样，一个 Context Instance 也不应该跨 Task、Task Version、Role、Phase、Workspace 或 Execution Lane 隐式复用。这里的 Lane 不是为了恢复旧平台里的复杂对象，而是强调一个很实际的隔离原则：如果两个执行者面对不同 Worktree、不同 Branch、不同可写范围或不同 Approval，它们就不应该共享一份默认“当前上下文”。Handoff 需要显式告诉接收方哪些事实和权限仍然有效，而不是继承发送方所有 Side Context。

这种设计也改变了 Token Budget（上下文预算）的理解。预算不是“尽量塞到窗口上限”，而是优先保护 correctness-critical 信息：Goal、Scope、当前 State、权限、Acceptance、Output Contract、Stop Condition、必要 Evidence 和最新 Reality；大量重复历史、已经有稳定引用的长正文、与当前 Role 无关的资料，优先只保留摘要或引用。

ProFlow RAG 里也验证了类似边界：Evidence Selection 先决定本次真正采用哪些知识，Context 只负责在预算内怎样表示这些 Evidence。Context 放不下，并不允许它偷偷重做一套相关性选择；否则系统就很难判断问题究竟出在 Retrieval、Evidence Selection 还是 Context Budget。

## Context 不是缓存：现实一变，旧上下文就可能失效

即使上一轮 Context 完全正确，也不表示下一轮还能继续用。

长期 Agent 最容易犯的错误，是把“曾经正确”误认为“仍然有效”。真正会让 Context 失效的，不只是文档更新，还包括 Task Version、Consumer、Role、Phase、Scope、Acceptance、Approval、Branch / HEAD、Workspace / Lane、Capability、Runtime、Evidence、Sensitivity 和外部服务现实的变化。

ProFlow 的 reopen 是一个很直观的例子。一个 Node 失败后重新执行，仍然保留相同 taskId / nodeId，但新的 runNo 表示新的执行轮次。旧 Conversation 里写着“这次已经失败”是历史事实，新一轮却必须重新读取当前 Task State、最新 Artifact、失败 Evidence 和新的允许动作。直接把旧聊天继续当本轮 Context，会同时混进两个运行世界。

Browser 也是一样。Extension reload、Tab 消失或页面刷新不应该改变长期 Role identity，但它们会改变当前控制位置和可观察 Reality。身份可以稳定，Context 里的 Locator、页面状态和 Observation 却必须重新获取。

timeout 更能说明问题。一个副作用调用超时以后，旧 Context 如果只留下“调用失败”，模型很可能自然选择重试；但 timeout 只说明没有拿到确定结果，并不证明现实没有变化。ProFlow 后来把 Effect 结果收敛为 APPLIED / NOT_APPLIED / UNKNOWN 三态，其中 UNKNOWN 必须先 Reality Reconciliation（真实结果核对：回到对应外部世界确认副作用是否已经发生），再决定能不能继续。

因此 Context Invalidation（上下文失效）不只是“重新检索一次”。更可靠的流程是：

~~~text
发现 Task / Role / Permission / Workspace / Runtime / Evidence / Source 变化
→ 停止受影响动作
→ 回到对应 Owner 获取最新事实
→ 检查声明强度、敏感度和继续条件
→ 标记旧假设和旧 Context 不再可信
→ 重新编译当前角色所需工作集
→ 只有 Output / Stop / Approval 等边界重新成立才恢复执行
~~~

这也是 Context Engineering 和缓存系统最大的区别之一：缓存追求尽量复用，Context 更关心**错误复用会不会让模型做出错误现实动作**。

## Handoff 和 Recovery 不是把旧聊天搬过去，而是重新建立工作世界

ProFlow 对 Context 最有价值的一次失败，不是“上下文太长”，反而是**上下文被压缩得太短**。

早期为了让新 Chat 快速接班，我们曾经把公共上下文收敛成很短的原则和结论。结果新 Chat 能解释架构，却没办法真正恢复执行。它缺的不是更多历史，而是五类可以直接进入现实的入口：

~~~text
EXECUTION_ENTRY
从哪里开始？

CANONICAL_ASSET
哪个脚本 / API / Tool 是稳定入口？

AUTHORITY_SOURCE
当前事实到哪里读？

RECOVERY_PATH
断连、timeout、UNKNOWN 后怎么恢复？

DO_NOT_REPEAT
哪些旧路线已经证明无效？
~~~

这促成了 Executable Project Memory（可执行项目记忆：不仅保存结论，还让失忆执行者能够恢复真实工作）。项目随后做 Lost-context Simulation（失忆上下文模拟）：故意不给新 Chat 完整历史，只给正式入口材料，看它能不能重新找到 Owner、恢复环境并继续任务。

这个实验让我们更明确：**好的 Context 不是“摘要得很漂亮”，而是新执行者在没有旧会话的情况下仍然能重新建立正确工作世界。**

因此正式 Handoff 更适合传递稳定引用和当前状态，例如 Task / Version、已完成与未完成、Artifact / Commit、Acceptance、Evidence、已发生 Side Effect、Workspace / Branch、最后安全点、下一 Goal、Output Contract 和 Stop Condition。接收方再基于这些引用读取当前 Owner，而不是继承发送方全部聊天。

这也是 Summary、State 和 Checkpoint 必须分开的原因：

~~~text
Summary
→ 压缩 History，帮助理解

State
→ 保存继续执行所需的当前真值

Checkpoint
→ 保存安全恢复所需的执行位置和引用
~~~

Monitor 换班后来进一步验证了这个思路。下一班并不依赖上一班 Conversation 永久存在，而是读取固定公共上下文、CURRENT、HANDOFF，再通过 boot proof 确认自己真的恢复到了当前运行现场。旧班交出的不是“大脑”，而是一组可以重新验证的入口。

## RAG、Knowledge Pack 和 Host Knowledge 都只是派生消费层

上下文系统还容易出现另一类双真源：同一套知识同时存在 Git、Feishu、Custom GPT Knowledge、Knowledge Pack、RAG Index 和 Runtime Context，时间一长谁都说自己是“最新版”。

旧知识系统最值得保留的一条原则是：**长期知识可以有很多消费形态，但正式知识只能有明确生产入口；下游形态应该可以删除并重新构建。**

这条原则在 ProFlow RAG 里被做得更具体。检索构建不是直接对“当前 main 目录”建索引，而是先把远端 ref 解析成 immutable commit（不可变提交），形成确定的 RepositorySnapshot，再经过 Corpus、Chunk、Embedding 和 Index 构建出 KnowledgeSnapshot。这样每次查询都能回答：这条 Evidence 到底属于哪一版知识世界。

~~~text
正式 Source
→ immutable RepositorySnapshot
→ validated KnowledgeSnapshot
→ Retrieval Candidate
→ selected Evidence
→ budgeted Context
→ Citation 回到固定源码
~~~

这里 RAG 不是 Source of Truth，它只是从确定知识快照生成可检索能力。Citation 也不是模型随手生成的链接，而是从已采用 Evidence 的身份和源码坐标派生。Context 因预算可能只表示部分 Evidence，但这不改变 Evidence 本身的来源和身份。

同样，Custom GPT Knowledge 或未来的 Role Knowledge Pack 更适合保存稳定角色参考，不应该包含实时 Task State、当前 Branch / HEAD、一次性 Approval 或最新 Browser Reality。动态事实仍然要在运行时重新注入。

派生渠道还有一个容易被忽略的边界：**“能从 Source 生成”不等于“真实渠道已经是这一版”。** 对 Feishu、Host Knowledge、Pack、RAG 等消费层，至少要能回答它是从哪个 Source Version 生成、当前渠道实际读回的内容或 Snapshot 是什么，以及 Source 更新后这份派生物是否已经重新生成。ProFlow RAG 用 immutable commit 和 ACTIVE KnowledgeSnapshot 把这件事做成了机器事实；其他渠道未必需要恢复旧版庞大的 Manifest / Projection Registry，但同样不能只靠“我刚刚发布了”的操作意图判断真实版本。

这也是为什么我们后来不再追求“所有知识渠道严格一一同步”。更简单也更可靠的关系是：

~~~text
正式 Knowledge / Source
        ↓ 固定 Source Version
按消费者派生
Feishu / Host Knowledge / Pack / RAG / Runtime View
        ↓ Readback / Snapshot / Version
确认真实消费层
        ↓
产生使用反馈
        ↓
Candidate / Review
        ↓
必要时修改正式 Source
~~~

反馈不能从下游直接反向覆盖 Source。一次模型总结、一次检索命中或一次用户纠正，都先只是 Candidate；只有经过 Evidence、Review 和正确 Owner 判断，才可能进入正式知识、Skill、Policy 或 Eval。

## 最后一次纠偏：Context Engineering 不等于先造一个 Context Platform

第一代统一平台 曾经把这套问题设计成五个完整领域：Knowledge Asset Governance、Context Compilation、Context Runtime、Distribution、Memory & Learning，并继续规划 Context Request / Package Schema、Context Instance Store、Delivery Receipt、Context Delta、Projection Registry、Knowledge Pack Publisher 和自动 Memory 晋升。

作为目标模型，它很完整；但真实实践给我们的结论和专业 Agent 资产化一样：**正确的抽象也可能做早。**

今天我们真正保留下来的，不是这些固定服务名，而是几个已经被 ProFlow、RAG 和长期工程反复验证的机制：

~~~text
事实必须有 Owner
Context 必须有明确 Consumer
声明强度不能在编译时被抹平
真实但敏感的信息也要按角色过滤
Task / Role / Workspace / Lane 不隐式串线
Package / Instance 是派生物，不是真源
动态 Reality 在执行前重新读取
Task / Permission / Source 变化可以使旧 Context 失效
Handoff / Recovery 通过稳定引用重建，而不是续用聊天
知识投影和 RAG 可以重建，但必须知道真实消费层对应哪一版 Source
Context 质量问题要能落到真正 Owner
~~~

当前没有必要为了这些原则先建立一个通用 Context Platform。ProFlow 已经用 Task / Runtime、正式项目上下文、Handoff、Browser Reality 和 Recovery 解决自己的连续性；ProFlow RAG 负责固定知识版本、Retrieval、Evidence、Context 和 Citation；Harness 在每次执行时决定当前 Context、Tool Surface、Workspace 和 Validator。它们可以共享原则，但没有必要提前共享一个巨大状态库。

Context 本身也需要 Eval。一次 Agent 失败，如果真正原因是缺了关键 State、用了旧 Source、不同 Task 串线、敏感信息暴露、权限信息丢失、RAG Evidence 正确但 Context Budget 把关键部分挤掉，就应该修 Context Assembly、Freshness、Consumer View、Redaction 或 Budget，而不是先换模型。

只有当多个真实消费者反复出现同一种 Context 编译、版本、失效和观察需求，而且各项目开始重复维护同一套机制时，通用服务才真正有了购买复杂度的理由。

所以我们现在对 Context Engineering 的定义已经很具体：

**它不是把更多信息交给模型，而是让系统在每一次判断前，都能从正确的 Owner 重新构建一个与当前角色、任务、权限和现实一致的最小工作世界。**

只要这个工作世界可以在 Conversation 消失、角色切换、Runtime 变化和失败恢复以后重新建立，Agent 才真正具备长期连续工作的基础。
