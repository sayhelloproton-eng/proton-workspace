# ProFlow RAG｜历史证据与决策档案

本文保存正式知识文章不适合展开、但未来追溯设计时仍有价值的历史 commit、实验数字、失败现场和阶段证据。它是历史证据层，不是当前 Spec；当前事实冲突时，以 `repos/proflow-rag` 的源码、Spec、数据库和 Runtime 为准。

## 1. 从项目起点到分仓

项目目标不是“做一个能聊天的 RAG Demo”，而是把公开 ProFlow `main` 变成可追溯 Knowledge Capability。早期曾把 Source Sync、Embedding、Retrieval、Rerank、Conversation 等按技术组件平铺，后来通过 DDD（领域驱动设计：按业务语义和 ownership 组织边界）收敛为 Knowledge Management、Grounded Answering、Quality & Evaluation。2026-09-06 ChatWeb 分仓后，Grounded Answering 又重基线为 RAG Query Orchestration：Answer/Conversation/Generation 移交 ChatWeb，RAG 只保留 QueryExecution→Evidence/Context/Citation。

早期上下文连续性复用了 ProFlow 的长期规则/CURRENT/Runbook/History 四层机制，但没有搬入 ProFlow 的 Deployment、Real-3、Browser 等业务专用知识。`proflow-rag@7ded602` 建立上下文机制，`c339565` 同步 CURRENT 基线。

## 2. P0｜工程骨架与工具链事实

P0 实现 commit=`a09f9e1`。当时真实环境 Node `v24.19.0`、pnpm `11.21.0`；产品只冻结 `node >=20`。Registry 实测 NestJS `12.0.1`、Fastify `5.12.1`、TypeScript `7.0.2`。

两次关键工具链纠偏：

- TypeScript 7 移除旧 `moduleResolution=node10`，从 `moduleResolution: Node` 切到现代解析后暴露更深的 ESM 边界；
- NestJS 12 package 已处在 ECMAScript Module 边界，最终采用 `module/moduleResolution=NodeNext`、workspace package `type=module`、相对 import 使用 `.js` specifier。

正式 P0 Gate：`ARCHITECTURE_GATE=PASS / typecheck=PASS / build=PASS / CONFIG_SMOKE=PASS / HEALTH_SMOKE=PASS`。

## 3. P1｜知识供应链的重要锚点

### Source / Corpus / Chunk

- P1-A implementation=`f853aea`；固定远端 ProFlow `main` 曾解析到 `c85e986b56eca8be3e5c016a14bc1470ee656d87`。
- P1-B implementation=`f073fee`；873 tree entries → 806 accepted / 67 excluded；`proflow-public-v0.2` Manifest SHA-256=`66e5c6adee6ffd7cfb8f8c3fb6070e75fe2f7e30d03c42e361c12b094077e7b2`。
- P1-C：806 docs → 7,624 chunks；Markdown=4,089、TypeScript AST=2,008、Test AST=1,131、text fallback=396、TS parser fallback=0；历史 char p50=296、p95=4,281、max=6,000。

### PostgreSQL / pgvector

历史真实运行时为 Postgres.app PostgreSQL `17.10` + pgvector `0.8.2`，数据库 `proflow_rag`。最初 migration `0001_knowledge_foundation` 建过 `knowledge / answering / quality / system` 四个逻辑 schema；后续 consolidation 才删除未使用的 `answering/quality`。

P1-D 曾发现 hydration bug：SQL `NULL` 被 Adapter 还原成 `{parentLabel: undefined, part: undefined}`，与 Domain canonical shape“缺省 key 不存在”不同。最终只修 PostgreSQL Adapter，没有改 Domain 或降低 round-trip 断言。

### Embedding 选型

手机 Generation Runtime 能稳定 chat，但 `/v1/embeddings` 不存在，说明“设备有模型”不等于“应用 Runtime 提供对应 contract”。Embedding 回到 Mac llama.cpp，Generation 仍可由手机模型承担。

EmbeddingGemma 300M Q8：768d、L2≈1，8 个真实 ProFlow Gold + hard negatives 全部 Top1。第一份社区 Q4 与 Q8 同文本 cosine 接近 0，最终确认缺 dense post-processing modules，因此作废。

正式 dense Q4_K 候选来自 `cduk/embeddinggemma-300m-GGUF-with-dense-modules`：Q4↔Q8 cosine mean=`0.9894`，8 文本 pairwise correlation=`0.998129`，固定 24 条 workload CPU time Q8=`19.55s`、Q4=`11.82s`，约降低 39.5%；文件约 318 MiB→228 MiB。

全量 tokenizer：7,624 Chunk 共 1,847,677 tokens；`<=512=6897`、`513~1024=290`、`1025~2048=400`、`>2048=37`。因此只有 0.49% 需要 Derived Index windows。早期按全部 ubatch=2048 推算约 27.8h 被废弃；分 bucket 后前三档 99.51% 估算约 6.63 CPU-hours，但明确不冒充真实 full rebuild wall-clock。

P1-E 正式候选 implementation=`8b6291e`，学习档案 baseline=`a6068e7`。

### Candidate Index

7,624 Source Chunk 最终形成 7,624 lexical rows 与 7,670 vector inputs。P1-F2 真实对比：FTS OR `Recall@10=0.30 / MRR=0.15 / p50≈550ms`；indexed exact substring `1.00 / 0.8533 / p50≈201ms`；full-query fuzzy trigram `0.60 / 0.3843 / p50≈14.7s`，后者明确拒绝。

全量 exact pgvector Top10 两轮历史 p50≈300~341ms、p95≈505~552ms，仍走 Seq Scan + Sort；没有因“有向量了”就提前加 HNSW/IVFFlat。vector heap 约 6.2MB，含 TOAST/indexes 总量约 38MB。

### Snapshot / Eval

P1-G 建立唯一 ACTIVE、READY→ACTIVE 原子切换和 direct previous rollback。P1-H 首次 RED 暴露 `DOM-KM-006` 的完整 build failure audit 缺口，新增 `0004_knowledge_ingestion_runs` 与 IngestionRun lifecycle。

P1-H 另一 RED 来自 Eval 自己：PostgreSQL `ORDER BY text` 与 JavaScript `localeCompare` canonical ordering 不同，造成 chunk-set hash 假失败。修复 Eval ordering，没有改真实知识数据。

P1 最终 baseline=`943841e0b37667ce8267b47bab31448f611eeb3e`。

## 5. P3～P6｜Evidence、Context、Citation、Capability Eval

P3 从模型层面明确 `Candidate → Evidence → Context`：Evidence Selection 不重排 relevance；Context 只表示 whole-Evidence contiguous prefix；NO_EVIDENCE 与 degradation 正交。

固定 Gold 最终推导 `maxEvidence=9 / maxPerSource=2 / maxCharacters=25748 / semanticAcceptance=NONE`。8 个 exploratory out-of-scope query 证明 RRF top1 正负分布重叠；保持所有正例时安全阈值只能拒绝 37.5% 负例，因此拒绝用 fusionScore 冒充 semantic probability。

P4 public API 允许 consumer 缩小 Context budget，但禁止修改 Retrieval/Evidence/rerank/snapshot。1-char 等不可满足预算映射为 422，而不是 NO_EVIDENCE。

P5 Citation 固定 `/blob/<commit>/<path>#Lx-Ly`，并以 contentSha256 + Evidence identity 绑定 provenance；不使用 moving `main`。

P6 13/13 public HTTP query：Evidence full Gold=100%、Context full Gold=100%、Citation correctness=100%、Snapshot/Contract consistency=100%。旧 Mac 正式 Gate API total p50=`1800.29ms`、p95=`11504.95ms`，仅作机械基线。

P6 还修过 benchmark SQL join 错误：权威关系实际是 `knowledge_snapshots → index_builds → chunk_builds → corpus_manifests → repository_snapshots`，没有为了让 Eval 通过去改生产 schema。

## 6. P7～P8｜独立 consumer 与运行时

P7 真实链路：`ChatWeb Runtime → ProFlowRagHttpContextProvider → /v1/rag/query → Context/Citation → Model fixture`。ChatWeb S5 22/22 PASS，zero-RAG / required / optional unavailable / required fail-closed 全通过，Knowledge DB read-only。

历史 paired measurement 约 RAG core 4298ms、HTTP 4447ms、Chat→Model 4648ms，consumer overhead≈201ms。此前用两个独立 run 相减曾出现负 overhead，被明确作废并改 transparent proxy paired measurement。

P8 建立 public readiness 与 repository-owned API lifecycle。一次 Local Dev connector 502 后，使用持久 exit/log 证明 targeted typecheck/build/runtime scenes 已 PASS，没有盲重跑。Formal Gate 又曾被旧 P6 Eval 30s startup harness 假阴性阻塞，最终只把 Eval overall deadline 调到 90s，不修改 P8 产品逻辑。

P8 吞吐样本：initial blast radius=23 files，final semantic implementation=24，DCR≈95.8%，implementation mutation calls=3，Mutation Density≈8 files/call，batch retry=0。

## 7. V0 与 Post-V0 consolidation

V0 fresh 视角发现缺正式 Knowledge operator，于是建立 `knowledge:rebuild`。首次 `pnpm knowledge:rebuild run ...` 因 pnpm 前导 `--` 被 parser 误当 command，在 DB mutation 前失败；只修 CLI parser 后继续。

正式 operator 在当前 ACTIVE commit 上跑出 806 docs / 7,624 chunks / 7,670 embeddings / pending=0，复用 COMPLETE index，不带 `--activate` 时 ACTIVE 不变。

一次机器重启让 `/tmp` Gate evidence、PID、进程同时消失，严格裁决 `EXTERNALLY_INTERRUPTED / UNKNOWN`，没有猜 PASS/FAIL。恢复 Postgres.app PG17 原 cluster 后，Gate evidence 改到 `.runtime/release`。

历史 V0 public RAG Eval mechanical latency p50=`1347.88ms`、p95/max=`1712.56ms`；paired ChatWeb consumer overhead≈151.24ms。Post-V0 consolidation 后一次 paired overhead≈257ms，均只作为当时机器观测值。

Consolidation 最终把 live apps 收到只有 `api`，真实 DB schema 收到 `knowledge + system`；空 `answering/quality` 通过 `0005/0006` 无 `CASCADE` migration 删除。新增正式 `knowledge:rollback`，只允许 previous successful snapshot。`verify:consolidation` durable Gate exit 0，real E2E 与 DB read-only 继续 PASS。

## 8. 长期保留的反例

这些失败比“最终 PASS”更值得长期保留：

- 模型文件名相似不代表 embedding space 相同；
- `/v1/embeddings` 的 model echo 不代表 Runtime identity；
- Eval 可以发现生产缺口，也可以自己写错 ordering/SQL；
- Reranker 单例质量提升不代表持续 workload 值得默认开启；
- Consumer 复制 Provider policy 会制造跨仓双真源；
- Runtime 端口活着不代表 capability ready；
- timeout、connector 断开、机器重启首先产生 UNKNOWN，需要恢复事实而不是盲重试；
- “V0 已通过”不等于 live tree、数据库和维护入口已经适合长期运行。
