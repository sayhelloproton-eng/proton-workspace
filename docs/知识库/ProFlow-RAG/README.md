# ProFlow RAG｜把持续变化的代码仓库变成可追溯知识能力

ProFlow RAG 是一个独立的 RAG（Retrieval-Augmented Generation，检索增强生成：先从受控知识源找到证据，再交给上层模型使用）能力服务。这个项目真正难的地方不在“接一个向量数据库”，而在于同时回答四个工程问题：知识来自哪个确定版本、为什么会检索到它、模型实际拿到了什么、最终引用能不能回到原始源码。

如果第一次接触这个项目，可以先抓住一条主线：**固定源码版本 → 可重复地构建知识 → 组合关键词和语义检索 → 从候选中形成证据 → 在预算内组织上下文 → 生成可追溯引用 → 通过稳定 API 给其他产品消费。** ChatWeb 可以使用它，但 ProFlow RAG 不拥有聊天会话、回答生成或最终 UI。

这组文章不是项目 Spec（正式设计规范）的镜像，也不是按内部阶段编号重放开发流水账。当前设计、代码和运行事实仍以产品仓库 `repos/proflow-rag` 中的 Spec、源码、测试、数据库和 Runtime（运行时实际状态）为准；这里保留跨版本仍值得理解的工程判断、机制、实验和失败证据。

## 为什么正文要保留过程，而不只保留最后答案

很多稳定设计都是被真实问题“逼”出来的。如果只留下最后的参数和架构，读者能看到答案，却看不到为什么这个答案可信。因此正文会保留**改变设计方向的关键过程**：例如精确工程词怎样暴露纯全文检索的缺口、错误的模型身份判断怎样被真实 Runtime 证伪、重排序模型怎样从“单例有效”走到“持续负载默认关闭”、HTTP smoke 的误报怎样被定位为 Harness（验收夹具）问题，以及 rebuild / activate / rollback 怎样从内部能力变成正式维护入口。

这里不重放每个阶段的任务清单。更细的时间线、commit、失败现场和旧路线统一放进[历史证据与决策档案](./历史证据与决策档案.md)。正文只保留那些**如果删掉，读者就无法理解当前设计为什么长成这样**的转折。

## 先看懂这条链，再按问题深入

系统先用 `RepositorySnapshot`（源码快照：固定到不可变 Git commit 的原料版本）锁住输入，再生成 `KnowledgeSnapshot`（知识快照：经过构建、验证后可被查询的一版知识成品）。中间的 `Corpus Policy`（语料准入规则）、`Manifest`（构建清单）和 `Chunk`（带源码身份的知识片段）负责让“索引里到底有什么”可重复、可审计。

```text
Git 源码
  ↓ 固定不可变 commit
RepositorySnapshot
  ↓ 语料准入 / 构建清单
Document → Structure-aware Chunk（按文档或代码结构切分）
  ↓ PostgreSQL + pgvector
关键词索引 + 向量索引
  ↓
Hybrid Retrieval（混合检索）
  ↓ RRF 融合 + 可选重排序
Evidence（本次真正采用的证据）
  ↓
Context（实际交给上层模型的受预算文本）
  ↓
Citation（可回到固定源码位置的引用）
  ↓
POST /v1/rag/query
  ↓
ChatWeb / 其他消费者
```

## 这套设计最值得关注的不是组件数量，而是事实边界

贯穿整个系统的核心是 `Fact Owner`（事实归属方：某类事实唯一可信的来源）。源码版本由源码快照负责，知识成品由知识快照负责，检索层只产出候选，证据层决定本次真正采用什么，上下文层只负责预算内表示，引用层只从已采用证据投影来源。任何一层都不能为了方便偷偷改写另一层的事实。

这种拆分让故障可以被定位，而不是统一归因成“RAG 效果不好”：召回错了看检索，证据选错了看选择策略，预算截掉关键内容看上下文策略，链接漂移则看引用与来源身份。

## 当前稳定边界

ProFlow RAG 当前是 headless service（无独立最终用户界面的后端能力服务）。Generation（回答生成）、Conversation（聊天会话）、Streaming（流式输出）、Tool/MCP 和 Public Chat UI 都不属于它；消费者只通过公开 RAG API 获取上下文和引用。

当前知识体系覆盖知识重建、混合检索、Evidence / Context / Citation、质量评测、运行状态和维护机制，但“此刻部署的是哪个版本、服务是否正在运行”等即时事实仍必须回到项目仓库和真实 Runtime 确认。
