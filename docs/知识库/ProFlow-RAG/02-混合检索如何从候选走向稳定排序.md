# 混合检索如何从候选走向稳定排序

固定知识版本以后，下一问才是：一次自然语言 Query（查询）怎样从 7,624 个 Source Chunk（带源码身份的原始知识片段）中找到真正有用的候选？这条检索链不是一开始就设计成“关键词 + 向量 + RRF”。它先从工程词召回的失败里发现纯全文检索不够，再引入语义向量；随后又遇到两种分数无法直接比较的问题，才采用 RRF（Reciprocal Rank Fusion，倒数排名融合：只根据各检索器内部名次形成统一排序）。最后，重排序模型和 Runtime 身份校验又分别通过真实实验补上边界。

这段演进比最后那三个参数更重要，因为它说明每一层为什么存在：**词法检索负责精确工程信号，向量检索负责语义相似，RRF 只融合名次；可用性问题可以降级，身份和数据一致性问题不能降级。**

## 在线查询为什么必须先固定一个 Snapshot

`KnowledgeReadContract` 是 Query 对 Knowledge 的只读 Published Contract（发布契约：一个领域允许另一个领域稳定依赖的最小接口）。一次 `QueryExecution`（一次查询执行）开始时先取得当前 ACTIVE Snapshot（当前在线知识快照），此后词法检索、向量检索和 `getChunks` 都显式携带同一个 `snapshotId`。

这样即使后台在请求中途激活新 Snapshot，本次请求仍然读完原版本。新请求只能从新的 ACTIVE 开始，已经固定的旧 Snapshot 即使变成 RETIRED 也允许继续读。这个规则把“能否开始新请求”和“已开始请求能否完成”分开了。

## 精确工程词先暴露了纯全文检索的缺口

早期词法检索实验里，单纯 FTS OR-term（全文检索 OR 词项）在 10 个工程 Gold case（预先确认正确来源的评测题）上只有 `Recall@10=0.30 / MRR=0.15`。对 path、CLI、symbol、error 等保留 exact term（精确字符串），走 trigram indexed substring（三元组索引子串匹配）后达到 `Recall@10=1.00 / MRR=0.8533`。

反过来，把整句自然语言 Query 做 fuzzy trigram（模糊三元组匹配）只有 `Recall@10=0.60 / MRR=0.3843`，而且延迟显著更高。这次实验没有得出“trigram 更强”，而是把职责分清了：**trigram 适合工程精确字符串，不适合冒充自然语言语义检索。**

后来统一 13-case Eval（13 题固定评测）又抓到一次真实回归：在线 Query 层最初只接了 FTS OR，导致 lexical Recall@10 只有 `0.1538`，与此前已经验证的 Exact Engineering Recall@10=`1.0` 冲突。修复不是给 benchmark 喂答案，而是把路径、camelCase、`Module.status`、`PACKAGE_JSON_INVALID`、`release:publish`、`workspace:^` 等 engineering signal（工程精确信号）重新送进真实 read path。修复后整体 lexical Recall@10=`0.6923`，Exact Engineering 子集恢复为 `1.0`。

## 为什么 Lexical 和 Vector 的分数不能直接相加

引入 Vector（向量检索：利用语义相似度找候选）以后，新的问题不是“有没有第二路结果”，而是两路分数没有共同尺度：全文检索 score 通常越大越相关，cosine distance（余弦距离）越小越相似，数值含义也不同。直接归一化再相加会制造一个看似统一、实际缺乏稳定语义的综合分。

因此 `Hybrid Candidate Pool`（混合候选池：合并两路命中的同一 Source Chunk，同时保留各自证据）只保存：

```text
snapshotId / chunkId
lexical? { rank, score }
vector?  { rank, distance, windowOrdinal }
```

它先解决“候选集合”和“证据不丢失”，不提前伪造全局 relevance score（相关性分数）。

## RRF 为什么只相信名次

RRF 的核心公式是：

```text
fusionScore(chunk) = Σ 1 / (k + branchRank)
```

它不读取 lexical 原始 score，也不读取 vector distance 的绝对尺度。项目专门把两路原始数值改成相反极值但保持 rank 不变，最终 RRF 顺序完全不变，机械证明实现依赖的是名次而不是异量纲分数。

13-case sweep（参数扫描）比较 branch depth 5/10/20 与 `k=10/30/60/100`。`d5/k10` 的 MRR=`0.6692` 看起来更高，但 Recall@10 只有 `0.9231`，会漏 Gold；depth20 才达到 Recall@10=`1.0`。在 full-coverage（完整召回）组里 `k=30` 的 MRR=`0.6581` 最好，所以首个稳定版本冻结为：

```text
lexicalLimit = 20
vectorLimit  = 20
rrfK         = 30
rerankDefaultEnabled = false
```

这次取舍留下的原则是：**先保证召回完整，再优化排序。**

## Query Embedding 的身份为什么也要从一次错误判断里修正

在线 Vector Query 需要把用户文本变成 Embedding（向量表示：把文本映射到可比较的语义坐标）。一个早期 guard（身份保护）用 `/v1/embeddings` response 里的 `model` 字段判断实际加载模型，后来实测 llama.cpp 会回显请求中的 model，因此这个字段不能证明 Runtime 真正加载了什么。

最终改成读取 `/v1/models` 的权威状态，再与固定 Snapshot 的 `EmbeddingProfile`（向量空间配置身份）对齐。这里的通用经验是：**request echo（请求回显）不是 Runtime identity（运行时真实身份）。** 同维度错误模型如果静默进入向量空间，比一次显式 503 更危险。

## Reranker 为什么从“看起来有效”走到默认关闭

Reranker（重排序模型：只对有限候选做更细的 query-document 相关性判断）在单个案例上确实能纠正 RRF 噪声，但旧 Intel Mac 的真实成本很高。

候选实验里：Qwen3-Reranker Q8 三文档约 `57.53s`，质量正确但无法在线使用；Q4 约 `11.65s`，却把无关 cooking 文档排第一；BGE-Reranker-v2-M3 Q4_K_M sanity（基础正确性检查）约 `5.51s`，成为可验证候选。进一步 workload（持续负载）显示 `2×200 chars≈4.55s`、`3×200≈6.33s`、`3×300≈9.02s`、`3×600≈22.50s`。

到了最终 13-case operational A/B（真实运行条件下的对比），给 rerank 15 秒评测 ceiling（上限），13/13 都 timeout 并完整回退原 RRF 顺序。于是系统没有删除 `RerankPort`，而是冻结为 **capability available, default OFF（能力保留、默认关闭）**。以后硬件或模型变化可以重新 A/B，不需要重写 Retrieval 架构。

## 失败时为什么有的能降级，有的必须停

Embedding timeout 或暂时不可用时，可以显式降级为 `DEGRADED_LEXICAL_ONLY`；但 model/profile/dimension/normalization mismatch（模型、配置、维度或归一化不一致）属于一致性错误，必须 fail closed（失败即停止，不带着不可信事实继续运行）。

最终形成的边界不是“尽量返回结果”，而是：**可用性故障可以降级，身份与数据一致性故障不能降级。** 这也是整条检索链经过多轮真实问题后留下的稳定原则。
