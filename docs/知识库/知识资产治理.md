# 知识资产治理：怎样让长期知识可信、可修订、可发布、可退役

一个工程知识库最容易出现两种极端。

第一种是“什么都记”：聊天结论、调试日志、临时方案、正式设计、历史事实全部堆在一起，几年以后谁也不知道哪一句仍然成立。第二种是“什么都治理”：给每篇文档建立 ID、Registry、关系图、发布状态、渠道映射和自动生命周期，结果维护治理系统的成本比知识本身还高。

旧 ai-agent-platform 两边都碰过。它一度设计了完整的 Knowledge Asset、Claim、Evidence、Registry、Publication Eligibility、Supersession 和 Projection；这些问题确实存在，但后来的实践也证明，不需要为了拥有这些边界就同时拥有一套重型知识平台。

现在我们的做法更简单：**本地材料允许自然积累，成熟主题才提炼成正式 Owner；正式知识中的重要 Claim 必须说清楚“这是什么性质的声明、为什么可信、当前是否仍成立”；需要给 Feishu、RAG、Host 或 Agent 使用时再从正式 Source 派生，而不是维护多套平行真源。**

~~~text
研究 / Chat / 实验 / 项目材料 / 真实故障
        ↓
识别稳定问题和 Candidate
        ↓
Claim 分类
当前事实 / 已接受决策 / 目标设计 / 历史 / 推断 / 未知
        ↓
回到 Source / Code / Test / Runtime / Evidence 核对
        ↓
确定唯一正式 Owner
        ↓
Review / 重写 / 去重 / 边界校准
        ↓
Git 管理的正式知识
        ↓
需要时固定 Source Version
        ↓
Feishu / RAG / Host Knowledge / Context 等派生消费层
        ↓
真实使用反馈
        ↓
Candidate / Evidence
        └──────────────→ 修订、取代或退役正式知识
~~~

这套机制的目标不是让文档“看起来更规范”，而是让几年后的自己、另一个 Agent 或一个外部读者仍然能回答：**这句话为什么能信、信到什么范围、如果现实变了应该改哪里。**

## 一篇文档不是一个事实，真正需要治理的是里面的 Claim

知识治理如果只管理“文件存在不存在”，很容易漏掉最重要的问题：同一篇文章里可能同时存在已经验证的当前事实、已经接受但尚未实现的设计、历史路线和作者推断。

因此真正需要区分的是 Claim（声明：文章中希望读者相信的一条事实、决策或判断）。

我们目前保留下面这组最有用的事实强度：

| Claim 类型 | 含义 | 使用边界 |
|---|---|---|
| Verified / Current Fact | 已由代码、测试、运行现实或可回读证据支持 | 可以支撑当前判断，但要绑定版本和时间 |
| Accepted Decision | 已正式确认的方向或规则 | 可以约束后续工作，不能冒充“已实现” |
| Target Design | 目标方案或下一阶段设计 | 用来解释方向，不得写成当前能力 |
| Historical / Superseded | 过去曾经成立、后来被替代的路线 | 用来解释演进和避免重走旧路 |
| Engineering Inference | 基于已有 Evidence 的工程判断 | 可以指导调查，但事实强度低于直接证据 |
| Open Hypothesis | 尚需实验验证的问题 | 不能进入正式结论 |
| Non-claim / Boundary | 明确不能宣称的能力或范围 | 防止读者和 Agent 自动补全不存在的事实 |

这个区分在长期 Agent 系统里尤其重要。旧文档写着“未来需要通用 Context Builder”，如果不保留 Target Design 标签，下一班 Agent 很容易把它当成“已经存在一个 Context Builder 服务”；一篇历史复盘写着“当时使用方案 A”，也不能覆盖当前源码已经迁到方案 B。

**知识可信不是“这句话写在正式文档里”，而是“这句话的事实强度和证据范围没有被写作过程抹掉”。**

## 正式知识不是从聊天里复制出来，而是从原始材料中提炼出唯一 Owner

我们现在不要求每一份本地材料都立刻登记成正式资产。研究笔记、过程记录、实验材料、聊天、旧设计和项目日志可以先自然积累；只有当一个问题已经反复出现、形成稳定判断，并且值得让未来的人或 Agent 直接复用时，才进入正式知识。

处理已经被新 Owner 接管的旧材料时，我们不会按旧文档数量逐篇搬家，而是先问：

~~~text
这个问题现在有没有正式 Owner？
→ 有：不复制，吸收到当前 Owner 或删除重复材料

旧文里有没有独有稳定判断？
→ 有：吸收到正确 Owner

哪些只是当时的平台 Schema / Catalog / Registry？
→ 没有真实消费者证明：退休

剩余内容能不能被一篇新文连贯解释？
→ 不能：拆成新的独立 Owner
~~~

于是 Context Compilation、Invalidation、Handoff / Recovery 进入《上下文工程》；知识 Claim、Evidence、修订、发布和退役则由本文承担。旧文档数量不再决定新知识结构。

一篇成熟正式知识至少要能回答：

~~~text
它解决什么稳定问题？
谁是当前 Owner？
哪些重要 Claim 属于什么事实强度？
主要 Source / Evidence 在哪里？
当前边界和未知是什么？
哪些旧材料被它取代？
哪些下游消费层依赖它？
~~~

这比给每篇文档强制维护一个复杂 Registry 更轻，但已经足够支持真实审计。

## Evidence 支撑 Claim，但 Evidence 不是知识本身

Evidence（证据：可以重新检查并支持某个 Claim 的事实材料）和 Knowledge（知识：经过综合后形成的长期解释与判断）必须分开。

一次测试通过、一个 Git SHA、一张截图、一次 Browser readback 都可以是 Evidence，但它们各自只能证明自己覆盖的范围。反过来，一篇解释性文章也不能因为写得完整，就自动获得比底层证据更高的事实权威。

因此稳定关系应该是：

~~~text
Source / Reality
→ Evidence
→ 支撑某个 Claim
→ 多个 Claim 组成正式知识
~~~

当 Claim 的事实强度提高时，证据要求也应该提高。一个推断可以来自多条迹象；“已实现”至少要回到代码和测试；“真实可用”还要继续回到运行环境或真实用户路径。

这和 ProFlow 的 Evidence Ladder、ProFlow RAG 的固定 KnowledgeSnapshot 是同一种纪律：**结论只能信到证据真正覆盖的位置。**

正式知识因此最好保留 Source Reference，而不是复制全部原始材料。需要追问时能够回到源码、实验、历史 Commit、测试或真实运行结果；不需要追问时，读者看到的是已经提炼过的机制和边界。

## 知识变化不是“改掉旧句子”，而是判断修订、取代还是退役

长期知识一定会变化。真正危险的是所有变化都被处理成“把旧段落直接改成新段落”，最后没人知道旧判断为什么消失，也不知道依赖旧判断的下游是否需要一起调整。

我们现在更关心三类变化。

**修订（Revision）**：Canonical 问题没变，只是证据更完整、边界更精确或机制被纠正。此时更新当前 Owner，并保留变更原因。

**取代（Supersession）**：旧文章的问题已经被新的正式 Owner 接管。当稳定知识已经吸收完成，就删除旧正文、旧目录和旧链接，不再保留迁移桩；如果以后需要追溯当时为什么这样设计，直接回到 Git 历史。

**退役（Retirement）**：某项知识或设计已经不再拥有当前使用价值，就从当前知识面彻底删除。正式知识只保留仍然有效的 Owner；历史证据留在 Git，而不是继续占据当前目录。

变化以后还要做 Impact Review（影响审查：判断哪些下游消费层可能因 Source 改变而需要重建或复核）。不需要恢复旧平台那种完整 Relation Graph，但至少要检查真正存在的消费者：

~~~text
正式文章改变
→ 其他正式文章是否仍引用旧结论？
→ RAG / Knowledge Snapshot 是否需要重建？
→ Feishu / Host Knowledge 是否仍是旧版本？
→ Agent / Context Pack 是否依赖旧边界？
→ Eval / Skill / Runbook 是否包含同一规则？
~~~

影响分析只决定“哪里值得检查”，不自动授权修改这些地方。

## 对外发布不是第二套知识生产流程

Feishu、Custom GPT Knowledge、Knowledge Pack、RAG Index 和 Runtime Context 都可能消费正式知识，但它们不应该各自拥有一套可以反向修改 Source 的生命周期。

更可靠的关系是：

~~~text
正式知识 Source
→ 固定可定位版本
→ 构建 / 投影
→ 外部消费层
→ Readback / Snapshot / Citation
→ 确认真实渠道对应哪一版 Source
~~~

这里最重要的不是建立统一 Publisher 平台，而是两个问题必须可回答：

1. **这份派生物是从哪一版正式 Source 生成的？**
2. **真实消费端现在到底是不是这一版？**

ProFlow RAG 已经把这件事做成确定的 RepositorySnapshot → KnowledgeSnapshot → ACTIVE → Citation 链；Feishu 或 Host Knowledge 不一定需要同样的数据模型，但同样不能把“执行了发布动作”自动当成“真实渠道已更新”。

Publication Eligibility（发布资格）也应该保持轻量而真实：正式 Owner 已经稳定、主要 Claim 的事实强度明确、敏感信息已处理、外部链接和资源可用、目标渠道确实有授权，才进入发布。目标设计、个人隐私、Secret、未经核验的模型输出和仍有重大冲突的 Candidate，不应该因为“文章已经写好了”就被投影出去。

## 反馈可以推动知识变强，但不能直接改写真源

模型回答、用户纠正、RAG 命中、Incident、Eval Failure 和新的运行结果都可能说明正式知识需要更新。但它们首先只是 Candidate。

~~~text
真实使用
→ Feedback / Incident / New Evidence
→ Candidate
→ 找到受影响 Claim 和 Owner
→ Review
→ Accept / Reject / Need More Evidence
→ Revision / Supersession / Retirement
~~~

这条边界避免了一个很诱人的错误：让 Agent “自动学习”以后直接修改长期规则。如果一次偶然成功就晋升成 Knowledge，一次临时用户偏好就写进公共 Context，一次错误总结就覆盖正式 Source，系统会迅速被偶然经验污染。

Memory 可以保存经过治理的长期经验，Eval 可以积累失败样本，Skill 可以吸收稳定方法；它们都不意味着原始 Feedback 自动成为正式 Knowledge。**学习可以自动产生候选，正式知识的事实强度提升必须经过正确 Owner 的核对。**

## 一次成功不够：成熟度和生命周期必须分开

旧知识体系里有一个很值得保留的判断：Experience（经历）、Memory、Evidence 和 Knowledge 不是同一类东西，一次事件也不应该直接升格成长期原则。

一个 Candidate 要继续晋升，至少要问：

~~~text
这次事件本身有可靠 Evidence 吗？
它的根因和适用前提清楚吗？
有没有独立 Occurrence 再次出现？
有没有 Counter-evidence 反驳或限制这条判断？
它是否真的改变了后续任务的成功率、恢复质量或维护成本？
~~~

因此可以把成熟度看成：

~~~text
candidate
→ provisional
→ validated
→ repeated
→ established
~~~

这里最重要的是“独立”。同一次故障产生三份日志、两段 Chat 和一个复盘，不等于出现了六次证据；它们可能只是同一个 Occurrence 的不同记录。只有新的独立任务、环境或消费者再次验证同一判断，才真正提高复用信心。

Counter-evidence（反证：说明某条规则不总成立、适用范围更窄或已经失效的事实）同样必须留下。没有反证机制，知识库会只会不断积累“成功经验”，最后把局部技巧写成普遍定律。

成熟度还不能和 Lifecycle（生命周期）混在一起。一条已经 established 的工程原则，在 Provider、产品阶段、运行环境或架构边界变化以后仍然可能被 revised、superseded 或 retired；反过来，一个刚进入 active 使用的 Candidate 也不代表它已经成熟。

这条纪律让“长期知识会学习”不等于“知识只会越来越多”。真正成熟的知识系统同样需要降低置信、缩小适用范围和主动删除。

## 最后一次纠偏：知识治理需要纪律，不一定需要重型 Registry

旧 ai-agent-platform 曾经希望通过稳定 Asset ID、Platform Registry、Relation Graph、Publication Mapping、统一生命周期和自动 Impact Analyzer 把所有知识关系机器化。

这些设计可以解决真实问题，但实践后来暴露出另一个问题：当正式知识数量、消费者和发布渠道还没有复杂到需要机器查询时，维护“本地文档 ↔ Registry ↔ Feishu ↔ Agent Profile ↔ Release”的严格映射，本身会成为一套新的工程负担。

现在更适合我们的原则是：

> **轻映射、重提炼。**

也就是：

~~~text
本地材料自然积累
→ 成熟后按稳定问题提炼
→ 一个问题只有一个当前正式 Owner
→ 重要 Claim 保留事实强度和 Evidence
→ 需要消费时再建立最小必要投影
→ 下游变化通过真实引用和搜索做影响审查
→ 多个消费者真的需要机器关系时再升级 Registry
~~~

这不是放弃治理，而是把治理从“维护一套完整资产图谱”收缩到真正决定知识可信度的几件事：Owner、Claim、Evidence、Version、Boundary、Consumer 和 Lifecycle。

只有当知识资产数量、跨产品消费者、自动发布、机器发现和影响分析真的反复出现同一种维护压力时，稳定 ID、Registry 或自动 Impact Graph 才重新拥有购买复杂度的理由。

知识资产治理最后要保证的，也不是“所有文档都有状态字段”，而是：

**任何一个未来的读者或 Agent，都能知道当前应该读哪一篇、里面哪句话能信到什么程度、现实变化以后应该改哪个 Owner；需要追溯历史时，再回到 Git，而不是让历史材料继续留在当前知识面。**END 2a00ef98-3b42-4c78-9e68-9d6d4136d692
