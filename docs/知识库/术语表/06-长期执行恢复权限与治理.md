# L6｜长期执行、恢复、权限与治理

> 这一层回答：**Agent 已经能改变现实以后，Timeout、断线、重启和高风险动作怎样做到不重复副作用？**
>
> 阅读方式不是按字母背词，而是先看下面的关系链，再把每个术语放回真实系统位置。

~~~text
Propose → Permission / Policy / Approval → Execute → Observe → Verify Effect → Truth Commit → Checkpoint / WAIT / Continue
~~~

## 术语表

| 术语 | 一句话 | 典型场景 | 关键边界 / 易混 |
|---|---|---|---|
| Event | 描述“发生了什么”的不可变事实记录。 | APPROVAL_GRANTED、NODE_READY。 | Event ≠ State。 |
| State Update | 根据合法 Event/Action 提交新的 Current State。 | Task version 变化。 | 更新必须服从 Owner/Version。 |
| WAITING | Task 暂时不运行，等待外部条件的合法状态。 | 审批、Timer、Webhook、Child Task。 | WAITING ≠ FAILED。 |
| Scheduler | 根据 Runnable、优先级和资源决定何时唤醒工作。 | 长期 Task。 | Scheduler 不负责业务判断本身。 |
| Webhook | 外部系统主动向指定端点推送事件通知。 | 异步 Job 完成、支付通知。 | Webhook 可能重复、迟到，需要幂等。 |
| Async Tool | 调用后不会在同一同步请求内立即完成的 Tool。 | Build、远程 Job。 | 需要 Handle/Event/Recovery。 |
| Recovery-safe Point | 系统已经持久化足够事实，可以安全中断并恢复的位置。 | Effect 已验证、Checkpoint 完成。 | 不是任意模型轮次。 |
| Machine Interruption | 进程、机器、网络或宿主意外中断。 | Crash、重启。 | Durable Execution 要求责任不随中断丢失。 |
| Effect | Action 对真实世界实际产生的状态变化。 | 文件写入、发布、付款。 | 请求发送 ≠ Effect 已确认。 |
| Effect Boundary | 系统从 Proposal 跨到现实副作用的边界。 | 真正提交外部写入。 | 跨过后必须考虑 UNKNOWN/Recovery。 |
| Effect Lifecycle | 从 Proposal、Authorize、Execute、Observe、Verify 到 Commit Truth 的完整生命周期。 | 高风险动作。 | 只看 Tool Call 会漏掉验证和提交。 |
| Truth Commit | 把经过验证的现实结果正式写成系统 Current Truth。 | 部署成功后更新 Release State。 | Model Claim 不能直接 Commit。 |
| UNKNOWN | 当前证据不足以判断 Effect 是否发生。 | Side-effect Tool Timeout。 | UNKNOWN ≠ FAILED。 |
| Ambiguous | 存在多个仍可能成立的现实解释。 | 网络断线后外部请求是否成功未知。 | 需要 Reconciliation，而不是拍脑袋。 |
| State Reconciliation | 重新查询权威系统，使本地状态和现实对齐。 | UNKNOWN 后查远端资源。 | 是副作用恢复第一步。 |
| Authoritative Source | 对某类现实事实拥有最高解释权的来源。 | Git、支付平台、Runtime API。 | 本地缓存和模型总结不能冒充。 |
| Recovery | 从故障/中断/未知状态恢复真实 Task，并决定安全继续路径。 | Timeout、重启、断线。 | Recovery > Retry。 |
| Retry | 在确认可安全重复的前提下再次执行同一路径。 | 只读网络失败、已确认无 Effect。 | Side Effect UNKNOWN 时不能直接 Retry。 |
| Replay | 重新播放历史事件/请求以重建结果。 | Event Sourcing、恢复测试。 | 有副作用时 Replay 必须受控。 |
| Rollback | 把可逆事务/版本恢复到先前状态。 | 代码部署回滚。 | 无法抹去已发送邮件等外部历史。 |
| Compensation | 通过新的业务动作抵消先前不可逆 Effect。 | 退款、撤销发布。 | Compensation 本身也是新 Effect。 |
| Saga | 把跨系统长事务拆成多个局部 Effect，并为失败步骤设计补偿。 | 分布式业务流程。 | Saga 不提供全局 ACID 回滚。 |
| Operation Identity | 一个逻辑业务操作跨重试保持稳定的身份。 | publish release-v2。 | 不同网络请求可以属于同一 Operation。 |
| Idempotency | 重复执行同一逻辑操作不会产生第二份业务结果的性质。 | 创建资源、付款。 | 接口“幂等”仍需 Scope/TTL/Reconciliation。 |
| Exactly Once | 业务上对一个 Operation 最终只承认一份有效 Effect 的语义目标。 | 支付、发布。 | 不是网络层“消息绝不重复”的魔法。 |
| Checkpoint | 在安全点持久化继续执行所需的 State、Artifact、Evidence 和 Pending Work。 | 跨进程恢复。 | Checkpoint ≠ Summary。 |
| Resume | 从持久化 Task World 和最新现实继续执行。 | WAITING 条件满足、重启恢复。 | Resume 前要重新读 Current State。 |
| Durable Execution | 让 Task 跨 Process/Session/机器中断仍能从持久事实继续。 | 长期 Agent。 | 目标不是进程永不挂。 |
| Lease | 在限定时间和 Scope 内授予某主体暂时执行权。 | Worker Claim、资源锁。 | Lease 会过期，不等于永久 Permission。 |
| Heartbeat | 执行主体周期性证明自己仍活着/仍持有 Lease 的信号。 | Worker 运行。 | Heartbeat 不能替代业务完成 Evidence。 |
| Reopen | 保留原 Task Identity，在新 Attempt/Version 下重新进入可执行状态。 | 失败后正式恢复。 | Reopen ≠ 新建 Task。 |
| Capability | 系统是否具备执行某类动作的技术能力。 | Tool/Provider 能不能做。 | Capability ≠ Permission。 |
| Permission | 某 Identity 原则上是否有资格使用某能力。 | Agent 是否能写 repo。 | Permission ≠ Policy/Approval。 |
| Policy | 结合 Task、State、Environment、Risk 决定当前动作是否允许。 | 生产发布需要 Gate。 | Policy 是动态规则。 |
| Approval | 对一次具体高风险 Action/Target/Version 的有限授权。 | 用户批准发布。 | Approval ≠ 永久 Permission。 |
| APPROVAL_REQUIRED | Policy 判断当前动作必须先获得审批的状态/结果。 | 高风险 Side Effect。 | 应进入正式 WAITING 状态。 |
| Evidence-bound Approval | Approval 绑定具体 Artifact Version 和 Evidence。 | 批准 release-v2。 | Artifact 改成 v3 后旧批准不自动有效。 |
| Human-in-the-loop | 人在关键 Decision/Approval 环节直接参与。 | 高风险动作。 | 不等于人工持续盯着所有步骤。 |
| Human-on-the-loop | 系统可自主运行，但人类负责监督和必要时介入。 | 成熟低风险自动化。 | 需要足够 Observability 和 Stop 能力。 |
| Risk-based Autonomy | 根据可逆性、影响范围和验证能力决定 Agent 自动化程度。 | read-only 高自治、生产删除低自治。 | 模型能力高不等于授权应该高。 |
| Reversibility | 一个动作是否可完整撤销或安全补偿。 | 风险分级。 | 越不可逆，治理越严格。 |
| Least Privilege | 只给主体完成当前任务所需最小权限。 | Tool/Workspace 权限。 | 减少 Blast Radius。 |
| IAM | Identity and Access Management，管理身份、认证与访问权限的体系。 | 企业系统。 | IAM 提供基线，不覆盖 Agent 动态 Policy。 |
| RBAC | Role-Based Access Control，按角色授予权限。 | 企业 Tool 权限。 | 静态 Role 不能表达所有 Task/Risk 条件。 |
| Credential | 用于证明身份的认证材料。 | Token、证书、Cookie。 | Credential 是敏感资产。 |
| Secret | 不应出现在普通文档、Prompt 或日志里的高敏感凭据。 | API Key、Private Key。 | Secret 管理应交给受控 Owner。 |
| Consent | 用户对某类数据访问/操作的明确同意。 | 连接外部账户。 | Consent 不能无限外推。 |
| Data Handling Restriction | 对敏感数据可读取、存储、发送和保留范围的限制。 | 企业/隐私数据。 | 能力可用不代表数据可以流转。 |
| Prompt Injection | 低信任内容通过自然语言试图获得高优先级控制权。 | 网页、RAG、邮件诱导 Agent。 | 外部 Data 不应成为 Control。 |
| Control Plane | 拥有 Identity、Task、Policy、Approval、Routing 和权威状态的控制层。 | Agent Platform。 | Control Plane ≠ Data Plane。 |
| Data Plane | 承载网页、文件、RAG、Tool Result 等业务数据与执行材料的区域。 | Agent 读取真实世界。 | Data 中的指令样文本不自动获得控制权。 |
| Assessment | 对 Observation 的解释、风险判断或假设。 | 401 可能是凭据过期。 | Assessment ≠ Truth。 |
| Decision | 在 Evidence/State 基础上选择下一步的正式判断。 | 执行、等待、升级。 | Decision 应可追溯输入。 |
| Artifact | Task 生成或修改的正式产物。 | commit、spec、report、build。 | Artifact ≠ Evidence。 |
| Claim | 关于系统、结果或原因提出的可验证判断。 | “发布成功”。 | Claim 需要 Evidence。 |
| Evidence | 能够被定位、复核或回放的证明材料。 | 测试、Hash、日志、Readback。 | Evidence ≠ Conclusion。 |
| Tool Success | Tool 调用按自身协议成功返回。 | HTTP 200、exit 0。 | Tool Success ≠ Goal Success。 |
| Goal Success | Task 的业务目标和 Success Criteria 真正满足。 | 功能完成且验收通过。 | 可能需要多个 Tool Success。 |
| External Truth | 来自模型概率闭环之外、可独立回读的现实验证。 | Git Diff、Test、Browser、API。 | 用于防止自我确认。 |
| Closed-loop Self-confirmation | 同一概率主体修改后又只靠自己宣布成功。 | Agent 自己说“验证通过”。 | 高风险系统应引入 External Truth。 |
| Audit | 保存谁在何时基于什么权限和 Evidence 做了什么。 | 治理、合规、事故复盘。 | Audit Log 不应成为随意可改的工作日志。 |
| Governance | 通过 Owner、Policy、Evidence、Lifecycle 等机制让系统长期可控。 | Agent Platform。 | 治理不是增加文档层数。 |
| Safety Gate | 在高风险动作前实施确定性风险检查和阻断。 | 生产写入、外部支付。 | Gate 应由软件边界执行。 |
| Failure Containment | 让失败影响限制在局部资源、Task 或 Agent 范围。 | Sandbox、多 Agent。 | 是可靠性和安全共同目标。 |

## 这一层必须真正会区分

- **Timeout ≠ FAILED**：副作用场景下首先可能是 UNKNOWN。
- **Retry ⊂ Recovery**：Recovery 先对账真实世界，Retry 只是其中一种可能动作。
- **Rollback ≠ Compensation**：前者恢复原状态，后者用新动作抵消不可逆 Effect。
- **Capability ≠ Permission ≠ Policy ≠ Approval**：会不会做、原则上能不能、这次应不应该、这次是否已批准。
- **Observation ≠ Assessment ≠ Truth**：看到了什么、怎样解释、权威状态最终是什么必须分层。
