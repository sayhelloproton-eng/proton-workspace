# AI 的生产变更、故障和恢复怎样治理

传统服务发布一个版本，通常可以用 Git Commit、镜像版本和配置版本描述。

AI 系统的行为却常常由很多东西共同决定：

~~~text
Model
+ Prompt
+ Knowledge
+ Retrieval
+ Tool
+ Workflow
+ Runtime
+ Policy
→ Production Behavior
~~~

所以“线上现在跑的是哪个版本”不能只回答一个代码 SHA。真正需要管理的是 Behavior Release（行为发布：一组共同决定 AI 线上行为的版本组合）。

## Behavior Release 应该成为正式对象

一次候选发布至少应该能追溯：

~~~text
release_id
code_version
model_revision
prompt_version
knowledge_version
retrieval_version
tool_contract_version
workflow_runtime_version
policy_version
feature_flags
eval_result
released_at
~~~

如果 Prompt 和模型独立热更新，却没有共同 Release Identity，回滚时很容易只回一半。

### 变更本身也要进入同一套管理

这些变化都可能改变行为：

~~~text
Model alias 变化
System Prompt 改两句
Knowledge 文档更新
Top-K 从 5 改到 8
Tool Schema 增加字段
Retry 规则改变
Policy 收紧 / 放宽
~~~

所以“没有部署新代码”不等于“线上行为没有发布”。

## 发布前先冻结行为合同

发布前至少要明确：

- 目标 Slice；
- Success Criteria；
- 关键 Failure；
- Quality Gate；
- Cost / Latency Budget；
- Risk Tier；
- Rollback Trigger；
- Recovery Owner。

然后再进入：

~~~text
Static / Contract Check
→ Offline Eval
→ Shadow
→ Canary
→ Production
~~~

不同 Gate 解决不同问题。

## Canary 的重点是受控扩大风险

Canary（金丝雀发布）不是“先放 10% 用户看看”。

真正需要同时定义：

~~~text
who enters canary
what risk is allowed
what metrics compare
how long observe
what triggers rollback
who owns decision
~~~

高风险系统可以按能力逐步打开：

~~~text
只读任务
→ 内部用户
→ 低风险写操作
→ 小规模真实用户
→ 更广流量
~~~

流量比例只是其中一个维度。

## AI 故障常常先表现成行为异常

传统服务常见 5xx、OOM、Crash。

AI 系统还会出现：

- Token Spike；
- Prompt Loop；
- Tool Loop；
- No-progress；
- Context Explosion；
- Retrieval Miss；
- Hallucinated Completion；
- Permission Escalation Attempt；
- Provider Degradation；
- Model Refusal Spike；
- Tool Schema Drift；
- Cost Explosion。

这些问题接口可能仍然返回 200，所以必须依赖行为级指标。

## Token Spike 是一个信号，不是根因

Token 突然上涨可能来自：

- History 没压缩；
- Retrieval Top-K 变大；
- Tool Result 过长；
- 模型开始重复解释；
- Agent Loop 增加；
- Retry 增加；
- Prompt 变化；
- 异常请求分布变化。

正确排查方式不是立刻把 max_tokens 调小，而是先找增长发生在哪个 Span、哪个 Release、哪个 Slice。

## 死循环要有结构化识别

最简单的方式之一，是给每一步生成 Fingerprint（步骤指纹：由当前状态、动作和关键参数归一化后得到的重复检测标识）。

例如：

~~~text
fingerprint =
hash(
  normalized_state
  + selected_tool
  + normalized_args
  + goal_phase
)
~~~

连续出现相同或近似 Fingerprint，同时 State 和 Evidence 没变化，通常说明 Agent 在空转。

No-progress Detection（无进展检测）还可以结合：

- 没有新 Evidence；
- State 没变化；
- Goal 距离没缩短；
- 同一错误反复出现；
- 同一 Tool / Query 重复。

检测到后应 Stop、Replan、Escalate 或 Human Review，而不是等预算耗尽。

## Budget 是生产保护，不只是成本控制

Budget 可以包括：

~~~text
max_steps
max_model_calls
max_tool_calls
max_retries
max_cost
wall_clock_deadline
parallel_workers
~~~

还可以观测：

~~~text
step_budget_utilization
tool_budget_utilization
cost_budget_utilization
~~~

如果 P95 长期接近上限，说明系统正在靠“把预算跑满”维持成功率，需要重新优化路径，而不是只把上限继续调大。

预算耗尽应该进入正式状态 BUDGET_EXHAUSTED，再决定 stop、escalate 或经批准继续。

## Timeout 必须分层

应该区分：

~~~text
Model Timeout
Retrieval Timeout
Tool Timeout
External Job Deadline
Task Wall-clock Budget
Human Approval SLA
~~~

一个 Build 需要十分钟，不代表模型调用也应该等十分钟。

长 Job 也不应该靠 Agent 不断轮询，而应进入 WAITING，等 Event 再唤醒。

## Retry、Fallback、Recovery、Rollback 是四件事

Retry 是同一路径再次执行。

Fallback 是换 Provider、模型、Retriever 或 Tool 实现。

Recovery 是先恢复当前现实状态，再决定下一步。

Rollback 是把系统行为或配置回到先前稳定版本。

对于不可逆业务 Effect，可能只能 Compensation，不能真正 Rollback。

完整副作用恢复机制见 [长期 Agent 怎样安全执行和恢复](../现代AI工程/09-长期Agent怎样安全执行和恢复.md)。

## Timeout 之后先问“副作用发生了吗”

例如：

~~~text
Agent → createRefund
→ timeout
~~~

这里不能直接推断退款失败。

如果第一次已经成功、只是 Response 丢失，Retry 可能产生第二次退款。

所以副作用动作应该：

~~~text
timeout / disconnect
→ effect = UNKNOWN
→ query authoritative source
→ reconcile
→ commit / safe retry / wait / human
~~~

Idempotency Key 是重要保护，但不能替代 Reconciliation。

## 一个实用的故障排查顺序

面对“Agent 卡死 / 超时 / 变贵”，可以按：

~~~text
1. 先看 Outcome 和当前 Task State
2. 查 Release / Version 是否刚变化
3. 查最后一个正常 Span
4. 查外部依赖 / Tool / Retrieval
5. 查 Retry / Fallback 是否放大
6. 查 step / fingerprint / no-progress
7. 查 Budget / Timeout 是否真的生效
8. 回到 First Divergence 定 Owner
~~~

不要从最后一个 Timeout 直接得出“模型坏了”。

## Circuit Breaker 防止所有 Task 重复撞同一故障

Circuit Breaker（熔断器：某依赖持续失败时暂时停止继续调用）适合：

- Provider 持续 5xx；
- Tool 明确不可用；
- 外部 API 限流严重；
- 某模型版本出现大面积错误。

熔断以后可以 Fallback、Queue、Degrade、Human 或 WAITING。

## Bulkhead 防止一个故障拖垮全部任务

Bulkhead（舱壁隔离：把资源和失败域分开）可以按 Tenant、Tool、Provider、Risk Tier、Workflow、Queue 隔离。

一个 Browser Tool 卡死，不应该把所有文本问答的并发槽一起占满。

## DLQ 适合无法自动安全处理的事件

Dead Letter Queue（死信队列）适合多次处理失败、需要后续调查或人工处理的异步 Event / Job。

进入 DLQ 的对象至少应该保留：

- original identity；
- failure reason；
- attempts；
- current state；
- evidence；
- next owner。

DLQ 不是垃圾桶，必须有人消费。

## 故障时要允许降级，而不是只有“继续 / 全停”

一个 Agent 系统可以设计多层 Degradation（降级：在能力受损或风险升高时主动收缩自动化范围）。

例如售后场景：

~~~text
Level 0
完整 Agent：判断 + 自动退款

Level 1
Agent 判断 + 人工确认退款

Level 2
只读 AI Assistant：给建议，不写业务状态

Level 3
规则 / 搜索 / FAQ

Level 4
完全转人工
~~~

这样外部 Tool 不稳定、模型异常或安全风险上升时，可以逐层收权，而不是二选一。

## Incident Response 应该先止血，再追根因

~~~text
Detect
→ Contain
→ Stabilize
→ Reconcile
→ Root Cause
→ Repair
→ Regression
~~~

Contain 可能是：

- Kill Switch；
- 降级只读；
- 禁用高风险 Tool；
- 回滚 Behavior Release；
- 收窄流量；
- 停止自动执行。

在现实还持续被改变时，先写长篇 Root Cause Report 没有意义。

## First Divergence 比最后一个错误更有价值

例如：

~~~text
Retrieval 取到旧规则
→ Model 生成错误参数
→ Tool 被拒绝
→ Agent Retry
→ Token Spike
→ Task Timeout
~~~

真正 Owner 是 Retrieval Freshness，而不是最后的 Timeout。

Incident Analysis 应尽量找 First Divergence（第一处分歧：实际行为首次偏离预期的节点）。

## 恢复以后也不要立刻全量放流

事故修复以后，可以：

~~~text
Fix
→ Offline Regression
→ 少量 Probe
→ Canary
→ Version-sliced Monitoring
→ Gradual Restore
~~~

恢复过程本身也要验证。

“服务重新起来了”不等于业务行为已经恢复。

## Runbook 应该描述动作，不只是解释

高频 Incident 可以沉淀 Runbook：

~~~text
Trigger
Evidence to inspect
Immediate containment
Owner
Safe recovery steps
Rollback conditions
Escalation
Regression requirement
~~~

Runbook 越稳定，越适合进一步转成 Automation。

## Rollback 应该围绕 Behavior Release

如果一次 Release 同时改变 Prompt、Model、Reranker 和 Tool Contract，回滚只恢复其中一个，很可能得到从未评测过的新组合。

因此发布系统最好支持：

~~~text
release_id
→ exact component versions
→ one rollback target
~~~

这能显著降低恢复复杂度。

## Postmortem 要追到系统为什么没拦住

事故结束后不只问“根因是什么”，还要问：

~~~text
为什么 Offline Eval 没发现？
为什么 Canary 没拦住？
为什么告警晚了？
为什么 Fallback 没生效？
为什么影响面这么大？
为什么 Recovery 这么慢？
~~~

这些问题分别会指向 Eval、Observability、Policy、Release 和 Runtime 的系统性缺口。

## 三类真实故障怎样把 Recovery 从“重试”改成 Reality Reconciliation

ProFlow 的长期运行给这套故障模型提供了最直接的现实证据。

第一类是 **Browser / publish timeout**。Browser submit 已经有 Delivery evidence 后，下游 response failure 不能把它重新改写成“没有发送”；`pnpm publish` timeout 以后也不能直接再 publish，而要回 Registry 查询 exact version。两者共同证明：**调用失败不等于 Effect 没发生。**

第二类是 **外部资源已经创建，但后续 validation 失败**。Custom GPT 一旦已经 `LIVE_CREATED` 并出现 stable g-id，后面的校验失败不能回滚本地 identity 再新建第二个资源；恢复必须承认远端现实，在原资源上继续验证。完整链路见 [ProFlow 如何从源码走到真实可运行产品](../ProFlow/07-ProFlow如何从源码走到真实可运行产品.md)。

第三类来自 **ProFlow RAG 的机器中断**。历史 V0 Gate 曾因为机器重启同时失去 `/tmp` evidence、PID 和进程；项目没有猜 PASS / FAIL，而是裁决 `EXTERNALLY_INTERRUPTED / UNKNOWN`，恢复真实数据库和运行环境后再继续。同样，ChatWeb 的旧 `V0_RELEASE=YES` 也曾在真实生产拓扑修正后被重新打开：Technical Gate 仍然可以 PASS，但 Release Truth 必须重新治理。见 [ProFlow RAG 历史证据](../ProFlow-RAG/历史证据与决策档案.md) 与 [ChatWeb 历史证据](../ChatWeb/历史证据与决策档案.md)。

所以 Retry、Fallback、Recovery、Rollback 之所以必须分开，不是术语洁癖，而是这几条真实链路一旦混在一起，就会制造重复副作用、假成功或错误回滚。

## 每次生产故障最终都应该留下资产

Incident 不应该只留下“已恢复”。

至少要问：

~~~text
是否新增 Regression Case？
是否新增 Dashboard / Alert？
是否需要 Budget / Stop Rule？
是否需要 Policy？
是否需要 Runbook？
是否需要调整 Golden Path？
~~~

这样一次故障才会让未来系统更强。

AI 生产治理的核心并不是让系统永远不出问题，而是：

> **变化可追踪、风险可限制、故障可止血、状态可恢复、旧问题不反复回来。**

当 Release、Trace、Recovery 和 Regression 都建立起来以后，生产系统会开始积累大量可以分析的真实材料：失败轨迹、用户反馈、人工修正、Incident 和 Outcome。下一篇 [怎样让 AI 反过来治理质量和业务](./07-怎样让AI反过来治理质量和业务.md) 继续回答：这些生产证据能不能反过来帮助团队发现质量问题、知识缺口和流程瓶颈。
