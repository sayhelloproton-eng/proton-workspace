# 模型到底应该怎么评

“这个模型更强吗？”如果没有任务、数据、运行参数和评测协议，这个问题没有稳定答案。

真正的 Model Evaluation（模型评测）不是打开几个排行榜看分数，也不是随便问十道题凭感觉比较，而是一套可复现实验：

~~~text
定义要评什么
→ 选公开 Benchmark + 自己的真实任务
→ 固定 Evaluation Protocol
→ 运行完整 Dataset
→ 保存原始输出与失败
→ 按任务选 Metric
→ 多次 Trial
→ 看置信区间和 Failure Slice
→ 比较质量、延迟与成本
~~~

公开 Benchmark 帮助建立行业坐标，Internal Eval（内部评测：使用自己的真实任务和成功标准进行评估）才决定当前产品到底能不能用。

## 第一步先分清：你评的是模型，还是整个系统

如果目标是比较基础模型本身，除了模型以外，其他条件应该尽量固定：

- 同一 Dataset；
- 同一 Prompt / System Instruction；
- 同一 Chat Template；
- 同样的 temperature / top_p / max output；
- 同样的 Tool；
- 同样的 RAG Context；
- 同样的 Agent Harness；
- 同样的 Reasoning Budget。

否则测出来的可能不是模型差异，而是 Prompt、Harness 或 Tool 差异。

真实产品评测则属于下一篇 [AI 系统到底应该怎么评](./04-AI系统到底应该怎么评.md)。

## Evaluation Protocol 决定比较是否公平

Evaluation Protocol（评测协议：规定样本、输入、运行配置、重复次数、评分方式和成本统计的完整规则）至少要记录：

~~~text
dataset_version
model_id / revision
prompt_version
chat_template
few-shot examples
temperature / top_p
max_tokens
reasoning_effort
tool_set
retriever_version
agent_harness_version
trials
grader_version
~~~

一个模型使用官方 Chat Template、高 Reasoning Budget、更多 Tool，另一个使用裸 Completion，再拿总分直接比较，并不是公平实验。

## 每一次 Evaluation Run 都要保留原始证据

最终总分只能告诉你“有差异”，不能告诉你“为什么”。

每个 Task 至少应该留下：

~~~text
input
raw output
parsed answer
score
latency
token / cost
failure reason
if agentic: trajectory / tool calls
~~~

两个模型都可能总分 80，但一个数学错得多、代码很好，另一个恰好相反。不同产品结论完全不同。

## 测试集首先要代表真实 Task Slice

Task Slice（任务切片：输入形态、风险、成功标准相似的一组任务）比总样本数更重要。

例如客服系统可以拆意图分类、退款资格、长对话总结、高风险投诉、Tool 参数抽取。

如果 95% 样本都是简单分类，平均 98 分可能掩盖剩余 5% 高风险退款只有 60 分。

内部数据至少要覆盖：

~~~text
normal path
+ edge / hard cases
+ historical failures
+ should reject / escalate
~~~

## 公开 Benchmark 应该按能力拼成 Battery

Benchmark（基准测试：固定 Dataset、Protocol、Grader 和 Metric 的公共评测）只是能力切片。

| 能力 | 典型任务形态 | 常见指标 |
|---|---|---|
| 通识 / 学科知识 | 多领域问答、选择题 | Accuracy / Exact Match |
| 高难推理 | 专业推理题 | Accuracy / Exact Match |
| 指令遵循 | 多约束输出 | instruction-level success |
| 数学 | 可验证最终答案 | Exact Match / pass@k |
| 代码生成 | 函数 + Test | pass@k |
| 真实软件工程 | Repo + Issue + Patch + Test | Resolution Rate |
| Web / Research Agent | 多步检索和环境任务 | task success / grader |
| 真实职业工作 | 专业交付物 | blind pairwise / win-tie-loss |
| 安全 / 稳健性 | 扰动、越狱、偏差样本 | robustness / safety metrics |

具体 Benchmark 会变化，但“按能力组合 Battery”比只看一个 Leaderboard 更稳定。

一个 Benchmark 值不值得跑，可以问五件事：它测什么、输入输出像不像真实任务、Grader 是否可靠、是否明显饱和或污染，以及**这个分数能不能改变模型选择**。

## Accuracy、Precision、Recall、F1 各自回答什么

Accuracy（准确率）适合类别相对均衡、错误代价接近的任务。

类别极不均衡时，99% Accuracy 也可能完全没抓到稀有高风险样本。

这时要看 Precision（精确率）、Recall（召回率）和 F1。业务仍应先决定漏报和误报哪个更贵，而不是自动追求最高 F1。

## Exact Match 适合答案可以精确标准化的任务

Exact Match（完全匹配）适合数学最终答案、短 QA、确定字段和 Benchmark 答案提取。

但要提前定义 Normalization（标准化）：大小写、空格、单位、标点是否应忽略。否则 Grader 本身会制造 Fake Failure。

## Perplexity 仍有用，但不能代表 Chat / Agent 能力

Perplexity（困惑度：衡量语言模型对文本序列预测的不确定程度）在传统语言模型评测中很重要。

通常 Perplexity 越低，说明模型对这类文本预测越好。

但它不能直接告诉你指令遵循、Tool 使用、代码执行、开放回答偏好和 Agent 完成真实任务的能力，所以现代应用选型不能只看它。

## Coding 为什么常用 pass@k 和 Resolution Rate

pass@k 看的是：生成 k 个候选时，至少有一个成功的概率。

Resolution Rate（解决率）更进一步：

~~~text
真实 Issue
+ Repository
+ base state
→ model / agent creates patch
→ patch applied
→ tests run
→ issue actually resolved?
~~~

它评的是问题有没有真的被修掉，而不是 Patch 文本像不像参考答案。

## pass@k 和 pass^k 表达相反方向的可靠性

~~~text
pass@k
→ k 次中至少一次成功

pass^k
→ 连续 k 次都成功
~~~

前者适合候选生成；后者更接近生产自动化的重复可靠性。

客服、支付、企业自动化如果每次都必须稳定正确，通常更关心多次连续成功，而不是多试几次总有一次行。

## 开放式回答更适合 Pairwise

当任务没有唯一标准答案，可以做 Pairwise Evaluation（成对评估）：

~~~text
same prompt
→ Response A
→ Response B
→ Human / Judge
→ A win / B win / Tie
~~~

多个模型的大量 Pairwise 结果还可以通过 Bradley-Terry（布拉德利-特里模型：从两两胜负估计相对强弱）或 Elo-like Rating 汇总成相对排名。

这类 Rating 是相对能力，不是绝对正确率。

## LLM-as-a-Judge 需要先校准 Judge

模型 Judge 可能偏爱更长答案、受展示位置影响、偏好某种风格，或者和人类标准发生系统性偏差。

所以至少要：

~~~text
human-labeled set
→ judge runs
→ inspect disagreement
→ refine rubric
→ periodic recalibration
~~~

能用 Test、Parser、SQL 或权威 API 判断的，仍然优先机械验证。

## Calibration 评的是“自信是否可信”

Calibration（校准：模型给出的置信度是否和真实正确率匹配）回答：模型说 90% 有把握的样本，长期看是否真的大约 90% 正确？

ECE（Expected Calibration Error，期望校准误差）是一种常见度量。

高风险自动化不能只信模型自报 confidence，还要结合历史 Calibration、Validator 和 Risk Rule。

## Robustness 看“题稍微变一下还会不会”

Robustness（鲁棒性）可以通过 paraphrase、typo、irrelevant context、format change、language / dialect change 等扰动来测。

如果轻微改写就显著退化，生产稳定性很可疑。

Safety、Toxicity、Bias、Fairness 也应该成为独立 Slice，而不是被一个总 Accuracy 吞掉。

## 随机模型不能只跑一次

同一道题可能 Trial 1 PASS、Trial 2 PASS、Trial 3 FAIL。

重要 Slice 应做 Multiple Trials，至少记录 mean / success rate、variance、failure count、critical errors 和 worst cases。

一次 PASS 不能代表概率模型稳定会做。

## 比较两个模型时要做 Paired Evaluation

让 A 和 B 跑同一批 Task，才能看哪些题谁赢、差距集中在哪个 Bucket，以及总分是否被少数样本拉出来。

开放任务还应随机交换 A/B 展示位置，控制 Position Bias。

## Confidence Interval 告诉我们小差距是否值得相信

100 道题 A=82%、B=84%，不等于 B 一定更强。

正式结果至少应报告 sample size、mean、trial variance、confidence interval 和 paired win/loss/tie。

如果区间高度重叠，合理结论可能就是：

> 当前证据不足以区分。

## Latency 和 Cost 也是模型评测的一部分

至少同时记录：

~~~text
quality
TTFT
output throughput
end-to-end latency
input / output tokens
reasoning usage
cost
~~~

云 API 与端侧模型比较时，还要明确 hardware、quantization、batch、context length、cold/warm、concurrency 和 provider queue。

## Failure Slice 比总分更能指导修复

如果主要问题是 JSON field missing，优先修 Structured Output / Validator；如果是最新政策不知道，优先修 Retrieval；如果复杂规划失败，才更像模型能力问题。

总分告诉你差多少，Failure Slice 告诉你为什么差。

## 评测集本身也有生命周期

~~~text
production failure
→ sanitize / label
→ add regression case
→ future candidate must pass
~~~

但同一 Test Set 被频繁用于调 Prompt 会产生 Eval Overfitting（评测过拟合）。

因此可以区分 development、validation、regression 和 holdout / challenge。

## 一份可以用于决策的模型评测报告

至少应该包含：

~~~text
Task / Slice
Dataset Version
Evaluation Protocol
Model + Revision
Inference Profile
Trials
Quality Metrics
Critical Failures
Calibration
Robustness
Latency
Cost
Confidence / Uncertainty
Known Gaps
~~~

模型评测最终要支持的是路由和选型，而不是寻找一个全局最强模型：

> **在给定任务、风险、硬件、延迟和成本约束下，哪条模型路径最合适。**

模型评测把“哪条模型路径更适合当前任务”说清以后，还不能直接证明产品会成功。真实结果还会受到 Retrieval、Context、Tool、Workflow、Runtime、Permission 和环境反馈影响。下一篇 [AI 系统到底应该怎么评](./04-AI系统到底应该怎么评.md) 会把评测对象从单个模型扩展到整条业务执行链。
