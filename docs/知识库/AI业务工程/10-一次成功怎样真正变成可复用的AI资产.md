# 一次成功怎样真正变成可复用的 AI 资产

很多 AI 经验只活在一次聊天里。某个人找到了一套很好的 Prompt、排障方法或工具组合，当时任务成功了；几周以后另一个人遇到同类问题，又从头探索。

这种成功还没有变成组织能力。真正的 Assetization（资产化：把重复有效的方法从个人经验升级成可复用、可治理、可验证的正式能力）要回答三个问题：什么值得留下、应该以什么形态留下、什么时候值得继续升级。

## 不是所有经验都应该直接做成 Agent

~~~text
Case
→ Checklist
→ Template
→ Context Pack
→ CLI / Script / Validator
→ Skill
→ Workflow
→ Agent
→ Shared Service / Platform Primitive
~~~

这不是成熟度排行榜。每升一级都会增加 Owner、Version、Test / Eval、Permission、Documentation、Consumer、Compatibility 和 Operations 成本。只有重复收益足够大，才值得升级。

## Case 是资产化起点

Case（案例）至少记录 Problem、Context、Decision、Action、Evidence、Outcome、Failure / Constraint 和 Learning。

只有最后怎么做不够。真正可复用的是为什么这样做、什么条件下成立、什么情况下会失败。尤其 Incident 类 Case，应该保留真实失败链，而不是只留下已修复。

## Checklist、Template 和 Context Pack 分别解决什么

Checklist 适合稳定的人类检查步骤，例如发布前确认 Scope、Test、Rollback Target、Approval 和 Monitor。

Template 适合重复结构，例如 Incident Report、Eval Report、Handoff、Release Plan、Tool Contract。

Context Pack（上下文包：为一类任务整理稳定入口、关键 Source、术语、Owner 和边界）解决的是每次都重新找资料。它不应该复制全部内容，而应该提供 Source Ref、阅读顺序、Known Constraint、Fact Owner、常见 Failure 和验证入口。稳定规则可以进入 Context Pack，实时事实仍然通过 Tool / RAG 获取。

## CLI / Script 适合确定性动作

当步骤已经稳定：

~~~text
input
→ deterministic transform
→ output
~~~

就应该下沉成 Script / CLI。固定格式转换、仓库扫描、生成 expected state、收集测试结果、规范化日志都更适合程序。让模型每次重新决定固定步骤只会增加 Token 和失败率。

## Validator 是很容易被遗漏的一类资产

有些经验不是怎么做，而是怎么判断结果是否合格。

Validator（验证器：对结果执行明确、可重复的检查）可以承接 JSON Schema、业务金额边界、Git Diff Scope、Citation Evidence 等稳定规则。

如果判断已经足够稳定，就不要永远留在 Review 经验里。

## Skill 适合可复用方法

Skill 更适合承载决策顺序、工程协议、什么时候用什么 Tool、风险判断、停止条件和验证策略。

Tool 是动作，Skill 是方法。Skill 不应该偷偷拥有长期 Task State。

## Workflow 适合稳定路径和状态机

~~~text
Draft
→ Review
→ Approve
→ Publish
~~~

模型可以在某个 Node 做语义判断，但 Workflow 拥有合法状态迁移。

## Agent 只有在路径真的开放时才值得

如果下一步必须根据运行时新 Observation 决定，Agent 才有增量价值。否则一个确定性 Workflow 外面再套一层 Agent，只会增加 Context、Cost、Permission、Recovery 和 Eval 负担。

## Runbook 是生产经验最适合的资产形态之一

Runbook（运行手册：针对已知故障或操作场景，明确触发条件、检查顺序、恢复步骤和升级条件）可以把 Incident 经验变成可执行路径。

~~~text
Trigger
→ refund-agent success rate drops

Check
→ release / tool / retry / idempotency

Contain
→ disable auto-refund

Recover
→ reconcile affected orders

Exit
→ regression passes + canary stable
~~~

Runbook 稳定以后，机械部分还可以进一步变成 Automation。

## Regression 让失败变成永久资产

~~~text
failure
→ reproduce
→ label
→ add regression case
→ fix
→ future release gate
~~~

所以 Asset 不只有 Prompt、Skill、Workflow；Dataset、Eval Case、Security Case 也是重要资产。

## Shared Service 只有在多个消费者出现以后再抽

一个 Script 被一个团队使用，不需要立刻服务化。真正的平台信号是 multiple consumers、stable contract、repeated maintenance 和 shared governance need。

这时才考虑 Shared Service / Platform Primitive（平台原语：多个产品稳定复用的基础能力）。

## 每个 AI Asset 都需要 Contract

Asset Contract（资产合同：明确一个可复用能力输入、输出、边界和使用条件）至少可以记录：

~~~text
name
problem
inputs
outputs
owner
scope
dependencies
permissions
success criteria
known limitations
version
eval
consumers
status
~~~

没有 Contract 的共享资产很容易变成大家都在用，但没人知道什么时候会坏。

## Owner、Version、Eval 和 Consumer 缺一不可

Owner 负责更新、兼容、Security、Eval、Deprecation 和 Consumer Communication。

Version / Change Log 让消费者知道当前版本、Breaking Change、Migration 和 Rollback。

Eval 是资产晋升条件：在多次真实任务中重复有效、Failure 已知、输入输出稳定、成本可接受、权限边界明确，才适合继续升级。

Consumer List（消费者清单）则决定 Breaking Change、Migration、Test Scope 和 Blast Radius。

## Promotion Rule 防止过早平台化

~~~text
repeated manually
→ checklist

stable deterministic steps
→ script

stable validation rule
→ validator

repeated method with judgment
→ skill

stable stateful path
→ workflow

open decision + clear runtime need
→ agent

multiple teams consume
→ shared service
~~~

这样复杂度有明确购买条件。

## Deprecation 和 Removal 同样重要

资产库只增不减，会越来越难用。每个资产应该支持：

~~~text
Draft
→ Experimental
→ Stable
→ Deprecated
→ Retired
~~~

Experimental 可以快速变化、不保证兼容；Stable 则应该有 Owner、Eval 和兼容策略。还要记录 Replacement、Consumers、Removal Date 和 Migration Guide。

## 真正可复用的是稳定责任，不是具体产品名

代码结构分析今天可以由某个工具实现，明天也可能换 Provider。长期应该保存的是 Capability Contract：例如 query symbol / caller / blast radius。

一个 Tool 或 Agent 的品牌名不应该成为长期知识结构。

## 三条真实演进说明“资产化”不是把东西登记进 Registry

**本机工程链先从一次性 Prompt 变成 Script / Skill / Automation。** 最早需要人工 zip 仓库、让 Chat 生成 handoff，再由人把动作搬回本机；后来才逐步出现 Local Dev、CodeGraph、Repomix、Browser、Engineering Skill 和 Frozen Decision Runner。每次升级都对应一个重复瓶颈，不是因为“Agent 平台应该拥有这些资产”。完整因果链见 [本机 Agent 工具链](../本机Agent工具链.md)。

**ProFlow 的 Project Memory 也经历过“有文档但不可执行”的失败。** 第一轮公共上下文过度压缩后，新 Chat 能理解原则，却不知道执行入口、Authority source、Recovery path 和 Do-not-repeat；项目后来通过 Lost-context Simulation 检查一个失忆执行者能否真正接管。见 [ProFlow 怎样从一次跑通走向长期可运行的工程系统](../ProFlow/05-ProFlow怎样从一次跑通走向长期可运行的工程系统.md)。

**ProFlow RAG 把失败真正升级成了 Eval 资产。** exact engineering term 召回缺口、Reranker 持续负载 timeout、Eval ordering / SQL 假失败都进入固定评测与回归，而不是只留一句“后来修好了”。见 [如何用 Eval 和降级治理 RAG 质量](../ProFlow-RAG/05-如何用Eval和降级治理RAG质量.md)。

这三条路径共同说明：资产化的判断标准不是“有没有一个正式名字”，而是**下一次遇到同类问题时，是否真的不用重新支付同样的发现成本。**

## 资产化的最终目标是减少重新发现

~~~text
first case
→ learning

repeated case
→ reusable asset

more consumers
→ shared capability

production feedback
→ eval / improvement
~~~

资产不是为了文档更多，而是让下次不必重新支付同样的探索成本。

真正长期的 AI 能力，最终都要从一次成功走向：

> **有 Contract、有 Owner、有 Version、有 Eval、有消费者、有生命周期、有退出机制。**

当一项 Asset 只有一个使用者时，它仍然可以留在项目内部；一旦多个团队开始重复消费同一类 Model、Knowledge、Tool、Eval、Trace 或 Security 能力，新的问题就变成“哪些责任应该共享，哪些仍然属于产品”。下一篇 [团队怎样建立公共 AI 能力而不是重复造轮子](./11-团队怎样建立公共AI能力而不是重复造轮子.md) 就从多个真实消费者出现以后继续。
