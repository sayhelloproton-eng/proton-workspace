# 组织怎样形成持续变强的 AI 能力飞轮

一个团队做完一个 AI 项目以后，真正重要的问题不是这次上线了没有，而是：

> **下一次遇到类似问题，组织是不是能从更高起点开始？**

如果每一次成功都只留在个人脑子里，每一次事故都只存在聊天和工单里，组织不会因为做过更多 AI 项目就自然变强。长期能力的关键，是让工作留下东西。

## 先看两种完全不同的组织

组织 A：

~~~text
每个人自己问 AI
↓
做完任务
↓
聊天结束
~~~

组织 B：

~~~text
AI 完成真实任务
↓
保留 Trace / Outcome
↓
失败进入 Failure Taxonomy
↓
形成 Case / Regression
↓
稳定做法升级 Asset
↓
公共问题进入 Shared Capability
↓
新项目默认复用
~~~

两者今天效率可能差不多。一年以后差距会非常大，因为 B 的每次工作都在增加未来的起点。

## 第一条飞轮：Production Failure → Regression

~~~text
线上失败
→ Root Cause
→ Regression Case
→ 修复
→ 以后所有 Release 自动检查
~~~

前提是 Failure 有 Evidence、Root Cause 找到正确 Owner、Regression 真能复现、后续 Gate 会执行。事故如果只写已恢复，并没有真正进入组织能力。

## 第二条飞轮：Repeated Work → Asset

多个工程师反复写同样 Prompt、查同样日志、走同样发布流程或重复相同判断时，组织应该识别它，然后逐级升级：

~~~text
Case
→ Template
→ CLI / Validator / Skill
→ Workflow
→ Shared Primitive
~~~

## 第三条飞轮：Asset Usage → Improvement

资产不是写完就结束。真实使用数据应该反过来推动资产演进。

例如一个 Incident Triage Skill：100 次使用里有 12 次 failure_bucket=unknown，人工分析后发现 3 类新故障，再更新 Skill、补 Regression，让 unknown 降到 4%。

如果资产没有 Usage / Failure Data，就很难知道它该怎么改。

## 第四条飞轮：Platform Friction → Golden Path

业务团队如果不断绕过平台，不要先怪业务不规范。要问为什么正确路径更难。

~~~text
接平台 Tool 要 3 天
自己写 HTTP 只要半小时
→ 绕过几乎必然
~~~

更好的回路是：

~~~text
绕过行为
→ Friction Signal
→ Platform Improvement
→ Golden Path 更简单
~~~

## 第五条飞轮：Human Review → Rubric / Eval

很多主观判断一开始只能靠专家 Review。长期来看，应该逐步问专家到底在看什么。

例如代码 Review 关注边界条件、副作用、兼容性、测试覆盖和权限影响，这些判断可以逐步沉淀成 Rubric、Static Check、Validator、Eval Case、Skill Instruction。

专家不会消失，而是把重复判断逐步转成组织能力。

## AI 会改变 Review 的对象

传统 Review 主要看代码、文档、方案。Agent 时代还要 Review Prompt / Instruction、Tool Contract、Knowledge Source、Eval Dataset、Agent Permission、Trace 和 Outcome。

所以 Review 不能只问这段代码写得好吗，还要问：这个 Agent 在什么条件下会做错？我们怎么知道？做错以后影响多大？

## AI 也会改变工程师的职责边界

当模型可以快速生成代码、文档和方案以后，越来越多工程工作会转向：

~~~text
定义任务
提供 Context
设计工具
设置约束
设计 Eval
审查证据
处理异常
沉淀能力
~~~

这不是工程师少写代码，而是控制面上移。工程师仍然要对任务正确性、系统边界、证据、验证和生产结果负责。

## 会用 AI 不是一个独立岗位技能

AI 会进入大量现有岗位：研发需要 Coding / Debug / Eval / Agent Engineering；产品需要 Task Definition / Acceptance / Failure Analysis；运营需要 Workflow / Quality / Feedback；安全负责 Permission / Threat Model / Audit；平台负责 Primitive / Runtime / Governance。

横向专业 Owner 仍然需要存在，例如 AI Platform、Model / Provider Strategy、Eval Infrastructure、Security / Governance、Shared Tool / Asset Registry，但横向团队不能替业务团队定义什么叫业务成功。

## 新的 Review 模式应该 Evidence First

~~~text
代码修改
→ Test

数据结论
→ Query / Source

Agent Action
→ Environment State

安全判断
→ Policy / Audit
~~~

AI 生成结果很快，也更容易制造看起来没问题的错觉。证据应该来自可验证系统，而不是让 AI 再生成一段更长解释。

## Human-in-the-loop 的角色也会变化

低成熟度阶段，人逐条检查所有输出；成熟以后则变成确定性检查自动化 + Eval 自动化 + 高风险动作人工审批 + 异常样本人工 Review。

人的工作会从逐条兜底逐渐转向校准系统。

## 组织知识不能只有 Wiki

Wiki 适合解释，但长期 AI 能力还需要大量可执行知识：CLI、Skill、Workflow、Schema、Eval Dataset、Policy、Runbook。

所以组织知识应该包含：

~~~text
Readable Knowledge
+ Executable Knowledge
~~~

Readable Knowledge 帮助人理解为什么；Executable Knowledge 则把稳定经验变成系统默认动作。

一个实用判断是：解释为什么 → 文档；稳定判断规则 → Validator / Policy；固定执行步骤 → CLI / Workflow；需要语义判断 → Skill / Model；真实失败 → Regression。

## Failure Taxonomy 是组织共同语言

~~~text
Task Definition
Context Missing
Knowledge Stale
Retrieval Miss
Wrong Tool
Tool Failure
Permission Denied
Loop
Timeout
Bad Side Effect
Security
Evaluator
~~~

统一 Failure Taxonomy（失败分类体系）可以跨项目统计、找共同问题、决定 Platform 优先级、自动生成 Regression、衡量能力是否改善。

## Capability Map 让组织知道自己真正有什么能力

不能只列我们有多少个 Agent，更应该知道已经稳定解决了哪些任务。

例如代码仓库理解、生产 Incident Triage、知识问答、合同抽取、客服退款、数据分析。每项能力再标 Owner、Maturity、Quality、Reliability、Consumers、Risk Tier、Evidence、Gaps。

## Capability Maturity 应按 Evidence 分层

~~~text
L0：个人临时使用
L1：可重复 Prompt / Template
L2：有 Asset + Owner
L3：有 Eval + Version + Trace
L4：多团队复用 + Platform 支撑
L5：生产反馈自动进入优化飞轮
~~~

成熟度不是自主程度。一个稳定 Workflow 完全可能比自由 Agent 更成熟。

真正成熟是知道什么时候该自治、什么时候不该自治、如何验证、如何控风险、失败后怎么恢复。

## AI Adoption 不能只看活跃人数

多少人每周用 AI 只能证明工具被打开。更值得看的指标是：

~~~text
Repeatable Workflows
Shared Assets
Task Success
Regression Coverage
Active Consumers
Time to Production
Human Rework
Cost per Useful Outcome
~~~

Token 用量也只是使用深度信号，不能替代真实 Outcome。

## 团队学习应该围绕真实 Case

更有效的训练材料是现实里的 Incident、Workflow、Eval、Tool、Agent Failure。内部案例应该保留原来怎么做、为什么卡住、AI 先解决哪一步、哪里失败、后来增加什么机制、最终什么指标变化。

只有提效百分比、没有失败机制的成功故事，几乎没有工程教学价值。

## 第六条飞轮：Security Incident → Security Regression / Policy

~~~text
Prompt Injection / 越权 / 数据外泄 / Tool Misuse
↓
还原攻击链和 Evidence
↓
Security Failure Taxonomy
↓
Security Regression
↓
修 Permission / Policy / Tool / Workflow / Platform Primitive
↓
重新做 Security Eval / Red Team
↓
版本化发布
~~~

这样新项目不需要重新理解一次同样的安全问题，而是默认继承现有防线。

## 资产和能力必须允许淘汰

长期能力不是资产越来越多。还需要 Deprecate、Merge、Replace、Delete。

旧 Prompt 被 Skill 取代、旧 Workflow 被新 API 取代、旧 Agent 使用量归零，就应该退出。否则 Registry 最终会让使用者不知道应该选哪个。

## 把反馈分成三种，不要混在一起

~~~text
User Feedback
→ 好不好用

System Evidence
→ Trace / Outcome / Cost

Eval Evidence
→ Regression / Benchmark
~~~

三种信息一起看，才能决定怎么改。只听用户评价可能定位不到根因；只看 Eval 又可能看不到线上真实需求变化。

## Roadmap 应该从 Gap 和 Friction 产生

比今年要做 Multi-Agent 平台更好的 Roadmap 输入是：哪类业务需求反复做不起、哪类 Failure 反复出现、哪类重复实现最多、哪个 Golden Path 摩擦最大、哪个 Security Gap 风险最高、哪个公共资产使用率高但可靠性低。

## 固定节奏让飞轮真的转起来

可以建立稳定节奏：每周看新 Failure、高频重复任务和 Asset 使用问题；每个 Release 跑 Regression、记录 Behavior Release、检查 Risk / Rollback；每月合并重复资产、复盘 Platform Friction、更新 Capability Map；每季度淘汰低价值资产、评估公共 Primitive、调整 Risk Tier / Governance。

周期不一定固定成同样数字，但没有节奏，持续改进很容易变成口号。

## 这套飞轮在当前工作区已经能看到哪些真实片段

这里讨论“组织能力”时需要控制事实强度。当前工作主要来自个人长期工程工作区，不应该把它包装成已经在大型公司完成的组织变革；真正可验证的是几个**小尺度飞轮已经反复发生**。

**Failure → Method / Automation。** 本机工程里曾反复出现长命令阻塞、timeout 后盲重试、边改边测、Browser 恢复重复探索等事故。稳定经验先进入 Engineering / Acceptance Skill，再把 Browser recovery、whole-file mutation 等机械步骤下沉到 Automation / Runner。见 [本机 Agent 工具链](../工程工具与运行时/本机Agent工具链.md)。

**Product Experiment → Shared Knowledge。** ChatWeb 真实做过 Tool / MCP / Local Dev，并完成过 API / Browser 验证；后来产品收缩成 Web Chat，这些能力退出产品，但 discovery / readiness / enablement / execution / approval 的分层经验没有一起删除，而是进入共享工程 Skill 与知识。见 [为什么 Tool、MCP、Local Dev 最终退出 ChatWeb 产品边界](../ChatWeb/07-为什么Tool-MCP-LocalDev最终退出ChatWeb产品边界.md)。

**Eval Failure → Better Eval。** ProFlow RAG 的排序假失败、SQL join 错误和 Reranker 持续负载 timeout 都没有被“调参数调绿”，而是分别修 Eval adapter、修权威关系读取、调整默认策略和回归集。见 [ProFlow RAG 历史证据与决策档案](../ProFlow-RAG/历史证据与决策档案.md)。

这些片段足以证明“工作可以留下可复用资产”的机制，但不能单独证明某个企业组织已经达到后文的 L4 / L5 maturity。后面的 Capability Map、固定治理节奏和跨团队 Platform 仍然是从这些机制向组织尺度推广时的设计框架。

## 最终飞轮：Outcome → Evidence → Asset → Better Outcome

~~~text
Real Outcome
↓
Trace / Evidence
↓
Eval / Failure / Feedback
↓
Learning
↓
Regression / Policy / Asset / Golden Path
↓
next project starts higher
↓
Better Outcome
~~~

当这条链持续运行，组织才真正获得复利。

AI 业务工程的终点不是一个超级 Agent，也不是一个巨大的 Platform。

更稳定的终点是：

> **每一次成功、失败和人工判断都能留下可复用证据，让下一次系统更快、更安全、更便宜地做对。**
