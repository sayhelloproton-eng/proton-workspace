# 怎样让 AI 反过来治理质量和业务

AI 最直观的用法，是直接完成业务任务。

但当系统已经积累大量 Trace、Feedback、Incident、Outcome 和人工 Review 后，还会出现第二层价值：

> **让 AI 帮助人理解系统本身正在发生什么。**

这不是让一个 Agent 自动决定所有治理动作，而是利用模型擅长的归纳、聚类、总结和模式发现能力，把海量生产材料变成更容易处理的 Evidence。

## 为什么生产数据很适合成为 AI 的分析对象

真实系统会持续产生 Trace、Error、Tool Result、User Feedback、Human Correction、Incident、Ticket、Outcome 和 Eval Failure。

这些材料数量大、结构不完全一致、包含大量自然语言，正是模型擅长处理的类型。

传统 Dashboard 能发现指标变坏了，AI 更适合帮助回答：

> **这些坏结果之间有什么共同模式？**

## 第一类价值：失败聚类

假设一周有 3000 条失败记录。

人工逐条阅读成本很高。可以先让系统抽取 task_type、failure_stage、tool、model、release、error、user_intent、risk、evidence 等结构化特征，再用规则、Embedding、聚类或模型归纳把相似失败放在一起。

最后得到：

~~~text
Cluster A
→ 退款政策旧版本
→ 42%

Cluster B
→ Tool timeout 后错误 Retry
→ 21%

Cluster C
→ 长对话 Context 丢失订单号
→ 13%
~~~

这比 3000 条原始日志更接近可行动问题。

## 第二类价值：Incident Triage

Incident Triage（事故分诊：根据影响范围、风险、证据和可能 Owner 对事故进行初步分类）可以帮助 SRE / Platform 团队快速处理大量告警。

模型可以辅助整理：

- 影响哪个版本；
- 可能属于哪一层；
- 相似历史 Incident；
- 当前已有 Evidence；
- 是否涉及高风险 Effect；
- 推荐先读哪些 Trace。

但最终 Severity、Owner 和高风险处置仍然应由确定规则或人确认。

## 第三类价值：从 Feedback 里发现真实需求

用户反馈通常是非结构化的：不准确、太慢、解释太长、总要人工补充、某类问题总失败。

模型可以帮助：

~~~text
Feedback
→ classify
→ deduplicate
→ cluster
→ quantify
→ link to task / release / outcome
~~~

这样产品团队看到的不再只是几十条抱怨，而是稳定 Failure Slice。

## 第四类价值：发现 Knowledge Gap

如果大量回答失败都指向找不到某类政策、文档版本冲突、Citation 总缺失或某主题总走人工，系统可以推断存在 Knowledge Gap（知识缺口：当前知识体系无法覆盖某类重复业务问题）。

但模型给出的缺口判断只是 Candidate。

真正进入知识库前还要确认 Source 是否存在、谁是 Owner、当前版本是什么、权限是什么、是否值得进入 Retrieval。

## 第五类价值：发现流程瓶颈

Trace 可以用来分析：

~~~text
哪里等待最长？
哪个步骤 Retry 最多？
哪个审批长期堆积？
哪些 Tool 调用没有带来新 Evidence？
哪些任务最终都被人工接管？
~~~

这类信息可以帮助判断真正瓶颈是在模型、流程、权限、外部系统还是组织协作。

AI 在这里更像 Process Mining 的语义增强层，而不是 Workflow Owner。

## 第六类价值：质量抽检

对于海量文本、对话、报告，可以使用 AI 做第一层质量筛查：

- 是否缺关键字段；
- 是否引用错误来源；
- 是否违反格式；
- 是否存在明显不一致；
- 是否需要人工 Review。

低风险场景可以直接用于自动分流；高风险场景更适合 AI triage → suspicious cases → human review。

重点是扩大人工注意力覆盖，而不是假装完全替代专家。

## 第七类价值：安全异常发现

生产 Trace 也可能暴露异常 Tool 组合、权限拒绝突然增加、Prompt Injection 模式、某 Tenant 异常调用、Credential 使用异常、高风险动作突然变多。

AI 可以帮助归纳这些复杂事件，但真正封禁、撤权、Kill Switch 仍然应该由 Security Policy 控制。

## AI 治理 AI 最大的风险是自我确认

如果同一个模型产生结果、自己评估、自己总结原因、自己批准修复，系统会形成闭环自证。

更可靠的结构是：

~~~text
AI proposes finding
↓
Evidence refs
↓
deterministic metric / authoritative source / human review
↓
accepted finding
↓
change / regression
~~~

AI 可以缩短分析成本，但不能因为分析文本写得有说服力就成为 Truth Owner。

## 治理输出应该结构化

一个有用 Finding 可以包含：

~~~text
finding_id
category
affected_slice
release
evidence_refs
estimated_frequency
risk
suspected_owner
recommended_next_check
confidence
~~~

这样后续可以进入 Ticket、Eval Backlog、Incident、Knowledge Backlog 或 Product Backlog，而不是只生成一份读完就丢的周报。

## AI Ops 周报应该追踪变化

有价值的报告更像：

~~~text
本周新增 Failure Cluster
旧问题是否下降
哪些 Release 引入退化
成本增长来源
人工接管主要原因
知识缺口变化
安全异常
需要 Owner 决策的事项
~~~

最好还能对比 Baseline 和上周状态。

“本周总请求 100 万”属于 Dashboard；“某类退款问题从 2% 升到 11%，集中在 release B”才是治理洞察。

## 生产材料进入 AI 分析前要先治理数据

Trace、Feedback、Ticket 可能包含 PII、Secret、客户业务数据、Credential、内部地址。

所以分析管道要先做：

~~~text
Data Classification
→ Access Control
→ Redaction / Minimization
→ Analysis
→ Evidence Reference
~~~

不能因为任务是治理就获得无限数据权限。

## AI 发现的问题也需要 Eval

例如一个失败聚类器应该验证 Cluster 是否稳定、同类问题是否真的被聚在一起、False Merge 是否过高、是否漏掉关键高风险 Failure、人工是否能基于结果采取行动。

治理型 AI 也不能免于 Eval。

## 最终目标是把海量生产噪声压成少量可行动事实

~~~text
Trace / Feedback / Outcome
→ structured extraction
→ clustering / analysis
→ Finding
→ Evidence
→ Owner
→ Action
→ Regression / Asset
~~~

AI 最适合的是中间的语义压缩和模式发现。

真正的治理能力来自最后几步：Finding 有证据、有人负责、能进入修复和回归。

所以“AI 反过来治理 AI”真正成立的条件不是再加一个 Supervisor Agent，而是：

> **让模型帮助发现模式，让正式系统决定事实、责任和动作。**

但一旦这些 Finding 不再只用于“看”，而是开始驱动修复、撤权、业务操作或自动处置，新的问题就出现了：**谁在执行、它到底被允许做什么、可以无人连续做到哪一步？** 下一篇 [Agent 的身份、权限和自治边界怎样设计](./08-Agent的身份权限和自治边界怎样设计.md) 就把这条治理链推进到真实执行权。
