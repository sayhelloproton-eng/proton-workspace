# AI 上线以后怎样真正看见它在发生什么

传统服务上线以后，团队通常先看 QPS、错误率、CPU、内存和接口延迟。AI 系统如果只看这些指标，往往会出现一种危险状态：服务看起来很健康，用户却开始觉得答案变差、Tool 越来越慢、成本突然上涨，或者某个 Prompt / Knowledge 版本已经让系统行为发生明显变化。

原因在于 AI 系统的生产行为不是一段程序单独决定的，而是：

~~~text
Input
+ Model
+ Prompt
+ Context
+ Knowledge / Retrieval
+ Tool
+ Workflow / Runtime
+ Permission
+ Environment
→ Behavior
→ Outcome
~~~

Production Observability（生产可观测性：通过 Trace、Metric、Log、Version 和 Outcome 还原线上系统真实行为）的任务，就是让这条行为链可以被重新看见。

## 可观测性的第一目标不是“日志更多”，而是能回答为什么

一个线上问题真正需要回答的是：

~~~text
这是谁的请求？
目标是什么？
走了哪条路径？
用了哪个模型和 Prompt？
检索到了什么知识？
调用了哪些 Tool？
哪些步骤失败或重试？
当时是什么版本？
最终现实结果是什么？
成本和延迟花在哪里？
~~~

如果这些信息散落在不同服务日志里，排障仍然只能靠人工拼图。

因此 AI Observability 的组织单位应该优先围绕 Task / Session / Trace，而不是围绕单个进程。

## Session、Trace、Span 各自回答不同问题

Session（会话）适合描述一段用户交互或业务上下文。

Trace（轨迹）描述一次请求或一个 Task 从进入系统到结束经历了什么。

Span（跨度：Trace 中一个局部动作的可观测单元）可以对应：

- Model Invocation；
- Retrieval；
- Tool Call；
- Policy Check；
- Validator；
- External API；
- Retry / Fallback。

~~~text
Session
└─ Task / Trace
   ├─ Retrieval Span
   ├─ Model Span
   ├─ Tool Span
   ├─ Model Span
   └─ Validation Span
~~~

Span 越细不一定越好。真正有价值的是能定位实际行为第一次偏离预期的位置。

## Trace、Metric、Log / Event 不要混成一类东西

三者最好各自承担不同问题。

### Trace

回答：

> 这一次任务具体经过了什么？

它适合看路径、依赖、顺序、版本和上下文。

### Metric

回答：

> 整体趋势是不是变了？

例如：

~~~text
task_success_rate
quality_score
human_handoff_rate
fallback_rate
p95_latency
cost_per_successful_task
~~~

Metric 适合发现“哪里值得进一步查”。

### Log / Event

回答：

> 某个组件在某一刻发生了什么具体事件？

例如 Tool 返回 409、Provider 12:03 开始 timeout、Policy 拒绝某动作。

一个完整排障链常常是：

~~~text
Metric
→ 发现退款 Agent 成功率下降

Trace
→ 失败集中在 createRefund Span

Log / Event
→ 支付服务从 12:03 开始 timeout
~~~

它们应该共享 trace_id / task_id / release_id 等上下文，而不是互相替代。

## 一条 Trace 必须能回到版本

同一个输入，在以下任意一层发生变化后都可能得到不同结果：

- Model / Provider；
- Prompt / System Instruction；
- Reasoning Profile；
- Knowledge Source；
- Index / Embedding；
- Retrieval / Reranker；
- Tool Schema；
- Workflow；
- Runtime；
- Policy；
- Feature Flag。

因此 Trace 至少应该能记录：

~~~text
trace_id
task_id
session_id
release_id
model_revision
prompt_version
knowledge_version
retrieval_version
tool_contract_version
workflow_runtime_version
policy_version
started_at
ended_at
outcome
quality_score
total_tokens
total_cost
~~~

不是所有系统都必须使用这些同名字段，但这些事实不能全部丢失。

## Output 和 Outcome 必须同时观测

模型返回了一段看起来很好的回答，不代表业务成功。

客服系统可以出现：

~~~text
Model Output
→ 回答看起来正确

Real Outcome
→ 用户继续追问
→ 最终转人工
→ 订单仍然没解决
~~~

Coding Agent 也一样：

~~~text
Output
→ 模型说修改完成

Outcome
→ Diff 是否正确
→ Test 是否通过
→ Runtime 是否真的生效
~~~

如果生产观测只记录 Model Output，会把大量业务失败掩盖成技术成功。

## 生产指标至少分四组

### Quality

例如：

- task_success_rate；
- resolution_rate；
- quality_score；
- user feedback；
- hallucination / groundedness signal；
- human_handoff_rate。

### Reliability

例如：

- timeout；
- retry_count；
- loop_count；
- fallback_rate；
- recovery success；
- partial completion。

### Performance

例如：

- TTFT；
- end-to-end latency；
- retrieval latency；
- tool latency；
- queue wait；
- p50 / p95 / p99。

### Cost

例如：

- input / output / cached tokens；
- reasoning usage；
- external tool cost；
- human review；
- cost_per_task；
- cost_per_successful_task。

如果 Dashboard 只有 Token 和 Latency，看不到 Quality；只有 Quality，也看不到系统是否已经变得不可运营。

## Drift 不只发生在模型

Drift（漂移：生产输入、知识、配置或系统行为相对基线发生持续变化）可以来自很多层。

### Traffic Drift

用户输入和任务分布变化。

### Knowledge Drift

知识源、权限、文档结构、索引新鲜度变化。

### Model Drift

模型 Revision、Provider、Serving 行为变化。

### Prompt / Context Drift

Prompt 没变，也不代表真实 Context 没变；History、Retrieved Context、Tool Result 都可能变化。

### Retrieval Drift

Embedding、Chunking、Top-K、Reranker、Fusion 变化。

### Tool Drift

API、Schema、错误码、权限、延迟变化。

### Workflow / Runtime Drift

路径分布、Retry、Stop Rule、Fallback、状态转换变化。

### Cost / Latency Drift

即使成功率稳定，调用次数、Context 或外部依赖变化也可能让成本失控。

## 监控一定要按版本和任务切片

总平均值经常最危险。

例如总体成功率仍是 93%，但：

~~~text
refund_high_risk
→ 72%

normal_faq
→ 98%
~~~

或者：

~~~text
release A
→ 96%

release B
→ 89%
~~~

因此至少要支持：

- task slice；
- risk tier；
- tenant / user group；
- model / prompt / release；
- tool；
- error class；
- environment。

平均值适合看趋势，Slice 才适合做决策。

## 线上质量不可能全部人工看

高流量系统通常要组合多种信号：

~~~text
deterministic checks
+ sampled human review
+ calibrated LLM Judge
+ user feedback
+ business outcome
~~~

高风险、异常、差评和新 Release 可以提高 Sampling（采样）比例；普通稳定流量则可以低比例抽查。

Sampling Policy 本身也应该版本化，否则不同时间段的质量数据无法直接比较。

## Trace 还要保留最小充分 Evidence

完整保存所有 Prompt、文件和 Tool Result 会产生隐私、成本和安全问题。

可以区分：

~~~text
metadata
structured event
redacted payload
reference
full evidence
~~~

敏感数据不应该因为“为了排障”就默认永久保存。

有稳定 Source 时优先保存 Reference，需要时再通过权限回读原始 Evidence。

## 告警不要只用固定阈值

“成功率低于 90% 告警”很容易在不同业务时段制造噪声。

更可靠的告警可以结合：

- 历史 Baseline；
- 环比变化；
- 同一 Slice 的正常波动；
- Release 前后差异；
- Error Budget；
- 风险权重。

例如：

~~~text
总体成功率只下降 1%
但高风险退款下降 18%
→ 应该告警
~~~

对有明显周期性的业务，还要按时间段建立 Baseline，不能拿凌晨和白天直接比较。

## 最容易被忽略的是“分母”

看到 human_handoff_rate 下降，不能立刻判断系统更好了。

可能同时发生：

~~~text
human_handoff_rate ↓
自动处理率 ↑
错误退款率 ↑
~~~

同样，cost_per_task 下降也可能只是因为大量任务提前失败。

因此 Metric 必须问清分母和样本集合：

- 全部请求？
- 完成任务？
- 成功任务？
- 某个 Release？
- 某个 Risk Tier？

分母不清楚，漂亮指标很容易制造错误结论。

## Production Dashboard 应该围绕问题设计

一个可用 Dashboard 不只是堆图，而应该能回答：

~~~text
今天整体 Outcome 是否退化？
哪个 Slice 最差？
哪个 Release 开始变化？
成本增长来自哪里？
最常见 Failure 是什么？
哪些 Tool / Provider 在拖慢任务？
哪些任务正在 Loop / Retry？
哪些异常值得进入 Regression？
~~~

这样 Dashboard 才是运维和产品决策入口。

## 一个实用的 Trace 排障顺序

面对单个异常 Task，可以按下面顺序收窄：

~~~text
1. Outcome 到底错在哪？
2. 哪个 Span 首先偏离预期？
3. 当时对应什么 Release / Version？
4. 输入和 Context 是否发生变化？
5. Retrieval / Tool 是否返回异常？
6. Retry / Fallback / Loop 是否放大问题？
7. 是否属于单例，还是同 Slice 大面积发生？
~~~

这比从最后一个 Error Message 反向猜更快。

## Trace 应该成为 Eval 和 Incident 的桥

~~~text
Production Trace
→ Failure Detection
→ Incident / Review
→ Root Cause
→ Regression Case
→ Future Release Gate
~~~

一条高价值失败如果只修线上、不进入 Regression，下一次很可能再次出现。

反过来，Eval 中定义的 Slice 和 Criterion 也应该进入生产 Dashboard，这样 Offline 和 Online 才使用同一套质量语言。

## 三个真实工程现场怎样校准了这套可观测性判断

这些结构不是为了把传统 Observability 换一套 AI 名词。几个真实项目分别暴露过“看到了日志，却仍然解释错现实”的问题。

**ChatWeb 的 SSE 终态曾经被 finish-only access log 漏掉。** Browser 主动断开连接时，不一定触发正常 `finish`；如果日志只认正常完成，系统会把真实 client disconnect 从观测面里抹掉。后续改成 `finish / close` 双终态并保证 exactly-once 记录，才真正能区分 completed 与 closed。这个事故说明 Trace / Event 首先要忠实描述真实生命周期，而不是只记录“成功路径里方便记录的事件”。见 [ChatWeb 历史证据与决策档案](../ChatWeb/历史证据与决策档案.md)。

**ProFlow 反复证明 Source 绿、Runtime adopted、Browser Effect 和业务 Task terminal 是不同观测层。** 一次 Source Gate PASS 不能推出 Extension 已加载新版本，更不能推出用户场景已经成功；所以它把 Source、Package、Workspace、Runtime、Browser / External Reality 和 Product Acceptance 分层。见 [ProFlow 怎样从一次跑通走向长期可运行的工程系统](../ProFlow/05-ProFlow怎样从一次跑通走向长期可运行的工程系统.md)。

**ProFlow RAG 又把“进程活着”和“能力可服务”拆成 liveness / readiness。** API 可以回应 HTTP，但 ACTIVE Snapshot 或 Embedding truth 不成立时，能力仍然不可用；Reranker 默认关闭则不应该成为 readiness blocker。见 [从一次构建走向长期 Maintenance](../ProFlow-RAG/06-从一次构建走向长期Maintenance.md)。

三类事故共同校准了一个边界：Observability 不是“多收集一些模型日志”，而是让**不同 Owner 的事实能够在同一次 Task / Release / Outcome 上重新对齐**。

## AI Observability 的最终目标

真正成熟的生产可观测性，不是日志更多，而是系统能回答：

> **这次 AI 为什么会这么做，当时依赖了什么事实和版本，哪里开始偏离预期，最终业务结果是什么，以及下一次怎样防止同类问题再次出现。**

做到这一点以后，AI 系统才从“能上线”进入“可运营”。
