# AI 系统到底应该怎么评

一个模型在离线 Benchmark 上很强，放进真实产品以后仍然可能失败。

原因很简单：最终结果不只由模型决定。

~~~text
User Input
→ Context / Retrieval
→ Model
→ Tool / Workflow / Agent
→ Environment
→ Artifact / Effect
→ Outcome
~~~

任何一层都可能成为第一分歧。因此 AI 系统评测不能把所有失败都压成模型答错了，而要建立一条从局部组件到真实 Outcome 的证据链。

## 先定义最终成功是什么

系统 Eval 的第一步不是选 Grader，而是写清 Success Criteria（成功标准：什么现实结果才算任务完成）。

例如 RAG 客服的成功不是生成了一段回答，而可能是读取当前政策、正确回答、引用有效来源、没有泄露无权数据，并且用户不需要再次咨询。

Coding Agent 的成功也不是修改了代码，而是 Scope 正确、Diff 正确、Test 通过、没有破坏无关 WIP，并且目标产品行为成立。

## 先保留一个简单 Baseline

Baseline（基线：当前已经在用、或更简单的可替代方案）是系统 Eval 最容易被遗漏的部分。

如果一个 Agent 成功率 85%，但普通 Workflow 已经能做到 92%，Agent 能工作并不能证明它更值得。

真正需要比较：

~~~text
candidate
vs
current baseline
~~~

并同时看 success、latency、cost、human intervention、recovery 和 risk。

没有 Baseline，只能证明方案可行，不能证明它有增量价值。

## 组件 Eval 和 End-to-End Eval 必须同时存在

Component Eval（组件评测）用来定位哪一层有问题。

End-to-End Eval（端到端评测）判断整条业务链最终是否成立。

只有前者，会出现每个组件都 PASS、整体仍失败；只有后者，又很难定位该修哪里。

## RAG 应该分 Retrieval、Context、Generation、Citation

Retrieval 看 Recall@K、Precision@K、source coverage、Freshness 和 permission filtering。

Context 看正确证据是否进入、噪声是否过多、旧版本是否压过新版本、Token Budget 是否裁掉关键内容。

Generation 看证据正确时模型能否正确综合、遵守业务规则，并在不确定时拒绝或升级。

Citation Faithfulness（引用忠实度）则单独判断引用是否真的支持对应 Claim。

完整机制见 [模型为什么必须使用外部知识](../现代AI工程/03-模型为什么必须使用外部知识.md)。

## Agent Eval 至少要同时看五层

~~~text
Outcome
Task Completion
Side Effect
Trajectory
Reliability
~~~

Outcome 是最终业务目标是否成立。

Task Completion 是任务是否真的走到合法完成状态，而不是模型自己说完成。

Side Effect（副作用）要检查正确对象、正确次数、正确参数，以及是否产生额外破坏。

Trajectory Eval（轨迹评测）看 Tool、参数、重复搜索、Loop、越权、错误 State、提前结束和不必要成本。

Reliability（可靠性）则看多次运行是否稳定，而不是偶尔成功。

## Artifact Eval 和 Effect Eval 也要分开

~~~text
release package exists
≠ deployment succeeded

refund request sent
≠ refund completed

button clicked
≠ target object updated
~~~

Artifact 可以通过结构、Test、Diff 评估。

Effect 必须回读权威系统。

## Golden Set 应该小而真实

Golden Set（黄金样本集）不需要一开始就很大，但至少应该覆盖：

- 高频正常场景；
- 历史失败；
- 边界输入；
- 高风险动作；
- OOD；
- 长 Context；
- Tool Failure；
- 应该拒绝 / 升级人工的样本。

只包含顺利样例会高估系统能力。

## Dataset 最好分四类

一套可维护的 Eval Suite（评测套件）可以区分：

- Development Set：日常开发和 Prompt 调整；
- Regression Set：已经修过、不能再回来的历史失败；
- Challenge Set：边界、高风险、复杂场景；
- Holdout Set：尽量不参与日常调参，用来检查是否只是在适配已知 Case。

不同集合承担不同职责，也能降低 Eval Overfitting。

## Grader 按确定性从低成本到高成本排列

| 结果 | 优先 Grader |
|---|---|
| JSON / Schema | deterministic parser |
| 代码行为 | test / compiler |
| 数据事实 | SQL / authoritative API |
| 浏览器结果 | DOM + business readback |
| 业务规则 | policy / validator |
| 文本开放质量 | rubric + human / LLM Judge |
| 高风险合规 | domain expert / human |

越能机械判断，越应该机械判断。

## Eval Harness 自己也可能有 Bug

Eval Harness（评测托架）如果错误构造请求、错误解析输出或使用错误版本，会制造 Fake Failure。

端侧模型曾出现过真实例子：请求在到达模型前就被 Harness 的 Schema 错误拒绝。如果直接计入模型失败，会完全误判能力。

因此 Eval Harness 也需要自己的 Contract、Fixture 和回归。

## Requirement、Verification、Evidence 必须双向追溯

Eval 体系还有一种更隐蔽的失真：Requirement（正式需求）、Verification（验证方法）和 Evidence（验收证据）各自维护久了以后，验收表可能逐渐变成第二套需求系统。

最直观的检查通常只有一个方向：

~~~text
Requirement
→ Verification
→ Evidence
~~~

它可以发现“正式需求有没有测试、测试有没有证据”，但还不够。

真实工程里还会出现相反的问题：

~~~text
Acceptance Matrix
→ 新增了一个检查项
→ 这个检查项长期被当成必须满足
→ 但正式 Requirement Owner 从未定义过它
~~~

这意味着 Verification 已经开始偷偷发明产品要求。后续团队可能为了让 Matrix 变绿修改实现，却没有人再问“这个行为到底是谁要求的”。

所以可追溯性必须双向成立：

~~~text
Owner Requirement
→ exactly mapped Verification
→ Evidence

同时反查：

Evidence / Verification / Acceptance Matrix
→ 必须能够回到正式 Requirement Owner
~~~

双向检查分别防两类漂移：

- Requirement 有定义但没有 Verification：需求被漏测；
- Verification / Matrix 有检查但没有 Requirement Owner：验收体系篡位成需求真源。

ChatWeb 的真实工程阶段曾同时暴露过这两种问题：一部分 Requirement 存在于正式 Spec 却没有进入 Acceptance Matrix；另一部分检查项只存在于 Matrix，没有 Owner Spec 定义。只有把两个方向都机械检查，最终 Gate 才真正收敛成“验证正式要求”，而不是“验证自己维护出来的表”。

这个原则也适用于更广的 AI 系统：

~~~text
Product / Domain Requirement
→ Eval Case
→ Grader / Runtime Check
→ Evidence

并且：

Eval Case / Gate / Dashboard
→ 能解释自己验证的是哪条正式 Requirement
~~~

如果一个 Gate 不能回答“我为什么存在、由哪个 Owner 定义成功语义”，它最多是一个候选检查，不应该独立改变产品 Truth。

## Failure Taxonomy 让 Eval 能指导修复

系统失败至少可以按 Owner 分类：

~~~text
Input / Task Definition
Context
Knowledge / Retrieval
Model
Tool Selection
Tool Execution
Permission / Policy
Runtime / Recovery
Environment Observation
Coordination / Handoff
Evaluator
~~~

如果所有失败都叫 hallucination，团队永远不知道该修哪一层。

每个 Failure Bucket 最好还能指向下一步检查。例如 retrieval_miss 查 Source/Query/Index，duplicate_effect 查 Idempotency/Recovery，false_eval_failure 查 Grader/Harness。

## Regression 把一次事故变成永久防线

~~~text
production failure
→ root cause
→ create regression case
→ fix
→ future release runs same case
~~~

否则修复只存在某几个人记忆里。

## 小 Eval 和大 Eval 应该有不同运行节奏

高频开发可以跑快速 Golden Set、核心 Regression、Contract / Safety smoke。

大规模多 Trial、长任务 Agent、Human Review、Shadow Comparison 可以定期或 Release Gate 运行。

不要因为 Full Eval 太贵，就让开发阶段完全没有 Feedback。

## Offline Eval 和 Online Eval 各自解决什么

Offline Eval（离线评测）可重复、便于比较候选、风险可控。

真实线上还会出现新输入分布、Session 行为、真 Tool 延迟、权限、环境漂移和人的实际使用方式。

所以候选通常逐步经过：

~~~text
Offline
→ Shadow
→ Canary
→ broader rollout
~~~

## Shadow、Canary、A/B 的目标不同

Shadow（影子运行）让新系统处理真实流量副本，但结果不影响正式业务，适合模型、Prompt、Retrieval、Router 的真实分布比较。

Canary（金丝雀发布）让少量受控真实流量进入候选版本，需要提前定义 traffic scope、risk scope、comparison metrics、rollback trigger 和 observation window。

A/B Test 适合比较转化和体验，但高风险动作不应该为了统计显著性无边界实验。

## Evaluation Version 必须可追溯

一次 Eval 至少要能回到：

~~~text
dataset_version
model_version
prompt_version
knowledge_version
retrieval_version
tool_version
workflow/runtime_version
grader_version
~~~

否则一个月后看到成功率 87%，已经不知道测的是哪套系统。

## 线上失败要进入 Eval Backlog

low score、human correction、incident、unexpected fallback、permission denial、loop、timeout 等信号经过脱敏和标注后，可以进入 Failure Review，再决定是否成为 Regression Case、Security Case、New Slice、New Rubric 或 Knowledge Freshness Test。

## Eval 最终要和 Economics 放在一起

如果候选系统成功率提高 1%，但延迟增加 5 倍、成本增加 10 倍、人工审批增加很多、Recovery 变差，它未必是更好的业务系统。

最终决策至少同时看：

~~~text
Task Success
Critical Error
Side Effect Error
Reliability / pass^k
p50 / p95 Latency
Cost per Successful Outcome
Human Intervention
Recovery Success
~~~

## 一套完整的系统 Eval 闭环

~~~text
Real Task
↓
Golden / Regression / Challenge / Holdout
↓
Component Eval
↓
End-to-End Eval
↓
Failure Slice
↓
Compare Baseline
↓
Shadow / Canary
↓
Production Outcome
↓
New Failure
↓
Regression
~~~

这条链真正建立以后，Eval 不再是上线前的一次考试，而是系统持续演进的反馈基础设施。

下一篇开始进入生产：**系统已经上线以后，怎样看见它每一次真实行为。**
