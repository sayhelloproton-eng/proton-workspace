# 团队怎样建立公共 AI 能力而不是重复造轮子

当多个产品开始使用 AI，最常见的早期状态是每个团队自己接模型、自己做 RAG、自己写 Tool、自己做 Eval。短期这样最快，但产品增加以后，Provider 接入、权限标准、Eval、Tool Contract、Trace 和安全边界会反复被重新发明。

这时才出现公共 AI 能力的需求。

## 共享的应该是 Primitive，不是所有业务逻辑

Shared Primitive（共享原语：多个产品稳定重复需要、但不包含具体业务流程的基础能力）常见包括 Model Access、Knowledge Access、Tool / Capability Contract、Identity / Policy、Eval、Observability、Asset Registry、Cost / Quota 和 Security。

业务 Product 仍然拥有 Goal、Domain Rule、Workflow、User Experience 和 Outcome。公共层不应该把所有业务都吸进去。

## 从重复问题出发，而不是从平台愿景出发

平台化前先问：哪些东西被至少两个真实产品重复实现、哪里已经出现不一致、哪类维护成本正在放大、哪些合同已经稳定、哪些能力需要统一治理。

如果答案只是未来可能有人会用，优先继续保持项目内实现。

一个有效规则是：

> **每一个新的 Platform Primitive，都应该有真实业务消费者。**

最好来自不止一个场景。

## 第一层：Model Access 统一怎样拿到模型能力

多个产品都会需要 Provider Adapter、Model Contract、Model Catalog、Routing、Quota、Usage、Health 和 Fallback。

共享 Gateway 可以减少重复，但它不应该拥有业务 Task。它提供的是计算访问，不是产品决策。

内部稳定 Contract 可以屏蔽 Provider 私有字段，但不能假装不同模型能力完全相同。

## 第二层：Knowledge Access 统一怎样拿到可信事实

可以共享 ingestion、parser、index、vector / keyword、rerank、provenance、permission filter 和 freshness metadata。

但 Knowledge Source 的业务 Ownership 仍然属于各自系统。平台不能因为维护 Index 就变成所有知识的最终 Truth Owner。

## 第三层：Tool / Capability Contract 统一动作边界

Tool Registry 应该管理：

~~~text
capability
owner
schema
version
permission
risk
provider
health
consumers
~~~

Registry 的价值是治理和发现，不是让模型一次性看到更多 Tool。

## 第四层：Prompt / Context Loader 统一稳定装配，不统一业务 Prompt

团队会反复需要 System Instruction 版本化、Prompt Template、Stable Context Pack、Tool Definition Loading、Tenant / Project Context。

这些可以共享 Loader、Version 和 Contract，但业务 Goal、领域规则仍然由产品拥有。公共层不应该把所有 Prompt 变成一个中央模板。

## 第五层：Eval Runner 统一怎样跑，业务定义什么叫对

如果每个团队自己写 Eval Harness，很容易出现 Dataset 格式不同、Metric 不同、Judge 不同、Version 不可追溯、结果无法比较。

共享 Eval Primitive 可以统一：

~~~text
case contract
runner
grader interface
version metadata
result store
regression
report
~~~

具体 Success Criteria 和 Rubric 仍然由产品定义。

## 第六层：Observability 统一 Trace Contract

跨产品公共能力可以统一：

~~~text
trace_id
task / session
release_id
model span
retrieval span
tool span
outcome
error class
tokens / cost
~~~

统一 Trace Schema（轨迹结构合同）通常比统一 Dashboard UI 更重要。有共同字段以后，平台才有机会发现跨产品共性故障。

## 第七层：Security / Identity 统一硬边界

例如 Identity Contract、Credential Broker、Tool Policy、ACL / Scope、Network Boundary、Audit Schema、Kill Switch、Security Eval。

不同产品 Risk Tier 可以不同，但硬安全能力不应该各自发明一次。

## 第八层：Asset Registry 让可复用能力不再散落

除了 Tool，团队还会重复 Prompt、Skill、Workflow、Dataset、Eval Set、Runbook 和 Context Pack。

一个轻量 Asset Registry 可以记录 Owner、Version、Status、Scope、Consumers、Evidence 和 Replacement。重点是可发现和可治理，不是先建设复杂门户。

## Build、Buy、Wrap 是三个不同选择

Build 适合核心差异化能力，或外部方案明显不满足需求。

Buy 适合非核心、标准化程度高的能力。

Wrap 则保留外部 Provider，但在内部加稳定 Contract / Adapter：

~~~text
internal stable contract
→ adapter
→ external provider
~~~

这样外部产品可以替换，内部产品不用跟着大改。

## Library、Shared Service、Platform 不要混成一个词

如果只是代码复用，Library 可能已经够用。

Shared Service（共享服务）开始承担网络可用性、SLO、Version、Capacity 和多 Consumer。

Platform 进一步承担 Governance、Control Plane、Multi-tenancy、Quota、Discoverability 和 Lifecycle。

不要为了平台化直接跳到最重形态。

## Public API 不等于 Public Platform

一个服务有 HTTP API，并不代表已经是平台能力。真正平台化还需要 Stable Contract、Owner、SLO、Version、Consumers、Quota、Security、Lifecycle 和 Support。

## Consumer List 和 Usage Analytics 决定平台是否真的有价值

公共能力变更前要知道谁在用、关键程度、当前版本和迁移成本。

平台团队也不应该只看服务 QPS、Registry 数量和文档数量，更应该看 Active Consumers、Task Success、Time Saved、重复实现是否减少、Migration Friction、Support Load 和 Escape Hatch Usage。

一个没人用的完美平台没有业务价值。

## Golden Path 不是强制唯一道路

Golden Path（黄金路径：团队完成常见 AI 工作时默认推荐的一套低摩擦、安全、经过验证的实现路径）可以包含模型调用、Retrieval、Tool、Eval、Trace、Release 和高风险权限申请。

它应该让正确做法更容易，而不是禁止所有差异。特殊产品仍然需要 Escape Hatch（逃生口：允许在明确责任下偏离默认路径）。

## Developer Experience 决定共享能力是否会被采用

如果正确平台方案需要申请三天、配置几十个字段、看十份文档、Debug 很难，团队会自然绕开。

所以公共能力还要优化 Quick Start、清晰错误、Local Dev、Example、Self-service、Observable 和 Migration。

## 平台绕过行为本身也是反馈

如果业务团队不断绕过平台，不要先归因成不规范。应该追：为什么正确路径更难、哪个 Contract 太重、哪个权限流程太慢、哪个 Debug 信息看不到、什么 Escape Hatch 被频繁使用。

Platform Friction（平台摩擦）本身是下一轮平台改进的 Evidence。

## 平台团队不能成为所有产品的排队瓶颈

公共能力应该尽可能 Self-service + documented contract + automation + delegated ownership。

如果每个 Prompt 改动都必须平台团队手工介入，平台反而降低整体 Lead Time。

## 共享能力也需要退出机制

某个内部组件如果消费者减少、外部标准成熟、运维成本过高、Contract 已可被通用方案替代，应该允许：

~~~text
deprecate
→ migrate
→ retire
~~~

平台不是永久增长的组件集合。

## 组织真正应该复用的是解决问题的方法

工具会换，Framework 会换，Provider 会换。长期应该保留的是：什么时候用 Workflow、什么时候用 Agent、怎么定义 Tool Contract、怎么做 Eval、怎么追 Trace、怎么做 Permission、怎么恢复失败、怎么判断平台化是否值得。

这些才是组织真正的 AI Engineering Knowledge。

## 两次反例比“应该做平台”更能说明共享边界

第一代 `ai-agent-platform` 曾经把 Knowledge Asset、Registry、Relation Graph、Projection、Context Runtime、Agent Profile、Publisher 等目标模型设计得非常完整。问题不是这些概念不存在，而是很多抽象在只有一个真实消费者时就先购买了治理成本。后来拆仓和知识重构保留下来的原则反而更轻：**真实 Owner 先存在，多个消费者和稳定 Contract 出现以后再共享。** 这段反例见[知识资产治理](../知识资产治理.md)和知识库总览。

ProFlow RAG / ChatWeb 的分离提供了正向样本。RAG 先成为 headless Capability Service，ChatWeb 再通过公开 Context Provider Contract 消费它；两边不共享数据库、不 import 对方内部 Domain type，RAG 拔掉以后普通 Chat 仍然成立。这里“两个仓库”不是平台化证据，**可拔除性 + 稳定 Contract + 独立生命周期**才是。见 [ChatWeb 为什么必须从 RAG 前端变成独立产品](../ChatWeb/01-ChatWeb为什么必须从RAG前端变成独立产品.md)。

本机 Browser 又展示了更小的一次共享：多个 Chat 真的会争同一个 Chrome owner 后，才出现共享 Browser Broker；Local Dev、CodeGraph、Repomix 并没有为了统一感一起塞进 Broker。见 [本机 Agent 工具链](../本机Agent工具链.md)。

因此“公共能力”不是把所有东西搬到中央平台，而是**只共享已经由第二、第三个真实消费者证明稳定的责任**。

## 公共能力真正成立的判断

~~~text
repeated across real consumers
+ stable responsibility
+ measurable duplication / risk
+ clear owner
+ reusable contract
+ governance need
+ adoption value > operational tax
~~~

这和 [AI 能力怎样最终变成产品和平台](../现代AI工程/14-AI能力怎样最终变成产品和平台.md) 的平台化原则一致。

最终目标不是减少所有重复，而是：

> **把已经稳定、重复、值得治理的责任共享掉，让产品团队把注意力留给真正不同的业务。**

公共能力建起来还不是终点。真正决定组织是否会越来越强的是：生产失败会不会变成 Regression，重复工作会不会变成 Asset，平台摩擦会不会改进 Golden Path，人的 Review 会不会沉淀成 Eval。下一篇 [组织怎样形成持续变强的 AI 能力飞轮](./12-组织怎样形成持续变强的AI能力飞轮.md) 会把这些反馈回路收成整套业务工程的最后一层。
