# AI 业务工程从哪里开始：先找对问题，再决定把责任交给 AI 到哪一步

AI 几乎可以插进任何信息工作：搜索、总结、写代码、分析数据、回复客户、操作软件、调用 API。真正困难的不是“能不能加一个模型”，而是两个更基础的问题：

1. **哪里值得用 AI？**
2. **一旦用了，责任应该交给 AI 到哪一步？**

一个任务很适合模型参与，不等于系统已经适合让 Agent 连续执行；一个 Demo 看起来很好，也不等于它改善了最终业务 Outcome（业务结果）。

## 先找真正限制结果的地方

研发场景很容易观察到这种错位。一项需求从提出到上线可能要三天，真正写代码只有两小时。如果 AI 把两小时压缩成二十分钟，却没有改善需求理解、影响分析、Review、测试和发布等待，最终 Lead Time（交付周期）不会按同样比例下降。

所以第一步不是问“哪一步 AI 最会做”，而是问：

> **哪一种限制现在最影响结果？**

~~~text
需求 / 输入
→ 理解
→ 获取事实
→ 判断
→ 生成 / 执行
→ Review / Validation
→ 发布 / 生效
→ Outcome
~~~

任何一段都可能是瓶颈。

### 代码生成很显眼，但不一定是瓶颈

CRUD、类型定义、数据转换、单测骨架很适合生成，因为输出清楚、验证也容易。

但成熟工程的大量时间花在找入口、理解调用关系、确认历史原因、找影响范围、补测试、Review 和排查线上事实。如果真正瓶颈在这些位置，继续优化生成速度只是在加快把工作推向下一个堵点。

### 有些价值来自扩大覆盖，而不只是节省时间

AI 还有一类更重要的价值：过去因为注意力和人力限制，某些工作根本做不起。

例如大型仓库中，不可能要求工程师每次改动都人工通读所有相关模块；海量客服记录也不可能全部人工检查；生产 Trace 很多时，人只能抽样看。

AI 配合结构化工具后，可以让这些工作第一次进入可执行范围：

- 更广的影响分析；
- 大规模质量抽检；
- Trace / Incident 聚类；
- 长文档和历史材料的批量理解；
- 大量候选测试的生成和筛选；
- 给刚接手系统的人快速建立局部心智模型。

这种价值不能只用“每次省几分钟”衡量，因为它改变了原来业务根本覆盖不了的工作上限。

## 优先把 AI 放在需要理解的地方，把确定性继续留给软件

~~~text
确定、可机械判断
→ Rule / SQL / Search / Type Checker / Test / Script

需要语义理解、归纳、生成、开放判断
→ Model

路径会随着新 Observation 改变
→ Agent

长期责任、等待、恢复
→ Runtime
~~~

formatter 能稳定格式化，就不要再让模型判断格式；精确符号搜索能回答函数在哪，就优先用结构化工具；权限能由 Policy 明确判断，就不要让 Prompt 决定。

AI 最适合承担确定性工具之间剩下的模糊部分。更完整的技术分层见 [现代 AI 工程](../现代AI工程/README.md)。

## AI 进来以后，有时应该重做流程，而不是原样加速

很多工作流中间产物存在，只是因为人和系统之间传递信息困难。

~~~text
需求文档
→ 人工拆任务
→ 每个人重新找代码
→ 开发
→ 手工整理测试点
→ Review 时重新解释背景
→ 发布前再写一遍变更说明
~~~

如果系统能持续携带 Goal、约束、Artifact、影响范围和 Evidence，那么每个环节重新整理一次未必有必要。

新的流程可以围绕同一个 Task Context（任务上下文）逐步更新：

~~~text
Task Context
├─ Goal / Constraints
├─ Relevant Source
├─ Current Plan
├─ Artifact Changes
├─ Test / Evidence
└─ Release Notes
~~~

这时 AI 改变的不是某个岗位，而是信息流。

## 判断一个场景是否值得做，可以连续追六步

1. 当前真正耗时或高风险的是什么：写、找、理解、等待、审核、返工，还是错误后果？
2. AI 减少的是有效工作，还是把工作换成了 Review？
3. 这一段变快以后，整条链会不会真的变快？
4. 有没有更便宜、更确定的方法已经能解决？
5. AI 是否让原来做不起的工作变得可做？
6. 结果做错以后能不能快速发现？

模型十秒生成，人工二十分钟检查，未必是提效。

反过来，如果工程师原来要半天才能摸清陌生模块，AI 配合代码图、搜索和文档把相关信息先整理出来，即使最后代码还是人写，价值也可能更大。

## 决定使用 AI 以后，先别急着换模型

很多“AI 能做但做不好”的问题，并不是模型能力不足，而是任务本身缺少承接条件。

一个实用排查顺序是：

~~~text
任务没说清
→ 补 Task Contract

任务说清了，但做判断所需的信息没进来
→ 补 Context

事实会变化、需要引用
→ 补 Retrieval / Tool

模型能判断，但结果下游无法稳定消费
→ 补 Output Contract

结果可解析，但不能证明正确
→ 补 Validator / Evidence

路径和状态开始变复杂
→ 补 Workflow / Runtime

这些都稳定以后仍反复暴露同一能力缺口
→ 再评估模型升级 / Few-shot / Fine-tuning
~~~

这个顺序非常重要。否则团队很容易用更强模型去掩盖输入、状态、工具或验证问题。

## Task Contract 先把“要做什么”说成可执行合同

Task Contract（任务合同：明确目标、输入、约束、成功标准和禁止事项）比一个宽泛 Prompt 更接近生产任务。

例如：

~~~text
Goal
→ 修复退款接口的重复提交问题

Allowed Scope
→ payments/refund/**

Must Preserve
→ 现有 API 兼容

Evidence
→ targeted tests + idempotency readback

Stop
→ tests pass / blocked by unknown external dependency
~~~

它解决的是“模型到底在完成什么”，而不是“模型应该扮演什么角色”。

任务合同越模糊，后面的 Context、Tool 和 Eval 越难定义。

## Context 要回答“做这个判断现在必须知道什么”

任务定义清楚以后，下一步不是把更多资料塞进 Prompt，而是问：

> 这个 Decision 依赖哪些事实？

Context（上下文：当前一次判断真正可见的工作集）可能来自代码、文档、数据库、Git、运行日志、历史事件和当前 State。

如果某个事实已经有权威工具，就应该查询那个 Owner，而不是让模型从旧聊天里猜。

动态事实也不要写进永久 Prompt。库存、版本、权限、当前 Task State 都会变化；稳定规则可以长期存在，实时事实应该运行时读取。

## Structured Output 让结果可以被软件检查

如果结果要进入程序，最好不要让下游继续猜自然语言。

~~~json
{
  "decision": "needs_review",
  "reason_code": "missing_business_rule",
  "evidence_refs": ["spec:refund-v3#section-4"]
}
~~~

Structured Output（结构化输出：让模型按固定 Schema 返回机器可解析结果）的价值，是把自然语言结果变成可检查合同。

但结构正确不等于业务正确。

~~~text
Schema Validation
→ 结果长得对

Semantic / Business Validation
→ 结果做得对
~~~

一个合法 JSON 里的状态仍然可能写错；一个 Patch 格式正确，也可能破坏真实行为。

## 输出最好带着证据和不确定性一起交付

比“答案 + 一段解释”更有价值的输出是：

~~~text
Decision
+ Evidence
+ Source / Version
+ Uncertainty
+ Next Action
~~~

例如：

~~~json
{
  "decision": "reject_refund",
  "reason": "outside_policy_window",
  "evidence_refs": [
    "policy:refund-v3#window",
    "order:8821#delivered_at"
  ],
  "confidence": 0.92,
  "needs_human": false
}
~~~

Evidence 让下游能回到现实世界验证，而不是只相信模型的自我解释。

## 找到值得用的位置之后，第二个问题才是责任交多少

同样是 AI 做研发，可以对应完全不同的责任深度：

~~~text
读资料
→ 解释
→ 给建议
→ 生成候选
→ 修改真实文件
→ 连续执行多步
→ 自己选择下一步
→ 完成测试 / 发布 / 收尾
~~~

从修改真实系统开始，AI 的结果会进入后续 State；从连续执行开始，前一次错误会被下一次继承。

这时风险不再只是回答错了，而是**错误被系统化放大**。

## 长任务的危险在于错误进入 State

大型重构是很好的例子。

第 1 批如果漏掉一个隐藏调用方，第 2 批可能基于错误边界继续迁移，第 3 批再删除旧实现。最后发现问题时，已经不是改一个文件，而是拆掉一串建立在错误前提上的变化。

所以长任务至少要把几类信息从聊天内容升成正式对象：

- Goal；
- Current State；
- Artifact Version；
- Evidence；
- Pending Work；
- Permission；
- Success Criteria。

这些内容怎样由 Runtime、State、Context、Memory 管理，完整机制由 [现代 AI 工程](../现代AI工程/README.md) 负责。

业务层只需要记住：

> **责任越连续，状态越不能靠模型自己记。**

## 自治边界还要看反馈速度和可恢复性

判断“能不能再多放一步权”时，可以连续问：

1. 当前事实够不够？
2. 这一轮怎么证明做对了？
3. 如果做错，下一轮开始前能不能知道？
4. 错了以后能不能回到可靠状态？
5. 一个错误会影响多大范围？
6. 当前 Task 到底需要什么权限？
7. 长任务状态由谁维护？

格式化、类型检查、Schema、单测反馈很快，适合更高自动化；跨模块重构、生产写入和外部发布反馈更慢、恢复更难，任务就应该拆得更细。

## 自主程度要和风险与验证一起决定

Autonomy（自主程度：AI 在无需人工逐步确认时可以连续执行到什么范围）可以用四个变量判断：

~~~text
reversibility
+ blast radius
+ observation reliability
+ validation strength
→ autonomy boundary
~~~

| 场景 | 自主程度倾向 |
|---|---|
| 只读搜索 + 明确证据 | 高 |
| 隔离 worktree 修改 + Test | 中高 |
| 共享配置修改 | 中低 |
| 对外发布 / 付款 / 删除 | 低，通常需要 Approval |

模型越强，只说明 Capability 上限提高；Permission 和风险边界仍然由软件控制。

## Human-in-the-loop 不等于系统不成熟

Human-in-the-loop（人在回路中：某些节点必须由人确认或判断）有两种完全不同的情况。

一种是设计上就应该有人承担高价值责任，例如法律判断、高风险付款、重大发布。

另一种是系统质量差，所有普通结果都需要人工重新做一遍。

成熟系统应该逐渐把人从重复检查移到高风险决策、异常样本、新 Failure Slice、Policy 变化和 Eval 校准。

## 一次 Demo 只能证明能做，不能证明值得交责任

~~~text
模型一次答对
< 固定样本稳定答对
< 接真实数据稳定完成
< 能在真实环境行动
< 能被验证和恢复
< 线上重复 Outcome 稳定
~~~

越往右，系统越接近长期业务能力。

后面的模型 Eval、系统 Eval、Observability、Release、Security 和资产化，就是因为能做只处在最左边。

## 最终判断：先找瓶颈，再购买复杂度

一个场景值得让 AI 进入，通常同时满足这些条件中的几项：

~~~text
存在真实业务瓶颈
+ 任务包含语义不确定性
+ AI 能降低有效成本或扩大覆盖
+ 有足够事实入口
+ 可以验证结果
+ 错误后果可控
+ 复杂度增量小于业务收益
~~~

如果问题已经能由确定性软件稳定解决，就停在那里；如果 AI 只需要给建议，就不要提前建设长期 Agent；如果任务必须跨时间、等待和恢复，再购买 Runtime；如果高风险副作用进入系统，再增加更严格的 Policy、Approval 和 Evidence。

AI 业务工程的第一条纪律因此不是尽量自动化，而是：

> **把概率智能放到最有价值的位置，并只交出当前证据足以支撑的责任。**

当这一层边界确定以后，新的约束才会变得明显：Context 会变长，Tool 和模型调用会增加，Agent 会出现更多回合，原本“能做”的系统开始变慢、变贵。下一篇 [AI 为什么越来越慢、越来越贵，以及怎样真正降低成本](./02-AI为什么越来越慢越来越贵以及怎样真正降低成本.md) 就从这里继续：不再讨论要不要用 AI，而是讨论怎样让一个已经值得做的 AI 任务以更低的总成本稳定成功。
