# AI 为什么越来越慢、越来越贵，以及怎样真正降低成本

AI 系统一开始通常很便宜：一个 Prompt，一次 Model Call，一个回答。

真正进入生产以后，链路会逐渐变成：

~~~text
用户请求
→ 读 History
→ RAG
→ Tool Discovery
→ Model
→ Tool
→ 再 Model
→ Validator
→ Retry / Fallback
→ Human Review
~~~

成本和延迟随之增长。如果只盯 Token 单价，很容易把问题看窄。真正应该优化的是：

> **Cost per Successful Outcome（每个成功结果的总成本）。**

一个便宜模型连续失败三次，再调用强模型并让人工修复，可能比一开始就走正确路径更贵。

## 先把“慢”和“贵”拆开

一次 AI Task 的总成本至少包括：

~~~text
Model input
+ Model output
+ Reasoning compute
+ Retrieval / Search
+ Tool / Browser / API
+ Queue / Waiting
+ Retry / Fallback
+ Storage / Network
+ Human Review
+ Repair Work
+ Failure Cost
~~~

延迟也类似：

~~~text
queue
+ prefill
+ decode
+ retrieval
+ tool wait
+ sequential turns
+ approval wait
+ retry / recovery
~~~

所以模型单价只是局部指标。

## 三个指标不要混在一起

Token Count 是同一段内容被 Tokenizer 切成多少 Token。

Per-token Cost 是当前模型 / Provider 处理这些 Token 的价格和计算成本。

Frontier Token Volume（高成本模型 Token 总量）则是系统真正送进昂贵强模型的总输入输出规模。

业务系统最能主动优化的通常是第三个：

~~~text
原始请求很多
→ 确定性工具先做
→ 小模型承接窄任务
→ Context 只保留必要证据
→ 强模型只处理复杂长尾
~~~

这比只压缩几句 Prompt 更有价值。

## 先找到成本占大头的那一段

优化前先测，而不是先安装“省 Token 工具”。

| 环节 | 关键指标 | 常见优化方向 |
|---|---|---|
| 模型输入 | input / cached tokens | Context Selection、压缩、裁历史 |
| 模型输出 | output tokens | Structured Output、Output Budget |
| 调用次数 | turns / requests | Cache、Stop Rule、减少无效 Loop |
| Tool | latency、result size | 按需加载、结果过滤、并行 |
| 人工 | Review、返工、接管 | 更早验证、证据化输出 |
| 失败 | retry / repair cost | Recovery、Fallback、路由 |

如果成本主要来自 Browser 等外部 Tool，压 Prompt 不会解决核心问题。

## 第一优先级：能程序化的先移出模型

最稳定的降本不是把 Prompt 再缩短 5%，而是把不需要概率判断的工作彻底移出模型。

~~~text
exact search → Search / CodeGraph
format transform → Script
schema validation → Code
known workflow → Workflow Engine
permission → Policy
aggregation → SQL
diff / test → deterministic tool
~~~

模型只处理剩余的语义判断。

这会同时减少 Token、调用次数、延迟和失败面。

## Context Optimization 真正管理的是信息生命周期

Context Engineering（上下文工程：决定这一轮模型应该看到哪些信息、以什么结构进入）不只是删 History。

可以先把输入分成：

~~~text
Stable Instruction
Current State
Working Context
Evidence
Tool Definition
Tool Result
History
Reference
~~~

它们不应该拥有相同寿命。

### Current State 不要重复用对话表达

如果 Task Status、Artifact Version、Pending Work 已经有结构化 State，就不要每轮把几十条旧对话重新喂进去。

### Working Context 只服务当前阶段

当前正在修改的文件、这一轮错误栈、当前候选方案属于 Working Context（工作上下文：只为当前阶段决策服务的临时信息）。

阶段结束以后，真正需要继承的是 committed State、Evidence Ref、Artifact 和 unresolved issue，而不是全部原始讨论。

### Tool Result 也应该有保质期

一次 Diff、一段 DOM、一个测试日志可能下一步非常重要，但十轮以后通常已经过期。

~~~text
即时结果
→ 当前 Turn 使用后退出

还会被后续验证
→ 保存 Artifact / Ref

改变了正式状态
→ 写入 State / Event
~~~

这样 Context 不会因为工具返回过一次就永久变胖。

## Pruning 和 Compaction 解决的问题不同

Pruning（裁剪：删除已经不需要的上下文）适合真正没有后续价值的信息。

Compaction（压缩：把仍需继承但原文太重的历史收敛成更小表示）适合长任务。

一个安全压缩至少要保住：

- Goal；
- Current State；
- Decisions；
- Constraints；
- Evidence Refs；
- Pending Work；
- Permission / Budget。

如果把“为什么不能改这里”压掉，下一轮模型会重新踩坑。

## 大对象尽量传引用

~~~text
full artifact repeated in every turn
→ artifact_ref + targeted read
~~~

需要细节时再读。

这对代码、文档、Tool Result、长日志都成立。保留 Reference 还能避免压缩以后无法回到原始证据。

## Tool Surface 本身就是固定 Context 税

工具少时感觉不明显；当系统接入几十或上百个 Capability，每个 Name、Description 和 JSON Schema 都可能成为固定输入。

更合理的是：

~~~text
all tools
→ hard permission filter
→ task relevance filter / Tool Search
→ small candidate set
→ model selection
~~~

Tool Search（工具检索：根据当前任务只加载少量相关工具定义）既降低 Token，也减少 Tool Selection Error。

如果某类 Tool 组合已经完全稳定，还可以用 Programmatic Tool Calling（程序化工具调用：由代码组织确定步骤，模型只提供必要语义参数）把不需要再判断的部分移出模型。

## Tool Result 可以压缩，但原始证据不能丢

Terminal 输出几万行、Browser DOM 几千节点，如果全部回填模型，Context 会快速爆炸。

可以先由确定性规则或低成本模型做结构化压缩：

~~~text
raw logs
→ error summary
→ key lines / refs
→ model
~~~

但压缩结果是 Derived Artifact（派生产物），不能替代原始日志。系统必须保留 Source Reference，需要时能回读。

## Prompt Cache、Pruning 和 Compaction 会互相影响

Prompt Cache（提示缓存：复用相同输入前缀的模型计算）希望前缀尽量稳定。

Context Pruning 却会修改历史。

如果每一轮都细碎删除旧内容，缓存前缀会频繁变化。

更合理的策略常常是：

~~~text
稳定前缀持续复用
→ Context 增长到阈值
→ 一次做足够大的 Prune / Compact
→ 形成新的稳定前缀
~~~

所以缓存命中率和上下文精简不是两个完全独立的优化。

## Exact Cache、Semantic Cache、Prompt Cache 各自解决什么

Exact Cache 在输入完全一致时复用结果。

Semantic Cache（语义缓存：针对相近输入复用已有结果）风险更高，因为语义相似不等于事实条件相同。实时库存、权限、当前 Git 状态通常不适合只靠它复用。

Prompt Cache 则复用相同前缀的模型计算。Token 逻辑上仍在 Context 里，只是 Provider 复用了部分 Prefill 计算，不能把 cached tokens 理解成“这些 Token 已经没有了”。

## Cache 必须设计 Invalidation

没有失效策略的缓存只是延迟错误。

至少考虑：

~~~text
version
time / TTL
source update
permission scope
tenant
model / prompt version
~~~

Knowledge Source 变化以后，相关缓存也应该失效或降权。

## Batch 主要优化吞吐，Parallelism 主要缩短关键路径

Batching（批处理）适合文档分类、Embedding、大量独立抽取、离线 Eval、批量质量检查。

它通常减少固定调度开销，提高 Throughput（吞吐：单位时间完成多少工作），但不一定让单个任务更快。

Parallelism（并行执行）主要缩短 Critical Path（关键路径：决定一次任务总完成时间的最长依赖链）。

前提是：

~~~text
input independent
+ write set independent
+ resource independent
+ merge rule known
~~~

Multi-Agent 数量增加不等于吞吐自动增加。

## 本地模型改变成本归属，不自动减少 Token

本地推理可以把云端 API 费用换成硬件、电量、内存、热量和运维，但同一段文本仍然可能拥有相同 Token Count。

所以“改成本归属”和“减少上下文”是两类优化。

真实端侧路径见 [端侧模型](../端侧模型.md)。

## 小模型和 Reasoning Budget 应该一起路由

[小模型为什么会成为 AI 系统里的高频语义执行层](../现代AI工程/15-小模型为什么会成为AI系统里的高频语义执行层.md) 已完整解释 Small-first。

业务层最重要的是建立 Cascade：

~~~text
Rule / Code
→ Small Model
→ Strong Model
→ Reasoning Model
→ Human
~~~

每一级都有明确 Escalation Condition，而不是所有请求默认进入最贵路径。

简单问题也不需要每次投入最大 Reasoning Budget。应该按 Task Difficulty、Risk、Validator Strength、Latency SLO 和 Cost Budget 路由。

## 输出预算经常比输入预算更容易直接控制

如果下游只需要几个字段，就没有必要让模型先写一页分析。

Structured Output 和 Output Budget 可以同时限制：

- max output；
- required schema；
- summary length；
- tool result verbosity；
- intermediate explanation。

输出减少以后，下一轮输入通常也会跟着下降。

## Stop Rule 是 Agent 成本控制的核心

一个开放 Loop 必须知道什么时候继续已经没有边际收益。

~~~text
new evidence gained?
state changed?
same tool repeated?
same query repeated?
budget remaining?
success criteria satisfied?
~~~

如果连续几轮没有新 Evidence，系统应该进入 No-progress Detection（无进展检测），而不是等 Token Budget 全部耗尽。

## Timeout 要分层，Retry 也不能冒充 Recovery

~~~text
Model Call Timeout
Tool Timeout
External Job Deadline
Task Wall-clock Budget
Human Approval SLA
~~~

一个 Build 需要十分钟，不代表模型调用也应该等十分钟。

Retry 是同一路径再次执行；Fallback 是换实现或 Provider；Recovery 是先恢复现实状态，再决定下一步。副作用操作尤其不能只因为 Timeout 就重试。

完整恢复纪律见 [长期 Agent 怎样安全执行和恢复](../现代AI工程/09-长期Agent怎样安全执行和恢复.md)。

## 优化必须做前后对比

一个优化动作至少应该比较：

~~~text
before
→ task success
→ p50 / p95 latency
→ input / output tokens
→ tool calls
→ total cost
→ human review

change

after
→ same metrics
~~~

如果 Token 少了 40%，但成功率下降、人工接管增加，不能称为整体优化。

## 一套更稳的优化顺序

~~~text
1. 删除没有业务价值的步骤
2. 把确定性工作移出模型
3. 缩小 Context / Tool Surface
4. 管理 Working Context / History 生命周期
5. 减少无效 Agent Loop
6. Cache 稳定结果
7. Batch / Parallelize 真正独立工作
8. Small-first / Reasoning Routing
9. 再比较模型价格和 Serving 优化
~~~

前几步往往同时改善成本、延迟和可靠性。

最后仍然回到同一个指标：

> **不是每次调用花多少钱，而是稳定完成一个真实 Outcome 总共花多少钱。**
