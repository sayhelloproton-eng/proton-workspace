# AI 视频工作流怎样从单次生成走向可验证产品闭环

AI 视频最容易给人一种错觉：只要模型已经能把 Prompt 变成视频，产品就只差把几个生成 API 串起来。

真正进入创作流程以后，问题很快会变成另一回事。一个故事需要被理解和修改，人物和场景要跨镜头保持一致，分镜要能回到原始剧情，模型和参数会变化，失败需要重试，生成成本要能解释，最后还要有人判断哪些结果值得保留。此时“生成一次视频”只是整个业务链里的一个动作，不是产品本身。

这篇文章把 AI 视频工作流作为一个具体的 AI 业务工程案例，回答三个问题：

~~~text
真正值得解决的产品问题是什么？
→ 怎样用最小纵向切片验证它，而不是一开始建设完整平台？
→ 哪些责任属于视频产品，哪些能力只有在重复复用以后才值得下沉成公共能力？
~~~

当前事实边界先说明：**AI 视频工作流目前仍是研究候选，尚未进入正式业务实现。** 下面描述的是已经形成的产品判断和验证方法，不代表 Story、Character、Scene、Shot、媒体资产平台或自动生成流水线已经落地。

## 真正的问题不是“能不能生成视频”，而是创作过程能不能持续编辑和追踪

一次生成任务可以很简单：

~~~text
Prompt
→ Model
→ Video
~~~

但一个可持续的视频创作过程至少会继续追问：

- 这个镜头来自故事里的哪一段？
- 当前人物为什么长这样，下一镜头怎样保持一致？
- 场景、时间、情绪和镜头语言怎样延续？
- 这次使用了哪个 Provider、模型、参数和参考资产？
- 生成失败以后，是改 Prompt、换模型、换参数，还是重新设计镜头？
- 哪一次结果被人工接受，为什么？
- 花了多少成本，重试是否真的提高质量？
- 最终作品能不能追溯回输入、决策和版本？

如果这些问题都没有稳定答案，系统即使能连续调用多个视频模型，也更像批量生成脚本，而不是一个创作产品。

因此这里真正想验证的产品 Outcome（业务结果：用户最终能观察和验收的价值）不是“模型返回了一个 mp4”，而是：

> **用户能把一个真实故事逐步变成可编辑、可复审、可追踪的镜头与媒体结果，并且知道每一次生成和修改为什么发生。**

这也决定了验证顺序必须从创作结构开始，而不是从最昂贵的视频生成开始。

## 为什么先做纵向切片，而不是先设计完整视频平台

Vertical Slice（纵向切片：从真实输入一路走到一个可验收结果的最小端到端业务路径）适合这类不确定性很高的产品。

横向铺能力很诱人：

~~~text
先建 Story Domain
+ Character Service
+ Scene Service
+ Prompt Platform
+ Media Asset System
+ Multi-Provider Router
+ Review Center
+ Cost Dashboard
~~~

问题是，在真正用户完成第一条创作路径之前，我们并不知道这些抽象是否值得存在。Story、Character、Scene、Shot 看起来都合理，不等于它们已经拥有稳定的产品语义；Provider Router 能被设计出来，也不等于当前真的需要多个 Provider；完整媒体血缘系统更可能在没有消费者时先制造维护成本。

因此更适合的验证路线是四个连续切片：

~~~text
真实故事
↓
Slice 1：故事结构化
↓
Slice 2：分镜与 Shot Plan
↓
Slice 3：单 Provider 真实生成
↓
Slice 4：人工 Review → Retry → Demo
~~~

每一层只购买当前证据要求的复杂度。上一层没有证明价值，就不进入下一层。

## Slice 1：先证明结构化故事真的比模型摘要更有用

第一步不生成图片，也不生成视频。

输入是一段真实故事文本，输出是一组仍然允许人工修改的结构化对象，例如：

| 候选对象 | 它要回答什么 |
|---|---|
| Story | 这一轮创作的整体故事是什么 |
| Chapter | 故事怎样被分成可处理的段落 |
| Character | 哪些人物需要跨场景保持身份和设定 |
| Scene | 事件发生在哪里、什么时候、是什么氛围 |
| Conflict / Plot Point | 哪些情节真正推动故事继续 |

这里最重要的不是 JSON Schema（结构化数据约束）写得多漂亮，而是这些对象是否给人带来新的编辑能力。

如果模型只是把原文换一种格式重新摘要，用户仍然无法稳定修改人物、场景和剧情关系，那么这个切片应该停止，而不是继续建设下游系统。

所以 Slice 1 的验收问题应该是：

~~~text
结构化以后
→ 人是否更容易理解故事？
→ 能否修改一个对象而不重写整段 Prompt？
→ 修改后能否稳定影响后续步骤？
→ 对象是否能追溯到原始故事位置？
~~~

这一层通过以后，才开始有资格讨论哪些对象值得继续拥有稳定身份和版本。

## Slice 2：把被批准的故事结构变成可修改的镜头计划

第二个切片回答的问题是：结构化故事能不能真正进入视觉创作，而不是停在“分析结果”。

输入应该是经过人工确认的故事结构，输出开始进入 Storyboard（分镜：把故事转换成一系列视觉镜头安排）和 Shot（镜头：一个可以独立设计、生成和复审的最小视觉单元）。

一个 Shot 至少可能需要表达：

- 它来自哪一段 Story / Scene；
- 画面主体和人物；
- Camera（机位 / 镜头语言）；
- Duration（预期时长）；
- 场景连续性；
- 人物外观或参考资产；
- 当前版本和修改原因。

这一层最值得验证的是“可编辑性”和“可追溯性”。

如果 Shot Plan 只是模型生成的一长段文本，人每次修改都需要把整段重新生成，那么产品仍然没有获得真正的结构优势。反过来，如果用户可以明确地说“保留故事和人物，只修改第 7 个 Shot 的景别和时长”，并且后续生成只受这次局部修改影响，领域对象才开始表现出工程价值。

这里也不应该提前冻结一套完整 DDD 模型。对象名称只是候选，真正的边界要由多次编辑、失败和生成行为继续验证。

## Slice 3：只接一个 Provider，先证明真实生成事实能被完整保存

第三个切片才进入真实媒体生成。

这里故意只接一个 Provider（外部模型或生成服务提供方），因为第一轮要验证的不是“路由能力”，而是一次生成是否具备完整、可检查的业务事实。

最小链路可以是：

~~~text
Approved Shot
↓
Prompt / Reference Assembly
↓
Provider Adapter
↓
Generation Request
↓
Result / Failure
↓
Cost + Parameters + Evidence
~~~

Provider Adapter（适配器：把外部模型的私有接口翻译成产品稳定语义的边界）在这里非常重要。产品应该关心“生成一个镜头”“使用哪些参考”“得到什么结果”，而不是让某家模型的 request 字段直接变成领域模型。

一次 Generation（生成执行）至少需要留下：

- 对应哪个 Shot 和版本；
- 使用哪个 Provider / Model；
- 输入 Prompt 和 Reference；
- 关键参数；
- 开始和结束时间；
- 成本；
- Result 或 Error；
- 生成资产引用；
- 是否进入后续 Review。

这一步真正要证明的是：**模型调用已经从一次不可追踪的副作用，变成可以比较、复审和重试的业务记录。**

如果 Provider 更换会迫使 Story、Character、Scene、Shot 一起改模型，说明边界仍然错误；如果外部差异主要停留在 Adapter，产品域才保持了自己的稳定语言。

## Slice 4：人工 Review 和 Retry 才真正形成质量闭环

生成结果出现以后，系统仍然不知道它是不是好作品。

AI 视频的质量包含大量主观判断：人物是否像同一个人、情绪是否对、镜头有没有表达剧情、连续性是否被破坏。单一自动分数很难替代创作者责任。

因此最后一个切片不是“自动再生成一次”，而是建立明确的 Review（人工复审：由人判断结果是否可接受以及需要怎样修改）闭环：

~~~text
Generated Result
↓
Human Review
├─ Accept → 进入 Demo / Final Asset
├─ Revise Shot → 回到镜头计划
├─ Revise Prompt / Reference → 重新生成
└─ Reject → 保留失败原因
↓
新的 Generation Attempt
↓
再次比较质量、成本和修改收益
~~~

这样 Retry（重试）才不是“同一句 Prompt 再赌一次”。

每次重试都应该能回答：

- 为什么重试？
- 改了什么？
- 成本增加多少？
- 结果是否真的更好？
- 哪一类修改最值得复用？

这条链把人工审美判断、模型概率输出和工程证据放进了同一个产品循环。

## Story、Character、Scene、Shot 属于产品，不应该提前被平台拿走

AI 视频案例最重要的边界之一，是 Product Domain（产品领域：直接承载用户业务语义和规则的责任范围）和公共平台能力必须分开。

视频产品应该拥有：

- Story、Character、Scene、Storyboard、Shot；
- 创作规则和连续性约束；
- 人工 Review 体验；
- 媒体质量标准；
- 作品版本和业务资产关系。

这些对象只有视频创作语境才知道真正含义。平台如果提前把它们定义成通用对象，就会让公共层开始反向决定产品应该怎样创作。

相反，一些底层责任可能在未来具有跨产品复用价值，例如：

- Task / Execution；
- Identity / Permission；
- Approval；
- Evidence；
- Provider Port / Adapter；
- Cost telemetry；
- Health / Recovery；
- 通用资产引用和版本能力。

但“可能复用”还不等于“现在下沉”。

更健康的顺序是：

~~~text
AI 视频产品先拥有真实业务责任
↓
用四个 Slice 验证
↓
出现第二个真实产品
↓
发现两边重复承担同一工程责任
↓
稳定 Contract 被真实使用证明
↓
再考虑 Library / Shared Service / Platform
~~~

这正是为什么 AI 视频工作流适合作为平台化判断的反例：它逼我们区分“业务对象”和“通用机制”，但不允许我们用未来复用假设提前建设平台。

## 成本和质量必须一起进入产品，而不是等生成完再统计

生成式视频通常比文本调用昂贵得多，重试成本也更明显。

因此产品从 Slice 3 开始就应该把成本和结果绑定，而不是只维护一个总账：

~~~text
Shot
+ Generation Version
+ Provider / Model / Parameters
+ Cost
+ Review Result
→ 这次钱换来了什么质量变化？
~~~

Cost per Successful Outcome（每个成功结果的真实成本）比“单次 API 多少钱”更接近产品价值。

例如某个模型单次更便宜，但平均需要五次重试；另一个模型单次更贵，却两次就能通过 Review。真正应该比较的是最终可接受 Shot 的时间、调用次数、费用和人工修改成本。

同样，质量 Eval（评估：用可重复标准判断结果是否满足要求）也不应该只追求一个总分。可以逐步拆成：

- 人物一致性；
- 场景连续性；
- 镜头意图；
- 叙事正确性；
- 技术可用性；
- 人工接受率；
- Retry 后改善幅度。

这些指标要等真实切片出现以后再校准，不能在产品还没有真实样本时先发明一套复杂评分平台。

## 什么时候应该继续，什么时候应该停止

这个产品候选真正需要的是 Evidence Gate（证据门：只有上一阶段获得足够事实，才允许继续购买下一层复杂度），而不是一张固定 Roadmap。

进入真实业务实现前，至少要具备：

- 一个真实故事样本；
- 明确的第一用户和完成任务；
- Slice 1 的人工修改与验收标准；
- Provider 和预算边界；
- 媒体、版权、隐私和内容安全约束；
- 大型媒体不直接进入公共 Git 的存储策略；
- 明确停止条件。

几个重要停止条件包括：

- Story / Character / Scene 结构化结果没有实际编辑价值；
- Shot Plan 无法被局部修改和追溯；
- 生成成本明显超过验证预算；
- Review / Retry 不能形成可解释改善；
- 为了这个候选产品开始过早扩张公共平台，反而拖慢主线。

停止不代表产品失败。它说明当前证据不足以继续购买下一层复杂度。

## 这个案例最终验证的不是“会不会做 AI 视频”

AI 视频工作流之所以值得保留在业务工程知识里，不是因为视频生成本身特殊，而是它同时压中了几乎所有 AI 产品常见矛盾：

~~~text
概率模型很强
但业务对象必须稳定

Provider 变化很快
但产品语义不能跟着漂

自动生成很方便
但质量责任仍然需要人

每次调用都能成功
但成功不等于最终作品有价值

平台抽象看起来很诱人
但真实复用必须等第二个消费者出现
~~~

所以这个案例真正提供的是一条产品验证方法：

> **先从用户能完成的最小纵向结果开始，把领域对象、生成事实、人工复审、成本和证据连成闭环；只有闭环被真实使用证明以后，再决定哪些东西值得长期建模，哪些能力值得共享。**

当前 AI 视频工作流仍停在研究候选阶段。它没有实现完整视频编辑器，没有冻结全部领域对象，没有建立媒体资产平台，也没有证明多 Provider 路由或自动质量评估已经成立。

保留这些边界，比把一张完整架构图提前画出来更重要。
