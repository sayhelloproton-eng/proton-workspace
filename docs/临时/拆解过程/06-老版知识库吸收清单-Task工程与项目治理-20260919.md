## 为什么最终只新增两篇，而不是重建旧平台架构树

旧 04 + 07 实际混合了三类问题：

1. 平台总体责任 / Control Plane；
2. Goal → Plan → Task → Execution → Handoff 的 Task 工程；

第一类已经被当前 ProFlow Control Plane、现代 AI 平台和复杂度边界文章完整承接，再新写“总体架构”只会制造重复 Owner。

因此本轮只新增真正缺失的两个稳定主题。

## 新 Owner 1：Task 工程

《Task 工程：怎样把目标冻结成可执行、可移交、可验证的长期任务》最终承担：

- Goal / Plan / Task / Execution / Session / Result / Evidence 分层；
- Problem Framing 与 Plan Freeze；
- Decision Tier：局部执行、架构、产品、高风险决策分别回到正确 Owner；
- Task Decomposition：按独立责任、风险、验收拆分，不按步骤数量拆分；
- Task Contract 的 Goal、Scope、Allowed / Forbidden、Input、Role、Capability、Context、Approval、Acceptance、Evidence、Stop、Git Policy、Budget；
- Guidance Tier 与 Execution Authority 分离；
- Execution Gate：合同、Source、Context、Capability、Approval、Acceptance、Workspace、Budget 未满足时不得偷偷降级继续；
- ProFlow Task / Node / TaskRoleBinding / Worker / Conversation / runNo 的具体分层；
- Handoff / Receipt；
- Execution Lane 与 Workspace / Worktree / Lease；
- Executor 选择按不确定性、风险、Capability、成本和验证方式，而不是把 Provider 名当 Role；
- Result / Deterministic Validation / Semantic Review / Completion 分层；
- Closeout 保留最终状态、Acceptance、Evidence、Side-effect Readback、Release / Migration、Follow-up、最终 Source；
- Reopen 保留 Task Identity；
- 并行 Task 必须隔离并预先定义 Integrator；
- Integration 后必须回到 Git / Remote / Registry / Runtime 等真实 Owner Readback。

## 新 Owner 2：Agent 项目治理

《Agent 项目治理：怎样从 Task 事实形成阶段基线，而不是靠进度汇报》最终承担：

- Task State 与 Project State 分离；
- Reporting Window；
- Project State 必须聚合 Git / Task / Test / Release / Installed / Runtime / Browser / External Reality；
- completed / in_progress / blocked / planned / placeholder / superseded / retired / unknown；
- accepted / planned / implemented / verified / released / adopted 分层；
- Drift / Gap / Issue / Risk / Dependency 分离；
- Decision Request 的问题、事实、选项、影响、建议依据、不决定后果与最迟决策点；
- Stage Gate 不是“测试全绿”，而是阶段完整 Evidence Gate；
- 上游 PASS 不能冒充下游 Reality；
- Baseline Candidate / Baseline Freeze；
- Baseline 只生成 Context / Roadmap 更新候选，不自动改写其它 Owner；
- 多窗口共享 Context 必须在最新共同基线上集成；
- 百分比只作为沟通估计，必须说明分母；
- 项目汇报可按受众压缩，但底层范围 / Evidence / Risk / Drift / Decision / Readback 不能消失；
- Project Governance Agent 只生成 Candidate，不拥有最终 Baseline Authority。

## 明确退休、不迁移为当前架构的旧设计

- 旧 ai-agent-platform 七大 Bounded Context 必须全部物化；
- Platform Registry / Publisher 作为所有资产的硬依赖；
- 通用 Task / Context / Approval / Evidence Store 在真实复用前提前平台化；
- Executor Router / Lane Registry 因接口存在就宣称动态路由；
- MVP-0～MVP-7 继续作为当前 Roadmap；
- Opportunity / Product Candidate / Specialized Workflow Plug-in 作为统一平台对象；
- 固定 Task Contract / Checkpoint 大 Schema 作为跨项目唯一实现；
- 自动 Impact Analyzer、统一 Projection Registry 和严格多渠道映射。

这些机制只有在多个真实消费者再次证明同一维护压力时才重新评估。
