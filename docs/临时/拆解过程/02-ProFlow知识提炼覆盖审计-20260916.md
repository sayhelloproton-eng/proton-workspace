# ProFlow 知识提炼覆盖审计｜2026-09-16

这份文档是 ProFlow 正式知识文章重写时的内部控制材料，不进入飞书正式知识目录。

目的只有一个：**证明“提炼”是在重组和去重，而不是把历史研究中的独有事实、事故、trade-off、证据和边界删掉。**

在本审计被接受以前，`docs/项目与实践/ProFlow/` 中的旧材料不得因为“已经有正式文章”而批量删除。

## 1. 三层材料的职责不能混

```text
repos/proflow/spec/**
+ repos/proflow/docs/phase4/**
= 当前工程真源 / 当前设计与验收材料
= NOT_REPLACEABLE


docs/项目与实践/ProFlow/**
= 历史研究、演进、事故、时间线、证据索引
= SOURCE MATERIAL / DELETION_REQUIRES_COVERAGE


docs/知识库/ProFlow/**
= 面向长期阅读的正式主题文章
= DISTILLED KNOWLEDGE
```

正式知识文章无论写得多完整，都不能替代当前 Source、Spec、Test、Runtime Evidence。`spec/` 和 Phase 4 文档不进入“旧文章可删”判断。

## 2. 什么叫“信息已经被消费”

不能用字数、标题数、关键词出现次数判断。

一个重要 Decision Episode 至少包含：

```text
旧假设 / 旧路线
→ Trigger / Failure / Bottleneck
→ Decision
→ 新机制
→ Trade-off
→ Evidence / evidence strength
→ Current boundary / safe claim
```

旧材料中的有效信息按以下维度检查：

| 信息类型 | 删除前必须满足 |
| --- | --- |
| 历史日期 / commit | 重要转折仍能追溯；不要求把所有 SHA 堆进正文，但关键锚点不能消失 |
| 失败 / 事故 | 读者仍能理解为什么改，而不只看到最终方案 |
| 机制 | 新文章能解释系统怎样工作，不只是下结论 |
| trade-off | 被放弃方案的价值与代价仍可理解 |
| 反例 | 能解释哪些“看起来合理”的做法为什么被拒绝 |
| Evidence strength | 不把 Owner 确认、派生判断、当前源码事实全部写成同等证据 |
| 当前边界 | 历史状态、目标状态、当前已验收状态不混 |
| Do-not-repeat | 旧路线如果承担防止重复踩坑的功能，必须有新落点 |

如果只保留一句“后来采用 X”，但丢掉“为什么不是 Y、Y 曾怎样失败、证据是什么”，判定为 `PARTIAL`，不能删除来源。

## 5. Evidence limitation 不能在提炼时消失

旧 90/91 有一项非常重要的作用：阻止把项目故事讲得比证据更漂亮。

以下说法继续禁止无证据升级：

- “Token 从来不是瓶颈”或可量化地证明 Context 成本下降多少；
- “AI 让开发成本 / 时间下降 X%”；
- “Multi-Agent 一定优于 Single-Agent”；
- “手机模型已经证明生产成本收益是多少”；
- 把某个 09-03 工作树中的 Tasks UI 形状写成今天不可变化的最终产品 identity；
- 把底层 targeted proof 写成完整 Phase 4 Runtime / Acceptance PASS；
- 把“有 Test Plan / RED-first Gate”夸成“每一个功能都有独立 Git RED commit”；
- 把 `UNKNOWN + reconciliation` 宣传成 exactly-once 或通用分布式事务。

正式文章已经在相应位置写回这些边界；本审计仍保留它们作为 deletion guard。

## 6. 对比上一版：为什么判定上一版不合格

上一版 7 篇正文把约五千行研究材料压到约千行。压缩本身不是问题，问题是多个 Decision Episode 被压成一句结论。

典型丢失包括：

```text
“Deployment 变成 Module 自治”
但没有六命令→七命令、为何 start/setup 仍有问题、删除哪些重复 truth

“手机模型塑造 Capability Runtime”
但没有 FAST/REASON 原本就存在、真实 latency/busy/JSON/Thinking 限制、单 Lane 因果

“Browser 变成 Reality Adapter”
但没有 scroll 观察副作用、delivery terminal、双控制面、Harness 假失败

“Executable Project Memory”
但没有最重要的反例：第一次公共上下文治理曾因压缩过度丢掉执行记忆
```

这种写法虽然更短、更顺，但读者无法回答“为什么”“怎么失败”“代价是什么”“证据在哪”。它不满足技术写作 Skill 对信息维度和因果完整性的要求。

本轮的修正不是简单把字数加回来，而是按 Decision Episode 恢复这些维度。

## 7. 删除资格与实际删除是两件事

旧 01～17 在本轮可以进入 **内容层删除候选**，因为它们的核心独有知识已经分别进入正式主题文章。

但真实删除仍需满足：

```text
1. 用户审阅正式 7 篇并接受内容质量
2. 本覆盖表没有被发现的 missing unique fact
3. 旧文档不再承担其它项目流程 / 引用 / 审计 Owner 职责
4. 必要的 evidence ref 已经留在 Git / spec / source 或正式文章中
5. 逐篇或按明确批准的批次删除，而不是因为“已提炼”自动清空
```

90、91 和旧 README 还承担控制 / 审计入口角色。本审计理论上可以接替其中一部分，但在用户确认之前标记 `CONTROL_RETAIN`，不自行删除。

## 8. `spec/` 与 Phase 4 永远不进入这次删除范围

必须再次强调：

```text
repos/proflow/spec/**
repos/proflow/docs/phase4/**
```

是当前工程设计、Contract、测试、规划与验收材料。正式知识文章只是对它们和历史材料的知识投影，不具备替换工程真源的资格。

即使未来正式文章完全覆盖历史研究，Spec / Phase 4 的删除仍只能由各自工程治理规则决定，与知识库提炼无关。
